# 03. AI 解析とシナリオ生成

本システムの心臓部。既存の作業手順書を、撮影現場でそのまま使えるシナリオへ変換する。処理は概念的に **「構造化 → 作業分解 → シナリオ生成」** の段階を踏む。

## 3.1 パイプライン全体

```
作業手順書（Excel/PDF/画像）
      │
      ▼  ① 構造化（OCR + 抽出）
統一フォーマット JSON（header + sections/steps）
      │   ・work_process（手順）
      │   ・work_points / safety_points / quality_points / pm_points（急所類）
      ▼  ② 作業分解（プロンプト A）
作業分解表：1 動作 1 行、手順と急所を分離
      │   | No | 作業手順（物理動作） | 急所（判断基準・数値・注釈） |
      ▼  ③ シナリオ生成（プロンプト B）
撮影シナリオ：カット単位に垂直展開
          | カット番号 | 作業/急所 | シーン | ヨリ/ヒキ | 撮影のポイント | ナレーション | 字幕①/② |
```

## 3.2 プロンプト A：作業分解（SOP 再構築）

**役割**: 製造現場の作業標準化エキスパート。資料を「読む」のではなく、作業者の「体の動き（動詞）」ごとに **1 行 1 動作** で解体・再構築する。

**主要ルール**（`汎用プロンプト：製造現場用 標準作業手順書（SOP）再構築.docx` / `AI-CUIE プロンプト案_0424.docx`）:

1. **一動作・一 No の原則（最重要）** — 1 文に複数の動詞（確認する・廃棄する・拭く…）があれば必ず行を分けて別々の No を振る。
2. **「手順」列の定義** — 「〇〇の清掃」のような括りは禁止。「何をどうする」という物理的な動詞のみ。
3. **「急所」列の定義** — 動作の具体的な判断基準（数値・対象物・良否の境目）と資料の注釈のみ。手順に書くべき動作を急所へ逃がさない。
4. **急所ごとの行分離** — 1 手順に複数の急所があれば、急所ごとに 1 行（1 セル）に分ける。1 セル内に「・」で複数並べない。2 つ目以降の急所行は No・手順セルを空欄にし、右側の急所列だけが複数行に分かれる見た目にする。
5. **資料への忠実性（JIS）** — 指差呼称を含め、資料にない言葉は一切付け加えない（捏造厳禁）。

> **裏付け（[07章](07_知見の理論的裏付け.md#74-1動作1手順の裏付け動作の細分化による標準化)）**: 「1動作1行」への細分化は標準化に効く。ディズニーランドの撮影指導手順書は「撮る」ではなく「両手で受け取る」「構図を決める」と**動作を細分化して短期間のスキル標準化を実現**〔「最強の一言」Webコピーライティング p.175-176〕。また商品説明を長文→箇条書きに変えるだけで成約率が20.5%向上した例もある〔同 p.177〕。箇条書きは把握しやすさから**7項目まで**が目安〔テクニカルライティング入門講座 p.143〕で、1手順あたりの急所数の設計指針になる。

出力表フォーマット:

| No | 作業手順（一つの物理動作・動詞） | 急所（判断基準・数値・資料の注釈） |
| :-- | :-- | :-- |
| 1 | 非常停止 SW を押す | ・指差呼称を行い「非常停止ヨシ」を確認する |
| | | ・ロックを確認する |
| 2 | 操作電源キー SW を切る | ・指差呼称を行い「操作電源切りヨシ」を確認する |

## 3.3 プロンプト B：シナリオ生成（動画構成案への垂直展開）

**役割**: 製造現場の動画教育コンサルタント。作業分解表を、撮影現場でそのまま使える動画構成案（シナリオ）へ垂直展開する。

**主要ルール**:

1. **ナンバリング** — カット番号は全体通し番号。「作業または急所」欄は、手順（親行）は「手順 1」「手順 2」、急所（子行）は「急所 1-1」「急所 1-2」と手順番号に対応した枝番で表記。
2. **シーン列の具体化** — 区分を見なくても撮影者が「何を撮るべきか」を単体で理解できるよう、主語・動作を補って具体的に書く。
3. **ヨリ / ヒキ** — 手順は原則「ヒキ（全体像）」、急所は原則「ヨリ（接写）」。撮影のポイントには「ドアップで」「真横から」など、急所を射抜く具体的なアングル・演出を指示。
4. **ナレーションの事務化** — 語尾は「〜します」「〜であることを確認します」に統一。指示的な「〜してください」は禁止。
5. **字幕の出し分け（最重要）**:
   - **字幕①（名称・数値）**: 最低限の情報。固有名詞・数値のみ。なければ「なし」。
   - **字幕②（完全情報）**: 音声がなくても内容が 100% 伝わる情報量。字幕①を内包し「何を・どうする」を明確にした言い切り型の短文。

> **文体ルールの裏付け（[07章](07_知見の理論的裏付け.md#75-手順文字幕ナレーションの文体ルール)）**:
> - **ナレーション語尾の統一**（ルール4）← 箇条書きの文末表現・句点の有無はリスト内で統一する〔テクニカルライティング入門講座 p.133-134〕。
> - **字幕①＝簡潔・単一情報**（ルール5）← マイクロコピーは一息で読める簡潔さを保ち、一度に2つ以上のことを伝えない〔ザ・マイクロコピー p.60〕。「5文字から40文字までです」→「5〜40文字」のように圧縮する〔UXライティングの教科書 p.184〕。
> - **字幕①／字幕②の二層**← **テロップ**（解説・情報の文字）と**字幕**（セリフ翻訳・聞き取り補助）の区別に対応づけられる〔動画制作の教科書 p.122〕。
> - **事務的・指示的ナレーション**← マニュアル動画は本題を先に伝える「報道」型が適切で、情報を遅らせる「演出」型とは対極〔動画の文法 p.124〕。

出力表フォーマット（8 列）:

| カット番号 | 作業または急所 | シーン | ヨリ／ヒキ | 撮影のポイント | ナレーション | 字幕① | 字幕② |
| :-- | :-- | :-- | :-- | :-- | :-- | :-- | :-- |

## 3.4 AI モデル検証（2026-03-06）

`検証/20260306/` は、手順書（画像/PDF）からの **構造化精度** と **シナリオ生成品質** を、複数エンジンで比較した検証結果。

### 検証対象エンジン

| エンジン | 位置づけ |
| :-- | :-- |
| **Claude** | LLM による OCR＋構造化 |
| **OpenAI** | LLM による OCR＋構造化 |
| **Gemini** | LLM による OCR＋構造化 |
| **Yomitoku** | OCR 専用エンジン |

### 成果物の構成

- `unified/{claude,openai,gemini,yomitoku}.json` — 手順書を統一スキーマに構造化した結果。
  - `header`: 文書名・作業名（例「グラインダー研削作業」）・想定リスク・保護具・工具・作成者・改訂履歴。
  - `sections[].steps[]`: `no` / `work_process`（手順）/ `illustration_notes`（図注）/ `work_points`・`safety_points`・`quality_points`・`pm_points`（急所類）。
- `scenarios/scenario_{engine}.{txt,xlsx}` — 上記から生成したシナリオ（初版）。
- `scenarios/scenario_v2_{engine}.{txt,xlsx}` — 改良版プロンプトによるシナリオ。`v2` ではシナリオの手前に**バリデーション結果**（マニュアルとして有効か、文末解析/語彙解析/構造解析、作業数、仮タイトル一覧、ノード数＝手順数/急所数、分割要否）を出力する構成。

### 観察された差異（構造化 JSON の比較より）

同一手順書に対し、エンジンごとに読み取り精度が異なる。実例（No.1「主スイッチの解放」）:

| エンジン | 手順の読み取り | 備考 |
| :-- | :-- | :-- |
| OpenAI / Gemini / Yomitoku | 「主スイッチの解放」 | 概ね正しく読めている |
| Claude | 「モスイッチの解放」 | OCR 誤読あり |

- 保護具・改訂履歴の承認者など細部の読み取りは各エンジンでばらつきがある（例: 承認者名を役職ごとに分解できるか、括りで返すか）。
- 図注（`illustration_notes`）を拾えるかもエンジン差が大きい（Gemini は「品 2-2 スキマ 5mm 以下」等を拾えている一方、拾えないエンジンもある）。

> **示唆**: 手順書は画像/PDF 由来のため OCR 誤読が避けられない。構造化とシナリオ生成は AI に任せつつ、**PC 側の「編集する」機能で人が最終確認・修正する**運用が前提。プロンプト（作業分解・シナリオ）の忠実性ルール（捏造禁止）は、この誤読リスクを踏まえた設計になっている。この「現場が最終的に確認・修正する」運用は、**標準は生産現場の人間が自らつくり上げ納得するもので、上からのお仕着せであってはならない**というTPSの原則とも一致する〔トヨタ生産方式 p.30, p.101〕（[07章](07_知見の理論的裏付け.md#73-標準作業の思想手順書現場が納得して作るもの)）。

## 3.5 生成シナリオの実例（scenario_v2_claude）

「グラインダー研削作業」から生成された v2 シナリオの冒頭。カット番号・手順/急所・映像説明・撮影方法・ナレーション・字幕を備え、冒頭に導入カット（作業目的の要約）、末尾に総括カットを自動で挿入している。

```

3  手順1   使用前点検の流れを一巡                   俯瞰(ヒキ)  使用前点検として主要箇所を順に確認します。
4  急所1-1 モスイッチ前で指差呼称する手元のアップ      中間(チュウ) モスイッチが「切」であることを指差呼称で確認します。
...
24 -       総括の俯瞰（安全ポイント再掲）            俯瞰(ヒキ)  作業の要点を振り返ります。
```
