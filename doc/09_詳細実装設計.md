# 09. 詳細実装設計（How）

[08_システムアーキテクチャ設計](08_システムアーキテクチャ設計.md)（概念設計＝What/Where）を受けて、本章は **実装の How** を詰める。テンプレートの実 API を確認した上での具体設計であり、判断の根拠と、実装前に潰すべき技術的トレードオフを明記する。

**確認済みのテンプレート実 API（設計の前提）:**
- LLM 実行: `Prompt::load('name', [...])->withMetadata(['organization_id'=>…, 'user_id'=>…, 'subject_type'=>…, 'subject_id'=>…])->executeSync()`。`PromptExecutionCompleted/Failed` → `llm_call_logs`（org + polymorphic subject で attribution）。
- チケット: `TicketLedgerService::reserve(org, amount): TicketReservation` → `commit(r)` / `release(r)`。**単一台帳（種別なし・amount 指定）**、**予約 TTL = 30 分**、stale 解放 cron あり。
- Quota: `QuotaService::check(org, QuotaKey::X, currentCount): void`（超過で例外→402）。config/quota.php の plan→limits。
- Web 資源: 薄い Controller（`resolveCurrentOrganization` → `resolveOrganizationProject`（認可前 404）→ `Gate::authorize` → relation 経由 create → `back()->with(...)`）。FormRequest に `ProhibitsProtectedKeys`。子∈親は route `scopeBindings()`。
- キュー: `database` 既定（sqs/redis 可）。**broadcast なし → 非同期の状態は HTTP ポーリング**。
- ストレージ: `s3` disk（`AWS_ENDPOINT` 可変 = MinIO で local 可）。

## 9.1 リポジトリ初期化（コピー手順）

1. テンプレートをクローン → リモート張り替え → リネーム（composer name / DB 名 / api-key prefix / app name）。
2. `./init.sh`（install / key:generate / migrate / pnpm build）→ `composer dev` で起動確認。
3. `AGENTS.md` の North Star（使命）を記入。`DESIGN.md` のテーマ token を差し替え。
4. ロールを rename（§9.9）、`config/quota.php` と `QuotaKey`・`PlanSeeder` を本プロジェクト値に（§9.8）。
5. サンプル `Item` は §9.3 の実リソース実装が済んだら削除。

## 9.2 データモデル詳細

命名は英語（テンプレ規約）、日本語概念を括弧で併記。すべて Project 配下（[08 §8.2](08_システムアーキテクチャ設計.md#82-ドメインモデル--tenancy-マッピング2)）。

### Category（カテゴリ）— Project 配下マスタ
`id, project_id(FK,protected), name, sort_order, timestamps`。削除時、所属 VideoManual は `category_id = null`（「未分類」）。

### VideoManual（動画マニュアル）— Project 配下
```
id, project_id(FK,protected), category_id(FK nullable), created_by(protected),
title, status(enum: draft/analyzing/ready/rendering/published),
total_length_ms(nullable, 派生), timestamps
```
`status` はワークフロー状態。`created_by` はサーバ導出（payload 不可）。

### SourceDocument（手順書）— VideoManual 配下
```
id, video_manual_id(FK,protected),
file_path(S3 key), original_name, mime, size_bytes,
extracted_json(json nullable: 統一スキーマ), timestamps
```
AI 解析の入力ファイルと抽出結果を保持（[03章](03_AI解析とシナリオ生成.md)の unified JSON）。

### Cut（手順/急所）— VideoManual 配下 ★設計の要
```
id, video_manual_id(FK,protected), parent_cut_id(FK→cuts nullable,protected),
type(enum: step 手順 / point 急所),
sort_order(int),                       -- 同一 (manual, 親スコープ) 内で一意
scene(text), shot_type(enum: hiki ヒキ / yori ヨリ),
shooting_point(text nullable),          -- 撮影のポイント
narration(text),                        -- 語尾統一（プロンプト規約）
subtitle_primary(string nullable),      -- 字幕①（名称・数値）
subtitle_secondary(text),               -- 字幕②（完全情報）
adopted_take_id(FK→takes nullable),     -- 採用テイク
material_type(enum nullable: video/still),
static_display_seconds(int nullable),   -- 静止画表示秒
cut_length_ms(int nullable, 派生),      -- 尺（ナレーション尺 vs 素材尺の max）
timestamps
```
**親子構造**: `type=point`（急所）は `parent_cut_id` で `type=step`（手順）にぶら下がる。手順は `parent_cut_id=null`。
**派生値（DB に持たない）**: 「カット番号」＝マニュアル内の通し順、「作業/急所ラベル」（手順N / 急所N-M）＝手順の順序 index + 急所の子 index。表示・レンダリング時に走査して算出。
**順序**: フラットな `sort_order`。手順を並べ替えると配下の急所ブロックごと移動。D&D は小規模（数十カット）なので、保存時にサーバが `sort_order` を再採番（gap 法: 10,20,30…）。

### Take（テイク）— Cut 配下
```
id, cut_id(FK,protected),
client_take_id(string, 端末生成 ULID),  -- (cut_id, client_take_id) UNIQUE = 同期の冪等キー
video_path(S3 key), thumbnail_path(S3 key nullable),
duration_ms(int nullable),
status(enum: uploading/processing/ready/failed),
comment(text nullable), captured_at(timestamp nullable),
sort_order(int),                        -- 採用候補順（先頭=既定採用）
timestamps
```
採用は `Cut.adopted_take_id`。「先頭テイク=採用候補」は `sort_order` で表現。

### AnalysisJob / RenderJob（非同期状態）— VideoManual 配下
```
id, video_manual_id(FK,protected), source_document_id(FK nullable),
kind(analysis/render), status(queued/running/succeeded/failed),
step(nullable: extract/decompose/generate | tts/compose/concat),
ticket_reservation_id(nullable), result_json(nullable), error(nullable),
progress(int 0-100 nullable), output_path(S3 key nullable, render), timestamps
```
PC は本レコードの status を**ポーリング**して「解析中…」「合成中…」を表示（broadcast なし）。

### メディア実体の扱い
汎用 polymorphic media テーブルは作らない（[08 §8.2](08_システムアーキテクチャ設計.md#82-ドメインモデル--tenancy-マッピング2) の多態回避）。ファイル参照は所有モデルの `*_path` 属性、実体は S3 の Project prefix（§9.5）。

## 9.3 ドメイン CRUD 実装（Item 見本のトレース）

Category / VideoManual / Cut / Take を Item と同じ 15 点セットで作る（[08 §8.2](08_システムアーキテクチャ設計.md#各リソース追加時の機械的手順item-見本のトレース)）。要点のみ:
- `MassAssignmentProtectedKeys` に `video_manual_id / cut_id / category_id / parent_cut_id / adopted_take_id / created_by` を追記。
- nested route: `/projects/{project}/manuals/{manual}/cuts/{cut}/takes/{take}` を `scopeBindings()` で解決。全階層を `NestedRouteIdorDefenseTest` inventory に登録（認可前 404）。
- Policy は親委譲（Cut→VideoManual→Project→org 所属）。直 fetch 禁止。

> **例外（Cut のシナリオ編集は per-row CRUD にしない）**: §9.4 参照。

## 9.4 シナリオ編集の実装（ドキュメント単位保存）★divergence

[04章](04_PCサイト機能仕様.md)のシナリオ編集は「行追加/削除/D&D 並べ替え/Undo/Redo、手順削除で配下急所も削除」。これらは**1 行ずつの CRUD では原子性と Undo/Redo が破綻**する。

**決定**: シナリオは**ドキュメント単位**で編集・保存する。
- PC 編集画面（Svelte）は cuts の**作業コピー**を保持。追加/削除/並べ替え/文字編集はすべてクライアント state に対して行い、Undo/Redo は編集操作スタックで実現（サーバ往復なし）。
- 「更新する」で **`PUT /projects/{project}/manuals/{manual}/scenario`** に cut 配列全体を送信。Service が 1 トランザクションで reconcile（既存 id は update、新規は create、消えた id は delete、`sort_order`/`parent_cut_id` 再構築）。
- 不変条件は維持: `video_manual_id`/`parent_cut_id` はサーバが URL と親子関係から導出（payload の FK は無視/422）、cross-manual の cut id 混入は 404、authz は保存前。
- **これは Item の per-row パターンからの逸脱** → `docs/template-divergence.md` に logic-driven（Undo/Redo + 親子カスケードの原子性要件）として登録する。

離脱警告（未保存で遷移）はクライアント state の dirty 判定で実装（[04章](04_PCサイト機能仕様.md)）。

## 9.5 メディア（アップロード/ダウンロード）

### アップロード（スマホ・PC 共通、大容量は直 S3）
1. `POST .../cuts/{cut}/takes/upload-url` に `{content_type, size, client_take_id}`。サーバは:
   - `QuotaService::check(org, MaxStorageBytes, 現使用量+size)`（超過 402）。
   - S3 キーをサーバ生成（`orgs/{org}/projects/{project}/manuals/{manual}/cuts/{cut}/takes/{ulid}.mp4`）。
   - **署名アップロードチケット**（HMAC of {key,cut_id,org,exp}）＋ S3 presigned PUT URL を返す。
2. クライアントは presigned URL で**直接 S3 へ PUT**（アプリサーバ非経由）。
3. `POST .../cuts/{cut}/takes` に `{署名チケット, client_take_id, duration_ms, ...}`。サーバは HMAC 検証→キー導出（**クライアント提供のキーを信用しない**）→ `HeadObject` で実在確認 → relation 経由で Take 作成（`status=processing`）。
   - 冪等: `(cut_id, client_take_id)` UNIQUE。再送は既存 Take を返す（同期の二重登録防止）。

### 後処理（transcode / thumbnail）
Take 作成でキュー投入 → ffmpeg で正規化（H.264/mp4）＋サムネイル生成 → `status=ready`。ready 前は採用不可（[04章](04_PCサイト機能仕様.md)「処理中」）。

### ダウンロード（同期時の採用テイク取得）
採用テイクは `Storage::disk('s3')->temporaryUrl($key, now()->addMinutes(…))`（署名付き期限付き）で配布。DL 済みテイクは端末側で「非削除・アップロード対象外」（[05章 §5.3](05_スマホアプリ機能仕様.md#53-同期の要点重複防止ロジック)）。

## 9.6 AI パイプライン実装

### プロンプト（YAML + Prompt クラスのペア、[08 §8.6](08_システムアーキテクチャ設計.md#86-llm-機能マッピング6)）
`sop-extract`（vision・マルチモーダル）→ `work-decomposition` → `scenario-generation`（+任意 `scenario-validation` / `translation`）。手順書テキスト等 untrusted は `UserInput` 型経由のみ。

### 構造化出力＋検証
各段の出力は JSON。**PHP 側で厳格 DTO に検証**（`webmozart/assert` or spatie-data）してから次段へ。壊れていれば**有界リトライ（最大 2 回）**、それでも不正なら job 失敗。[03章](03_AI解析とシナリオ生成.md)の unified スキーマ／v2 バリデーションはこの検証段に対応。

### 非同期ジョブ + チケット（TTL 制約への対処）★
- 起動: `POST .../manuals/{manual}/analyze` → **残高の事前チェック**（0 なら即 402、UX 用）→ `AnalysisJob(queued)` 作成 → キュー投入。**この時点ではチケットを予約しない**。
- ジョブ実行時（ワーカー内）に **`reserve(org, COST_ANALYSIS)` を実行**（authoritative）。残高不足なら `AnalysisJob=failed('残高不足')`。
  - 理由: 予約 TTL=30 分。**enqueue 時に予約するとキュー滞留で TTL 失効**しうる。予約〜commit をジョブ実処理時間（<30 分）に収めるため、予約はジョブ開始時。
- 3 段の LLM 呼び出しを順に実行（各 `withMetadata([... subject=AnalysisJob ...])` で llm_call_logs に attribution）。成功で `commit(reservation)`、Cut 群を生成、`VideoManual.status=ready`。例外で `release(reservation)`、`status=failed`。
- **再解析の安全性**: cut が既にある manual への再解析は既存 cut を上書きしない（新規 job で `result_json` に保持、ユーザーが明示「再生成」時のみ置換＝警告付き）。トリガー API は `Idempotency-Key` 配線。

### 進捗表示
`AnalysisJob.status/step/progress` を GET する status route を PC がポーリング（broadcast なし）。

## 9.7 動画合成（レンダリング）★divergence・最重要作り込み

`VideoComposer` インターフェースの背後に実装を隠蔽（将来 AWS MediaConvert 等へ差し替え可能に）。初期実装は **専用キュー（`media`）＋ffmpeg ワーカー**。

> **v1 スコープ（2026-07-10 確定）**: **字幕のみ**。合成音声ナレーション（TTS）は v1 に含めず、後続フェーズで追加する（`TtsProvider` 差し込み口を用意して先送り。§9.7 末尾）。narration テキストは v1 でも保存・字幕表示に使う（音声化しないだけ）。

### RenderJob パイプライン（v1・字幕のみ）
1. `reserve(org, COST_RENDER)`（ジョブ開始時。§9.6 と同じ TTL 対処）。
2. カットごと:
   - **尺算出（v1）**: `cut_length = material_ms`（採用テイクの尺）。静止画は `static_display_seconds*1000`。
   - **クリップ合成**: 採用テイク（or 静止画）＋字幕焼き込み（既定 字幕②）。音声トラックは採用テイクの生音のみ（無音でも可）。
3. 全クリップ連結 → 最終 mp4 → S3（`output_path`）。`total_length_ms` 更新。
4. 多言語（`feature_multilang`）: 字幕を言語別に差し替えて出力（v1 は字幕のみのため音声再合成は不要）。
5. 成功で `commit`、`status=published`。失敗で `release`、`failed(reason)`。ffmpeg 段は決定的、出力キーは version 付きで再実行安全。

### プレビュー（テイク未登録でも再生）★チケット非消費
[02章](02_システム全体像.md#プレビューの特徴)。同一パイプラインを**プレースホルダ映像（黒/静止）＋字幕**で回す軽量経路。編集中確認は中核 UX のため **`video_render` チケットを消費しない**（最終「完成/DL」レンダのみ消費）。乱用防止は rate limit で。

### TTS 追加時の差し込み（v1 では未実装）
将来ナレーション音声を足すときは、レンダパイプラインに `TtsProvider` を挿すだけで済む形にしておく（`VideoComposer` と同じ抽象化方針）:
- カットごとに `narration → 音声`。`hash(text, lang, voice)` でキャッシュ（S3）。
- 尺算出が `cut_length = max(narration_audio_ms, material_ms)` に変わる。
- `TtsProvider` の実装は **自前ホストの OSS TTS（推奨: VOICEVOX / Kokoro 等を Docker で HTTP サービス化）** か、クラウド TTS（Azure/Google 等）を差し替え可能に。外部呼び出しなら `config/ssrf-pin.php` に pin。
- OSS TTS は日本語品質・商用ライセンス可のものを選定する（VOICEVOX＝各話者のクレジット条件、Kokoro＝Apache-2.0 等）。詳細は選定時に確認。

### TTL への注意（render は長い）
予約 TTL=30 分。長尺マニュアルの HQ レンダが 30 分に迫る場合の扱いは**要判断**（§9.11）: (a) レンダ時間を 30 分未満に収まる設計（並列化・尺上限）＋TTL 内 commit、(b) TTL を延長 config 化、(c) render を分割 job にして各々短時間で commit。初期は (a)＋尺上限で回避する想定。

## 9.8 課金の具体

- **チケットは単一台帳**（種別なし）。operation ごとに **消費 amount を変える**: `COST_ANALYSIS=1`、`COST_RENDER=N`（尺/解像度で係数）。付与は `PlanSeeder` の `monthly_ticket_grant`、購入は `grantPurchased`。
- **Quota**（`config/quota.php` + `QuotaKey` case 追加）: `max_projects`(既存)/`max_members`(既存)/`max_manuals`/`max_storage_bytes`/`feature_multilang`(bool)。チェックは `QuotaService` のみ、超過 402。プラン名分岐禁止（能力は値で表現）。
- ゲートは `BillingAccess` + `require-active-subscription` middleware（業務 route group）。

## 9.9 ロール・権限・認証

- ロールは rename のみ（[08 §8.3](08_システムアーキテクチャ設計.md#83-ロール権限マッピング3)）: project_admin=編集者、project_member=撮影者。org 3 ロール維持。
- permission enum: `ManualPermission`（create/edit/delete/render/download）/ `ShootingPermission`（capture/upload/adopt）/ `CategoryPermission`。判定は常に `$org->laratrust_team_id` 明示。
- **撮影アプリ認証（PWA/Web, 同一オリジン）**: first-party のため **通常のセッション認証**（Fortify ログイン）。撮影 PWA は同一ドメインで動き、`/api/v1` 系エンドポイントを session guard（web）で叩く（または Inertia 直）。テンプレの `auth:api-key,api-oauth`（機械/サードパーティ用）は温存し、撮影 PWA には使わない。カメラは `MediaRecorder`、オフライン一時保持は Service Worker + IndexedDB。ability 相当の粒度は Policy（撮影者ロール = takes の capture/upload/adopt）で担保。

## 9.11 実装順序と要判断事項

### フェーズ（[08 §8.10](08_システムアーキテクチャ設計.md#810-実装ロードマップitem-見本をトレースする順) を詳細化）
0. 初期化（§9.1）
1. ドメイン骨格: Category→VideoManual→Cut→Take の CRUD + シナリオ document 保存（§9.3/§9.4）。PC 編集画面（Undo/Redo なしの素の編集から）
2. AI パイプライン: prompt 3 段 + 検証 DTO + AnalysisJob + チケット（§9.6）。PC 解析導線 + ポーリング
3. メディア基盤: presigned 直 S3 + 署名チケット + transcode/thumbnail + storage quota（§9.5）
4. 撮影 PWA（同一オリジン Web/PWA、§9.9）+ 同期冪等（§9.5）
5. 合成パイプライン: VideoComposer + ffmpeg + RenderJob + プレビュー（§9.7）。TTS は v1 方針次第
6. 課金確定・多言語・MCP read tools

### 決定事項（2026-07-10 時点）
1. **動画合成インフラ** → **自前 ffmpeg ワーカーで開始**。`VideoComposer` インターフェースで隠蔽し、将来 AWS MediaConvert 等へ差し替え可能にする（技術判断として確定）。
2. **Project の粒度** → **単一 Default Project で開始**（1 社=1 組織 + Default Team + Project 1 個）。`max_manuals` は**組織単位**。将来、現場/店舗ごとに Project 分割する余地は残す（技術判断として確定）。
3. **撮影アプリの形態** → **PWA/Web（同一オリジン）**。PC と同じ Svelte で実装一本化。カメラ撮影はブラウザの `MediaRecorder`、オフライン一時保持は Service Worker + IndexedDB。**認証は Passport OAuth ではなく通常のセッション認証**（first-party 同一オリジンのため。API は `/api/v1` を session guard で叩く or Inertia 直）。api-key/OAuth は将来のサードパーティ連携用に温存。

### 決定事項（追記・2026-07-10）
