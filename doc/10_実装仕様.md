## 10.2 Enum と状態遷移

```
VideoManualStatus: draft → analyzing → ready → rendering → published
  - draft:      作成直後/手順書未解析
  - analyzing:  AI 解析中（AnalysisJob 実行中）
  - ready:      シナリオ確定・編集/撮影可
  - rendering:  合成中（RenderJob 実行中）
  - published:  完成動画あり
  - 編集で cut を変更したら published → ready へ戻す（完成動画は要再合成）
  - draft → ready（シナリオ保存で cuts ≥ 1 になったとき。自作シナリオ経路）
  - ready → analyzing（**再解析**。SOP 差し替え後の明示トリガー。既存 cuts は
    materialize で全置換されるためフロントは確認ダイアログを挟む）
  - 解析失敗の復帰: cuts ≥ 1 なら ready、無ければ draft へ戻し AnalysisJob.error に理由
    （「失敗は draft へ」は cuts 無しの初回解析ケースとして包含）
  - 書き込み経路はメソッド粒度で固定（ScenarioService::save /
    ScenarioService::materializeIntoLockedManual / AnalysisJobService::trigger /
    AnalysisJobService::failJob / RenderJobService::trigger /
    RenderJobService::failJob / RenderJobService::completeRenderIntoLockedManual。
    ScenarioWritePathInventoryTest が deny-by-default で強制）

CutType: step | point          ShotType: hiki | yori
JobStatus: queued → running → (succeeded | failed)
TakeStatus: uploading → processing → (ready | failed)   # ready 前は採用不可
```

その他 enum: `MaterialType(video|still)`、`QuotaKey`(既存 + `max_manuals` / `max_storage_bytes` / `feature_multilang`)、permission enum（`ManualPermission` / `ShootingPermission` / `CategoryPermission`）。

## 10.4 プロンプト草案（YAML + Prompt クラス）

[03章](03_AI解析とシナリオ生成.md)のプロンプトを、テンプレの YAML 規約（`DefensiveInstructions` preamble + `{{ $var }}` に `UserInput`、JSON 出力→PHP で DTO 検証）に落とした**草案**。名称は全 YAML で一意。

### resources/prompts/work-decomposition.yaml（草案）
```yaml
name: work-decomposition
provider: anthropic
model: claude-sonnet-4-5-20250929
client_options:
  timeout: 120
system_prompt: |
  {{ \Kent013\PrismPrompt\Values\DefensiveInstructions::forUserInputJa() }}

  あなたは製造現場の作業標準化エキスパートです。資料を「読む」のではなく、
  作業者の体の動き（動詞）ごとに「1 動作 1 行」で解体・再構築します。
  出力は JSON のみ（前後に説明文を付けない）。
prompt: |
  次の抽出済み手順書データから「作業分解表」を作成し、JSON で出力してください。
  ルール:
  - 一動作・一 No（1 文に複数動詞があれば行を分ける）
  - 手順列は物理的な動詞のみ（「〇〇の清掃」等の括りは禁止）
  - 急所は判断基準・数値・良否境界・資料の注釈のみ。1 急所 1 要素
  - 資料にない語を足さない（指差呼称含め忠実に）
  出力スキーマ: { "steps": [ { "no": int, "action": string,
    "points": [string] } ] }

  抽出済み手順書データ:
  {{ $extracted }}
```
→ `WorkDecompositionPrompt::make(UserInput $extracted)`。出力は `WorkDecompositionData` DTO で検証（不正なら最大 2 回リトライ）。

## 10.5 課金・権限の確定値

- **チケット消費**（単一台帳・amount 可変）: `COST_ANALYSIS = 1`（`config/manual.php` の `analysis_ticket_cost`）、`COST_RENDER = 3`（`config/manual.php` の `render_ticket_cost`。尺/解像度係数化は後続、初期は固定 3）。プレビューは 0。予約はジョブ開始時（TTL=30 分対処）。
- **LLM 入力上限**（AI 解析）: 抽出テキストは **UTF-8 バイト数**で上限判定（`analysis_max_text_bytes = 150,000`）。根拠: モデル context 200,000 token − 出力予約 16,000（YAML max_tokens）− 固定プロンプト余裕 4,000 = 入力 budget 180,000 token。byte-fallback BPE 系 tokenizer では token 数 ≤ UTF-8 バイト数が安全側上界のため `strlen ≤ 150,000 ≤ 180,000` で context 超過を構造的に防ぐ（算術は `AnalysisTokenBudgetInvariantTest` が CI 固定。モデル/tokenizer 変更時は要再確認）。
- **Quota**: `max_manuals`（組織単位）、`max_storage_bytes`、`feature_multilang`(bool)。`config/quota.php` の各プラン + `QuotaKey` に追記。
- **ロール**: project_admin=編集者、project_member=撮影者（rename のみ）。permission は Policy で（編集者=manual CRUD/render/download、撮影者=take capture/upload/adopt + manual read）。

## 10.8 設計レビュー反映（2026-07-10・着手前修正）

GPT-5.2 Codex レビュー（生ログはセッション scratchpad）で挙がった穴のうち、採用した修正を確定仕様に織り込む。**実装時はこの節が §10.1〜§10.7 に優先する。**

### 10.8-1 チケット予約の二重消費・再試行・TTL 切れ（Critical）
キュージョブは自動再試行される。単純に「ジョブ開始時 reserve」だと再試行で二重予約になる。
- `analysis_jobs` / `render_jobs` の `ticket_reservation_id` を**予約の冪等キー**として使う。ジョブ開始時、**当該 job に有効な予約が無いときだけ** `reserve` する（既にあれば再利用）。
- 予約が TTL 切れ（stale cron で release 済み）だった場合は、**旧予約を明示 release 済みとして扱い、新規 reserve → job に付け替え**。`commit` は予約 status=Reserved のときのみ（Released/Committed なら guard）。
- ジョブは `tries=1` を基本とし、再実行は**明示トリガー**（下記 10.8-6）に限定。想定外の例外時は必ず `release`。

### 10.8-2 シナリオ保存の並行編集競合（Critical）
document 単位保存は後勝ちで順序・構造が壊れうる。
- `video_manuals.scenario_version`（楽観ロック）を追加。編集画面ロード時の version をクライアントが保持し、`PUT .../scenario` に `expected_version` を必須化。
- サーバは version 不一致なら **409 Conflict**（保存せず、UI は差分再取得を促す）。成功時 `scenario_version += 1`。

### 10.8-3 PWA・セッション・CSRF・大容量アップロードの整合（Critical）
- 撮影 PWA のデータ API は **`/api/v1`（dual guard）とは別の web ガード route group**（例: `/app/*`）に分離。テンプレの `/api/v1` は機械/サードパーティ用に温存（レビュー指摘の guard 混在を回避）。
- 書き込みは CSRF 必須（Inertia の `XSRF-TOKEN` cookie）。Service Worker 経由の再送でも `X-XSRF-TOKEN` を付与し、**419（CSRF 失効）時は cookie 再取得 → リトライ**する共通処理を用意。
- S3 直アップロード完了後の `POST .../takes` はセッション/CSRF 有効前提。バックグラウンド同期はフォアグラウンド復帰時に実行。
- **カメラ非対応フォールバック（必須）**: iOS Safari 等で `MediaRecorder` が使えない場合、`<input capture>` によるファイル選択アップロードに自動フォールバック。v1 の最小要件に含める。

### 10.8-4 容量 Quota の実計上・削除減算・孤児掃除（Critical）
`check()` だけで実使用量を持たないと Quota が機能しない。
- 使用量の真実源: `takes.size_bytes` の org 単位合計（`bytes_used`）＋ **アップロード中の予約分 `bytes_pending`**。`QuotaService::check` の `currentCount` にこの合算を渡す。
- upload-url 発行時に `bytes_pending += size`（予約）。`POST .../takes` 成功で `bytes_pending -= size`（確定分は `size_bytes` で自動計上）。
- **Take 削除**: `cut_id` cascade または Take 削除で S3 オブジェクト削除ジョブ（`media` queue）＋使用量再計算。`adopted_take_id` が指す take が消えたら null 化。
- **孤児掃除 cron**: 一定時間（例 30 分）未完了の pending 予約を解放し、対応する S3 未登録オブジェクトを削除。

### 10.8-5 scenario 保存の protected キー（Critical）
`parent_cut_id` / `adopted_take_id` は protected。クライアントから送らせない。
- `PUT .../scenario` の payload は **「step 配列の中に point 配列をネスト」した構造 + 各 cut の既存 id（照合用）+ 本文フィールドのみ**。`parent_cut_id` はサーバがネスト構造から決定、`sort_order` もサーバ採番。
- `adopted_take_id` は **`POST .../adopt` でのみ**変更（scenario payload から除外）。
- payload 内の cut id は**照合用**。当該 manual に属さない id が混入したら 404（tenant キー不信）。

### 10.8-6 レンダ中の編集競合・バージョン固定（Critical）
`published→ready` 戻しと `rendering` の並走で、進行中レンダに編集が混入しうる。
- RenderJob は開始時に対象 manual の `scenario_version` を**スナップショット**し、そのバージョンのカット集合を参照。
- `status=rendering` 中のシナリオ保存は **禁止（409/403）**。完成後に編集したら `published→ready` に戻し、再レンダは明示トリガー。

### 10.8-7 アップロード署名チケットは「検証専用」（Critical/Security）
署名チケットの `cut_id`/`org` を信頼して代入しない。
- `cut` は**URL の nested route から解決**（`$project->manuals()->cuts()`）。チケットの値は**一致検証にのみ**使用（不一致は拒否）。
- 署名対象に `content_type` と `size`（必要なら `md5`）も含め、`POST .../takes` で `HeadObject` の ContentLength/ContentType と照合。不一致は削除・拒否。

### 10.8-8 その他（Warning・採用）
- **一括同期は D9 即時アップロード方式へ吸収され sync endpoint は廃止**（照合専用の payload-ID 原則は scenario PUT §10.8-5 / upload ticket §10.8-7 に残る）。
- **analyze/render の Idempotency**: 同一 (manual, 操作種別) で同時 in-flight は 1 つ。`failed` のときのみ再トリガー可。
- **Category 削除**: FK `onDelete('set null')` を明示（未分類化）。
- **job 進捗ポーリング**: `GET .../jobs/{job}` に `ETag`/`Last-Modified` を付け HTTP キャッシュで負荷軽減（任意）。

### 採用しなかった/保留
- **TicketLedgerService に TTL 延長 API 追加**: テンプレ課金プリミティブの内部変更にあたり不変条件外。v1 は「レンダを 30 分未満に収める」設計（10.8-1 + 尺上限）で回避し、追加しない。
- **AnalysisJob/RenderJob の共通抽象化**: 現状カラムがほぼ共通で利得小。過剰設計を避け見送り（必要時に trait 化）。
