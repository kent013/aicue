# ドキュメント更新

## 引数

| 引数 | 必須 | 説明 |
|------|------|------|
| scope | No | 更新対象のスコープ（省略時は docs/ 全体）。特定コンポーネント名やファイル名で絞り込み可能 |

`docs/` 配下のドキュメント（および `AGENTS.md` / `CLAUDE.md` / `DESIGN.md`）を、ソースコードの現状と突き合わせて陳腐化・欠落を検出し、更新する。

**出力**:
- 更新されたドキュメントファイル群
- 必要に応じて新規ドキュメント

**独立利用**: YES — 単体で実行可能。

---

## 前提: worktree 必須

**ドキュメント更新も「実装」であり、必ず worktree で行う（main 直接編集は禁止）。** AGENTS.md §worktree 運用ルールに従う。

```bash
scripts/setup-worktree.sh docs-update      # .claude/worktrees/tasks/docs-update に worktree + todo/docs-update ブランチ
# → cd .claude/worktrees/tasks/docs-update で作業
```

- スキル本体（`.claude/skills/app-update-docs/SKILL.md`）の変更も同じ worktree 内で行いブランチに含める
- 完了後は通常フロー（コミット → main マージ → `scripts/teardown-worktree.sh docs-update`）
- docs のみの変更で `composer test` / `pnpm lint` 等が不要な場合でも、worktree 経由は省略しない

---

## 基本原則

### ハルシネーション防止

**ドキュメントに書く内容は必ずソースコードで裏取りすること。** 推測で書かない。

- 設定値はソースコード・config・マイグレーションから直接引用
- アーキテクチャ記述はソースコードのクラス・関数構造と一致させる
- 「〜と思われる」「〜の可能性がある」は禁止。確認できないなら書かない

### 最小変更の原則

- 正確な記述は変更しない
- 構造が変わっていない部分の書き直しは不要
- 新規ドキュメント作成は、既存ドキュメントに統合できない場合のみ

## Step 1: 現状把握

### 1-1. ドキュメント一覧の確認

```
Glob: docs/**/*.md
```

現在どのドキュメントが存在するか把握する（`AGENTS.md` / `CLAUDE.md` / `DESIGN.md` も対象に含める）。
ただし `docs/TODO.md` / `docs/TODO-closed.md` は `/app-todo-add` / `/app-todo-close`
スキルの管轄のため、本スキルの更新対象から除外する。

### 1-2. ソースコード構造の確認

`scope` 引数に応じてソースコードを探索する。

**全体スコープ（デフォルト）の場合:**

```
app/ 以下の主要ディレクトリ構造を確認（存在するもののみ）:
- Models/           — Eloquentモデル
- Services/         — ビジネスロジック
- Http/Controllers/ — コントローラー
- Http/Requests/    — FormRequest
- Http/Middleware/  — ミドルウェア
- Policies/         — 認可ポリシー
- Prompts/          — LLMプロンプトfactory
- Enums/ / Actions/ / Providers/ 等

resources/js/ 以下:
- pages/            — Svelteページコンポーネント
- components/       — 共通コンポーネント（atoms/molecules/organisms/templates）
- lib/              — 共有ロジック・型定義

routes/ — ルーティング定義
database/migrations/ — DBスキーマ
config/ — 設定ファイル
```

**絞り込みスコープの場合:**
指定されたコンポーネントに関連するディレクトリ・ファイルのみ探索。

---

## Step 2: 陳腐化チェック

各ドキュメントについて、以下の観点でソースコードとの乖離を検出する。

| チェック観点 | 方法 |
|------------|------|
| **クラス・関数の追加・削除・リネーム** | ドキュメント記載のファイル名・クラス名 vs 実ファイル |
| **ルート・API定義の変更** | ドキュメント記載のエンドポイント vs `routes/` |
| **DBスキーマの変更** | ドキュメント記載のテーブル・カラム vs マイグレーション |
| **新機能の未反映** | ソースコードにあるがドキュメントにない機能 |
| **削除済み機能の残存** | ドキュメントにあるがソースコードにない機能 |
| **型定義の乖離** | ドキュメント記載のDTO/Props vs 実際の型定義 |

**手順:**

1. ドキュメントを1つずつ `Read` する
2. ドキュメントに記載されているファイルパス・クラス名・関数名を抽出
3. 対応するソースコードを `Read` / `Grep` で確認
4. 乖離を検出したら記録する

**scope指定時**: 指定スコープに関連するドキュメントのみチェック。

### 検出結果の記録

```
[陳腐化] {ドキュメント名}: {記載内容} → 現在は {実際の内容}
[欠落]   {コンポーネント名}: ドキュメントなし。{概要}
[削除]   {ドキュメント名}: {記載機能} はソースコードから削除済み
[OK]     {ドキュメント名}: 最新の状態
```

---

## Step 3: 欠落コンポーネントの検出

### 3-1. ソースコードの走査

`app/` および `resources/js/` 以下を走査し、ドキュメントでカバーされていないコンポーネントを特定する。

**判定基準:**
- 独立したServiceクラス群にドキュメントがない → 欠落候補
- 主要な機能を持つモジュール（複数クラスで構成）にドキュメントがない → 欠落候補
- 既存ドキュメントのセクションとして記載可能なら新規ドキュメントは不要

### 3-2. 新規ドキュメントの要否判断

欠落候補ごとに:
- 既存ドキュメントに追記で対応可能か？ → 追記
- 独立したドキュメントが必要か？ → 新規作成
- 内部実装詳細でドキュメント化不要か？ → スキップ

---

## Step 4: ドキュメント更新の実施

### 4-1. 既存ドキュメントの更新

Step 2で検出した陳腐化・乖離を修正する。

**更新ルール:**
- 設定値・スキーマはソースコードの値に合わせる
- 削除済み機能の記述は削除する
- 新機能は適切なセクションに追記する
- テンプレート由来のドキュメント（`docs/app-integration-guide.md` 等）の共通部は、テンプレート更新の取り込みを容易にするためできるだけ書き換えない（AGENTS.md「テンプレートとの関係」参照）

### 4-2. 新規ドキュメントの作成

Step 3で新規作成が必要と判断したコンポーネントのドキュメントを作成する。

**テンプレート:**

```markdown
# {コンポーネント名}

**実装**: `{ソースファイルパス}`

## 概要

{1-3文でこのコンポーネントが何をするか}

## アーキテクチャ

{処理フロー、主要クラス・関数}

## 関連ファイル

| ファイル | 役割 |
|---------|------|
```

### 4-3. 不要ドキュメントの削除

以下に該当するドキュメントは削除する:
- 対応するソースコードが完全に削除されている
- 他のドキュメントに統合済み

**削除前にユーザーに確認すること。**

```
## ドキュメント更新完了

### 更新サマリー
- 更新: {N}件（{ファイル名リスト}）
- 新規作成: {N}件（{ファイル名リスト}）
- 削除: {N}件（{ファイル名リスト}）

### 陳腐化修正
- {修正内容の箇条書き}
```
