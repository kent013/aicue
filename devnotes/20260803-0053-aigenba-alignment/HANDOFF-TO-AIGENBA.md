# F-6. 自動チケット購入で、同意した上限額を超えて請求されうる

## ひとことで

**「少なく買ったのに、多く買うより高く請求される」**状態です。
そのせいで、利用者が同意した上限金額を超えて請求されることがあります。

## 前提の仕組み

チケットは**まとめ買いすると1枚あたりが安くなる**価格表になっています。
（`database/seeders/data/stripe_initial_prices.php` の実値）

| 買う枚数 | 1枚あたり |
|---|---|
| 1〜19枚 | 100円 |
| 20〜49枚 | 80円 |
| 50〜99枚 | 70円 |
| 100枚〜 | 65円 |
| 200枚〜 | 60円 |
| 300枚〜 | 55円 |
| 500枚〜 | 50円 |

## 利用者が同意すること

「チケットが減ったら自動で買い足す」をオンにするとき、利用者は
**1回に買う上限枚数**を決めます。仮に「1回あたり最大50枚」とします。

このとき画面には「**1回の請求は最大 3,500円**」と表示されます。
50枚は70円の段なので 70円 × 50枚 = 3,500円、という計算です。
利用者はこの金額を見て同意します。

## 実際に起きること

自動購入が動くとき、いつも上限いっぱいの50枚を買うとは限りません。
「48枚あれば足りる」なら48枚だけ買います。

ところが請求額を計算するとき、**48枚という実際の枚数で価格表を引き直します**。
48枚は「20〜49枚」の段なので1枚80円。

**80円 × 48枚 = 3,840円**

利用者は「最大3,500円」に同意したのに、**3,840円が請求されます**。340円の超過です。

## なぜこうなるか

**同意画面の金額と、実際の請求額とで、価格表の引き方が違う**からです。

| | どちらの枚数で価格表を引くか | 該当箇所 |
|---|---|---|
| 同意画面に出す上限額 | **上限枚数**（50枚 → 70円） | `app/DataTransferObjects/Billing/AutoRechargeConsentTermsDto.php:27` |
| 再同意が必要かの判定 | **上限枚数** | `app/Services/Billing/AutoRechargeService.php:197` |
| 同意条件の組み立て | **上限枚数** | `app/Services/Billing/AutoRechargeService.php:302` |
| 現在の上限額の再計算 | **上限枚数** | `app/Services/Billing/AutoRechargeService.php:1198` |
| **実際の請求額** | **実際に買う枚数**（48枚 → 80円） | **`app/Services/Billing/AutoRechargeService.php:466`** |

4箇所は上限枚数で計算しているのに、**請求だけが実際の枚数**で計算しています。
まとめ買い割引の段差をまたぐと、そこでずれます。

## 直し方の提案

**実際の請求も、同意したときと同じ「上限枚数」の価格で計算する。**
つまり `AutoRechargeService.php:466` の

```php
$tier = $this->tickets->resolveVolumeTier($quantity);
```

を、上限枚数基準に変えます。すると48枚は 70円 × 48枚 = **3,360円**となり、
同意した3,500円に必ず収まります。

**副作用**: 自動購入は、同じ枚数を手動で買うより少し安くなります
（48枚が3,360円 vs 手動購入なら3,840円）。
**利用者に有利な方向**で、約束を破らないので、AI-CUE ではこちらを選びました。
ただし「価格ポリシーとしてそれでよいか」は、そちらの判断です。

**別案**: 同意画面の上限額のほうを「実際の枚数基準」に合わせる、という方向もありえますが、
**同意する時点では実際の枚数が決まっていない**ので、現実的には難しいと思います。

**いずれを採るにせよ**、「同意上限の計算式」と「実請求の価格表の引き方」は
**同じ基準でなければならない**、という決まりをテストで固定しておくと安全です。

## こちらが確認したこと / していないこと

| | |
|---|---|
| **確認した** | 上記5箇所のコードを読み、**4箇所が上限枚数・1箇所だけが実枚数**であることを確認 |
| **確認した** | 価格表（`stripe_initial_prices.php`）が**まとめ買い割引の段差構造**であることを確認。AI-CUE とまったく同じ値でした |
| **確認した** | AI-CUE 側で同じ計算をして、**340円の超過**が出ることを数値で検証 |

# F-1. bug-hunt スクリプトの安全確認

## ひとことで

**(a)** データベースを消す操作の直前に「本当にこのDBを消してよいか」の確認がありません。
**(b)** デバッグ用にスクリプトを詳細表示モードで動かすと、**API キーがそのまま画面とログに出ます**。

## (a) データベースを消す操作の確認がない

`scripts/bug-hunt-shard.sh` は、変数で受け取った名前のデータベースを、
確認なしでそのまま作成・削除・初期化します。

| 行 | やっていること |
|---|---|
| `:444` | `createdb "${db}"` — 変数の中身をそのまま使ってDB作成 |
| `:448` | `migrate:fresh --seed --force` — DBの中身を全消しして作り直す |
| `:595` | 同上 |

`require_orchestrator`（親プロセスだけが実行できる仕組み）はありますが、
**「その名前が本当に bug-hunt 用のDBか」を確かめる仕組みがありません**。

変数の取り違え・環境変数の漏れ・引数のミスが起きたとき、
**開発用のDBを消してしまう可能性**があります。

**提案**: 消す/作る操作をする関数の先頭で、DB名が
「bug-hunt 用の名前パターンに合っているか」を確認し、合わなければ**その場で止める**。
「呼ぶ側が正しい名前を渡してくれる」という前提を、仕組みで置き換えるという考え方です。

AI-CUE では3段階（DB名のパターン確認 / 実行環境の確認 / 管理者権限の明示確認）にしていて、
確認自体が働いているかのテストも用意しています。実装は
`scripts/bug-hunt-shard.sh` の `guard_*` 関数群です（そのまま流用できます）。

## (b) デバッグ時に API キーがログに出る

`scripts/bug-hunt-shard.sh:526` は、環境変数の API キーを配列に入れています。

```bash
[[ -n "${ANTHROPIC_API_KEY:-}" ]] && real_llm_env+=("ANTHROPIC_API_KEY=${ANTHROPIC_API_KEY}")
```

`bash -x` のような**詳細表示モード**でスクリプトを動かすと、
bash はこの行を**値を展開した状態で**出力します。つまり**キーがそのまま出ます**。

出た先は、そのときの端末の履歴や CI のログです。

**やっかいな点**: 詳細表示モードは「困ったときに使う」ものです。
つまり**障害調査をしているまさにそのときに漏れます**。

**提案**: キーを扱う区間だけ詳細表示を一時的に切って、後で戻す。2行で済みます。

```bash
# 元の状態を覚えて切る
case $- in *x*) SAVED=1; set +x ;; *) SAVED=0 ;; esac
#   …キーを扱う処理…
# 元が詳細表示なら戻す
[[ "$SAVED" == 1 ]] && set -x
```

# F-4. ログアウト後に「戻る」で個人情報が残りうる

## ひとことで

ブラウザには「**戻る**を速くするために、前のページをそのまま保存しておく」仕組みがあります。
ログアウトした後に「戻る」を押すと、**保存されていた画面がそのまま復元される**ことがあります。
その画面にメンバー一覧などが載っていると、**次に使う人に見えてしまいます**。

## 現状の対策と、残っている穴

サーバー側は対策済みです（`app/Http/Middleware/NoStoreCacheHeadersForAuthenticatedPages.php`）。
ログイン中の画面に「保存しないで」という指示を付けています。

ただし**この指示の効き方はブラウザによって違います**。
Firefox と Chrome には効きますが、**Safari は指示があっても保存することがあります**。
`docs/architecture.md` にも「Safari は別施策」と書かれている通りです。

そして aigenba は**ホーム画面に追加して単独アプリのように使える設定**になっています
（`public/site.webmanifest` が `"display": "standalone"`、アイコン3種）。
この形で使うと、**iOS では Safari が土台**になります。
つまり「Safari は別施策」の残りリスクが、**主要な使われ方にそのまま残ります**。

## 実際に起きることが確認できている手がかり

`resources/js/pages/Billing/PurchaseTickets.svelte:74-79` に、
**「戻る」で復元されたときの処理**が既に入っています（bug-hunt の F-5-01 対応）。

つまり **aigenba では「戻るで画面が復元される」ことが実際に起きると分かっている**わけです。
ただしこの処理の目的は**入力欄の値の整合を取ること**で、
**個人情報を隠すことではありません**。

## 直し方の提案

1. **まず確かめる**: iOS の Safari（できればホーム画面から起動した状態）で
   「ログイン中の画面 → ログアウト → 戻る」をやってみて、個人情報が出るかを見る。
2. 出るなら、**「復元されたら、確認が終わるまで画面を隠す」**形にする。
   - ページを離れるときに画面を隠す（隠した状態がブラウザに保存される）
   - 復元されたら、**隠したまま**ログイン状態を確認する
   - 有効なら隠すのをやめるだけ / 無効ならログイン画面へ移す
3. **「復元してから確認する」順番だと意味がありません**。確認が終わるまでの間、
   古い画面が実際に見えてしまうからです。**先に隠す**のが要点です。
4. 画面を隠すのは**見た目だけ**にして、入力途中の値や撮影中のデータは壊さないこと。

## 先にお伝えしておく落とし穴

**自動テスト（Playwright）では、この「戻るで復元される」状況を再現できません。**
AI-CUE で試して分かりました。

| 試したこと | 復元されたか |
|---|---|
| Chromium そのまま | されない |
| 復元を無効にする起動オプションを外す | **されない** |
| さらに復元を有効化するオプションを付ける | **されない** |
| WebKit そのまま | されない |
| ブラウザ操作の接続自体を外す構成 | **起動できない** |

理由は、**Chrome はブラウザ操作用の接続がつながっている間、この保存機能を止める**からです。
Playwright はブラウザを動かすためにその接続を必ず使うので、設定では回避できません。

**つまり、この件の確認は実機でやるしかありません。** 同じ袋小路に入らないよう共有します。

# F-2. カバレッジ集計の分母について（不具合の指摘ではなく、意図の確認）

## ひとことで

**これは「直してほしい」ではなく「どちらのつもりですか」という質問です。**

## 何の話か

`.claude/skills/aigenba-bug-hunt/operations.md` は、
「どの操作を確認したか」を数えるための一覧表です。

この表のほとんどの節は `| route name | 操作 | story | 区分 |` という形で、
**1列目がルート名**です。

ところが **190行目からの節だけ** `| 操作 | 内容 | story | 区分 |` という形で、
**1列目が操作の名前**になっています。この節にはそう書いてある通りの説明があります。

> Filament の書き込みは Livewire アクション経由で発火し名前付き REST ルートを持たない。
> よって本節は「UI で実行すべき admin 操作」を機能単位で列挙する（**ルート名でなく操作で数える**）。

**つまり意図的にそうしてあります。**

集計プログラムは1列目を一律にルート名として読むので、
この節の **28件**（`admin.login` / `admin.organizations.crud` など）も
ルート名として取り込まれます。全体は143件なので、**約2割**がこれにあたります。

## 質問

この28件を、**カバレッジの分母に入れたいですか？ 外したいですか？**

- **入れたい**なら、今のままで意図どおりです。**何もしなくて構いません。**
- **外したい**なら、AI-CUE 側の集計プログラムが参考になります。
  1列目の見出しを見て「ルート名の列が見つからない表は数えない」という作りにしてあるので、
  この節は自動的に対象外になります。ただし**分母が28件減ります**。

**こちらでは決められません。** 仕様を持っているのはそちらなので、判断をお預けします。

## ついでの小さな改善（独立して採れます）

集計プログラムがルート名を読むとき、`` `api.v1.projects.store` `` のように
バッククォートで囲まれていると、ルート名として認識されずに**静かに数から漏れます**。
バッククォートを外す1行を足すだけで直ります。副作用はありません。
