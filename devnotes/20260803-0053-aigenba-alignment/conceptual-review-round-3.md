# 全体判定: CHANGES_REQUESTED

Round 2 の Critical は解消されています。P1 の total inventory は概念設計として成立しています。一方、P3 に契約上の矛盾とテスト完了条件の曖昧さが残っています。

## 1. 使命との整合性

[Warning] 冒頭では「ログアウト後に PII が見えないことを保証する」と断定していますが、後段では Safari をスコープ外としています。

修正提案: 主便益を「サポート対象ブラウザで再表示を防止する」に変更し、詳細設計で対象ブラウザを明示してください。

## 2. 禁止事項違反

[Critical] Browser 検証手段が「E2E または bug-hunt」になっています。bug-hunt は探索的確認であり、恒久的な回帰テストへの登録を代替できません。このままでは、bug-hunt の一度限りの確認だけで P3 を完了扱いでき、禁止事項 #1 に抵触します。

修正提案: P3 の完了条件として自動 Browser E2E テストを必須にしてください。bug-hunt は追加の探索確認としてのみ扱います。CIで実行しない場合も、恒久テストの配置場所と標準実行コマンドを固定してください。

## 3. 実現可能性

[Warning] P3 のヘッダ契約が内部矛盾しています。

- 「既存ヘッダを上書きしない」
- 「`no-store` を持たない応答には付与する」

既存値が `private, max-age=60` の場合、前者なら変更できず、後者なら上書きまたは追記が必要です。

修正提案: 次のどちらかへ契約を確定してください。

- `Cache-Control` 自体が存在すれば untouched
- `no-store` がなければ既存 directive を安全に統合して `no-store, private` を成立させる

セキュリティ baseline の目的からは後者が妥当です。`public` など矛盾する directive の扱いも詳細設計で固定する必要があります。

## 4. 期待効果の妥当性

[Warning] 「既存4経路が untouched」と「将来の矛盾値を同テストが検出する」は同義ではありません。期待値を完全一致で固定するなら検出できますが、単に `no-store` の存在だけを見るテストでは `public, no-store` を検出できません。

修正提案: 既存4経路について、許容する directive の集合またはヘッダ完全値をテスト契約として明記してください。

## 5. リスク

[Warning] Safari をスコープ外とする判断自体は可能ですが、現場端末として利用される可能性を評価せず除外すると、共用端末の PII リスクが残ります。

修正提案: サポートブラウザ方針に基づく除外であることを前提条件にしてください。Safari がサポート対象なら、`pageshow` の `persisted` 判定後に再検証・再読込するなど、別対策の検討が必要です。

## 6. スコープの適切さ

[Suggestion] P1 の bigint・UUID 対応を同じトラックで扱うこと、P2 の運用ガードを同一変更集合に含めること、P4/P5 を後段へ分離することはいずれも適切です。

## 7. 型安全性

[Suggestion] total inventory の4分類、Response class の明示、純粋な判定メソッドという方針は PHPStan level 10 と整合します。DTO/JsonResource 規約への抵触もありません。

承認に必要なのは、P3について「自動 Browser E2E を必須化」「Cache-Control の統合契約を一意に定義」「サポート対象ブラウザを明示」の3点です。
