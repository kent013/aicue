## [Warning] 観点3 — P3-b の状態表と第一候補 (hard reload) が整合していない

- **判断: 対応する（概念設計の時点で修正）**
- **根拠**: 正しい。私の状態表は
  「3. セッション有効 → **表示を戻す**」「4. 無効 → hard navigation」と書いていたが、
  第一候補である **hard reload は新しい Document へ遷移する**ため、
  旧 DOM の「表示を戻す」経路は**そもそも通らない**。
  「表示を戻す」が必要になるのは専用再検証 endpoint を採用した場合だけであり、
  第一候補と代替案の状態遷移を 1 つの表に混ぜていたのが誤り。
- **対応内容**: 状態遷移表を**第一候補 (hard reload) 用**に統一し、
  代替案 (専用 endpoint) の遷移は**別表**に分離した。

  **第一候補 (hard reload)**:
  `pagehide で秘匿 → persisted 復元時も秘匿のまま → hard reload →
   認証済みなら新 Document を表示 / 未認証なら login へ redirect`

  この形なら「旧 DOM を検証結果に応じて出し直す」という難しい状態管理が不要になり、
  秘匿は「reload が効くまでの目隠し」という単純な役割に閉じる。

## [Warning] 観点5 — 全 `pagehide` で秘匿すると通常遷移時にちらつく

- **判断: 詳細設計で確定する（Codex の指摘どおり）**
- **根拠**: 妥当。`pagehide` は通常遷移でも発火するため、無条件秘匿は
  「ページを離れる瞬間に画面が隠れる」ちらつきを生む。
  一方 `PageTransitionEvent.persisted` は `pagehide` 側でも
  「この Document が bfcache に入る見込みか」を示すため、これで絞れる可能性がある。
  ただしブラウザ差があり、**利用できない環境では安全側 (秘匿する) へ倒す**必要がある
  = セキュリティとちらつきのトレードオフを詳細設計で確定する。
- **対応内容**: 概念設計に**詳細設計での決定事項**として明記した。
  - `pagehide` の `PageTransitionEvent.persisted` が利用できる環境では **bfcache 対象時だけ秘匿**。
  - 利用できない環境では**安全側 (秘匿する)** へ倒す。
  - 通常遷移への副作用は Browser E2E シナリオ 1 (撮影画面からの通常遷移) が固定する
    (現在の 4 シナリオ構成で担保できる、と Codex も是認)。
