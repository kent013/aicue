# 対応マトリクス: conceptual-review Round 4

## [Critical] 観点3 — `pageshow.persisted` 後の非同期検証では、検証完了まで古い DOM が表示され PII が一瞬露出する

- **判断: 対応する（設計の欠陥。指摘が正しい）**
- **根拠**: 全面的に正しい。私の Round 3 案「`pageshow` で `persisted` を検知したらセッションを
  再検証し、無効なら再読込 / ログイン画面へ倒す」は、**bfcache から復元された DOM が
  画面に出た後に検証を始める**構造だった。
  「無効なら遷移する」は「**再表示しない**」と同義ではない。P3 の主便益は
  「ログアウト後に前の作業者の PII が**再表示されない**」ことなので、
  一瞬でも露出する時点で主便益を達成していない。**Round 3 Critical (過大申告) と同じ誤り**を
  別の層で繰り返していた。
- **対応内容**: P3-b を「**復元後に検証**」から「**検証完了まで復元内容を秘匿**」へ強化した。
  状態遷移を以下に確定し、詳細設計と Browser E2E の契約として固定する:

  1. **`pagehide`** 時に画面を**同期的に秘匿**する (この秘匿状態が bfcache snapshot に入る)。
  2. **`pageshow` (`persisted === true`)** 時は**秘匿状態のまま**再検証する。
  3. セッション**有効時のみ**表示を戻す。
  4. セッション**無効時**はログイン画面へ **hard navigation** する。

  「単純な `pageshow` → 非同期検証では不十分」という不変条件自体を、
  詳細設計と Browser E2E に明示的に書く (将来この構造が崩れたら E2E が落ちるように)。

## [Warning] 観点3 — 「再検証」の通信契約が未定義 (通常ページ再取得か専用 endpoint か)

- **判断: 対応する（Codex の第一候補を採用）**
- **根拠**: 正当。専用 endpoint を足すと キャッシュ・認証・DTO 規約・攻撃面がすべて増える。
  思考原則 #1「フレームワークのレンジ内でやる」・#2「今必要なものだけ作る」からも、
  既存の session middleware に再判定させる方が筋が良い。
- **対応内容**: **第一候補を「専用 endpoint を追加せず hard reload で既存の session middleware に
  再判定させる」**と明記した。
  hard reload なら `no-store` により bfcache ではなくネットワークから取り直され、
  未認証なら既存の `auth` middleware が login へリダイレクトする = **新しい経路を増やさない**。
  専用 endpoint が必要になった場合の必須条件 (同一オリジン / `no-store` / セッション認証 /
  DTO・JsonResource 応答 / PHPStan level 10 対象) も条件付きで記載した。

## [Warning] 観点4 — Playwright WebKit と実機 iOS Safari は同一でない

- **判断: 対応する**
- **根拠**: 正当。WebKit エンジンは共通でも、**bfcache の挙動・PWA (standalone) モード・
  iOS 固有の WebKit ビルド差**があり、Playwright WebKit の green を
  「iOS Safari 対応を実証した」と言い換えるのは過大申告。
  AI-CUE は撮影が PWA なので、standalone モードの挙動差は特に無視できない。
- **対応内容**: P3-c に**検証レベルの区分**を追加した。

  | 区分 | 対象 | 扱い |
  |---|---|---|
  | **自動回帰テスト (恒久)** | Chromium / WebKit (Playwright) | 完了条件。CI/ローカルで反復実行 |
  | **実機受入確認 (手動・一度きり)** | iOS Safari 実機 (PWA standalone 含む) | **「恒久テスト済み」とは表現しない**。確認記録を devnotes に残す |

  自動化できない実機確認を恒久テスト扱いしないことを明記した。

## [Warning] 観点5 — `pagehide` / `pageshow` の全体処理が撮影中 media stream・未送信フォーム・Inertia 履歴に影響し得る

- **判断: 対応する**
- **根拠**: 正当かつ AI-CUE では特に重い。撮影 PWA が中核なので、
  秘匿処理が media stream やフォーム状態を壊すと**使命に直撃する**。
- **対応内容**:
  1. **秘匿処理は DOM 表示に限定する**と設計制約を明記した。
     **撮影データ・未送信フォーム状態・Inertia 履歴状態は破棄しない**。
  2. Browser E2E に以下の 4 シナリオを**分けて**登録することを施策に含めた:
     - 撮影画面からの通常遷移 (秘匿処理が誤発火しないこと)
     - bfcache 復元 (一般)
     - **未ログアウト**での復元 (表示が正しく戻ること = 誤検知しないこと)
     - **ログアウト後**の復元 (PII が出ないこと = 本来の目的)
