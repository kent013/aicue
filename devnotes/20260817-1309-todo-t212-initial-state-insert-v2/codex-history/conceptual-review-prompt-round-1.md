## 使命 (North Star)

**AI-CUE** は、現場に既にある**作業手順書(SOP)を起点に**、AI が撮るべきカットを設計した**動画シナリオ**を生成し、そのシナリオを**スマホ(PWA)でナビゲーション撮影**することで、専門知識ゼロの現場作業者でも**標準化されたマニュアル動画**を作れるようにする。

- 「思考ゼロ・編集ゼロ」— 台本作成・撮影判断・編集の 3 ハードルを AI とナビ撮影で肩代わりする。
- 競合(OJT を撮って形式化する tebiki)と異なり、**標準作業を起点に AI が教材設計し撮影を指示する**（撮影者・教える人のスキルに品質を依存させない）。
- 熟練者の暗黙知を動画マニュアルという形式知へ変換する装置（SECI）。

> 詳細な設計は本リポジトリの `doc/`（01〜10）に置く。ドメインをテンプレート構造へどうマップしたかは `doc/08`〜`doc/10`（特に `doc/10 §10.8` に設計レビュー反映済み）。
> **v1 スコープ**: 字幕のみ(TTS 後回し) / 撮影は PWA(同一オリジン・セッション認証) / 動画合成は自前 ffmpeg / 単一 Default Project。

## 概念設計

# 概念設計: NULL が初期状態を表す列の分類とスキーマ pin (正典 v2 追従)

## 目的と台帳の根拠

家系の機能台帳 lctl の機能 `explicit-initial-state-on-insert`
(新規行の初期値は DB の既定値に頼らず明示的に代入する規約) が、
**裁定 AG-191 (2026-08-16)** により正典 v2 へ上がった。
本リポジトリ (aicue) のセルは `update_pending` / `version: v1` /
`target_version: v2 (NULL が初期状態を表す状態列の分類 + 既定値後付けを赤にするスキーマ pin)` である。

台帳が確定している不変条件のうち、本施策が追加で満たすのは **i10** である
(確定設計 s10。旧 未決論点 q1 が本裁定で解消された):

> **i10**: NULL 自体が初期状態を表す状態列 (受諾日時・処理日時・失効日時など、値が入ったら
> 処理済みと読む列) も本 feature の守備範囲に含める。守り方はスキーマ pin 形 —
> この一族の列を検査の分類に 1 つ足して既定拒否の全数申告に載せ、この列へ後から DB 既定値を
> 足したら赤くなることをスキーマ側で固定する。CHECK 制約は使わない (i7 と衝突しない)。
> この分類の追加をもって正典は v2 とする。

併せて効き続ける既存の不変条件:

- **i5**: 検査の母集団は**実際のスキーマ**から取る。コード側が持つ一覧を母集団にしない。
  母集団が 0 件と算出されたら合格にせず落とす
- **i6**: 保証しない範囲は検査自身が明文で持ち、それが正本である。
  走査で証明できない受け手は適合と判定せず未解決として扱う
- **i7**: データ層の制約 (CHECK・排他制約・部分一意索引・外部キー) を義務化しない。
  データ層へ求めるのは「既定値を置かない」ことだけである

裁定の根拠は「穴の実在が正典の実装自身の中で観測された」ことである
(laravel-claude-template が既存列を nullable 化して「NULL なら処理中」と読む列を、
自分の検査の母集団外に足していた)。

台帳 ID の書式について: 本文書では家系の規律に従い、単一リポジトリでのみ意味が通る ID を
`<repo>:ID` の形で書く (例: aicue:T151 / aicue:T152 / laravel-claude-template:T131)。

## 背景・課題

本リポジトリの v1 (規約明文 + ファイル粒度の許可一覧) は実装済みである。

- 規約の明文: `AGENTS.md` ドメイン固有規約 1 (ii) 生成経路 と 規約 2
  (「初期状態 `pending` は INSERT 時に明示代入する」)
- 準拠実装: `app/Services/Manual/VideoManualService.php` の `create()` / `duplicate()`
  (aicue:T151)、`app/Services/Capture/TakeUploadService.php` の `issue()` (aicue:T152)
- 機械検査: `tests/Architecture/ScenarioWritePathInventoryTest.php`
  (ファイル粒度の許可一覧。同一ファイル内のメソッド追加は検出しないことを自認済み)

v1 が守っているのは「**DB 既定値を持つ状態列**を、生成点が明示代入しているか」である。
これに対し、**NULL であること自体が初期状態を表す列**は v1 の関心の外にある。この一族には
書き忘れが存在しない — 列が nullable で既定値を持たないとき、生成点が何も代入しないことが
そのまま正しい意味になるからである。

しかし穴が 1 つ残る。**後から migration でこの列に DB 既定値を足すと、アプリのコードを
1 行も変えずに新しい行の意味が変わる**。例えば `organization_invitations.accepted_at` に
既定値を足せば、これから作られる招待はすべて「受諾済み」になる。
`stripe_webhook_events.processed_at` なら「処理済み」になる。
既存行は変わらないので、テストも画面も静かなまま新しい行だけが壊れる。

本リポジトリの実スキーマを実読したところ、この形の列は現に多数実在する
(受諾日時・失効日時・処理日時・完了日時・既読日時・退会予約日時・論理削除日時など)。
また「NULL = まだその段階に入っていない」を**時刻ではなく状態語彙**で表す列も実在する
(`analysis_jobs.step` / `render_jobs.step` = NULL なら段階に入っていない)。

## 改善アイデア

**実スキーマから母集団を取り、NULL が初期状態を意味しうる列を全数分類する台帳を 1 つ足し、
その台帳と実スキーマが両方向で集合一致することを検査する。**

要点は 1 つだけである。母集団の条件を「**nullable かつ DB 既定値を持たない**」に置くと、
**登録済みの列に既定値を足した瞬間にその列は母集団から抜ける**。台帳側には登録が残るので、
両方向の集合一致が破れて赤くなる。つまり AG-191 が求めた「既定値の後付けを赤にする
スキーマ pin」は、除外規則や CHECK 制約を足すことなく、母集団の定義そのものから出る。

逆向きも同時に閉じる。新しく nullable かつ既定値なしの列を足すと未分類として赤くなり、
その列が一族かどうかを人が宣言するまで緑にならない (deny-by-default)。

分類は 3 区分とし、区分と 30 文字以上の根拠を 1 列につき 1 行書く
(家系の目録記法 = `RetentionTableRegistry` / `ThrottleCoverageExemption` /
`ForbiddenStatementExemption` と同じ形)。

## 期待効果

- **使命への貢献**: 撮影 PWA とレンダ基盤の進行状態は「受諾したか」「処理したか」
  「採用したか」という NULL / 非 NULL の判定で動いている。ここに既定値が後付けされると、
  現場が撮る前のカットが「撮影済み」に見えるといった形で**教材の完成判定が静かに狂う**。
  その静かな破壊を、migration を書いた瞬間に赤で止める
- 家系の正典 v2 への追従が完了し、台帳のセルを `update_pending` から進められる
- 実スキーマの nullable な列のうち「意味を持つ NULL」がどれかが 1 か所に集まり、
  新しい表を足す人が判断を迫られる (隠れた前提が減る)

## 実装方針 (概要)

| # | 施策 | 中身 |
|---|------|------|
| 1 | 分類の型 | `Tests\Support\InitialState\NullInitialStateClass` (enum 3 区分) |
| 2 | 台帳の 1 行 | `NullableStateColumnEntry` (readonly。区分ごとの名前付き生成子・根拠 30 文字以上) |
| 3 | 全数台帳 | `NullableStateColumnRegistry::entries()` (現在値 59 列) |
| 4 | 検査 | `tests/Feature/InitialState/NullInitialStateColumnClassificationTest.php` |
| 5 | 規約の明文 | `AGENTS.md` ドメイン固有規約へ 1 項追加 (v1 の 規約 1・2 から参照させる) |
| 6 | 運用の説明 | `docs/architecture.md` に 1 節追加 (保証しないものは複写せず gate を参照) |

母集団の定義 (実スキーマ起点):

- 現在のスキーマの base table の列で、**nullable** かつ **DB 既定値を持たない**、
  生成列・identity 列でないもの。ここから
  - (a) 時刻型 (`timestamp` / `timestamptz` / `date`) の列。ただし枠組みが行の作成・更新の
    たびに書く 2 列 (`Model::CREATED_AT` / `Model::UPDATED_AT` の既定値) は外す
  - (b) 所有する Eloquent モデルが **BackedEnum への cast を宣言している**列
    (時刻ではなく状態語彙で「まだ / 済んだ」を表す形)
- 実測 (2026-08-17 時点のスキーマ): (a) 50 列 + (b) 9 列 = **59 列**

## 制約・前提

- **CHECK 制約は使わない** (AG-191 が明記。i7 と衝突させない)
- **v1 の資産は 1 文字も変えない** (`ScenarioWritePathInventoryTest.php` /
  `VideoManualService` / `TakeUploadService`)。v2 は独立した 1 本の検査として足す
- 検査は実スキーマを引くため **Feature レーン**に置く
  (`RefreshDatabase` がグローバル適用済み。先例は
  `tests/Feature/Retention/RetentionTableClassificationTest.php`)
- PHPStan の走査根は `app` / `config` / `database` / `routes` であり `tests` を見ない。
  型の厳密さは走査で強制されないので、**書く側が明示的な型で書く** (widen しない)
- 母集団 0 件は合格にしない (i5)。(a)(b) の各系統がそれぞれ 1 件以上寄与していることも
  正のコントロールで固定する (片方の抽出が壊れて静かに縮むのを防ぐ)

## スコープ外 (やらないと決めたこと)

- **DB 既定値を持つ状態列の扱い (v1 の担当)**。同じ事実を 2 か所で検査しない
- **CHECK 制約・部分一意索引・排他制約の導入** (i7。裁定が明示的に排除)
- **Factory / Seeder の走査** (家系の未決論点 q3。本裁定の範囲外)
- **生成点のコード走査 (構文解析)**。この一族には書き忘れが存在しない
  (生成点が何も代入しないことが正しい意味になる) ため、走査しても守るものが無い
- **既定値を「置かない」ことの家系標準 (i2) への全面移行**。本リポジトリの規約 2 は
  「migration の `default('pending')` は既存行と Factory 以外の INSERT 経路のために残す」と
  書いており、正典 i3 の申告で表現できる形になっている。ここは v2 の要求ではないので触らない
- **列の意味が区分どおりかの機械判定**。区分は人が宣言し、機械は集合の一致と根拠の長さだけを見る
