# 実査ブリーフ: 状態を区別しない汎用メッセージの是正 (F-2-01 / F-2-02)

> bug-hunt run `20260811-003230` の finding 2 件に対応する。
> 統合レポート: `devnotes/20260811-003230-bug-hunt/report.md`
> シャード詳細: `devnotes/20260811-003230-bug-hunt/shard-2/shard-report.md`

**共通の症状**: システムは具体的な状態を知っているのに、画面には**どの状態でも同じ汎用メッセージ**が出る。
結果、ユーザーは「自分に何が起きているか」「次に何をすればよいか」が分からない。

---

## F-2-01 (Medium): 未契約ユーザーに「支払いが確認できない」と表示される

**一度も契約していない**ユーザー (NoSubscription) のダッシュボードに
「サブスクリプションのお支払いが確認できないため…」が出る。**支払い失敗 (PastDue) と同じ文言**である。

- 原因: `hasBillingAccess` が両状態を **1 つの真偽値に潰している**ため、
  `Dashboard.svelte` が区別できない。
- **影響範囲が広い**: S1 登録ファネルを通る**全新規ユーザー**が最初にこれを見る。
- species: `ux_dead_end:organization:read:self` / oracle: `H10` (直前の操作結果と矛盾)
- 証跡: `devnotes/20260811-003230-bug-hunt/shard-2/screenshots/F-2-01-dashboard-billing-callout.png`

**阻害されているユーザージョブ**: 登録直後に「次に何をすればよいか」を知る。
本来は「プランを選ぶ」へ誘導すべきところで、身に覚えのない支払い失敗を告げられる。

---

## F-2-02 (Low): passkey の 429 が他の失敗と区別されない

`/passkeys/login/options` が `throttle:passkeys` で 429 を返したとき、
画面には「パスキー認証を開始できませんでした」の**汎用 alert のみ**が出る。
**流量制限だと分からない**ため、ユーザーは何度も再試行してしまう (状況を悪化させる)。

- species: `ux_dead_end:passkey:read:guest` / oracle: `H4`
- 証跡: `devnotes/20260811-003230-bug-hunt/shard-2/screenshots/F-2-02-passkey-429.png`

**阻害されているユーザージョブ**: パスキーでログインする。待てば解決すると分かれば待てる。

---

## 設計で決めるべきこと

1. **F-2-01 の状態の切り方**。`hasBillingAccess` の真偽値を何に置き換えるか。
   最低限「未契約」と「支払い失敗」を区別する必要があるが、**他に区別すべき状態があるか**を実コードで確認する
   (試用中 / 猶予中 / 解約予定 など)。**enum で持つか、既存の DTO を拡張するか**を判断する。
   なお `App\Enums\...` の作法と TS 同期テスト (`enum-ts-sync-gate` 系) がある点に注意。
2. **F-2-02 の粒度**。429 だけを特別扱いするのか、他のエラーも分類するのか。
   **今必要なものだけ作る** (思考原則 2)。429 は「待てば直る」という他と質の違う情報なので、
   それだけを区別する最小形で足りる可能性が高い。
3. **2 件を 1 つの仕組みにまとめるべきか**。どちらも「状態を区別しない汎用メッセージ」だが、
   **層が違う** (片方は Inertia props の設計、片方はフロントの 429 ハンドリング)。
   **無理に共通化しない**判断もありうる。設計者が根拠を示して決めること。
4. **再発防止**。機械で守れるか。守れないなら「保証しないもの」に正直に書く。

## 読むべき現行コード

- `resources/js/pages/Dashboard.svelte` と、その props を組み立てる Controller
- `hasBillingAccess` の定義元 (`app/Services/Billing/` 配下)
- `App\Enums\Billing\` の既存 enum (状態の語彙が既にあるか)
- passkey ログインのフロント (`resources/js/` の passkey 関連) と `throttle:passkeys` の limiter 定義
- `app/Exceptions/InertiaExceptionRenderer.php` (aicue:T129 で入れた Error 画面差し替え。
  429 の扱いが既にあるかを確認する)

## やらないこと

- **課金ゲートの判定ロジック自体は変えない** (誰が何にアクセスできるかは変えない)。表示の問題である。
- 流量制限の閾値は変えない (AGENTS.md「閾値は既存値を変えない」)。
