# 対応マトリクス: design-review Round 1

## [Critical] (M2) `declaredClassifications` の外側キーをソートせず順序込みで比較している
- 判断: 対応する
- 根拠: 実装すれば必ず赤くなる実バグである。定数の宣言順は `value_pin → required_key` で、
  比較相手の `$expectedKinds` は `sort()` 済み (`required_key → value_pin`) なので
  `array_keys() !== $expectedKinds` が常に真になり、現物の台帳も V11 の正例も落ちる。
  連想 map の宣言順を仕様にしない、という指摘のとおり。
- 対応内容: `$declaredClassifications` も `ksort()` してからキー集合を比べる形に直した
  (`$declaredKinds` と同じ扱い)。あわせて M2 の「リスク」から
  「申告 map のキーを昇順で書く必要がある」という注記を削除した (順序に依存しなくなったため)。

## [Critical] (M4) 正典 i1 と `collectUnresolvedEnvRefs()` の 3 枚走査が矛盾する
- 判断: **反論する** (実装は現状維持。ただし docblock の書き方は指摘どおり直す)
- 根拠: 3 つある。
  1. **正典 s11 が明示的に裁量としている**。「対象は本 feature の見本 1 枚に限る
     (**他の commit 済み env ファイルへ広げるかは、それぞれを担当する feature の判断**)」。
     i1 が定めるのは「本 feature が守る対象」であって、「この gate のファイルに他 feature の
     関心事を 1 行も置いてはならない」ではない (それを定めるのは i14 で、i14 は
     **同じ関心事の検査を別名のファイルへ並置しない**ことしか要求していない)。
  2. **正典 s1 が同型のはみ出しについて撤去を求めないと明記している**。aigenba が本番ひな形を
     同じ gate の第 2 対象として抱えている件を「守りすぎではなく帰属のはみ出し」と裁定し、
     「**実装の撤去は求めない (検査能力を失わせないため)**」と書いている。本件は同じ形である。
  3. **狭めると実際に検査能力が失われる**。`tests/Architecture/BughuntEnvExampleContractTest.php`
     の docblock は「注: `${VAR}` 未解決参照の**一般則は EnvExampleInvariantTest が本ファイルも
     含めて検査済み**。本テストは『最小セットの存在と値』の契約に限定する」と明記しており、
     bughunt 側の gate は `APP_NAME` の `${...}` だけを見る。3 枚から 1 枚へ狭めると
     `.env.bughunt.local.example` の一般則と `.env.testing` の検査が**どの gate にも無くなる**
     (禁止事項 3「既存テストの削除・上書き」にも触れる)。
     移設先の候補である「テスト lane の env の前提を担当する feature」は正典の未決論点 q1 で
     **まだ台帳に存在しない**ので、今移設すると受け皿の無い削除になる。
- 対応内容: 指摘のうち**docblock の過剰主張は直した**。
  「走査対象は `.env.example` の中身だけ」ではなく、
  「**本 gate の主対象**は `.env.example` 1 枚 (正典 i1)。末尾の `${VAR}` の検査だけは
  commit 済みの見本 3 枚を見る = 正典 s11 の裁量の行使であり、帰属のはみ出しであって
  過剰ではない (s1 が同型の件で撤去を求めていない)。移設先の feature が台帳に立ったら
  そちらへ渡す」と書き、保証しないもの一覧にも 1 項目として明記した。

## [Warning] (M1) CR 単独改行の検出力が裏取りされていない
- 判断: 対応する
- 根拠: 妥当。現行 docblock は「反証の表に CR 単独の行は無い」と自ら注記して保証範囲を
  狭めていたが、変更後の docblock は「CRLF / CR / LF のいずれでも行に割る」と書くので、
  注記を消すなら裏取りが要る (走査器規約 (c))。
- 対応内容: **R29 `"A=1\rB=2"`** を正例として追加し、`ENV_EXAMPLE_COUNTEREXAMPLE_IDS` を
  R1〜R29 の 29 件へ更新した。解析器の docblock からは CR 単独の保証範囲の注記を外した
  (裏取りが付いたため)。

## [Warning] (M2) V 系データセットに床が無い
- 判断: 対応する
- 根拠: 妥当。R 系にだけ床を置いても、V1〜V10 を消して V11 だけ残す差分が緑で通る
  (まさに i9 が塞ぐ形の穴)。
- 対応内容: `ENV_EXAMPLE_LEDGER_COUNTEREXAMPLE_IDS` を新設し、識別子の完全一致と
  負例・正例がどちらも 1 件以上あることを床の検査で見る形にした
  (R 系の床と同じテストに 2 系統まとめて置く)。

## [Warning] (M2) 負のコントロールが新設した分岐を網羅していない
- 判断: 対応する
- 根拠: 妥当。未知の種別・固定値の改行/禁止文字・申告 map の外側キー不整合・空白の分類名・
  申告件数 0 の分岐は V1〜V11 では踏まない。V1 の期待メッセージも「空の台帳」だけなので
  申告値の検査が壊れても緑になる。
- 対応内容: **V12〜V18 を追加**し、判定分岐と期待メッセージを 1:1 で対応させた
  (V12 種別の申告のキー集合 / V13 分類の申告のキー集合 / V14 種別の申告件数 0 /
  V15 空白のみの分類名 / V16 分類の申告件数 0 / V17 未知の種別 /
  V18 固定値に改行または禁止文字)。V1 は「空の台帳」の期待メッセージのままとし、
  申告値の検査は V14 / V16 が独立に押さえる形にした。

## [Warning] (M2) 固定値の禁止文字検査が `preg_match(...) === 1` で fail-open
- 判断: 対応する
- 根拠: 妥当。M1 で「`false` を畳まない」と宣言したのに同じファイルの別関数で畳んでいたら
  規約 (b) の不整合である。
- 対応内容: 誠実性の検査の中の `preg_match()` 2 か所 (キーの綴り = 規則 3 /
  固定値の禁止文字 = 規則 6) を、戻り値を変数で受けて `Assert::notFalse()` を通してから
  `=== 1` を判定する形に直した。
