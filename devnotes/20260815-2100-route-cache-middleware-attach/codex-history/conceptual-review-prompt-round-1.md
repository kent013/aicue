## 概念設計

# 概念設計: route-cache-middleware-attach (経路キャッシュ起動での middleware 後付けの契約を決着させる)

## 背景・課題

### 何が問題か

vendor (Fortify / laravel-passkeys / Cashier) が登録した route へ、アプリ側が起動完了後に
middleware を後付けする経路が 2 本ある (`RouteThrottleBinder` / `RouteMiddlewareBinder`)。
この後付けが載せているのは装飾ではなく保護そのものである:

- `recent-auth` — 2FA の秘密 (QR / セットアップキー / リカバリコード) を返す GET 3 本の step-up
- `ensure-login-method` — passkey 削除時の「最後のログイン手段を失わせない」guard
- `throttle:passkeys` / `throttle:two-factor-secret-read` — 連続取得と総当りの上限
- `no-store` — WebAuthn challenge を載せた応答をキャッシュさせない

現在の契約は「**経路キャッシュ (route cache) がある起動では後付けを 1 本も走らせない**」であり、
cached 起動で実際に効いているのは **cache ファイルに焼き込まれた内容だけ**である。
したがって **古い cache のまま起動すると保護が無音で外れる**。実測されている壊れ方は
「鮮度切れセッションの 2FA 秘密 GET が 409 でなく 200 で秘密を返す」「passkey 削除の
手段保持 guard が消える」で、どちらも**誰も気づかないまま本番が無防備になる**型である。

この危険を今日押さえているのは `AGENTS.md` と `docs/app-integration-guide.md` §7c に書かれた
**「`php artisan route:cache` を毎デプロイ再生成する」という人手の運用要件だけ**である。

### 家系の機能台帳 (lctl) の観測

機能 `route-cache-safe-middleware-attach` において本リポジトリは `update_pending` である。
理由は、家系の正典 (a) 形 = 「経路の一覧が組み上がった後に走らせる専用の実行点クラスを 1 つ持ち、
経路キャッシュ起動でも後付けを効かせる」に到達しておらず、採ったのが (b) 形 =
「cached 起動では走らせず、cache 生成時の焼き込みを実効とする」の変種だからである。
台帳の裁定は (b) を「**デプロイのたびの再生成が機械強制される場合に限り許容**」としている。

その許容条件は 2026-08-09 に**不成立**が確認されている — 本リポジトリにデプロイ定義の実体は
1 つも無く (`deploy/` / terraform / k8s / Procfile / fly / render / CI のデプロイ job のいずれも無い)、
`route:cache` を実行する記述は追跡下に 0 件で、`composer.json` の scripts にも無い。
つまり毎デプロイ再生成は**説明文としてしか存在せず、検査も無い**。

### 残タスクの二択と、この二択に効く自リポジトリの規約

台帳が示す残タスクは「(1) 毎デプロイ再生成の**機械強制**を足す」か「(2) 正典 (a) 形へ**移行**する」の
どちらかである。ところが `AGENTS.md` の route:cache 運用要件の節が

> 本リポジトリにデプロイ定義は無い。よって現在この要件は人手でのみ守られている。
> デプロイ基盤を作る PR は、本要件と TRUSTED_PROXIES 運用要件 (T108) の 2 つを実装するまで
> 完了にできない。**存在しない基盤のための preflight 機構を先回りして作らないこと (思考原則 2)**。

と明記しているため、(1) は現時点で構造的に採れない。よって決めるべきは (2) を採るか、
採らないなら**その判断を逸脱として登録する**か、である。

## 改善アイデア

### 結論: (2) 正典 (a) 形へは今は移行しない。判断を逸脱として登録し、前提を機械で固定し、保護の所在を回帰で固定する

3 つの施策で構成する。

1. **判断の登録** — 「正典 (a) 形の実行点クラスへ移行せず、(b) 焼き込み変種を維持する」ことを
   `docs/template-divergence.md` へ逸脱として登録する (根拠・保証し続ける不変条件・**再検討の条件**つき)。
   `AGENTS.md` と `docs/app-integration-guide.md` §7c からその登録を指す。
2. **前提の機械固定 (トリップワイヤ)** — (b) を選べる前提そのもの =
   「デプロイ定義の実体が無く、`route:cache` を実行する記述が追跡下に 1 件も無い」を
   deny-by-default の検査で固定する。前提が崩れた瞬間 (デプロイ定義や `route:cache` の実行行が
   入った瞬間) に赤くなり、失敗メッセージで次の担当者へ二択 ((a) 形への移行 / 毎デプロイ再生成の
   機械強制) を提示する。
3. **保護の所在を回帰で固定** — 「後付けは cache 生成時に焼き込まれる」と
   「焼き込みが欠けた cache で起動すると保護が無音で外れる」の**両面**を、
   別プロセスを起こさずに常設のテストへ落とす。

### なぜ (2) を今やらないのか (根拠)

- **今日この壊れ方は起こり得ない**。`route:cache` は開発・CI・bug-hunt のどこでも実行されておらず
  (bug-hunt が呼ぶのは `optimize:clear` = 消す側)、本番デプロイ自体が存在しない。
  つまり (a) 形が防ぐ事故の発生確率は現時点でゼロである (思考原則 2: 今必要なものだけ作る)。
- **(a) 形は見た目より重い**。Laravel 13 の実機序を読むと、(a) を正しく作るには
  「容器の `routes` 束縛の張り替えを捕まえる」「その束縛が**まだ無い**ときに張り替えが
  発火しない穴 (= 無音の fail-open) を自分で塞ぐ」「経路一覧の実体ごとの冪等」
  「cached 起動で fail-fast すると `route:list` も `route:clear` も落ちて復旧手段を失う問題
  (T120 と同型) への例外設計」の 4 つを同時に解く必要がある。さらに実証には
  別プロセスで起動する検査基盤が要る (家系では `subprocess-boot-probe-harness` として
  独立の取り決めになっており、本リポジトリは未導入)。
- **(a) を採る本当の利益は「運用要件を 1 つ消せること」**であり、その運用要件が効く相手
  (デプロイ基盤) がまだ無い。基盤を作る PR の時点で (a) 形への移行を選ぶ方が、
  実物のデプロイ手順と突き合わせて設計できるぶん確実である。
- 逆に**今やる価値が高いのは「前提が変わったことに気づける状態にすること」**である。
  今の弱点は (b) を選んでいること自体ではなく、**(b) が成り立つ前提が声に出して固定されておらず、
  崩れても誰も気づかない**ことである。

### なぜ施策 2 は「先回りの preflight 機構」ではないか

`AGENTS.md` が禁じているのは「**存在しないデプロイ基盤のための** preflight 機構」= デプロイの
正しさを事前検査する仕組みを先に作ることである。施策 2 が固定するのは**逆方向**で、
「その基盤がまだ無い」という**免除の前提**である。同じ形は本リポジトリに既にあり
(`ThrottleExemptionPremiseTest` / `IdempotencyExemptionPremiseTest` = 免除の前提を機械で固定する)、
新しい発明ではない。デプロイの正しさは 1 ミリも検査しない。

## 期待効果

- **使命への貢献**: 撮影 PWA (ドメイン規約 3) と 2FA / passkey の保護は、認証面の後付け
  middleware に乗っている。無音で保護が外れる経路を「気づける」状態にすることは、
  現場作業者の組織データを預かる前提条件である。
- 台帳上の宙ぶらりん (`update_pending` / `divergence_candidate`) が、**明示的に登録された逸脱**へ
  変わる。次に触る人が「未着手なのか、判断済みなのか」を読み違えない。
- 実測でしか語られていなかった「stale cache は無音で保護を外す」が、**常設の回帰テスト**になる。
  台帳・docblock の主張が口伝でなくなる。
- 前提が崩れた瞬間 (デプロイ基盤の追加) に、必要作業が失敗メッセージとして提示される。

## 実装方針（概要）

### 施策 A: 逸脱の登録 (ドキュメントのみ)

- `docs/template-divergence.md` に新エントリを追加する (既存の最新は D18 なので **D19**)。
  - 観点の表: 「実行点」「経路キャッシュ起動での契約」「実証方法」をテンプレート/家系正典と本アプリで対比
  - なぜ logic-driven か: 上記「なぜ (2) を今やらないのか」
  - 揃えている不変条件: 「後付けした保護は実効の経路に必ず載る」「後付けの入口は 2 binder に限る」
    「経路名が消えたら起動を止める」を、どの機構が保証し続けるか
  - **再検討の条件 (解消条件)**: デプロイ定義が入る / `route:cache` の実行が入る / 家系の裁定が変わる
- `AGENTS.md` の route:cache 運用要件ブロックへ 2〜3 行追記 (家系の正典は (a) 形であること、
  本リポジトリは (b) を選び D19 として登録済みであること、前提は機械で固定してあること)。
- `docs/app-integration-guide.md` §7c の「現状」段落から D19 と前提検査を指す。

### 施策 B: 前提のトリップワイヤ (新規 Architecture テスト 1 本)

`tests/Architecture/RouteCacheDeploymentPremiseTest.php` (新規)。git 追跡下のファイルを走査し、
次の 2 つを 0 件で固定する。

1. **デプロイ定義の実体が無いこと** — `deploy/` / `terraform/` / `*.tf` / k8s manifest 置き場 /
   `Procfile` / `fly.toml` / `render.yaml` / `app.yaml` / `.ebextensions/` / `ansible/` /
   `.github/workflows/` 内でデプロイを名乗る job のいずれも存在しないこと。
2. **`route:cache` を実行する記述が無いこと** — 追跡下の**非 PHP・非 Markdown** ファイルに
   `route:cache` と「`artisan optimize` (後ろに `:` が続かない形)」が現れないこと。
   `optimize:clear` (消す側。bug-hunt が使う) は対象外。

赤くなったときのメッセージで、二択と参照先 (D19 / §7c / AGENTS.md) を提示する。
**保証範囲を誇張しない**: PHP からの `Artisan::call(...)` や Markdown 中の説明文は見ない。
これは「前提が変わったことに気づかせる」ためのものであって、デプロイの正しさの検査ではない。

### 施策 C: 焼き込みと剥落の 2 面を回帰で固定 (新規 Feature テスト 1 本)

`tests/Feature/Security/RouteCacheBakedProtectionTest.php` (新規)。
**別プロセスも route cache ファイルの生成も要らない**方式にする。鍵は 2 つ:

- `RouteCollection::compile()` は `php artisan route:cache` が**ファイルへ書き出すのと同じ配列**
  (`compiled` + 経路名ごとの `attributes`) を返す。テストは cache 無しで起動しているので、
  後付けは既に走っている。よって `compile()` の中身を見れば「**焼き込まれるはずの内容**」を
  そのまま検査できる。
- `Router::setCompiledRoutes()` は同じ形の配列を受け取る。**alias を 1 本抜いた配列**を流し込めば、
  「古い cache で起動した状態」を同一プロセス内で再現でき、HTTP 応答の差
  (409 → 200) を実測として固定できる。

固定する 2 面:

1. **焼き込みの実証**: `compile()` の `attributes` に、2FA 秘密 GET 3 本の `recent-auth` と、
   passkey 系の `throttle:passkeys` → `recent-auth` → `ensure-login-method` が**この順で**載っていること。
2. **剥落の実証 (負のコントロール)**: 同じ配列から `recent-auth` を 1 本抜いて流し込むと、
   鮮度切れセッションの 2FA 秘密 GET が **409 でなく 200 で秘密を返す**こと。
   抜かずに流し込んだ場合は 409 のままであること。

これで「保護を持っているのは cache の中身である」という契約が、文章ではなく振る舞いで固定される。

## 制約・前提

- **アプリのコード (`app/`) は 1 行も変えない**。後付けの内容・順序・入口を絞る目録
  (`PostBootRouteMutationInventoryTest`) はいずれも T135 が固定したもので、本設計はこれを壊さない。
- 走査対象に `app/` を足さないので `PostBootRouteMutationInventoryTest` の allowlist は不変。
- 施策 C は `RefreshDatabase` グローバル適用・`--parallel` 実行の既定に従う (個別 `DatabaseTransactions` は使わない)。
- 施策 C は同一プロセス内で経路一覧を差し替えるため、**テスト内で後始末が要る** (差し替えたまま
  他テストへ漏らさない)。Laravel のテストはテストごとにアプリを作り直すため既定では漏れないが、
  設計上明示する。

## スコープ外
