# 対応マトリクス: conceptual-review Round 2

## [Critical] `Inactive` の分割が不足 (Incomplete → fallback 不可 とすべき)
- 判断: **一部対応・一部反論**
- 根拠:
  - 賛成する部分 = 状態ごとに意味を固定する必要がある、という指摘そのもの。判断基準を
    「提供済みの利用に対する**未回収の請求**が残っているか」の 1 つに定め、全 case に
    理由を付けた。
  - 反論する部分 = `Incomplete` を fallback 不可にすること。Stripe の `incomplete` は
    **初回請求が完了しておらず契約が成立していない**状態で、提供済みの利用も未回収の請求も無く、
    23 時間で自動的に `incomplete_expired` になる。ここで無料枠の読み替えを止めると、
    カード認証 (3-D セキュア) 待ちの数時間だけ**無料利用者を締め出す**副作用が出る。
    無料枠は暗黙の空欄ではなく申告済みの明示レコードであり、有料契約の初回決済が通らなかった
    ことはその申告を取り消す理由にならない。AG-035 (3) が禁じたのは
    「サブスクリプション不在 = 無料」という**暗黙の読み替え**であって、明示申告の否定ではない。
  - `Paused` も同じ理由で可へ変更した (trial 終了 & カード無しの read-only。請求は発生していない)。
    Round 1 で不可にしていたのは「Stripe 上まだ生きている契約」という粗い基準だったが、
    未回収の請求の有無で見ると不可にする理由が無い。
- 対応内容: `allowsFreePlanFallback()` は `PastDue` / `Unpaid` のみ不可。`Unpaid` の 1 case
  追加は維持する (`canceled` と答えが逆になるため)。`Incomplete` / `IncompleteExpired` を
  `Inactive` から分割する enum 変更は行わない (答えが同じ case を増やさない)。
  詳細設計では Stripe status 文字列 → `SubscriptionState` → `allowsFreePlanFallback()` を
  1 つのテーブル駆動テストで固定する。

## [Warning] PM の「観測できた」と「false」を型で区別する
- 判断: 対応する
- 根拠: 指摘のとおり。展開されていない応答を `false` と読むと既存の単調性を守れない。
- 対応内容: gateway が返す DTO の PM フィールドを `?bool` にし、**null = 観測できなかった**と
  定義。書き込むのは明示的に `true` を観測できたときだけ、と概念設計 (c) に明記した
  (専用 enum は作らない — 3 値を表す最小の型で足り、語彙を増やす理由が無いため)。

## [Warning] 仮説の成功条件 3 が保証範囲と矛盾
- 判断: 対応する
- 対応内容: 成功条件 3 を「日次突き合わせが**正常完了した契約について** `stripe_status` は
  Stripe の観測値へ収束し、PM 登録の取りこぼしは true 方向に修復される」に限定し、
  「翌日」を「次に突き合わせが正常完了したとき」に直した。404 / API 障害 / scheduler 停止では
  収束しないことも併記した。

## [Warning] 「無期限の利用が止まる」は無条件には保証できない
- 判断: 対応する
- 対応内容: 保証を「**アプリが `past_due` を観測できた契約では**無期限の利用が止まる」に限定し、
  観測できていない契約は止まらないことを「主張しないこと」に明記。埋め合わせとして
  未確認・失敗の件数を監視対象に定義した。

## [Warning] reconcile の運用上の収束条件が不足
- 判断: 対応する (5 点すべて)
- 対応内容: (c) に運用契約として明記 — 重複起動の抑止 (onOneServer + withoutOverlapping +
  Cache::lock) / `chunkById` 分割 / 1 件失敗で止めない / 確認・収束・未確認・失敗の 4 件数と
  id のみを 1 回だけ集約報告 (PII を載せない) / **失敗が 1 件でもあれば異常終了コード**。
  404 (未確認) は状態を変えないので正常終了だが件数が 0 でなければ必ず報告に出す
  (= 未確認を無言の成功にしない)。監視対象も明記した。

## [Suggestion] Architecture テストで migration を無条件許可しない
- 判断: 対応する (構造で母集団外であることを明記する形)
- 根拠: 本検査の走査根は `app/` のみで、`database/migrations/` はそもそも母集団に入らない。
  許可リストに足すのではなく「保証範囲外である」と書くのが事実に合う。
- 対応内容: (a) に「走査根は `app/` だけなので migration と生 SQL は母集団に入らない。
  移行が 1 本きりであることは詳細設計のファイル一覧で固定し、runbook で手動 SQL を禁じる」
  と明記した。

- 判断: 変更なし (すでに反映済み)
