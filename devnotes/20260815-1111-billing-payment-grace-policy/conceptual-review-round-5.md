全体判定: **APPROVED**

Round 4 の指摘はすべて意図どおり解消されています。契約終了後の債権管理を entitlement から分離する事業判断、観測順序に関する保証範囲、ロック期限と実行上限の関係が明確になりました。概念設計として詳細設計へ進めます。

## 1. 使命との整合性

[Suggestion] 問題ありません。

支払い失敗中の有料利用を有限化しつつ、終了した契約の債権管理によって明示的な無料資格まで失わせない設計は、利用体験と原価管理の両方に整合しています。

## 2. 禁止事項違反

[Suggestion] 違反はありません。

テストファースト、Architecture テスト、単一 writer、DTO、実 Stripe を呼ばないテスト方針まで実装完了条件に含まれています。

## 3. 実現可能性

[Suggestion] Laravel 12 の scheduler、Cache lock、chunk 処理、service transaction、gateway interface で実現可能です。

`SubscriptionSnapshot` と PM の三値観測を SDK 境界で正規化するため、webhook と reconcile を同じ更新経路へ収束させる構造も成立しています。

## 4. 期待効果の妥当性

[Suggestion] 保証と非保証が適切に分離されています。

特に以下が明確です。

- 猶予起点は失敗実時刻ではなく観測時刻
- reconcile は次回正常完了時に収束
- PM は true 方向だけ修復
- 404・API 障害中は収束しない
- webhook と reconcile の瞬間的な順序は保証しない

効果の誇張は解消されています。

## 5. リスク

[Suggestion] 「回収中」という語だけは、詳細設計時に定義を少し正確にしてください。

Stripe の `unpaid` は督促処理を終えている場合があるため、「Stripe が現在取り立てている最中」という字義とは完全には一致しません。実際の判定は明確なので概念上の阻害事項ではありませんが、次の表現がより正確です。

> 契約が終了しておらず、支払い不健全を理由に無料枠 fallback を認めない状態

`PastDue` / `Unpaid` を不可とする状態表自体は妥当です。

ロックについて、次は詳細設計で扱う実装事項です。

- TTL と実行時間上限の具体値
- 1 chunk の最大処理時間と Stripe timeout を含む停止余裕
- ロックキーと scheduler 側ロック名
- 時間上限・ロック取得失敗時の終了コード
- 報告する organization id が多い場合の件数上限と省略表現

これらは値とテスト方法の確定であり、概念設計の差し戻し理由ではありません。

## 6. スコープの適切さ

[Suggestion] 適切です。

債権追跡、猶予残日数 UI、通知追加、Stripe dunning 設定を分離したことで、AG-035 (5)(6) を満たすための変更に収まっています。関連する無料枠 bypass と二重契約防止を同じ PR に含める判断も妥当です。

## 7. 型安全性

[Suggestion] 問題ありません。

詳細設計では次をテスト計画へ具体化すれば十分です。

- Stripe 全 status → `SubscriptionState` → fallback 可否
- `past_due_since` の初回打刻・維持・解除
- `null / false / true` の PM 観測と `=== true` の更新条件
- `incomplete` が有料 entitlement を得ないこと
- 有料チケットの付与契機
- 古い観測が後勝ちし得ることを前提とした次回 reconcile での収束
- lock、時間上限、404、部分失敗、集約報告の各終了状態
