全体判定: **CHANGES_REQUESTED**

`Incomplete` を fallback 不可にする必要がある、という Round 2 の結論は撤回します。今回示された基準に照らすと、明示的な無料枠を維持する設計は成立します。ただし、その反論を成立させる重要な前提が設計に固定されておらず、Stripe の請求状態に関する記述にも不正確さが残っています。

## 1. 使命との整合性

[Suggestion] 整合しています。

初回決済の認証待ちだけを理由に、既存の明示的な無料利用資格まで失わせない判断は、「思考ゼロ」で利用できる体験を不必要に中断しないという使命にも合います。

## 2. 禁止事項違反

[Suggestion] 明示的な違反はありません。

テストファースト、Architecture テスト、外部通信の gateway 隔離、migration と通常 writer の保証範囲の区別も適切です。

## 3. 実現可能性

[Warning] `Incomplete` に関する反論は方向として成立しますが、「未回収の請求を残さない」という説明は正確ではありません。

Stripe の `incomplete` は通常、初回 invoice の支払いが未完了で、PaymentIntent が認証待ちまたは失敗している状態です。つまり invoice 自体は存在し得ます。今回の判断を支える本質は「請求が存在しない」ことではなく、次の2点です。

- 有料サービス・有料チケットをまだ提供していない
- fallback で許可するのは、以前から明示的に付与されている無料枠だけ

修正提案: 判断基準を「未回収請求の有無」だけにせず、次のように直してください。

> 有料の利用権・チケットを提供済みで、その対価が未回収か。未提供であれば、既存の明示的な無料資格は維持できる。

併せて、`invoice.paid` より前には有料チケットや有料 entitlement を一切付与しないことを既存テストで確認し、不足していれば Feature/Architecture テストに登録してください。この不変条件が成立するなら、`Incomplete` を分割せず fallback 可とする判断を承認できます。

[Suggestion] `Paused` を fallback 可とする整理も、Stripe の「trial 終了時に請求を発生させず pause する」状態だけへ正しく対応付けられている限り妥当です。status 文字列から内部状態へのテーブル駆動テストで固定する方針が重要です。

## 4. 期待効果の妥当性

[Warning] 「期待効果」に古い保証表現が残っています。

> 翌日の突き合わせで両方向に収束する

これは修正済みの仮説および「期待効果として主張しないこと」と矛盾します。404、API 障害、scheduler 停止では翌日に収束しません。

修正提案:

> `stripe_status` は、次にその契約の突き合わせが正常完了したとき、Stripe 側の観測値へ両方向に収束する。PM は true 方向のみ修復する。

## 5. リスク

[Warning] `onOneServer`、`withoutOverlapping`、`Cache::lock` の三重ロックは、責務と有効期限を決めないと過剰かつ危険です。

特に scheduler のロックとコマンド内部のロックが別キー・別 TTL になると、一方だけ残留して実行が長期間抑止される可能性があります。

修正提案: 各層の責務を明記してください。

- `onOneServer`: 複数 scheduler ノードからの同時起動防止
- `withoutOverlapping`: scheduler による前回実行との重複防止
- `Cache::lock`: 手動実行を含むコマンド本体の排他

手動実行との排他が要件でなければ `Cache::lock` は削除できます。必要なら、ロックキー、TTL、解放方法、取得失敗時の非ゼロ終了を詳細設計で固定してください。

[Suggestion] 404 を状態変更なし・集約報告あり・正常終了とする判断は許容できます。ただし「監視対象」と書くだけで報告が捨てられる構成なら意味がないため、既存の報告経路へ確実に接続されることをテスト対象に含めるべきです。

## 6. スコープの適切さ

[Suggestion] 過大ではありません。

`Incomplete` と `IncompleteExpired` は今回の fallback 結論が同じであるため、内部 enum を分割しない判断は「今必要なものだけ作る」に沿っています。Stripe status ごとの期待値を変換テストに残せば、将来判断が分かれた時点で分割できます。

## 7. 型安全性

[Suggestion] `?bool` による `true / false / unknown` の表現は、この用途では十分です。

ただし PHPDoc または DTO の constructor 名で、`null` が「PM なし」ではなく「未観測」であることを固定してください。書き込み条件は `=== true` とし、truthy 判定にしないテストが必要です。

結論として、Round 2 の核心だった `Incomplete` の分割要求については、今回の反論を受け入れます。残る必須修正は、判断基準を「請求の存在」から「有料価値の提供済みかつ未回収」へ正し、その前提をテスト可能な不変条件として固定すること、および残存する「翌日収束」の表現を除くことです。
