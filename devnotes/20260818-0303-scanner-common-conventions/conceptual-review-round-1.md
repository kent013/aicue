## 全体判定: CHANGES_REQUESTED

使命への間接的な整合性、Laravel/Pest による実現可能性、索引を今回作らないスコープ判断は概ね妥当です。ただし、正典 v1 への「追従完了」を主張するには、既知の fail-closed 違反と規約の適用境界を解消・明確化する必要があります。

### 1. 使命との整合性

[Suggestion] 使命への寄与は適切に「間接」と位置付けられています。テナント境界、PWA の秘匿性、プロンプト防御を支える gate の見逃しを減らすことは、標準化された安全な撮影・動画作成体験の前提になります。

[Warning] 「台帳の pending 理由が解消する」と断定していますが、既知の D1 が正典 (a)(b) に抵触したままです。規約を文書化した事実と、機能が正典準拠になった事実は分けるべきです。

修正提案: 期待効果を「規約未成文化という pending 理由の解消候補」へ弱め、台帳の更新可否は監督セッションが D1/D2 を含む例外の扱いを確認して決める、と明記してください。

### 2. 禁止事項違反

[Warning] 文書変更だけで完了する方針自体は、列挙された禁止事項には抵触しません。ただし「新設・変更する gate はテストファースト」を新規規約に置く一方、今回の文書規約には検証機構を設けません。禁止事項の「テストなしの実装完了報告」と緊張します。

修正提案: 今回は「規約本文の変更」であって gate 実装ではないことを明記し、少なくとも既存の AGENTS.md 同期検査を実行する前提にしてください。将来、規約違反を機械で防ぐものではないことも明記すると、保証範囲が正確です。

### 3. 実現可能性

[Critical] (b) を全走査器へ文字どおり適用すると過剰です。「抽出 0 件」「目録が空」を常に fail-closed とすると、違反サイトが存在しないこと自体が正常な検査や、任意ディレクトリを対象とする再利用可能な検出器まで失敗します。D2 の候補抽出も heuristic であり、空振り検査が必要な gate を網羅的に確定していません。

修正提案: (b) の対象を明示してください。例えば「違反を検出する gate で、対象母集団または期待される inventory が非空であることが不変条件の場合」に限り空振りを fail-closed とし、検出器単体・違反ゼロが期待される検査には適用しない、とします。各 gate が母集団非空を必要とする理由をテストで表現する設計にしてください。

[Warning] 「構文解析ライブラリは不要」は妥当ですが、字句走査で完全修飾名比較を行うなら、相対名・namespace alias・group use・動的構文をどう区別して `unresolved` にするかの契約が必要です。D1 はまさにその未解決部分です。

修正提案: 新規規約に「完全解決できない参照を完全修飾名として emit してはならない。`unresolved` として gate を失敗させるか、その構文を対象外として明示し、対象外なら検出力を主張しない」を加えてください。

### 4. 期待効果の妥当性

[Warning] 規約だけでは新規 gate 作成者が必ず (b)(c)(e) を守る保証はありません。参照実装 aigenba が索引と投影 gate を持つ理由は、規約の存在と実際の遵守を分離しないためです。本設計はその強制を意図的に持たないため、「毎回発明しなくてよい」「信頼度を支える」は合理的な期待ではあるものの、限定的です。

修正提案: 期待効果を「レビュー時の判断基準を揃える」「将来の gate 実装の設計漏れを減らす」に限定してください。遵守の自動保証、既存 gate 群の信頼性向上を直接主張しないでください。

### 5. リスク

[Critical] D1 はプロンプト防御・外部到達点というセキュリティ不変条件に関わる既知の見逃し経路です。それを「別 TODO」とするだけでは、規約導入によって既知の不適合を可視化したまま、実質的に容認することになります。また「別 TODO として起票する申し送り」は、実際の TODO 起票ではありません。

修正提案: D1 の是正を実装する必要は今回ありませんが、少なくとも追跡先となる具体的な TODO を起票し、その ID を divergence survey に記録してください。起票権限がない場合は、完了条件を「監督者が起票した TODO ID を追記すること」としてください。あわせて、D1 の影響範囲と、当面完全検出を主張できない対象を既存 docblock に明記する必要があります。

[Warning] 「索引が無いせいで漏れた実測が 2 度目に出たら起票する」は、索引なしでは漏れ自体を系統的に観測しにくいため、実効性が弱いトリガーです。

修正提案: 回数基準ではなく、「新設 gate のレビューで規約適用漏れが判明した」「走査器候補の棚卸しが再度必要になった」など、観測可能な事象を起票条件にしてください。

### 6. スコープの適切さ

[Suggestion] 今回、索引・投影 gate・共通基盤統合を作らない判断は妥当です。正典 v1 の必須要件ではなく、候補抽出器から始めると文書化より大きな実装・検証案件になります。既存の三層構造を壊さない点もよいです。

[Warning] 一方で棚卸しの「検出器」「gate」の母集団定義が限定的です。`tests/Architecture/*.php` と JS の特定ディレクトリだけでは、他のテスト階層や scripts/configuration に存在する走査ロジックを除外し得ます。「既存の走査器・gate を棚卸し」という表現は広すぎます。

修正提案: 棚卸し対象を「定義したコマンドで列挙される候補」に限定して明記し、全数性を主張しないでください。全数棚卸しを将来必要とするなら、それが索引導入を再検討する条件になります。

### 7. 型安全性

[Suggestion] 本件は `AGENTS.md` と devnotes の文書変更であり、DTO / JsonResource / PHPStan level 10 に影響するアプリケーションコードはありません。Laravel 12、Svelte 5、Inertia.js の型安全性に関する実装上の懸念もありません。

[Warning] 将来の `unresolved` 導入では、曖昧な `string|null` や例外握り潰しで表現すると PHPStan level 10 と fail-closed の意図を損ねます。

修正提案: 将来 TODO の設計条件として、解決結果を判別可能な値オブジェクトまたは明示的な例外で表し、未解決を通常の完全修飾名文字列へ混ぜないことを記録してください。
