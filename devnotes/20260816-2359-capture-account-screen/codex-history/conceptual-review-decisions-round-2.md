# 対応マトリクス: conceptual-review Round 2

## [Warning] 案 B を退ける論理が成立していない (最大論点)
- 判断: **反論する (案 A を維持)。ただし根拠を全面的に書き直す**
- 根拠: Round 1 版の「案 B では確認後も `/settings` が着地になる」という論法は、指摘のとおり
  ドロワーに email を出せば崩れる。よってその論法は捨てる。代わりに、**現行 `AppLayout` の
  該当ブロックを実読して分かった具体的事実**を根拠にする。
  1. **置き場所が `truncate` + `text-caption` の 2 行ブロックしかない**。
     desktop は `width: 256px` 固定のサイドバー、mobile は `w-64` (256px) のドロワーで、
     `px-2` と `size-9` のアイコン + `gap-2` を引くと文字に使える幅は約 **196px**。
     そこに `<p class="truncate …">` が並ぶ。`k.isitoya@example.co.jp` 級の実在するメールは
     12px でも収まらず**省略記号で切れる**。**先頭 20 数文字しか見えない識別子では
     「自分のアカウントか」を確かめられない** — 確認という目的そのものが達成できない。
  2. **DESIGN.md の役割マッピングに反する**。`DESIGN.md` L132-134 は
     「本文/入力値/主要数値 → `text-body`、ラベル/補助情報/日時 → `text-caption`」と定めている。
     ログイン ID は補助情報ではなく主要な識別値であり `text-body` で出すべき値である。
     ドロワーのブロックは設計上 `text-caption` (補助情報) の場所で、そこへ主要値を足すのは
     DS の役割マッピングを崩す。幅を広げる / ramp を上げるという回避は、
     **PC 全ページの共有 chrome のレイアウトを変える**話になり、案 B の「小さい」という長所を失う。
  3. **同じメニューに誤タップの隣接がある**。ドロワーは
     組織切替ボタン群 → 個人設定 / 組織設定 / CLI セットアップ / MCP セットアップ →
     詳細 (法務) → ログアウト の順に並ぶ縦スクロールである。共有端末の引き渡し時に
     「確認してログアウトする」だけをしたい利用者に、**組織切替と API 系セットアップが
     隣接した管理メニューを識別確認の手段として要求する**ことになる。
     使命の「専門知識ゼロの現場作業者」に対して、これは要求水準が高い。
  4. doc/05 §5.1 が独立した画面として要求していること。ただしこれは**主たる根拠ではなく裏付け**である
     (doc に書いてあるから作る、はしない)。
- **案 B が優れている点も明記して残す**: 変更が 1〜2 ファイルで済む。本設計はそれを承知のうえで、
  「識別子を省略なく読める場所」という機能要件のために案 A を採る。
- **Codex の折衷案 (AppLayout に Capture 文脈用 slot/prop を足す) も却下**: 共有 chrome に
  文脈分岐を持ち込むことになり、PC 面の回帰リスクという案 A 採用理由そのものと衝突する。
  さらに、それでも表示位置は 256px の truncate する列のままで、上記 1. と 2. は解決しない。
- 対応内容: §2 の比較表と本文を書き直した。
