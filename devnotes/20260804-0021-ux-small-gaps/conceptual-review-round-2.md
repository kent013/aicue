# 全体判定: CHANGES_REQUESTED

Round 1 の主要な論理的飛躍は解消されています。ただし施策 B の判定方法とセッション終了境界に、依然として重大な不足があります。

なお、現在提供されているリポジトリ参照手段を確認しましたが、シェル以外のテキストファイル読取ツールや code-review-graph MCP は利用できませんでした。「コマンド実行禁止」を守ると実ファイルを開けないため、指定されたファイル内容と delete route 全件は独立検証できていません。この事実検証未了も承認を妨げます。

## 1. 使命との整合性

[Suggestion] 施策 C を主施策とした優先順位は妥当です。2FA enrollment のデバイス依存を減らすことは、現場作業者の操作詰みを直接防ぎます。

[Suggestion] 施策 A/B は使命への寄与が間接的ですが、操作結果を明示する基盤品質としてスコープ内です。

## 2. 禁止事項違反

[Warning] B-1 の「pass なら観測 artifact と確定」は、テストファーストの形式は満たしても、仮説検証として成立していません。

修正提案: B-1 の成功条件を単なる toast 可視確認ではなく、次のように定義してください。

- リダイレクト完了直後、4秒未満で toast が表示される
- 4秒経過後には消える
- flash の toast 変換時点を component/store テストで別途固定する
- Chromium/WebKit 双方で同じ結果になる

pass が意味するのは「テスト環境では再現しない」までであり、H-b の確定ではありません。

## 3. 実現可能性

[Critical] B-2 の「AppLayout のログアウトハンドラで clear」だけでは、セッション終了境界を網羅できません。

ログアウト以外にも、少なくとも以下の authenticated → guest 遷移があります。

- アカウント削除
- セッション失効
- 認証ミドルウェアによるログイン画面への送還
- 別タブでのログアウト
- 将来追加される強制ログアウト

特に施策 A の対象であるアカウント削除は、AppLayout のログアウトハンドラを通りません。B-2 で `onDestroy(clearToasts)` を撤去すると、既存 toast を `/` に持ち越す可能性が残ります。

修正提案: 「ログアウト操作」ではなく、認証済み layout から未認証 layout への遷移を境界にしてください。汎用メタデータを追加しないなら、`GuestLayout` と `AuthLayout` の初期化時に次の順序を契約化する方法が単純です。

1. 既存 toast を消去
2. 着地レスポンスの flash を消費
3. 新しい toast を表示

これなら古い認証文脈を落としつつ、アカウント削除成功 flash は表示できます。

## 4. 期待効果の妥当性

[Critical] B-1 は H-a/H-b の「唯一の判別器」ではありません。

- fail: lifecycle 問題、4秒超過、テスト待機条件の誤りを区別できない
- pass: 本番の観測 artifact だったとは確定できない
- ブラウザ差やタイミング依存なら、同じテストでも揺れる可能性がある

修正提案: 結論を次の範囲に限定してください。

- fail かつ4秒未満で検査: H-a を支持する
- pass: 自動テスト条件では未再現
- bug-hunt の観測 artifact 確定には、bug-hunt の遷移完了から snapshot までの実測時間が必要

[Suggestion] 施策 C の効果主張は妥当です。

## 5. リスク

[Critical] B-2 の認証情報持ち越し防止が、明示ログアウトにしか効きません。

修正提案: 上記の未認証 layout 着地時の「clear → current flash consume」を、AuthLayoutを含めてテストしてください。最低限、以下を固定すべきです。

- 古い認証文脈 toast は guest/auth 画面に出ない
- アカウント削除の新しい success flash は出る
- セッション失効後のログイン画面に古い toast が出ない

[Warning] `onDestroy` 撤去後のタイマー安全性は、「DOM参照がない」だけでは十分ではありません。toast が自動消去された場合にも timeout ID の管理領域から削除されるか確認が必要です。

修正提案: `toast.ts` の timer Map/Set の生成・削除経路を詳細設計で確認し、auto-dismiss 後に管理エントリが残らないテストを追加してください。

## 6. スコープの適切さ

[Warning] A を無条件、B-2 を条件付きにすると、A 適用後から B-1 判定まで GuestLayout が既存 toast を描画するリスクがあります。

修正提案: 同一実装セッションでも順序を明記してください。

1. B-1 を現行コードで実施
2. C を実装
3. A と認証→未認証境界の安全策を同時実装
4. B-2 は B-1 の結果に応じて判断

A と guest 境界保護は不可分として扱うべきです。

## 7. 型安全性

[Warning] `TwoFactorQrCodeResponse` / `TwoFactorSecretKeyResponse` の型 alias だけでは、実行時レスポンスの妥当性は保証されません。`fetchJson<T>` の generic は型 assertion に近い可能性があります。

修正提案: 既存 `fetchJson` の設計に従い、少なくとも `svg` / `secretKey` が文字列であることを使用前に絞り込んでください。型を緩めず、取得失敗と不正レスポンスを同じ独立エラー経路へ流します。

[Suggestion] サーバ実装を変更しないため、PHPStan level 10への直接的影響はありません。

結論として、C は承認可能、A も認証→未認証境界の clear と一体なら承認可能です。B は「pass なら artifact 確定」を撤回し、明示ログアウトではなく全セッション終了遷移を覆う設計へ修正する必要があります。
