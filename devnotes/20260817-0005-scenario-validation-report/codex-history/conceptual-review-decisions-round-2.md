# 対応マトリクス: conceptual-review Round 2

Codex 判定: CHANGES_REQUESTED (Critical 0 / Warning 3 / Suggestion 5)。
「provider 実費の表現」と「根拠のない token 比率」を直せば APPROVED、との結論。

## [Warning] 「課金なし」「失うのは時間だけ」は利用者チケットと provider 実費を混同している
- 判断: **対応する**
- 根拠: 指摘が正しい。予約 release は**利用者側**の話で、失敗した各試行の provider 利用料は
  運営側に発生する。保証範囲を誇張しないという本リポジトリの作法にも反する。
- 対応内容: 必須度の節から「失敗しても課金されない」を削除し、
  「失われるのは**利用者の待ち時間**と**運営側の provider 実費 (最大 3 試行分)**であり、
  **利用者のチケット予約は release される**」と書き分けた。リスク表の影響欄も同じ言い方に統一。
  厳格必須の第 1 根拠も「無料だから安全」ではなく
  「所見が欠けた解析を成功として扱わない = 機能の名前に沿った品質上の選択」に置き換えた。

## [Warning] 「+700 token」「3 段合計の 1% 未満」は上界として成立しない
- 判断: **対応する**
- 根拠: 指摘が正しい。日本語の文字数は token 数と一致せず、JSON のキー・引用符・構造が加わる。
  `max_tokens` は予約上限であって実消費の分母にできない。実測を持たないまま比率を書くのは誇張。
- 対応内容: token 換算と比率 (「5% 未満」「1% 未満」) を**全部削除**し、
  「出力側は日本語で最大およそ 800 字 (仮タイトル 10 件 × 60 字 + 理由 200 字) と その JSON 構造、
  入力側はプロンプト本文の追記 (日本語で約 400 字)」という**文字数ベースの記述**に置き換えた。
  主張は「2 段目の既存出力の余裕を大きく損なわない見込み」までに留め、
  実装後に `llm_call_logs` で 2 段目の出力 token 分布を観測すると明記した。

## [Warning] 厳格必須の妥当性を継続判断する観測条件が無い
- 判断: **対応する**
- 根拠: 指摘が正しい。「今は閾値を置かない」と言う以上、後から判断するための材料の出し方を
  設計に書いておかないと再評価できない。
- 対応内容: 「観測条件」を必須度の節に追加した。
  (a) `validation` のスキーマ違反を `steps` 側の違反と識別できる形で記録する
      (違反パスを `validation.` 始まりにし、リトライログに載せる)、
  (b) 評価指標は「validation 起因の再試行数 / 最終失敗数 / 2 段目の出力 token 分布」の 3 つ、
  (c) 閾値は今は置かない。

## [Suggestion] `fromStorage()` の警告に失敗分類を構造化 context で持たせる / 保存 JSON 本文はログに出さない
- 判断: **対応する**
- 根拠: 運用しやすさと、LLM 由来の可変文字列をログに載せない方針の両方に合う。
- 対応内容: 警告の context を「job id + 失敗分類 (どのキーが不正か)」とし、
  **保存 JSON 本文はログに載せない**と明記した。

## [Suggestion] `toArray()` に具体的な array shape / list 型を宣言し Controller には戻り値だけを渡す
- 判断: **対応する (詳細設計で実施)**
- 根拠: PHPStan level 10 の要求そのもの。
- 対応内容: 概念設計の DTO 階層はそのまま。詳細設計で各 `toArray()` の array shape PHPDoc を書き切る。

## [Suggestion] 厳格必須への反論は受理 / スコープ / 型安全性 / 使命整合は問題なし
- 判断: 受領 (変更なし)
