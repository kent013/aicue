全体判定: **CHANGES_REQUESTED**

**1. 使命との整合性**

[Suggestion] 使命への貢献は「顧客価値に直結する機能」ではなく「開発基盤の秘密保護」として妥当です。North Star との距離はありますが、CipherSweet/Stripe/LLM key を含む `.env` の複製面を狭めることは、アプリの信頼前提を守る改善として合理的です。

**2. 禁止事項違反**

[Warning] 「変更後に実際に worktree を作って完走すること」を受入条件に含める点は妥当ですが、このレビュー対象の制約ではコマンド実行不可です。詳細設計では、実装者が実行する検証として明記し、レビュー段階で「実行済み」と誤記しないでください。

修正提案: 受入条件を「実装フェーズで `scripts/setup-worktree.sh <tmp-task-id>` を実行し、完走と秘密ファイル mode を確認する」に留める。

**3. 実現可能性**

[Warning] `provision_secret_file` を `install -m 600` 1 コマンドにする方針は実現可能ですが、`storage/oauth-private.key` / `storage/oauth-public.key` の親ディレクトリ存在を前提にしている点が未整理です。worktree 側に `storage/` は通常ありますが、契約テストで一時ディレクトリを使うなら宛先親ディレクトリ未作成ケースで `install` が失敗します。

修正提案: 関数の契約をどちらかに固定してください。  
`provision_secret_file` が親ディレクトリ作成まで責務を持つなら `install -D -m 600` を使う。既存ディレクトリ前提なら、呼び出し側・テスト fixture で宛先親ディレクトリを作ることを明記する。

[Warning] `.env` を必須にして `.env.example` フォールバックを撤去する方針は正しい一方、失敗タイミングが `[1/7] git worktree add` の後です。現行の cleanup trap により worktree/branch は消える想定ですが、「必須不足の事前検出」としては遅いです。開発ワークフロー自身を止めうる変更なので、不要な worktree 作成を避けた方が安全です。

修正提案: `.env` の存在チェックは `[0/7]` の事前条件に入れ、足りなければ worktree 作成前に fail-fast する。実ファイルのコピーは `[2/7]` で行う。

**4. 期待効果の妥当性**

[Warning] 「0600 で困る利用者がいないことは、`.env.bughunt.local` が既に 0600 で運用されている実績で裏付けられる」は少し強いです。`.env.bughunt.local` と `.env` / Passport 鍵は利用経路・ツール・OS 連携が異なるため、完全な裏付けにはなりません。

修正提案: 「同一ユーザーで Laravel/PHP/Passport が読む通常運用では 0600 で足りる見込み。異なる OS ユーザーで読む運用は本スクリプトの対象外」と保証範囲を絞ってください。

**5. リスク**

[Critical] `storage/oauth-public.key` まで 0600 にする設計は再検討が必要です。秘密性は private key と `.env` が中心で、public key は「対になる鍵素材」と書かれているだけです。公開鍵を 0600 にすること自体は大抵問題ありませんが、Passport や周辺ツールが別ユーザーで読む構成がある場合、不要に壊す可能性があります。開発ワークフロー基盤の変更としては、秘密扱いの根拠が弱い対象まで同一契約に入れています。

修正提案: 対象を `.env` / `storage/oauth-private.key` / `.env.bughunt.local` に絞るか、`oauth-public.key` も 0600 にすべき理由を「同一ユーザー実行前提」「worktree-local 供給物は公開配布物ではない」などとして明文化し、テストで固定してください。

[Warning] `.env` 必須化は「壊れた worktree を作らない」効果がある一方、初回セットアップや CI 的な乾いた環境で setup が即停止します。設計では CI は呼ばないとされていますが、開発者オンボーディングへの影響があります。

修正提案: エラーメッセージに最短復旧手順だけでなく、「親チェックアウトで `.env` を作ってから再実行する」こと、途中作成物がない/cleanup されることを明記する。

**6. スコープの適切さ**

[Suggestion] スコープは概ね適切です。`public/build`、既存 worktree の遡及是正、親 `.env` の権限是正を外している判断は過剰対応を避けています。

[Warning] ドキュメント更新範囲がやや広いです。`docs/worktree-isolation-strategy.md` と `AGENTS.md` は妥当ですが、`scripts/README.md` は台帳的説明がある場合のみで十分です。

修正提案: 詳細設計で各ドキュメントに書く事実を最小化してください。特に「0600 は新規 worktree だけ」「親の権限は直さない」「`.env` 不在は作成前に停止」を重複なく記載する。

**7. 保証範囲の誇張**

[Critical] 「親の権限がどうであれ 0600 に揃う」は新規供給または関数が正常完了した対象に限ります。既存 worktree、親 `.env`、追跡下の `.env.testing`、Laravel 以外のツールが生成する秘密ファイルには効きません。本文の制約には一部書かれていますが、期待効果の箇条書きだけ読むと広く見えます。

修正提案: 期待効果を「このスクリプトが新規 worktree 作成時に供給する秘密ファイルは、供給元 mode に依存せず 0600 で作成される」に書き換えてください。

[Warning] 契約テストの「静的な退行検出」は保証範囲が限定的です。現行テストは既知の回帰形を検出するだけで、bash の全条件コンテキストを証明しません。この限定は現行コメントにあり、設計にも引き継ぐべきです。

修正提案: 追加ケース一覧に「既知回帰形の静的検出であり完全な構文解析ではない」と明記してください。

結論として、方向性は妥当ですが、`.env` 必須チェックのタイミング、`oauth-public.key` の扱い、保証範囲の表現を直してから詳細設計へ進めるのがよいです。
