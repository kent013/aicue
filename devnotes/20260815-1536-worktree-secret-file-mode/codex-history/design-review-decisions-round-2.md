# 対応マトリクス: design-review Round 2

## [Warning] 施策 4: S-3 の検査対象がファイル全体で偽緑になりうる
- 判断: 対応する
- 根拠: 指摘のとおり。別の関数や残骸に同じ行があるだけで通ってしまい、
  「関数本体が install -m 600 を使っている」ことの検査になっていない。
- 対応内容: `provision_secret_file()` の**本体を切り出してから**完全一致を検査する形に変更し、
  切り出しヘルパのコードと、切り出し失敗時に空文字を返して落ちる (fail-closed) ことを設計へ明記した。

## [Warning] 受入確認 V-2: `.env` 不在の確認が偽緑 (`|| { echo ...; }` は終了コード 0)
- 判断: 対応する
- 根拠: そのとおり。`echo` が成功するのでブロック全体が 0 になり、コメントと挙動が食い違う。
  受入確認の手順自体が偽緑を作るのは最も避けたい形である。
- 対応内容: V-2 の確認を「目視で mode を読む」形から
  「そのまま実行して最後に `rc=0` が出ることを見る」形へ書き換えた。
  `.env` 不在・mode が 600 でない・親に無いものが作られている、のいずれでも非ゼロで止まる。

## [Warning] 受入確認 V-2: mode 確認が `stat` の表示だけで機械的に保証していない
- 判断: 対応する
- 根拠: 上と同じ。
- 対応内容: `stat -c '%a'` の値を `600` と比較し、違えば非ゼロで止める形にした。

## [Warning] 受入確認 V-2: `public/build` が常に存在する前提で偽赤になる
- 判断: 対応する
- 根拠: `public/build` は任意供給なので、親に無い環境では正常な setup を落としてしまう。
- 対応内容: 親の有無で期待値を切り替える形にした
  (親にあれば供給されている / 親に無ければ worktree にも無い)。

## [Suggestion] 施策 1: テスト計画の参照が D-1〜D-12 のまま
- 判断: 対応する
- 対応内容: D-1〜D-13 に更新した。

## [Suggestion] 施策 1: symlink 検査と install の間の時間差 (TOCTOU)
- 判断: 対応する (保証範囲として明記する)
- 根拠: 検査と書き込みの間に供給先を差し替えられれば素通りする。防ぎたいのは
  「うっかり張られた symlink を辿らないこと」であって、並行して書き換える攻撃者ではない。
  これ以上の防御は今必要でない (思考原則 2)。
- 対応内容: 施策 1 のリスク欄に「並行して供給先を書き換える攻撃者までは防がない」と明記した。

## [Suggestion] 施策 4: S-4 の保証範囲を明記
- 判断: 対応する
- 対応内容: 保証範囲の段落に「S-4 も `cp` の直接の退行形だけを見る (変数経由・別コマンド・別表記には沈黙する)」を追記した。
