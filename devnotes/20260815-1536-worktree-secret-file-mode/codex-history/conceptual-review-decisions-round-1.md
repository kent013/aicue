# 対応マトリクス: conceptual-review Round 1

## [Critical] storage/oauth-public.key まで 0600 にする設計の再検討
- 判断: 対応する (対象は変えず、根拠を明文化して契約テストで固定する)
- 根拠: 本リポジトリで Passport 鍵を読むのは worktree 内で走る PHP プロセスだけであり、
  供給と同一の OS ユーザーで動く。公開鍵を狭く置いて壊れる利用者は現構成に存在しない。
  一方で 1 本だけ例外にすると「どれを狭く置くか」の判断がスクリプト内に 2 種類生まれ、
  次に供給行を足す人が毎回判断させられる。関数の契約を
  「worktree へ供給する実行時ファイルは、供給元の権限に依存させず作業者本人だけが読める形で置く」
  と書き直し、公開鍵もこの契約に入る理由 (同一ユーザー実行前提・配布物ではない) をコメントとテストに残す。
- 対応内容: 概念設計の「改善アイデア」に関数の契約文を追記。対象表に公開鍵を入れる根拠列を追加。
  詳細設計の契約テストへ「公開鍵も 0600 で置かれる」ケースを入れ、意図的な選択であることを固定する。

## [Critical] 期待効果の書き方が保証範囲より広い
- 判断: 対応する
- 根拠: 既存 worktree・親の .env・追跡下の .env.testing・他ツールが作る秘密ファイルには効かない。
  制約欄には書いてあるが、期待効果だけ読むと広く見える。誇張しない規約に反する。
- 対応内容: 期待効果を「このスクリプトが新規 worktree 作成時に供給する秘密ファイルは、
  供給元の権限に依存せず 0600 で作成される」に限定して書き換え、効かない対象をその場で併記する。

## [Warning] 供給先の親ディレクトリの扱いが未整理
- 判断: 対応する (親ディレクトリは作らない、と契約を固定する)
- 根拠: `install -D` で親を作ると、供給先のパスを間違えたときに worktree の外へ静かに
  ディレクトリを作る経路ができる。worktree には `storage/` が追跡下で必ず存在するので作る必要がない。
- 対応内容: 概念設計に「親ディレクトリは作らない (無ければ失敗させる)」を明記。
  契約テストに「供給先の親ディレクトリが無ければ非ゼロで落ちる」ケースを追加し、fixture 側で作る。

## [Warning] .env 必須チェックが worktree 作成後で遅い
- 判断: 対応する
- 根拠: 現行でも EXIT trap が作りかけの worktree を消すが、そもそも作らない方が速く安全である。
- 対応内容: `[0/7] 事前条件チェック` に親の `.env` 存在確認を足して worktree 作成前に停止する。
  ただし**決着は供給関数側**に置く (必須指定で供給元が無ければ非ゼロ)。
  `[0/7]` は早期に止めるための事前確認であり、判定の正本ではないことを設計に明記する。

## [Warning] 0600 で足りる根拠 (.env.bughunt.local の運用実績) が強すぎる
- 判断: 対応する
- 根拠: 利用経路が異なるので完全な裏付けにはならない、という指摘は妥当。
- 対応内容: 「同一ユーザーで PHP / Laravel / Passport が読む通常運用では 0600 で足りる。
  別の OS ユーザーが読む構成は本スクリプトの対象外」と保証範囲を絞って書き直す。

## [Warning] .env 必須化のオンボーディング影響
- 判断: 対応する
- 根拠: 初回セットアップの人が止まるのは想定内だが、止まった人が何をすればよいか分かる必要がある。
- 対応内容: 停止時のメッセージに「親のチェックアウトで `.env` を用意してから再実行する」ことと
  「worktree はまだ作っていないので後片付けは要らない」ことを含める、と設計へ書く。

## [Warning] ドキュメント更新範囲がやや広い
- 判断: 一部対応する
- 根拠: `scripts/README.md` は「スクリプトを追加したら表に 1 行追記する」という台帳規約を持ち、
  setup-worktree.sh の行に実行時ファイルのコピーの説明が既にある。放置すると説明が実装とずれる。
  ただし書く量は最小にする。
- 対応内容: 各ドキュメントに書く事実を「0600 は新規 worktree だけ / 親の権限は直さない /
  `.env` 不在は作成前に停止」の 3 点に絞り、重複しない配分を詳細設計で決める。

## [Warning] 静的な退行検出の保証範囲
- 判断: 対応する
- 根拠: 現行テストのコメントが既に「既知の回帰形の検出であって証明ではない」と書いている。引き継ぐべき。
- 対応内容: 詳細設計のテスト方針に、静的検査は既知の回帰形の検出であり
  bash の全条件コンテキストの証明ではない、と明記する。

## [Suggestion] レビュー段階で「実行済み」と誤記しない
- 判断: 対応する
- 根拠: そのとおり。設計段階では実行しない。
- 対応内容: 受入条件を「実装フェーズで実行する検証」として書く。設計時点の実行結果は載せない。
