全体判定: **CHANGES_REQUESTED**

中核設計は承認可能な水準まで整理されています。CAS を採らない判断も、「同等の保証」ではなく、既存の時間序列を根拠とした明示的なリスク受容としてなら妥当です。

ただし、修正後全文のスコープ外表に Round 2 以前の主張が残っており、本文と正面から矛盾しています。この状態では詳細設計へ進めません。

## 1. 使命との整合性

[Suggestion] North Star との整合性に問題はありません。

LLM・レンダ・課金の不要な外部呼び出しを抑止し、成果物と課金への信頼を支える改善として妥当です。

## 2. 禁止事項違反

[Suggestion] 禁止事項への抵触は確認できません。

Feature/Architecture テスト、mutation による gate の赤化確認、規約とテストの対応表まで完了条件に入っており、禁止事項 1 に沿っています。

## 3. 実現可能性

[Critical] スコープ外表の claim token / CAS の除外理由が、本文で撤回した主張のままです。

表には次の記述が残っています。

> 残余窓を縮めない — CAS 成功と外部送信の間にも同じ幅の窓が残る

これは本文の以下と矛盾します。

> この窓は CAS で閉じられる  
> `running → sending` と `running → failed` は直列化される

対応マトリクスでも「全面的に撤回」としているため、単なる補足差ではなく旧裁定の残存です。

修正提案: スコープ外表を本文と一致させ、例えば次の趣旨へ置き換えてください。

- CAS は `recoverStale` と送信開始の競合を閉じられる。
- 一方、`sending` 獲得後のプロセス死には「外部送信結果が不明」という別の回収問題が生じる。
- 現行の timeout/stale 序列下では元の競合リスクが低い。
- 状態機械、回収処理、UI、TS 型への波及に対して便益が小さいため、今回はリスク受容する。

「同一行の奪い合いが存在しない」も主理由から外すべきです。今回 CAS が解く対象は複数 worker 間の奪い合いだけでなく、**worker と stale recovery 間の送信権競合**だからです。

[Warning] 「`sending` の回収閾値で同じ形の競合が再び現れる」という説明は正確ではありません。

`running` の競合は「送信前に cron が失敗させた後、旧 worker が送信する」問題です。一方、`sending` の stale 回収は「送信されたか分からない状態をどう収束させるか」という結果不明問題です。外部冪等キーがあれば再送可能で、なければ照会・補償・人手確認が必要になります。

修正提案: 「同じ競合が再発する」ではなく、「送信開始後の結果不明を扱う新しい回収契約が必要になる」と書いてください。この方が CAS を採らないコスト評価も正確になります。

[Warning] 「`running` が実質 `sending` の役割を果たしている」も不正確です。

`running` は LLM 前処理や ffmpeg compose を含む長い区間を表し、cron が `failed` 化できます。`sending` のような送信権を保護する状態ではありません。

修正提案: 「`running` と timeout/stale 序列により、正常運用下では stale recovery と送信が競合しにくい」と表現してください。

## 4. 期待効果の妥当性

[Suggestion] 「結果の一回性」「外部呼び出し回数の一回性」「preflight suppression」の分離は妥当です。期待効果も検出時点以降に限定され、過大主張は解消されています。

[Warning] 「OOM kill / deploy / ホスト死は本設計以前から安全」という表現は、二重実行についてだけ成立します。

旧 worker は復帰しませんが、LLM 送信後・DB確定前に死亡すれば課金済み結果不明、S3 PUT 後なら孤児成果物が残ります。

修正提案: 「stale recovery と旧 worker の競合は起きない」と限定してください。「安全」という包括表現は避けるべきです。

## 5. リスク

[Warning] Canceled 検出後の invoice 終端は、単なるログ付き後処理ではなく新たな外部副作用です。

best-effort void 自体が timeout・通信断・再実行される可能性を持つため、少なくとも以下を詳細設計で固定する必要があります。

修正提案:

- 終端操作にも attempt に固定した idempotency keyを使う。
- void 対象の Stripe invoice ID が当該 attempt に保存された値と一致する。
- already void / paid などの Stripe 状態を成功または明示的な非成功へ分類する。
- 終端失敗ログに固定 event 名と attempt IDを含める。
- 課金処理へは進まないことを Feature テストで固定する。

[Suggestion] `job_ownership_lost` の固定 event、型付きコンテキスト、PII/payload 非包含は適切です。

## 6. スコープの適切さ

[Suggestion] 18件すべてを deny-by-default の母集団に保ち、配信系を個別根拠付き免除にする判断は妥当です。

[Warning] `DuplicateDeliveryAccepted` の条件「ユーザーに実害を与えない」は判定が曖昧です。認証・課金・招待・失敗通知では、重複が混乱や誤操作を招く場合があります。

修正提案: 詳細設計では各クラスについて、重複時の具体的影響と受容理由を記述し、セキュリティ通知や課金関連通知を一括免除しないでください。

## 7. 型安全性

[Suggestion] `GuaranteeEntry` と `PreflightCheckpoint` の分離、readonly value object、enum、`class-string`、`non-empty-string`、`void` 検査は PHPStan level 10 と整合します。

[Warning] `preflight: null = 外部呼び出しを持たないジョブ` という意味は型だけでは証明できません。

修正提案: `null` の場合にも「外部呼び出しなし」という型付き分類または個別根拠を要求してください。そうしないと、新しい外部呼び出しを追加しても目録が green のままになる可能性があります。

結論として、**設計判断そのものは概ね妥当**です。残る主な問題は、撤回済みの CAS 主張がスコープ外表に残っていることと、`sending` 回収問題を元の競合と同一視していることです。この2点を整合させれば、概念設計として APPROVED にできます。
