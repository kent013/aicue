> 2026-08-07 の実査。設計フェーズの入力であり、設計そのものではない。

## 序列

- 順位: #1 / 候補 8 件
- 想定 TODO タイトル: ジョブ二重実行の所有権再検証を追加
- テーマ / 優先度 / モード: backend / High / incremental

- 選定理由: 判断基準 1 が名指しする「二重実行」を実際に閉じる唯一の候補。recoverStale が running を failed へ落とした後も旧ワーカーが AnalysisPipeline の LLM 3 段と RenderPipeline の storage->upload を最後まで走らせられる (外部呼び出し直前の所有権再検証が 0 箇所)。金銭 (LLM 課金 / Stripe 課金) と外部副作用 (孤児 S3 オブジェクト) に直結し、finalize の guard では課金済みの外部呼び出しを取り消せない。保証側の骨格 (lockForUpdate + status guard、where(status=pending)->update() の条件付き UPDATE、予約 CAS) は既に 3 系統実在するため、追加は再検証の挿入と序列の機械固定に限定でき effort 6 に収まる。aigenba@a2bf07ac に同一裁定への先行実装 (OwnershipClaim 一式と JobExecutionDedupBaseline) があり設計の手戻りが小さいことも押し上げ要因。

## 設計で最初に決めるべき論点

入口の排他 (ShouldBeUnique を RunManualAnalysis / RunManualRender へ足すか) を今回のスコープに入れるか否かを最初に確定する。uniqueFor はジョブ実行上限 (1,560 / 1,500 秒) を上回る必要があり、鍵の残留が recoverStale 後の再トリガー (§10.8-1「再実行は analyze/render 再トリガーのみ」) を最大 uniqueFor 秒ブロックして現行設計と正面衝突する。裁定は保証側だけが保証を担うと明記しているので、入口の排他は AutoRechargeTriggerJob の現状維持 + 免除理由の inventory 登録に留め、実装は (i) 外部呼び出し直前の再検証 (ii) Cache::lock TTL と実行上限の序列固定 (iii) 横断 gate の 3 点へ絞る、という線引きを設計冒頭で決める。

## 台帳が確定させた標準形

裁定 AG-082 (2026-08-06) は「入口の排他」と「結果の一回性」の両方を標準形 v1 の必須要件とし、保証を担うのは後者だけであることを定義に明記した。入口の排他 (ShouldBeUnique / WithoutOverlapping / 実行中鍵) は公式が「失敗や timeout で鍵が解放されないことがある」と明言する best-effort。保証側は (1) 条件付き UPDATE による所有権獲得、(2) 外部呼び出しの直前の所有権再検証 (検証の後に自前の書き込みを挟むと接続断で旧担当が送信できる窓が開くため直前に置く)、(3) 状態遷移と課金計上の一体更新、(4) ロック TTL と $timeout の序列、(5) 「設定整合では閉じない 4 つの窓」の記録。implemented の条件は保証側まで揃うこと。どのジョブへ適用するか (全数か代償の大きいものへ選択適用か) と機構の実装形は各リポジトリに委ねられている。HTTP/MCP の冪等キー、Stripe webhook 冪等、滞留回収は範囲外。

## ギャップ

1. 外部呼び出しの直前の所有権再検証が AnalysisPipeline (LLM 3 段) と RenderPipeline (storage->upload) に無く、recoverStale cron が running を failed にした後も旧ワーカーが LLM 課金と S3 upload を続行できる。
2. 所有権を表す共通語彙 (claim token / claim TTL / 0 行更新の意味の分離) が無く、保証側の実装が lockForUpdate + status 文字列比較の各所書き下ろしで、新しいジョブが同じ形を踏襲する保証が構造的に無い。
3. Cache::lock の TTL (AutoRechargeService::LOCK_TTL_SECONDS=180) と、その lock 内で走るジョブの実行上限 (既定接続 database の worker --timeout=540 / ExecuteAutoRechargeAttemptJob は $timeout 未宣言) の序列が逆転しており、機械固定もされていない。
4. AutoRechargeTriggerJob の uniqueFor=30 がジョブ実行時間より短いかどうかを固定する検査が無く、入口の排他が静かに無効化されうる。
5. 入口の排他と保証側が揃っていることを横断で検査する deny-by-default gate が無い (家系のどこにも無い項目で、aigenba が JobExecutionDedupBaseline として先行実装済み)。
6. 二重実行の代償が大きいジョブ (RunManualAnalysis = LLM 課金 / RunManualRender = ffmpeg + チケット / ExecuteAutoRechargeAttemptJob = Stripe 課金) のうち入口の排他を持つものが 0 本で、保有する 1 本は代償の小さい起票用 trigger ジョブである。

## リスク

(1) 新 gate は deny-by-default で ShouldQueue 実装 18 件 (Mailable 2 / Notification 6 を含む) 全数の分類を要求するため、登録漏れがあると CI が即赤になる。母集団が QueuedJobLeaseInventoryTest と同一なので、そちらの目録と二重管理になる drift リスクがある (片方だけ更新される)。(2) LLM 呼び出し直前の所有権再検証は解析 1 本あたり 3 回の追加 SELECT を入れる。実行時間の増加は無視できるが、AnalysisPipeline の時間 budget モデル (D + C + M1 + S = 1,560s) のコメントと AnalysisTimeBudgetInvariantTest の前提に触れるため、余白 S (90s) の説明を書き換える必要が出うる。(3) 再検証で中断する経路を足すと、これまで「旧ワーカーが最後まで走って finalize で false を返す」だった振る舞いが「途中で例外/return する」に変わり、catch → failJob が二重に走る可能性がある (failJob は terminal guard で冪等なので実害は無い見込みだが、通知とチケット release の呼び出し回数が変わる)。(4) RunManualAnalysis / RunManualRender へ ShouldBeUnique を足す場合、uniqueFor はジョブ実行上限 (1,560 / 1,500 秒) を上回る必要があり、鍵が残留すると recoverStale 後の再トリガーを最大 uniqueFor 秒ブロックする = 「再実行は analyze/render 再トリガーのみ」という現在の設計 (§10.8-1) と正面から干渉する。(5) AutoRechargeService は org 単位の Cache::lock を updateSettings / recordPreConsent / maybeCreateAttempt / executeAttempt / applySetupCompletion / applyReusedPaymentMethod の 6 経路で共有しており、TTL を変えると全経路の待ち時間 (block 3〜10 秒) の意味が変わる。(6) tests/Architecture 追加は composer test 全体 (10,000 件規模) のホスト全体グローバルロック下で走るため検証サイクルが長い。

## 実装者への申し送り (台帳と実コードの食い違いを含む)

【台帳と実コードの食い違い — 必読】lctl の projects.aicue.note は「入口の排他が 1 本のみで保証側の層が無い」だが、後半は実コードと合致しない。保証側に相当する層は 3 系統実在する: (a) AnalysisPipeline / RenderPipeline の startJob() (lockForUpdate + status===Queued guard) と finalize() (lockForUpdate + status===Running guard の同一 tx で materialize + tickets->commit() + Succeeded を原子化) — これは裁定文が spirux から標準形へ採用したと書く「状態遷移と課金計上の一体更新」そのもので、機構が条件付き UPDATE ではなく悲観ロック + status guard である点だけが違う。(b) AutoRechargeService::recordSuccessfulCharge() / transitionToTerminal() の `where('status','pending')->update()` は文字どおりの条件付き UPDATE で、0 行更新のときに後続を行わない形になっている。(c) TakeRegistrationService の予約 CAS (pending→verifying→completed) と StaleUploadReservationSweeper の対称 CAS。したがって aicue の実際の欠落は「保証側が無い」ではなく「(i) 外部呼び出し直前の所有権再検証が無い (ii) claim token / TTL という語彙が無い (iii) 排他 TTL と実行上限の序列が固定されていない (iv) 横断 gate が無い」の 4 点である。実装前にこの差分を append_event の handover として台帳へ戻すことを勧める。【入口の排他の数え方】ShouldBeUnique は確かに 1 本 (AutoRechargeTriggerJob) だが、Cache::lock による org 単位の相互排他が AutoRechargeService に 6 箇所、SubscriptionService に 2 箇所、TicketCheckoutService と ReconcileAutoRechargeAttempts に各 1 箇所ある。「1 本のみ」は ShouldBeUnique/WithoutOverlapping の grep 結果であって、入口の排他そのものの実数ではない。【aigenba が先行実装済み】aigenba@a2bf07ac (aigenba:T1105) が同じ裁定へ追従し、App\Support\JobExecution の共通語彙 (OwnershipClaim / ClaimOutcome / ClaimResult / ClaimedOperationOutcome / JobExecutionTimeouts)、0 行更新を AlreadySettled と HeldByOther へ分離する設計、期限切れ claim 奪取後に「既に決着済み」を再確認する settledOrClaimed()、横断 gate (JobExecutionDedupBaseline) まで作っている。設計履歴は aigenba の devnotes/20260806-1154-job-execution-dedup/。aicue で作る前にこれを読むこと。【gate の下敷き】tests/Architecture/QueuedJobLeaseInventoryTest.php (const QUEUED_JOB_LEASE_INVENTORY = ShouldQueue 実装 18 件、対称差が空であることを要求) と tests/Architecture/ThrottleCoverageInventoryTest.php (App\Enums\Security\ThrottleCoverageExemption + case 別上限 + 30 文字以上の理由) の 2 本が既存の書き方の正本。【既存 TODO】docs/TODO.md の Open にこの feature 由来のタスクは無い (T124/T125/T126 は throttle と外部 SDK timeout、T127 は既定キュー接続の分割で Conditional)。付番するなら T129 以降。
