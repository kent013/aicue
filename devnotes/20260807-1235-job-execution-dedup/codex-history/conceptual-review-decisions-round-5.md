# 対応マトリクス: conceptual-review Round 5 (全体判定 APPROVED)

Round 5 で **APPROVED**。指摘は Warning 2 件のみで、いずれも「本文後半と完全に整合させるための
表現修正」であり設計判断の変更ではない。両方とも詳細設計着手前に反映済み。

## [Warning] 「現状は `$timeout < stale 閾値` の序列で実質同じ効果を、追加状態ゼロで得ている」は CAS と同等ではない

- 判断: **対応する**
- 根拠: 妥当。timeout 序列は競合を「起きにくくする」ものであり、CAS のように直列化しない。
- 対応内容: 「現状は `$timeout < stale 閾値` の序列により、**生存ワーカーと `recoverStale` の
  競合可能性を追加状態なしで低減している**。CAS / lease と同じ効果ではない」へ書き換えた。

## [Warning] 「claim token は同じ行を複数の担当が奪い合うモデルで必要」は必要条件として狭すぎる

- 判断: **対応する**
- 根拠: 妥当。claim token は worker 間だけでなく **worker と stale recovery の世代識別**にも使える。
  「該当モデルが存在しない」を主理由にすると、後段のリスク受容と論理が噛み合わない。
- 対応内容: 不採用の理由を **「claim token を導入しても送信結果不明を収束させる回収契約が
  別途必要になる一方、現行の `$timeout < stale 閾値` 序列の下では元の競合の発生可能性が低く、
  導入コスト (カラム 3 本 + TTL + `recoverStale` / UI / TS 型への波及 + 新しい回収契約) が
  便益を上回る」** というリスク受容へ書き換えた。
