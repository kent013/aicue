| 3. 実現可能性 | [Warning] `countExpired()` から `kind = carry_forward` を除外すると、共通の `BillingRetentionPurgeResultDto` が表す「期限超過レコードが残っていない」の意味が target ごとに変わります。実装は可能ですが、publication-ready が真でも DB には古い行が残るという差を、DTO の全利用者・運用手順・監視が許容することを確認する必要があります。**修正提案:** 詳細設計で `expiredRemaining` を「削除対象となる取引明細の残数」と再定義し、全 purger の意味との整合、利用箇所、監視文言を列挙してテストで固定してください。 |
| 4. 期待効果の妥当性 | [Warning] 「実質 2〜3 行/組織」は、group key が `(organization, source, expires_at)` である以上、付与期限の種類・購入チケットの期限設定次第では成立しません。正典追従と有界化の主張は妥当ですが、行数の絶対値は未検証です。**修正提案:** 効果は「期限切れ窓が残り続けない」「存続する group key 数に上限づけられる」と表現し、実データまたは fixture 分布で導入前後の group 数を観測してから数値目標を置いてください。 |
| 5. リスク | [Critical] `carry_forward` を保持期限の対象外とする根拠が、現時点では「取引明細を持たない」という設計上の説明に留まっています。保持期限・監査の文脈で台帳行自体が課金記録と扱われるなら、古い繰越行を無期限に保持することは「7 年後に削除」の契約と衝突し得ます。**修正提案:** 列単位で、繰越行に残るデータ、取引明細・PII・監査識別子を含まないこと、無期限保持を許容する記録分類を明文化し、法務・運用上の保持方針の正本に合意を得てください。許容できない場合は、残高スナップショットの保持方針を別途設計する必要があります。 |
| 5. リスク | [Warning] `SUM(delta)` の int4 範囲外で組織単位ロールバックする方針は正しいですが、DB 側の集計値の型・返却形式、正負境界、`0` 合計 group の扱いが未確定です。特に 0 の繰越行を作ると、残高に寄与しない行を恒久的に残す可能性があります。**修正提案:** `INT_MIN` / `INT_MAX` / 範囲外、正負相殺で 0、既存繰越行を再畳み込みするケースを Feature テストへ明記し、0 合計を作成するか削除のみとするかを正典実装との照合結果として決着してください。 |
| 5. リスク | [Warning] 集計と削除の件数一致で並行 insert による残高消失を防ぐ説明は合理的です。ただし「一致しなかった時に全変更が rollback される」「再実行で収束する」が実装境界として明示されていません。**修正提案:** 組織単位 transaction 内で、ロック取得→対象数記録→集計→削除→件数照合→繰越 insert の順序を固定し、不一致時の例外・rollback・次回再試行可能性をテスト仕様にしてください。 |
| 6. スコープの適切さ | [Suggestion] 正典が要求する 7 点と、aicue 固有の retention adapter・件数一致検査を分けており、過剰なテンプレート追従になっていません。drop migration を追加して add migration を歴史として残す判断も適切です。 |
| 7. 型安全性 | [Warning] `CarryForwardGroup` を query-builder の生値から生成する方針は、Eloquent cast の二重変換回避として妥当です。ただし DB ドライバから来る `SUM`、日時、nullable `expires_at`、`source` の値が DTO 境界で fail-closed に検証される設計が必要です。**修正提案:** DTO に `fromRow()` 相当の明示的 factory を置き、未知の source、非数値・範囲外 delta、不正日時を例外化してください。PHPDoc の配列 shape／ジェネリクスも付与し、PHPStan level 10 で query 結果の曖昧さを DTO 境界より先へ流さないようにしてください。 |
| 7. 型安全性・静的 gate | [Warning] 新設 gate の狙いは正しい一方、表名文字列・モデル名・変更語彙だけの検出では、別名 import、group use、動的な query 組立て、`DB::table()` などの迂回を見落とす恐れがあります。**修正提案:** AGENTS.md の走査器規約どおり、完全修飾名への解決、未解決構文の fail-closed、各走査根の非空、正例・負例を具体的に設計してください。また保証対象外があるなら gate の名称・docblock・不変条件の主張をその範囲に狭めてください。 |

承認前の必須条件は、主に次の 2 点です。

1. `carry_forward` を retention 完了判定から除外する意味を、法的・運用的・DTO 契約上で矛盾なく確定すること。  
2. 範囲境界・0 合計・並行 insert 不一致・再実行収束を含むテスト仕様と、fail-closed な DTO／静的 gate の詳細を追加すること。
