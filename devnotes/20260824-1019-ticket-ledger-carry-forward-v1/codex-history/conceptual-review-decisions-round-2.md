# 対応マトリクス: conceptual-review Round 2

## [Critical] 繰越行の保持分類は技術的事実だけでは確定しない (契約終了 vs Organization 削除)

- 判断: **全面的に対応する (反論を取り下げる)**
- 根拠: 指摘が正しい。さらに実コードを追加で実読したところ、こちらの根拠 3 は**もっと弱い**ことが分かった。
  - `app/Models/Organization.php` は `SoftDeletes` を使う。退会・アカウント削除は
    `deleted_at` を打つ**論理削除**であり、`app/` 配下に `forceDelete` の呼び出しは
    **1 件も無い** (grep で確認)。したがって `organization_id` の
    `constrained()->cascadeOnDelete()` は**通常運用では発火しない**。
  - 帰結として繰越行は**退会後も残り続ける**。これは `docs/template-divergence.md` D23 が
    「課金記録の保持義務は退会より寿命が長い」と宣言した設計そのものであって事故ではないが、
    「契約終了で消える」という説明は**成り立たない**。
  - 「v0 も同じだった」は差分リスクの不在の証明であって、分類が文面上正しいことの証明ではない。
- 対応内容: 概念設計 §繰越行の保持分類 を**条件付き判断**へ書き換える。
  - 技術設計上の分類 (継続残高) を採る。**プライバシー文面との最終整合はオーナー / 法務確認を
    実装・リリースの前提条件とする** (未完了のまま「衝突しない」と断定しない)。
  - 確認事項を 4 点に明示する (契約終了と Organization 削除のタイミング差 /
    契約終了後も Organization を残す場合の繰越行の扱い /
    集約済みの `delta` `source` `expires_at` `created_at` が「取引関係書類等」に当たるか /
    契約終了後に残高を保持する必要があるか)。
  - 記録先は `docs/billing-retention-runbook.md` の申し送り (決定主体・決定日・分類・再判定条件)。
  - 機械で固定できるのは**データ形状だけ**であることを明記する (法的分類は固定しない)。

## [Warning] `expiredRemaining` を target 別の例外として書くと契約が弱い

- 判断: 対応する (提案の定義をそのまま採る)
- 根拠: 共通 DTO の語を target 別に分岐させると、読み手が target を知らないと解釈できない。
  「継続状態を表す集約レコードは含まない」という**共通定義**にすれば分岐が消える。
- 対応内容: `BillingRetentionPurgeResultDto` の docblock (正本) を
  > `candidates` / `expiredRemaining` は、各 target の保持ポリシーにより**物理削除または
  > 不可逆な明細除去の対象となるレコード数**であり、**継続状態を表す集約レコードは含まない**。
  とし、台帳では `kind = carry_forward` がその「集約レコード」に該当すると明記する。
  他 6 target は集約レコードを持たないので実質の値は変わらない (意味は分岐しない)。

## [Warning] 列分類テストは「許可列以外が NULL」では不十分

- 判断: 対応する
- 対応内容: 検査を 5 条にする。
  1. `kind` が厳密に `carry_forward`
  2. `description` が定数 (固定文言) と厳密一致 (自由文が入らない)
  3. 明細識別列・決済識別列・冪等キー・予約参照・個別付与時刻がすべて NULL
  4. 「許可列 ∪ NULL 必須列」が**実スキーマの全列と完全一致**
  5. 新しい列が増えたら未分類として**失敗**する (deny-by-default)

## [Warning] int4 範囲検査を PHP `int` へ変換した後に行うと fail-closed にならない

- 判断: 対応する
- 根拠: 指摘が正しい。PHP の `int` は 64bit なので int4 超過は落ちないが、
  **PHP 整数範囲を超える数値文字列**を先にキャストすると値が壊れた後に検査することになる。
  「解決できない形は落とす」の原則にも反する。
- 対応内容: `CarryForwardGroup::fromRow()` で
  1. `delta_sum` が `int` ならそのまま採る
  2. 文字列なら **`/\A-?[0-9]+\z/` に完全一致**することを要求する
     (指数表記・小数・空文字・前後空白・符号のみは**例外**)
  3. **10 進文字列のまま**符号 + 桁数 + 辞書順で int4 境界 (`-2147483648` / `2147483647`) と比較する
  4. 境界内であることが確定してから `int` へ変換する
  という順序に固定する。float が返る driver は**受けない** (`Assert` で例外)。
  単体テストのケースを指摘どおり 6 群 (境界ちょうど / 境界 +1 / PHP 整数範囲超 /
  指数表記・小数・空・空白 / driver が `int` で返す正常値 / 負側) 置く。

## [Warning] `CarryForwardGroup` の列ごとの許容型を確定させる

- 判断: 対応する
- 対応内容: 列ごとに受ける型を宣言する。
  - `source`: `null` または**文字列**のみ → `TicketSource::from()` (未知値は例外)
  - `expires_at`: `null` または**文字列 / `DateTimeInterface`** のみ → `CarbonImmutable`
  - `max_created_at`: **非 null** 必須。文字列 / `DateTimeInterface` のみ
  - `delta_sum`: 上記の 10 進文字列規則 (bool / float は例外)
  - `row_count` / `carry_forward_rows`: **非負整数**であること (`Assert::natural`)
  - 列の**欠落**は例外 (`Assert::propertyExists`)。**想定外の余剰列は拒否しない**
    (集約 SQL は本サービスが組み立てるので余剰列は入らず、拒否すると driver が付ける
    内部列で偽赤になるおそれがある)。この判断を docblock に書く。

## [Warning] 静的 gate の主張が保証外と矛盾する

- 判断: 対応する
- 根拠: 「穴が静的に塞がる」「変更するのは 1 ファイルだけ」は、
  呼び出し側と共通処理側で語彙が分かれる形を検出できない以上、言い過ぎである。
- 対応内容: 期待効果と gate の主張を
  > **対象構文の範囲で**、台帳モデル参照または表名リテラルと変更語彙が同一ファイルに現れる
  > 変更サイトを deny-by-default (件数完全一致) で固定する
  へ狭める。「append-only の例外は畳み込み 1 ファイルだけ」は**人間向けのドメイン規約**として
  AGENTS.md に残すが、**gate がそれを証明するとは書かない**。
