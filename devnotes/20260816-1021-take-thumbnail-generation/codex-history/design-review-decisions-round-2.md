# 対応マトリクス: design-review Round 2

## [Warning] S3: 再試行時に 1 回目の出力が残り、空出力を成功と誤判定しうる
- 判断: **対応する (指摘どおりの欠陥)**
- 根拠: `-y` は「既存があれば上書きしてよい」という許可であって、ffmpeg が必ず書き直すことの
  保証ではない。指摘の順序 (1 回目が非 0 終了で非空を残す → 2 回目が終了コード 0 のまま
  新しいフレームを出さない → 実体検査が 1 回目の残骸を見て成功と判定) は成立し、
  **壊れた/誤ったサムネイルを PUT する**ことになる。
- 対応内容: `attempt()` の**実行前に出力先を削除**する処理を追加し、削除できないこと自体も
  失敗理由として返す形にした。テスト計画に「1 回目が残骸を作り 2 回目が新規出力を作らない場合は例外」
  「出力先を削除できない場合も失敗」を追加した。

## [Warning] S10: `resumeUploads()` 経由で登録されたテイクが監視集合に入らない
- 判断: **対応する (指摘どおり。オフライン撮影の主経路が取り残されていた)**
- 根拠: 現行は `outcomes.some(...)` で reload の有無だけを決めており、`clientTakeId` を
  1 つも取り出していない。設計書の擬似コードも `handleCaptured` 側だけを書いていたため、
  キュー再開で確定したテイクは監視されず、最初の reload 時点で未生成なら以後反映されない。
  **オフライン → 復帰**は撮影 PWA の主要経路 (概念設計 D9 / IndexedDB 一時バッファ) なので、
  ここが抜けると機能の価値が半分になる。
- 対応内容: uploaded な outcome を型絞り込み付きで抽出し、**全件を `watch()` してから
  reload を 1 回だけ**呼ぶ形へ変更した。テスト計画に 4 項目
  (uploaded だけが監視される / queued・quota_exceeded は監視されない / reload は 1 回だけ /
  再開直後に未生成でもその後の再取得で反映される) を追加した。

## [Warning] S11: 「最後に登録したテイク」は実装の保証単位と一致しない
- 判断: **対応する**
- 根拠: 指摘のとおり。スケジューラが扱うのは「**最後に監視集合へ新規追加された ID**」であり、
  重複 ID の `watch()` は早期 return するため予算は戻らない。また resume では
  「登録完了順 = 配列順」とは限らない。
- 対応内容: scheduler の docblock と S11 のドキュメント文言を
  「最後に**監視集合へ追加された**テイクを起点に最大 4 回・約 29 秒」へ統一し、
  「既に監視中の ID の再追加では予算が戻らない」「キュー再開で複数件を追加した場合は
  最後に追加された 1 件が起点」も明記した。テスト計画の文言も実装語彙へ合わせた。
