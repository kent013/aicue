全体判定: **CHANGES_REQUESTED**

Round 1 の主要指摘には概ね適切に対応されています。特に direct fetch の目録登録、Quota の既存表示経路との接続、キー導出の変更は妥当です。ただし、非同期生成結果を PWA が認識する経路がなく、現状のままでは主目的が撮影セッション中に成立しません。

### 1. 使命との整合性

[Critical] `has_thumbnail` が撮影完了時点の Inertia props に固定され、ジョブ完了後に更新される仕組みが設計されていません。

テイク登録直後は通常 `thumbnail_path = null` なので、返却される `has_thumbnail` は `false` です。その後ジョブが生成を完了しても、`TakeStrip.svelte` は `<img>` を描画しないままです。ページ再読込や既存の再取得処理がない限り、「録画後の下部サムネイルで即確認」は成立しません。

修正提案: 次のいずれかを明示してください。

- テイク登録後、サムネイルが生成されるまで既存 endpoint を短時間ポーリングし、`has_thumbnail` を更新する。
- Take 一覧の部分 Inertia reload を、上限時間・間隔・停止条件付きで行う。
- 画像 route を常に描画し、404 時のプレースホルダと限定的な再試行をクライアント側で管理する。

無制限ポーリングは避け、「成功・テイク削除・画面離脱・試行上限」で停止する設計が必要です。

### 2. 禁止事項違反

[Suggestion] `DirectFetchInventory`、キュー・S3・nested route の各目録まで含めた方針は規約に沿っています。

[Warning] S3 目録の件数が本文内で不一致です。

`downloadToLocal()`、`upload()`、`temporaryThumbnailUrl()` の3 public method を新設すると読めますが、「新規 public メソッド2件を面分類」と記載されています。

修正提案: 実際の既存 interface を基準に、新規・既存変更を区別して3メソッドそれぞれの面分類を列挙してください。

### 3. 実現可能性

[Warning] ffmpeg の Process timeout とジョブ `$timeout = 240` の関係が未確定です。

Process がジョブ制限と同じ240秒まで動けると、後処理・例外処理・work dir 削除の余裕がありません。worker に強制終了されれば `finally` も保証されません。

修正提案: ffmpeg の Process timeout をジョブ timeout より十分短くし、例えば「Process 210秒未満、Job 240秒、retry_after 300秒」のように階層を明記してください。画像の最大幅・高さも固定し、巨大入力から巨大 JPEG を生成しないことを明記すべきです。

[Suggestion] `-protocol_whitelist file` は新経路の境界として妥当です。既存 render 経路との差異を観測事実として分離した判断も、本タスクのスコープとして受容できます。

### 4. 期待効果の妥当性

[Warning] 「即確認」という表現は、生成完了通知または再取得経路が実装されて初めて成立します。

修正提案: 非同期反映経路を設計に追加したうえで、生成待ち中はプレースホルダを表示し、完了後に同じ枠が画像へ置き換わることを受入条件にしてください。

先頭1秒、失敗時0秒という抽出方針と、「判別の手がかり」に限定した効果表現は妥当です。

### 5. リスク

[Warning] 最終の条件付き UPDATE が preflight の条件を完全には引き継いでいません。

現在の記述は `where id=? and thumbnail_path is null` だけです。preflight 後に状態が変わった場合、`ready` でないテイクへサムネイル情報を書き込めます。

修正提案: 最終 UPDATE も最低限、次の条件にしてください。

```sql
WHERE id = ?
  AND status = 'ready'
  AND thumbnail_path IS NULL
```

[Warning] 重複ワーカー間で、S3 の実体サイズと `thumbnail_size_bytes` がずれる可能性があります。

A が PUT、B が PUT、A が DB 更新に勝つと、DB には A のサイズ、最終オブジェクトには B の内容が残り得ます。同一入力・同一 ffmpeg なら通常同じですが、worker のバイナリや設定にデプロイ差がある場合、「同じ意味」は「同じバイト数」を保証しません。

修正提案: 次のいずれかを設計上の保証にしてください。

- S3 の conditional PUT により最初の1件だけ作成する。
- PUT 所有権をDB側で事前取得できる状態機械を導入する。
- 全 worker の抽出設定・バイナリが同一で、出力がバイト単位で決定的であることを運用契約とテストで固定する。

最後の案を採る場合も、「実測使用量と恒常的に一致する」という主張は弱める必要があります。

### 6. スコープの適切さ

[Suggestion] バックフィル、PC描画、既存 render の protocol 制限を分離した判断は妥当です。

ただし、PWA への非同期反映は追加機能ではなく、本タスクの期待効果を成立させる必須範囲です。スコープ外にはできません。

### 7. 型安全性

[Warning] `sum(DB::raw(...))` が PHPStan level 10 を通ることは、概念上まだ確定していません。

Laravel/Larastan のシグネチャによっては `sum()` の引数に `Expression` を渡す箇所が問題になります。また、SQL集計結果の `mixed` を単に `(int)` にするだけでは、リポジトリ固有の型規約を満たすとは限りません。

修正提案: 詳細設計では既存の型が通っている集計パターンに合わせ、PHPStan テストを先に赤にしてください。必要なら `selectRaw()` と型を限定した結果DTO、または型付きの専用集計メソッドに閉じ込めます。型を緩める対応は不可です。

DTOへパスや署名URLを露出せず、`has_thumbnail: bool` のみ追加する方針自体は適切です。
