# 対応マトリクス: conceptual-review Round 5

## [Critical] C3 の公開条件が `failClosed` を除外していては「最長 7 年」を満たさない

- 判断: **対応する (指摘が正しい)**
- 根拠: そのとおり。`failClosed` は「安全のため削除できなかった**期限超過データ**」であり、
  保持期限上は依然として超過している。分類して report しても**データが残っている事実は変わらない**。
  Round 2 で自分が受け入れた「除外目録は可視化するが解決しない」と同じ構造の誤りを、
  別の名前で再導入していた。
  **安全上データを残す判断**と**規約を公開してよい判断**は別物である。
- 対応内容 (指摘の 4 点をすべて採用):
  1. **C3 の公開条件を「分類を問わず期限超過件数が 0 件」に変更**した。
  2. `failClosed > 0` なら **C3 を出さない**。参照元を解消して再実行する。
  3. **初回有効化 apply は `failClosed > 0` でも非 0 終了**にする
     (「安全に残した」を成功として黙らせない)。
  4. **日次運用でも `failClosed` の継続・増加を正常成功として扱わない**。
     監視対象として `docs/architecture.md` の監視対象リストへ登録し、`report()` で通知する。
- 帰結: horizon の postcondition から「`failClosed` を除く」という但し書きを**削除**した。
  postcondition は **「起算済み・期限超過の行が 0 件」**に戻る。

## [Warning] C2 の日次 schedule と runbook 手順 6 の制御点が不明

- 判断: **対応する (提示された前者を採用)**
- 根拠: 妥当。C2 を通常デプロイすると、登録済み schedule が初回手動 apply や horizon 確認より
  先に走りうる。追加機構で止めるのは思考原則 2 に反する。
- 対応内容: **C2 デプロイ時点から schedule は有効**とし、runbook 手順 6 を
  **「継続監視へ移す」**に変更した。手順 3 の `--apply` は「初回を能動的に完走させて結果を確認する」
  ためのものであり、schedule を抑止する意味ではないことを明記した。

## [Warning] `Subscription` / `SubscriptionItem` の表と本文で方式が不一致

- 判断: **対応する**
- 対応内容: §4-3b の表の方式欄を「詳細設計で確定」→ **「物理削除 (子から親)」**に修正。
  起算点も分けて明記した — `Subscription` は**自身の `ends_at`**、
  `SubscriptionItem` は**親 Subscription の `ends_at`**。

## [Warning] 台帳への `implemented (v1)` 報告時点

- 判断: **対応する**
- 根拠: 妥当。v1 の構成要素である規約文面は C3 まで入らないので、C2 マージ後の報告は早すぎる。
- 対応内容: 報告時点を **C3 完了後**に変更し、条件を 5 つ明記した —
  (a) C2 デプロイ済み / (b) 初回 apply 完走 / (c) **`failClosed` を含む期限超過件数が 0** /
  (d) C3 マージ・デプロイ済み / (e) 三者一致 gate が green。

## [Suggestion] DTO の判定メソッドを 3 つに分離

- 判断: **対応する**
- 対応内容: `hasFailClosedRecords(): bool` / `hasUnexpectedFailures(): bool` /
  `isPublicationReady(): bool` の 3 つを持たせる。Command の終了コード判定と C3 公開判定で
  件数の解釈が分岐しないよう、解釈を DTO 側に閉じる。

## [Suggestion] 繰越設計への追加 (0 合計の繰越行 / `carried_forward_through` の単調性)

- 判断: **対応する (詳細設計の必須項目として記録)**
- 対応内容: §4-3b に「詳細設計で固定すること」として明記した —
  **合計 0 の繰越行を作らない** (残高に寄与しない行を増やさない) /
  **再畳み込み後も `carried_forward_through` が単調に進む**。
