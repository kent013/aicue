全体判定: **CHANGES_REQUESTED**

Round 1 の主要指摘には適切に対応されています。特に purge 対象の目録化、凍結範囲の deny-by-default 化、メール通知の追加、DTO 化は妥当です。反論された `deleteAccount()` の層分離についても、提示された実装事実を前提とすれば反論は成立します。

一方、保持期間の意味と実処理にまだ重大な不整合があります。

## 1. 使命との整合性

[Warning] 「1 クリックで永久に失われる経路を塞ぐ」という期待効果は、即時削除 route を副導線として残す以上、事実より強い表現です。

`recent-auth` は本人確認の強化であり、不可逆操作の誤選択を防ぐ確認ではありません。また、禁止事項 8 は「条件未充足時に disabled にせず押下後に説明する」という規約であり、確認画面や確認ダイアログを否定する根拠にはなりません。

修正提案: 二段確認を必須とはしませんが、期待効果を「既定導線における誤操作を回復可能にする」に修正してください。即時削除については、明示文言・視覚的な副導線化・`recent-auth`・既存監査記録を安全条件として設計に固定します。

## 2. 禁止事項違反

禁止事項への直接的な違反は見当たりません。

[Suggestion] 即時削除の確認を設けない根拠から「禁止事項 8 の思想」を外した方がよいです。この規約は destructive action の確認 UX とは別の問題です。根拠は「標準形による併存」「既存の step-up」「追加機構の費用対効果」で十分です。

## 3. 実現可能性

[Warning] purge バッチの失敗分離と競合処理が未定義です。

最初の対象者で `ValidationException` が発生して Command 全体が終了すると、それ以降の期限到達者が毎日処理されない可能性があります。また、抽出後に取消されたユーザーを古いスナップショットのまま削除してはいけません。

修正提案:

- 主キー順の chunk 処理にする
- 各ユーザーを独立した処理単位にする
- `deleteAccount()` のロック取得後に、予約状態と `deletion_purge_after <= now()` を再確認する
- blocker は対象者単位で `report()` して次へ進む
- 想定外例外の継続可否、終了コード、再実行契約を決める
- 「抽出後の取消」「二重バッチ」「1 人目 blocker、2 人目成功」の Feature テストを追加する

[Warning] 凍結 allowlist に認証回復系の経路が不足する可能性があります。

`recent-auth.*` だけでなく、パスワード確認画面、2FA challenge、passkey、メール再検証、ログイン手段維持など、取消へ到達するまでに必要な route が別名で存在する場合があります。

修正提案: route 名を推測で列挙せず、「予約済みユーザーがセッション切れ・recent-auth 期限切れ・2FA 有効の各状態から取消完了まで到達できる」Browser/Feature テストから必要な exact-fit allowlist を確定してください。`dashboard` は詰み回避に不可欠ではないため、必要性を再確認すべきです。

## 4. 期待効果の妥当性

[Warning] メールを予約トランザクション内で dispatch するだけでは、ロールバック時の誤通知を防げるとは限りません。

キューワーカーがコミット前に実行できる構成では、予約がロールバックしてもメールだけ届く可能性があります。「dispatch の位置」と「ジョブが参照する状態・実行可能時点」は別問題です。

修正提案: aicue の「tx 内 dispatch」規約を守りつつ、ジョブ側で予約状態と予約識別子を再確認し、取消済み・更新済み・存在しない予約なら送信しない契約にしてください。通知の重複防止も Feature テストで固定します。

[Suggestion] 三者一致について、マーカーだけ残る穴は現行の behavioral test で一定程度防げています。さらに privacy テストで節見出しと先例に由来する固定文言も検査すれば、「数字だけ別文脈に残る」退行を検出できます。

## 5. リスク

[Critical] 「最長 7 年」と宣言しながら `TicketLedgerEntry` や `Subscription` を期限なく保持する設計は、単一出典化では解消できない実質的な不整合です。

削除すると残高や契約状態を壊すため今回削除しない、という判断自体は正しいです。しかし、それらが「取引関係書類等」に該当するなら、7 年を超えて残り続けるため「保持 7 年の実処理」が成立しません。目録への除外登録は不整合を可視化しますが、解決はしません。

修正提案: PR-C の完了条件を次のいずれかで閉じてください。

- 期限超過 ledger を残高スナップショットへ安全に畳み込み、原明細を削除する
- 契約状態と法定保持対象を分離し、期限超過部分を削除または匿名化する
- 当該モデルが規約文面の対象外であることを、法務草案上のデータ分類と purge inventory の両方で明示する

これを別タスクへ送る場合、PR-C 単独で「保持期間の実装完了」「implemented (v1)」とは主張できません。

[Warning] target の基準日時に一律 `created_at` を使う例は危険です。

長期間未完了だった checkout session が期限経過後に terminal へ遷移すると、次の purge で即時削除されます。保持期間の起算点が取引完了・失効日時なら契約違反になります。

修正提案: 各 target に「保持期間の起算イベント」と対応列を明記してください。terminal 対象は原則として `completed_at`、`expired_at`、`failed_at` などの確定日時を使い、null・状態不整合を fail-closed に扱います。その境界テストも target ごとに必要です。

[Warning] `BillingNotification` を「詳細設計で分類」としたままでは、概念設計の exact-fit 母集団が閉じていません。

修正提案: この段階で削除対象か除外かを確定してください。dedup のために必要なら Exclusion に置き、別保持ポリシーの所有者と理由を明記します。

## 6. スコープの適切さ

[Warning] PR-C のスコープは現在、宣言した「保持 7 年」を完結させるには過小です。

修正提案: ledger の畳み込み等が必要なら PR-C を分割しても構いませんが、台帳の `implemented` 更新は、期限超過データが inventory 上すべて削除・匿名化・対象外分類のいずれかで閉じた後にしてください。

PR-A → PR-B → PR-C の順序自体は妥当です。A と B はそれぞれ単独で main を壊さず完結できます。

## 7. 型安全性

[Warning] `BillingRetentionTarget` に「対象条件」「方式」を enum の自由文字列や callable として持たせると、PHPStan level 10 で型が崩れやすくなります。

修正提案: enum は識別子とメタデータだけにし、処理は target ごとの型付き handler に委譲してください。例えば `BillingRetentionPurgeTarget` interface に、基準日時・dry-run count・apply を表す明示的な戻り値 DTO を定義します。任意の Builder/callable 配列を共通化しない方が安全です。

`AccountDeletionStateDto` と対応する TypeScript 型を設ける方針は妥当です。日時は ISO 8601 nullable、blocker は文字列配列ではなく既存の型付き blocker 表現へ合わせることを詳細設計で固定すれば、PHPStan level 10 と Svelte 側の型検査に乗せられます。

結論として、Round 1 の設計上の穴の大半は解消されています。承認を阻む中心点は、**7 年保持を宣言しながら、取引履歴の SoT を無期限除外する可能性が残っていること**です。ここを「対象外分類」または「状態を壊さない期限処理」として閉じれば、概念設計は承認可能な水準です。
