## 1. 使命との整合性

## 2. 禁止事項違反

[Critical] C1 単独では、公開規約が「最長 7 年」と宣言する一方で、`TicketLedgerEntry` の期限処理が未実装です。

`pending_carry_forward` は未了を機械的に可視化しますが、C1 マージ後の利用者に対する規約と実処理の不一致は解消しません。「各 PR 単独で完結する」「後方互換の並走を残さない」という説明とも矛盾します。

修正提案: 次のいずれかにしてください。

- C1 と C2 を同一 PR に戻す
- C1 は内部基盤とテスト準備だけにし、privacy 文面・日次スケジュール・`--apply` の運用開始をC2へ移す
- C1 の horizon test を `pending_carry_forward` が存在する限り失敗させ、main へマージ不能にする

4 PR を維持するなら、2 番目が最も自然です。C1 は「準備 PR」であり、単独で保持機能が公開されたとは主張しない構成になります。

## 3. 実現可能性

[Warning] purge Command が想定外例外をすべて握って常に `SUCCESS` を返す設計は、障害検知を弱めます。

対象者ごとの失敗分離は必要ですが、全件でDB障害が起きた場合まで成功終了すると、scheduler の失敗通知や終了コード監視が機能しません。`report()` の成功自体も保証されません。

修正提案: 処理は最後まで継続しつつ、想定外例外を1件以上記録した場合は最終的に `FAILURE` を返してください。業務 blocker は正常な保留として `SUCCESS`、インフラ障害や不変条件違反は `FAILURE` と分類します。

[Warning] `TicketLedgerEntry` の畳み込みが保証する不変条件を、残高3メソッドだけに限定するのは不足する可能性があります。

`source`、`expires_at`、作成順、原取引への参照を利用する照会や FIFO 消費処理があれば、`SUM(delta)` が同じでも挙動は変わります。

修正提案: ledger の全 reader を目録化し、各 reader が依存する粒度を固定してください。少なくとも以下を検証対象にします。

- 総残高
- 利用可能残高
- 有効期限別残高
- source 別残高
- debit/reserve/commit/release の選択順序
- 外部キー、重複防止キー、監査表示

畳み込み行には専用 source を用いるのか、元 source を引き継ぐのかも詳細設計で確定が必要です。

## 4. 期待効果の妥当性

[Warning] `BillingRetentionHorizonTest` が「全 target で期限超過行が0件」と保証する、という表現は運用状態まで保証するように読めます。

テストが保証できるのは、fixture に対して purge 後の postcondition が成立することです。本番で日次処理が止まっていないことまでは保証できません。

修正提案: 保証を「purger 実行後の postcondition」に限定してください。本番の horizon 超過は、Command の件数報告・失敗終了コード・scheduler 運用の責務として分離します。

[Suggestion] privacy のマーカー、節見出し、固定文言、同一要素内の年数を検査する4点構成は妥当です。「節だけ消える」「数字だけ別文脈に残る」の双方を十分に検出できます。

## 5. リスク

[Warning] 繰越仕訳が古い取引を集約した記録である以上、単に新しい `created_at` を付けると、7年後に再び畳み込まれて保持時計が永久に更新され続けます。

これは残高状態の維持として正当化できる可能性がありますが、「取引記録」から「現在残高の状態」へ性質が変わる境界を明示しないと、規約との対応が曖昧になります。

修正提案:

- 繰越行を原取引記録ではなく「現在残高スナップショット」と定義する
- 原取引ID・説明・個別日時など、不要な取引追跡情報を引き継がない
- `carried_forward_through` など集約境界を表す型付き情報を持つ
- 繰越行を再畳み込みする契約と、その際も個別取引情報が復元不能であることをテストする

[Warning] `Subscription` と `SubscriptionItem` の物理削除順序、参照整合性、再契約時の参照について方式が未確定です。

修正提案: 概念設計で少なくとも「子から親」「期限到達判定は親契約の `ends_at`」「他モデルから参照中なら fail-closed + report」と固定してください。方式そのものを詳細設計へ送る場合でも、安全境界はここで必要です。

## 7. 型安全性

[Suggestion] enum をメタデータに限定し、処理を `BillingRetentionPurger` の型付き実装へ委譲する方針はPHPStan level 10に適合します。

`BillingRetentionPurgeResultDto` には少なくとも以下を明示的な型で持たせると安全です。
