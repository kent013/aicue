新変種だったため、Round 6 では**修正差分の再判定**に加えて
**保証境界の設定そのもの**を判定に付した (境界は前提ではなく判定対象である旨を明記した)。
あわせて、こちらが自分で見つけた不利な材料 2 件 (§3 測定手法の誤り / §4 未閉塞の経路) を

## こちらから報告した不利な材料の扱い

### §3 測定手法の誤り (自己申告)

Round 3〜5 でこちらは注入実測の判定に `laravel/pao` の JSON (`"result":"passed"`) を使い、
「全緑になった」と書いていた。本ラウンドで終了コードまで測り直したところ、
**`--filter` 実行の終了コードは skip の有無と無関係に 1 を返し得る**ことが分かった
(skip 0 件・失敗 0 件の `--filter=ArchBaselineScannerTest` でも exit 1)。
したがって終了コードは根拠に使えない。一方**フィルタ無しの全実行**は
正当な skip 2 件を含んだまま exit 0 を返す。

- 結論: 「skip 系の注入は suite を赤くしない」という**主張の実質は維持される**
  (静的 gate とテスト 38 が要るという前提は正しい)。
- 対応: コード中の「全緑になった」2 箇所を
  「**失敗 0 件になった (Pest の出力に赤が 1 つも出ない)**」へ訂正した。
- Codex の判定: この runner の性質を D43 / docblock に**足さない**のが妥当
  (Pest arch ベースラインの契約ではない)。残すなら別 TODO / runbook / 調査 devnote。
  → **本変更には足していない**。

### §4 `tests/Pest.php` 経由のレーン全体 skip (自己申告)

`tests/Pest.php` の `->in('Architecture')` レーンの `beforeEach` 先頭へ
`$this->markTestSkipped()` を 1 行入れると、**フィルタ無しの全実行が
1405 skipped / 5363 passed / 失敗 0 件 / EXIT=0 で緑になる** (対照: 6766 passed / 2 skipped / EXIT=0)。
テスト 38 は `Unit` レーンなので走り続けるが、その中身は宿主ファイルの**静的**検査であり、
宿主ファイルは 1 文字も変わらないため赤くならない。

- Codex の判定: **T252 の境界外**。宿主固有の欠陥ではなく、
  Architecture レーン全体を 1405 件規模で無力化するテスト基盤の問題である。
  本 gate だけで対処すると `phpunit.xml` / runner / Composer script / CI 設定まで
  監視対象が際限なく広がる。
- ただし**影響が大きいので別 TODO を立てる価値がある**とし、候補の不変条件を挙げた:
  - 既知の skip だけを理由付き inventory へ登録する
  - 全実行結果で**未知の skip の増加**を失敗扱いにする
  - レーン配線に無条件 skip が無いことを外部レーンから検査する
  - runner の終了コードだけでなく fail / skip の内訳を検証する
- **T252 の完了とは分離する** (本 worktree では対応しない)。
