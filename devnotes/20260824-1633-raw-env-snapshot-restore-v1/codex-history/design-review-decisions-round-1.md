# 対応マトリクス: design-review Round 1

## 施策 1

### [Critical] i10 の契約テストが機序を通っていない (口を消しても緑になりうる)
- 判断: 対応する
- 根拠: 指摘のとおり。g-1 (repository のインスタンス変更) と g-2 (通常の `env()` 読み出し) だけでは
  「1 度目の boot で `.env.testing` を書いた immutable writer が 2 度目の読み込みで注入値を
  上書きする」経路を 1 度も通らない。上流実装を実読して機序を確定した
  (`Dotenv\Repository\Adapter\ImmutableWriter::write()` は `isExternallyDefined()` =
  「読めて、かつ自分が `$loaded` に記録していない」ときだけ書き込みを見送る。
  つまり**自分が書いたキーは 2 度目に上書きする**)。
- 対応内容: g-2 を機序を通す形へ差し替えた。`refreshApplication()` は
  `RefreshDatabase` のトランザクションを壊しうるので使わず、
  **`Illuminate\Foundation\Bootstrap\LoadEnvironmentVariables` を現在の app に対して再実行する**
  (env の再読み込みだけを起こす最小の経路)。
  検査は 2 部構成 — (g-2) 口を呼ばずに再読み込みすると注入値が `.env.testing` の値へ戻ること、
  (g-3) 口を呼んでから再読み込みすると注入値が維持されること。
  プローブキーは `.env.testing` が実際に宣言していて振る舞いに影響しないもの (`APP_LOCALE`) を使い、
  「そのキーが `.env.testing` に在る」ことも前提の pin として検査する。

### [Critical] h-1 / h-2 の構造検査が実装可能な粒度まで設計されていない
- 判断: 対応する
- 根拠: そのとおり。新しい走査ロジックなので AGENTS.md の走査器共通規約と
  「同じ PR で揃える 4 点」が発火する。
- 対応内容: 純関数の走査器 `Tests\Support\RawEnv\RawEnvGuardStructure` を新設し、
  自己検査 `tests/Unit/Architecture/RawEnvGuardStructureTest.php` を足した (新設 2 ファイル)。
  ブロック境界の取り方 (`try` / `catch` / `finally` の本体の波括弧をトークン深さで対応付ける。
  文字列補間の `T_CURLY_OPEN` を開き括弧として同列に数える)、
  対象メソッドの切り出し方 (`ReflectionMethod` の開始行・終了行で切り、`<?php` を前置してから
  トークン化する)、判定 (適用の `foreach` が `try` 本体の範囲に入り `finally` / `catch` の範囲に
  入らないこと / `restore()` の呼び出しが `finally` (または `catch`) 本体の範囲に入ること)、
  fail-closed (メソッド未検出・`try` が 1 件でない・括弧の不整合・対象の `foreach` が
  ちょうど 1 件でない場合は例外) を明記した。負例は 2 形 (適用を `try` の外へ出した形 /
  復元を `finally` の外へ出した形) をナウドキュメントの合成入力で置く。

### [Warning] 不正キーの契約テストと PHPDoc 型が衝突する
- 判断: 対応する
- 根拠: `non-empty-string` を宣言すると、空文字を渡す負例が PHPStan level 10 で落ちる。
  虚偽の `@var` や ignore は禁止事項 2 に触れる。
- 対応内容: 公開 API の宣言を **`array<string, RawEnvChannels>` / `list<string>`** に改め、
  非空・書式・拒否キーは**実行時の契約**として第 1 段で検査する
  (これは `Webmozart\Assert` の本来の用途である)。
  整数キーの負例は `$changes[$numericKey] = …` (`$numericKey` は `string` 型の変数 `'0'`) で作る
  — PHP が実行時に整数へ畳むので、静的には矛盾せず実行時の拒否を検査できる。
  この変更は施策 3 の `productionEnvGuardFakeFlagVariables()` (`list<string>`) の
  型不一致も同時に解消する。

### [Warning] `restore()` が最初の失敗で止まる / 本体の例外を上書きする
- 判断: 対応する
- 根拠: 「成否によらず元へ戻す」という契約より弱い。
- 対応内容: `restore()` は**全キーの 3 面を最後まで戻し**、失敗したキーを集めて
  最後に 1 つの `RuntimeException` にする形へ改めた。
  `with()` は本体の例外を `restore()` へ渡し、復元にも失敗したときは
  **本体の例外を `previous` に連結**して送出する (情報を落とさない)。
  優先順位 (復元失敗の例外が表に出て、本体の例外が `previous` に入る) を docblock の契約に書いた。

### [Warning] `putenv` 面の値の NUL を第 1 段で検証していない
- 判断: 対応する
- 対応内容: 第 1 段で `processSpecified` な値に NUL が含まれないことを検査する
  (`putenv()` の `ValueError` を適用の段まで持ち越さない)。負例を契約テストへ追加した。

### [Warning] 契約テストの前後掃除が実行環境の値を破壊する
- 判断: 対応する
- 対応内容: `beforeEach` でプローブキーの 3 面の**元の存在状態と値を自前で退避**し、
  `afterEach` でその状態へ戻す形に改めた (単に unset して終える形にしない)。

## 施策 2

### [Critical] 可変関数呼び出しの仕様が矛盾している
- 判断: 対応する (Codex が示した 3 案のうち **3 案目「保証外にして表現を狭める」**を採る)
- 根拠: 「すべての可変関数呼び出しを未解決にする」は raw env と無関係な呼び出しまで
  全件違反にするので採れない。「文字列リテラル `'putenv'` を未解決にする」案も検討したが、
  **走査器自身と `RawEnvWriteKind` がその文字列リテラルを持つ**ため、
  許可 3 か所を増やさない限り自分自身が違反になる (設計が自己矛盾する)。
  限定的なデータフロー解析は、閉じる穴の大きさに対して実装と保守が重すぎる (思考原則 2)。
- 対応内容: 自己検査の「未解決 1」(`$fn = 'putenv'; $fn('K=V');`) を削除し、
  **可変関数呼び出し・`call_user_func` 経由の呼び出しを保証しないものへ明記**した。
  あわせて gate の docblock・D50・契約文書の表現を
  「**列挙した字句の書き込み形に限る**」へ統一した (絶対表現をやめた)。
  監視条件として「この形が実際に現れたら、目録へ登録するのではなく検出規則を足す」を残した。

### [Critical] 分割代入を保証外にしながら「直接の書き込みが無い」と絶対表現している
- 判断: 対応する (**検出対象へ加える**)
- 根拠: 指摘のとおり、分割代入は間接ではなく**字句として明示された直接の書き込み**である。
  検出は難しくない。
- 対応内容: 検出規則へ「分割代入の左辺」を追加した。判定は
  **`[` の対応する `]` の直後が代入記号 (`==` / `===` / `=>` ではない `=`) である `[`…`]`**、
  および **`list(` … `)` の直後が `=` である区間**を「分割代入の対象」として印を付け、
  その区間の中に現れた面を書き込みとして数える (入れ子も同じ規則で扱う)。
  正例をナウドキュメントで 2 形 (`[$_SERVER['K']] = $v;` / `list($_ENV['K']) = $v;`) 置く。

### [Warning] `unset()` の中に現れただけで書き込み扱いすると誤検出する
- 判断: 対応する
- 対応内容: `unset(` の引数リストの中でも、**その面が書き換え対象の根にあるとき**
  (引数の先頭 = 直前の有意トークンが `(` または `,`) だけを `element_unset` にする。
  `unset($other[$_SERVER['K']]);` を負例として置く。

### [Warning] 名前解決に `T_NAME_RELATIVE` / 複数 namespace / 波括弧つき namespace が無い
- 判断: 対応する
- 対応内容: 取り込み対応表を**名前空間ごと**に持つ形にし、次を明記した —
  `T_NAME_RELATIVE` (`namespace\putenv`) はグローバル名前空間のときだけ一致する /
  **1 ファイルに namespace 宣言が 2 つ以上ある、または波括弧つき namespace を使っている場合は、
  そのファイルの `putenv` 相当の出現をすべて未解決にする** (fail-closed)。正例・負例を追加した。

### [Warning] 検出を宣言する代入演算子に対して自己検査が不足している
- 判断: 対応する
- 対応内容: `RawEnvWriteKind` が宣言する代入系トークンを **data provider で全数 1 回ずつ**通す
  (`=` `.=` `+=` `-=` `*=` `/=` `%=` `**=` `??=` `|=` `&=` `^=` `<<=` `>>=` /
  前置・後置の `++` `--` / 多段添字 / 面全体への複合代入)。

### [Warning] 目録の型付き分類が実質的に検証されていない
- 判断: 対応する
- 対応内容: gate の検査を 4 つ足した — 許可パス集合の完全一致 / パスと
  `RawEnvDirectWriteAllowance` の対応の完全一致 / `counts` のキーが既知の
  `RawEnvWriteKind` の値だけであること / 件数が正の整数であること。
  「`unresolved` を登録していない」は既存の G7 が持つ。

## 施策 3

### [Warning] snapshot の入れ物が `null` を setter として扱えず消去できない
- 判断: 対応する
- 対応内容: `store()` と `take()` に分け、`take()` は**必ず保存スロットを空にして**返す形にした。
  `afterEach` は取り出したローカルの snapshot だけを復元する (前ケースの snapshot を
  再利用する経路が構造的に消える)。

### [Warning] `productionEnvGuardFakeFlagVariables()` の `list<string>` と型が合わない
- 判断: 対応する (施策 1 の型変更で解消)
- 対応内容: 公開 API を `list<string>` 受けに改めたので不一致は起きない。

### [Suggestion] 旧関数名が 0 件であることを目録で固定する
- 判断: 見送る
- 根拠: 旧実装の復活は **gate の G1 が構造的に止める** (許可 3 か所以外で 3 面へ書けない)。
  名前の目録を別に持つと、同じことを 2 か所で見張ることになり保守が増える (思考原則 2)。

## 施策 4

### [Warning] 「結線」の新ケースが結線を検査していない
- 判断: 対応する
- 根拠: 提示した assertion は compose の固定値だけを見ており、
  `pgsqlTestParentEnv()` が空を返しても `pgsqlTestConnValues()` の結果を捨てても緑になる。
- 対応内容: 3 面の配列を引数に取る純関数 `pgsqlTestMergeParentEnv()` を切り出し、
  優先順 (`$_SERVER` > `$_ENV` > `getenv`) を決定的に検査する。
  結線のケースは (1) `PATH` / `HOME` / `TMPDIR` が `pgsqlTestParentEnv()` の値と一致すること、
  (2) `DB_HOST` / `DB_PORT` / `DB_USERNAME` / `DB_PASSWORD` が
  `pgsqlTestConnValues()` の結果と一致すること、を見る形に改めた (親環境は 1 面も触らない)。
