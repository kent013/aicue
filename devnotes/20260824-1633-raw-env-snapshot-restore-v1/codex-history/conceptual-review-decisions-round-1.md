# 対応マトリクス: conceptual-review Round 1

## [Critical] 3-1 `RawEnvChannels` の状態モデルが不十分 (未指定 と 明示的 null が潰れる)
- 判断: 対応する
- 根拠: 指摘のとおり。`array<string, mixed>` の口を公開すると i3 (存在と値の分離) と i7
  (未指定の面は明示的に未設定) が呼び出し側の作法頼みになる。aicue には
  「`$_SERVER` に非文字列 (配列) を入れて fail-closed を確かめる」既存ケースがあるため
  値の型は絞れず、**指定の有無を値と別に持つ以外に解が無い**。
- 対応内容: 概念設計の §実装方針に **状態モデル** の節を追加。
  `RawEnvChannels` は面ごとに `specified: bool` + `value: mixed` を持つ不変オブジェクトにし、
  生成は `none()` からの `withServer()` / `withEnv()` / `withProcess()` と
  `sameOnAllSurfaces()` に限る (配列リテラルの口を公開しない)。
  退避側 (`RawEnvSnapshot` の内部状態) も `exists: bool` + `value: mixed` を面ごとに持ち、
  `getenv()` だけは `string|false` をそのまま保持する。

## [Critical] 5-1 i12 gate の走査仕様が曖昧
- 判断: 対応する
- 根拠: 指摘のとおり。不完全な走査器は新しい手書きを黙って通すので、i1 が
  「入れた直後だけ成り立つ」性質に戻る (正典 s13 と同じ理由)。
- 対応内容: 概念設計へ **走査の検出契約** の節を追加。検出する形 (通常代入 / 複合代入 /
  `??=` / インクリメント / `unset()` / 参照取得 / 面そのものへの代入 / `putenv('K=V')` と
  `putenv('K')` の両形) と、**解決できない形は無視せず違反として報告する fail-closed** を明記。
  併せて誤検出しない側 (文字列・コメント・ヒアドキュメント本文・`putenv` を接頭辞 / 打ち消し /
  接尾辞で含む別識別子) も負例として固定することを書いた
  (AGENTS.md 走査器共通規約 (b)(c)(e))。

## [Critical] 7-1 公開 API の型境界が未設計
- 判断: 対応する
- 根拠: 3-1 と同根。曖昧な連想配列を公開すると面の指定漏れ・存在状態の潰れ・
  拒否キーの混入を静的に防げない。
- 対応内容: 3-1 の状態モデルに加えて、キーの検証を**生成の境界**で行うことを明記
  (`with()` / `captureAndClear()` の第 0 相)。`putenv()` の戻り値 `false` は必ず例外へ変換する。

## [Warning] 2-1 `TestDatabaseSchemaUpdateTest` の書き換えで結線の検証を失わないこと
- 判断: 対応する (ただし新しい結線テストは足さない)
- 根拠: 実読で確認したところ、**結線は既に別のケースが押さえている** —
  「`$runArtisan` へ渡る引数列がちょうど 2 通り・この順序・これ以外は 1 度も渡らない」を
  固定するケースが実在し、`ensureTestDatabaseSchemaUpdated()` が
  `pgsqlTestArtisanEnv()` の戻り値を `$runArtisan` の第 2 引数へ渡す経路はそこを通る。
  今回の変更は `pgsqlTestArtisanEnv()` の**内部を純関数へ切り出すだけ**で、
  この関数の呼び出し位置も戻り値の形も変えない。
- 対応内容: 概念設計へ「保持する検証」を明記し、
  `pgsqlTestArtisanEnv()` が「実際の親環境の読み出し + 接続値」から組み立てる結線を
  薄い 1 ケースで固定する (固定キーが戻り値に載っていること) ことを追加した。
  子プロセス起動そのものの検証は T249 の領域なので広げない。

## [Warning] 3-2 i10 の副作用依存を実行時にも固定すべき
- 判断: 対応する
- 根拠: docblock の監視条件だけでは「緑のまま保証だけ失われる」(正典 q3 が名指しした形) を
  検出できない。
- 対応内容: 契約テストへ (g) として追加 —
  `Env::getRepository()` のインスタンス同一性が `forgetLaravelEnvRepository()` の前後で

## [Warning] 4-1 「適用途中でも巻き戻る」を動的保証のように書くのは強すぎる
- 判断: 対応する
- 根拠: そのとおり。正典 q2 も動的に作れないことを認めている。
- 対応内容: 概念設計の期待効果の表現を「構造の固定で代える」と明示に改め、
  契約テストの「保証しないもの」へ書くことを明記。あわせて
  「検証で拒否されたときに 1 面も変わっていない」は**動的テストで必ず持つ** (i11 (d))。

## [Warning] 5-2 走査器の負例を fixture ファイルで持つと gate と矛盾する
- 判断: 対応する
- 根拠: 指摘のとおり。`tests/Architecture/fixtures/` に置くと母集団に入り、
  許可箇所を増やすことになる。
- 対応内容: 負例は**ソース文字列 (nowdoc) を走査器へ直接渡す形**に限ると明記した。
  nowdoc の本文は `token_get_all()` では 1 つのトークンになり中の綴りが見えないため、
  自己検査ファイル自身は gate に対して違反にならない (既存の
  `ForbiddenStatementScanner` の docblock が同じ性質を実測で記録している)。

## [Warning] 5-3 `devnotes/` 全除外の扱いと件数の固定
- 判断: 対応する (ただし「追跡 PHP 総数の完全一致」は採らない)
- 根拠: 追跡 PHP 総数を定数で完全一致させると、無関係な PHP ファイルを 1 本足すだけで
  赤くなる。守りたいのは「**どこにも分類されずに黙って走査から落ちるファイルが無いこと**」
  なので、恒等式で見るほうが強くかつ壊れにくい。
- 対応内容: gate に (1) 走査対象数の床値、(2) `走査対象数 + 除外数 = 追跡 PHP 総数` の恒等式、
  (3) 除外集合が `devnotes/` 配下と完全一致すること、(4) `devnotes/` に追跡 PHP が実在すること
  (除外の形骸化の検出) の 4 つを置く。docblock に「`devnotes/` 配下は保証対象外」と明記する。
