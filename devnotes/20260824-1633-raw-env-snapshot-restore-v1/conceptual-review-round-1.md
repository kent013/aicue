全体判定: **CHANGES_REQUESTED**

### 1. 使命との整合性

[Suggestion] 本件はテスト基盤の改善ですが、PWA の秘匿性・本番起動時 fail-fast を守るテストの再現性を高めるため、使命への間接的かつ本質的な貢献はあります。特に親プロセスへ開発用 DB 名や攻撃者制御パスを注入する経路の撤去は妥当です。

### 2. 禁止事項違反

[Warning] `TestDatabaseSchemaUpdateTest` の書換えで、親環境を書き換える検査から「配列を渡す純関数の検査」へ移す場合、子プロセスへ渡す最終環境の挙動検証まで失わないことを明示してください。純関数だけのテストになると、組立結果が実際の Artisan 起動へ渡される結線を検証しなくなるおそれがあります。

修正提案: 純関数の単体テストに加え、親環境を変更せずに最終的な子プロセス起動引数へ組立済み配列が渡ることを既存の安全なモック／プロセス境界で確認してください。T249 の領域へ拡張せず、現行の結線不変条件だけを保持する形に限定します。

[Suggestion] 旧「ヘルパー関数」の削除は既存テストの削除には当たりません。ただし各テストが検証する不変条件数を維持することを、変更レビュー時に対応表で確認できるようにすると安全です。

### 3. 実現可能性

[Critical] `RawEnvChannels` の状態モデルがまだ不十分です。「未指定なら明示的に未設定」と「明示的に `null` を設定する」を区別しなければ、i3・i7 と PHPStan level 10 を同時に満たせません。単なる `array<string, mixed>` や nullable 値では、指定有無が消えます。

修正提案: 各面を `specified: bool` と `value: mixed` で表す値オブジェクト、または同等の明示的な状態型にしてください。退避側も `exists: bool` と `value: mixed` を別保持し、`getenv()` だけは `false|string` をそのまま区別して保持します。

[Warning] i10 の `Env::enablePutenv()` 利用は可能ですが、repository を捨てる副作用に依存します。設計上、「いつ repository を再構築するか」と「この操作が後続テストへ残す状態」を明確化しないと、環境値の復元後も Laravel 側の repository が古い状態を保持する危険があります。

修正提案: `forgetLaravelEnvRepository()` の呼出し前後で Laravel の `env()` が三面の変更を読むこと、復元後に元の値へ戻ることを契約テストに追加してください。docblock の監視条件だけでなく、現行 Laravel 12 に対する実行時検証として固定すべきです。

### 4. 期待効果の妥当性

[Warning] 「適用途中の失敗でも必ず巻き戻る」は合理的な設計目標ですが、現計画では動的に検証されず、構造固定に依存します。期待効果を動的に保証されたものとして表現すると強すぎます。

修正提案: 構造テストで保証する範囲を明記し、「`putenv()` が途中で失敗する実行時ケースは未検証」と契約テストの保証外に明示してください。また、検証失敗時に三面が一切変わらない動的テストは必須です。

[Suggestion] 読み出し順のテストは raw な三面の確認だけでなく、実際に Laravel `env()` を通して `$_SERVER → $_ENV → getenv()` を検証するのが適切です。

### 5. リスク

[Critical] i12 の gate はこの改善の維持可能性の中心ですが、走査仕様が曖昧です。`$_SERVER`／`$_ENV` の代入・`unset`・参照代入・複合代入、ならびに `putenv()` の呼出しをどこまで「直接書込み」と認定するかが未定義です。不完全な scanner は、新たな手書き実装を黙って通す可能性があります。

修正提案: scanner の契約に検出対象を明記し、少なくとも通常代入、複合代入、`unset`、`putenv('K=V')`、`putenv('K')` を正例として固定してください。文字列・コメントは誤検出せず、解釈不能な対象構文は無視せず gate を失敗させる fail-closed 方針を採用してください。

[Warning] i12 の許可箇所を「部品・契約テスト・bootstrap のみ」とするなら、scanner 自己テスト用 fixture の PHP ファイルに直接操作を書けません。fixture を置くと gate が矛盾します。

修正提案: scanner 自己テストはソース文字列を入力する方式にするか、fixture を用いるなら gate の母集団外であることを設計・テスト双方で明示してください。後者は許可箇所を増やすため、前者が簡潔です。

[Warning] `devnotes/` の全除外は q1 の実測に対しては理解できますが、将来そこに実行される PHP が置かれても検出対象外です。

修正提案: 除外対象が `devnotes/` のみであること、追跡 PHP 数・除外数・検査対象数が期待値と一致することを gate で固定してください。さらに docblock に「devnotes 配下の実行可能 PHP は保証対象外」と明記してください。

### 6. スコープの適切さ

[Suggestion] 旧実装の集約、危険な親環境操作の撤去、専用契約テスト、i12 gate は一つの不変条件群として結合しており、スコープは適切です。T249 の子プロセス環境統制や config 評価の重複統合を外している判断も妥当です。

### 7. 型安全性

[Critical] `mixed` を保持する方針自体は i3 と PHPStan level 10 に整合しますが、公開 API の型境界が未設計です。曖昧な連想配列を公開すると、面の指定漏れ・存在状態の潰れ・許可されないキーの混入を静的に防げません。

修正提案: `RawEnvSnapshot`、各面の入力状態、退避済み状態を専用 value object に分離してください。`mixed` は値フィールドにだけ閉じ込め、キーは検証済みの `non-empty-string` 相当として constructor/factory 境界で確立します。`putenv()` の失敗は例外へ変換し、PHPStan に false を見逃させない実装にしてください。

上記、とくに状態型・i10 の実行時検証・i12 scanner の検出契約を設計へ追加できれば、正典 v1 への追従として承認可能です。
