# 全体判定: CHANGES_REQUESTED

2件の反論はいずれも受け入れます。

- 可変関数呼び出しを保証外とし、検出力の主張を狭める判断は妥当です。
- 旧関数名専用の目録を追加しない判断も妥当です。G1 が旧実装と同等の直接書き込みを止めるため、別の名前 inventory は不要です。

ただし、施策1を中心に未解決点が残っています。

## 施策 1: REQUEST_CHANGES

- [Critical] g-2 / g-3 は immutable writer の `$loaded` 状態を決定的に作れていません。  
  現在の例では、「既存 repository がすでに `.env.testing` から `APP_LOCALE` を書き、`$loaded` に記録している」ことに依存しています。一方、各テスト後の `forgetLaravelEnvRepository()` は repository を捨てます。次のテストで repository が空の状態から作られると、先に注入された `zz` は外部定義と判断され、g-2 でも上書きされない可能性があります。

  実行順や直前のテストによって結果が変わるため、現状では機序の固定になりません。

  修正案: g-2 / g-3 の各ケース内で、次の priming を明示してください。

  1. `APP_LOCALE` の3面を一旦未設定にする
  2. `forgetLaravelEnvRepository()` を呼ぶ
  3. `LoadEnvironmentVariables` を実行する
  4. `.env.testing` の値が読み込まれたことを確認する  
     これにより、その repository の writer が `APP_LOCALE` を `$loaded` に持つ
  5. その後に `RawEnvSnapshot::with(...'zz'...)` を実行する
  6. g-2 は口なしで再読込して `.env.testing` 値へ戻ること、g-3 は口ありで `zz` が残ることを確認する

  ケース全体の外側では、自前で退避した元の3面へ戻してください。

- [Critical] i-3 は提示された実装では動的に検査できません。  
  設計自身が「検証を通ったキーで `putenv()` を失敗させる状況を作れない」としていますが、i-3 は以下を動的に確認すると宣言しています。

  - 復元が最初の失敗で止まらない
  - 全キーを戻してから例外になる
  - 本体例外が `previous` に入る

  `putenv()` を差し替える seam は設計されていないため、このテストは実装不能です。

  修正案は次のいずれかです。

  - `putenv` 実行を注入可能な小さな test-only writer に分離し、指定したキーだけ `false` を返す fake で動的に検査する
  - i-3 を構造検査へ変更し、`restore()` が失敗をリストへ蓄積し、ループ終了後にだけ例外を投げることを `RawEnvGuardStructure` で固定する

  後者を選ぶ場合、「動的テスト」ではなく「構造テストのみ」と保証表にも明記してください。

- [Warning] `RawEnvGuardStructure` は「対象の適用ループ」を十分に同定していません。  
  `$changes` を直接回す `foreach` が `try` 内にあることだけでは、そのループ内で `self::apply()` が呼ばれていることを保証できません。空のループを `try` 内に残し、実際の適用を別の場所へ移しても通り得ます。

  また、h-2 は「復元と再送出」を保証するとしていますが、現在の走査 API は catch 内の `$snapshot->restore()` しか検査せず、`throw $e` を検査しません。

  修正案:

  - 対象 `foreach` のブロック範囲を取得する
  - `self::apply(...)` がその `foreach` 内にちょうど1件あることを検査する
  - `captureAndClear()` では `throw $e` が対象 catch 内にあることを検査する
  - `with()` は `try=1 / catch=1 / finally=1`
  - `captureAndClear()` は `try=1 / catch=1 / finally=0`

  のように、メソッドごとの期待件数を明記してください。「`T_FINALLY` / `T_CATCH` も同様」では両メソッドの構造差を表現できません。

## 施策 2: REQUEST_CHANGES

- [Warning] 分割代入の範囲内にあるすべての面を target とすると誤検出します。

  例えば次の `$_SERVER` は添字を求めるための読み出しであり、書き込み対象ではありません。

  ```php
  [$other[$_SERVER['K']]] = $values;
  list($other[$_SERVER['K']]) = $values;
  ```

  現在の「分割代入区間の中に現れた面を書き込みとして数える」規則では、これらも `destructuring_target` になります。

  修正案: 分割代入の各要素について、lvalue の根が `$_SERVER` / `$_ENV` である場合だけ検出してください。上記2形を負例へ追加し、次のような実際の target は引き続き正例にします。

  ```php
  [$_SERVER['K']] = $values;
  [[$_ENV['K']]] = $values;
  ```

可変関数呼び出しを保証外にした判断と、その限定表現・監視条件には異論ありません。

## 施策 3: APPROVE

`store()` / `take()` に分けて stale snapshot の再利用経路を消した対応は妥当です。

旧関数名専用の目録を追加しない判断も受け入れます。ここは追加変更不要です。

## 施策 4: APPROVE

3面の合成を純関数へ分け、優先順と実際の結線を別々に検査する構成で、前回の指摘は解消されています。

親プロセスへ拒否対象値を立てず、接続値にも識別可能な probe 値を使う点も妥当です。

## 施策 5: REQUEST_CHANGES

- [Warning] D50 の限定表現がまだ完全には統一されていません。  
  「揃え続ける不変条件」では適切に限定されていますが、D50 の見出しと「業務要件起因の説明」は依然として次の絶対表現です。

  可変関数呼び出しなどを保証外とした以上、この表現は保証範囲より広く読めます。

  修正案: 見出しと業務要件起因の説明も、例えば次へ揃えてください。
