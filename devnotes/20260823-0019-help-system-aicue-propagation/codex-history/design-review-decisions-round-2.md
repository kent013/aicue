## [Warning] S4 — 例外メッセージの契約（クラス・不正箇所・直し方）と実装が一致していない

- 判断: **対応する**
- 根拠: 正当な指摘。docblock で「例外には**対象クラス / 不正だった箇所 / 直し方**を必ず含める」と
  宣言しておきながら、`required` の重複・パラメータ名の不正・パラメータ定義の不正の 3 分岐に
  **直し方 (`$hint`) が無い**。**自分が掲げた契約を実装が満たしていない**のであり、
  かつテスト計画 (T4) が「直し方が含まれる」を assert すると宣言しているので、
  このままでは設計どおりのテストが書けない。
- 対応内容: 3 分岐すべてに `— {$hint}` を付けた。
  `required` 重複は「不正箇所」としてキー名を含む形をそのまま残す
  （`$hint` を足すだけで、クラス・箇所・直し方の 3 点が揃う）。

## [Warning] S6 — T4 のメッセージ検査が一律で「パラメータ名」を要求していて成立しない

- 判断: **対応する**
- 根拠: 正当。`required` が list でない・`properties` が配列でない等の**構造異常では
  パラメータを特定できない**ので、パラメータ名を一律に要求する assertion は書けない。
  曖昧な一律 assert は検出力の主張を薄めるので、負例ごとに何を要求するかを分ける。
- 対応内容: T4 の検査契約を 3 段に分けた。
  1. **全負例で共通**: 対象クラス名 / 不正箇所 / 直し方 の 3 点
  2. **パラメータを特定できる負例のみ**: 追加でパラメータ名
  3. **キーが判明している負例（`required` 重複・未知の required 名）**: 追加でそのキー名
