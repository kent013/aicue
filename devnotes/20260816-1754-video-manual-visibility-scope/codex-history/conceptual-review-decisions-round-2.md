# 対応マトリクス: conceptual-review Round 2

Codex 全体判定: CHANGES_REQUESTED (「作らない」結論は支持。前提の明示・Project 分割の扱い・T-1 の判定力を要修正)

## [Warning] 「使命と衝突する」は恒久的な作成者限定に限定すべき (観点 1)
- 判断: **対応する**
- 根拠: 妥当。「撮影依頼時に可視範囲が遷移する」設計は要求としてあり得るし、それは
  恒久的な公開範囲ではない (状態遷移である)。前提を書かないと過剰な一般化になる。
- 対応内容: §3 の仮説と §7 の結論に **「`doc/02` の値を、完成後も維持される恒久的な公開範囲と
  解釈する限り」** という前提を明記した。可視範囲が遷移する要求は (B) 側 (状態/workflow) と整理した。

## [Warning] draft の記述は「PC 一覧では見える」までしか証明できていない (観点 2)
- 判断: **対応する (実読して範囲を確定した)**
- 根拠: 妥当な指摘。一覧のクエリと Policy だけでは詳細経路の状態制約の不在は言えない。
- 対応内容: PC 側の manual 到達経路の状態条件を実際に grep + 実読した。
  `ManualScenarioController` / `ManualAnalysisController` / `SourceDocumentController` /
  `CutTakeController` / `VideoManualController` には状態による遮断が**無く**、
  状態を見ているのは `ManualDownloadController`
  (`$manual->status !== VideoManualStatus::Published` で 404) **1 か所だけ**である。
  §2-4 に「実読して確認した経路」を列挙する形へ書き換えた。

## [Warning] 「403 では目的を果たさない」は強すぎる。取得不能と存在秘匿を分けよ (観点 3)
- 判断: **対応する**
- 根拠: 妥当。存在秘匿が要件でなければ 403 は通常の選択肢であり、その場合は
  現行の層分けを壊さずに実装できる (コストの見積りが変わる)。
- 対応内容: §5-1 を「要求が *取得不能* までなら 403 で層 3 に載る / *存在秘匿* まで求めるなら
  主体依存 404 の再設計が要る」と 2 分岐に書き換え、T-1 の条件 4 も同じ 2 分岐で問う形にした。

## [Warning] §4-3 の「4 件すべて Project 分割で代替できた」は本文と矛盾 (観点 4)
- 判断: **対応する**
- 根拠: そのとおり。未承認 draft は workflow、事故・懲戒は閲覧者リストであり Project 分割ではない。
- 対応内容: 結論文を **「4 件とも『作成者のみ』を必要とせず、Project 境界 / workflow /
  閲覧者リストのいずれかで扱う」** に修正した。

## [Suggestion] 反例「編集者個人の恒久的な下書き・検証用 manual」を足す (観点 4)
- 判断: **対応する**
- 根拠: 唯一「作成者のみ」が素直に当てはまる形の反例であり、扱わないと検討漏れに見える。
- 対応内容: §4-3 に 5 件目として追加し、「標準化された教材を組織へ受け渡す」使命から外れるため
  アプリが提供すべき機能ではない、と根拠付きで棄却した。

## [Warning] T-1 は「作成者のみが解になる」ことを判定できていない (観点 5)
- 判断: **対応する**
- 根拠: 決定的な指摘。現行 T-1 は「安全担当 3 名に限定したい」でも成立してしまい、
  それは `created_by` では解けない (閲覧者リストの要求である)。
- 対応内容: T-1 に条件を追加した — (a) 許可主体が**作成者本人だけ**であること、
  (b) 受け渡し時点 (撮影依頼・承認・公開) と可視性の遷移が記録されていること、
  (c) Project 境界・workflow/状態・閲覧者リストの**3 つとも**代替にならない理由が記録されていること、
  (d) その理由を要求元の主張だけでなく**設計責任者が確認した**こと。

## [Suggestion] T-2 は自動昇格ではなく再評価開始条件 (観点 5)
- 判断: **対応する**
- 対応内容: T-2 を「Open へ昇格する条件」ではなく「本設計を読み直して要否を再評価する条件
  (不要になる可能性の方が高い)」と明記した。

## [Warning] Project 分割は現行で使える代替ではない (v1 は単一 Default Project) (観点 6)
- 判断: **対応する (事実を確認して記述を弱めた)**
- 根拠: 妥当。AGENTS.md の v1 スコープは「単一 Default Project」であり、
  `DefaultProjectResolver` の docblock も「v1 = 単一 Default Project 前提」と明記している
  (撮影 PWA の入口 `capture.home` は org の先頭 project へ redirect する)。
  複数 Project 自体は PC UI から作成できる (`ProjectController::create/store`) が、
  `ProjectPolicy::view` が組織メンバー全員に true を返すため**分割しても可視性は分離されない**。
- 対応内容: §4-2 / §4-3 / §5-5 の表現を「現行で受けられる」から
  **「要求が出たときに `visibility_scope` より先に設計すべき将来案 (複数 Project 運用 +
  読み取り境界の 2 点セット)」**へ改めた。v1 スコープとの緊張も明記した。

## [Warning] §5-5 の「案 1 が先」は無条件には成り立たない (観点 7)
- 判断: **対応する**
- 根拠: 妥当。manual 単位で少人数へ公開したい要求では Project 乱造より閲覧者リストが適切。
- 対応内容: 固定の優先順位をやめ、**要求の単位で分岐する対応表**へ書き換えた
  (束/顧客/工程 → Project 境界、承認前だけ → workflow/状態、manual 単位の複数人 → 閲覧者リスト、
  本当に作成者本人だけ → visibility_scope を再評価)。
