# 対応マトリクス: design-review Round 2

Codex 全体判定: CHANGES_REQUESTED (§6 のみ REQUEST_CHANGES。他 8 節は APPROVE)

## [Warning] §6-2 の適用範囲と決定点表の「実装の形」が一致していない
- 判断: **対応する**
- 根拠: 妥当。冒頭で「全 manual-bound ability に適用」と確定しておきながら、
  直後の案 (あ) の欄が「`VideoManualPolicy::view` に条件を足す」だけだったため、
  表を起点に実装すると Round 1 で排除した `view` 限定へ戻れてしまう。
- 対応内容: 案 (あ) の「実装の形」を
  「Project 境界確認の後、全 manual-bound ability に共通述語を適用 / 子リソース Policy も
  親 manual の同じ述語を前提 / 一覧・集約・通知クエリには同義の query scope」へ書き換え、
  コスト欄にも「`view` だけに足す形は採らない」と明記した。

## [Warning] §5 の昇格条件 (A / C) と §6 の「撮影者例外」が論理的に両立しない
- 判断: **対応する (指摘が正しい。設計の矛盾だった)**
- 根拠: 決定的な指摘。T-1 の適格条件 A は「許可主体は作成者本人だけ」、C は
  「終端状態まで作成者限定を維持」である。それを満たして昇格した要求に対して
  「撮影対象になったら Project 内へ開く」規則を実装すると、**昇格させた要求とは別物**になる。
  「撮影依頼までは作成者だけ」という要求は C により既に workflow 側へ振り分けられており、
  §6 で例外を復活させると実装仕様が 3 通りに割れて別の設計者が到達できない。
- 対応内容: T-1 の定義を維持し、**§6 から撮影者例外を削除**した。
  - §6-3: 「撮影者の詰みを防ぐ規則を述語に置く」を削除し、
    **「撮影者への例外公開を述語に入れてはならない」**と理由付きで反転させた。
    本設計で扱う「作成者のみ」は**撮影者を含め終端まで開かない**ものただ 1 つと定義した。
  - §6-6: テスト項目を「作成者限定の manual が撮影工程へ進まないこと」+
    「作成者限定でない manual は撮影者が今までどおり見られること (非後退)」へ差し替えた。
  - §6-7: リスクを「**作成者限定のまま撮影工程へ投入できてしまう状態遷移の不整合**」とし、
    例外公開で塞がないことを明記した。

## [Suggestion] §6-1 の再調査方法は route 起点だけでは脱落する
- 判断: **対応する**
- 根拠: 妥当。ダッシュボード (`DashboardService` の 3 クエリ) と通知は `{manual}` を
  route parameter に持たないため、route 起点の数え直しでは落ちる。
- 対応内容: 「`{manual}` route を起点に数え直し、**加えて `VideoManual` または cuts/takes から
  manual へ到達する Controller・Policy・一覧/集約/通知クエリを検索する**」へ書き換えた。
