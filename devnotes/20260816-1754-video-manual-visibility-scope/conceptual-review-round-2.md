作らない判断は引き続き妥当ですが、Project 分割を現実に利用可能な代替策として扱う前提と、T-1 が「作成者のみ」の必要性を判定できていないため、現時点では CHANGES_REQUESTED です。

全体判定: **CHANGES_REQUESTED**

### 1. 使命との整合性

[Suggestion] 恒久的な「作成者のみ」が編集者から撮影者への受け渡しを遮断する、という中心的な判断は妥当です。一時的な非共有を workflow の問題として分離したことで、「作成者のみは常に不要」という過剰な一般化も解消されています。

[Warning] §3 と §7 の「作成者のみは使命と衝突する」という表現は、設定中だけでなく公開後も作成者限定を維持する場合に限定すべきです。撮影依頼時に可視範囲が遷移する設計は「恒久的な作成者のみ」ではありませんが、要求としては十分あり得ます。

修正提案: 「`doc/02` の値を完成後も維持される恒久的な公開範囲と解釈する限り」と前提を明記してください。

### 2. 事実の正確さ

[Suggestion] `mine` についての訂正は正確です。これは利用者自身の一覧を絞る検索条件であり、他者からの到達を制限しません。

[Warning] `draft` について、提示された根拠から確実に言えるのは「PC 一覧では同一組織メンバーに表示される」ことです。`manualRows` と `ProjectPolicy::view` だけでは、すべての「PC 詳細」経路に状態ベースの追加制約がないことまでは証明できません。

修正提案: 実読済みの詳細 route/controller を列挙するか、記述を「少なくとも PC 一覧では見える」に限定してください。後者でも今回の見送り判断は成立します。

### 3. セキュリティ不変条件

[Suggestion] cross-org の「全ユーザー」を組織内全員へ読み替える判断、および主体依存 404 を「不可能ではないが既存の固定物の再設計が必要」とした訂正は妥当です。

[Warning] 「403 では公開範囲の目的を果たさない」も少し強い表現です。認可拒否で存在を秘匿することが業務要件でなければ、403 は通常の選択肢です。現在の T-1 では直接 URL でも「見えない」とありますが、404 が必要なのか、内容を取得できない 403 でよいのかが区別されていません。

修正提案: T-1 で「取得不能」と「存在秘匿」を分け、存在秘匿まで必要な場合だけ主体依存 404 の再設計対象にしてください。

### 4. 業務シナリオの見落とし

[Suggestion] 代表的な反例は十分に扱われています。特に事故・懲戒動画が「作成者のみ」ではなく複数人 ACL の要求だという整理は適切です。

[Warning] §4-3 の「4 件すべて Project 分割で代替できた」は本文と矛盾します。未承認 draft は承認 workflow で扱うとしており、Project 分割ではありません。また、事故・懲戒動画は既存 Project 内の一部担当者だけに見せる要求なら、Project 分割が業務上妥当とは限りません。

修正提案: 結論を「4 件とも作成者のみを必要とせず、Project 境界・workflow・別の閲覧者モデルのいずれかで扱う」に変更してください。

追加すべき反例は「編集者個人の恒久的な下書き・検証用 manual」です。ただし、これは標準化された教材を組織へ受け渡す North Star から外れるため、AI-CUE が提供すべき機能ではない、と棄却できます。

### 5. トリガー条件

[Warning] T-1 は記録の有無を客観化できていますが、「作成者のみが解になる」ことは判定できません。現在の4条件は、事故動画を安全担当者3名だけに見せる要求でも成立します。しかし、その要求を `created_by` で制御しても解決しません。

修正提案: 次の条件を追加してください。

- 要求される許可主体が「作成者本人だけ」であること
- 撮影・承認・公開など、他者への受け渡しが必要になる時点と可視性の遷移が記録されていること
- Project 境界だけでなく、承認 workflow・状態・閲覧者リストでも代替できない理由が記録されていること
- 「代替できない理由」を要求元の主張だけでなく、設計責任者が確認したこと

これにより、判定者が変わっても「単なる限定公開」と「作成者のみ」を区別できます。

[Suggestion] T-2 と T-3 は再評価トリガーとして妥当です。ただし T-2 は Open への自動昇格ではなく、要否の再評価開始条件です。Project が境界になれば公開範囲が不要になる可能性も高いためです。

### 6. スコープの適切さ

[Warning] Project 分割を「既に存在する正面の解」とする主張には、v1 の「単一 Default Project」と緊張があります。さらに現行 `ProjectPolicy::view` では分割しても可視性が分離されません。したがって現時点の Project 分割は、利用可能な代替機能ではなく将来案です。

修正提案: 「現行で受けられる」ではなく、「要求発生時には visibility_scope より先に Project の複数運用と読み取り境界を設計する」と記述してください。複数 Project が v1 外なら、その点も明示すべきです。

[Suggestion] カラムだけ先行追加しない判断は妥当です。全行が同一値になるカラムには現時点で業務情報がなく、移行と認可経路だけを増やします。

### 7. 型安全性・実現可能性

[Suggestion] 実装コストの評価は概ね妥当です。Policy だけでなく一覧、ダッシュボード、通知、子リソース経由、行別 ability の前提まで影響するため、要求がない段階で導入する合理性はありません。DTO / JsonResource と PHPStan level 10 を阻害する本質的問題もありません。

[Warning] §5-5 の「案1が先」は条件付きでのみ妥当です。Project が実際の業務分離単位であり、複数 Project の運用が提供され、組織管理者の横断アクセスや非所属ユーザーの扱いを定義できる場合に限られます。manual 単位で所属が異なる、または少人数の横断担当者へ公開する要求では、Project の乱造より閲覧者リストが適切な可能性があります。

修正提案: 優先順位を固定せず、要求の単位で分岐させてください。

- 束・顧客・工程単位: Project 境界
- 承認前だけ: workflow / 状態
- manual 単位の複数人: 閲覧者リスト
- 本当に作成者本人だけ: visibility_scope を再評価

以上を直せば、「今は作らない」という結論は十分に APPROVED にできる状態です。
