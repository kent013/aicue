[Warning] §6-2 の適用範囲と決定点表の「実装の形」が一致していません。

§6-2 冒頭では、述語をすべての manual-bound ability に適用すると確定しています。一方、直後の案（あ）は「`VideoManualPolicy::view` に `created_by` 条件を足す」とだけ記載されています。表だけを起点に実装すると、Round 1 で排除した `view` 限定実装へ戻る余地があります。

修正案: 案（あ）の実装の形を次の趣旨へ変更してください。

> Project 境界確認後、`VideoManualPolicy` の全 manual-bound ability に共通の可視性述語を適用する。子リソース Policy も親 manual の同じ述語を前提とする。一覧・集約クエリには同義の query scope を適用する。

[Warning] §5 の昇格条件と §6-3・§6-6 の「撮影者例外」が論理的に両立していません。

T-1 の A は「許可する主体が作成者本人だけ」、C は「終端状態まで作成者限定を維持」としています。これを満たして昇格した manual を「撮影対象になった時点で Project 内へ開く」と、A・C を満たさなくなります。さらにテスト計画の「撮影者が撮るべき manual を見られること」も、作成者限定 manual について求めるなら同じ矛盾になります。

これは用語上の問題だけではありません。別の設計者は次のいずれを実装すべきか判断できません。

- 作成者以外には、撮影者を含めて終端まで一切見せない
- 作成者限定だが、撮影者には例外的に見せる
- 撮影工程への移行時に、作成者限定を解除する

後二者は、現在の T-1 ではそれぞれ A または C により Conditional の対象外です。

修正案: T-1 の定義を維持し、§6 から撮影者例外を削除するのが整合的です。

- §6-3: 「撮影者の詰みを防ぐ規則を述語に置く」を削除
- §6-6: 「撮影者が撮るべき manual を見られること」を、「作成者限定 manual が撮影対象として割り当てられないこと、または撮影工程へ進めないこと」へ変更
- §6-7: リスクを「作成者限定のまま撮影工程へ投入できてしまう状態遷移の不整合」とする

撮影依頼時に公開する要求は、§5 C が既に workflow 側へ正しく振り分けています。この境界を§6でも維持するのが最も明快です。

[Suggestion] §6-1 の再調査方法は、`routes/web.php` の `{manual}` だけでなく、manual を直接 route parameter に持たない関連経路も対象にするとより確実です。

現在の一覧にもダッシュボードや通知が含まれているため、次のように書くと調査母集団の脱落を防げます。
