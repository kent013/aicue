全体判定: **CHANGES_REQUESTED**

使命への方向性は強く妥当です。状態表示・撮影ナビゲーションの可読性を、実装後の目視ではなく不変条件として守る意義は大きいです。ただし、i15/i16 の「実在する組を漏れなく検査する」という核心主張を成立させるには、走査境界と背景モデルをさらに厳密にする必要があります。

1. 使命との整合性

- [Suggestion] AA 未達の状態色を是正し、未宣言の配色追加を検査で防ぐ方針は、「思考ゼロ」の撮影体験に本質的に寄与します。
- [Warning] 「屋外では読めない」は AA 4.5:1 の計算だけでは立証できません。AA は通常の閲覧条件の基準であり、屋外環境光での可読性保証ではありません。  
  修正提案: 期待効果は「少なくとも WCAG AA の最低基準を満たし、可読性劣化を機械的に防ぐ」と表現し、屋外での実利用評価は別途検証対象として分けてください。

2. 禁止事項違反

- [Suggestion] PHP を変更せず、既存 gate を削除せず、検査・CSS・文書・乖離台帳を同一変更に収める計画は、提示された禁止事項と整合しています。
- [Suggestion] `response()->json()`、Prism 直呼び、POST リダイレクト、disabled UI に関わる変更もありません。

3. 実現可能性

- [Critical] i15 の状態単位解析は、単純な class 文字列だけでは Svelte の実際の適用 class を網羅できません。`class:` ディレクティブ、条件式・テンプレート文字列、`clsx` 相当のヘルパー、spread、動的 class、親から渡る class などの扱いが未定義です。「解析できなかった経路を件数台帳へ載せる」だけでは、将来の未知の記法を見逃す fail-open になり得ます。  
  修正提案: 走査対象構文を明示し、対象内で解決不能な class は必ず失敗させてください。保証対象外にする構文が必要なら、実行時に配色へ影響しないことを別の不変条件で示すか、理由・対象・失効条件を持つ例外として個別登録してください。抽出 0 件遮断だけでは不十分です。

- [Critical] i16 の下地を `neutral` と `surface` の二つに固定する根拠が、提示された実測表自身と矛盾しています。不透明な背景には `danger`、`primary`、`success`、`tertiary`、`border` も実在します。二つだけを「実在する不透明な下地すべて」と呼ぶと、実装上の背景経路を取りこぼします。  
  修正提案: class 走査で導出した各状態について、当該状態の不透明背景を下地として追跡してください。背景が親要素にあるため静的に決められない場合は、固定二下地での検査を「最低保証」と明記し、親背景を特定できない使用箇所を不合格または個別例外にしてください。

- [Warning] `bg-<token>/<N>` の扱いは、Tailwind の生成 CSS とブラウザ実装が前提です。`color-mix(in oklab, … transparent)` を alpha 合成へ還元する仮定はテスト環境の実装と一致させる必要があります。  
  修正提案: gate の負例だけでなく、代表的な `/10`、`/12`、派生 `rgba()` token について、生成 CSS と計算モデルが一致する契約テストを置いてください。

4. 期待効果の妥当性

- [Warning] i9 は `text-white` の三箇所を直しても、将来の Tailwind 既定 token・任意値・CSS `var()` 参照による写像外参照を防げなければ、閉包を保証できません。  
  修正提案: 「class suffix の token」だけでなく、`resources/css` の `var(--color-...)`、任意値クラス、Tailwind 既定色の利用をどう分類するかを契約表に定義してください。未登録の `text-*` / `bg-*` を token と誤認することも防ぐ必要があります。

- [Suggestion] `border` を塗り面の役割として分類し直し、`surface` を fill label に登録する判断は、実装上の使用実態に基づいており妥当です。

5. リスク

- [Warning] primary / success / warning 等の一段暗色化は、コントラストを改善する一方、既存のブランド印象、hover の視認性、非テキスト UI の意味的な区別を変えます。本文コントラストだけの測定では後退を検知できません。  
  修正提案: 変更対象 token の全利用箇所を逆引きし、少なくとも通常・hover・disabled・選択状態について、前景/背景の組と意味的役割をレビュー可能な表として残してください。

- [Warning] `PENDING_CONTRAST_PAIRS` を残す方針は妥当ですが、判定不能分類の件数だけを固定すると、新しい未解析使用を「件数更新」で通す誘惑が残ります。  
  修正提案: 各 pending 項目に、発生箇所・分類・解消条件・担当不変条件を持たせ、件数ではなく実体集合の一致を主判定にしてください。

6. スコープの適切さ

- [Suggestion] 正典 v1 の欠落条件、既存実害、関連文書、採用時債務を一つの PR で同期する範囲は適切です。
- [Suggestion] q1〜q3、広色域、非テキスト 3:1、テンプレート逆同期を切り出した判断も適切です。

7. 型安全性

- [Warning] TypeScript の共有パーサ・契約表・台帳は文字列配列や `Record<string, string>` に寄せると、token 種別、前景/背景役割、alpha 判定、例外理由の取り違えをコンパイル時に防げません。  
  修正提案: token 名、用途、解決結果、判定不能理由を discriminated union と `as const satisfies` で表現し、未知 token・未分類 token が `never` に収束する設計にしてください。台帳と parser の境界値も `unknown` から検証して narrow してください。

- [Suggestion] PHP を変更しないため PHPStan level 10 の直接的なリスクは低いです。ただし TS 側は `pnpm typecheck` を通すだけでなく、共有 parser の入出力を型で閉じることが i9/i15/i16 の信頼性に直結します。
