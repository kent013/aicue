# 対応マトリクス: conceptual-review Round 2

## [Critical] 「未対応構文なら落ちる」の検出方法が設計されていない (規則 1〜5 から導けない)

- 判断: **対応する**。指摘のとおり規則 1〜5 からは導けないので、**主張を削り、
  Codex が提示した代替案 (保証する構文集合を限定 + 既知の入口の deny 検査) をそのまま採る**。
- 根拠: 「未知の構文をすべて認識する」ことは静的走査では成立しない
  (規約 (b) の「保証範囲の外にする構文は docblock へ明記し、明記したなら検出力を主張しない」に従う)。
  一方、Codex が名指しした入口はいずれも**現状 0 件**で、語彙の deny として機械化できる。
  実測 (`resources/js` 全数):
  - Svelte の `class:` ディレクティブ (コロン直後が識別子の形): **0 件**
  - `clsx` / `twMerge` / `tailwind-merge` / `classnames` / `cva` の出現 (import・呼び出しとも): **0 件**
  - テーマ名前空間の接頭辞の**内側**に補間が入る形
    (`bg-${…}` / `text-${…}` / `rounded-${…}` 等): **0 件**
- 対応内容: 概念設計の「走査対象構文の全数分類」を次のように書き換えた。
  1. **走査器が保証する構文集合を 1 つに限定して宣言する** — 文字列リテラルの中の class トークン。
     それ以外の形については**検出力を主張しない** (docblock に明記)。
  2. **未対応の入口を語彙の deny で塞ぐ**。上の 3 語彙群を走査して **0 件であることを固定**する。
     0 件が壊れたら「走査器が対応していない入口が現れた」として赤くなる。
     これは「未知の構文をすべて認識する」主張ではなく、**既知の入口の deny** である。
  3. 各 deny 語彙に**負例**を置く (合成入力で「導入したら赤くなる」ことを固定する)。
     語彙一致は区切り文字で分割したトークンの完全一致で判定し、負例には接頭辞つき・
     打ち消しつき・接尾辞つきの 3 形を置く (共通規約 (e))。
  4. **母集団の非空**を別に固定する (deny が 0 件なのは「語彙が無い」からであって
     「走査が壊れて 1 ファイルも読めていない」からではないことを分ける)。
  5. `class={identifier}` / 配列 + `.join(" ")` / 三項は**対応済みの形**である
     (中の文字列リテラルが走査単位に入る)。残る穴は「1 つの組が複数のリテラルへ割れる」ことだけで、
     これは i14 の役割直積が大部分を覆っており、限定を docblock に明記する
     (Round 1 の対応と同じ)。
