## S1

### [Critical] CSS 字句走査の前提が現行 `tokens.css` と矛盾する (文字列リテラルが実在する)

- 判断: **対応する** (事実誤認をそのまま設計に書いていた)
- 根拠: 実測すると `--font-sans` は `'Noto Sans JP'` / `'Hiragino Sans'` / `'Yu Gothic UI'` /
  `'Segoe UI'` / `'Apple Color Emoji'` … と**引用符つきの値を 8 個**持つ。
  「文字列リテラルは 1 件も無い」は明確な誤りで、
  「集合一致が赤くなるので無言では通らない」という保証も一般には成立しない。
- 対応内容: 走査を**5 状態の字句走査**にした —
  通常 / コメント / 単引用文字列 / 二重引用文字列 / エスケープ。
  `@theme`・コメント開始・波括弧は**通常状態でだけ**解釈する。
  固定検体に (a) 文字列の中の `/* … */`、(b) 文字列の中の `{` `}`、
  (c) エスケープした引用符、(d) 現行 `--font-sans` と同形の宣言 の 4 形を足した。

### [Warning] `parseCssColor()` の契約が rgba/rgb のみで、S10 が hex を渡している

- 判断: **対応する** (S10 の Critical と同じ原因)
- 対応内容: `#rrggbb` を**正式な入力形式**に加え、
  RGB 各値の範囲 (0..255) / alpha の範囲 (0..1) / 余分な末尾文字 / 数値にならない値を
  **厳密に拒否**する契約にした。正例・負例を固定検体に置く。

## S2

### [Critical] 固定検体から唯一の解析実装を呼べない (Round 1 の S1 指摘が S2 で再発)

- 判断: **対応する** (同じ穴を別の場所で作っていた)
- 対応内容: 純粋入口を**唯一の実装**にした —
  `scanClassUsageSource(source, file)` / `scanCssVarReferencesSource(source, file)` /
  `unsupportedEntryPointsSource(source, file)`。
  実リポジトリ用の `scanClassUsage()` 等は**ファイルを読んで集約するだけ**の薄いラッパーにする。

### [Warning] 文字列抽出の字句仕様が不足 (コメント / エスケープ / 複数行 template / `${…}`)

- 判断: **対応する**
- 対応内容: 保証する字句構文を明記し、4 形の正例・負例を固定する。
  **解析不能な template 構文は `interpolated` として残す** (無言で通常リテラルにしない)。

### [Warning] 不透明度修飾の値域と端点が未定義 (`/0` `/100` `/101` 負数 任意値)

- 判断: **対応する**
- 対応内容: 受理するのは `/` + 半角数字 1〜3 桁で値が **0..100** の形だけにした。
  `/100` は**修飾なし (不透明)** と同じ扱い。`/0` は**透明**なので背景が親から来る =
  `keyword-color` と同じ判定不能。範囲外・任意値・小数は
  `unresolved: "unsupported-alpha-syntax"` (値域へ追加) にして**素通りさせない**。

## S5

### [Critical] `ParsedColor.alpha` と台帳の「実効 alpha」を合成関数が二重適用しうる

- 判断: **対応する** (関数シグネチャが曖昧で、実装者が二通りに読める)
- 対応内容: 合成の直前に**完全正規化**する型を入れた。

  ```ts
  interface ResolvedAlphaBackground {
      readonly rgb: Rgb;
      readonly effectiveAlpha: number;
  }
  ```

  合成関数は `rgb` + `effectiveAlpha` + `base` **だけ**を受け、`ParsedColor` を直接受けない。
  3 形 (不透明 token の `/10` = 0.10 / 値に alpha を持つ token = 0.12 /
  値に alpha を持つ token の `/40` = 0.048) を固定検体で固定する。

### [Warning] ファイルパスの契約が一致していない (型はリポジトリ相対、台帳例は走査根相対)

- 判断: **対応する**
- 対応内容: **すべて `resources/js/...` のリポジトリ相対に統一**した (型 / 診断 / 台帳)。
  正規化を固定検体で確認する。

### [Warning] 「キーの取り違えが型で落ちる」を成立させる型定義が無い

- 判断: **対応する** (主張だけあって根拠が無かった)
- 対応内容: CSS suffix の literal union を `COLOR_TOKEN_MAP` と `DERIVED_COLOR_TOKENS` から
  **直接導出**し、`AlphaPair.fg` / `bg` の型に使う。

## S9

### [Critical] 「直前が空行または文書先頭」では CommonMark の字下げコードを十分に検出できない

- 判断: **対応する**。**Codex が提示した案 2 (fail-closed) を採る**
- 根拠: 指摘のとおり、字下げコードが中断できないのは**段落**であって、
  見出しや区切り線の直後の 4 空白行は字下げコードになりうる。
  提案していた状態機械はこれを本文として残すので、
  **規範の最小断片を見出し直後の字下げコードへ退避させると緑になる**穴が残っていた。
- 対応内容: 状態機械で近似するのをやめ、
  **囲みコードの外に 4 空白以上で始まる行が現れたら gate 自体を失敗させる**形にする。
  - i12 の目的 (契約の本文を読者に見えない場所へ退避させられないこと) は、
    **そもそも書かせない**ことで**より強く**満たす。見逃しは 0 になる。
  - 実測: `docs/design-system.md` に 4 空白以上の行は **0 行**、1〜3 空白の行も **0 行**である。
    したがって現時点で偽陽性は起きない。
  - 失敗時のメッセージに「囲みコード (```) を使うこと」を書く (直し方が分かる形にする)。
  - **CommonMark パーサは導入しない** (依存が無く、この 1 検査のために増やすのは
    「今必要なものだけ作る」に反する)。必要になった時点で導入する契機も docblock へ書く。
  - S11 で足す運用契約の 1 行は、**4 空白以上の継続行を作らない書き方**にする
    (1 行に収めるか、2 空白の継続にする)。
