## S1

### [Warning] 「通常状態かつ文の位置」の判定規則が実装可能な粒度まで定義されていない

- 判断: **対応する**。ただし**手書き字句走査そのものをやめる**
- 根拠: `postcss` は**既に devDependency で、`tokens.test.ts` が生成 CSS の解析に使っている**。
  写像 (tokens.css) の解析にも同じ解析器を使えば、
  - 文字列リテラルの中の `/*` `{` `}` の誤認 (Round 2 の Critical)
  - at-keyword の境界 (`@theme-extra`。Round 3 の Warning)
  - 宣言値の中の `@theme` / 「文の位置」の定義 (Round 4 の Warning)
  - 未終端コメント・未終端文字列・閉じないブロック
  が**すべて解析器の側で解決する** (postcss は `CssSyntaxError` を投げるので fail-closed)。
  自前の 5 状態走査を書く理由が無い。
- 対応内容: `parseThemeMap(source, file)` を **`postcss.parse()` の上に実装**する。
  - `@theme` は `AtRule` かつ `name === "theme"` の**完全一致**で数える
    (コメントは `Comment` ノードなので数えない / `@theme-extra` は別の `name`)
  - `topLevel` は `parent` が `Root` であること
  - 宣言は**トップレベル `@theme` の直接の子 `Decl`** だけを採る
  - `@theme` の中に `Rule` / `AtRule` が現れたら**例外** (深さ 1 段の前提を破る形 = i20)
  - 同名の再宣言は**例外**
  - 構文エラー (未終端コメント・未終端文字列・閉じないブロック) は
    postcss の例外がそのまま伝播する
  - `@utility text-<name>` も同じ AST から採る
  固定検体は変わらず `parseThemeMap()` へ直接渡す (実ファイルを読む経路は薄いラッパー)。
  負例に `@utility-extra` / 宣言値の中の `@theme` / コメントを挟んだ at-keyword を足した。

## S2

### [Critical] 未終端の字句と `${…}` 内部の解析失敗を fail-closed にする契約が無い

- 判断: **対応する**。ここも**手書き字句走査をやめる**
- 根拠: このリポジトリには**同じ問題を既に解いた準拠実装がある** —
  `tests/js/support/file-input-scan.ts` は `svelte/compiler` の `parse()` で
  `.svelte` を AST にし、解析できない形を診断へ落とす (`parse-failed` /
  `unresolved-*`)。`typescript` も既に devDependency で、
  `tests/js/support/enum-ts-sync/*` が `ts` の API を使っている。
- 対応内容: 走査の入力を**トークン列 / AST**にする。
  - `.svelte`: `parse(source, { modern: true })` の AST を歩く。
    `class` 属性の `Text` チャンクと、式の中の**文字列リテラルのノード**を単位にする。
    parse が失敗したら `parse-failed` の診断にして**gate を落とす**
  - `.ts`: `ts.createScanner()` でトークン列にし、
    `StringLiteral` / `NoSubstitutionTemplateLiteral` を単位にする。
    `TemplateHead` が現れた template literal は**置換を含む**ので `interpolated` にする
  - **未終端**のコメント・文字列・template・補間は、いずれも解析器が
    エラートークン / 例外として返すので**例外**にする (`"}` / object literal /
    入れ子 template / 未終端補間 の固定検体を置く)
  - **解析不能後に残りのファイルを無言で捨てない** — 診断は必ず結果に残り、
    gate は診断が 1 件でもあれば落ちる (共通規約 (b))
  これで「単純な brace count が補間の終端を誤認して以降を読み落とす」経路は消える。

## S3

### [Warning] 「走査根が生きている」と「各根に現在参照が存在する」を混同している

- 判断: **対応する** (正当に参照を消しただけで赤くなる形だった)
- 対応内容:
  - **各根の存在**と**列挙したファイル数が 0 でないこと**を検査する (走査の生存)
  - **参照の総数**が 0 でないことは**全体にだけ**課す (これはドメインの不変条件である —
    アプリのスタイルが token を 1 つも参照しないことは無い)
  - **根ごとの参照件数の非空は要求しない**
  - **契約表の各チャネルの非空も要求しない** (最後の局所変数の例外を解消した
    正常な状態を赤にしないため)。チャネルごとの判定分岐は**固定検体で点灯**させる

## S5

### [Warning] 台帳行の一意性と値域が明示的な不変条件になっていない

- 判断: **対応する**
- 対応内容: 次を it として足す。

- 判断: **対応する**
- 対応内容: 「射影が一致する」の it は**削り**、代わりに
  **導出関数 `distinctPairs()` の仕様を固定検体で固定する** (重複除去 / 並び順 / キー生成)。
  恒真に近い検査を残すのは共通規約 (d)「集めた走査結果を判定に使わない形を作らない」に近い形骸化である。

## S9

### [Critical] container marker の除去規則が未定義なので「見逃し 0」が成立しない

- 判断: **対応する**。**container 文法を扱うのをやめ、判定を書き換える**
- 根拠: `>` と list marker の除去を手書きで完全に定義するのは
  (ordered marker の桁数・`1)` 形式・marker 前の 0〜3 空白・異種 container の入れ子・
  marker 後の空白数による content indent の違い…) 明らかに割に合わない。
  **判定を「有効字下げ列」ではなく「4 個以上連続した半角空白」に変えると、
  container 文法が 1 つも要らなくなる。**
- 証明 (docblock に書く): タブを禁じた前提で、字下げコードブロックが成立するには
  container の内容開始列から**4 列以上**の字下げが要る。列を作れるのは半角空白だけであり、
  container marker が消費する空白は marker ごとに高々 1 個なので、
  **4 個以上の空白は必ず連続して現れる**。よって
  「4 個以上連続した空白」を拒否すれば**字下げコードは 1 つも書けない**。
- 対応内容: 判定を次の 2 条にする (囲みコードの外に限る)。
  1. **タブを含む行**を拒否する (列の解釈が環境依存になるため)
  2. **4 個以上連続した半角空白を含む行**を拒否する (行頭に限らない)
  - 実測: `docs/design-system.md` は**両方とも 0 件**である (囲みコードの外で確認済み)。
  - 偽陽性の class は「本文の中で意図的に 4 空白以上を並べる書き方」(表の桁揃え等) だけで、
    これは**書き方を直す**のが正しい対応である。docblock に明記する。
  - 固定検体: 行頭 4 空白 / 見出し直後 / 段落継続行 / 行頭タブ / 1〜3 空白 + タブ /
    `>␣␣␣␣text` / `> >␣␣␣␣text` / `-␣␣␣␣␣␣text` / `1)␣␣␣␣␣text` /
    囲みコードの中の 4 空白とタブ (**検出しない**) /
    通常の blockquote・list 本文と 2 空白の継続行 (**検出しない**)
  - container 文法の列挙・再帰除去は**要らなくなった**ので設計から削る。
