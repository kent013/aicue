## 施策別判定

### S1 — REQUEST_CHANGES

[Warning] 「通常状態かつ文の位置」の判定規則が実装可能な粒度まで定義されていません。

CSS宣言値中の `@theme`、ルールブロック内のat-rule、コメントを挟んだ位置などをどう区別するかが実装者依存です。また完全一致の固定検体は `@theme-extra` だけで、同じ解析対象である `@utility-extra` がありません。

修正案:

- 「文の位置」を、ブロック文脈と直前の有意tokenを用いて具体的に定義する
- 宣言値中の `@theme` を数えない固定検体を追加する
- `@utility-extra`、コメントを挟んだat-keywordも固定する
- 対応可能なら既存のCSSパーサ利用も再評価する

旧正規表現を5状態走査へ置き換える矛盾は解消されています。

### S2 — REQUEST_CHANGES

[Critical] 未終端の字句と `${…}` 内部の解析失敗をfail-closedにする契約がありません。

S1では未終端コメント・文字列を例外にしていますが、より複雑なS2では次が未定義です。

- 未終端のブロックコメント・文字列・template literal
- `${…}` の未終端
- `${ condition ? "}" : value }` のような文字列中の波括弧
- object literalや入れ子templateを含む補間
- コメント中の波括弧

単純なbrace countでは補間の終端を誤認し、その後のソースを読み落としても、リポジトリ全体の母集団が非空ならgateが緑になり得ます。

修正案:

- template式の中も、文字列・コメント・入れ子templateを持つ状態スタックで解析する
- 未終端のコメント、3種の文字列、template、補間はすべて例外にする
- `"}`、object literal、入れ子template、未終端補間の固定検体を追加する
- 解析不能後に残りのファイルを無言で捨てないことを固定する

Round 3のalpha単位、最長接尾辞、結果型分離は解消されています。

### S3 — REQUEST_CHANGES

[Warning] 「走査根が生きていること」と「各根に現在参照が存在すること」を混同しています。

`resources/js` と `resources/css` からそれぞれ1件以上の `var()` 参照を要求すると、参照を正当に削除しただけでも失敗します。同様に、契約表の2チャネルをともに非空とする条件は、最後の局所変数例外を解消した正常な状態を赤にします。

修正案:

- 各根の存在と列挙ファイル数の非空を検査する
- 参照総数の非空が本当にドメイン不変条件なら、全体にだけ課す
- 例外契約表には非空を要求しない
- 各チャネルの判定分岐は固定検体で点灯させる

走査根の食い違い自体は解消されています。

### S4 — APPROVE

実装本体の `linearizeChannel(0.04)` を呼ぶため、旧しきい値のままでは確実に赤になります。テストファーストの順序も具体的です。

### S5 — REQUEST_CHANGES

alphaの二重適用と全数台帳の問題は解消されています。

[Warning] 台帳行の一意性と値域が明示的な不変条件になっていません。

集合＋件数の比較実装によっては、同じキーを複数行へ分割したり、`count: 0`、非整数、範囲外modifierを登録したりしても、正規化方法次第で意図しない一致が起こります。

修正案:

- `(file, fg, bg, modifierPercent)` の一意性を検査する
- `count` は正の整数に限定する
- `modifierPercent` は `null` または0〜100の整数に限定する
- `UNDECIDABLE_PAIR_LEDGER` も `(file, reason)` の一意性と正の整数件数を固定する

[Suggestion] `ALPHA_CONTRAST_PAIRS` が台帳から直接導出されるなら、「台帳の射影と集合一致する」テストは恒真に近いものです。導出関数の重複除去・順序・キー生成を固定検体で検査する方が実益があります。

### S6 — APPROVE

値変更の前にS5の赤を確認する順序、派生tokenの追随検査、disabled状態を含む目視対象は妥当です。

DTO、JsonResource、Inertia Props、サーバー側認可への波及はありません。

### S7 — REQUEST_CHANGES

[Warning] `DECLARED_CONTRAST_PAIRS` の各ペアが実装に実在することを検査していません。

現在の3条件が保証するのは、背景roleが少なくとも1件の宣言を持つことまでです。同じ背景へ、実装に存在しない前景ペアを追加して母集団を広げることは可能です。

修正案:

- 各個別宣言ペアが、走査された不透明ペアに少なくとも1回現れることを要求する
- 同一 `(fg, bg)` の重複宣言を拒否する
- 実装に存在しない個別宣言ペアを固定検体で赤にする

役割分類の全数性を個別宣言ペアから分離した点は適切です。

### S8 — REQUEST_CHANGES

[Warning] basename重複の扱いが二通りに読めます。

探索規則では「basenameの重複を拒否する」としつつ、「重複させたい場合は申告表で明示する」としています。しかし `classifyComponentTree()` は申告表を受け取らないため、そこで拒否すれば後段の申告表では救えません。固定検体も無条件の不合格だけです。

修正案はどちらかに統一してください。

- 無条件に禁止するなら「申告表で許可」を削除する
- 申告表で許可するなら、重複判定を `compareComponentDocumentation()` 側へ移し、明示申告された重複が通る正例を追加する

構造型、二段階ディレクトリ一致、Markdown非描画領域の除外契約は解消されています。

### S9 — REQUEST_CHANGES

[Critical] CommonMark container markerの除去規則が未定義なため、「見逃し0」はまだ成立しません。

現在は「`>` とlist markerを取り除く」「`1.` 等」としか定義されていません。少なくとも次が未確定です。

- ordered listの `1)` 形式
- ordered markerの1〜9桁規則
- marker前の0〜3空白
- `> -     text` のような異種containerの入れ子
- list marker後の空白数によるcontent indentの違い
- container内のfenced code
- thematic breakとlist markerの区別
- containerを再帰的に何段まで除去するか

このままでは実装者ごとに判定が変わり、見逃しまたは正当な囲みコードへの偽陽性が起こります。

修正案:

1. CommonMarkパーサでblock種別を判定する、または
2. 手書きを維持するなら、対応するcontainer文法を完全に列挙し、再帰除去のアルゴリズムを定義する

後者では最低でも以下を追加してください。

- `1)     text`
- 複数桁ordered marker
- `> -     text`
- `- >     text`
- container内のfenced codeにあるタブ・4空白
- thematic breakをlistとして誤認しない正例
- 未対応containerを解析成功扱いしない分岐

`scanMarkdownLines()` への一本化は解消されています。

### S10 — APPROVE

hex対応、派生tokenのRGB・alpha関係、生成CSSの前提固定は整合しています。S5の単位契約とも接続できています。

### S11 — APPROVE

責務境界表との双方向一致、本数の散文廃止、新規4本の登録は妥当です。新設gate数と追加行数も一致しています。

### S12 — REQUEST_CHANGES

[Warning] D51がS9の未確定保証を確定事項として記述しています。

「引用やリストの記号を除いた有効字下げ」「見逃し0」は、現在のcontainer文法ではまだ保証できません。

修正案:

- S9の解析契約と固定検体を確定してから、その実装が保証する範囲だけをD51へ記載する
- 手書き解析のままなら、保証対象のcontainer構文と保証外をD51にも正確に反映する
- 「完全なCommonMark解析ではない」と「見逃し0」が両立する範囲を明示する

D50のalpha正規化・全数台帳の説明は今回の改訂で整合しました。
