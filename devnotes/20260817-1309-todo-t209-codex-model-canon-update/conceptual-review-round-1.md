## 全体判定: CHANGES_REQUESTED

### 1. 使命との整合性

[Suggestion] アプリ機能への直接変更ではないものの、設計・実装レビュー工程を継続可能にする保守として使命への間接的な貢献は合理的です。効果の主張も「動画生成機能が直接改善する」とはしておらず、適切です。

### 2. 禁止事項違反

[Suggestion] 提案範囲には禁止事項への抵触は見当たりません。アプリ側の Prism 呼び出しや実行時コードを対象外に分離している点も妥当です。

### 3. 実現可能性

[Warning] `.claude/` と `scripts/` の「git 追跡下全ファイル」を走査するなら、対象ファイル列挙と読み込みの仕様を明確にしてください。特に `git ls-files -z` による安全なパス処理、読めないファイルを黙って除外しないこと、リポジトリルート基準で走査することが必要です。

修正提案: テスト設計に「追跡下ファイル一覧は NUL 区切りで取得し、各対象を必ず検査する。読込失敗はテスト失敗」と明記してください。

### 4. 期待効果の妥当性

[Critical] 「ファイル → 許可モデル集合」の期待表では、用途ごとの割当を固定できません。`app-design/SKILL.md` には `gpt-5.6-terra` と `gpt-5.6-sol` の両方が現れるため、概念設計と詳細設計の指定を入れ替えても、ファイル単位の集合比較は通ります。これは「割当の取り違えも検出できる」「静かな後退を赤にする」という期待効果と一致しません。

修正提案: 期待値を少なくとも「ファイル・意味上の配置・モデル名」の組にしてください。例えば、該当見出しまたは安定した指示文ごとにモデル指定を抽出し、`概念設計 → terra`、`詳細設計 → sol`、`実装レビュー → sol` を完全一致で検証します。単純な出現回数も併せて固定すると、重複追記も検出できます。

[Suggestion] 提供元での利用可否は文字列検査では保証できない、と明示している点は適切です。

### 5. リスク

[Warning] 正本のスキル文書と検査の期待表に同じ割当が二重に存在します。将来のモデル更新時に片方だけ更新されるリスクがあります。今回の同時変更で解消しても、次回更新で再発し得ます。

修正提案: 今回は過剰な自動抽出を避けつつ、期待表が「正本から独立した意図的な検証」であることをテスト内コメントで明記してください。また、正本表の用途行と期待表の対応をレビュー項目として残してください。

### 6. スコープの適切さ

[Suggestion] モデル名、呼び出しスキル、既存の検査に限定し、reasoning effort やアプリ側 LLM を対象外にする判断は適切です。`gpt-5.6-luna` の新規利用を作らない点も YAGNI に沿っています。

[Suggestion] AG-193 は「現状確認のみ」としており、本件へ記録機構を持ち込まない判断は妥当です。実装時には、確認結果をコード変更に混ぜずレビュー記録として扱うべきです。

### 7. 型安全性

[Suggestion] Vitest の既存アーキテクチャテストを更新する方式は TypeScript strict と両立可能です。期待表は `as const` とモデル名のユニオン型を用い、任意文字列を許さない形にすると、許可集合と期待値の齟齬をコンパイル時にも抑止できます。

主要な修正点は、ファイル単位のモデル集合比較を、用途・配置まで識別する期待値へ強化することです。これを満たせば、提案の方向性とスコープは承認可能です。
