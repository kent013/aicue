# 概念設計: Codex 正典モデルの現行世代への追従 (aicue:T209)

> ステータス: **APPROVED** (Codex `gpt-5.6-terra` / medium、Round 2)。履歴は `codex-history/`

## 背景・課題

### 台帳の根拠

家系の機能台帳 lctl の機能 `skill-codex-integration` に対して、
オーナー裁定 **AG-186 (2026-08-15)** が入っている。内容は次のとおり。

- Codex に指定するモデルの正典を**現行世代の 3 本**へ上げる。
  - `gpt-5.6-sol` — コードの分析・レビュー・技術設計 (**既定**)
  - `gpt-5.6-terra` — 議論・概念設計
  - `gpt-5.6-luna` — 軽い判定
- 「指定してはいけない名前」と「期限つきで使えるが新たに指定しない名前」
  (`gpt-5.4` / `gpt-5.4-mini` は 2026-08-31 提供終了、`gpt-5.5` も選ばない) の区分は
  spirux 側の呼び出し規約スキルの表を正とする。
- **名前は接尾辞まで含めて 1 つ**であり、接尾辞を落とした名前を書かない。
- 本裁定が動かすのは**モデルの軸だけ**で、正典のもう 1 つの中身
  (使命・禁止事項を規約文書から導いて差し込む 3 小節の構造) は従来のまま。
- 追従は 5 リポジトリへ配布され、aicue のセルは `update_pending` になっている。
  aicue 宛ての申し送りには「機械検査
  `tests/js/architecture/codex-model-consistency.test.ts` の正典モデル名一覧の更新も必須
  (更新しないと新モデル名を既定拒否で赤にする)」と明記されている。

関連する裁定がもう 1 つある。**AG-193 (2026-08-16)** は、Codex の会話の握り
(継続用の一時状態) を記録・成果物として扱わないと定めた。aicue の
`app-codex-review` スキルは既にセッション JSONL をリポジトリ外へ置く運用なので、
本件で変更は要らない (裁定と現状が一致していることの確認だけ行う)。

他リポジトリの到達状況 (台帳の実読):

| リポジトリ | 状態 |
|---|---|
| spirux | 到達済み。正典の表の実体を持つ (作業項目 spirux:T1181 / spirux:T1188) |
| laravel-claude-template | 到達済み (作業項目 laravel-claude-template:T115)。正本を `app-codex-vscode/SKILL.md` に置き、`.claude/` と `scripts/` の追跡下全件を走査する検査を併設した |
| aicue (本リポジトリ) | 追従待ち。現状は `gpt-5.5` 一本化版 |
| aigenba / motivation / metamovics | 追従待ち |

### 実害

- spirux の実測 (2026-08-15) では、旧世代の既定モデルは**すでに提供元から外れており**、
  指定すると HTTP 400 で即座に落ちた。つまり「古いまま動く」のではなく
  **設計レビューも実装レビューも実行できなくなる**。
- aicue の全設計フロー (`app-design`) と実装フロー (`app-implement`) は
  Codex 合議を前提にしているため、モデル名が使えなくなった時点で
  規約どおりの工程が回らなくなる。

### aicue 固有の事情 (ここが他リポジトリと違う)

`tests/js/architecture/codex-model-consistency.test.ts` が
**許可する綴りを `gpt-5.5` の 1 つに固定**して既定拒否で走査している。
そのため:

- スキルだけを先に直すと、**検査が新しい名前を違反として赤にする**。
- 検査だけを先に直すと、**呼び出し側の古い名前が違反として赤になる**。

どちらの順でも赤が出るのは検査が正しく働いている証拠であり、
**同じ変更で両方を動かす**必要がある (テストファーストの赤はこれを利用して取る)。

## 改善アイデア

1. **正本を 1 つ決める**。`.claude/skills/app-codex-vscode/SKILL.md` を
   モデル指定の正本とし、「使う 3 綴りと用途の割当」を表で持つ。
   呼び出し側のスキルは正本の割当に従って綴りを書く。
2. **呼び出し側を割当どおりに差し替える**。aicue の呼び出しは 4 ファイル 7 箇所ある。
3. **検査を正典 3 本へ更新し、同時に取りこぼしを塞ぐ**。検査は 3 層で構成する。
   - **層 1 (綴りの既定拒否)**: 走査根の全ファイルで、
     許可 3 綴り以外のモデル名の出現を 0 件で固定する。
     走査根は「`app-*/SKILL.md` の 9 ファイル」から
     **`.claude/` と `scripts/` の git 追跡下の全ファイル**へ広げる
     (現状これで増える赤は 0 件であることを実測済み。下の「調査結果」参照)。
     併せてファイルごとの**出現回数**も期待値で固定する (重複追記の検出)。
   - **層 2 (用途割当の固定)**: モデルの宣言 (`**model**: ...`) を全数え上げし、
     同じ節のラベル宣言 (`**label**: ...`) と対にして
     (用途ラベル → 綴り) の写像を作り、期待写像と**完全一致**で突き合わせる。
     対にできない書き方は**読めない書き方として赤にする**
     (読めなかったから緑、を構造的に無くす)。
     層 1 だけではファイル内の取り違え (概念設計と詳細設計の入れ替え) を
     検出できないため、この層が要る。
   - **層 3 (正本の表の固定)**: 正本の「利用可能モデル」表の行から綴りを取り、
     **3 綴りちょうど**であることを完全一致で確認する
     (正本の表が痩せる / 増えることの検出)。
4. **旧綴りの全数を洗い出し、各箇所の扱いを決める** (更新する / 履歴として残す)。

### 判断 1: 旧綴りの「禁止表」を本文に持たない

正典は 3 区分 (使う / 指定してはいけない / 期限つきで使えるが選ばない) を持つが、
**区分の正本は spirux 側の表**であると裁定が定めている。
aicue の正本には**「使う」区分だけ**を綴りで書き、他の 2 区分は
**綴りを書かずに文で述べる** (「前の世代の名前・末尾に codex が付く名前・
接尾辞を落とした名前は指定しない」)。

理由:

- aicue の検査は**許可集合の外を既定拒否**する。禁止表を書くと、
  禁止表そのものが違反として赤になる。避けるには
  「正本の中の特定区間だけ走査から外す」機構が要るが、
  それは検査の形の話であり、**どの形を正典とするかは台帳上まだ未決**である
  (家系に 3 実装があり比較中)。未決の形を先取りして機構を増やさない (思考原則 2)。
- 禁止表が無くても目的は達せられる。**許可集合の外は 1 綴りも書けない**ので、
  禁止表より広く効く。禁止表は「書いてよい違反例の一覧」でもあるため、
  持たないほうが機械検査は素直になる。

### 判断 2: 検査ファイルの名前と置き場所は変えない

台帳の gates 欄が `aicue:tests/js/architecture/codex-model-consistency.test.ts` を
名指しで参照している。改名すると台帳の参照が切れるため、
**中身だけを差し替える**。

### 判断 3: 推論の深さ (reasoning effort) の表は触らない

裁定は「動かすのはモデルの軸だけ」と明記している。
テンプレート側は実測を反映して深さの表を直したが、**aicue はその実測を持たない**。
実測なしで表だけ写すのは「データに真摯に向き合え」に反する。
本件では**現在の割当 (概念設計 = medium / 詳細設計・実装 = high) をそのまま使い**、
新しいモデルでその深さが実際に通ることを本設計自身の Codex レビューで確かめる
(通らなければ設計に反映する)。

## 期待効果

- **使命への貢献 (間接)**: 本件はアプリの機能ではなく開発の進め方に効く。
  設計レビュー・実装レビューが止まると、標準作業から動画マニュアルを作る機能の
  改善そのものが止まる。提供終了で全リポジトリ一斉に壊れる前に手当てする。
- 旧世代の提供終了 (`gpt-5.4` 系は 2026-08-31) に対して、
  aicue の Codex 工程が **400 で止まらない**状態を先に作る。
- 検査の守備範囲が「9 ファイル」から「`.claude/` と `scripts/` の追跡下全件」へ広がり、
  スキルの追加・分割・別ファイルへの切り出しで綴りが逃げる経路が閉じる。
- 用途と綴りの対応が**期待表**として機械で固定され、
  「全部いちばん安いモデルに寄せる」ような静かな後退が赤になる。

## 制約・前提

- 変更するのは開発ツール (スキル文書と 1 本の検査) だけで、
  `app/` `resources/` `routes/` `database/` には一切触れない。
  アプリの実行時挙動は変わらない。
- `gpt-5.6-luna` (軽い判定) を使う呼び出しは aicue に**現在 1 つも無い**。
  正本の表には割当の規則として載せるが、呼び出しは作らない (思考原則 2)。
- 検査は `pnpm test` (vitest root project) のレーンで走る。
  `git ls-files` を使う検査は既に前例がある
  (`tests/js/architecture/pages-path-case-invariant.test.ts`)。
- テンプレートとの差 (検査の走査の起点・主張の広さ) は、
  台帳が「どの形を正典とするかは未決」と記録している段階なので、
  `docs/template-divergence.md` への登録は行わない
  (登録すべき「正典からの逸脱」がまだ定義されていない)。

## スコープ外 / やらないと決めたこと

| やらないこと | 理由 |
|---|---|
| 推論の深さ (reasoning effort) の表の書き換え | 裁定が動かすのはモデルの軸だけ。aicue に実測が無い |
| 使命・禁止事項の 3 小節構造の見直し | 正典のもう 1 つの中身だが、本裁定の範囲外。spirux も未着手 |
| 「指定してはいけない名前」の一覧を綴りで持つこと | 既定拒否の検査と両立させるには走査から外す区間の機構が要る。その形は台帳上まだ未決 (判断 1) |
| `devnotes/` と `docs/TODO-closed.md` の旧綴りの書き換え | 過去の事実の記録であり、書き換えは記録の改竄になる |
| アプリ側の LLM 呼び出し (Prism 経由) のモデル名の統制 | 呼び出し口が違えば使える名前の体系も違う。本件の正本の管轄外 |
| 台帳への書き込み (実装完了の報告) | 設計フェーズの責務ではない。実装完了時に別途行う |

## 保証しないもの (誇張しない)

- 検査が見るのは **`.claude/` と `scripts/` の git 追跡下のファイルだけ**である。
  `docs/` `app/` `resources/` `tests/` に綴りが現れても**沈黙する**。
  `devnotes/` は履歴として意図的に走査の外にある。
- 検査は**リポジトリ内の文字だけ**を見る。提供元へ疎通しないので、
  「その名前が今も使える」ことは保証しない。
  提供終了の告知を追うのは人の仕事である。
- 検査は**綴りが期待表どおりに現れること**しか見ない。
  スキル文書が意味として正しく書かれているか
  (例えば「概念設計に議論向けのモデルを充てる」という判断の妥当性) は
  人のレビュー対象である。
- 走査は字句である。動的に組み立てた文字列 (例えば変数へ入れて連結する書き方) や
  リポジトリの外にある手順は対象外である。
- 正本のスキル文書と検査の期待表には**同じ割当が二重に現れる**。これは意図した形で、
  片方だけ直すと赤になることが目的である (この repo の目録型 gate と同じ作り)。
  自動抽出で一本化しないのは、正本が壊れたときに検査も一緒に壊れて
  緑のまま通ってしまう側へ倒れるためである。**モデル世代を上げるときは
  正本と期待表を同じ変更で直す**。
- 用途割当の層が読むのは、モデルとラベルを対で宣言している書き方だけである。
  対にできない書き方は赤にするので取りこぼしはしないが、
  「ラベルの語が用途を正しく表しているか」までは見ない (人のレビュー対象)。
