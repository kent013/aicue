## レビュー結果

検証仮説は「正典モデル名の更新そのものではなく、不正な綴り・用途の取り違え・構文崩れ・走査範囲の縮退を検査が fail-open せず検出できれば成功」です。

### 施策1: 検査の3層化と走査根拡大

判定: **REQUEST_CHANGES**

- [Critical] `MODEL_TOKEN_PATTERN` が正典名を不正な文字列の一部として受理します。

  境界指定がないため、例えば `xgpt-5.6-sol` から `gpt-5.6-sol` を抽出します。また `gpt-5.6-sol_preview` でも正典部分だけを抽出し、正しい1件として数える可能性があります。`/i` と小文字化を併用した場合は `GPT-5.6-SOL` も通ります。「接尾辞まで含めた完全な綴り」の保証になりません。

  修正案: 正典3綴りを大文字小文字も含めて完全一致させ、前後がモデル識別子に使える文字 `[A-Za-z0-9_.-]` でないことを確認してください。さらに、正典として消費できなかった `/gpt-/i` の出現を違反にする二段階検査が安全です。少なくとも次を負のコントロールへ追加してください。

  - `xgpt-5.6-sol`
  - `gpt-5.6-sol_preview`
  - `gpt-5.6-sol-`
  - `GPT-5.6-SOL`

- [Warning] 負のコントロールが実運用の判定経路を通る設計になっていません。

  設計されている純粋関数は「収集器」だけですが、負のコントロール3・6・8が検証したいのは回数・写像・正本の「比較器」です。テスト内に比較ロジックを再実装すると、本番の `it` の配線が壊れても負のコントロールだけ緑になり得ます。

  修正案: `validateOccurrences`、`validateAssignments`、`validateCanonTable` のような診断関数まで純粋関数化し、実ファイル検査と検体検査の双方が同じ関数を呼ぶ構造にしてください。

- [Warning] 「表にないファイルは0件」の重要分岐が負のコントロールにありません。

  期待済みファイル内で1件増やすテストだけでは、`EXPECTED_OCCURRENCES[path] === undefined` のときに誤って検査をスキップする実装を検出できません。

  修正案: 期待表にない仮想ファイルへ正典名を1件置き、違反になる検体を追加してください。併せて、期待していた割当を完全に削除した場合と、未知の割当キーが増えた場合も確認すべきです。

- [Warning] 用途割当を `Map` に変換すると重複キーが上書きされます。

  同一の `{path}#{label}` が複数節に現れた場合、最後の値だけを比較すると重複を見逃します。層1の総数と相殺する変更を組み合わせれば緑にできる余地があります。

  修正案: 写像化の前に複合キーの重複を明示的に違反にしてください。割当数、キーの多重集合、値のすべてを比較する形が安全です。

- [Warning] `collectAssignments` の戻り値仕様が曖昧で、strict実装時に扱いにくい形です。

  「割当配列または理由配列」では両者を型で識別しにくく、同じファイルに正常な節と異常な節が共存した場合の情報も失います。また、バッククォートなしの行を単に「宣言なし」と扱う実装になり得ます。

  修正案: 次のように正常値と診断を同時に返してください。

  ```ts
  type AssignmentCollection = {
      readonly assignments: readonly Assignment[];
      readonly diagnostics: readonly ParseDiagnostic[];
  };
  ```

  まず `**model**:` / `**label**:` で始まる候補行を検出し、その後に行全体をアンカーした厳密な構文で検証します。候補なのに構文不正なら必ず診断へ入れてください。

- [Warning] 層3が「利用可能モデル節の正本表」を固定できる仕様になっていません。

  単に正本ファイル中のMarkdown表行を集めるだけでは、3行が別節や別表へ移動しても通ります。

  修正案: `## 利用可能モデル` がちょうど1節あることを確認し、その節内の対象表だけを解析してください。見出しの重複、表の欠落、対象節外への移動も負のコントロールに含めるべきです。

- [Warning] テストファーストの順序が検出器自身には適用されていません。

  段1で検出器を実装した後、段3で負のコントロールを追加しています。これは文書差し替えに対するテストファーストではありますが、検出器ロジックに対するテストファーストではありません。

  修正案: 判定関数を未実装または誤ったスタブにした状態で負のコントロールを先に赤にし、その後に判定関数を実装してください。現物の旧綴りによる赤とは分けて記録すると原因が明確になります。

- [Suggestion] 診断結果はパス、行、トークンでソートしてください。`git ls-files` の順序だけに依存しない方が失敗ログを安定させられます。

### 施策2: `app-codex-vscode` の正本表更新

## 横断的な指摘

- [Warning] 変更ファイル一覧と実際に残す成果物が一致していません。

  「新規なし」としていますが、テストファースト記録の `test-first-red.md` と、A6の `codex-history/impl-review-*.md` をリポジトリへ残す計画です。

  修正案: これらを「新規または更新される検証記録」として変更ファイル一覧へ追加してください。

- [Warning] A6とA7は機械検証可能な受け入れ条件ではありません。

  A6はMarkdownファイルの存在だけでは指定モデルが実際に応答したことを証明できません。A7の `git grep` も、出力を人が読んで判断するコマンドであり、不正な名前を検出しただけではコマンド自体は失敗しません。

  修正案: A6は「外部サービスを含む運用確認」として機械的不変条件から分離してください。A7は層1と重複するため診断用コマンドへ格下げするか、テストのアサーションに一本化してください。

- [Warning] A1の「正典3綴り以外のモデル名が1件もない」は保証範囲が広すぎます。

  提案された検出器が見るのは `gpt-` で始まる限定形式だけで、`o3` など別形式のモデル名や動的構築は検出しません。

  修正案: A1を「検出対象形式に一致する `gpt-` モデル様トークン」に限定するか、別形式も統制する検出規則を設計してください。「保証しないもの」に動的構築だけでなく、検出形式外の名前も明記すべきです。

セキュリティについては、アプリの実行経路・認証・テナント境界・外部通信を変更しないため、直接的な本番セキュリティ影響はありません。固定引数での `git ls-files` 実行にもシェルインジェクション要因は見当たりません。

## 全体判定

**CHANGES_REQUESTED**

モデル割当と対象文書の変更方針は妥当です。一方、中心となる層1検出器には正典文字列を部分一致で通す明確なfail-open経路があります。完全一致境界、共通判定関数、重複割当検出、正本節の固定、受け入れ条件の機械検証範囲を修正した後に再レビューが必要です。
