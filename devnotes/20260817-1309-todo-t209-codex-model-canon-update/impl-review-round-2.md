## `tests/js/architecture/codex-model-consistency.test.ts`

[Critical] `NON_MODEL_EXEMPTIONS` が候補全体ではなく、候補の開始位置だけで例外適用を判断しています。

`isCoveredByLiteral()` は次の条件しか見ていません。

```ts
at <= hit.column && hit.column < at + literal.length
```

そのため、`scripts/codex` の4箇所を維持したまま、例えば1箇所を次のように変更できます。

```text
chatgpt-gpt-beta
```

抽出される候補は `gpt-gpt-beta` ですが、開始位置が `chatgpt-` の範囲内なので例外として握り潰されます。例外件数も4件のままになり、N-24とN-25の両方を通過できます。`chatgpt-5.5` のように旧モデル名を直接続ける場合も同様です。

したがって、Round 1 の候補抽出 fail-open は解消方向へ進んだものの、例外境界へ移った形で残っています。

修正案:

- 例外文字列を `chatgpt-` ではなく、実際の識別子である `openai.chatgpt-` に狭める。
- 候補の開始位置だけでなく、候補の全範囲が例外文字列内に収まることを要求する。

```ts
at <= hit.column
    && hit.column + hit.token.length <= at + literal.length
```

- `openai.chatgpt-5.5`、`openai.chatgpt-gpt-beta` などが必ず点灯する負の検体を追加する。
- 併せて例外目録の `(path, literal)` 重複も違反にすると、目録の保守がより安全です。

[Warning] 層3には、Markdown表として成立しない区切り行で緑になる経路が残っています。

`TABLE_DELIMITER` はハイフンを1文字から許しています。

```ts
const TABLE_DELIMITER = /^\|(?:[ \t]*:?-+:?[ \t]*\|)+$/;
```

そのため、例えば以下でも表の開始として受理されます。

```markdown
| モデル | 用途 |
|-|
| `gpt-5.6-sol` | ... |
| `gpt-5.6-terra` | ... |
| `gpt-5.6-luna` | ... |
```

また、ヘッダーと区切り行の列数も照合していません。GFMの表として成立しない構造でも、正典3行が連続していれば `validateCanonTable()` は違反を返しません。「節内の行をかき集める」問題は解消していますが、「実在しない表で緑になる」経路は完全には閉じていません。

修正案:

- 区切りセルを `^:?-{3,}:?$` で検証する。
- ヘッダーと区切り行のセル数を一致させる。
- この正本ではヘッダーが `モデル | 用途` の2列であることまで固定してもよいです。
- 1ハイフンの区切り、ヘッダーと区切り行の列数不一致を負の検体へ追加してください。

TypeScriptのstrict観点では、`any`、非null断言、握り潰された例外はなく、型付けは良好です。各検体も `it.each` により独立しています。
