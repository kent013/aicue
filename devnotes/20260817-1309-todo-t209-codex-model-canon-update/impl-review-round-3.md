## Warning

### W1 — 層3は依然として「GFMとして成立しない表」で緑になり得る

対象: `parseTableCells` / `isValidDelimiterRow`

`parseTableCells` はすべての `|` をセル境界として扱い、GFMで認められるエスケープ済みの `\|` を考慮しません。例えば次は検査上ヘッダー3セル・区切り3セルとして受理されます。

```markdown
| モ\|デル | 用途 |
|---|---|---|
| `gpt-5.6-sol` | 用途 |
| `gpt-5.6-terra` | 用途 |
| `gpt-5.6-luna` | 用途 |
```

しかしGFMではヘッダーは2セル、区切り行は3セルなので表として成立しません。Round 2 の「実在しない表で緑になる」経路は、単純なセル数不一致については閉じましたが、一般にはまだ残っています。

正本の表形式が固定なら、汎用GFMパーサーを作るより、ヘッダーを `モデル / 用途` の2セルちょうどに固定する方が小さく確実です。併せて上記を負の検体にしてください。

### W2 — コードフェンス判定がCommonMark/GFMより広く、構造を隠せる

対象: `FENCE_OPEN` / `FENCE_CLOSE` / `computeFenceMask`

`^[ \t]*` により4文字以上インデントされたフェンスも開始記号として扱います。CommonMark/GFMの fenced code block は最大3スペースのインデントです。

そのため、例えば次の構造では検査器と実際のMarkdown解釈が逆転します。

```markdown
    ```
## 利用可能モデル
説明だけ
```

## 利用可能モデル

| モデル | 用途 |
|--------|------|
| `gpt-5.6-sol` | 用途 |
| `gpt-5.6-terra` | 用途 |
| `gpt-5.6-luna` | 用途 |
```

検査器は最初の4スペース付き行をフェンス開始と読み、最初の見出しを隠して後半の表を受理できます。一方、GFMでは4スペース付き行は fenced code block の開始ではなく、後の裸の ``` がフェンスを開始するため、後半の正本表がフェンス内になります。

少なくとも以下が必要です。

- フェンスのインデントをGFM相当に限定する
- バッククォート式フェンスのinfo stringにバッククォートを許さない
- 4スペース付き疑似フェンスで正本構造を隠せない負の検体を追加する
