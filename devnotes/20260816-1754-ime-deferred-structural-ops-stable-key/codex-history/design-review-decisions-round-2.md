## [Warning] 施策 4: ケース 8 の壊れ方の説明が JavaScript の挙動と一致していない

> 配列の `array[-1]` は末尾要素を返さない。負数を末尾からの位置として扱うのは `splice(-1, 1)` であり、添字アクセスではない。

- 判断: **対応する (こちらの誤り)**
- 根拠: 完全に正しい。`steps[-1]` は `undefined` であって末尾要素ではない
  (負数の末尾参照は `Array.prototype.at(-1)` と `splice` の第 1 引数の話)。
  したがって `removePoint` の**親側**の早期 return を落とした場合は
  `parent` が `undefined` になり、`parent.points.findIndex(...)` で **`TypeError`** になる。
  「B の急所を巻き添えにする」という設計文の記述は誤りだった。
  一方 `removePoint` の**子側**と `removeStep` は `splice(-1, 1)` に到達するので、
  「末尾が消える」で正しい。**親側と子側で壊れ方が違う**ことを設計が取り違えていた。
- 対応内容: ケース 8 の説明を
  「親の早期 return が無いと `parent` が `undefined` で `TypeError` になり、
  後続の B への急所追加が実行されない」へ書き換えた。
  期待値も「B の既存 2 件が残る」に加えて「追加されて 3 件になる」ことを明示した
  (2 件のままなら drain が中断した証拠になる)。
  壊れ方の分類表も親側 (`TypeError`) と子側 (`splice(-1,1)`) に分けた。

## [Warning] 施策 4: 負の実装 (c)「空の履歴エントリが積まれる」は現在の履歴コアでは成立しない

> `commitStructural` は変異前後を比較し、`pushHistory()` が変更なしを返せば履歴を追加しない。

- 判断: **対応する (こちらの誤り)**
- 根拠: 正しい。`commitStructural` は `before` / `after` を `serializeSteps` で採って
  `pushHistory` へ渡し、`pushHistory` は before === after なら false を返す (no-op)。
  よって「解決失敗時に `commitStructural` を呼んでしまう実装」を作っても
  空エントリは積まれず、ケース 6・7 の Undo 検証はそれを検出していない。
  検出しているのは Codex の言うとおり
  「`splice(-1, 1)` による**誤った実変異**と、それに伴う履歴エントリ」である。
  自分が「早期 return は履歴を汚さないため」と書いた根拠は、実は
  「無駄な `serializeSteps` を 2 回避けるため」でしかなかった。
- 対応内容: Codex の推奨どおり**負の実装 (c) を削除**し、ケース 6・7 の説明を
  「2 回目が誤って実変異してしまうこと (末尾行の巻き添え) と、その分の履歴エントリが
  積まれることを Undo 回数で検出する」へ書き換えた。
  併せて `removePoint` / `removeStep` の設計コメントから
  「履歴を汚さないため」という誤った根拠を外し、
  「変異しないなら履歴機構に触れない (無駄な直列化を避ける)」という正確な表現にした。

## [Warning] 施策 6: 「function 宣言への帰属」を保証していない / コメント除去は「必ず赤に倒れる」と言えない

> `current` は関数の閉じ括弧で解除されない。未登録 arrow function の追加と既存呼び出しの削除が同時に起きると、件数と集合が一致して緑になる配置があり得る。

- 判断: **対応する (Codex の「最小変更」案を採り、加えて穴を 1 つ塞ぐ)**
- 根拠: 指摘は正しい。`current` は「最後に現れた `function` 宣言名」でしかなく、
  閉じ括弧で解除されないので、arrow function / メソッド / 入れ子関数からの呼び出しは
  直前の名前付き関数へ**誤帰属**する。件数と集合が同時に釣り合う配置があれば緑のまま通る。
  コメント除去の正規表現が文字列・テンプレートリテラル・正規表現リテラルを区別しないのも
  そのとおりで、「誤検出は必ず件数不一致で赤に倒れる」という設計文の主張は**証明できない**。
  AST 走査 (推奨案) は Svelte 5 + `lang="ts"` のパースを前提にすることになり、
  この 1 本のトリップワイヤのために parser 依存を新設するのは
  「今必要なものだけ作る」に反すると判断した。本リポジトリの JS レーンの既存目録テスト
  (`logout-call-site-inventory` / `svg-inline-allowlist`) もすべて字句走査である。
- 対応内容: 最小変更案を採用し、**保証範囲の記述を全面的に書き直した**うえで、
  Codex が具体的に挙げた「未登録 arrow function からの直接呼び出し」の穴だけを
  安価に塞ぐ検査を 1 つ足した:
  - 各 `runSettled(` 呼び出しについて、**直前に現れた「スコープを開く行」**
    (名前付き `function` 宣言 / arrow / 無名 function) を求め、
    それが**名前付き `function` 宣言でなければ赤**にする。
    これで「arrow function から直接呼ぶ」形は帰属を偽装できなくなる。
  - 「誤検出は必ず赤に倒れる」という記述を**削除**した。
  - 保証外として **arrow function / メソッド / 入れ子関数 / 複数行にまたがる呼び出し /
    文字列・テンプレートリテラル・正規表現リテラル中のコメント記号 / 間接呼び出し /
    別モジュールへの切り出し**を明記した。
  - テストの位置づけを「関数への正確な帰属を保証する検査」ではなく
    **「現在のソース書式に対するトリップワイヤ」**と言い切った。
  - 施策 5 の負のコントロール (d) に、Codex の指示どおり
    **通常の function からの呼び出しと arrow function からの呼び出しの両方**を足し、
    **実測でどちらが検出されるかを記録する** (検出できない形が見つかったら、
    それを「保証しないもの」の実測済みの証拠として残す)。
