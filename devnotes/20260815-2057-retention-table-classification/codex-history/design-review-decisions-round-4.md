# 対応マトリクス: design-review Round 4 (全体判定 APPROVED)

Round 4 で [Critical] / [Warning] は 0 件。[Suggestion] 3 件はいずれも実装の精度を上げるので反映した。

## [Suggestion] 情報が足りないときは fail-closed にする
- 判断: 対応する
- 根拠: 空の列一覧に対して「全部 nullable」と答える空虚な真は、検査を無音で素通りさせる。
  本リポジトリの目録 gate は一貫して deny-by-default なので、判定側も同じ方へ倒すのが自然である。
- 対応内容: 純関数の docblock に fail-closed の 2 条件を明記した。
  - 外部キーの列が空 (`columns === []`) → 違反
  - 列の nullable が一覧に無い → 違反 (`?? false` で倒す)
  併せて `set null` を非違反にできる条件 (列が空でない / 全列が一覧にある / 全列が true) を
  コード注記として置いた。docs 側にも同じ扱いを書く指示を追加した。

## [Suggestion] RC-7 のテスト名を実際の保証範囲に合わせる
- 判断: 対応する
- 根拠: nullable な `set null` の参照は許すので、「親に持っていない」は検査より強い表現だった。
- 対応内容: テスト名と検査一覧の説明を
  「期限が要る区分の表を**矛盾する削除動作で**参照していない」に直した。

## [Suggestion] 複合外部キーの一部だけを対象にする書き方への注意
- 判断: 対応する (保証文として明記)
- 根拠: Laravel の `getForeignKeys()` は外部キーの列を 1 組で返し、削除動作の対象列を
  区別しない。よって判定は必要条件より厳しくなりうるが、これは見落としではなく
  **余分に赤くなる側**への偏りである。
- 対応内容: 「見るのは Laravel の Schema API が返す外部キーの列すべてである。
  複合外部キーの一部だけを対象にする書き方があっても区別しないので、判定は必要条件より
  厳しくなりうる (見落としではなく、余分に赤くなる側へ倒れる)」を docblock に明記した。
