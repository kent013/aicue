# 対応マトリクス: conceptual-review Round 1

## [Critical] 保持期限の安全性を保証していないのに保証しているように読める
- 判断: 対応する
- 根拠: 本リポジトリには「保証範囲を誇張しない」を明文の規約として持つ先例が複数ある
  (AGENTS.md のテストレーン外部 HTTP 出口 / 禁止する文 / 外部到達点の目録)。指摘のとおり
  「FK がある = 親と一緒に消える」「FK が無い = 個人情報を持たない」はどちらも成立しない。
- 対応内容: 概念設計に「この gate が保証するもの / 保証しないもの」節を新設し、
  保証は (a) 実スキーマの全表が分類されていること (b) 課金 7 年の表集合との結線
  (c) 未確定が無音で増えないこと (d) 宣言した期限の保持者が実在すること の 4 つに絞った。
  区分名も保証範囲に合わせて改名した (下記)。

## [Warning] migrations 等の基盤表を業務の保持期限と同じ区分に混ぜると分類の意味が薄まる
- 判断: 対応する
- 根拠: 除外一覧を作らない方針は維持したいが、指摘のとおり「基準データ」と「基盤の表」は
  寿命の持ち主が違う (前者は運用者、後者はフレームワーク / キューの実装)。同じ区分に置くと
  根拠の文章が両方の意味を兼ねてしまう。
- 対応内容: 区分を 5 → 6 に増やし、`ReferenceData` (基準データ) と `FrameworkManaged`
  (基盤が寿命を持つ表) を分けた。除外一覧は作らない (分類の 1 つとして台帳に載る)。

## [Warning] 「親と一緒に消える」の裏取りが「FK を 1 本以上持つ」では不十分
- 判断: 対応する
- 根拠: そのとおり。`getForeignKeys()` は `on_delete` を返すので、cascade かどうかまでは
  実スキーマから機械で確かめられる。確かめられることを確かめていなかった。
- 対応内容: 「実 FK のうち `on delete cascade` のものを 1 本以上持つ」を必須にし、
  cascade でない (アプリ側の Service が消す) 場合は削除責務の保持者クラスの宣言を必須にした。

## [Warning] 「期限を持たない」を「個人情報を持たない」の裏取りに使うのは弱い
- 判断: 対応する (ただし列名ヒューリスティックは見送る)
- 根拠: FK が無くても email / token / IP は単独で個人・端末に紐づく。指摘は正しい。
  一方で列名の当て推量による検査は偽陽性と偽陰性の両方を生み、目録が「当たらない検査を
  黙らせるための例外」で埋まる。本リポジトリは目録に例外の口を作ることを強く避けている。
- 対応内容: 区分名から個人情報の含意を外し (`NoExpiry` → `ReferenceData` / `FrameworkManaged`)、
  FK 検査の主張を「期限が要る区分の表を親に持つなら、その表も期限の連鎖の中にある」に限定した。
  「列の内容が個人情報かどうかは見ない」を保証しないものへ明記。列名ヒューリスティックは
  スコープ外として理由付きで書いた。

## [Warning] 期限の保持者が自由文字列だと二重管理になる
- 判断: 対応する
- 根拠: 文字列を書き写すだけでは、解決点クラスの改名やコマンドの廃止に追随できない。
- 対応内容: 保持者を「解決点クラスの FQCN」と「artisan コマンド名」の 2 つに分け、
  gate が `class_exists()` と登録済みコマンド一覧への実在を検査する。
  enum 化までは行わない (対象が 5〜6 件で、実在検査があれば腐りは検出できる)。

## [Warning] 構造検査を増やすこと自体を目的にしない
- 判断: 対応する
- 根拠: 「区分ごとに 1 つずつ」は形を揃えるための言い方であって、保証の設計ではなかった。
- 対応内容: 「区分ごとに 1 つ」の書き方をやめ、検査は 6 本に整理した
  (うち FK を見るのは 2 本で、`ReferenceData` と `FrameworkManaged` は同じ 1 本が担う)。

## [Warning] 検証コマンドの明記
- 判断: 対応する
- 対応内容: 実装方針に `composer test` / `composer phpstan` / `vendor/bin/pint --test` を明記。

## [Suggestion] holder を enum / value object へ
- 判断: 見送る (部分対応)
- 根拠: 上記のとおり実在検査で腐りは検出できる。5〜6 件のために型を 1 つ増やすのは
  思考原則 2 (今必要なものだけ作る) に反する。
