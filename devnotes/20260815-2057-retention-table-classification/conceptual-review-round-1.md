全体判定: **CHANGES_REQUESTED**

設計の方向性は妥当です。実スキーマを母集団にして「表を足したら分類が必要」にするのは、このリポジトリの inventory gate 作法とも合っています。ただし、現状の区分ごとの機械裏取りが弱く、**保持期限の分類を保証しているように見えて、実際には保証できない主張が混ざっています**。ここは概念設計段階で直すべきです。

## 1. 使命との整合性

[Suggestion]  
法人顧客のSOP・撮影データ・業務ノウハウを扱う以上、保持期限の可視化は North Star に間接的だが本質的に貢献します。直接の動画生成機能ではないものの、導入審査・情報管理・削除要請対応の前提になるため、改善テーマとして妥当です。

## 2. 禁止事項違反

[Warning]  
「テスト側だけで完結」はよいですが、実装完了時に `composer test` だけでなく、影響範囲に応じて `composer phpstan` / `vendor/bin/pint --test` も必要です。PHP の enum / DTO 的クラスを追加するため、PHPStan level 10 の確認は必須です。

修正提案: 実装方針に検証コマンドとして少なくとも以下を明記してください。

```text
composer test -- --filter=RetentionTableClassificationTest
composer phpstan
vendor/bin/pint --test
```

## 3. 実現可能性

[Warning]  
Feature lane で実スキーマを読む方針は妥当です。ただし `migrations` 表を含める設計は、Laravel / package / test bootstrap の変更でノイズになりやすいです。除外口を作らない意図は理解できますが、基盤表まで業務保持期限と同じ台帳に混ぜると、分類の意味が薄くなります。

修正提案: 除外一覧ではなく、区分として `frameworkManaged` / `migrationMetadata` のような「基盤メタデータ」を明示分類してください。これなら逃げ口ではなく、台帳対象として扱えます。

[Warning]  
`主体と一緒に消える` の裏取りが「外部キーを1本以上持つ」だけでは不十分です。FK があっても `ON DELETE CASCADE` ではない、nullable で孤立しうる、親側の purge が実装されていない、アプリケーションサービスでしか削除されない、というケースがあります。

修正提案: この区分は少なくとも次のどちらかを必須にしてください。

```text
- DB FK が on delete cascade / restrict 等どの挙動かを検査し、期待する削除連動と一致する
- DB cascade でない場合は、削除責務を持つ Service / command / policy 名を holder として宣言する
```

## 4. 期待効果の妥当性

[Warning]  
「個人情報を持たない」という分類を「期限が要る区分の表への外部キーを持たない」で裏取りするのは弱いです。PII は FK なしでも存在します。例として email、name、phone、ip、token、user_agent、external_id 的な列は単独で個人・端末・アカウントに紐づき得ます。

修正提案: `期限を持たない` は「個人情報を持たない」と断定せず、名前を `保持期限の対象外と裁定` などに寄せてください。そのうえで、保証しないものに「列内容のPII性は保証しない」を明記するか、軽量な列名ヒューリスティックの負のコントロールを足してください。

## 5. リスク

[Critical]  
この設計の最大リスクは、**保持期限の安全性を保証していないのに、保証しているように読めること**です。特に以下の2点です。

```text
- FK がある = 親と一緒に消える、ではない
- FK がない = 個人情報を持たない、ではない
```

このまま実装すると、レビュー上は緑でも、実際には残留データを見逃す可能性があります。

修正提案: gate の責務を次のように絞って明文化してください。

```text
この gate が保証するもの:
- 実スキーマ上の全テーブルが retention 台帳に分類されていること
- 既存の保持期限 holder との集合不整合を検出すること
- 未確定テーブルが明示され、無音で増えないこと

この gate が保証しないもの:
- 列単位のPII分類
- 実データが実際に削除されること
- FK の存在だけによる削除連動
- S3/object storage の保持期限
```

そのうえで、区分名・検査名もこの保証範囲に合わせるべきです。

## 6. スコープの適切さ

[Suggestion]  
新しい purge 実装や保持期限値の変更をスコープ外にしているのは適切です。まず母集団を作る、という順序は良いです。

[Warning]  
一方で「区分ごとに実スキーマの外部キーを見る検査を1つずつ付ける」は、区分によっては意味のある検査になっていません。構造検査を増やすこと自体を目的にせず、分類ごとに保証できることだけを検査してください。

## 7. 型安全性

[Suggestion]  
`RetentionClass` enum、`RetentionTableEntry` value object、`RetentionTableRegistry` の構成は PHPStan level 10 と相性がよいです。

ただし `holder` を nullable string にすると分類ごとの必須条件が緩みやすいです。`RetentionOwner` のような enum / value object に寄せるか、named constructor で分類ごとの不正状態を作れないようにするとよいです。

## 8. 二重管理

[Warning]  
`config/retention.php` を作らず、値の正本を既存 resolver に委譲する判断は正しいです。

ただし `定期実行が消す` に artisan コマンド名だけを書くと、既存 scheduler / command / resolver との対応が文字列二重管理になりやすいです。

修正提案: holder は自由文字列ではなく、既存の解決点クラス名や既存 inventory から導出できるものを優先してください。少なくとも「表示用ラベル」ではなく「存在検査できる FQCN / command signature」にするべきです。

---

結論として、**実スキーマ全表を台帳化する発想は承認可能**です。ただし、現案のままだと構造検査の意味が強く見えすぎます。  
次版では「この gate が保証する範囲」を狭く正確に定義し、`主体と一緒に消える` と `期限を持たない` の裏取り条件を修正してください。
