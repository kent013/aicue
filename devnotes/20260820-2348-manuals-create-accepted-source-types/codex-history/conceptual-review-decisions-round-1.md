# 対応マトリクス: conceptual-review Round 1

## [Critical] (D) の gate は「props が真に単一情報源から来ている」ことを保証できない (観点 3)

- 判断: **対応する**
- 根拠: 指摘は正しい。`accept={sourceDocumentAccept}` という**形**を静的に見ても、
  その識別子が Controller の `AcceptedSourceDocumentTypes` 由来であることは
  Svelte 側の走査では確定できない (Inertia props は実行時に注入されるため、
  静的検査の到達範囲外)。AGENTS.md の共通規約 (b) 「保証しない構文について検出力を
  主張しない」に照らしても、gate の名前と主張を到達範囲へ縮める必要がある。
- 対応内容: 概念設計の (D) を**責務 2 つに分割**して書き直した。
  1. **静的層 (目録)**: 「`resources/js` の file input が accept の供給元区分を
     宣言していること」だけを deny-by-default で強制する
     (区分は「サーバ props 由来」/「クライアント固定値 + 理由」の 2 つ)。
     **単一情報源との一致は主張しない**ことを docblock と概念設計に明記。
  2. **実挙動層 (2 段の契約テスト)**:
     (i) PHP Feature テストで `create()` / `show()` の Inertia props を
     `AcceptedSourceDocumentTypes` の**出力そのもの**と比較する (両フラグ)。
     (ii) JS component テストで、その props が `accept` 属性と案内の表示条件に
     実際に使われることを固定する (両フラグ)。

## [Warning] 共有コンポーネント化で既存の testid・文言・表示順を実質変更しないこと (観点 2)

- 判断: **対応する**
- 根拠: 詳細画面は T234 で承認済みの面であり、共有化は内部移動に留めるべき。
- 対応内容: 既存 `tests/js/components/` の `SourceDocumentUpload` テスト
  (無ければ新設) で testid 2 種・文言・**案内 → file input の表示順**を固定することを
  施策のテスト計画に明記する。

## [Warning] Svelte の属性形態 (spread・条件レンダー・引用符・式) の扱いが未定義 (観点 3)

- 判断: **対応する**
- 根拠: 素朴な正規表現走査では検出漏れと誤検出の両方を生む。共通規約 (b) の
  「解決できない形は落とす」を満たすには構文の解決手段を決める必要がある。
- 対応内容: gate は **`svelte/compiler` の `parse()` が返す AST** を走査する方式に確定した
  (svelte ^5.56.2 が依存に既に入っており、`modern: true` で
  `Attribute` / `SpreadAttribute` を区別できることを実測で確認済み)。
  `SpreadAttribute` を持つ file input・`accept` 属性が無い file input・
  parse に失敗したファイルは**すべて失敗**させる (fail-closed)。
  走査対象・保証しない範囲・母集団非空検査を docblock に書く。

## [Warning] ラベルと config の拡張子集合が将来乖離しうる (観点 4)

- 判断: **対応する (ただし「ラベルの機械導出」は採らない)**
- 根拠: 拡張子リストから日本語ラベル
  (「PDF・Excel・テキスト形式、または JPEG・PNG の画像」) を機械導出するには
  拡張子 → 表示名の写像と接続助詞の組み立てが必要で、**法務確認済みの文面を
  コードが生成する**形になる。文面が意図せず変わる方が危険であり、
  「今必要なものだけ作る」にも反する。
- 対応内容: ラベルは承認済みの 2 文をそのまま単一情報源クラスに置き、
  **前提の pin** で乖離を検出する。すなわち
  `config('manual.source_document_mimes')` の基底集合と画像拡張子集合が
  現在値ちょうどであることを検査 (`*PremiseTest` の既存文化に合わせる) し、
  config を触ったらラベルの見直しが必ずレビューに乗るようにする。
  併せて両フラグ状態で「extensions / accept / ラベル / FormRequest の 422 文言」が
  同じ集合を指すことを 1 つのテストで固定する。

## [Warning] 画像導線が開くとアップロード試行と外部送信対象が増える (観点 5)

- 判断: **対応する**
- 根拠: 開示をファイル選択の**前**に置くのは指摘どおり妥当 (押した後では遅い)。
- 対応内容: 案内 2 段落を file input の**上**に置くことを設計に明記
  (詳細画面と同じ並び)。サーバ側の二段防御 (FormRequest + 内容 sniff) は
  1 行も変えないことをスコープ外へ明記し、既存の OCR 受理テストが回帰を担うことを記す。

## [Warning] D の維持コストが不整合修正に対して大きい (観点 6)

- 判断: **対応する (責務縮小で受ける)**
- 根拠: Critical への対応で gate の責務が「分類漏れ検出」だけに縮み、
  実装は AST 走査 + 目録 1 ファイルになる。撮影側 2 件は値を変えず理由付き登録のみ。
- 対応内容: 上記のとおり (D) を書き直し、優先度を「低 (再発防止)」として
  A〜C とは独立に実装できる位置付けにした。

## [Warning] props を個別に増やすと将来の追加漏れが起きる (観点 7)

- 判断: **対応する**
- 根拠: 今回の事故そのものが「props の追加漏れ」である。
- 対応内容: Critical 対応の (i) で `create()` と `show()` の**両方**を
  同じ 1 つの Feature テストが `AcceptedSourceDocumentTypes` の出力と突き合わせる形にした
  (面が増えたらこのテストへ 1 行足す = 追加漏れがレビューに見える)。
  props を 1 つのオブジェクトへ束ねる案は採らない (既存 show() 側の props 形状を
  破壊的に変えることになり、T234 の承認済み契約を壊すため)。
