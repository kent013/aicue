# 対応マトリクス: design-review Round 2

## [Warning] 施策 2: Feature テストは `formatsLabel()` の呼び出しを証明できない (置換忘れは検出できない)

- 判断: **対応する (提案のうち「現実的な案」= 記述の訂正を採用)**
- 根拠: 指摘は正しい。置換前の三項演算子を残しても両フラグで同じ文言を返すため、
  提示していたテストは緑になる。「置換忘れを検出する」という保証は成立しない。
  構造的な結線を機械で見る Architecture テスト (完全修飾名の解決を伴う走査器) を
  2 ファイルのために新設するのは、得られる保証に対してコストが見合わない
  (共通規約 (a) を満たす走査器を 1 本増やす作業になる)。
- 対応内容: テスト計画から誤った保証の記述を削除し、
  「保証するのは**両エンドポイントの 422 出力契約**であって呼び出しの証明ではない。
  構造的な結線はコードレビューで確認する。**文面が経路ごとにずれたら検出する**」へ訂正した。
  期待文を `formatsLabel()` から組み立てる理由も「経路ごとの文面のずれの検出」へ書き換えた。

## [Warning] 施策 5: 母集団・diagnostic の判定責務が gate と判定関数に分裂している

- 判断: **対応する (提案どおり 1 関数へ集約)**
- 根拠: 指摘のとおり、母集団非空と `diagnostics` を gate 側の assert に置くと
  その分岐に負例が付かず、「走査器は診断を集めたのに gate が無視する」実装ミスを
  自己検査できない (共通規約 (d) の裏取りが弱い)。ケース 24 の入力先も曖昧だった。
- 対応内容: `evaluateFileInputInventory()` へ
  走査空振り / 母集団空 (2 種を別々の違反として) / `diagnostics` の全件違反化 /
  目録比較のすべてを集約し、gate 本体は「走査 → 判定関数の結果が空」の 2 ステップだけにした。
  自己検査 (B) へ 24〜28 の 5 ケース (`svelteFileCount=0` / `nativeInputCount=0` /
  `fileInputs=[]` / `diagnostics` 1 件 / `supply` と `syntax` の整合違反) を追加し、
  合計 13 ケースにした。関数の docblock に集約の理由を書く方針も明記した。

## [Suggestion] `server-prop` は `syntax === "expression"` のみ許す整合条件

- 判断: **対応する**
- 根拠: 宣言値を判定に使える安価な整合条件であり、静的テキストの `accept` を
  「サーバから来る」と宣言している矛盾を潰せる。保証範囲は広がらない。
- 対応内容: 判定関数の違反種類へ追加し、「**由来の証明ではない** —
  `expression` であることしか確かめておらず `server-prop` の意味は宣言のまま」と明記した。
