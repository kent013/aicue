# 全体判定: CHANGES_REQUESTED

Round 2 の指摘はすべて適切に解消されています。設計本体のセキュリティ境界、責務分担、型安全性は承認可能です。

残る変更要求は、新設する字句走査 gate が AGENTS.md の「走査器・gate を新設・変更するときに同じ PR で揃える4点」を満たすことの明記だけです。

## 1. 使命との整合性

- [Suggestion] 問題ありません。メール抑止基盤の安全性と継続性を通じた間接的な貢献として、過大に主張せず整理されています。

## 2. 禁止事項違反・セキュリティ不変条件

- [Suggestion] SSRF 防御の保証範囲は正確になりました。private IP への接続試行自体は残ること、TLS が制限する範囲、CA 検証への依存が明示されています。

- [Suggestion] `inspect → fetch` を採用し、`PinnedHttpClient` を使わない理由も、vendor API と AG-199 の裁定に基づいており妥当です。

## 3. 実現可能性

- [Suggestion] Laravel HTTP Client、SSRF inspector、Cache lock、AWS validator の cert client を組み合わせる構成は実現可能です。

- [Suggestion] 応答サイズ検査について、メモリ上限ではないことを明示したため問題ありません。ストリーミング機構を今回追加しない判断もスコープと整合します。

## 4. 期待効果の妥当性

- [Suggestion] キャッシュ命中時に限定した外向き通信削減、503 による回復可能性、再送期間経過後の配送断念がそれぞれ区別され、合理的な主張になっています。

## 5. リスク

- [Suggestion] DNS TOCTOU、単一ロックによる正規通知の 503、lock TTL 超過、非共有 cache store、キャッシュ済み証明書の有効性について、保証しない範囲が十分に明示されています。

- [Suggestion] ロックを外向き通信だけに限定する反論は妥当です。守る不変条件が同時外向き通信数であり、キャッシュ昇格条件が署名検証成功に独立して固定されるため、署名検証までロックを延長する必要はありません。

## 6. スコープの適切さ

- [Warning] TLS 検証無効化を検出する新しい字句走査は、AGENTS.md の走査器共通規約の発火対象ですが、計画には「字句走査 + 負例」しか明記されていません。新設 gate には、負例だけでなく正例、走査母集団の非空確認、走査対象と保証外構文を記した docblock が必要です。語彙照合を行うなら、区切り文字によるトークン完全一致と、接頭辞・打ち消し・接尾辞付きの負例も必要になります。  
  修正提案: `SnsCertificateFetchContractTest` の計画へ次を追加してください。

  - 違反入力を検出する負例と、正常な TLS 設定を誤検出しない正例
  - 取得口を含む走査母集団が空でないことの検査
  - 走査対象、判定対象、変数経由・動的配列など保証しない構文を記した docblock
  - 語彙一致なら、区切り文字の宣言と接頭辞・打ち消し・接尾辞付き負例
  - 収集した走査結果を実際の assertion に使用すること

  単一の既知クラスだけを守る目的なら、広い汎用走査器にせず、その取得口を明示的に対象とする小さな契約テストで十分です。

## 7. 型安全性

- [Suggestion] `fromString(string): self` と専用例外による失敗表現は、nullable や汎用例外を避けており適切です。

- [Suggestion] `openssl_x509_read()` の union 戻り値を private メソッド内で `false` と明示比較し、公開境界とキャッシュを `string` に固定する方針は PHPStan level 10 と両立します。

- [Suggestion] `SnsCertificateFetcher` が検証済み `SnsCertificateUrl` しか受け取らないため、未検証 URL の混入経路も型で閉じられています。

上記の gate 計画を補えば、概念設計は APPROVED にできます。アプリ本体の設計に新たな Critical はありません。
