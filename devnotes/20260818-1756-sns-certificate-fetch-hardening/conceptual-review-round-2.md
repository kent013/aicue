# 全体判定: CHANGES_REQUESTED

Round 1 の主要な設計矛盾だったロック保持範囲とキャッシュ昇格についての反論は妥当です。ロックの不変条件が「同時外向き通信数 = 1」であるなら、署名検証まで保持する必要はありません。未検証 PEM の非キャッシュ化も、昇格条件を署名検証成功だけに限定すれば独立して保証できます。

一方、SSRF と応答メモリに関する主張には、まだ修正すべき過大表現があります。

## 1. 使命との整合性

- [Suggestion] 妥当です。使命への寄与を「無認証 webhook の安全性とメール抑止基盤の継続性」に整理したことで、間接的な基盤改善であることが明確になりました。

## 2. 禁止事項違反・セキュリティ不変条件

- [Warning] DNS rebinding への説明は「HTTP レスポンス本文を取得できない」という範囲では概ね妥当ですが、「TOCTOU を押さえる」という表現は強すぎます。再解決先の private IP への TCP 接続と TLS ClientHello 自体は発生します。TLS ホスト名検証は、接続そのものを防ぐものではありません。また、接続先が対象ホスト名について信頼される証明書を持つ特殊な環境では、その先も阻止できません。  
  修正提案: 「TOCTOU を解消する」ではなく、「残る TOCTOU による HTTP 層での情報取得を、通常の CA 検証が有効であることを前提に TLS が制限する。ただし private IP への接続試行自体は防がない」としてください。

- [Warning] TLS による耐性は、HTTP Client の証明書検証が無効化されていないことに依存しますが、その前提の固定方法がありません。将来 `verify => false` や等価な設定が入ると、設計上の補完防御が無音で消えます。  
  修正提案: 取得クライアントで TLS 検証を明示的に維持し、少なくとも `withoutVerifying()` や `verify => false` を使わないことを契約テストまたは既存の外部 HTTP gate で固定してください。機械固定できない部分は運用前提として明記してください。

- [Suggestion] `PinnedHttpClient` が本文を返さず、このユースケースに直接使えないという反論は妥当です。さらに AG-199 が `inspect → fetch` を適合形として認めているなら、今回 `PinnedHttpClient` への移行を要求する必要はありません。

## 3. 実現可能性

- [Warning] 「読み取りの時間上限により実メモリが有界」という主張は成立しません。時間制限は、帯域が大きければその時間内に受信できるバイト数を制限しません。host 固定・TLS・redirect 禁止も、数学的または設定上のメモリ上限にはなりません。  
  修正提案: 「メモリ使用量に明示的な上界は設けない。信頼対象を SNS ホストへ限定し、短い時間予算で運用上のリスクを低減する」に修正してください。明示的な上界を主張しないなら、ストリーミング機構の追加は本スコープで必須ではありません。

- [Suggestion] Laravel HTTP Client、Cache lock、値オブジェクト、AWS validator の cert client 注入を用いる構成は、Laravel 12 で実現可能です。

## 4. 期待効果の妥当性

- [Suggestion] 「キャッシュ命中時」に限定した記述へ直されたため妥当です。

- [Suggestion] 非ブロッキング取得の利点を保証ではなく期待値として表現した修正も適切です。

## 5. リスク

- [Warning] 「503 は SNS の再送対象なので抑止漏れにはならない」は断定が強すぎます。再送には回数・期間の限界があり、攻撃や障害が継続すれば最終的な配送断念はあり得ます。恒久的な 403 より回復可能性が高いことは確かですが、抑止漏れを完全には否定できません。  
  修正提案: 「503 により即時の恒久ドロップを避け、SNS の再送期間内に競合が解消すれば回復できる」に変更してください。

- [Suggestion] 単一ロックによる head-of-line blocking、ロック寿命超過、非共有 cache store の限界が明記され、リスクの記述は大きく改善しています。

- [Suggestion] キャッシュ値を再検査し、破損時に `forget` して miss 扱いにする方針は、不変条件 11 と整合します。

## 6. スコープの適切さ

- [Suggestion] 適切です。今回の不変条件に必要な URL 型、取得口、ロック、キャッシュ、例外写像、テストに限定され、throttle や抑止表の再設計を切り離せています。

- [Suggestion] 状態遷移表によって責務と失敗時の挙動が十分に具体化されました。

## 7. 型安全性

- [Warning] `SnsCertificateUrl::fromString()` が不正入力時に何を返すかが未確定です。nullable や汎用例外にすると、403/500 の写像が呼び出し側の分岐に散らばる可能性があります。  
  修正提案: `fromString(string): self` とし、専用の署名不正例外を投げる、または失敗型を明示した Result DTO を使ってください。Fetcher は `SnsCertificateUrl` だけを受ける設計を維持すれば、PHPStan level 10 と両立できます。

- [Warning] `openssl_x509_read()` の戻り値は PHPStan 上 `OpenSSLCertificate|false` です。検査だけに使う場合でも、戻り値を明示的に `false` と比較し、証明書オブジェクトをキャッシュや DTO に混ぜない必要があります。  
  修正提案: PEM 検査を `assertValidPem(string $pem): void` のような専用メソッドへ閉じ込め、キャッシュ境界は常に `string` に固定してください。

- [Suggestion] 未検証 URL を Fetcher の API から型で排除し、キャッシュも素の文字列に限定する方針は適切です。

結論として、Round 1 のロックに関する Critical は解消しています。残る変更要求は、主として保証範囲の正確化です。「TLS は private IP への接続自体を防がない」「時間制限はメモリ上限ではない」「503 でも最終的な配送断念はあり得る」の3点を修正すれば、概念設計として APPROVED にできます。
