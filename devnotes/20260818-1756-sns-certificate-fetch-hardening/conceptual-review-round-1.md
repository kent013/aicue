全体判定: CHANGES_REQUESTED

1. 使命との整合性

- [Suggestion] 使命への寄与は間接的ですが妥当です。招待・通知メールの到達性を支える抑止処理の信頼性向上は、AI-CUE を継続利用できる運用基盤に寄与します。実装目的は「SNS webhook の外部通信境界と障害挙動を安全にする」と簡潔に表現すると、使命との因果がより明確になります。

2. 禁止事項・セキュリティ不変条件

- [Critical] 「`UrlSafetyInspector::inspect()` の後に通常の HTTP Client で取得する」だけでは、SSRF 防御として十分かを明確に検証する必要があります。検査時と接続時で DNS 解決結果が変わる DNS rebinding を防げない実装なら、不変条件 8 の意図を満たしません。  
  修正提案: `inspect()` が接続先 IP を pin した安全な取得手段を返す／提供するかをライブラリ仕様で確認し、そうでなければ `PinnedHttpClient` を使って検査結果と実際の接続を結び付けてください。「一本化はスコープ外」という裁定がある場合も、この経路で rebinding 耐性をどこが担保するかを設計に明記してください。

- [Warning] `Http::fake()` と `FakeDnsResolver` を使うテスト方針は適切です。ただし、実際の HTTP 接続が pin 済み IP を使う設計にする場合、偽装対象は DNS だけでなく接続層も含む必要があります。  
  修正提案: 「許可ホストだが private IP に解決される」「inspect 後に解決先が変わる」ケースを、ライブラリが担保できる範囲に応じて Feature テストへ加えてください。

3. 実現可能性

- [Critical] キャッシュ昇格の責務とロック保持期間が矛盾しています。`SnsCertificateFetcher` がロック・取得・キャッシュを担い、`AwsSnsSignatureVerifier` が「署名成功後の昇格」を担う構成では、取得直後にロックを解放すると、署名検証完了前に別リクエストが再取得を始められます。一方、Fetcher が先にキャッシュすると未検証 PEM をキャッシュしてしまいます。  
  修正提案: Fetcher に「ロック取得→キャッシュ確認→未キャッシュ PEM 取得」を行わせ、Verifier の署名検証成功／失敗を受けて同じ処理単位内で `commit`／破棄できる API を設計してください。例えば `fetchAndVerify(callable $verify): bool` のように、ロックを署名検証成功後のキャッシュ昇格まで保持する形です。ロック取得失敗時は即時 503、キャッシュ命中時はロック不要、という状態遷移を設計・テストで固定すべきです。

- [Warning] HTTP 応答サイズ上限を「受信後の本文長チェック」で実装すると、大きな応答をメモリへ読み込んだ後になり、上界を作る目的を達成できません。  
  修正提案: `Content-Length` の事前拒否に加え、ストリーミング受信中にも上限を強制できる実装手段を確認してください。Laravel HTTP Client 単体で難しければ、実際に保証できる範囲へ要件を狭め、制限不能な応答へのタイムアウト依存を明記してください。

4. 期待効果の妥当性

- [Warning] 「正常時の外向き通信が消える」はキャッシュ有効期間中に限るため、少し強すぎる表現です。証明書ローテーション、キャッシュ失効・削除、キャッシュ障害では通信が再発します。  
  修正提案: 「キャッシュ命中時には外向き通信とロック待機を発生させない」に修正してください。

- [Suggestion] 「503 後の SNS 再送時には winner がキャッシュを埋め終えている」は一般には期待できますが、winner の通信・署名検証失敗やキャッシュ障害では成立しません。ここは保証ではなく、非ブロッキングを選ぶ合理的な期待値として書くのが適切です。

5. リスク

- [Warning] 単一のグローバルロックは、攻撃者が形式上有効な異なる SNS 証明書 URL を連続送信したとき、正規通知の証明書取得まで 503 にする可用性リスクを意図的に導入します。これは同時外向き通信数を 1 にする目的とのトレードオフとして妥当ですが、明文化が必要です。  
  修正提案: ロック競合時は即時 503 とすること、ロック TTL が HTTP 接続・読取・署名検証の合計時間より長いこと、TTL 超過時に同時取得上界が崩れることを Architecture テストで固定してください。

- [Warning] PEM の `openssl_x509_read` 成功は、SNS 署名検証に使えることの十分条件ではありません。最終的な安全性は vendor validator による対象メッセージの署名検証成功で担保されます。  
  修正提案: PEM 確認は「早期の形式不正排除」、署名検証は「キャッシュ昇格の唯一の条件」と役割を分けて明記し、未検証・検証失敗 PEM が一切キャッシュされない負例テストを必須にしてください。

- [Suggestion] キャッシュから読み戻した PEM についても、破損や手動改変に備えて `openssl_x509_read` に失敗したら削除して miss 扱いにする方針を明記すると堅牢です。

6. スコープの適切さ

- [Suggestion] route throttle や抑止表の変更をスコープ外に置く判断は適切です。既存の webhook throttle を変えず、証明書取得という無認証外部通信の一点へ集中しています。

- [Warning] 実装方針の「新設・改修ファイル数」より、責務境界と状態遷移を先に確定すべきです。現在は Fetcher と Verifier のキャッシュ昇格責務が重なっています。  
  修正提案: ファイル数の記述に加え、キャッシュ hit / lock 取得失敗 / HTTP 失敗 / PEM 不正 / 署名失敗 / 署名成功の各状態で、HTTP・ロック・応答・キャッシュがどうなるかを小さな表として設計へ追加してください。

7. 型安全性

- [Warning] `SnsCertificateUrl` を単なる string wrapper に留めると、未検証 URL を Fetcher へ渡す経路が将来復活し得ます。  
  修正提案: Fetcher の公開 API は `SnsCertificateUrl` のみを受け、生成は検証ファクトリ経由に限定してください。URL 文字列、PEM、取得結果、検証結果を別の明示的な型／DTOとして扱い、`mixed` や `array<string, mixed>` で境界を曖昧にしない設計にしてください。

- [Suggestion] キャッシュ値は PEM の素の文字列に限定し、読み戻し時に明示的に検査する方針は、既存のキャッシュ不変条件および PHPStan level 10 と整合します。`Cache::remember()` の曖昧な戻り値推論に依存せず、戻り値型を明示した専用メソッドに切り出すと通しやすくなります。

上記の Critical、特に「SSRF 検査と実接続の結合」と「検証成功までロックを保持したキャッシュ昇格」を解消できれば、本改善は t1 の目的・スコープ・技術選定に整合します。
