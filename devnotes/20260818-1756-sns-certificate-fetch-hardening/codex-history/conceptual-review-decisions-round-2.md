# 対応マトリクス: conceptual-review Round 2

## [Warning] 「TOCTOU を押さえる」は強すぎる (TLS は接続自体を防がない)

- 判断: 対応する
- 根拠: 指摘のとおり。再解決先の private IP への TCP 接続と TLS ClientHello は実際に発生する。
  TLS が制限するのはその先の HTTP 層のやりとりである。
- 対応内容: 「残る TOCTOU による HTTP 層での取得を、通常の CA 検証が有効であることを
  前提に TLS が制限する。private IP への接続試行そのものは防がない」に書き換えた。

## [Warning] TLS 検証が無効化されない前提を機械で固定していない

- 判断: 対応する
- 根拠: `withoutVerifying()` や `verify => false` が入ると補完防御が無音で消える。
  同じ「無音で消える」性質の前提は本リポジトリでも機械固定するのが作法である。
- 対応内容: 新設する契約テストの検査項目に「取得口が `withoutVerifying()` /
  `verify` の無効化を持たないこと」を追加した (字句走査 + 負例)。
  字句走査の限界 (変数経由・オプション配列の動的組み立て) は保証範囲外として書く。

## [Warning] 「読み取りの時間上限により実メモリが有界」は成立しない

- 判断: 対応する
- 根拠: 指摘のとおり。帯域が大きければ時間内に受信できるバイト数は制限されない。
- 対応内容: 「メモリ使用量に明示的な上界は設けない。信頼する取得先を SNS のホストへ
  限定し、短い時間予算で運用上のリスクを下げるだけである」に書き換えた。
  逐次読み出し機構は本スコープでは作らない (上界を主張しないため必要にならない)。

## [Warning] 「503 なので抑止漏れにはならない」は断定が強すぎる

- 判断: 対応する
- 根拠: SNS の再送には回数と期間の上限がある。
- 対応内容: 「503 により即時の恒久ドロップを避け、SNS の再送期間内に競合が解消すれば
  回復できる。再送期間を超えて競合が続けば最終的な配送断念はありうる」に書き換えた。

## [Warning] `SnsCertificateUrl::fromString()` の失敗の表し方

- 判断: 対応する (元設計の意図を明文化)
- 対応内容: `fromString(string $url): self` が失敗時に
  `SnsSignatureInvalidException` (403 へ写像される既存の例外) を投げる、と明記した。
  nullable も汎用例外も使わない。

## [Warning] `openssl_x509_read()` の戻り値の扱い

- 判断: 対応する
- 対応内容: PEM 検査を専用の private メソッドへ閉じ込め、戻り値は `false` との比較だけに使い、
  `OpenSSLCertificate` をキャッシュ・戻り値・DTO のいずれにも出さない (境界は常に `string`)
  ことを明記した。詳細設計のコードでも同じ形にする。
