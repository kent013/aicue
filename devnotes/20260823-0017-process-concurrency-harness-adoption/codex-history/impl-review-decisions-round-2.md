# 対応マトリクス: impl-review Round 2

Codex 全体判定: **CHANGES_REQUESTED** ([Critical] 0 / [Warning] 4)

## [Warning] 秘密の伏せ字が stderr 経路にしか適用されていない

- 判断: **対応する**（指摘の方向をさらに広げる）
- 根拠: 妥当である。子は untrusted なので、**子が書いた文字列は例外メッセージのどこにでも入りうる**
  (ready / entered の payload、観測 JSON の各項目、未知の完成合図の**名前**、stderr)。
  生成箇所ごとに伏せ字を撒く形では必ず撒き漏らす。
- 対応内容: **生成箇所ごとの伏せ字をやめ、唯一の出口 (`run()`) に choke point を 1 つ置いた**
  (`redactedForDiagnostics()`)。ここで本ハーネスの 2 型
  (`ConcurrencyProtocolException` / `BarrierTimeoutException`) のメッセージを伏せ字にし、
  型は保つ。`abortCondition()` / exit code 検査に撒いていた `redactSecrets()` は撤去した
  (二重機構を並走させない)。
  - previous は引き継がない (previous 側のメッセージまでは作り直せないので、
    伏せ字にできない文字列を連鎖へ残すほうが危ない)。回収失敗時の `reapFailed()` は
    **伏せ字済みの実体**を previous に持つ。
  - 保証しないもの (完全一致でしか伏せられない = 切り詰められた断片は子側で出さないことで閉じる) は
    docblock に明記した。
- 追加テスト: 群 4-43 を **(a) stderr 経路**と **(b) 合図の中身の経路**の 2 本立てにした。

## [Warning] `uri` の新しい受理条件に負例がない

- 判断: **対応する**
- 根拠: 実装だけ入れて負例が無いと、照合を消しても緑のままである (検出力が裏取りされていない)。
- 対応内容: 群 4-45 を新設。`request_hash` は親の期待値と一致させたまま **uri だけをすり替えた**
  観測を返す偽の子を差し、受理条件で拒否されることを固定した。

## [Warning] symlink を辿らない削除にも回帰テストがない

- 判断: **対応する**
- 根拠: 同上。`is_link()` の分岐を消しても緑のままだった。
- 対応内容: 群 4-46 を新設。workspace の外に sentinel を置いたディレクトリを作り、
  workspace 内から symlink を張って回収させ、**外側が無傷である**ことを固定した。
  - 実装時に踏んだ落とし穴を記録する: 最初は 2 子とも同じパスへ symlink を張る台本にしていたため、
    2 本目の `symlink()` が失敗して**台本側が例外を投げ**、回収の途中で抜けて
    workspace が残る別の分岐になっていた。張るのは 1 子だけにした。

## [Warning] sentinel 検査が既知の秘密 5 種のうち 3 種しか検証していない

- 判断: **対応する**
- 根拠: `CIPHERSWEET_KEY` / `DB_PASSWORD` を `$secrets` から消しても緑のままだった。
  実環境では `DB_PASSWORD` が空のこともあり、そのままでは検査できない。
- 対応内容: 群 4-43 で **config を sentinel へ差し替えてから**走らせ、
  5 種すべてが伏せ字になることを固定した (偽の子しか使わないので実プロセスへは 1 バイトも渡らない)。
