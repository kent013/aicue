## 施策 4

### [Critical] 停止確認不能時に workspace を残すと**秘密が残留する**
- 判断: **対応する**
- 根拠: **私の Round 3 の修正が新しい穴を作っていた。** 指摘のとおり、
  workspace には親の `APP_KEY` / `CIPHERSWEET_KEY` / DB password / plain API key / request body が
  ある。0700 / 0600 でも「長期間ディスクに残す」前提にはできないし、
  リスク欄の「`finally` で必ず削除」とも矛盾していた。
  **秘密と診断材料を同じ残置方針にしてはいけない**という指摘は正しい。
- 対応内容: 片付けを**2 系統に分けた**:
  1. **秘密（env ファイル / 入力ファイル）は回収の成否にかかわらず `finally` で必ず `unlink` する。**
     子がまだ読んでいなければ危険な接続を未然に防げるし、読んでいてもディスクに残さない効果がある
  2. **workspace ディレクトリ全体の削除は「全子の停止を確認できたとき」だけ**にする
  3. 診断用に残すのは**秘密を含まないもの**だけ（`signals/` の合図・child ID・終了状態・
     秘密を除いた `stderr`）
  4. 秘密の `unlink` に失敗したら、**そのパスを明示したセキュリティ例外**にする（黙って通さない）
  5. 残置するディレクトリの mode は引き続き **0700** を検査する

### [Warning] 「全子をまとめて poll」の実装契約が曖昧（順番に長い `waitFor()` を呼ぶと逐次に戻る）
- 判断: **対応する**
- 根拠: そのとおり。フェーズ単位と書いても、実装が「子ごとに残り時間いっぱいの
  blocking wait」なら逐次と同じになる。
- 対応内容: 実装契約を明記した — **reap の各フェーズは単一ループで全子の `isRunning()` を
  短い間隔（ポーリング）で確認する**。個々の子へ残り時間いっぱいの blocking wait を
  順番に行わない（`waitFor()` はフェーズの poll ループの中では使わない）。

## 施策 1

### [Warning] `link()` の失敗をすべて `duplicateSignal()` と分類している
- 判断: **対応する**
- 根拠: そのとおり。権限・I/O 障害・hard link 非対応でも `link()` は失敗するので、
  誤分類すると「二重送信を検出した」という嘘の診断が出る。
- 対応内容: 失敗後に **target の存在で分類**する —
  存在すれば `duplicateSignal()`、存在しなければ `signalNotPlaced()`。
  どちらの場合も一時ファイルは `finally` で削除する。
  施策 7 に**両方の負例**（二重配置 / 一般的な配置失敗）を置く。

### [Warning] 文書が旧方式（`rename()`）のまま残っている箇所がある
- 判断: **対応する**
- 根拠: 規律の数（6 点 vs docblock 7 点）、リスク欄の「`rename()` が同一 FS 内」、
  設計冒頭の「一時ファイルから rename」が旧方式のままだった。
- 対応内容: **`link()` に統一**し、規律を **7 点**へ揃え、
  保証範囲を「**同一 filesystem 上で hard link を作れることが前提**」と書き直した。

## 施策 7

### [Critical] 秘密残留対策に対応する失敗経路テストが無い
- 判断: **対応する**
- 対応内容: 群 4 へ 4 件追加した:
  - KILL 後も停止確認できないとき、**workspace 全体は残る**
  - そのとき **env ファイルと入力ファイルは削除されている**
  - `signals/` など**非秘密の診断材料は残る**
  - **秘密ファイルの `unlink` 失敗は黙って通らない**（パスを明示した例外になる）

### [Warning] `link()` の一般的な配置失敗が `duplicateSignal()` と誤分類されない検査
- 判断: **対応する**
- 対応内容: 群 1 へ「target が存在しない状態での配置失敗は `signalNotPlaced()` になる
  （`duplicateSignal()` にならない）」を追加した。
