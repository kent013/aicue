# 対応マトリクス: conceptual-review Round 1

## [Critical] barrier の ready 合図が子ごとに区別されていない
- 判断: **対応する**
- 根拠: 指摘のとおり。共有 ready では「片方だけ準備できた状態で go を出す」ことが起こり、
  正典の最重要前提 (全員の準備を確認してから同一の合図で解き放つ) が壊れる。
  この壊れ方は**テストが緑のまま**進むので致命的である。
- 対応内容: 合図ファイルを子ごとに分ける (`ready-{childId}` / `out-{childId}.json`)。
  親は**全員ぶんの ready を確認してから** go を 1 つだけ作る。
  ready の中身に nonce と childId を書き、親が起動時に割り当てた値と**一致検証**する
  (家系の aigenba が持つ「子の自己申告と起動時の割り当てが食い違ったら観測を通さない」検査と同型)。
  合図ファイルは一時ファイルを作ってから rename する (書きかけを相手に見せない。aigenba の規律)。

## [Critical] 「本当に重なった」保証が無い (409 が偶然に依存する)
- 判断: **対応する (ただし Codex 案とは別解を採る)**
- 根拠: 指摘の中身は正しい。共通 go で解き放っても、勝者が本処理を終えてから敗者が到着すれば
  敗者は `replay` (200) を受け、**並行していないのに緑**になる。これは本設計が埋めようとしている
  穴そのものなので放置できない。
  一方 Codex の修正案 (「テスト支援の注入点を用意して勝者を待たせる」) は**アプリコードへの
  注入点追加**を含意する読み方ができ、家系の先行 2 例が守った「本番コードは 1 バイトも変更しない」を
  崩す危険がある。同じ効果を**アプリコードを一切触らずに**得られる形があるので、そちらを採る。
- 対応内容: **重なりを「祈る」のではなく「構成する」**。
  probe route の**ハンドラは probe スクリプト (テスト側コード) が登録するもの**であり、
  アプリコードではない。そこで
  1. ハンドラに入った子は `entered-{childId}` を置き、`release` 合図を締切つきで待つ
  2. 親は `entered-*` を 1 つ観測したら、**もう一方の子が終了する (= その out が出る) まで待つ**
  3. その後に `release` を置き、勝者を先へ進める
  という 3 段にする。これにより敗者は**勝者の claim 行が `processing` のまま在る間に必ず claim へ到達する**
  ため、`in_progress` (409) の観測が偶然ではなく**構成的に決定的**になる。
  併せて「重なっていない」形を fail-closed にする:
  `entered-*` が 1 つも出なければ締切超過で例外 (どちらも本処理へ入っていない = 主張が成立していない)。
  さらに `entered-*` が 2 つ出たら親は締切を待たずに**即座に「二重実行を検出」で中断**する
  (これが探している退行そのものなので、締切超過という紛らわしい形で出さない)。

## [Warning] 要素 (3) の証明が「array を渡した」だけで弱い
- 判断: **対応する**
- 根拠: aicue の既存 `FakeWiringProbeRunner` が既に「起動側が載せる分」と「子が実際に受け取った分」を
  突き合わせる作法を持っており、そちらに合わせるのが自然。
- 対応内容: 子が**解決済み**の cache store の具象クラス名と driver 名を JSON で申告し、
  親が 2 子ぶんについて `Illuminate\Cache\ArrayStore` であることを主張する。
  「宣言」と「実測」の両方が揃って初めて要素 (3) を満たしたとみなす。

## [Warning] 締切超過時の子の停止・回収・一時ファイル削除が未明文
- 判断: **対応する**
- 根拠: paratest 下で子が残ると接続とロックが残り、以後を汚染する。実害が具体的。
- 対応内容: 回収規約を明文化する (SIGTERM → 猶予 → SIGKILL → 必ず wait して終了コードを取る /
  runner が握った handle を残さない / 一時ディレクトリの削除は `finally`)。
  失敗経路の単体検査に「回収が実行される」ことを含める。

## [Critical] `.env` 遮断と DB 座標固定の具体機構が未記載
- 判断: **対応する**
- 根拠: 指摘のとおり `env -i` は親のプロセス環境を消すだけで、子の Laravel が
  チェックアウトの `.env` を読むことは止められない。また DB_DATABASE / DB_URL だけでは
  host / port / user / password / connection の経路が残る。
- 対応内容: aicue に**既に実在する機構**を明示的に踏襲する形で書き直す。
  `tests/Support/ExternalFakes/fake-wiring-probe.php` は bootstrap の**前**に
  `$app->useEnvironmentPath($dir)` / `$app->loadEnvironmentFrom($file)` を呼び、
  設定の出所を専用の一時 env ファイル 1 つへ固定している。同じ順序を本 probe でも使う。
  固定する DB 座標は `config/database.php` の pgsql 接続が読む**全キー**とする:
  `DB_CONNECTION` / `DB_URL`(空文字固定) / `DB_HOST` / `DB_PORT` / `DB_DATABASE` /
  `DB_USERNAME` / `DB_PASSWORD` / `DB_CHARSET` / `DB_SSLMODE`。
  値の出所は親の**実行時に解決した実接続設定** (`config('database.connections.pgsql')`) とし、
  env の再読解ではない (親と子が同じ DB を見ることが構造的に保証される)。
  検査段は 3 か所: 親 (起動前) / 子 (bootstrap 前) / 子 (bootstrap 後の実効設定の申告と親側突合)。

## [Warning] `OutOfTransactionFixtures` の既定接続差替えの副作用
- 判断: **対応する**
- 根拠: 接続キャッシュ・RefreshDatabase の transaction との相互作用は実際に起こりうる。
- 対応内容: 別名接続は「既定接続設定の複製」として動的登録し、
  使用前に `DB::purge($alias)`、使用後も `finally` で `DB::disconnect($alias)` + `DB::purge($alias)`、
  既定接続名は保存して `finally` で必ず復元する、と明記する。
  なお「モデル/Factory 単位で接続を指定する標準経路を優先せよ」は**採らない** —
  Laravel の Factory には接続を指定する第一級 API が無く、
  検体は複数モデル (組織 / 利用者 / API キー) にまたがるため、閉じた区間で既定を差し替えて
  finally で戻す形のほうが漏れが少ない。家系の先行 2 例も同じ形を採っている。

## [Critical] 接続・ロック枯渇への対策が不足
- 判断: **対応する (一部は前提の明確化で解消)**
- 根拠: 家系 (motivation) の一次情報がある以上、無視できない。
- 対応内容: (a) 強制回収の必須化は上記のとおり対応。
  (b) 「paratest worker ごとに走るのか」を明確化する — **paratest はテストを worker へ分配するので、
  本テストは実行全体で 1 回、1 worker でのみ走る**。したがって同時に増える接続は
  子 2 本 × 1 + 親の別名接続 1 = **最大 3 本**であり、恒常的な上限圧迫にはならない。
  (c) motivation が踏んだ形 (テストごとのスキーマ再作成による排他ロック枯渇) は、
  本設計が**スキーマを作り直さない** (既存 worker DB へ行を足すだけ) ため構造的に起こらない。
  この 3 点を制約節に書く。

## [Warning] 型安全性: probe JSON は外部入力である
- 判断: **対応する**
- 根拠: `phpstan.neon` が `tests` を解析しない以上、型の保証は fail-closed factory と検査で作るしかない。
- 対応内容: `ConcurrentProbeObservation::fromDecodedJson(mixed $value): self` を fail-closed とし、
  必須キー・厳密なスカラー型・childId・nonce・HTTP status・ハンドラ実行回数・cache 観測を全検証、
  欠損・型違い・未知キーは例外にする。`phpstan.neon` を変更しないことの根拠も併記する。
