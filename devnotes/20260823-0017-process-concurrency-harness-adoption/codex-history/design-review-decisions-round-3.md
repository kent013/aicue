## 施策 1

### [Warning] `SignalName::make()` が public で `ready-c` も作れる（「8 通りだけ」が成立しない）
- 判断: **対応する**
- 根拠: そのとおり。`/\A[a-z]\z/` は 26 文字を許すので、説明と実体が食い違っていた。
- 対応内容: child ID を **`['a', 'b']` の 2 つに限定**した（`SignalName::CHILD_IDS`）。
  入口も 1 つに絞る — `SignalName::make()` を**唯一の生成口**とし、
  `ProcessBarrier::name()` は**廃止**する（二重入口を残さない）。
  これで生成できるのは実際に **8 通りだけ**になり、説明と実体が一致する。
  施策 7 に「`ready-c` を作れない」負例を追加した。

### [Warning] 同じ名前への 2 回目の `rename()` が既存を上書きし、二重送信を隠す
- 判断: **対応する**
- 根拠: POSIX の `rename()` は上書きする。ready や out の二重送信が**黙って隠れる**。
- 対応内容: 配置を `link()` + `unlink()` の 2 段に変える —
  `link($temporary, $target)` は**target が既に在れば失敗する**ので、
  TOCTOU のある `is_file()` 判定を挟まずに二重配置を弾ける
  （成功したら `unlink($temporary)`）。同一 FS 内なので hard link が使える。
  失敗時は `ConcurrencyProtocolException::duplicateSignal()` にする。
  施策 7 に負例を追加した。

## 施策 4

### [Critical] 回収予算 2 秒を 2 子へどう配分するか未定義（1 子目が使い切ると 2 子目を回収できない）
- 判断: **対応する**
- 根拠: 決定的な指摘。「子ごとに TERM → wait 1 秒 → KILL → wait 残り」を逐次でやると、
  1 子目で予算を使い切って 2 子目が回収されない。
  「全子の回収を最大 2 秒で完遂する」という契約が**子数に依存して破れる**設計だった。
- 対応内容: 回収を**子単位ではなくフェーズ単位**に変えた（子数にかかわらず最大 2 秒）:
  1. 生存する**全子へ TERM** を送る
  2. 単一の reap deadline のうち**最大 1 秒、全子をまとめて poll** する
  3. まだ生存する**全子へ KILL** を送る
  4. reap deadline まで**全子をまとめて poll** する
  5. 終了を確認できない子があれば、**その child ID を含む回収失敗例外**にする
  施策 7 に「a は TERM で終わり、b は KILL が要る」混在ケースを追加した。

### [Warning] KILL 後も終了を確認できないとき workspace を消してよいかが未定義
- 判断: **対応する**
- 根拠: まだ動いている子が削除済みパスへ書き込む可能性がある。
- 対応内容: **全子の停止を確認できたときだけ workspace を削除する**。
  確認できなければ workspace を**診断用に残し**、child ID と残置パスを添えて例外にする
  （テストは赤くなるので放置されない）。
  併せて表現も狭めた — 「必ず回収を完遂する」ではなく
  **「bounded な回収操作を必ず要求し、停止を確認できなければ失敗させる」**。

### [Warning] env キー検査は「許可外が無い」だけでなく必須キーとの完全一致が要る
- 判断: **対応する**
- 根拠: 必須の DB キーが**欠落**しても親側で止まらなかった（欠落は子の `.env` 読み込みで
  埋まりうるので、まさに塞ぎたい形である）。
- 対応内容: `$values` のキー集合と `ALLOWED_ENV_FILE_KEYS` を**ソート後に完全一致**で比較する。

## 施策 5

### [Warning] 自前 parser との round-trip だけでは phpdotenv が同じ値を読むと言えない
- 判断: **対応する**
- 根拠: そのとおり。二重解釈の一致は**両方の parser に通して**初めて言える。
  段 9 の実プロセス検査は正常な現在値しか通らないので、`$` や `${NAME}` の裏取りにならない。
- 対応内容: 施策 7 群 2 の正例を**二重にした** — `encodeLine()` の出力を
  (a) 自前 parser と (b) **プロジェクトが実際に使っている phpdotenv の parser** の
  両方へ通し、**双方が元の値を返す**ことを同一プロセスの単体検査で固定する。
  対象値: `$` / `${NAME}` / `\` / `"` / `#` / 空文字 / 前後空白。

### [Warning] 「作成時点から 0600」は不正確（`fopen('x')` から `chmod()` まで umask 依存）
- 判断: **対応する**
- 根拠: 正確でない表現だった。秘密はまだ書いていないので漏洩ではないが、書き方が誤り。
- 対応内容: 表現を **「秘密を書き込む**前に** 0600 へ変更する」**へ直した。
  加えて、作成時の mode も 0600 にするため
  **`umask(0o077)` を一時的に設定し `finally` で必ず復元する**手順を足した。

## 施策 7

### [Critical] 回収テスト #34・#35 では 2 子への予算配分問題を捕まえられない
- 判断: **対応する**
- 対応内容: 混在ケースを追加した —
  「**a は TERM 後すぐ終了 / b は TERM では終わらず KILL が必要**。
  TERM は a と b の**両方**へ、KILL は **b だけ**へ送られる。
  全体の回収時間が 2 秒以内で、b には KILL 後の `waitFor()` も要求される」。
  これがフェーズ単位の回収でなければ通らない検査になる。

### [Warning] 二重配置を拒否するなら負例も置く
- 判断: **対応する**
- 対応内容: 群 1 へ「同じ合図を 2 回置こうとすると `duplicateSignal()` で失敗する」を追加した。
