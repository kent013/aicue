# 対応マトリクス: conceptual-review Round 2

## [Critical] 解決済み cache store の具象クラス観測が aicue のキャッシュ不変条件と衝突する
- 判断: **対応する (指摘は正しい。実読で裏を取った)**
- 根拠: `tests/Architecture/CachePayloadPlainDataGateTest.php` を実読したところ、指摘のとおり
  `getStore()` は「受け皿 (Repository) の境界を迂回する書き方」として
  `extend` / `setStore` / `tags` / `macro` などと同列に**静的層で deny-by-default** に置かれており、
  実行時層の自己テストだけが名指しの目録へ exact-fit で pin されている。
  ここで使えば静的 gate 違反か目録変更のどちらかになり、
  「最小追従」「ハーネスを見張る gate は増やさない」という本設計の方針と正面から衝突する。
  **見落としていた実在の衝突**であり、Codex の指摘がなければ実装段で目録を触る羽目になっていた。
- 対応内容: 具象クラスの観測をやめ、子は `config('cache.default')` と
  `CacheManager::getDefaultDriver()` の 2 つを申告する形へ変更した。
  あわせて**境界を明記**した — 「標準 Laravel の `array` driver が `ArrayStore` を生成すること」は
  フレームワークの責務として扱い、本テストでは具象クラスまで再検証しない。
  本テストが主張するのは「子の既定 cache driver が `array` = プロセス間で共有される
  キャッシュロックの土台が存在しない」ところまで、と書いた。

## [Warning] `release` を置く条件が「out が出た」だけになっている
- 判断: **対応する**
- 根拠: 「出てきたから release して、あとから赤くする」形は結果的に赤にはなるが、
  プロトコルの証拠が弱い。決定的な重なりを**構成する**という本設計の趣旨からすると、
  release の前提が満たされたことを release の条件にするのが筋である。
- 対応内容: release の条件を 5 項目の合議として明記した
  (entered がちょうど 1 子 / 反対側の out が原子的に完成 / nonce と childId の一致 /
  HTTP status が 409 / ハンドラ実行回数が 0)。1 つでも欠けたら release せずその場で失敗させる。

## [Warning] `DB_URL` 主体で接続している場合、設定配列の個別キーは実効座標とは限らない
- 判断: **対応する (提案された 2 案のうち前者 = fail-fast を採る)**
- 根拠: 指摘のとおり。URL 主体の設定では host / port / database が実効座標を表さないため、
  子が親と**別の DB** を見る形になりうる。開発 DB 保護の話なので黙って踏めない。
  一方「URL を正規化して実効座標へ展開する仕組み」を自前で持つのはオーバーエンジニアリングである。
- 対応内容: 前提検査を足した — 親の `config('database.connections.pgsql.url')` が空でなければ
  **子を起こさずに例外**。現行の `phpunit.xml` は `DB_URL` を `<server force="true" value=""/>` で
  空に固定しているので前提は成立しており、**成立しなくなった日に赤くなる**形になる。

## [Warning] 「同時最大 3 接続」は過少
- 判断: **対応する**
- 根拠: 親の既定接続 (`RefreshDatabase` の transaction が居る接続) を数え落としていた。単純な誤り。
- 対応内容: **最大 4 本**へ訂正した (親の既定接続 1 + 親の別名接続 1 + 子 2)。
  「子起動前に別名接続を切れば 3 と主張できる」案は採らない — 片付けと裏取りで別名接続を
  使い続けるほうが単純で、4 本は問題になる水準ではないため。

## [Warning] 「子を起こさない単体検査」では SIGTERM/SIGKILL/wait の実効性は証明できない
- 判断: **対応する**
- 根拠: 指摘のとおり。実プロセスの kill を試すテストを足すと正典の要素 (6) に反するので、
  **主張の範囲を正確に書く**のが正しい解決である。
- 対応内容: runner はプロセスを直に触らず**抽象越し**に扱うことにし、
  失敗経路の検査が主張するのは「runner がその抽象へ停止・kill・wait を必ず要求すること」までだと明記した。
  実 OS プロセスに対する SIGKILL の実効性は主張しない、と境界も書いた。

## [Warning] PHPStan level 10 は tests を解析しないので「静的に型安全」とは言えない
- 判断: **対応する**

## 背景・課題

### 正典が言っていること

正典 (spirux) の主張は 1 行で言うと **「同時に来ても 1 回だけ、はふつうのテストでは原理的に証明できない」**である。

1 つのプロセスの中で順番に呼ぶテストでは、テスト用のトランザクションもアプリ側のロックも
共有されてしまうため、DB の一意制約や排他が本当に効いているかは確かめられない。
通っていても「ロックが効いていたから」かもしれないし「そもそも同時ではなかった」かもしれない。

そこで正典は、フレームワークを自前で起こす小さな実行スクリプトを**別プロセスで 2 本**立て、
両方が「準備できた」と合図したところで親が同時に解き放ち、業務処理がちょうど 1 回だけ走ることを
実経路で確かめる。さらに**守りたい層以外をわざと無効化してから測る**ので、
「アプリ側のロックが効かなくても DB 側だけで二重にならない」ところまで言い切れる。

### 正典 v1 の不変条件 (boundary の 6 要素) — 全列挙

| # | 正典が要求すること |
|---|---|
| (1) | フレームワークを自前で起動し、**引数で受けた ready / go ファイル**で親と同期してから対象処理を叩く実行スクリプトを持つ |
| (2) | 子プロセスから見えるよう、**フィクスチャをテストの transaction の外** (別名の独立接続) に作り、**末尾で明示的に片付ける** |
| (3) | **守りたい層以外を意図的に無効化してから測る** — 子のキャッシュ store を配列固定にし、プロセス間でアプリ側ロックが共有されない状態を作ってから DB 層だけで守れることを確かめる |
| (4) | 合図待ちのループで**ファイル状態のキャッシュを毎回捨てる** (捨てないと合図に気付くのが遅れ、2 本の実行が重ならず並行テストの意味が消える) |
| (5) | 待ちには**締切**を置き、超えたら例外にする |
| (6) | 重いので**実プロセス版は 1 本に絞り**、細かい分岐 (実行中 / 再生 / 順序) は同一プロセスのテストへ回す |

正典が **含まないと明記している**もの (= 本設計のスコープ外の根拠):

- 何を並行で守るかという個別の不変条件 (冪等キー / ジョブ重複排除 / チケット確保 などが持つ。
  ハーネスはそれらを**証明する道具**であって主張ではない)
- **同一プロセス内の並行テスト** (家系に多数あるが、DB の一意制約や advisory lock の実効性は
  証明できない**別層**)
- テスト実行を直列化して衝突を避ける仕組み (`global-test-lock` — こちらは逆に**意図的に衝突させる**)
- テストレーンの構成 (`pest-lane-wiring` / `php-test-pgsql-lane`)

### 依頼文の triage 要約と正典の食い違い (先に潰す)

本設計の依頼文は正典を「**同一プロセス内**の並行実行を決定的に検証するテストハーネス」と要約していたが、
これは正典と逆である。正典の boundary は「同一プロセス内の並行テスト」を**含まないものとして名指しで除外**している。
したがって本設計は**正典本文 (実プロセス 2 本 + barrier 同期) に従う**。

同じ理由で、依頼文にあった「既存の同一プロセス並行テスト 2 本を標準形へ載せ替える」も採らない。
正典の要素 (6) は「細かい分岐は同一プロセスのテストへ回す」と**明示的に同一プロセス側の存続を前提**にしている。
既存 2 本は**そのまま残すのが正典準拠**であり、載せ替えは正典が要求しない一般化にあたる。

## 改善アイデア

**正典 v1 の 6 要素を満たす最小のハーネスを `tests/Support/Concurrency/` に新設し、
それを使う実プロセス並行テストを「ちょうど 1 本」だけ載せる。**
証明対象は aicue が自分で「証明していない」と書いている冪等キーの実行前 claim とする。

### なぜ冪等キーを対象に選ぶか

1. 台帳の aicue セルが名指ししている (「冪等キーと課金の確保経路」)
2. 守られている実装が **「unique 制約が唯一の調停者」**と宣言している = 正典の命題とぴたり一致する
3. 既存テストが**自分で穴を宣言している** = 埋めた/埋めていないの判定が主観にならない
4. アプリコードを 1 バイトも変えずに叩ける (middleware は既存の production 経路)

対抗馬だった「org 同時 preview 上限」(D7) は **行ロックによる直列化**の主張であり、
一意制約の実効性という正典の中心命題からは 1 段遠い。要素 (6) は 1 本に絞れと言うので、選ぶのは 1 つだけである。

### 何を証明するか (テストの主張文)

> 「準備完了を**全員ぶん**確認してから**同一の合図で同時に解き放った実プロセス 2 本**が、
> 同一 actor・同一 route・同一 Idempotency-Key・同一 body の書き込み要求を送ったとき、
> `IdempotentRequest` middleware が**本処理を通したのはちょうど 1 本**であり、
> もう 1 本は本処理を実行せずに `in_progress` (409) で弾かれる。
> **プロセス間で共有されるアプリ側ロックは 1 つも無い**状態で、である。」

主張はここまでに**狭める**。「撮影ジョブやレンダジョブが二重に走らない」は
この middleware 契約から導かれる**帰結**であって、本テストが直接測るものではない。

**勝者の判定は行の最終状態ではなく一次観測で行う** (正典・テンプレートの作法):
各子が自プロセス内で数えた「本処理ハンドラの実行回数」と受け取った HTTP ステータスを
JSON で親へ返し、親はその**合計が 1** であることを主張する。DB の行の状態は**裏取り**に置く。
(行だけを見ると「2 本とも実行したが後着が上書きした」形と区別がつかない)

### 「本当に重なった」を祈らずに構成する (本設計の中核)

同一の go で解き放つだけでは足りない。勝者が本処理を終えてから敗者が到着すると、
敗者は 409 ではなく **`replay` (200)** を受け取り、**並行していないのに緑**になる。
これは本設計が埋めようとしている穴そのものなので、偶然に委ねない。

鍵は **probe route のハンドラが probe スクリプト (テスト側コード) の持ち物である**点にある。
アプリコードを 1 バイトも触らずに、ハンドラ内で待たせることができる。

| 段 | 誰が | 何をする |
|---|---|---|
| 1 | 子 | 起動・準備が済んだら `ready-{childId}` を置き、`go` を待つ |
| 2 | 親 | **全員ぶんの ready** を確認してから `go` を 1 つだけ置く |
| 3 | 子 | 実 middleware 列を通して要求を投げる |
| 4 | 勝者 | ハンドラに入った瞬間に `entered-{childId}` を置き、`release` を締切つきで待つ |
| 5 | 親 | `entered-*` を観測したら、**もう一方の子の `out` が出る**まで待ち、その中身を検査する |
| 6 | 親 | 検査を通ったら `release` を置く。勝者はハンドラを完了し 2xx を確定させる |

これで敗者は**勝者の claim 行が `processing` のまま在る間に必ず claim へ到達する**。
409 の観測は偶然ではなく**構成的に決定的**になる。

**`release` を置く条件は次の合議である** (どれか 1 つでも欠けたら release せず、その場で失敗させる)。
「出てきたから release して、あとで赤くする」形にしない — プロトコルの証拠が弱くなるからである。

1. `entered-*` が**ちょうど 1 子**ぶん
2. 反対側の `out` が**原子的に完成**している (子は一時ファイルへ書いてから rename する)
3. その `out` の **nonce と childId が親の割り当てと一致**する
4. その `out` の **HTTP status が 409**
5. その `out` の**ハンドラ実行回数が 0**

fail-closed の設計 (「実は並行していないのに緑」を塞ぐ):

- `entered-*` が締切内に **1 つも出ない** → どちらも本処理へ入っていない = 主張が成立していない → 例外
- `entered-*` が **2 つ出た** → 親は締切を待たず**即座に「二重実行を検出」で中断**する
  (探している退行そのものなので、締切超過という紛らわしい形で出さない)
- 子が先に異常終了したら、親は締切を待たずに中断する

### 守りたい層以外の無効化 (要素 (3)) — aicue での具体形

| 層 | 子プロセスでの扱い | 狙い |
|---|---|---|
| キャッシュ (アプリ側ロックの土台) | `CACHE_STORE=array` に固定し、子が **`config('cache.default')` と `CacheManager::getDefaultDriver()`** を JSON で申告 | プロセス間で共有されるロックが存在しないことを観測で示す |
| キュー | `QUEUE_CONNECTION=sync` | 本処理の副作用が子プロセス内で完結する |
| セッション | `SESSION_DRIVER=array` | 同上 |

配列固定を「渡した」だけでなく**子が申告し親が突き合わせる**のは、
`FakeWiringProbeRunner` が既に採っている作法 (「起動側が載せる分」と「子が実際に受け取った分」を
両方見て初めて退行が映る) の踏襲である。
親は 2 子ぶんの申告が**ともに `array`** であることを主張する。
**宣言 (渡した env) と実測 (子が解決した driver) の両方が揃って初めて要素 (3) を満たした**とみなす。

> **`getStore()` は使わない (aicue 固有の制約)。**
> 解決済み store の**具象クラス**を取る通常手段は `Repository::getStore()` だが、
> aicue はキャッシュ payload の 2 層強制 (AGENTS.md セキュリティ不変条件 11 / 家系の裁定 AG-151) により
> `getStore()` を**受け皿の境界を迂回する書き方**として通常経路で 0 件に固定し、
> 実行時層の自己テストだけを名指しの目録へ exact-fit で pin している。
> ここで使うと (a) 静的 gate に違反するか (b) 目録を変更して走査器・gate 側の追随まで発火させるかの
> どちらかになり、「最小追従」「ハーネスを見張る gate は増やさない」という本設計の方針と衝突する。
>
> **境界の明記**: 「標準 Laravel の `array` driver が `ArrayStore` を生成すること」は
> **フレームワークの責務**として扱い、本テストでは具象クラスまで再検証しない。
> 本テストが主張するのは「子の既定 cache driver が `array` である = プロセス間で共有される
> キャッシュロックの土台が存在しない」ところまでである。

### 既存資産の再利用 (先人の知恵を探せ)

正典の台帳は本 feature が `subprocess-boot-probe-harness` に **depends_on** すると書き、
aigenba/テンプレートはその「起動器の回収規約」を踏襲している。
aicue における相当物は **`tests/Support/ExternalFakes/FakeWiringProbeRunner.php`** であり、
以下の 6 点の回収規約が既に実装されている:

`env -i` で環境を作り直す / 専用の一時 env ファイル 1 つだけを設定の出所にする /
一時ディレクトリ 0700・env ファイル 0600 を起動前に検査して違えば子を起こさない /
締切つき実行 / 解釈できない子の出力は fail-closed で例外 / `finally` で必ず片付ける。

**新しい起動器はこの規約を明示的に踏襲する** (docblock で名指しする)。作法を 2 つに分岐させない。

### 開発 DB への到達遮断 (aicue 固有の最重要リスク)

`FakeWiringProbeRunner` は **DB に接続しない**観測なので DB 座標を子に渡していない。
本ハーネスの子は**逆に DB へ接続しなければならない**ため、遮断の設計を新規に持つ必要がある。
テンプレートが実装レビューで穴を 6 段まで塞いだ箇所であり、aicue でも最も慎重に設計する。

**`env -i` は親のプロセス環境を消すだけで、子の Laravel がチェックアウトの `.env` を読むことは止められない。**
遮断は「環境変数を消す」ではなく「**設定の出所を差し替える**」で作る。
その機構は aicue に**既に実在し実働している** — `tests/Support/ExternalFakes/fake-wiring-probe.php` は
bootstrap の**前**に `$app->useEnvironmentPath($dir)` / `$app->loadEnvironmentFrom($file)` を呼び、
設定の出所を専用の一時 env ファイル 1 つへ固定している。同じ順序を本 probe でも使う。

| 段 | 内容 |
|---|---|
| 1 | 親のプロセス環境を `env -i` で空にし、合図・出力・env ファイルの座標だけを載せる |
| 2 | 子は**bootstrap より前**に `useEnvironmentPath()` / `loadEnvironmentFrom()` で設定の出所を専用 env ファイル 1 つへ固定する (親のチェックアウトの `.env` / `.env.testing` は読ませない) |
| 3 | `config/database.php` の pgsql 接続が読む**全キー**を専用 env ファイルで固定する — `DB_CONNECTION` / `DB_URL` (**空文字で固定**。キーを消すと `.env` 読み込みで復活する。テンプレートが実装レビューで見つけた実在の穴) / `DB_HOST` / `DB_PORT` / `DB_DATABASE` / `DB_USERNAME` / `DB_PASSWORD` / `DB_CHARSET` / `DB_SSLMODE`。**値の出所は親が実行時に解決した実接続設定** (`config('database.connections.pgsql')`) であり env の再読解ではない (親と子が同じ DB を見ることが構造的に保証される) |
| 4 | 親は子を起こす**前**に、渡す DB 名を既存の単一点ガード `Tests\Support\Ci\TestDatabaseEnv::assertPgsqlTestDatabaseSafe()` (allowlist 一致 + dev denylist) へ通す。落ちたら**子を起こさない**。あわせて**親の実効 `url` が空であること**を前提検査する (下記) |
| 5 | 子は **bootstrap の前・provider 登録の前**に、読み込んだ env の値で**同じ判定をもう一度**通す (親を信用しない)。落ちたら DB へ触る provider が動く前に非ゼロで死ぬ |
| 6 | 子は bootstrap 後の**実効接続設定** (driver / host / port / database / username) を JSON で申告し、親が**自分が渡した値と一致するか突き合わせる** (「渡した分」と「実際に効いた分」の両方を見て初めて退行が映る) |
| 7 | `APP_CONFIG_CACHE` を一時ディレクトリ配下の**存在しない絶対パス**へ向け、共有の `bootstrap/cache` を作らない・消さない (並列実行と衝突しない) |
| 8 | 子は**マイグレーションを一切実行しない** (スキーマは親のレーンが用意済み)。`RefreshDatabase` も使わない |

### 前提検査: 親が `DB_URL` 主体で接続していないこと

段 3 は「親の設定配列の個別キーを子へ移す」形なので、
**親が実際には `url` 主体で接続している場合、設定配列の host / port / database は実効座標とは限らない**
(URL 解析の結果が優先されるため)。これを黙って踏むと、子が親と**別の DB** を見ることになりうる。

最小の解は**前提を検査して fail-fast すること**である (URL の正規化・展開の仕組みは持たない):

> 親の `config('database.connections.pgsql.url')` が空でなければ、
> **子を起こさずに例外**にする (「このハーネスは個別キー接続のレーンを前提にする」と明記)。

aicue の `phpunit.xml` は `DB_URL` を `<server force="true" value=""/>` で空に固定しているので、
現行レーンではこの前提は成立している。**成立しなくなった日に赤くなる**形にしておく。

### 子の回収規約 (締切超過時に何が起きるか)

`FakeWiringProbeRunner` の規約に、並行ならではの回収を足して明文化する:

1. 待ちの締切は**単調時計** (`hrtime`) で測る (壁時計は NTP 補正で戻りうる)
2. 締切超過・親側の中断条件成立のいずれでも、子へ **SIGTERM → 猶予 → SIGKILL** の順で停止をかけ、
   **必ず wait して終了コードを取る** (runner が握った handle を残さない)
3. 一時ディレクトリ (合図・出力・env ファイル) の削除は `finally` で必ず通る —
   締切超過・JSON 解釈失敗・`Process` の例外のいずれでも
4. これを検査可能にするため、runner は**プロセスを直に触らず抽象越しに扱う**。
   失敗経路の単体検査が主張するのは
   「**runner がその抽象に対して停止・kill・wait を必ず要求すること**」までであり、
   実 OS プロセスに対する SIGKILL の実効性までは主張しない
   (実プロセスを起こすテストを増やすと正典の要素 (6) に反するため、そこは踏み込まない)

### 検体の置き場 (要素 (2)) と後始末

`RefreshDatabase` の transaction の外に検体を作る仕組み (`OutOfTransactionFixtures`) を新設する:

- 既定接続の設定を**複製した別名接続**を動的に登録し、
  **閉じた区間だけ**既定接続をその別名へ差し替えて Factory を回す
  (テストデータは必ず Factory で生成する規約を守るため)
- その接続の**明示トランザクションで commit** する
- 接続キャッシュとの相互作用を避ける: 使用前に `DB::purge($alias)`、
  使用後は `finally` で**元の既定接続名を必ず復元**し、`DB::disconnect($alias)` + `DB::purge($alias)` する
- **片付けは呼び出し側の責任**と docblock に明記し、見本テストの末尾で冪等に削除する
  (子が **commit した** `idempotency_keys` 行も同じ経路で消す。
  `RefreshDatabase` の rollback では消えないので、放置すると同一 worker の後続テストへ漏れる)
- 片付けは `finally` で必ず通し、子が落ちても走る
- 親の主張の裏取り (DB の行の状態) も**この別名接続で読む** —
  既定接続は `RefreshDatabase` の transaction の中に居るので、
  どちらで読んでも同じであることに依存しない形にしておく

> **採らない案**: 「モデル / Factory 単位で接続を指定する Laravel 標準経路を優先する」。
> Laravel の Factory には接続を指定する第一級 API が無く、検体は複数モデル
> (組織 / 利用者 / API キー) にまたがる。閉じた区間で既定を差し替えて `finally` で戻すほうが
> 指定漏れが構造的に起きない。家系の先行 2 例も同じ形である。

## 期待効果

### 使命への貢献

AI-CUE の使命は「思考ゼロ・編集ゼロ」で現場作業者が標準化されたマニュアル動画を作れること。
その入口である REST API v1 の write 経路は `Idempotency-Key` を受け付けており、
**同じ要求が同時に 2 回届いても本処理が一度しか通らない**ことは、
現場の「思考ゼロ」を成立させる土台である (二重に通れば作業者へ二重の指示が出る)。
今それは**証明されていない主張**として立っている — 実装は「unique 制約が唯一の調停者」と宣言し、
テストは「真の並行 2 本は走らせていない」と宣言している。本設計はその宣言を実経路の証拠に変える。

> 本テストが直接測るのは **middleware が本処理を一度だけ通すこと**までである。
> 「撮影ジョブ / レンダジョブが二重に走らない」はそこから導かれる帰結であり、
> テストの主張文には書かない (測っていないものを主張しない)。

### 具体的な改善見込み

- `IdempotentRequest::claim()` の「unique 制約が唯一の調停者」という宣言が、**実プロセス 2 本の証拠**を持つ
- `IdempotencyConcurrentClaimTest` の「保証しないこと」宣言のうち、
  **claim の commit と別接続からの可視性**の 2 点が実測で埋まる (docblock も是正する)。
  **削るのは今回実測した範囲だけ**にする — 任意の production route や

- 以後、課金のチケット確保など**別の不変条件を実プロセスで裏取りしたくなったとき、道具が既にある**
  (道具は主張と独立、という正典の設計思想の恩恵)

## 制約・前提

- `RefreshDatabase` はグローバル適用。個別の `DatabaseTransactions` は使わない。
  本設計は RefreshDatabase を**外さない** — 検体だけを別名接続で transaction の外へ出す
- テストは `--parallel` (paratest) 実行。DB は worker ごとに `<base>_test_<token>` へ分離済みなので
  子が commit する行が別 worker を汚すことはない。子が使う DB 名は**親が実行時に解決した実効名**を渡す
- **paratest はテストを worker へ分配する**ので、本テストは実行全体で **1 回・1 worker でのみ**走る。
  この worker が同時に持つ接続は
  **親の既定接続 (`RefreshDatabase` の transaction) 1 + 親の別名接続 1 + 子 2 本 × 1 = 最大 4 本**である
  (親の既定接続を数え落とさない)。worker 数に比例して増えることはない
- `composer test` は global-test-lock 配下で走る (`scripts/run-test.sh`)。
  本テストは**意図的に衝突させる**側なので、ロックとは層が違い干渉しない
- PHPStan の解析対象は `app / config / database / routes` であり `tests` を含まない
  (`phpstan.neon`)。したがって**`phpstan.neon` は変更しない** —
  同ファイルは `docs/template-fingerprints.json` の共有パスかつ採用時債務にあり、
  触ると乖離台帳の突合 gate を巻き込む。触らないのが最小である。
  **その代わり、子の JSON は「外部入力」として扱う** — 型の保証は PHPStan ではなく
  `ConcurrentProbeObservation::fromDecodedJson()` の fail-closed 検証と、
  それ自体を固定する失敗経路の単体検査で作る
- 禁止する文 (`echo` 等) の走査は `tests/` 配下にも及ぶため、実行スクリプトの出力は
  `fwrite(STDOUT, …)` を使う (既存 `fake-wiring-probe.php` と同じ)
- 実プロセス版の所要時間は子 2 本で数秒を見込む (家系の実測: テンプレートで約 3 秒)。
  1 本に絞る限りレーン全体への影響は許容範囲

### 家系からの警告 (motivation セルの一次情報)

motivation の台帳セルは、**コミットを要する並行テストと並列 worker の組合せが
PostgreSQL の排他ロックスロットを枯渇させた**実測を記録し、
「**このハーネスを導入する前に効いてくる前提条件**」と書いている。

motivation が踏んだのは「**テストごとにスキーマを作り直す**ため 1 回の全表削除が
約 3,700 個の排他ロックを取り、2 worker で既定の 6,400 スロットを枯渇させる」という形である。
本設計は**スキーマを作り直さない** (既に用意済みの worker DB へ行を足して消すだけ) ので、
この形は構造的に起こらない。そのうえで予防として:

- 子が持つ接続を最小 (1 本 × 2) にし、親の別名接続も 1 本に留める (**同時最大 4 本**)
- 締切超過時に **SIGTERM → SIGKILL → wait** で必ず回収し、応答しない子の接続を残さない
- 本テストは 1 worker でしか走らないので、worker 数に比例した増加は起こらない
