# 対応マトリクス: conceptual-review Round 2

## [Critical] 解決済み cache store の具象クラス観測が aicue のキャッシュ不変条件と衝突する
- 判断: **対応する (指摘は正しい。実読で裏を取った)**
- 根拠: `tests/Architecture/CachePayloadPlainDataGateTest.php` を実読したところ、指摘のとおり
  `getStore()` は「受け皿 (Repository) の境界を迂回する書き方」として
  `extend` / `setStore` / `tags` / `macro` などと同列に**静的層で deny-by-default** に置かれており、
  実行時層の自己テストだけが名指しの目録へ exact-fit で pin されている。
  ここで使えば静的 gate 違反か目録変更のどちらかになり、
  「最小追従」「ハーネスを見張る gate は増やさない」という本設計の方針と正面から衝突する。
  **見落としていた実在の衝突**であり、Codex の指摘がなければ実装段で目録を触る羽目になっていた。
- 対応内容: 具象クラスの観測をやめ、子は `config('cache.default')` と
  `CacheManager::getDefaultDriver()` の 2 つを申告する形へ変更した。
  あわせて**境界を明記**した — 「標準 Laravel の `array` driver が `ArrayStore` を生成すること」は
  フレームワークの責務として扱い、本テストでは具象クラスまで再検証しない。
  本テストが主張するのは「子の既定 cache driver が `array` = プロセス間で共有される
  キャッシュロックの土台が存在しない」ところまで、と書いた。

## [Warning] `release` を置く条件が「out が出た」だけになっている
- 判断: **対応する**
- 根拠: 「出てきたから release して、あとから赤くする」形は結果的に赤にはなるが、
  プロトコルの証拠が弱い。決定的な重なりを**構成する**という本設計の趣旨からすると、
  release の前提が満たされたことを release の条件にするのが筋である。
- 対応内容: release の条件を 5 項目の合議として明記した
  (entered がちょうど 1 子 / 反対側の out が原子的に完成 / nonce と childId の一致 /
  HTTP status が 409 / ハンドラ実行回数が 0)。1 つでも欠けたら release せずその場で失敗させる。

## [Warning] `DB_URL` 主体で接続している場合、設定配列の個別キーは実効座標とは限らない
- 判断: **対応する (提案された 2 案のうち前者 = fail-fast を採る)**
- 根拠: 指摘のとおり。URL 主体の設定では host / port / database が実効座標を表さないため、
  子が親と**別の DB** を見る形になりうる。開発 DB 保護の話なので黙って踏めない。
  一方「URL を正規化して実効座標へ展開する仕組み」を自前で持つのはオーバーエンジニアリングである。
- 対応内容: 前提検査を足した — 親の `config('database.connections.pgsql.url')` が空でなければ
  **子を起こさずに例外**。現行の `phpunit.xml` は `DB_URL` を `<server force="true" value=""/>` で
  空に固定しているので前提は成立しており、**成立しなくなった日に赤くなる**形になる。

## [Warning] 「同時最大 3 接続」は過少
- 判断: **対応する**
- 根拠: 親の既定接続 (`RefreshDatabase` の transaction が居る接続) を数え落としていた。単純な誤り。
- 対応内容: **最大 4 本**へ訂正した (親の既定接続 1 + 親の別名接続 1 + 子 2)。
  「子起動前に別名接続を切れば 3 と主張できる」案は採らない — 片付けと裏取りで別名接続を
  使い続けるほうが単純で、4 本は問題になる水準ではないため。

## [Warning] 「子を起こさない単体検査」では SIGTERM/SIGKILL/wait の実効性は証明できない
- 判断: **対応する**
- 根拠: 指摘のとおり。実プロセスの kill を試すテストを足すと正典の要素 (6) に反するので、
  **主張の範囲を正確に書く**のが正しい解決である。
- 対応内容: runner はプロセスを直に触らず**抽象越し**に扱うことにし、
  失敗経路の検査が主張するのは「runner がその抽象へ停止・kill・wait を必ず要求すること」までだと明記した。
  実 OS プロセスに対する SIGKILL の実効性は主張しない、と境界も書いた。

## [Warning] PHPStan level 10 は tests を解析しないので「静的に型安全」とは言えない
- 判断: **対応する**
- 対応内容: 成功条件の 4 に注記を足した — PHPStan level 10 エラー 0 は
  **アプリ側に退行がないことの確認**であって、ハーネス自身の静的解析保証ではない。
  ハーネスの型の保証は `fromDecodedJson()` の実行時 fail-closed 検証と単体検査が担う。

## [Suggestion] 既存 docblock から削る「保証しないこと」は実測した範囲だけに
- 判断: **対応する**
- 対応内容: 期待効果の節に「削るのは今回実測した範囲だけ。任意の production route や
  実ジョブの副作用まで保証した表現へは広げない」と明記した。

## [Suggestion] 使命 / 6 要素 / `entered-release` の位置づけ / D7 の据え置き
- 判断: **記録のみ (対応不要)**
- 根拠: いずれも現行記述が妥当という評価。`entered` / `release` を
  「正典外の一般化ではなく対象テスト固有の観測補強」と読んでもらえたので、
  スコープ過大化の懸念は解消したと判断する。
