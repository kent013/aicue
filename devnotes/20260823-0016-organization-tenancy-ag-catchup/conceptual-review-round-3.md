# 全体判定: CHANGES_REQUESTED

Round 2 の DB 制約、検証コマンドの正本参照、`relation_scoped` の信頼起点、型境界への対応は概念設計として十分です。一方、予約語の適用、AG-047 の分類単位、旧 URL の走査根に未解消の穴があります。

## 1. 使命との整合性

[Suggestion] 「保持列と自己修復に起因する誤組織表示」に効果を限定したため、期待効果の記述は適切になりました。選択画面での誤操作を保証外とした点も妥当です。

## 2. 禁止事項違反

[Warning] 検証コマンドは必要な10本をすべて含むようになりましたが、本文では「9本」と記載されています。

修正提案: 「本設計時点の正本の内容は次の10本」に直してください。正本を AGENTS.md とする判断自体は適切です。

## 3. 実現可能性

[Suggestion] `CHECK (slug = lower(slug))` と通常の `UNIQUE` の合成は、PostgreSQL 固定という前提のもとで妥当です。直接 SQL に対する CHECK の実測と、並行改名の競合テストも適切です。

[Warning] migration 前処理の順序が「既存行の小文字化と、正規化後の衝突確認」となっており、衝突確認前に更新するようにも読めます。

修正提案: 概念上の順序を次のように固定してください。

1. 更新せずに正規化後の値を計算する。
2. 正規化後の衝突を検査し、存在すれば停止する。
3. 衝突がない場合だけ既存値を小文字化する。
4. CHECK と UNIQUE を付与する。

## 4. 期待効果の妥当性

[Suggestion] URL と membership-scoped binding による組織決定、非所属者への 404、自己修復撤去の因果はいずれも妥当です。

## 5. リスク

[Critical] 予約語を「登録・分類・route 表と照合する」設計はありますが、予約語を実際の slug として保存させない契約が明記されていません。現状の成功条件でも、予約語設定と route 整合検査が存在すれば、作成・改名で `admin` 等を保存できても達成扱いになります。これは AG-039 の未充足です。

修正提案: 次を明記してください。

- `fromInput()` と `deriveFromName()` の双方で予約語を拒否する。
- 新規作成・改名・既存組織の移行が同じ予約語判定を通る。
- 値オブジェクトが構文だけを担当するなら、保存可能な slug を表す別の検証済み型または factory で「構文妥当＋非予約語」を保証する。
- 予約語での新規作成・改名を拒否する Feature テストを成功条件に含める。
- 既存 slug が新しい予約語に該当する場合の migration 方針を、衝突時と同様に fail-closed で確定する。

[Critical] AG-047 の分類単位が「入口」だけでは不十分です。1つの controller、command、Filament action、MCP handler が複数の組織解決を持ち、一方は `actor_derived`、もう一方は任意文字列による検索、という実装を持てます。入口を1種類へ分類しただけでは後者を隠せます。

修正提案: 母集団を二段階にしてください。

- 第1段: 機械経路の全入口を機械抽出し、入口自体を完全一致で inventory 化する。
- 第2段: 各入口内の「組織または組織帰属資源を確定する全解決点」を抽出し、解決点ごとに許可 provenance を分類する。

`not_organization_scoped` は、当該入口に解決点がゼロであることを検査した場合だけ許可してください。入口に複数の解決点がある場合、それぞれが独立して契約を満たす必要があります。

[Critical] Filament の母集団にある「組織解決を持ち得る構成要素」という条件は循環しています。何が「持ち得る」かを走査器が事前に判断できるなら、その判定から漏れた構成要素が母集団にも入らず、全数性を失います。

修正提案: 対象 panel に属する application-defined の Resource / Page / RelationManager / Widget / Action 等を、組織解決の有無にかかわらず全件母集団へ入れてください。その後で解決点あり、または理由付き `not_organization_scoped` に分類します。対象種別の正本と、未知の Filament 構成種別をどう fail-closed に扱うかは詳細設計で決められます。

## 6. スコープの適切さ

[Critical] 旧 URL の「走査根ベースで閉じる」という設計と、実際に列挙した走査根・表・成功条件が一致していません。

明示された走査根は次だけです。

- git 追跡下の PHP 全数
- `resources/js/`
- `docs/`
- `.claude/`

しかし確認対象の表には、走査根に含まれていないものがあります。

- `doc/`
- ルート直下の `README`
- PHP 以外の config・manifest・テンプレート
- `tests/js/` や Browser テスト
- bug-hunt の inventory
- その他の生成物

さらに成功条件 6 は、現在9行ある表を「上表の6系統」と呼んでいます。

修正提案: 旧 URL 検査の母集団を、原則として「git 追跡下ファイル全数」から対象形式を分類する形にしてください。バイナリや生成物など走査しない分類には理由を持たせ、未分類の配置が現れたら fail-closed にします。少なくとも `doc/`、`docs/`、README、テスト、設定、manifest、テンプレート、bug-hunt inventory が母集団へ入る必要があります。

成功条件 6 は「上表の6系統」ではなく、「定義した走査根で検査可能なリポジトリ内の旧 URL 生成・記述がゼロ」と修正してください。

## 7. 型安全性

[Suggestion] `CurrentOrganizationData|null`、最終境界だけでの配列化、backed enum、型付き改名結果は、PHPStan level 10 を前提とする概念設計として十分です。

[Warning] `OrganizationSlug` が「構文的に妥当な slug」だけを表すのか、「予約語でもない保存可能な slug」まで表すのかが曖昧です。型名からは後者にも読めます。

修正提案: 型の不変条件を明示してください。予約語判定を外部に分ける場合は、構文検証済み値と保存可能値を型で区別し、Service が未検証の型を保存できない境界にしてください。
