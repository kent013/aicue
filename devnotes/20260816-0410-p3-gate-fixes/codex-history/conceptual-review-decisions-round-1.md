# 対応マトリクス: conceptual-review Round 1

全体判定は Round 1 で APPROVED。Warning 3 件はいずれも詳細設計で決めるべき粒度の指摘なので、
概念設計は据え置き、詳細設計へ仕様として落とす。

## [Warning] php -l の出力を文字列で解釈すると PHP の版差で gate が不安定になる

- 判断: **対応する** (詳細設計へ仕様として書く)
- 根拠: 実際に版差の可能性がある。ただし正典 t1 は `php -l` を真値と定めているので真値そのものは変えない。
- 対応内容: 詳細設計の施策 2 に次を明記する。
  (a) 比較するのは警告の文面ではなく **「非複合名 + 行番号」の組の集合**に正規化した結果である。
  (b) 真値を取る PHP は**テストを走らせている実行系そのもの** (`PHP_BINARY`) とする。
      別の PHP を探しにいかない。よって「CI と手元で版が違うと結果が変わる」ではなく
      「その実行系で警告が出る形をその実行系で検出する」になり、版差は検査の意味を壊さない。
  (c) 真値が 1 件も取れなかったら**その時点で赤にする** (空振りを緑にしない)。

## [Warning] 施策 1 のトークン境界の定義が曖昧 (Svelte / Tailwind の実際の書き方に耐えるか)

- 判断: **対応する**
- 根拠: 指摘のとおり、境界の取り方を決めずに実装すると「直したつもりで別の穴が開く」。
  家系でも同型の失敗 (重要度の修飾が新しい区切りとして働いてしまう) が実測されている。
- 対応内容: 詳細設計の施策 1 に、
  (a) `stripAllowlisted` の入力は**ファイル全文**であること (class 属性を抜き出す処理は挟まない) を明記し、
  (b) class トークンを構成する文字の集合を字句で定義し、
  (c) 自己検査に「許可語そのものは消える」「許可語を部分に含む語は消えない」「引用符・空白・改行・括弧に隣接しても同じ」
      「重要度の修飾が付いた形は消えない (許可を広げない側へ倒す)」を入れる。

## [Warning] カンマ区切りの複数要素が同一行に集約報告される仕様の扱い

- 判断: **対応する**
- 根拠: 実測どおり `use\n Foo,\n Bar;` は Foo と Bar の両方が **Foo の行**で報告される。
  検出側が要素ごとの実際の行を返すと、真値との照合が版差ではなく仕様差で落ちる。
- 対応内容: 詳細設計で、検出側の行番号を **「その use 文の中で最初に現れる名前トークンの行」**と定義し、
  この定義自体を見本で固定する (複数行に散らしたカンマ区切りの見本を 1 本置く)。

## [Suggestion] 施策 2 の見本を形ごとに分ける / 走査器に小さな値オブジェクトを使う

- 判断: **対応する** (詳細設計の構成に反映)
- 対応内容: 見本は形ごとに 1 ファイル 1 形で置く。走査器の戻り値は配列の shape を docblock で固定する
  (小さなテスト補助なので、専用クラスを増やさず `array{...}` の shape 宣言で PHPStan level 10 に乗せる)。

## [Suggestion] 施策 3 は別 TODO へ送るのが必須条件 / 施策 4 を落とす判断は妥当

- 判断: **対応する**
- 対応内容: 詳細設計の末尾に「本設計から落とした施策と、その行き先」の節を置き、
  施策 3 を別 TODO として起票することを申し送りに明記する。
