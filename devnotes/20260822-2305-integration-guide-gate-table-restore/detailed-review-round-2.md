## 施策2: `IntegrationGuideGateTableSyncTest`

判定: **REQUEST_CHANGES**

- [Warning] 区切り行の検査がまだ不十分です。

  ```php
  preg_match('/^\|[\s\-:|]+\|$/', $separator)
  ```

  この正規表現は、次のようなMarkdown表の区切りとして成立しない行も受理します。

  ```markdown
  ||||
  | | | |
  |---|
  ```

  ヘッダが3列でも、区切り行の列数は確認されません。

  修正案: 区切り行も`integrationGuideCells()`で分割し、以下を検査してください。

  - ヘッダと同じ列数である
  - 最低3列ある
  - 各セルが`/^:?-{3,}:?$/`等の区切りセル形式に完全一致する

  `||||`、列数不足、1セルだけ不正、配置指定付きの正常例を負例・正例へ追加してください。

- [Warning] 正例が依然として実装後に追加される計画になっており、AGENTS.mdの「負例と正例を先に赤くする」を満たしていません。

  現在の順序は「最小抽出器 → 負例 → 本体実装 → 正例」です。

  修正案:

  1. まず正例を、常に例外を投げるstubに対して赤くする
  2. 最小の正常系を実装して正例を緑にする
  3. 負例を追加し、素朴な実装が受理して赤くなることを確認する
  4. fail-closed分岐を順次実装する
  5. 最後に実文書との統合テストを赤→緑にする

- [Warning] 走査器共通規約(e)を「適用」としていますが、必須とされる接頭辞付き・打ち消し付き・接尾辞付きの3負例がありません。

  今回は許可語彙の除去や否定形判定をしておらず、ゲート名の構文とファイル実在性を検査しているため、(e)は「対象外」と整理する方が自然です。`|`を区切りとする宣言は、独立した走査契約として残せます。

  もし(e)を適用扱いにするなら、3形が既存ゲート名と同一視されず、不存在違反になることを負例で固定してください。

- [Suggestion] 負例数の記述が一致していません。対応マトリクス冒頭は「8形」、規約適合表は「7形」、実コードの表形状datasetは「9形」です。最終設計では9形へ統一してください。

- [Suggestion] `integrationGuideSectionTwo()`は最初の`## 2. `だけを採用します。章見出しの一意性まで保証するなら、アンカーと同様に§2見出しもちょうど1件であることを検査すると、章構造の曖昧さを防げます。

PHPStan関連のoffset、クロージャ戻り値、捕獲群の絞り込みは適切に修正されています。母集団下限の削除、アンカー一意性、regular file判定、表の分割検出も妥当です。

## 施策3: 乖離台帳の付け替え

判定: **REQUEST_CHANGES**

- [Warning] D40の削除条件が、意味的一致とファイル指紋一致を混同しています。

  現在は次のように設計されています。

  > 同じ判定を同じ抽象度で要求していると確認できたら本登録は削除し、指紋の一致へ戻す

  しかし`TemplateDivergenceFingerprintTest`はファイル単位のハッシュを比較します。同じ不変条件を要求していても、ゲート名や文章が異なれば指紋は一致しません。D40だけを削除すると、未登録の不一致として再び失敗します。

  修正案: 削除条件を次のいずれかまで含めてください。

  - 配布されたテンプレート現物を正規の取り込み手順で採用し、実ファイルが指紋台帳と一致した
  - 正規のテンプレート台帳更新により、新しい指紋が取り込まれた
  - 別の承認済み同期機構がファイル単位の不一致を解消した

  意味的一致だけが確認でき、ファイル内容が異なる場合は、登録簿の原則上は同じ不変条件でも、現行の指紋検査上D40を削除できないことを明記する必要があります。

それ以外では、還流済み3節との矛盾、2文制約、監視中登録としての位置付け、件数pinの更新は適切に修正されています。
