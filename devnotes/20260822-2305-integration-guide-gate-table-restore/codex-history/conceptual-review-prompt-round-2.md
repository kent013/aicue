## 改訂版 概念設計（全文）

# 概念設計: integration-guide-gate-table-restore

> Round 1 のレビューを受けて改訂（到達の主張を下げ、写像であることの明示、D40 の中身の具体化、
> 分類基準の定義、単位の定義を追加）。

## 背景・課題

家系の機能台帳 lctl の feature `app-integration-guide`（アプリ組み込みガイド = 要件を
テンプレートの構造へ写す手順と判定規則の契約文書）について、裁定 **AG-116 (2026-08-08)** が
「家系の正として配る中身」を **合成版**と確定している。合成版の構成要素は 3 つ:

1. テンプレート現行版
2. aicue の独自 3 節の還流（§5 エラー応答の優先順位 / §7 テナント境界を経路解決の直後で閉じる /
   §7 末尾の新規ルート追加チェックリスト）
3. **aicue が失った §2 のゲート表 2 本（計 34 行）の復帰**

このうち (2) はテンプレート側が `laravel-claude-template:T121` / `T132` で還流を完了し、
台帳のテンプレートセルは `implemented (t2)` へ上がっている。(3) について台帳は
「2 表ともテンプレートには実在するので、**これは aicue 側の取り込み作業である**」と明記し、
テンプレートセルの担当から明示的に外している。**担当が aicue に名指しされている作業**が本件である。

aicue が 2 表を失った経緯も台帳が特定している。aicue は初期コミット `aicue@f693dd2` の時点で
`laravel-claude-template@616550b`（2026-07-05 版 198 行）と byte 一致していたが、テンプレートが
2026-08-01/02 に入れた文書一括更新（198 → 267 行）を**一度も取り込まないまま**、監査で見つかった
実所見を独自節として足す形で育った。結果として、その一括更新に含まれていた §2 のゲート表 2 本が
aicue には存在しない（差分巡回 2026-08-14 / 観測点 `aicue@a5553b5` でも欠落の継続を確認）。

**課題の実害**: §2 は「新しいドメインリソースを足すときの手順」の正本であり、AGENTS.md の実装規約が
「新しいドメインリソースの追加手順は Item リソースが見本（§2 のチェックリスト）」として名指しで
参照している導線である。aicue の §2 が持つのは *Item のどのファイルを見るか* の対応表 21 行だけで、
**「どの Architecture ゲートが発火し、何をどこへ登録しなければならないか」の索引が無い**。
その結果、新規リソースを足す設計者（人間・LLM）は 131 本ある `tests/Architecture/` のどれが
自分に関係するのかを毎回 §7 の散文と実装を読んで再発見することになる。§7 末尾の
「新規ルート追加チェックリスト」は *route* を足すときの 7 項を持つが、*リソース*（Model +
マイグレーション + FormRequest + 画面 + API + Factory）を足すときの索引ではなく、母集団が違う。

## 改善アイデア

aicue の `docs/app-integration-guide.md` §2 に、失われたゲート表 2 本を復帰させる。

- **表 A「新規リソースで必ず踏む Architecture ゲート」（8 件）**
- **表 B「条件付きで発火するゲート」（13 件）**

列は 3 列に固定する: **ゲート / 何を落とすか / 何をどこへ登録するか**。

### これは逐語復元ではなく「判定規準としての写像」である（本設計の性質の明示）

テンプレートの現物はこのリポジトリにも CI にも無い（`docs/template-divergence.md` D34 が
「テンプレートの現物が CI に無い」ことを前提として明記している）。正典が保存しているのは
「表が 2 本あり、それぞれ 8 件 / 13 件、2 表で 34 行」という**規模の記述だけ**で、行の中身の
逐語は台帳にも無い。したがって本件は **aicue の実在ゲート（`tests/Architecture/` 配下）で
表を構成する意味的な写像**である。

これは本件の発明ではなく、**家系の正が既に採った作法**である。テンプレート側の還流 `T121` は
aicue 本文を実読できない環境で実施され、「aicue 本文の逐語復元ではなく裁定の所見を実装へ
写像した規約」と本文自身に明記する形で完了し、台帳はそれを `implemented (t2)` として受理した。
本件は同じ作法を逆向き（テンプレート → aicue）に適用する。**§2 本文の導入文と乖離台帳 D40 の
両方に、逐語復元ではないことを明記する。**

### 単位の定義（「8 件 / 13 件」と「34 行」を混ぜない）

- **契約にするのは 21 件のゲート**（表 A 8 件 + 表 B 13 件）。この件数を機械で pin する。
- **「34 行」は Markdown の物理行数の記述**（小見出し・表ヘッダ・区切り行・空行を含む）であって、
  復元の根拠にも契約にも使わない。結果として 34 行前後に落ち着くが、行数の一致は主張しない。

### 表 A / 表 B の分類基準（恣意性を避けるための定義）

- **表 A**: 「Project 配下のドメインリソースを 1 つ足す」という操作が**それ自体で**そのゲートの
  母集団を増やすもの。新 Model・新 FormRequest・新 nested route・新 binding param・変更系
  ハンドラは、リソースを足せば必ず生まれるので、対応するゲートは条件なしに発火する。
- **表 B**: リソースの**性質や付随機能**が加わって初めて母集団に入るもの（API を公開する /
  LLM を呼ぶ / キャッシュへ入れる / 外部 URL を取る / 画面を足す / MCP tool を足す /
  上限を設ける）。

この基準は表の行を将来増減させるときの判断根拠でもある（基準に照らして議論できる形にする）。

### 表が腐らないための機械を 1 本だけ足す

表の各行はゲート名を名指しするので、ゲートが改名・削除されたときに表だけが古い名前を指し続けると
「索引を読んで登録しに行ったのに存在しないゲートを探す」形の空振りが起きる。
`tests/Architecture/IntegrationGuideGateTableSyncTest.php`（新規）が次を deny-by-default で固定する:

- 表 A / 表 B が §2 の範囲内に実在し、**安定した小見出しをアンカー**として抽出できること
  （§2 の範囲外・別節の同名文字列は対象にしない）
- 各行が名指しするゲートが `tests/Architecture/<名前>.php` として**実在**すること
- 表 A = 8 件 / 表 B = 13 件を**完全一致で pin**（無断の縮小・膨張のどちらでも赤）
- 走査が空振りしていないこと（走査根の実在・母集団の非空）
- 負例（実在しないゲート名を含む合成入力 / 表そのものが無い合成入力）で赤になること

実在判定は**ファイルの存在だけ**を見る（PHP のクラス参照解決は行わない）。

**この機械が保証しないもの（誇張しない）**:
表に書かれた条件や登録先の**意味的な正確さ**は見ない。設計者が実際に §2 を読んで登録したかも
見ない（正典の gates が「設計時に §2〜§7 の判定を踏んだかどうかを確かめる機械は家系のどこにも
無い」と明記しており、本件はその状況を変えない）。表に載っていないゲートの存在も見ない
（索引の網羅性は主張しない）。

## 期待効果

- **使命への寄与（間接）**: 使命を直接改善するものではなく、**使命を支えるテナント境界・
  安全な機能追加の開発契約を回復する**。AI-CUE の使命は「専門知識ゼロの現場作業者でも
  標準化されたマニュアル動画を作れる」ことであり、その前提は SOP・シナリオ・撮影テイクといった
  テナントデータが組織を跨いで漏れないことである。新しいドメインリソースを足すたびに踏むべき
  防御の登録先が 1 か所に集まる。
- **レビュー時に確認できる索引を提供し、関連ゲートの探索コストを下げる**
  （実装時の登録を強制する効果は主張しない。強制はリソース種別ごとの inventory gate が
  存在して初めて言える）。
- 台帳が aicue 側に名指しした取り込み作業を、**参照可能な一次資料の範囲で写像として実施する**。
  台帳セルの status を上げる判断はキュレーターの巡回の責務であり、本件は完了を宣言しない。
- 表が指すゲート名の実在が機械で固定されるので、ゲートの改名で索引が腐る形を防げる。

### なぜ乖離台帳の付け替えが必須なのか（機構が決めており、分離できない）

「内容をテンプレートへ戻す」か「意図的逸脱として登録簿へ書く」。テンプレート現物が無いので
前者は物理的に取れない。よって**後者が唯一の経路**であり、
「本文の変更」と「債務削除 + D40 登録」を分離することは機構的に不可能である。

### D40 に必ず書く 5 点（債務から登録へ移ることで失うものの補償）

突合 gate の docblock は「**登録済みのパスの追加の drift は検出しない**（検出するのは
一致から不一致へ移る瞬間である）。**債務パスは例外**で、採用時ハッシュとの一致まで見る」と
明記している。つまり債務から登録へ移すと**採用時ハッシュによる追跡は実際に失われる**。
これは避けられないので、登録側でそれを補償する:

1. テンプレート現物が参照不能だった事実（正典が持つのも規模の記述だけであること）
2. 表は**逐語復元ではなく判定規準としての意味的写像**であること
3. **ハッシュ追跡を失うこと自体**を明記する
4. **再照合が必要になる条件** — テンプレート更新の一括取り込みを行うとき /
   家系の巡回で合成版の現物が配られたとき / §2 のゲート表の行を増減させるとき
5. **再照合時の正本** — lctl の feature `app-integration-guide` と
   テンプレートの `docs/app-integration-guide.md`

状態は `恒久` ではなく **`監視中` + 見直し期限**にして、D34 と同じ期限管理に乗せる。

## 制約・前提

- **正典の gates（台帳が記録する不変条件）を壊さないこと**。特に「設計時に §2〜§7 の判定を
  踏んだかどうかを確かめる機械は家系のどこにも無い」— 本件が足す機械は
  「表が指すゲート名の実在と件数」までであり、この保証範囲を docblock に明記して誇張しない。
- **番号体系に触らない**。aicue の §7 は 1〜10、テンプレートは 1〜11 で対応が崩れているが、
  AGENTS.md の採番注意が「どちらの側も renumber しない」と定めており、正典自身も
  番号体系の食い違いを付随論点として扱っている。表から §7 を参照するときは
  **番号ではなく項目名**で指す。
- **新規 PHP テストは `declare(strict_types=1)` 必須**
  （`StrictTypesDeclarationGateTest` が git 追跡下の PHP 全数に deny-by-default で強制し、
  免除の登録簿を持たない）。抽出結果は `list<string>` として型注釈・検証する（PHPStan level 10）。
- **Markdown の説明文は `RouteCacheExemptionPremiseTest` の検査 B の対象外**（同テストの
  docblock が「見ないもの: Markdown の説明文」と明記）。ただし PHP は文字列リテラルまで
  走査されるため、新規テストに `route:cache` に相当する語をリテラルで持たせない。
- 表の行が名指しするゲートは**すべて実在確認済み**（本設計で 21 本すべてを
  `tests/Architecture/` 配下に実物として確認した）。
- devnotes 配下は `ForbiddenStatementTokenInvariantTest` の走査対象外（理由付きで除外分類済み）。
- HTTP 境界・DTO・JsonResource・Inertia Props を一切変えないので、`response()->json()` 直書きや
  DTO 違反の余地は無い。
