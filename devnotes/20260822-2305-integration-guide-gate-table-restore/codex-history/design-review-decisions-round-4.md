# 対応マトリクス: design-review Round 4

Round 4 は全施策 APPROVE / 全体判定 **APPROVED**。Suggestion 1 件のみ(非ブロッキング)。

## [Suggestion] PHPStan 適合チェックの説明が実装と厳密には違う

- 判断: 対応する(説明の精度を上げるだけの変更であり、実装は変わらない)
- 根拠: データ行は `count($cells) !== count($headerCells)` の完全一致で見ているのに、
  チェックリストは「ヘッダ・データ行とも最低列数」と書いていた。実装が正しく説明が古い。
- 対応内容: 「**ヘッダは最低列数、区切り行とデータ行はヘッダとの完全一致**」へ書き換えた。

## 最終確認 (app-design Phase 2-5)

- **使命との整合**: 全施策が「使命を支えるテナント境界・安全な機能追加の開発契約の回復」に
  寄与する。直接的なプロダクト価値は主張していない(概念設計 Round 4 で承認済みの位置づけ)。
- **禁止事項**: 1(テストなしの完了)は施策 2 が担う。2(PHPStan の widen / baseline)は
  適合チェックで型を絞る方針を明記済み。4〜8 は HTTP 境界・UI・LLM 経路を触らないため非該当。
  9(Artifact)は成果物をリポジトリ内ファイルとして出力することで守る。
- **コーディングルール**: PHPStan level 10 / Pest / `declare(strict_types=1)` /
  DB 不使用の静的検査(個別 `DatabaseTransactions` を使わない)を設計に反映済み。
- **正典の不変条件**: G1〜G5 の 5 本すべてについて「本設計が壊さないこと」を詳細設計の表で
  1 本ずつ示した。特に G2(設計時の判定を確かめる機械は家系に無い)は本件でも変えない。
