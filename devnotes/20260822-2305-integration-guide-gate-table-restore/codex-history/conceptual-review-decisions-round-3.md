# 対応マトリクス: conceptual-review Round 3

Round 3 の指摘は 2 件（観点 2 と観点 7）で、**内容は同じ 1 つの穴**を別の側から指している —
「抽出不能な表の行」について (b) fail-closed の宣言はあるが (c) 負例の裏取りと失敗の表現が
決まっていない。どちらも対応する。

## [Warning] 「ゲート名を取り出せない行は識別可能な失敗にする」に対応する負例が無い（観点 2）

- 判断: 対応する
- 根拠: AGENTS.md 走査器共通規約は (b)「解決できない形は落とす」と (c)「検出力は負例で裏取りする」を
  **組み合わせて**要求しており、宣言だけで負例が無い状態は規約違反である。指摘は正しい。
- 対応内容: 負例の一覧に**抽出不能行**の 3 形を追加した。3 列のデータ行の形は保っているが
  ゲート名を取り出せないもの — (i) ゲート列のバッククォート欠落、(ii) ゲート列が空、
  (iii) 許容しない表記（パス区切りを含む / 末尾が `Test` でない）。いずれも
  「無言で候補から外れて件数だけ合う」形にならず失敗することを固定する。
  併せて、負例が押さえる分岐を実施順の 3 に明記した。

## [Warning] 抽出不能値を `list<string>` に混ぜると fail-closed が崩れる（観点 7）

- 判断: 対応する
- 根拠: 空文字列や `null` を混ぜて型だけ満たす形は、走査器共通規約 (b) の
  「未解決を解決済みと同じ値へ混ぜない」に正面から反する。
- 対応内容: **抽出の失敗表現を契約として決めた** — 抽出処理は
  「**正常に全行を解決できたときだけ `list<string>` を返す**」契約にし、解決できない行が
  1 行でもあれば**行番号と理由を持つ例外**を投げる（呼び出し側の検査はそれをテスト失敗として
  報告する）。戻り値へ混ぜる形・無言で除外する形はどちらも取らない。
  この契約と負例の対応を概念設計に明記し、詳細設計の PHPStan 適合チェックにも落とす。
