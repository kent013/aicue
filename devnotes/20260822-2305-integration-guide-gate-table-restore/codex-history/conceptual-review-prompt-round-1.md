## 使命 (North Star)

<!-- app-codex-review スキルはこのセクションをレビュー使命として参照する。 -->

**AI-CUE** は、現場に既にある**作業手順書(SOP)を起点に**、AI が撮るべきカットを設計した**動画シナリオ**を生成し、そのシナリオを**スマホ(PWA)でナビゲーション撮影**することで、専門知識ゼロの現場作業者でも**標準化されたマニュアル動画**を作れるようにする。

- 「思考ゼロ・編集ゼロ」— 台本作成・撮影判断・編集の 3 ハードルを AI とナビ撮影で肩代わりする。
- 競合(OJT を撮って形式化する tebiki)と異なり、**標準作業を起点に AI が教材設計し撮影を指示する**（撮影者・教える人のスキルに品質を依存させない）。
- 熟練者の暗黙知を動画マニュアルという形式知へ変換する装置（SECI）。

> 詳細な設計は本リポジトリの `doc/`（01〜10）に置く。ドメインをテンプレート構造へどうマップしたかは `doc/08`〜`doc/10`（特に `doc/10 §10.8` に設計レビュー反映済み）。
> **v1 スコープ**: 字幕のみ(TTS 後回し) / 撮影は PWA(同一オリジン・セッション認証) / 動画合成は自前 ffmpeg / 単一 Default Project。

## 禁止事項

1. テストなしの実装完了報告(不変条件は対応する Architecture/Feature テストへの登録まで含めて「実装済み」)
2. PHPStan エラーの widen(型を緩めて黙らせる)・baseline 化
3. dev DB への破壊操作(`migrate:fresh` 等)をエージェント判断で実行すること
4. `response()->json()` の直書き(DTO / JsonResource / Inertia を使う。仕様固定 endpoint のみ例外)
5. LLM 呼び出しの Prism 直呼び(`app/Prompts/` の factory → 窓口 (`PromptDefense`) →
   実行単位 (`GuardedPrompt`) の**1 本道のみ**。`PromptGuardrailTest` が
   app/ routes/ database/ config/ bootstrap/ の 5 走査根で検出する)。
   **実行経路を持つ prompt factory は `LlmCallContextData` を必須引数で受け、
   `PromptDefense::load()` へ渡して帰属 (organization / subject) を付ける** — 付け忘れは
   PHPStan level 10 が落とす。帰属の対象を持たない見本 (`ExampleSummaryPrompt`) だけが
   `PromptDefense::loadUnattributed()` を使え、窓口 gate が**この 1 件を名指しで pin** する。
   併せて `PromptUntrustedInputContractTest` の inventory へ**帰属キーを空配列で exempt 登録**する
   (deny-by-default なので exempt にする操作がレビューで必ず見える)。
   欠けると `llm_call_logs.metadata_missing` になり組織別・対象別の費用が出せない
6. prompt 文字列のコード直書き(`resources/prompts/*.yaml` に置く)
7. 操作系 POST の応答での `redirect()->intended()`(ログイン直後フロー専用。
   招待送信等は `back()->with(...)` で完結させる)
8. 必須条件未充足を理由にボタンを disabled にする UI(押下時にエラー表示する。DESIGN.md)
9. Artifact の使用(Artifact ツールでの成果物公開を行わない。成果物はリポジトリ内のファイルとして出力する)

## 背景・課題

家系の機能台帳 lctl の feature `app-integration-guide`（アプリ組み込みガイド = 要件を
テンプレートの構造へ写す手順と判定規則の契約文書）について、裁定 **AG-116 (2026-08-08)** が
「家系の正として配る中身」を **合成版**と確定している。合成版の構成要素は 3 つ:

1. テンプレート現行版
2. aicue の独自 3 節の還流（§5 エラー応答の優先順位 / §7 テナント境界を経路解決の直後で閉じる /
   §7 末尾の新規ルート追加チェックリスト）
3. **aicue が失った §2 のゲート表 2 本（計 34 行）の復帰**

このうち (2) はテンプレート側が `laravel-claude-template:T121` / `T132` で還流を完了し、
台帳のテンプレートセルは `implemented (t2)` へ上がっている。(3) について台帳は
「2 表ともテンプレートには実在するので、**これは aicue 側の取り込み作業である**」と明記し、
テンプレートセルの担当から外している。つまり合成版の完成に残っている唯一の作業が本件である。

aicue が 2 表を失った経緯も台帳が特定している。aicue は初期コミット `aicue@f693dd2` の時点で
`laravel-claude-template@616550b`（2026-07-05 版 198 行）と byte 一致していたが、テンプレートが
2026-08-01/02 に入れた文書一括更新（198 → 267 行）を**一度も取り込まないまま**、監査で見つかった
実所見を独自節として足す形で育った。結果として、その一括更新に含まれていた §2 のゲート表 2 本が
aicue には存在しない（差分巡回 2026-08-14 / 観測点 `aicue@a5553b5` でも欠落の継続を確認）。

**課題の実害**: §2 は「新しいドメインリソースを足すときの手順」の正本であり、AGENTS.md の実装規約が
「新しいドメインリソースの追加手順は Item リソースが見本（§2 のチェックリスト）」として名指しで
参照している導線である。aicue の §2 が持つのは *Item のどのファイルを見るか* の対応表 21 行だけで、
**「どの Architecture ゲートが発火し、何をどこへ登録しなければならないか」の索引が無い**。
その結果、新規リソースを足す設計者（人間・LLM）は 131 本ある `tests/Architecture/` のどれが
自分に関係するのかを毎回 §7 の散文と実装を読んで再発見することになり、登録漏れは
実装が終わってテストが赤くなってから気付く。§7 末尾の「新規ルート追加チェックリスト」は
*route* を足すときの 7 項を持つが、*リソース*（Model + マイグレーション + FormRequest + 画面 +
API + Factory）を足すときの索引ではなく、母集団が違う。

## 改善アイデア

aicue の `docs/app-integration-guide.md` §2 に、失われたゲート表 2 本を復帰させる。

- **表 A「新規リソースで必ず踏む Architecture ゲート」（8 本）** — Project 配下の新しい
  ドメインリソースを足すなら条件なしに全部発火するもの
- **表 B「条件付きで発火するゲート」（13 本）** — 「API を足したら」「LLM を呼ぶなら」
  「キャッシュに入れるなら」のように、リソースの性質で発火するもの

**行の中身は aicue の実在ゲート（`tests/Architecture/` 配下）で構成する。**
テンプレートの現物はこのリポジトリにも CI にも無く（`docs/template-divergence.md` D34 が
「テンプレートの現物が CI に無い」ことを前提として明記している）、正典が保存しているのは
「表が 2 本あり、それぞれ 8 本 / 13 本、合計 34 行」という**規模の記述だけ**で行の中身の逐語は
持たない。したがって本件は逐語復元ではなく、**テンプレート側の還流 (T121/T132) が採ったのと同じ
やり方 —「逐語復元ではなく判定規準としての写像」— を aicue 側で行う**（T121 は自分の本文に
その旨を明記している。同じ作法に揃える）。

さらに、復帰させた表が**黙って腐らないための機械**を 1 本だけ足す。表の各行はゲート名を
名指しするので、ゲートが改名・削除されたときに表だけが古い名前を指し続けると、
「索引を読んで登録したのに存在しないゲートを探す」形の空振りが起きる。
正典の gates も「文書と実装ゲートの整合を検出する機械」を家系の資産として数えており
（motivation が最初、テンプレートが 2 本目）、aicue はそれを持たない。
本件で足すのは**その全面版ではなく、§2 の表が指すゲート名の実在と行数だけを見る最小の 1 本**である。

## 期待効果

- **使命への貢献（間接だが実質的）**: AI-CUE の使命は「専門知識ゼロの現場作業者でも
  標準化されたマニュアル動画を作れる」ことであり、その前提は SOP・シナリオ・撮影テイクといった
  **テナントデータが組織を跨いで漏れないこと**である。§2 のゲート索引は、新しいドメインリソース
  （撮影テイクの派生・SOP の付帯データ等）を足すたびに踏むべき防御の登録先を 1 か所に集める。
  索引が無い状態は「登録漏れに実装後まで気付けない」= 監査で見つかった存在オラクルと同型の
  事故の再発経路である。
- 家系の裁定 AG-116 の合成版が完成する（残タスクが 0 になる）。台帳の aicue セルが
  `pending` から上がる根拠のうち §2 欠落の 1 点が解消する。
- 新規リソース追加時の設計レビューで「どのゲートに登録したか」を表の行単位で確認できる。
- 表が指すゲート名の実在が機械で固定されるので、ゲートの改名で索引が腐る形を防げる。

### なぜ乖離台帳の付け替えが必須なのか（設計の必然）

`docs/app-integration-guide.md` は**テンプレート共有ファイル**（`docs/template-fingerprints.json`
のキーに実在）であり、かつ**採用時債務一覧に載っている**。現物の sha256 は債務一覧の

`mutatedDebtPaths`（F10）が落ちる。債務一覧が縮む契機は `AdoptionDebtInventory` の docblock と
D34 が定める 2 つだけ —「内容をテンプレートへ戻す」か「意図的逸脱として登録簿へ書く」。
テンプレート現物が無いので前者は取れない。よって**後者（D40 の新設 + 債務一覧から 1 行削除）が
唯一の経路**である。これは選択ではなく機構が決めている。

## 制約・前提

- **正典の gates（台帳が記録する不変条件）を壊さないこと**。特に「設計時に §2〜§7 の判定を
  踏んだかどうかを確かめる機械は家系のどこにも無い」— 本件が足す機械は
  「表が指すゲート名の実在」までであり、**設計者が実際に判定を踏んだかは見ない**。
  この保証範囲を docblock に明記し、誇張しない。
- **番号体系に触らない**。aicue の §7 は 1〜10、テンプレートは 1〜11 で対応が崩れているが、
  AGENTS.md の採番注意が「どちらの側も renumber しない」と定めており、正典自身も

  **番号ではなく項目名**で指す。
- **Markdown の説明文は `RouteCacheExemptionPremiseTest` の検査 B の対象外**（同テストの
  docblock が「見ないもの: Markdown の説明文」と明記）。ただし新規 PHP テストは

- 表の行が名指しするゲートは**すべて実在確認済み**（本設計で 21 本すべてを
