## [Warning] 「deny-by-default」という表現が検査内容より強い（観点 3）

- 判断: 対応する（表現を限定する側で対応。期待集合をテストへ pin する案は**採らない**）
- 根拠: 21 件の期待集合をテスト側へ写すと、表と検査の 2 か所に同じ一覧を持つことになる。
  AGENTS.md は「2 か所に書くと必ず食い違う」を理由に、件数だけを pin して中身の正本を
  片方に置く作法を繰り返し採っている（`ForbiddenStatementExemption` の件数 pin、
  `LedgerPins` の 3 定数、`RouteCacheExemptionPremiseTest` の mentions 件数 pin）。
  本件も同じ作法に揃え、正本は文書側の表 1 か所とする。
- 対応内容: 保証の言い方を
  「各抽出行について**未解決・不存在・件数不一致・重複を拒否する**」へ限定し、
  **「表の構成集合そのものは固定しない = 別の実在ゲート名への差し替えは検出しない」**を
  保証しないものへ明記した（docblock の必須記載事項に含める）。「deny-by-default」の語は
  この検査の説明から外す。

## [Warning] 表 A の定義と例示に内部矛盾（読み取り専用・画面だけのリソースが成立する）（観点 5）

- 判断: **対応する**（指摘は正しい。「ドメインリソース」だけでは FormRequest・変更系ハンドラの
  必須性を導けない）
- 根拠: レビューが提示した 2 案のうち **1 案目（§2 が対象にする「新規リソース」を特定の
  実装単位として明示する）** を採る。§2 は元々「見本: Item リソース」= Project 配下の
  書き込み可能なリソースの実演として書かれており、対応表 21 行もその単位を前提にしている。
  単位を明示するのは既存本文の意図の明文化であって、新しい制約の発明ではない。
- 対応内容:
  1. 表 A の適用単位を定義した — **「§2 の手順で Project 配下に *書き込み可能な* ドメインリソースを
     1 つ足す」= 見本 Item と同型の実装単位**。この単位は定義上、マイグレーション（親 FK
     `constrained()` + NOT NULL）/ Model / Factory / FormRequest（store・update）/
     nested route（変更系を含む）/ 親 Policy 経由の認可 / Feature テスト を必ず持つ。
  2. 単位から外れる形（読み取り専用リソース / 画面だけの追加 / 組織直下のマスタ）を足すときは、
     **表 A のうち該当しない行を設計書で名指しして外す理由を書く**、という但し書きを表 A の
     直下に置く（黙って外させない）。
  3. 上の定義に照らして**分類を 1 件入れ替えた** — `ValidationAttributeCoverageTest` は
     新 FormRequest の rules キーが必ず母集団に入るので表 A へ移し、
     `ModelDirectFetchInvariantTest` は「route parameter **以外**の id 受け口（POST payload /
     MCP tool 引数 / token claim / queue payload）を足すとき」に発火する条件付きなので表 B へ移した。
     結果は 8 件 / 13 件のまま（合計 21 件）で、正典が記録する規模とも一致する。
  4. 21 件の具体名と分類根拠を概念設計に列挙した（3 列の本文は詳細設計で埋める）。
