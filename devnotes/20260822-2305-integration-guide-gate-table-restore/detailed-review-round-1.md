## 施策2: `IntegrationGuideGateTableSyncTest`

判定: **REQUEST_CHANGES**

- [Critical] PHPStan level 10で問題になる可能性が高い未絞り込みがあります。

  特に次の箇所です。

  ```php
  integrationGuideCells($header)[0]
  ```

  `integrationGuideCells()` の戻り値は `list<string>` で、空でない保証が型にありません。壊れたヘッダが `|` だけだった場合には、実行時にも未定義offsetになります。

  また、次のクロージャ戻り値は要素型のない `array` です。

  ```php
  fn (): array => integrationGuideGateNames(...)
  ```

  修正案:

  - ヘッダセルを変数へ受け、非空・列数を検査してから `[0]` を参照する。
  - 例外確認用クロージャは戻り値型を省略するか、ブロッククロージャで `void` にする。
  - 必要なら `$matches[1]` も `Assert::keyExists()` と `Assert::string()` で明示的に絞る。

- [Warning] 同じアンカーが§2内に複数存在しても、最初の1件だけを採用して緑になります。これは「2つのアンカー表を持つ」という契約に対して曖昧な文書を許します。

  修正案: 各アンカーの出現数を数え、**ちょうど1件**でなければ例外にしてください。重複アンカーの負例も追加してください。

- [Warning] `glob()` の結果をbasenameへ変換するだけなので、`.php` で終わるディレクトリなども「実在するゲートファイル」として数えられます。また「読めるディレクトリ」「regular file」という宣言も検証していません。

  修正案: 走査前に対象ディレクトリへ `is_dir()` / `is_readable()` を適用し、各パスを `is_file()` で検査してください。

- [Warning] `INTEGRATION_GUIDE_GATE_FLOOR = 50` は、保証したい不変条件と結び付かない閾値です。60件から51件へ大幅に欠落しても通り、正当な統廃合で49件になれば落ちます。

  修正案: 母集団の非空、代表ゲート、表に記載した全ゲートの実在で確認してください。全体件数そのものが不変条件なら、下限ではなく根拠付きの完全一致pinにする必要があります。

- [Warning] テストファーストの実施順がAGENTS.mdと一致していません。設計では抽出器本体を先に完成させ、負例を後から追加し、一時的に壊して赤を確認するとしています。これは新設走査器に対する「負例・正例を先に赤くする」という規則を満たしません。また、正規表現を「緩める」だけでは正例が赤になるとは限りません。

  修正案: 先に単純な抽出実装を置き、受理してはいけない入力を実際に受理する赤を確認した後、各fail-closed分岐を実装する順序へ変更してください。その後、実文書を読む統合テストを赤にして施策1を追加します。

- [Warning] 「実行不能」の全列挙に対して負例が不足しています。壊れたヘッダ、壊れた区切り行、アンカー重複の分岐は未検証です。

  修正案: 少なくとも次を追加してください。

  - 1列目の見出しが `ゲート` でない
  - 区切り行が不正
  - 同一アンカーが複数存在する
  - 表途中の不正行を黙って表終端として扱わない

- [Suggestion] テスト計画の「新規テスト6ケース」は、提示コードの7個の`test()`宣言と一致しません。dataset展開後は11テスト相当です。宣言数と検証シナリオ数を分けて記載してください。

- [Suggestion] docblockは「保証しないものを契約文書本文へ写さない」としながら、本文にも「網羅性を主張しない」「設計者が踏んだかは見ない」という制限を記載しています。短い注意書きの重複自体は有益なので、「詳細の正本はdocblock」と表現を修正すると矛盾が消えます。

## 施策3: 乖離台帳の付け替え

判定: **REQUEST_CHANGES**

- [Warning] D40の比較表にある「テンプレートは独自節を持たない」が、本設計の前提である「T121/T132で独自3節のテンプレート還流が完了済み」と矛盾します。

  修正案: この行を削除するか、少なくとも「本アプリ由来だがテンプレートへ還流済み」と修正してください。テンプレート現物を参照できない以上、台帳で確認できる範囲を超えた現状断定も避けるべきです。

- [Warning] D40の「業務要件起因の説明」は、登録簿規約の「1〜2文」を超えています。また、ゲート索引の復帰は家系の裁定への追従でもあるため、SOP等の業務ドメインだけを理由とする現在の説明は因果がやや過剰です。

  修正案: メタ表のセルは2文以内に圧縮し、詳細は後続の「なぜ正当な差分か」へ移してください。理由は「本アプリ固有のセキュリティ境界と実在ゲートへの写像」に限定すると明確です。

- [Warning] D40は「テンプレートと同じ8件・13件だがローカルゲートへ写像する」と述べる一方、登録簿の原則は「同じ不変条件を同じタイミング・抽象度で保証するなら構文差は逸脱ではない」としています。現在の説明だけでは、なぜ単なるローカル実装名の違いがlogic-drivenな逸脱になるのか不十分です。

  修正案: 「テンプレート現物が届くまでの監視中登録」であることと、現物到着時に意味的不変条件が一致すればD40を削除する判断基準を明記してください。「採用時点にもテンプレートにも収束しない」という恒久差分に近い表現は弱めるべきです。
