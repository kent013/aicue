全体判定: **CHANGES_REQUESTED**

Round 1 の指摘はほぼ適切に解消されています。特に dry-run と Schedule の安全性、候補列挙上限、競合の結果化、失敗通知の正本化は明確になりました。ただし、上限導入による starvation と例外分類に未解消の問題があります。

## 1. 使命との整合性

[Suggestion] 課金系を含める理由まで含め、North Star との接続は十分に説明されています。「パイプラインの滞留を人手なしで前へ進める」という定義も妥当です。

## 2. 禁止事項違反

[Warning] `LogicException` を stream 側で一律に `Skipped` へ変換すると、本当の不変条件違反まで競合として隠す可能性があります。

本文では「例外を通すのは本当の不変条件違反だけ」としていますが、同じ `LogicException` 型から競合と不変条件違反を安全に判別する方法が示されていません。メッセージ文字列による判別は避けるべきです。

修正案: `TicketLedgerService::release()` の契約を、競合時に専用結果または専用例外を返す形へ変更してください。例えば `ReleaseResult::AlreadyReleased`、または `ReservationStateChangedException` のみを `Skipped` に変換し、その他の例外は sweeper へ通します。

## 3. 実現可能性

[Critical] 主キー昇順の先頭 `limit` 件を毎回取得する方式では、回収時に例外を出して滞留状態に残る行が `limit` 件を占有し続け、後続行が永久に処理されない starvation が発生します。

「1件の失敗後も次へ進む」は同一実行内では有効ですが、次回も同じ先頭候補が選ばれるため、上限導入前にはなかった無音の滞留を作ります。look-back を採らない判断とも矛盾し、「古い滞留も必ず候補になるが、その後ろへ進めない」状態になります。

修正案: 概念設計で公平性を保証する方式を確定してください。選択肢は次のいずれかです。

- 例外になった候補を、各ドメインの再試行状態や `next_recovery_at` により一時的に候補外へ出す
- sweeper が永続カーソルを持ち、前回の続きから巡回する
- stream が「繰り返し例外になった行を有限回で別状態へ前進させる」ことを契約にする

単なる `limit` の増加や over-fetch では、障害件数がその値に達した時点で同じ問題が再発します。

## 4. 期待効果の妥当性

[Warning] S3 削除失敗を `Recovered` と数えると、「結果の種類ごとの件数」が実際の完了状態を表さなくなります。

DB の利用枠解放を成功として扱う判断自体は妥当ですが、S3 削除は失敗しており、再回収もされません。それを単一の `Recovered` に畳むと、未削除オブジェクトの増加を集計から把握できません。

修正案: DB 回収結果と付随処理結果を区別してください。例えば `RecoveredWithCleanupFailure` を enum に設け、件数を監視可能にします。少なくとも `report()` だけに依存せず、結果 DTO とコマンド出力に失敗件数を残してください。これを終了コード失敗へ反映するかは詳細設計で決められます。

## 5. リスク

[Critical] 前述の starvation が最大の後退リスクです。特に外部 API、S3、キュー投入など継続的に失敗し得る stream では、障害行が後続の正常回収を全面的に塞ぎます。

修正案: 公平性について Feature テストを追加対象として明記してください。「先頭候補が毎回失敗しても、候補数が limit を超える後続行が有限回の掃引で処理される」を不変条件として固定する必要があります。

[Warning] Schedule gate が何を同一性として突き合わせるか、まだ曖昧です。全 entry が同じ `work:recover-stuck` コマンドなので、コマンド名の集合だけでは stream の欠落や重複を検出できません。

修正案: registry の stream enum/key と、Schedule の `--stream=<key>` を一対一で比較すると明記してください。周期、`--apply`、排他指定、失敗通知まで stream key 単位で検査し、未登録・未定期実行・重複登録をそれぞれ失敗させます。

## 6. スコープの適切さ

[Suggestion] 1 PR のまま段階的に fail-first で移設する方針は妥当です。アップロード予約の purge 分離も、既存責務の解体に必要な範囲へ限定されています。

## 7. 型安全性

[Warning] `RecoveryOutcome` enum と結果 DTO の方向性は妥当ですが、`recover()` の正確な戻り値契約がまだ書かれていません。S3 cleanup failure や webhook の4内訳を扱うため、stream ごとに任意の outcome を返せる設計にすると、registry 全体で集計可能な outcome の対応漏れが生じます。

修正案: `recover(...): RecoveryItemResultData` のような共通戻り値を固定し、DTO が `RecoveryOutcome` と必要最小限の補助情報を保持する形にしてください。集計側で enum を網羅的に処理し、自由文字列や未型付け配列を介在させないことを詳細設計の条件にします。

結論として、Round 1 の主要事項は解消されていますが、`ORDER BY id LIMIT n` と永続的な失敗候補の組み合わせは、新基盤そのものが後続回収を停止させる構造的問題です。公平性の契約とテストを追加し、競合例外の型を分離できれば、概念設計として承認可能です。
