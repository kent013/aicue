## 施策 3: REQUEST_CHANGES

[Warning] 追加した近傍パターンは偽陽性が広すぎます。

```regex
/--parallel[^\n]*[5-9]/
/parallel[^\n]{0,20}?[5-9](?![0-9])/i
```

`8014` や `8010` 自体には `[5-9]` がないため、それ単体は誤検出しません。しかし、次の正当な行は誤検出します。

```text
parallel=4 の結果を S7 で検証する
--parallel=4 は AG-048b に基づく
parallel 実行は 2025 年に導入した
```

後者のパターンは `8018` 内の `8` も単独値と区別できません。

修正案: 「20文字以内」ではなく値の構文を限定してください。

```regex
/--parallel\s*(?:=|は|:)\s*(?:[0-9]+(?:\/[0-9]+)*)/
/(?<![0-9A-Za-z])N\s*=\s*[0-9]+(?![0-9])/
/parallel\s*(?:=|は|:|の上限(?:は|=))\s*(?<![0-9])[0-9]+(?![0-9])/i
```

マッチ後に数値列を抽出し、いずれかが cap 超過かをPHP側で判定する形が安全です。少なくとも `S7`、`AG-048b`、`2025`、`:8018` が偽陽性にならない負のコントロールを追加してください。

## 施策 5: REQUEST_CHANGES

[Warning] マーカー制約には、追加した検出パターンとの不整合による抜け道があります。

現在の `CAP_MARKER_DENY_CONTEXT` は `N=8` と `parallel=8` を含みません。そのため、以下が通過します。

```text
parallel=8 は guard 用。cap-defense-ok
N=8 は残留検出用。cap-defense-ok
```

allowlist 内ファイルで守り語を添えれば、マーカーが散文検査全体を除外します。

修正案: マーカー無効化判定には、散文検査と同じ「割り当て値抽出」を再利用してください。別々の正規表現集合を持たせると再び差分が生じます。マーカー行から割り当て値が抽出され、その値が cap 超過なら、守り語の有無にかかわらず違反とします。

正当な守りの説明は、割り当て文脈と行を分ければ表現できます。

```text
現在の並列上限は4。
残留ポート :8018 までは guard が検出する。cap-defense-ok
```

## 全体判定: CHANGES_REQUESTED

Round 2の4項目のうち、prefix順序とdefense surface具体化は閉じています。残るのは、近傍regexの偽陽性と、その検出ロジックを共有していないマーカーの抜け道です。値抽出を1つの純関数へ寄せれば局所修正で閉じられ、追加の機能拡張は不要です。
