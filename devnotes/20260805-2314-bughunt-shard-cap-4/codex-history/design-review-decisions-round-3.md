全体判定: **CHANGES_REQUESTED** (Critical 0 / Warning 2)。施策 1・2・4 は APPROVE。
Warning 2 件は**いずれも同じ根 (割り当て値の抽出ロジックが 1 本化されていない)** で、両方対応した。

## [Warning] 施策 3: 近傍パターンの偽陽性が広すぎる
- 判断: **対応する**
- 根拠: 指摘の例 (`parallel=4 の結果を S7 で検証する` / `--parallel=4 は AG-048b に基づく` /
  `parallel 実行は 2025 年に導入した`) はいずれも正当な文であり、
  `/--parallel[^\n]*[5-9]/` や `/parallel[^\n]{0,20}?[5-9]/i` はこれらを誤検出する。
  「近傍に cap 超過**数字**があるか」ではなく「**割り当て値として書かれた数値**が cap を超えるか」を
  見るべきだった。
- 対応内容: 検出を **2 層**に分けた。
  - **Tier A (割り当て値)**: 純関数 `bughuntCapAllocationValues(string $line): list<int>` が
    `--parallel=N` / `parallel は N` / `N=<数>` / `cap=<数>` / `shard 1..<数>` の**構文**から
    数値列を抽出し、cap 超過値があれば違反。数字の近接では判定しない。
  - **Tier B (literal)**: ポート `801[5-9]` / DB 名 `bug_hunt_[5-9]` / regex `_[1-[5-9]]` /
    範囲表記 `8011..801[5-9]` / `0-[5-9]` — 従来通りの literal 走査。
- 追加した負のコントロール: `S7` / `AG-048b` / `2025 年` / `:8018` (Tier B のマーカー付き行) /
  `parallel=4 の結果を S7 で検証する` が**いずれも Tier A の違反にならない**こと。

## [Warning] 施策 5: マーカーが Tier A の抜け道になる (`parallel=8 ... cap-defense-ok`)
- 判断: **対応する**
- 根拠: 指摘の通り。`CAP_MARKER_DENY_CONTEXT` を独立した正規表現集合で持たせていたため、
  散文検査側にパターンを足すたびにマーカー側と差分が生じる構造だった。
  実際 `parallel=8` / `N=8` は deny context に含まれておらず、守り語を添えれば通過した。
- 対応内容: `CAP_MARKER_DENY_CONTEXT` を**廃止**し、マーカー無効化判定に
  **Tier A と同じ `bughuntCapAllocationValues()` を再利用**する。
  規則を「**Tier A の違反はマーカーで免除できない。Tier B の違反のみ免除できる**」に単純化した。
  正当な守りの説明は Codex の例の通り、割り当て文脈と行を分ければ書ける。
- 副次効果: マーカー制約 (b) が不要になり、残るのは (a) allowlist ファイル と
  (c) 守りの語の 2 条件のみ。ロジックが 1 箇所に寄って再発差分が生じなくなった。
