全体判定: **CHANGES_REQUESTED**

Round 1 の Critical は適切に解消されています。既知 5 本の包含検査は、既知分母の欠落を検出しつつ新規 prompt を妨げないため妥当です。残る問題は `PromptWaitBudget` の公開 API と失敗契約の記述にあります。

### 1. 使命との整合性

[Suggestion] SOP 解析パイプラインの待ち予算宣言を安定して検査する改善であり、North Star に整合します。アプリ実行経路を変更せず、既存の解析完遂性を守るスコープも適切です。

### 2. 禁止事項違反

[Suggestion] 禁止事項への抵触はありません。Prism 実行経路、prompt 本文、DB、API、UIには変更がありません。仕様値 360 秒を YAML から導出せず、独立した突合対象として残す方針も適切です。

### 3. 実現可能性

[Warning] 「API は1つだけ公開」と書かれている一方、`read()`、`evaluate()`、`requirePositive()` の3メソッドを公開 API として列挙しており、契約が矛盾しています。特に `evaluate()` を公開すると、利用側が戻り値の `timeout` を直接読む第4の経路を作れます。

修正提案: 「公開クラスは1つ」なのか「公開メソッドは1つ」なのかを明確にしてください。単一の利用経路を重視するなら、通常の利用口を `requirePositive()` に限定し、`read()` と `evaluate()` は非公開にするのが最も強い設計です。自己テストから純関数を直接検査する必要があるなら、3メソッドを公開することを認めたうえで、「timeout の妥当性判定を実装するクラスが1つ」という保証へ表現を狭めてください。

[Warning] `PromptYaml::parseOrFail()` へ委譲しながら、「parse 不能・非 map・ファイル不在も違反として返す」とする例外契約が未確定です。`parseOrFail()` が例外を投げるなら、単に委譲するだけでは `array{timeout: null, violations: ...}` は返りません。

修正提案: `read()` が捕捉する例外型と違反ラベルへの変換を明記してください。無差別な `Throwable` 捕捉はテストコードのバグまで契約違反へ潰すため避け、ファイル不在・YAML parse 失敗・root 非 map をそれぞれ意図した例外または戻り値から分類する設計にしてください。

### 4. 期待効果の妥当性

[Suggestion] 既知 5 本の相対パス集合に対する包含検査は妥当です。完全一致を避ける理由も合理的で、新規 prompt は再帰全数走査による既定拒否へ委ねられます。

[Warning] 「負例9類型＋解決不能形」では、今回追加された `read()` の fail-closed 分岐をどこまで裏取りするかが曖昧です。ファイル不在、構文解析不能、root 非 map は別の分岐であり、「解決不能形」1件だけでは残りが未検証になり得ます。

修正提案: 自己テスト対象を次のように分けて明記してください。

- `evaluate()`：9類型と正例
- `read()`：ファイル不在、YAML parse 不能、root 非 map、正常ファイル
- `requirePositive()`：違反時の例外と正常時の正整数返却

これにより、収集した違反が上位 API で無視されないことまで確認できます。

### 5. リスク

[Suggestion] 実効値を保証しない範囲を docblock に、運用上の前提と再評価条件を `docs/architecture.md` に置く役割分担は適切です。同じ文章の複製ではなく、正本と道標を分けられています。

[Suggestion] vendor 解決順などを現時点では機械検査しないことも、保証範囲を明示する限り許容できます。将来の導入条件も具体的です。

### 6. スコープの適切さ

[Suggestion] `PromptYaml` の採用時債務へ踏み込まず、timeout の解釈だけを統一する範囲は適切です。台帳の「4本」を実装 PR の完了報告で5本へ訂正する扱いも、設計フェーズの書き込み制約と両立しています。

[Suggestion] `sop-extract-media` を3段パイプラインの `PROMPT_NAMES` へ加えない判断も妥当です。到達証明の分母と、deadline 算出上のステージ集合は別概念です。

### 7. 型安全性

[Suggestion] 本変更は PHPStan level 10 の検査対象外であることを正確に説明しています。array shape は静的保証そのものではありませんが、自己テストと `requirePositive(): int` を組み合わせ、呼び出し側から再解釈を排除する方向は妥当です。

[Warning] `evaluate(array<string, mixed> $parsed, ...)` はPHPのネイティブ型表記ではなく、PHPDoc で表現する型です。概念設計上の表記としては読めますが、実装契約として誤解が残ります。

修正提案: 実際のシグネチャを `evaluate(array $parsed, string $label): array` とし、直前のPHPDocで `@param array<string, mixed>` と厳密な戻り値 shape を宣言する、と明記してください。PHPStan対象外でも、IDEと将来の静的解析に正しい契約を渡せます。
