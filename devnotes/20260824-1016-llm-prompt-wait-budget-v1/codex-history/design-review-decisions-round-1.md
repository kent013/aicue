# 対応マトリクス: design-review Round 1

## [Warning] 施策1: ファイル不在 / parse 失敗 / 非 map の**分類**をテストしていない
- 判断: 対応する
- 根拠: 指摘のとおり。「違反が空でない + ファイル名を含む」だけでは、ファイル不在が
  再び parse 失敗へ統合されても緑のままで、概念設計で決着させた「独立ラベル」を固定できていない。
- 対応内容: 自己テスト 3 本目を `[$path, $expectedFragment]` の組で回す形に変更し、
  ラベルの**安定部分**を分類ごとに照合するようにした
  (`prompt YAML が無い` / `parse 失敗` / `top-level が連想配列(map)でない`)。
  vendor の例外本文は引き続き pin しない。test 名も
  「解決できない形は 3 種それぞれが**別の分類で**違反になる」へ改めた。

## [Suggestion] 施策1: `is_numeric` へ緩めたときに落ちるのは bool ではない
- 判断: 対応する
- 根拠: 事実。`is_numeric(true)` は `false`、`is_numeric(null)` も `false` なので、
  集合から落ちるのは `numeric-string` と `float` の 2 本だけである。
  設計に「3 本落ちる」と書くと実測と食い違い、負のコントロールの記録が嘘になる。
- 対応内容: 施策 1 のテスト計画の該当行を「`numeric-string` と `float` の 2 本が落ちる」へ訂正し、
  bool / null が違反のまま上がる理由も併記した。

## [Warning] 施策2: `catch` に関する docblock が実態を過大評価
- 判断: 対応する
- 根拠: `PromptWaitBudget` 自身は catch を書かないが、委譲先の
  `PromptYaml::parseOrFail()` が `catch (Throwable)` で囲んでいるので、
  「テストコード自身のバグを潰さない」とは言えない。
- 対応内容: docblock の段 2 の説明から当該の主張を削り、
  「分類は既存の共有ヘルパに従う。同ヘルパは `Yaml::parseFile()` の `Throwable` を
  まとめて parse 失敗へ分類するため、構文エラーと vendor 内部エラーの区別までは保証しない
  (ヘルパは採用時債務として凍結されており本 PR では変えない)」へ書き換えた。
  同じ限界を「保証しないもの」の一覧にも追加した。

## [Warning] 施策3: 到達証明は「再帰の破損」を検出できない
- 判断: 対応する (検出力の主張を狭める)
- 根拠: 指摘が正しい。既知 5 本はいずれも `resources/prompts` **直下**にあるので、
  `paths()` が非再帰へ退行しても 5 本は取れて緑になる。設計は限界として認識しながら
  test 名・失敗メッセージ・テスト計画・D50 の 4 か所で「再帰破損を検出する」と書いていた
  (AGENTS.md「検出力の主張の書き方」に反する)。
- 対応内容: 4 か所すべてを書き換えた。
  - test 名: 「走査の**列挙結果に**既知の prompt YAML が**含まれる** (分母の到達証明)」
  - 失敗メッセージ: 「走査根の改名・移動、または既知ファイルの削除・改名」
  - gate の docblock 保証しない項 3: 「全数性は `PromptYaml::paths()` の実装契約に依存する。
    既知 5 本は直下にあるので非再帰へ退行しても緑のままになる」
  - 定数の docblock / テスト計画 / リスク節 / D50 の 3 か所も同じ境界へ統一
  再帰まで裏取りするには探索根を引数で受ける検出器が必要で、採用時債務の `PromptYaml`
  変更を伴うため本 PR では広げない (指摘の判断に同意)。

## [Warning] 施策3: 不変条件 test 単独では分母 0 件を検出しない
- 判断: 対応する
- 根拠: 指摘のとおり。`expect($files)->not->toBeEmpty()` を到達証明の test へ分離すると、
  本体の test を `--filter` で単独実行したときに分母 0 件で緑になる。
  AGENTS.md「『違反が 0 件』と『母集団が 0 件』を区別する」に反する。
- 対応内容: 本体 test の冒頭に `$files = PromptYaml::paths();` +
  `expect($files)->not->toBeEmpty();` を戻し、
  「到達証明と重複するが**各不変条件 test を単独実行可能に保つため意図的に残す**」と
  コメントで理由を書いた。

## [Warning] 施策6: D50 が施策 3 の検出力を過大に記録する
- 判断: 対応する
- 根拠: 施策 3 と同じ問題が台帳側にも写っていた。台帳は**正本**なので、
  過大な記述を残すと後から読んだ人が「再帰まで守られている」と誤読する。
- 対応内容: D50 の「揃え続ける不変条件と保証機構」/ 比較表 / 「保証しないもの」を
  施策 3 と同じ境界 (全数性はヘルパの実装契約に依存 / 裏取りは現在の列挙結果への包含 /
  再帰性の退行は検出しない) へ統一した。parse 段の分類の限界も追加した。

## [Warning] 施策7: 読み取り器の利用経路の列挙から施策 5 が抜けている
- 判断: 対応する
- 根拠: 事実。施策 5 で `AnalysisTokenBudgetInvariantTest` が
  `requirePositive()` を直接呼ぶようになるので、2 経路の列挙は不正確になる。

  OCR 変種の突合 (`sop-extract-media.yaml`) を列挙した。波及変更の節にも明記した。

## [Warning] 施策7: 「実効タイムアウトである」の断定と「前提は機械で見ていない」が矛盾して見える
- 判断: 対応する
- 根拠: 指摘のとおり。同じ節に断定と「前提依存」が並ぶと読み手が混乱する。
- 対応内容: 施策 7 を「追記だけ」から「**(a) 既存箇条の 1 行目を条件付きへ書き換え + (b) 3 箇条の追記**」

  後続の「`config/prism.php` ではなく prompt YAML を見ること」は据え置く。
