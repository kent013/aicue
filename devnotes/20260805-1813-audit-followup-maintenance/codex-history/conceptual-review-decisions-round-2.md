# 対応マトリクス: conceptual-review Round 2

## [Warning] `--confirm` は「人間が確認した集合との一致」を保証しない (TOCTOU + hash の弱さ)

- 判断: **対応する**
- 根拠: 指摘は正しい。dry-run と apply が別プロセスである以上、token は「読んだ時点の状態」の
  指紋でしかなく、apply 側が**同じ入力を lock 下で再計算して照合**しなければ TOCTOU は閉じない。
  また区切りなしの連結は `["a_b","c"]` と `["a","b_c"]` を区別できず、sha1 先頭 8 桁は
  指紋として弱すぎる。「集合が変われば必ず不一致」「機械的に保証」という表現は撤回する。
- 対応内容:
  - token の入力を **canonical JSON** にする:
    `{"orphans":[...昇順...],"live_hashes":[...昇順...],"protected":[...昇順...]}`
    (JSON 配列なので要素境界が曖昧にならない)
  - token = **SHA-256 の全長** (先頭切り詰めをしない)
  - **apply は lock 取得後に DB 一覧・worktree 一覧を再取得して token を再計算し、
    `--confirm` と一致しなければ中止する** (不一致時は新しい token を表示して再確認を促す)。
    これで token は「指紋」ではなく **lock 下のスナップショット照合**になる
  - 表現を「集合が変われば必ず不一致」→
    「**apply は lock 下で判定入力を再計算し、人間が承認したスナップショットと一致する場合のみ実行する**」へ訂正

## [Warning] 別クローン (同一 PostgreSQL 共有) への防御が人間の目視だけ

- 判断: **対応する** (提案より踏み込んだ機械的な出自記録を導入する)
- 根拠: 指摘のとおり、DB 名の hash からは「削除済み worktree の残骸」と
  「別クローンの生存 DB」を区別できない。「由来不明は既定で除外」を素直に適用すると、
  **現存する 17 個はすべて由来不明なので 1 つも掃除できず、施策 4 が無意味になる**。
  したがって「区別できない」こと自体を解消する方が正しい —
  PostgreSQL には `COMMENT ON DATABASE` という出自記録の標準機構がある (先人の知恵)。
- 対応内容:
  - `scripts/ci/ensure-test-db.php` が base DB 作成時に
    **`COMMENT ON DATABASE <base> IS '<worktree の realpath>'`** を記録する (1 文追加)。
    以後に作られる test DB は出自が**機械判定可能**になる
  - 孤児 sweep は `shobj_description` で出自を読み、hash ごとに 4 分類する:

    | 分類 | 条件 | 既定の扱い |
    |---|---|---|
    | live | hash が生存 worktree hash 集合に含まれる | **保持** |
    | foreign | ラベルあり / ラベルの path が実在する (= 別クローンが生きている) | **保持** + 報告 |
    | orphan (確度高) | ラベルあり / ラベルの path が実在しない | DROP 候補 |
    | unlabeled (確度低) | ラベルなし (本施策以前に作られた legacy、または base 不在の worker のみ) | **既定は除外**。`--include-unlabeled` を明示したときだけ候補 |

  - `--protect-hash=<hash>` を**複数指定可**にする (既知の別クローンを明示保護)
  - dry-run 出力に **「所有元を確認できない hash」を明示**する
  - 現存 17 個は全て unlabeled なので、**初回の回収は `--include-unlabeled` + `--confirm` +
    人間の明示指示**の 3 点が揃って初めて実行される
  - 詳細設計の受入条件に「apply 前に、同一 PostgreSQL を共有する別チェックアウトが無いことを
    確認する具体的手順」を含める

## [Warning] 「実装は必ず worktree」と「施策 5 を main で実行する contingency」が矛盾

- 判断: **対応する** (contingency を撤回する)
- 根拠: 指摘のとおり AGENTS.md §worktree 運用ルールへの正面からの抵触であり、
  「うまくいかなかったら main で」は禁止事項の骨抜きになる。
- 対応内容: **C2 は task worktree の branch/index で完結させることを原則かつ必須**とする。
  worktree 上で完結できないことが実証された場合は「通常の代替経路」ではなく
  **人間の明示的な例外承認を要する停止条件**として扱う (設計にそう明記する)。

## [Warning] 実測値の内部不整合 (重複 blob 55 vs 衝突グループ 58)

- 判断: **対応する** (両者は別指標。定義を明記して統一する)
- 根拠: 再実測して原因を特定した。2 つは異なる指標である:
  - **「重複 blob 55」** = index 内で **2 回以上出現する distinct blob hash の個数**
    (`git ls-files -s | awk '{print $2}' | sort | uniq -d | wc -l`)。
    出現回数の内訳は 2 回×42 / 3 回×3 / 4 回×7 / 6 回×3 で、
    **NFC/NFD 由来ではない「内容が同じ別名ファイル」も数えている**
    (distinct blob 総数 113 に対する重複)
  - **「NFC 正規化衝突グループ 58」** = path を NFC 正規化したときに衝突する group 数
    (全て size 2、blob 一致 58/58)
  58 組が 55 個の distinct hash に収まるのは、**異なる衝突グループ同士が同一内容の画像**である
  ためで、矛盾ではない。
- 対応内容: 背景表の「重複 blob 55」に算出定義を併記し、
  **C1 の fail-fast 基準は「NFC 正規化衝突 58 / blob 一致 58 / NFC 相手なし 0 / 197−58=139」の
  4 条件のみとする** (55 は判定に使わない) と明記する。
