[Warning] AC4は以前より改善しましたが、古いJUnitファイルによる偽グリーンが残ります。

2つのコマンドが独立しているため、テスト実行が失敗しても、その後に以前生成された22件のXMLを読むと件数判定が成功します。AC3とは別に、AC4自身も完結した判定にする必要があります。

修正案:

```bash
JUNIT_FILE="${TMPDIR:-/tmp}/env-example-invariant-junit.xml"
rm -f "$JUNIT_FILE"

composer test -- --filter=EnvExampleInvariant \
  --log-junit="$JUNIT_FILE" &&
python3 -c "import sys, xml.etree.ElementTree as E; \
p=sys.argv[1]; n=sum(1 for _ in E.parse(p).iter('testcase')); \
print(n); sys.exit(0 if n == 22 else 1)" "$JUNIT_FILE"
```

より堅くするなら`mktemp`と`trap`を使い、実行ごとに一意な出力先を作ります。

[Warning] `vendor/bin/pest`の直接実行という逃げ道は、AGENTS.mdのグローバルテストロック運用と整合しません。

DBやポートを使わないという局所的な安全性は理解できますが、規約は`composer test`などのテスト実行をホスト全体で直列化する運用です。個別判断でロック外実行を認めると、実行経路が二重化します。

修正案:

- `vendor/bin/pest`を直接使う逃げ道を削除する。
- `--log-junit`がラッパーを通らない場合は、既存のロック機構を通る別コマンドを使うか、件数確認方法を`composer test`で利用可能な方式へ変更する。
- 実装時に実際に`--log-junit`が通ることを確認し、通るなら例外説明自体を置かない。

[Warning] AC5は行IDを検査しますが、「コミットされた証跡」であることまでは検査していません。

未追跡ファイルでも`grep`は成功するため、AC5の条件文との間に差があります。

修正案として、ループ前に次を追加してください。

```bash
git ls-files --error-unmatch "$EV" >/dev/null || exit 1
```

また、IDの存在確認は証跡の内容が正しいことまでは保証しません。その保証範囲は「11個の証跡行IDが一意に存在する」までと明記すると誇張がありません。
