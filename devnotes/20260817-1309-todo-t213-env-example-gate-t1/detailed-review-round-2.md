## 指摘

[Warning] 段2の「現行 t0 では緑」の記述が、B2b の実際の挙動と矛盾しています。

B2b は既存行を `SESSION_ENCRYPT=false` に書き換えるため、現行 t0 の次の検査も赤になります。

```php
expect($contents)->toContain('SESSION_ENCRYPT=true');
```

したがって、次の記述は誤りです。

> B1 と B2b は現行の t0 の 5 本では緑のまま通る

修正案:

- t0 で偽グリーンになるものを「B1 と B2」に修正する。
- B2b は「新旧どちらも赤になるが、新実装では行単位の値比較として検出する」と整理する。

[Warning] AC4 のコマンドは件数を表示するだけで、22件以外でも成功終了します。

現在の `python3 -c` は、たとえば21件でも `21` を表示して exit 0 になります。したがって、CIや手順の機械的な合否判定にはなっていません。

修正案:

```bash
python3 -c "import sys, xml.etree.ElementTree as E, os; \
p=os.environ.get('TMPDIR','/tmp')+'/env-example-invariant-junit.xml'; \
n=sum(1 for _ in E.parse(p).iter('testcase')); \
print(n); sys.exit(0 if n == 22 else 1)"
```

[Warning] AC5とAC6は、条件が書かれているだけで、提示された検証方法では条件全体を機械判定できません。

AC5の「ファイルの存在と表の行数」には具体的なコマンドや構造化された識別子がありません。Markdown表の目視確認なら「機械検証可能」という表題と食い違います。

AC6の`rg`は「他ファイルにも該当文字列があるか」は確認できますが、次は確認しません。

- 新設名が10種類ちょうどか
- 各定数・関数の宣言が1回だけか
- `ENV_EXAMPLE_`を含むコメントや参照行を名前として誤集計していないか

修正案:

- AC5は証跡表の各行に`R1A`、`R1B-1`、`B1`などの固定IDを持たせ、それぞれ1件存在することを検査するコマンドを示す。
- AC6は宣言だけに対象を絞り、抽出した名前を`sort -u`した件数と、宣言総数の両方を10と比較する。
- そこまで自動化しないなら、AC5・AC6を「レビュー確認」と明記し、「全条件が機械検証可能」という主張を狭める。

[Suggestion] 段2の説明にまだ「6通り」とありますが、B2b追加後はB1、B2、B2b、B3、B4、B5、B6の7通りです。「7通り」に直すとAC5の記述とも一致します。
