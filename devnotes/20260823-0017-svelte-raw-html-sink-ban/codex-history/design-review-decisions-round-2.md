# 対応マトリクス: design-review Round 2

Round 1 の Critical 2 件は Codex 再判定で **解消済み**と確認された。
Round 2 の新規 Warning 3 件 + 実装順の記述誤り 1 件はすべて **対応する**（反論・見送りは 0 件）。

## [Warning] 施策 4 — C' の「近縁形」の期待値が曖昧で、検出契約と衝突しうる
- 判断: **対応する**
- 根拠: 指摘が正しい。検出器の契約は「部分文字列 `{`+`@html` を含めば違反」なので、
  **禁止文字列を内包する接尾辞つきの形は正例ではなく違反**である。
  そこに「接頭辞つき・打ち消しつき・接尾辞つきの 3 形を正例に置く」と書くと、
  実装者が矛盾した期待値を書くことになる。
  さらに AGENTS.md (e) の 3 近縁形要件は「**許可語を否定的に除去する照合**」に対する規約であり、
  **許可一覧を持たない**本検出器には適用されない（(e) の適用範囲の読み違いだった）。
- 対応内容: C' の期待値を `true` / `false` の 2 表に明示的に書き分けた。
  「接頭辞つき・打ち消しつき・接尾辞つき」の記述と (e) への言及は削除した。
  代わりに **`{@htm value}`（禁止文字列を内包しない近い綴り）** を `false` 側の正例に入れ、
  **禁止文字列を内包する接頭辞・接尾辞つき** を `true` 側に入れた。

## [Warning] 施策 4 — F の「ignored 扱いを落とす」が実装表に無く、fatal/ignored の恒久的負例も無い
- 判断: **対応する**
- 根拠: 指摘が正しい。docblock で宣言した ignored 判定が実装表に落ちておらず、
  **宣言と実装の乖離**（AGENTS.md が最も嫌う「守っているつもりの穴」）になっていた。
  加えて B/B'/D はすべて正常に parse される入力なので、
  **F の検査を削除・破壊しても誰も気付かない**（(c) 未適合）。
- 対応内容:
  - 純関数 `assertLintExecutionUsable(result, isIgnored)` を切り出した。
  - 各仮想パスについて ESLint 公開 API `isPathIgnored(filePath)` も確認する検査を足した。
  - **恒久的な正負コントロール**（正例 1 / 負例 3: `fatalErrorCount > 0` /
    `message.fatal === true` / `ignored === true`）を合成入力で追加した。
    これで F も (b)(c) を機械で裏取りでき、「最初から green」問題も解消する。

## [Warning] 施策 7 — 現在の負のコントロールでは token 完全一致の検出力を裏取りできない
- 判断: **対応する**
- 根拠: 指摘が正しい。`img-src 'self'`（`data:` が無い）で落ちることは、
  **素朴な部分文字列実装でも同じく落ちる**ので、防ぎたい誤検出
  （`https://data:443` を `data:` と誤認する）を区別できない。
  負のコントロールが**押さえるべき分岐を押さえていない**。
- 対応内容: helper `cspDirectiveSources()` への**合成入力テスト**に置き換えた
  （`img-src 'self' data:` → 含む / `img-src 'self' https://data:443` → **含まない** /
  `script-src 'self'; img-src 'self' data:` → 正しい directive を選ぶ /
  タブ区切りでも token 化できる）。
  config を書き換える負のコントロールは廃止した（helper 直接テストの方が強い）。
- 併せて: AGENTS.md 走査器共通規約 (e) を Feature テストへ「直接適用」と書いていた説明を
  **外した**。同規約の形式的な対象は `tests/Support/` と Architecture gate であり、
  ここへ (e) を持ち出すのは規約の適用範囲の誇張である。
  完全一致を採る理由は「CSP 判定の正確性」だけで十分に説明できる（そう書き直した）。

## [誤り] 実装順 — 「`return false` にすると C と C' が赤くなる」は誤り
- 判断: **対応する**（設計の記述誤り）
- 根拠: Codex の指摘が正しい。現行 `Security.svelte` に違反がある状態で
  `containsRawHtmlSink()` を `return false` にすると、
  **C は違反を見逃して green になる**（赤くなるのは C' の違反入力側だけ）。
  つまり自分で書いた文が「C' が必要な理由」を否定していた。
- 対応内容: 段 1 の記述を次に差し替えた。
  1. C' の違反入力テストを先に書き、`return false` の stub で **C' が赤くなる**ことを確認する
  2. 実装して C' を green にする
  3. その状態で統合検査 C が現行 `Security.svelte` の 1 件を検出して赤になることを確認する
  4. **`return false` へ戻すと C は green になってしまう** — だから C' が恒久的な検出力を担う
  D が最初から green なのは正例なので問題にしない。
  F は上の fatal/ignored 合成負例の追加により「最初から green」問題が解消する。
