# 対応マトリクス: design-review Round 1

## [Critical] 施策 2 — 新部品の docblock が施策 4 の検査 C に**自己違反**する
- 判断: **対応する**（指摘は完全に正しい）
- 根拠: 検査 C は「`resources/js` 配下の `.svelte` 本文に文字列 `{@html` が 0 件」を
  **コメント内も含めて**数えると宣言している。
  一方で提案した `QrCodeImage.svelte` の docblock はその字面を複数回含む。
  つまり**唯一の実サイトを消しても C は緑にならない**。設計の内部矛盾である。
  対処は 2 択で、(a) コメント側で字面を使わない / (b) 走査器を構文解析にしてコメントを除外。
  (b) は AGENTS.md (a) の但し書き「構文解析ライブラリの使用は必須ではない」に照らして
  過剰であり、かつ**コメント内の字面も違反として数える方が fail-closed 側**である。
  よって (a) を採る。
- 対応内容:
  - **`resources/js` 配下の `.svelte` では禁止構文の字面を書かない**ことを
    明示的な運用契約として設計に格上げした（`QrCodeImage.svelte` /
    `Security.svelte` の両コメントを字面なしに書き換え、
    「raw HTML 挿入構文」「生 HTML を DOM へ差し込む構文」と呼ぶ）。
  - 検査 C の docblock にこの契約の理由を書き、
    **禁止の字面を書きたくなったら `DESIGN.md` か gate 側（走査対象外）へ書く**と案内する。
  - 設計に「実装時に全 `.svelte` 提案本文へ同じ部分文字列検査をかけてから入れる」手順を足した。
  - 走査対象外である `eslint.config.js` / `DESIGN.md` / gate 自身は字面を書いてよい
    （むしろ gate は負例入力として**必要**である）ことを明記した。

## [Critical] 施策 4 — 直接走査 C の検出力を裏取りする恒久的な負例・正例が無い
- 判断: **対応する**
- 根拠: 指摘のとおり。「実装前に現行 `Security.svelte` で赤を見る」のは**一度きり**の確認で、
  違反を消した後に走査器を壊してもテストは緑のままになる。
  B/B' は ESLint 規則の検出力であり、C の文字列走査とは**別の機構**である。
  AGENTS.md 走査器共通規約 (c)「検出力は負例で裏取りする」と
  「新設・変更時に揃える 4 点」の 1 に未適合。
- 対応内容: 検査 C を純関数 `containsRawHtmlSink(source: string): boolean` に切り出し、
  合成入力による**恒久的な**負例・正例を追加した（検査 C2）。
  実ファイルの本文も同じ関数へ渡し、収集結果を最終判定に必ず使う（(d) 対応）。

## [Warning] 施策 4 — 検査 A が仮想パス 1 件では「全 `.svelte` で error」を保証しない
- 判断: **対応する**
- 根拠: 正しい。特定ファイル向け override で規則を off にされたら代表 1 件では見逃す。
  「許可一覧の口を持たない」(I6) という設計とも整合しない。
- 対応内容: 検査 A を **C が収集した実在 `.svelte` 全件**（実測 123 件）について
  `calculateConfigForFile()` を回す形に変えた。違反パスは一覧で報告する。
  これで**同じ母集団を A と C の両方が判定に使う**ことになり、(d) にも合致する。

## [Warning] 施策 4 — 「lint 実行失敗は throw される」だけでは fail-closed にならない
- 判断: **対応する**
- 根拠: 正しい。ESLint は構文解析エラーを throw せず
  `LintResult.messages` の fatal message として返すことがある。
  対象 rule の件数だけを見ると**解析失敗を正常扱い**してしまう
  （特に B'（error が 0 件になること）と D（0 件であること）は
  「解析に失敗して何も出なかった」と区別が付かない = 典型的な fail-open）。
- 対応内容: 全 `lintText()` 結果について
  `fatalErrorCount === 0` かつ `messages` に `fatal === true` が無いことを
  **対象 rule の件数を見る前に**確認する検査 F を追加した。
  ignored file 扱い（`warningCount` に "File ignored" が出る形）も正常扱いしない。

## [Warning] 施策 2 — `class` prop を「万一のため」に残すのは思考原則 2 に反する
- 判断: **対応する**
- 根拠: 正しい。呼び出し箇所は wrapper 側で寸法・装飾を管理しており `class` を渡さない。
  「あったら便利」は作らない（AGENTS.md 思考原則 2）。
- 対応内容: `class` prop を**初版から削除**。props は `svg` / `alt` / `testId` の 3 つ。
  施策 5 のテストと施策 8 の `DESIGN.md` からも `class` を除いた。
  将来寸法差が要るときは任意 class ではなく DS 制約付き prop を検討する、と申し送りに残した。

## [Warning] 施策 5 — 検査 3 の記述が本文とリスク節で矛盾
- 判断: **対応する**

## [Warning] 施策 7 — `/img-src[^;]*\bdata:/` は CSP source の完全一致になっていない
- 判断: **対応する**
- 根拠: 正しい。`https://data:443` のような別 source の部分列にも一致し得る。
  AGENTS.md 走査器共通規約 (e)「語彙一致は区切り文字で分割したトークンの完全一致で判定する。
  正規表現の語境界や素の部分文字列一致に頼らない」に直接該当する
  （本件は CSP という**区切りが明確に定義された**文字列なので (e) が効く場面である）。
- 対応内容: `;` で directive へ分割 → ASCII 空白で token へ分割 →
  directive 名が `img-src` のものを取り、source token に `data:` が
  **完全一致で**含まれることを検査する型付き helper
  (`@return list<string>`) を設計に書いた。既定・GTM の両構成に同じ helper を当てる。
