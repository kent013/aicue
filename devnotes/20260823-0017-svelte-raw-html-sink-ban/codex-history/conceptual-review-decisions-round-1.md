# 対応マトリクス: conceptual-review Round 1

## [Warning] 3. 実現可能性 — data URI のエンコード方式と props 契約が未確定
- 判断: **対応する**
- 根拠: 指摘は正しい。SVG 文字列をそのまま連結すると `#` (fragment 開始) で切れ、
  `%` は不正な percent escape になり、非 ASCII は URI として壊れる。
  ここは「値を弄る」話ではなく**契約の欠落**なので概念設計の段で決めるべきである。
- 対応内容: 概念設計へ次を明記した。
  - props は `svg: string` (必須) / `alt: string` (必須) の 2 つだけ。
  - `src` は `data:image/svg+xml,${encodeURIComponent(svg)}` で生成する
    (base64 を採らない理由も併記 — `btoa` は UTF-8 で例外を投げ、
    `TextEncoder` 経由の base64 化は同じ安全性のために手数が増えるだけである)。
  - 部品テストで「`img` が出る」「`alt` が渡る」「`src` が期待どおりエンコードされる」
    「生の `<svg>` 要素を DOM に出さない」を固定する。

## [Warning] 4. 期待効果 — 「外部リソースも取得しない」は断定が強すぎる
- 判断: **対応する**
- 根拠: 主張の強さと保証機構が釣り合っていない。
  本設計が機械で固定するのは「`{@html}` が 0 件であること」と
  「`img-src` に `data:` が居ること」までであり、
  browser の画像文脈における SVG の細部挙動は**本設計の検査対象ではない**。
  AGENTS.md が繰り返し求める「保証範囲を誇張しない」に照らして、書き換える。
- 対応内容: 安全根拠の記述を
  「DOM への HTML 挿入をやめ、SVG を**画像リソースとして**扱う経路へ移す」
  + 「本設計が機械で固定するのは 4 点そろいだけである」に改めた。
  外部取得に関する包括的保証の主張は削除した。

## [Warning] 5. リスク — 無効化コメント 3 形式が文面上あいまい
- 判断: **対応する**
- 根拠: 「3 形式を負例に持つ」は正典の要求そのものであり、
  **どの構文をどこに置くか**が決まっていないと
  「ESLint が inline configuration として解釈すらしていない文字列」を
  負例と称して緑になる — つまり検出力の裏取りが空振りする。
  AGENTS.md の走査器共通規約 (c)「検出力は負例で裏取りする」の趣旨に直結する。
- 対応内容: 3 形式を具体的な構文と配置で確定して概念設計に書いた。
  さらに **「その 3 形式が `noInlineConfig: false` の対照条件では実際に error を消せること」**
  を同じ gate で確かめる (= 負例が負例として効いている裏取り) ことを足した。
  これが無いと「3 形式が元から効かない文字列だった」場合に区別が付かない。

## [Warning] 7. 型安全性 — atom に nullable を吸収させない
- 判断: **対応する**
- 根拠: 指摘のとおり。`qrSvg: string | null` の分岐は既存の状態機械
  (取得失敗 Alert / step-up / 世代管理) が持っており、
  atom がもう一度 null を吸収すると**分岐の正本が 2 か所**になる。
- 対応内容: `svg: string` を必須にし、`Security.svelte` 側は既存の `{#if qrSvg}` 分岐の
  内側でのみ描画する、と明記した (既存の分岐構造は変えない)。
