全体として Round 1 の主要な設計欠陥はほぼ閉じていますが、A-6b が現状の差分定義では成立しない点と、既知出現の pin が旧名ごとの内訳を固定していない点が残っています。

## 施策 1: REQUEST_CHANGES

[Warning] `BUGHUNT_NAMING_KNOWN_MENTIONS` が旧名の合計件数しか pin していません。

現在の述語は、2つの旧名の出現数を `$total` に合算して `2` と比較します。そのため、例えば次の変化を検出できません。

- `BughuntBillingSeeder`: 1件 → 0件
- `FakeExternalsServiceProvider`: 1件 → 2件
- 合計: 2件のまま

これは「過去の事実として残す名前」を別の旧名へ書き換えても緑になるため、件数 pin として粒度が不足しています。

修正案: ファイルごと・旧名ごとの件数を固定してください。

```php
const BUGHUNT_NAMING_KNOWN_MENTIONS = [
    'docs/TODO-closed.md' => [
        'BughuntBillingSeeder' => 1,
        'FakeExternalsServiceProvider' => 1,
    ],
];
```

実測値が異なる場合は、その実測値を登録します。N-4にも「合計は同じだが内訳が違う入力」を追加すると、同じ述語による負のコントロールになります。

[Warning] 「保証しないもの」の記述が新設した件数 pin と矛盾しています。

末尾では次のように書かれています。

> `docs/TODO-closed.md` / `devnotes/` の旧名  
> 帰結として、この2か所では旧名の再流入に沈黙する

修正後の設計では `docs/TODO-closed.md` の増減は検出されるため、沈黙するのは `devnotes/` と自己除外ファイルだけです。

修正案: `docs/TODO-closed.md` と `devnotes/` を別行に分け、前者は「既知件数を許容するが増減は検出」、後者は「丸ごと除外のため再流入に沈黙」と記述してください。

[Suggestion] `devnotes/` の丸ごと除外は妥当です。

過去記録を含む約190ファイルについて、旧名ごとの件数 pin を保守する費用は目的に見合いません。現役資産ではないこと、保証の穴を明記していること、既存Architectureテストに同じ分類があることから、deny-by-defaultを不当に弱める除外とは判断しません。

## 施策 4: REQUEST_CHANGES

[Critical] A-6bが現在の変更後コードとは一致せず、そのままでは必ず不合格になります。

`FakeClassCatalog::placementExceptions()` の理由文字列が、改名前より長くなっています。

```php
BughuntFakesServiceProvider::class =>
    '...名前の規則では拾えないため参照走査の候補としてここに残す。',
```

この理由はコメントではなく文字列リテラルなので、`token_get_all()`では実行トークンとして残ります。逆置換後も旧内容とは一致せず、A-6bが許可する次の2差分以外に、3つ目の差分が発生します。

1. 3-10の候補集合変更
2. 4-3の明示assertion
3. `placementExceptions()`の理由文字列変更

修正案: 「名前の規則では拾えないため……」という説明はdocblockだけに置き、理由文字列はクラス名の逆置換後に旧内容と一致する形へ戻してください。そうすればA-6bの「実行トークン差分は2か所だけ」が成立します。

理由文字列にも残す必要があるなら、A-6bへ3つ目の許可差分として明示し、「振る舞い完全不変」ではなく「許可した検査メタデータ変更のみ」と位置付ける必要があります。

[Warning] A-6a/A-6bは検証方針として妥当ですが、実行手段がまだ一意に定義されていません。

特に次が未確定です。

- 変更ファイルの母集団を何から導出するか
- rename前後のパス対応をどう取得するか
- トークン列の差分を「2か所」と判定する具体的な境界
- 対象ファイルの取りこぼしをどうfail-closedにするか

文章を読みながら手作業で比較する場合、機械検証可能な受け入れ条件とは言い切れません。

修正案: 実装セッション内の一時検証スクリプト、またはArchitectureテストとして次を固定してください。

- `git diff --name-status -M main...HEAD`から母集団を導出
- 全変更ファイルがA-6a/A-6b/A-6cのいずれか1つに分類される
- 未分類・重複分類は失敗
- rename行から旧パスと新パスを取得
- A-6bは許可する追加トークン列そのものを固定し、それ以外の差分を失敗

恒久テストにする必要はありませんが、検証コードまたは再実行可能なコマンドを実装記録に残すべきです。

[Suggestion] 「振る舞い完全不変」という表現は保証範囲を少し超えています。

逆置換後のバイト一致と限定的なトークン差分は、意図しないソース変更がないことを強く示しますが、autoload、キャッシュ、外部スクリプト、動的クラス名などを含む振る舞いの同値性そのものを証明するわけではありません。

A-6の見出しを「意図しない実行コード差分がない」にし、振る舞いについては既存Feature/Architectureテストと全体テストで担保する、と分ける方が保証を正確に表現できます。

候補集合へ`placementExceptions()`を加え、4-3でproviderとgateの包含を明示する対応自体は、Round 1のCriticalを閉じています。関数名を維持する判断も、docblockとassertionで削除事故を機械検出する限り妥当です。

## 受け入れ条件

[Warning] A-5の`git log --follow`は「git mvを使ったこと」の証明にはなりません。

Gitはrename操作を履歴へ記録せず、内容の類似度からrenameを推定します。`git mv`を使わなくても成立し、逆に内容差分が大きければ`git mv`を使っても追跡できないことがあります。

修正案: 条件を「改名前の履歴がrename検出によって追跡可能」に変更してください。操作手段としての`git mv`は実装手順に残し、機械的受け入れ条件とは分離するのが正確です。

A-9の総テスト数pin撤回は適切です。新設テスト、指定invariant、全体失敗数を分けたことで、失敗時の意味も読み取れるようになっています。
