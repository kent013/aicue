## 施策 4: REQUEST_CHANGES

[Critical] A-6スクリプトの差分母集団が`main...HEAD`なので、未コミットの実装と結果ファイルを認識しません。

検証手順では、空の`rename-verification.md`を置くことで「差分に現れる状態を作る」とあります。しかし、次のコマンドが見るのはコミット済みの`HEAD`までです。

```bash
git diff --name-status -M main...HEAD
```

ファイルを作成・更新しただけでは母集団に入りません。同様に、実装変更が未コミットならA-6a/A-6bの対象にも入りません。その状態でスクリプトが通っても、最終ワークツリーの差分を検証していない偽グリーンになります。

修正案は、次のどちらかを明示してください。

1. 検証前のチェックポイントコミットを必須にする。

   - 実装と空の結果ファイルをコミット
   - スクリプトを実行
   - 結果を書き込んでコミットまたはamend
   - 最終HEADに対して再実行
   - 2回目の出力と保存済み結果が一致
   - 最終的にワークツリーがcleanであることも確認

2. スクリプトの母集団をワークツリー対応にする。

   - `main`から現在のindex・working treeまでの変更を取得
   - untrackedファイルも別途列挙
   - staged、unstaged、untrackedを統合
   - 同一パスの重複状態を正規化
   - 実行中の出力ファイル更新によるTOCTOUを避ける

この用途では、1のチェックポイントコミット方式の方が単純です。`main...HEAD`を維持でき、rename検出も安定します。

[Warning] A-6の「未分類」規則と「残りをすべてA-6a」の規則は表現上矛盾しています。

A-6b/A-6c/A-6e以外を無条件でA-6aへ入れるなら、未分類は発生しません。未知の追加ファイルはA-6aの比較で落ちる可能性がありますが、「未分類で落ちる」のではありません。

修正案: 規則を次のように明文化してください。

- `R`/`M`: A-6b、A-6eの明示一覧に該当しなければA-6a
- `A`: A-6cまたはA-6eへの明示登録を必須とし、それ以外は未分類で失敗
- `D`: 無条件で失敗
- 各明示一覧の重複と、一覧にあるのに差分にないパスも失敗

これなら新規ファイルをA-6aへ誤分類して`git show`失敗に依存せず、分類段階で明確に拒否できます。

[Suggestion] 施策4の背景にある「将来providerが別の配線基盤クラスを名指しした場合」という説明は正確ではありません。

候補集合へprovider自身を加えることで増えるのは、主に`BughuntFakesServiceProvider`への参照検出です。他の配線基盤クラスの検出可否は、その別クラス自身が候補集合に含まれるかで決まります。

候補集合を統一する変更自体は妥当ですが、説明は「providerクラス自身が候補集合から脱落することを防ぐ」と留める方が正確です。
