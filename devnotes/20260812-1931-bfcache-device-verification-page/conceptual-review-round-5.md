全体判定: **CHANGES_REQUESTED**

Round 4 の承認条件だった `/login` 到達の扱いは閉じています。手動確認と2枚の証跡セットに限定し、完全自動判定を主張しない判断は妥当です。派生 verdict を表示時に導出する方針も正しいです。

ただし、修正方針と本文の間に2件の不整合が残っています。いずれも小さな修正ですが、保存済み証跡の成立条件に関わるため、現状のまま APPROVED にはできません。

## 1. 使命との整合性

[Suggestion] 使命との整合性は保たれています。

失効セッション経路と有効セッション経路の両方を必須にすることで、PII 非露出と撮影状態の温存を対で確認できます。正のコントロールを必須にした判断も妥当です。

## 2. 禁止事項違反

[Suggestion] 明確な禁止事項違反はありません。

検証対象、既存 logout 契約、JSON endpoint、production 認証ページに変更を加えない方針は維持されています。Architecture テストも実装範囲に含まれています。

## 3. 実現可能性

[Critical] 手入力する端末情報が sessionStorage の保存 allowlist に含まれていません。

試行開始時に次を入力し、stored report の必須表示項目にすると定義されています。

- 端末モデル
- 確認済み OS バージョン

しかし「保存可」の列挙にはこれらがありません。失効セッション経路では `/login` を経由して A を再読込するため、保存しなければ stored report で復元できません。保存すれば現行 allowlist 違反です。

修正提案:

保存可に、用途を限定した型付きフィールドとして次を追加してください。

- `deviceModel`
- `verifiedOsVersion`

これらは自由記述ではなく、最大長と使用可能文字を制限し、氏名等を入力しない旨を画面に示します。保存された値は「利用者申告」として表示し、自動観測値とは引き続き区別してください。

または、端末情報を event log 外の証跡メタデータとして保存する設計も可能ですが、その場合も保存先、検証、allowlist を定義する必要があります。

## 4. 期待効果の妥当性

[Suggestion] 「1枚」の主張を撤回し、証跡セットとした修正は適切です。

手動確認で証拠強度が自動観測より低くなる点も明示されており、期待効果を誇張していません。

詳細設計では、2枚の画像が同じ試行に属することを devnotes 上で関連付ける手順を定めてください。これは概念設計の承認阻害事項ではありません。

## 5. リスク

[Warning] `/login` のスクリーンショット単独では、試行 IDとの対応を証明できません。

手動確認方式を採用する以上、この限界は受容可能ですが、`RedirectObserved` は「画像から自動的に裏付けられた事実」ではなく「利用者による確認記録」です。

修正提案:

- `RedirectObserved` に確認者入力を要求する必要はないが、`observationMethod: 'manual'` を固定値で持たせる
- stored report に「manual confirmation」と明示する
- devnotes で `/login` 画像と trial IDを同一証跡セットとして関連付ける

具体的なファイル命名や貼付形式は詳細設計事項です。

## 6. スコープの適切さ

[Suggestion] スコープは適切です。

production の `/login` や guard に debug ロジックを持ち込まず、手動確認の限界を明記して受け入れる選択は、「今必要なものだけ作る」という原則に沿っています。

## 7. 型安全性

[Critical] append-only event log 節に、撤回済みの設計が残っています。

同節には次の記述があります。

> 最終 verdict もイベントとして追記する

一方、型境界では正しく次の方針へ変更されています。

- union から `TrialVerdict` / `GuardVerdict` を削除
- event log には観測事実だけを保存
- 全 verdict は表示時に純粋関数で導出

両者は直接矛盾します。

修正提案:

「最終 verdict もイベントとして追記する」を削除し、append-only event log 節も次に統一してください。

> event log には観測事実のみを追記する。軸1、軸2、総合判定は保存せず、検証済みイベント列から表示時に純粋関数で導出する。

[Suggestion] `RedirectObserved` を union に追加した判断は適切です。

詳細設計では、runtime validator がイベント種別ごとに余分なキーを拒否し、手入力フィールドの長さも検証すれば、TypeScript の型境界を維持できます。PHP DTO は不要で、PHPStan level 10への悪影響も見当たりません。

## 結論

`/login` 到達の証明方法、正のコントロール、append-only モデル、保存不能時の扱いという主要な概念判断は承認できます。

残る承認条件は次の2点だけです。

1. 端末モデルと確認済み OS バージョンを保存 allowlist と型へ整合させる  
2. 「verdict もイベントとして追記する」という残存記述を削除する  

これらを修正すれば、残りは runtime validation、保存 read-back、証跡ファイルの関連付け、iOS Safariと standalone の具体的操作手順など、詳細設計で詰める事項だけになります。
