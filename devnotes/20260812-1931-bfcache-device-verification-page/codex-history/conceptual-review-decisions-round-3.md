# 対応マトリクス: conceptual-review Round 3

Round 3 の指摘は全件受け入れ（反論なし）。うち 1 件（正のコントロールの位置づけ）は
「決めよ」という指摘なので、根拠を添えて**必須**と決定した。

## [Critical] 軸 1 に `incomplete` が無い (§3)
- 判断: **対応する**
- 根拠: 指摘が正しい。「離脱したがまだ復帰していない」「操作を中断した」
  「Safari が履歴項目を破棄した」「`pagehide` だけあって `pageshow` が無い」は
  既存 4 分類のどれでもない。これらを `inconsistent` に落とすと
  **観測値の矛盾と単なる未完了が混ざる**。
  また「A 以外へ復帰」は A の JS が動かなければ A 自身に判定できない、という指摘も正しい。
- 対応内容:
  - 軸 1 に **`incomplete`** を追加（試行開始済みだが判定可能な離脱・復帰の組が未成立）
  - `invalid-wrong-route` の定義を「**A が実際に再表示された**うえで、対応する lifecycle が無い」に限定
  - 観測できない場合は `incomplete` のままにする
  - **タイムアウトで自動的に失敗へ変換しない**。利用者が「試行を中止」と確定する
    （`TrialAborted` イベント）

## [Warning] `pagehide.persisted` の「原則」が判定規則に残っている (§3)
- 判断: **対応する**
- 根拠: 機械判定に「原則」は書けない。曖昧さがそのまま誤判定になる。
- 対応内容: `valid-bfcache` の必要十分条件を 5 つに厳密化した。
  `pagehide.persisted === true` / `pageshow.persisted === true` / 離脱前後の **full token** 同一 /
  同一 trialId・同一 A route / 離脱イベントと復帰イベントの順序が正しい。
  「原則」は説明文にのみ残し、判定条件から外した。
  `pageshow.persisted=true` かつ token 同一だが `pagehide.persisted=false` は
  定義どおり `inconsistent`。

## [Warning] 「書き写し誤りが原理的に消える」は成立しない (§4)
- 判断: **対応する**
- 根拠: 指摘が正しい。UA から得られる OS バージョンは受入記録に必要な
  端末名・正確な OS バージョンと一致しない（UA reduction / iPadOS の desktop-class UA /
  standalone と Safari の差）。効果を誇張していた。
- 対応内容:
  - 自動取得値は **「UA reported OS」** と明記する
  - **端末モデルと確認済み OS バージョンは試行開始時の手入力項目**にする
  - 自動取得できない値を推測しない
  - 証跡上で**手入力値と自動観測値を区別**する
  - 期待効果の記述を「**イベント観測値の書き写しをなくす / 環境情報の転記を減らす**」に修正

## [Warning] 「immutable record」と「都度追記」が矛盾 (§5)
- 判断: **対応する**
- 根拠: 指摘が正しい。同じ record に追記するならそれは immutable ではない。
  用語が不整合だった。配列全体の read-modify-write は途中状態の破損も招く。
- 対応内容: 論理モデルを **append-only event log** に統一した。
  各イベントは immutable、試行レポートは**イベント列から純粋関数で導出**する。
  最終 verdict もイベントとして追記する。
  sessionStorage への物理的な配列再保存は実装詳細として許容し、論理モデルとは分けて書く。

## [Warning] sessionStorage の保存失敗が判定モデルに無い (§5)
- 判断: **対応する**
- 根拠: 重要な指摘。Safari の容量制限・private browsing・壊れた既存値・
  `setItem()` 例外があると、画面内で guard を観測できても `/login` 後に証跡を回収できない。
  黙って live 表示だけで続行すると「撮ったつもりで証跡が無い」事故になる。
- 対応内容:
  - **保存成功を試行成立とは別の必須前提**として持つ
  - 保存失敗時は試行を **`unrecordable`** として明示する
  - storage 書き込みは例外を捕捉し、**黙って live 表示だけで続行しない**
  - `StorageFailed` イベントを型に追加
  - read-back validation の要否は詳細設計で決める

## [Warning] ログイン維持シナリオのスコープ / 正のコントロールの位置づけを決めよ (§6)
- 判断: **必須の正のコントロールとして残す**（指摘は「決めよ」なので決定を明記）
- 根拠:
  1. **ログアウト後シナリオだけでは、常に `/login` へ飛ばす壊れた guard が PASS する。**
     負のコントロールには対になる正のコントロールが要る、というのは
     本設計そのものの存在理由と同じ論法である。
  2. **セッション有効時に秘匿解除だけで済ませることは使命に直結する要件である。**
     親設計 (`bfcache-guard.ts` docblock) は「hard reload は常用しない。
     撮影中の media stream・未送信フォーム・Inertia 履歴を破棄してしまい、
     **撮影 PWA という使命に直撃する**ため。有効なら秘匿を外すだけにする」と明記している。
     つまり `authenticated-unhidden` の確認は「余分な機能」ではなく
     **撮影導線を壊していないことの確認**であり、T085 の射程内である。
  3. リポジトリ内の前例と整合する。`InertiaHistoryRestoreAfterLogoutTest` は
     経路 C について正のコントロール 2 種を必須検証にしている。
- 対応内容: 2 シナリオとも T085 完了の必須条件とし、
  それぞれの役割（本試行 / 正のコントロール）を概念設計に明記した。

## [Warning] シナリオ宣言と実際の操作がずれた場合 (§6)
- 判断: **対応する**
- 根拠: 指摘のとおり。logout を宣言して `authenticated-unhidden` になった場合、
  guard 故障なのか未ログアウトなのかを区別できない。guard 故障として記録すると誤診になる。
- 対応内容: **`scenario-mismatch`** を導入し、guard 故障とは別に分類する。
  総合判定は FAIL（PASS にはしない）だが、原因を「guard 故障」と断定しない。

## [Warning] union に保存・試行終了を表す型が不足 (§7)
- 判断: **対応する**
- 対応内容:
  - union に `StorageFailed` / `TrialAborted` を追加
  - **総合判定は型として保持せず、両 verdict から純粋関数で導出する**
    （判定の二重保持による不整合を避ける。指摘の後者案を採用）

## [Suggestion] 使命との整合性 (§1) / 禁止事項違反なし (§2)
- 判断: 追加対応なし（現状維持）
