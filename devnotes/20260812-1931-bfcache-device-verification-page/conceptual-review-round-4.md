全体判定: **CHANGES_REQUESTED**

Round 3 の4条件はすべて概念上閉じています。正のコントロールを必須とした判断も妥当です。

ただし、軸2の `unauthenticated-redirected` を現在列挙されている観測値だけから確定できない、という観測可能性の穴が1点残っています。これは PASS 条件そのものに関わるため、詳細設計へ送らず概念設計で閉じる必要があります。

## 1. 使命との整合性

[Suggestion] 正のコントロールを必須にした論証は妥当です。

ログアウト後シナリオだけでは、常に `/login` へ送る実装を排除できません。また、セッション有効時に DOM・フォーム状態を温存して撮影を継続できることは、撮影 PWA の使命に直接関係します。

したがって、次の2面をセットで受け入れる設計は過剰なスコープ拡大ではありません。

- 失効セッションでは表示しない
- 有効セッションでは不要な破棄をしない

ただし「ログアウト後の復元」を「負のコントロール側」と呼ぶより、`本試行（失効セッション経路）` とした方が意味が明確です。

## 2. 禁止事項違反

[Suggestion] 明確な禁止事項違反はありません。

新規 logout 経路や JSON endpoint を作らず、検証対象にもフックを追加しない方針を維持できています。Architecture テストの登録も実装範囲に含まれています。

## 3. 実現可能性

[Critical] `unauthenticated-redirected` を現在の観測値だけでは確定できません。

A が外から観測できる guard 状態は、概ね次の範囲です。

```text
pageshow(persisted=true)
→ pending
→ verifying
→ 秘匿を維持したまま A から離脱
```

A の `pagehide` では、離脱先が `/login` だったことまでは分かりません。次の事象は保存ログ上で同じ形になり得ます。

- guard が `/login` へリダイレクトした
- 利用者が検証中に別ページへ移動した
- 別のコードが navigation を発生させた
- タブが閉じられた、または試行が中断された

再ログイン後に stored report を開いても、「その前に `/login` へ着地した」という事実は遡って観測できません。このままでは軸2の `unauthenticated-redirected` は推測になり、本試行を機械的に PASS にできません。

修正提案:

概念設計で、リダイレクト先の到達証拠をどう取得するかを1つ選んでください。

- `/login` 側で、未完了の debug 試行がある場合に限り「ログイン画面へ到達した」イベントを同じ append-only log に追記する
- debug 限定の中継着地点を使えるよう guard 側に検証フックを設ける。ただしこれは「検証対象を変更しない」要件と衝突するため非推奨
- `/login` 到達を人が確認し、その確認を手入力イベントとして記録する。この場合、軸2を「自動観測」と「手動確認」に分け、完全自動判定とは主張しない
- 1枚のスクリーンショット要件を撤回し、`/login` 到達画面と stored report の2証跡で成立させる

最も変更範囲が小さいのは手動確認イベントですが、証跡の強さを優先するなら `/login` 側の debug 限定観測が適しています。どちらを採る場合も、通常ユーザーの情報や URL query を保存しない既存 allowlist は維持できます。

## 4. 期待効果の妥当性

[Warning] 上記が閉じるまでは「スクリーンショット1枚で本試行の PASS を証明できる」とはいえません。

stored report は guard の遷移と試行成立を表示できますが、現状は `/login` 到達を証明できません。

修正提案:

- 到達証拠を event log に追加できるなら1枚を維持する
- 追加しないなら「1試行の証跡セット」と表現し、ログイン画面と stored report の2枚を許容する

環境情報について「自動観測」と「手入力」を分けた修正は適切です。

## 5. リスク

[Warning] `scenario-mismatch` という名称は、実際より強い断定になっています。

例えば logout シナリオで `authenticated-unhidden` になった場合、分かるのは「宣言した期待結果と観測結果が一致しない」ことです。利用者がログアウトし忘れたとは限らず、セッション失効判定やプローブの異常もあり得ます。

修正提案:

`scenario-mismatch` を `expectation-mismatch` または `scenario-outcome-mismatch` とし、「操作不一致またはシステム異常のいずれかで、原因未確定」と定義してください。総合 PASS にしない判断は正しいです。

[Warning] `StorageFailed` 自体は、sessionStorage が故障した場合には永続化できません。

これは設計矛盾ではありませんが、stored report に必ず残るイベントとは扱えません。

修正提案:

- 試行開始時の保存テスト失敗は、離脱させず live 画面で `unrecordable` を表示する
- 試行途中の保存失敗は、可能な範囲で live 表示するが、再表示後の回収は保証しない
- `StorageFailed` は「保存できれば記録する診断イベント」であり、保存不能の永続証拠ではないと明記する

read-back validation の具体方式は詳細設計で決めて構いません。

## 6. スコープの適切さ

[Suggestion] `incomplete` の追加と `invalid-wrong-route` の限定は適切です。

観測不能な事象を無理に invalid と断定せず、利用者の明示的な中止まで未完了に留める設計になっています。

2シナリオ必須も、本件では適切です。ただし T085 の完了条件は個々の試行ではなく、次の組として記録すると明確です。

```text
同一の端末・OS・実行モード
├─ 失効セッション経路: PASS
└─ 有効セッション経路: PASS
```

片方だけ成功した場合は、T085 全体を未完了とします。この組の識別子を試行 IDとは別に持つかは詳細設計事項です。

## 7. 型安全性

[Warning] 「最終 verdict もイベントとして追記」と「レポートはイベント列から純粋関数で導出」が部分的に競合しています。

`TrialVerdict` と `GuardVerdict` が派生結果なら、それらを保存した後に追加イベントが発生すると stale になります。特に redirect 到達証拠を追加する場合、先に保存した `GuardVerdict` が変わり得ます。

修正提案:

- event log には観測事実だけを保存する
- `TrialVerdict`、`GuardVerdict`、総合判定は表示時に純粋関数で導出する

または、verdict イベントを残すなら `finalizedAt` 以後のイベント追加を禁止し、確定前後の状態機械を定義する必要があります。前者の方が単純で、append-only モデルとの整合性も高いです。

具体的な union、runtime validator、schema migration、sequence 採番は詳細設計で詰められます。

## 結論

Round 3 の4条件と正のコントロール必須化は承認できます。残る概念レベルの承認条件は1点です。

**ログアウト後シナリオで、A の外から `/login` 到達をどのように証明し、`unauthenticated-redirected` を確定するか。**

併せて、派生 verdict を event log に保存せず表示時導出へ統一すれば、概念設計として APPROVED にできる水準です。
