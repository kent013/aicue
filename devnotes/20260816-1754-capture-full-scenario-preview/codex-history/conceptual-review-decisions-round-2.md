# 対応マトリクス: conceptual-review Round 2

## [Warning] 3-1. `error` が発火しない停滞 (waiting / stalled のまま無限待ち)
- 判断: 対応する
- 根拠: 指摘のとおり `<video>` は「進まないが error も出ない」状態を作る。現場のモバイル回線では
  実際に起きる。行き止まりを作らないという本リポジトリの UI 方針にも反する。
- 対応内容: 概念設計に「再生の状態機械と契約」節を新設し、
  `loading → playing | blocked | failed` / `playing → ended | stalled → playing | failed` /
  `failed → placeholder → next` を図で固定した。停滞判定は**経過時間ではなく進捗イベントの途切れ**で行い、
  タイマーと時刻源を注入可能にして Vitest が fake timer で固定する。
  **テストで固定するのは閾値ではなく「有限時間で必ず次へ進む」こと**であると明記した
  (仕組みが機能する前に値を弄らない)。

## [Warning] 3-2. `play()` の Promise 拒否 (自動再生制限)
- 判断: 対応する
- 根拠: クリップ差し替えが利用者操作の継続と認められるかは環境差がある。拒否を即「欠落」に落とすと、
  素材に問題が無いカットを欠落として見せることになり、本機能の目的 (撮り漏れの検出) が壊れる。
- 対応内容: `blocked` 状態を状態機械へ追加し、「再生を続ける」ボタンで利用者操作を作り直す設計にした。
  再操作でも失敗したときにだけ `failed` へ落とす。拒否された Promise を未処理で漏らさないこと、
  **拒否後もダイアログを閉じられること**を component テストへ登録した。

## [Warning] 5. 先読みの二重取得
- 判断: 対応する
- 根拠: 署名 URL は毎回変わるため、先読み用と本再生用で別に叩けば同じ動画を 2 回取得する。
  「通信量が増える」という自分の説明を自分で過小評価することになる。
- 対応内容: 「**1 クリップにつき playback route の解決は通常 1 回**」を期待契約として明記し、
  実現方法を「**2 枚のメディア要素を交互に使い、先読みした要素をそのまま本再生へ引き継ぐ**」に固定した。
  先読み対象は次の 1 クリップだけ。ブラウザ HTTP キャッシュへの命中は契約に含めないこと、
  再試行では取得が増えることを「保証しないもの」に明記した。
