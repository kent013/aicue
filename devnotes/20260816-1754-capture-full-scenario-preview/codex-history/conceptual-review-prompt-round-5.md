## 再生の状態機械と契約 (無限待ち・自動再生拒否・二重取得を作らない)

端末側連結再生の難所はメディア要素の非決定性である。次の 4 つを**設計契約**として固定し、
純関数側 (`lib/capture/scenario-preview.ts`) に状態遷移として実装して Vitest で固定する。

### 状態の持ち方 (再生状態と可視性は**直交**する)

- **再生状態**: `loading | playing | paused | blocked | failed | placeholder`
- **可視性**: `visible | suspended` (ページの表示状態。再生状態とは別の軸)
- **停滞監視を動かす条件**: `visible && 再生を要求している && (loading || playing)`

可視性を再生状態の 1 つにすると、`playing → paused → 非表示 → 復帰` で
一時停止が失われる (復帰先が `playing` になってしまう)。**画面復帰では再生状態を変更しない** —
元が `playing` なら再生の再開を試み、元が `paused` なら停止のまま、`blocked` なら `blocked` のままにする。

```
loading ──(再生開始)──▶ playing ──(ended)──▶ next
   │                       │  ▲
   │                       │  └──(利用者が再生)
   │                       └──(利用者が一時停止)──▶ paused
   │
   ├──(error イベント / 404)────────────────────▶ failed
   ├──(進捗が途切れたまま既定時間: 監視条件下のみ)─▶ failed
   └──(自動再生制限と判定できる play() 拒否)─────▶ blocked
                                                    ├──(「再生を続ける」→ 成功)──▶ playing
                                                    ├──(「再生を続ける」→ また拒否)──▶ blocked (滞留)
                                                    └──(「このカットをスキップ」)──▶ next

failed ──▶ placeholder (「このカットは再生できませんでした」) ──▶ next

可視性: visible ⇄ suspended (再生状態は変えない。suspended の間は停滞監視を止める)
```

### (1) 無限待ちを作らない — ただし監視する区間を限定する

- **不変条件は「ページが表示されていて、かつ再生を要求している間 (`loading` / `playing`) に
  進捗が途絶えたら、有限時間で `failed` へ進む」**である。これより広い保証はしない。
- 停滞判定は「経過時間」ではなく「**進捗イベントが途切れた時間**」で行う
  (長尺テイクを尺だけで失敗にしない)。
- **利用者が一時停止している間 (`paused`) と、ページが非表示の間 (`suspended`) は監視を止める**。
  止めないと、意図的な一時停止・タブのバックグラウンド化・画面ロックが「停滞」と誤判定され、
  復帰したら勝手に次のカットへ進んでいたことになる。`visibilitychange` で止め、復帰で再開する
  (撮影 PWA の既存 `handleVisibility` と同じ考え方)。
- 既定値は保守的に置き、**タイマーと時刻源は注入可能**にして Vitest が fake timer で固定する。
  テストで固定するのは**閾値の数値ではなく「監視条件を満たす限り有限時間で必ず次へ進む」こと**である。
- **`failed` は通し再生を止めない**。そのカットだけプレースホルダに落として次へ進む
  (1 本の失敗で行き止まりを作らない)。原因の区別 (削除 / 差し替え / 通信断) は主張しない。

### (2) 非同期結果は世代トークンで受け付ける (誤認を構造で消す)

- `play()` の Promise は自動再生制限以外でも拒否される (`src` 差し替えや `load()` による中断、
  メディア非対応など)。2 枚の要素を入れ替える実装では、**正常な切り替えによる中断**を
  `blocked` や `failed` と取り違えうる。
- そこで**契約を例外名ではなく世代に置く**: クリップを進めるたびに世代トークンを更新し、
  **現在のクリップ (世代) と一致する非同期結果だけが状態を変えられる**。
  古い世代の遅延 reject は**無視する** (状態を 1 ビットも変えない)。
- 世代が一致する拒否の扱いは 2 分類だけにする:
  - **自動再生制限と判定できるもの** → `blocked`
  - **それ以外** → **状態を変えない**。失敗の確定は `error` イベントと停滞監視 (1) に委ねる。
    ブラウザ例外名の分類に依存して失敗を確定させない (名前は環境差が大きい)。
- **拒否された Promise を未処理のまま漏らさない**。拒否後もダイアログを閉じられることを
  component テストで固定する (ここが壊れると閉じられない画面 = 詰みになる)。

### (3) 自動再生の拒否は「素材の失敗」にしない (`blocked` は滞留し、出口は利用者が選ぶ)

- 拒否を「再生できないカット」に落とさない (実際には素材に問題が無いのに欠落として見えるのは、
  この機能の目的そのものを壊す)。`blocked` は**素材の問題ではなく操作の問題**として表示する。
- **再試行が何度拒否されても `blocked` のままにする**。「N 回目の拒否で `failed`」という
  **根拠のない閾値を持たない** (仕組みが機能していない段階で値を弄らない)。
- 代わりに**出口を利用者に渡す**: `blocked` 中は常に
  「**再生を続ける**」「**このカットをスキップ**」「**閉じる**」の 3 つを操作できる
  (行き止まりを作らない)。スキップは `failed` を経ずに次のカットへ進む
  (素材の失敗ではないので、プレースホルダの文言「再生できませんでした」を使わない)。

### (4) 先読み (二重取得を作らない)

- **1 クリップにつき `capture.takes.playback` の解決は通常 1 回**とする。
  先読み用と本再生用で別々に叩くと、署名 URL が毎回変わるため**同じ動画を 2 回取得する**ことになり、
  「通信量は増える」という説明を自分で過小評価することになる。
- 実現方法は **2 枚のメディア要素を交互に使う** (現在再生用と先読み用を入れ替える) 形にし、
  **先読みした要素をそのまま本再生へ引き継ぐ**。先読み対象は**次の 1 クリップだけ**。
- **ブラウザ HTTP キャッシュへの命中は契約に含めない**。上の「1 回」は設計上の期待であって、
  再試行 (`blocked` からの再操作・失敗後の再入場) では増えることを認める。
