## 追加した節 (原文)

## 再生の状態機械と契約 (無限待ち・自動再生拒否・二重取得を作らない)

端末側連結再生の難所はメディア要素の非決定性である。次の 3 つを**設計契約**として固定し、
純関数側 (`lib/capture/scenario-preview.ts`) に状態遷移として実装して Vitest で固定する。

### 1 クリップの状態遷移

```
loading ──(再生開始)──▶ playing ──(ended)──▶ next
   │                        │
   │                   (stalled: 進捗が途切れた)
   │                        │  └─(進捗が再開)─▶ playing
   ├──(error / 404)─────────┴──(進捗が既定時間途切れたまま)──▶ failed
   │
   └──(play() が拒否された)──▶ blocked ──(利用者が「再生を続ける」を押す)──▶ loading
                                  └──(再操作でも拒否/失敗)──▶ failed

failed ──▶ placeholder (「このカットは再生できませんでした」) ──▶ next
```

- **不変条件: 無限待ちを作らない**。`error` が発火しない停滞 (`waiting` / `stalled` のまま進まない、
  あるいは `loadstart` の後に何も起きない) を検出するため、**進捗が既定時間途切れたら `failed` にする**。
  判定は「経過時間」ではなく「**進捗イベントが途切れた時間**」で行う (長尺テイクを尺だけで失敗にしない)。
  既定値は保守的に置き、**タイマーと時刻源は注入可能**にして Vitest が fake timer で固定する。
  テストで固定するのは**閾値の数値ではなく「有限時間で必ず次へ進む」こと**である。
- **`failed` は通し再生を止めない**。そのカットだけプレースホルダに落として次へ進む
  (1 本の失敗で行き止まりを作らない)。原因の区別 (削除 / 差し替え / 通信断) は主張しない。

### 自動再生の拒否 (`play()` の Promise 拒否) の扱い

- `HTMLMediaElement.play()` は端末・ブラウザの自動再生制限で拒否されうる。**クリップ差し替えが
  最初の利用者操作の継続と認められるかは環境差がある**ため、拒否を即「再生できないカット」に
  落とさない (実際には素材に問題が無いのに欠落として見えるのは、この機能の目的そのものを壊す)。
- 拒否は `blocked` として扱い、**「再生を続ける」ボタン**を出す (= 利用者操作を作り直す)。
  再操作でも拒否・失敗したときに初めて `failed` へ落とす。
- **拒否された Promise を未処理のまま漏らさない**。拒否後もダイアログを閉じられることを
  component テストで固定する (ここが壊れると閉じられない画面 = 詰みになる)。

### 先読み (二重取得を作らない)

- **1 クリップにつき `capture.takes.playback` の解決は通常 1 回**とする。
  先読み用と本再生用で別々に叩くと、署名 URL が毎回変わるため**同じ動画を 2 回取得する**ことになり、
  「通信量は増える」という説明を自分で過小評価することになる。
- 実現方法は **2 枚のメディア要素を交互に使う** (現在再生用と先読み用を入れ替える) 形にし、
  **先読みした要素をそのまま本再生へ引き継ぐ**。先読み対象は**次の 1 クリップだけ**。
- **ブラウザ HTTP キャッシュへの命中は契約に含めない**。上の「1 回」は設計上の期待であって、
  再試行 (`blocked` からの再操作・失敗後の再入場) では増えることを認める。



## 「保証しないもの」へ追記した項目

> - **「1 クリップにつき 1 回取得」は設計上の期待であって保証ではない**。自動再生拒否からの再操作や
>   失敗後の再入場では取得が増える。ブラウザ HTTP キャッシュへの命中も契約に含めない。
> - **停滞判定の閾値が「正しい」ことは主張しない**。固定するのは「有限時間で必ず次へ進む」ことだけで、
>   閾値そのものは実地の観測が出るまで動かさない。
