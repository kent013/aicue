# 対応マトリクス: conceptual-review Round 1

## [Warning] 1. 「撮影者がもう帰ってよいかを判断できる」は強すぎる
- 判断: 対応する
- 根拠: 通し再生は完成レンダ可能性を保証しないと自分でも書いており、期待効果の表現と矛盾していた。
  嘘をつかない (保証範囲を誇張しない) は本リポジトリの一貫した規律である。
- 対応内容: 背景・期待効果の表現を「撮り終わったかを判断できる」から
  「**その場で直せる不足 (採用漏れ・撮り漏れ) と通しの流れを、現場を離れる前に見つけられる**」へ弱めた。
  UI 文言もこの意味に揃える旨を明記した。

## [Warning] 2. captureActive 時の挙動 (押せるが開かない) の責務を明確に
- 判断: 対応する
- 根拠: 禁止事項 8 との整合は取れているが、記述が曖昧だと実装で disabled 化されうる。
- 対応内容: 「ボタンは**常に押せる**。押下時に `captureActive` ならその場でエラーを表示し、
  ダイアログは開かない (既存 `TakeStrip` の preview と同じ規則)」と明記した。

## [Warning] 3. `adopted_ready_take_id` の算出が判定式の二重化になる
- 判断: 対応する (指摘どおり構造を変える)
- 根拠: `isMissing()` は bool しか返さないため、DTO 側で `adopted_take_id` と `TakeStatus::Ready` を
  再度組み合わせると T148 の不変条件 (判定式は 1 ファイル) を実質的に破る。
  正本サービスに「ready な採用テイクの id を返す」を足し、`isMissing()` をその上に載せ替えるのが
  唯一の正しい形である。
- 対応内容: `AdoptedReadyTakeCoverage::readyTakeId(Cut): ?int` を新設し、
  `isMissing(Cut)` を `readyTakeId($cut) === null` に置き換える方針を実装方針へ追加した。
  述語の意味は変わらず、実体が 1 つになる。

## [Warning] 3-2. 再生時に 404 になりうる (props 生成後に状態が変わる)
- 判断: 対応する
- 根拠: `capture.takes.playback` は ready 以外・削除済みを 404 にする。通し再生の途中で 1 本落ちたときに
  全体が止まると「行き止まり」を作る (DESIGN.md の思想に反する)。
- 対応内容: 再生エラー / 404 は**そのクリップだけをプレースホルダ扱いに落として次へ進む**、
  という進行規則を明記した (文言は「このカットは再生できませんでした」)。

## [Warning] 4. 「追加費用ゼロ」は過大
- 判断: 対応する
- 根拠: 正しい。レンダ実行費用と成果物保存は増えないが、署名 URL 発行・ストレージ egress・
  モバイル通信量は増える。
- 対応内容: 比較表と期待効果を「**レンダ実行費用と成果物保存は増えない。再生の通信量と
  署名 URL 発行回数は増える**」に書き換えた。

## [Warning] 5. 短時間に多数の 302 / S3 取得が走る
- 判断: 対応する
- 根拠: 大量カットのマニュアルでは端末負荷と通信量が効く。先読みの上限を設計で決めておかないと
  実装時に全件先読みへ倒れうる。
- 対応内容: 「**先読みは次の 1 クリップまで**。それ以上は行わない」を設計制約として明記し、
  再生前の告知にカット件数を含めた。

## [Warning] 5-2. 「新たに露出する情報は 1 バイトも無い」は強すぎる
- 判断: 対応する
- 根拠: 情報の到達可能性 (アクセス容易性) は上がる。権限境界と情報量を同一視しない。
- 対応内容: 「**権限境界を広げない。対象は同一画面で既に個別再生できるテイクに限る**」へ書き換えた。

## [Warning] 6. 権限が変わっていないことの確認観点をタスクに入れる
- 判断: 対応する
- 根拠: 「変えない」ことは回帰テストが無いと守られない。
- 対応内容: テスト方針に「撮影者が `POST .../preview` / `GET .../render-jobs/{id}/playback` /
  `GET .../download` に到達できないこと (403/404) を固定する」を追加した。

## [Warning] 7. `previewPlaceholderSeconds` の型・単位・命名
- 判断: 一部反論 (命名) / 対応する (型・単位・テスト固定)
- 根拠: 命名について、本リポジトリの流儀は
  「**DTO の `toArray()` が作る資源の shape は snake_case** (`adopted_take_id` / `placeholder_cut_count`)、
  **Controller が組み立てるページ props の複合キーは camelCase**
  (`Manuals/Show` の `analysis.hasDocument` / `render.finishedJob`)」の 2 段構えである。
  新しい cut の項目は前者なので `adopted_ready_take_id`、ページ props は後者なので
  `previewPlaceholderSeconds` が既存流儀に一致する。snake_case へ寄せると `Manuals/Show` と食い違う。
- 対応内容: 反論を明記したうえで、型と単位 (**秒。正の整数**) と、Feature テストでキーと値の型を
  固定することを設計に追記した。

## [Suggestion] 使命整合 / スコープ / nullable int
- 判断: 見送る (指摘なし・現状維持)
- 根拠: 追加作業を要さない肯定的評価のため。
