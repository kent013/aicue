### 1. 使命との整合性

- [Warning] Q-2-01 の変更意図は North Star と整合します。非管理メンバーを、操作権限のない請求導線ではなく業務入口へ着地させることは、現場作業者の初動摩擦を減らします。  
  修正提案: 「`/dashboard` が現場作業者にとって実際に業務開始可能な入口である」ことを、表示内容・必要な権限・次の行動まで含めて確認対象に明記してください。単に 200 を返すだけでは soft dead-end の解消を保証できません。

- [Suggestion] 「摩擦ゼロ」は達成目標として強すぎるため、「不要な請求画面への初回遷移を除去する」と限定して効果を表現する方が、検証可能で誠実です。

### 2. 禁止事項違反

- [Warning] 禁止事項 8 は「必須条件未充足を理由にボタンを disabled にしない」という UI 規約であり、「操作不能な画面を見せない」という一般原則そのものではありません。設計の結論は妥当でも、根拠付けとしては拡張解釈です。  
  修正提案: 禁止事項 8 は補助的な思想としてのみ扱い、主根拠を North Star と「権限のない利用者を仕事開始可能な導線へ送る」という UX 判断に置いてください。

- [Suggestion] F-3-02 / S6-1 / S6-2 は既存実装・既存 Feature テストの確認報告であり、新規実装の完了報告ではありません。したがって「テストなしの実装完了」には抵触しません。むしろ重複テストや不要なコード追加を避ける判断は、思考原則 2 および prompt 文字列を増やさない禁止事項 6 の趣旨に沿います。

### 3. 実現可能性

- [Warning] `manageBilling` 判定の主体・対象が設計上曖昧です。Laravel の Gate はユーザー単独ではなく、組織や請求対象を追加引数として必要とする可能性があります。誤ったコンテキストで判定すると、権限境界を崩すおそれがあります。  
  修正提案: 実装では既存の請求画面・請求操作と同一の Gate 呼び出し形式、同一の organization 解決経路を再利用すると明記してください。新たな「role 判定」は導入せず、設計文言も「role」ではなく「`manageBilling` 能力」と統一してください。

- [Suggestion] Laravel 12 + Inertia の redirect 分岐としては、既存の named route を返すだけなので、技術的な実現性は高く、DTO / JsonResource を新設する必要もありません。

### 4. 期待効果の妥当性

- [Warning] 「機能破綻ゼロ」は過剰な主張です。着地点の変更は、オンボーディング継続、メール認証後の continuation、直アクセス、ブラウザ履歴などに影響し得ます。  
  修正提案: 効果を「既契約組織の非管理メンバーについて、オンボーディング入口で billing ではなく dashboard へ遷移する」に限定し、下記の回帰テストで保証範囲を具体化してください。

### 5. リスク

- [Critical] テスト方針が「既存の非管理メンバー → billing.index の期待を dashboard に更新」とだけ書かれており、意図しない既存挙動の置換を検知できません。とくに、メール認証完了後の continuation と、直接 `/onboarding/checkout` へのアクセスは別の入口です。  
  修正提案: 少なくとも次を分離して Feature テストにしてください。

  - 既契約組織・`manageBilling` 保持者は `billing.index` のまま。
  - 既契約組織・非保持者が onboarding へ直接来ると `dashboard`。
  - 招待登録からメール認証完了までの continuation を通った非保持者が `dashboard`。
  - 未契約または支払い未解決組織の既存着地は変わらない。

- [Warning] 「非管理メンバーの billing 閲覧可否は変えない」なら、dashboard から billing へ到達する既存リンク・ナビゲーションがある場合、初回遷移だけ直しても混乱が残る可能性があります。  
  修正提案: 今回は閲覧設計を変えないことを維持しつつ、dashboard 上で請求導線がどう露出するかを確認し、必要なら別 finding として切り出してください。

### 6. スコープの適切さ

- [Suggestion] Q-2-01 を既存の `hasActiveAccess()` と既存 Gate の組合せだけで直す方針は、最小変更として適切です。未契約組織向けの課金ゲート反転や billing の閲覧設計を同時に変えない線引きも適切です。

- [Warning] ドキュメント更新を touch-point として認識しながら、別責務として実編集しないなら、変更の完了条件が曖昧です。  
  修正提案: 本変更の実装 PR では「文書更新は別担当・別変更として追跡する」ことを明示し、追跡先を設定してください。追跡不能なら、実装と同時に最小限の仕様記述を更新する方が安全です。

### 7. 型安全性

- [Suggestion] この変更は controller 内の既存 redirect 分岐と既存 authorization API の利用に留まるため、DTO / JsonResource の対象ではありません。`response()->json()` を導入しない限り、該当禁止事項にも触れません。

- [Warning] PHPStan level 10 を通すには、Gate 判定に渡す組織・利用者の nullability と戻り値を既存の型付き経路に合わせる必要があります。  
  修正提案: controller で推測的な nullable 値や独自 role 文字列を使わず、既存の organization-scoped な能力判定をそのまま用いてください。
