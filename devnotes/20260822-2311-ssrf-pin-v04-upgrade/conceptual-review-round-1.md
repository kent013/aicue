全体判定: **CHANGES_REQUESTED**

使命との整合性  
- [Suggestion] 直接のユーザー価値ではないものの、無認証 SNS 入口が誘発する外部取得の防御を強化するため、SOP・撮影データを預かる基盤の信頼性に合理的に貢献する。North Star の前提を守る改善として妥当。

禁止事項違反  
- [Warning] 「当該 1 パッケージだけを更新し、他の lock 差分がないことを機械照合」とあるが、Composer の解決結果は依存制約次第で関連メタデータ等が変わり得る。「lock 差分が package 本体の 1 件だけ」という過度に狭い判定にすると、正当な更新を失敗扱いしかねない。  
  修正提案: 許容差分を明示し、`kent013/laravel-ssrf-pin` とその新規に必要となる依存だけに限定する、という検査にする。既存 lock に依存があることも更新前に確認する。

実現可能性  
- [Warning] `app(UrlSafetyInspector::class)` を使う回帰テストは正しいが、DNS resolver の差し替え後に Inspector が既に singleton として解決済みなら、差し替えがテスト対象へ届かない可能性がある。  
  修正提案: 各ケースで resolver を差し替えた後に Inspector を解決すること、または既存 `bindSnsDnsResolver()` がコンテナ再解決を保証することをテスト設計の前提として明記・確認する。
- [Suggestion] DNS 応答を通す方式は `deny_ip_literals: true` の実設定を通るため、IP literal で直接検査するより適切。外部 HTTP を一切発生させない点も Architecture レーンに適合する。

期待効果の妥当性  
- [Warning] 「登録簿が古くなると fail-open しうる」という AGENTS.md 追記案は表現を改めるべき。v0.4 の `Unclassified` は拒否であり、未知の区間を単純に許可する旧版型の fail-open ではない。古い登録簿で起こり得るのは、分類・到達可能性の更新を反映できないこと。  
  修正提案: 「未分類は拒否されるが、登録簿の到達可能性判断が最新の IANA 状態を反映しない可能性がある」と正確に書く。
- [Suggestion] `classificationRegistryVersion() = "2025-10-09"` の pin は、`^0.4` による将来のパッチ更新で意図的に赤くなる。これは回帰検知として合理的なので、「更新時に登録簿差分と全回帰ケースをレビューするための意図的な pin」と明記すると保守者に親切。

リスク  
- [Warning] 正の fixture を「公開到達可能なアドレス」へ移す際、実通信を伴わない DNS 偽装テストであることが曖昧だと、将来その IP が実際に到達可能かを外部 HTTP で確認する誤ったテストに変わり得る。  
  修正提案: fixture は「グローバル到達可能として分類される DNS 応答値」であり、接続先・実在ホストの検証ではない、と定数またはコメントに残す。`93.184.216.34` を採用するならこの意図を明記する。
- [Suggestion] SNS URL のホスト形式が厳格に固定されているため、実攻撃には DNS 支配・rebind 条件が必要という脅威モデルの限定を維持する。過大な「任意 URL SSRF が直ちに防げる」といった表現にはしない。

スコープの適切さ  
- [Warning] 第二層契約検査、config の `registry_version`、`PinnedHttpClient` 一本化を外す判断は概ね妥当。ただし新設 gate が実質的に「導入版の分類能力」を担保する唯一の検査になるため、8 区間・混在応答・従来拒否・公開許可・登録簿版の全てを必須ケースとして明示的に列挙し、いずれかを削る変更がレビューで分かるようにすべき。  
  修正提案: データプロバイダを使う場合も、8 区間がテスト上で読み取れる名前・期待 deny reason を持つケースとして固定する。
- [Suggestion] `config/ssrf-pin.php`、既存 boundary gate、`SnsTestData.php` を触らないのは不自然な回り道ではない。採用時債務パスを不必要に動かさず、既存境界 test と新規回帰 test の責務を分離できている。

型安全性  
- [Suggestion] DTO / JsonResource の対象となる HTTP 応答変更はなく、禁止された `response()->json()` も発生しない。新規 Pest テストでは resolver の実装・戻り値をパッケージの `DnsResolverInterface` に厳密適合させ、`mixed` な配列や無名オブジェクトで PHPStan を回避しないこと。IP・ホスト・期待理由を型付きの小さな test case 値オブジェクト、または明確な shape 配列にすれば level 10 と整合する。

結論として、方向性とスコープは承認可能です。ただし、登録簿の「fail-open」説明を正し、DNS 差し替えが実際に Inspector へ届くテスト構造と、lock 差分の許容範囲を具体化してから実装へ進めるべきです。
