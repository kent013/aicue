全体判定: **CHANGES_REQUESTED**

Round 1 の5件の Warning は、意図としてはすべて適切に処理されています。特に `bind → forgetInstance → resolve` の説明は十分です。ただし、改訂によって残った表現上・検証条件上の Warning が2件あります。

### 1. 使命との整合性

- [Suggestion] 安全上の追従として North Star の前提を守る位置づけは妥当です。脅威成立に DNS 支配が必要であることも明記され、効果を過大に見せていません。

### 2. 禁止事項違反

- [Suggestion] テストを追従の本体に置き、既存 boundary gate を弱めず、新しい Architecture テストで分類能力を固定する方針は、禁止事項1に適合しています。
- [Suggestion] DTO・JsonResource・LLM 経路・DB 破壊操作などに関係する変更はなく、禁止事項への抵触はありません。

### 3. 実現可能性

- [Warning] lock の許容差分を、対象パッケージ内の一部フィールドだけに限定する条件はまだ狭すぎます。v0.2.0からv0.4.1への更新では、`autoload`、`description`、`license`、`authors`、`extra` など、列挙されていないパッケージメタデータが正当に変化する可能性があります。これらは依存解決の巻き添えではなく、対象パッケージ自身の版更新に伴う正常な差分です。

  修正提案: 許容差分を次の単位に変更してください。

  - `composer.json`: 対象パッケージの制約と `content-hash` の原因となる変更
  - `composer.lock`: `kent013/laravel-ssrf-pin` のパッケージエントリ全体
  - 更新前に不足を確認した新規依存のパッケージエントリ
  - lock ルートの `content-hash`

  そのうえで、「上記以外の既存パッケージについて、名前→版の写像が不変」を機械照合すれば、目的を過不足なく満たせます。対象パッケージのエントリ全体を許容しても、`version === v0.4.1`、VCS source、期待 reference、require を別途確認すれば緩みません。

- [Suggestion] `bind → forgetInstance → app(...)` の3段手順は十分に説明されています。singleton の残存による偽グリーンまで理由づけされており、Round 1 の指摘は解消しています。

### 4. 期待効果の妥当性

- [Warning] 「本設計は登録簿の陳腐化を検知できる形にする」という主張は、まだ強すぎます。`classificationRegistryVersion() === '2025-10-09'` の pin が検知するのは、導入パッケージ内の登録簿が変更されたことです。IANA の最新版が更新されても、パッケージを更新しなければテストは緑のままであり、外部レジストリとの比較も行わないため、陳腐化そのものは検知できません。

  修正提案: 次のように保証範囲を狭めてください。

  > 本設計は使用中の登録簿版を明示的に固定し、将来のパッケージ更新で登録簿が変化した際にレビューを要求する。IANA 登録簿の更新や、現在の同梱登録簿が既に陳腐化していることを自動検知するものではない。

  「保証しないもの」に「登録簿の陳腐化を解消しない」と書く部分は正しいため、最後の「検知できる形にするところまで」だけを修正すれば整合します。

### 5. リスク

- [Suggestion] 「任意 URL SSRF 全般を防ぐものではない」「DNS rebinding は残る」「非公開宛て接続自体は発生し得る」という記述は適切です。脅威を過大にも過小にも見せていません。
- [Suggestion] 公開アドレス fixture を分類入力として扱い、実到達性を検査しないという docblock 方針も十分です。TEST-NET fixture の交換は検査の緩和ではなく、deny と allow の意味を分離する正常な修正です。

### 6. スコープの適切さ

- [Suggestion] 必須ケース18件は過大ではありません。内訳も適切です。

  - 新たに塞ぐ8区間
  - 従来拒否6分類
  - IPv4/IPv6 の正例2件
  - 混在応答1件
  - 登録簿版1件

  とくに正例と混在応答は、常時 deny や先頭要素だけを見る壊れ方を防ぐため必要です。第二層契約検査を作らない以上、この程度の明示性は合理的です。

- [Suggestion] `config/ssrf-pin.php`、既存 boundary gate、`SnsTestData.php` を触らない判断も妥当です。回帰 gate が必要な実効契約を直接検査するため、不自然な迂回にはなっていません。
- [Suggestion] 実装方針表の `E` 行が「D の置き場所」節の途中へ移動しており、Markdown表から外れています。内容上の問題ではありませんが、概要表へ戻してください。

### 7. 型安全性

- [Suggestion] package 同梱の `FakeDnsResolver`、`array<string, list<string>>`、`SsrfDenyReason` enum を使う方針は PHPStan level 10 と整合します。文字列 deny reason や自作 fake に逃げない点も適切です。

結論として、実装方針そのものに重大な欠陥はありません。承認までに必要なのは、次の2点です。

1. lock の許容単位を「対象パッケージの限定フィールド」から「対象パッケージのエントリ全体」へ直す。
2. registry version pin は「陳腐化の自動検知」ではなく「導入版の登録簿変更をレビューへ上げる仕組み」と表現する。
