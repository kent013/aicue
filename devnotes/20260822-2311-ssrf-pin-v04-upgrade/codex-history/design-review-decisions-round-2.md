## [Warning] 施策 B: 構造比較スクリプトが packages / packages-dev の所属を失っている
- 判断: **対応する**
- 根拠: **スクリプトの実バグである。** `{q['name']: q for q in d['packages'] +
  d.get('packages-dev', [])}` と畳んでいたので、
  (1) 対象外のパッケージが `packages` から `packages-dev` へ移っても
      エントリ内容が同じなら差が出ず検出できない、
  (2) 同名が両セクションに現れた場合に一方が黙って上書きされる。
  設計文が「両配列を含む残りの構造が完全一致」と宣言しているのに
  検証がそれより弱い = Round 1 で指摘されたのと同じ種類の穴を、
  修正の中で作り直していた。
- 対応内容: `load()` を**セクション所属を保つ**形へ書き換えた
  (`{s: {name: entry} for s in ('packages','packages-dev')}`)。
  新規 / 消滅の検査 (手順 2) と、対象を除く全エントリの完全一致 (手順 3) を
  **セクションごとに**回す形にした。これでセクションを跨いだ移動は
  片方で `removed`・他方で `added` になって必ず落ちる。
  さらに対象パッケージ自身の**所属セクションも固定**した
  (`packages` に在り `packages-dev` に無いこと)。
  出力の件数も両セクションの合計で数えるよう直した。

## [Warning] 施策 B: 受け入れ基準 3 が古い「名前 → 版の写像」のまま
- 判断: **対応する**
- 根拠: 指摘が正しい。本文は構造比較へ強化したのに、最終受け入れ基準だけが
  旧表現で残っていた。**受け入れ基準は実装者が最後に見る契約**なので、
  ここが弱いと本文の強化が効かない (概念設計 Round 3 で同種の
  「1 か所だけ旧表現が残る」指摘を受けたのと同じ失敗)。
- 対応内容: 受け入れ基準 3 を
  「対象パッケージ・`content-hash`・事前承認済み新規依存を除き、
  `composer.lock` のルートキー / `packages` / `packages-dev` が
  **構造として完全一致**すること (セクション所属も比較対象に含む。
  『名前 → 版の写像』だけの照合では不足)」へ差し替えた。

## [Warning] 施策 C: AAAA レコード内の複数応答を最後まで検査することが固定されていない
- 判断: **対応する**
- 根拠: 指摘が正しく、これも実質的な検出力の穴である。
  A 側には「公開 + 特殊用途」があるが AAAA 側に同等のケースが無いため、
  「**AAAA は先頭 1 件しか分類しない**」という後退が 3 ケースすべてを
  すり抜けられる (A→AAAA 交差は AAAA の先頭が特殊用途なので拾えてしまう、
  AAAA→A 交差は A 側で落ちる、A 内複数は AAAA を使わない)。
- 対応内容: S4 へ 4 件目
  `'AAAA 内で 公開 + 特殊用途' => [[], ['2606:2800:220:1:248:1893:25c8:1946', '2001:db8::1']]`
  を追加した。docblock にも 4 ケースの内訳
  (「A 内の複数」「A→AAAA 交差」「AAAA→A 交差」「AAAA 内の複数」) と、
  *どちらの family でも、どの位置にあっても*非公開が 1 件あれば拒否されることを
  覆う設計意図を書いた。
  **両版に対して再実測した** — v0.4.1 は 4 件すべて deny、v0.2.0 は 4 件すべて allow。
  → 版上げ前の期待 fail は **13 件から 14 件**へ更新
  (Codex の予測 14 件と実測が一致した)。
  設計文中の件数 5 か所 (実測表 / 内訳 / テスト計画 / 実装モードの判断根拠 /
  受け入れ基準) をすべて 14 へ揃えた。

## [Suggestion] 施策 C: S3/S4 の closure 引数は静的には array<mixed, mixed> なので説明が不正確
- 判断: **対応する**
- 根拠: 正確な指摘。`array $ipv4` の型宣言だけでは PHPStan からは
  `array<mixed, mixed>` であり、「`mixed` を経由しない」「`tests/` を解析対象へ
  広げても安全」という PHPStan 適合チェックの記述が現状と食い違っていた。
  説明を実態へ合わせるか、コードを説明へ合わせるかの二択で、**コード側を直す**
  (説明を弱めると、後で解析対象を広げたときに手戻りになる)。
- 対応内容: S3 / S4 の closure を
  `test('...', /** @param list<string> $ipv4 @param list<string> $ipv6 */ function (...) {...})`
  の形へ書き換え、docblock で `list<string>` を明示した
  (PHP は closure の直前の docblock を許し、PHPStan もこれを読む)。
  PHPStan 適合チェックの該当項目も
  「`array` の型宣言だけでは静的には `array<mixed, mixed>` になるので
  docblock を付ける」と理由付きで書き直した。
