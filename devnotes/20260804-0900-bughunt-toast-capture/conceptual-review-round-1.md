全体判定: **CHANGES_REQUESTED**

**1. 使命との整合性**
- [Suggestion] 問題設定は妥当です。bug-hunt の誤検知低減は、本物の UX 不具合へ調査資源を寄せる改善なので、North Star への間接貢献として筋が通っています。特に「台帳の心構え」ではなく「観測手順の穴」を埋める、という仮説の置き方は良いです。

**2. 禁止事項違反**
- [Suggestion] 記載範囲では明確な禁止事項違反は見当たりません。アプリ本体をいじらず、bug-hunt 基盤側で閉じる方針も妥当です。
- [Suggestion] 「テストで固定する」を明示している点も良いです。今回の主戦場が skill/ledger/test 側である、という特殊事情に合っています。

**3. 実現可能性**
- [Warning] `@playwright/cli` の `eval` + `MutationObserver` で「操作前に記録器を仕込む」方式自体は十分実現可能です。ただし、成立条件は「新規ノード追加」だけではなく「既存 live region のテキスト更新」も拾うことです。ここが詳細設計で曖昧なままだと、toast 実装差分で簡単に抜けます。  
  修正提案: probe の契約を明文化してください。最低でも `childList` / `characterData` / `subtree` を監視し、「追加」「テキスト変化」「属性変化による hidden→visible」をどこまで観測対象にするかを先に固定するべきです。
- [Warning] jsdom テストで DOM 変化の契約は固定できますが、「実ブラウザで live region として扱われるか」「Playwright CLI の eval 注入タイミングが常に安定か」は担保できません。本文でも一部触れていますが、受入条件としてまだ弱いです。  
  修正提案: 次回 live run の受入条件に、少なくとも「F-1-02 と同型の SPA 削除導線で probe が `seen` を返すこと」「CodeSnippet copy 導線で 2 秒窓の `status` を 1 回以上拾うこと」を具体的に追加してください。

**4. 期待効果の妥当性**
- [Critical] 現案のまま `role="status"` / `role="alert"` を広く見ると、**操作と無関係な既存 live region を“フィードバックあり”と誤認して新しい偽陰性を作る**危険があります。`present` 非空で finding を抑止する規約は特に危険です。たとえば既存のフォームエラー、常駐 alert、別操作由来の toast が残っているだけで、「今回の操作に対するフィードバックあり」と判定されかねません。これは false positive を減らす代わりに false negative を増やす設計です。  
  修正提案: `present` は「arm 後に新規出現した live region」または「arm 時点から内容が変化した live region」に限定してください。具体的には、arm 時に live region の `node identity + textContent + visibility state` を基線として保持し、判定はその差分だけで行うべきです。少なくとも「arm 前から存在しただけの live region」は証拠に使わない、を規約化しないと不十分です。
- [Warning] 「ARIA live region なら新規 component も自動で載る」は筋が良い一方、対象の一般化がやや強すぎます。今回の再発原因は toast/コピー通知という**一過性 UI**であって、live region 全般ではありません。一般化しすぎるとレビュー観点 4 の「別概念の統合」に寄ります。  
  修正提案: 規約上は「非単調 UI のうち、live region を使うものを probe 対象にする」と明記し、`role=status/alert` は手段であって概念そのものではない、と切り分けてください。

**5. リスク**
- [Warning] `installed_now: true` を「未検証に倒す」だけだと、cross-document 遷移を含む導線で H7 が事実上機能停止します。誤検知は減りますが、カバレッジ低下を無言で持ち込む形です。  
  修正提案: H7 の適用条件を明文化してください。例えば「同一 document 継続が前提の導線にのみ H7 を適用する」「cross-document は H7 非適用として report に明示する」と切るべきです。再実行を許すなら、再実行条件と上限回数も必要です。
- [Warning] DOM 出現だけを証拠にすると、`hidden`/`aria-hidden`/非表示コンテナ内の live region を拾ってしまう可能性があります。これは「視覚的には出ていないのに出た扱い」の偽陰性源です。  
  修正提案: probe の証拠条件に最低限の可視性判定を入れてください。厳密なレイアウト判定までは不要でも、少なくとも `hidden` と `aria-hidden="true"`、DOM 未接続は除外した方がよいです。

**6. スコープの適切さ**
- [Suggestion] 「アプリコードは触らない」「wait-for 自作はしない」「単調 UI には広げない」という切り方は適切です。今必要なものだけに留めています。
- [Suggestion] 一方で `spec-ledger` の書式拡張と `template-divergence` 追記は、詳細設計で本当に必要最小限かだけ再確認した方がよいです。probe 導入そのものに必須なのは前者で、後者は“テンプレート逸脱”の事実が確定してからでも遅くありません。

**7. 検証計画の誠実さ**
- [Warning] 「spec-ledger の file:line 実在チェック」を強く固定しすぎると、将来の通常リファクタで台帳テストが無駄に壊れやすくなります。誠実さというより保守負債になりやすいです。  
  修正提案: 検証対象は「根拠ファイルの存在」と「識別子/抜粋の近傍一致」程度に留め、line number の厳密固定は避けた方がよいです。少なくとも skill/ledger 以外のアプリ本体参照までは line 厳密一致にしない方が安全です。
- [Suggestion] live run の受入基準をもう一段具体化するとよいです。「誤検知 0」だけだと曖昧なので、`F-1-02` 同型導線と `CodeSnippet` 導線の 2 ケースを必須観測ケースとして明記すると、成功条件が検証可能になります。

主な差し戻し理由は 1 点です。**“今回の操作に起因する live region 変化” と “ページ上に存在した別の live region” を区別する基線設計がまだ不足しています。** ここを埋めれば、設計全体の方向性はかなり良いです。
