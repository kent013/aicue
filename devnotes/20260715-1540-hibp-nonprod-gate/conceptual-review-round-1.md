全体判定: CHANGES_REQUESTED

**1. 使命との整合性**
- [Suggestion] 非本番の外部依存を外して bug-hunt / ブラウザテストを高速・決定化する方向は、改善サイクルを詰まらせず North Star に整合しています。SOP→シナリオ→撮影の本筋を阻害する待ち時間を減らす、という主張は妥当です。

**2. 禁止事項違反**
- [Suggestion] 提案自体は禁止事項 1/2/4/5/6/7/8 に直接抵触していません。特に「単一述語へ集約してテストで固定する」方針は、場当たり的な閾値調整ではなく設計変更として筋が通っています。

**3. 実現可能性**
- [Warning] Laravel 12 + Svelte 5 + Inertia.js の文脈では実装可能ですが、実装案の述語 3 が `App::environment('staging')` 固定なのに、本文は「staging 等の実運用ミラー環境」と書いており、設計説明と実装案が一致していません。`preprod` `qa` `review` など別名の実運用ミラー環境があると、想定に反して HIBP が無効になります。修正提案: HIBP を有効にすべき `APP_ENV` 名をこの設計で明示し、`App::environment([...])` の allowlist と説明文を一致させてください。
- [Suggestion] `bughunt.local` は host 名に見えるため、`APP_ENV` と `APP_URL`/host を文書上で明確に分離すると、実装者の解釈ぶれを減らせます。

**4. 期待効果の妥当性**
- [Warning] 「10〜14 秒遅延の根因が HIBP」という仮説はかなり有力ですが、設計書上の受け入れ基準がまだ弱いです。効果を主張するなら、実装前後で「登録/リセット/変更 POST の所要時間」「外部 HIBP 呼び出し有無」を比較する成功条件を明文化した方がよいです。修正提案: 非本番では HIBP 呼び出し 0 回、対象フォームの POST が一定閾値未満、という検証条件をテスト計画かレビュー観点に追加してください。
- [Suggestion] 本番 UX は不変なので、今回の効果は「非本番の開発・検証速度改善」に限定して書くと、期待値が過大になりません。

**5. リスク**
- [Critical] セキュリティ上の主張は「production では必ず有効」でよいのですが、準本番の扱いが曖昧です。本文では「staging 等の実運用ミラー環境は有効」と言いながら、実装案は `staging` しか有効にしません。これだと、本番直前検証を別 env 名で回している場合に HIBP が静かに外れ、検証代表性が落ちます。修正提案: 「どの env を実運用ミラーとみなすか」を設計で固定し、その env 一覧に対するテストを追加してください。少なくとも設計文言の「等」は削るか、allowlist を明示すべきです。
- [Warning] `rule()` の `uncompromised` を reflection で検査する案は Laravel 内部実装への結合が強く、フレームワーク更新で壊れやすいです。修正提案: `shouldCheckPwned()` の単体テストを主に据え、`rule()` 側は公開 API ベースの振る舞いテストを優先し、reflection は補助に留めてください。
- [Suggestion] production で `fake_externals=true` が混入しても `shouldCheckPwned()` が `true` を返す設計順序は fail-secure として妥当です。ここは設計の強い点です。

**6. スコープの適切さ**
- [Suggestion] スコープは概ね適切です。今回を「非本番での HIBP gating」に閉じ、本番のタイムアウト/リトライ/キャッシュ改善を切り離しているのは妥当です。
- [Warning] ただし「staging 等」問題を未解決のまま実装に入ると、見た目は小変更でも運用定義の曖昧さをコードへ埋め込むことになります。修正提案: env 分類だけ先に確定させてから着手してください。

**7. 型安全性**
- [Suggestion] `shouldCheckPwned(): bool` に集約し、`config('testing.fake_externals') === true` で `mixed` を狭める方針は PHPStan level 10 と相性がよいです。型安全性の方向性は問題ありません。
- [Suggestion] `rule()` の戻り値型と docblock は、Laravel の `Password` fluent rule を前提に実態へ合わせて更新すれば十分です。widen で黙らせる設計には見えません。

結論として、方向性自体は妥当です。ただし「どの env で HIBP を有効にするか」の定義が設計本文と述語実装案で不一致なので、そこを解消してから進めるべきです。
