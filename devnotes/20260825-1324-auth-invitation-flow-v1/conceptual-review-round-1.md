全体判定: **CHANGES_REQUESTED**

使命・正典 v1 への追従という目的、既存資産を壊さない最小スコープ、テストファーストの方針は妥当です。ただし、i7 の競合対策と i16 のイベント時機は、現記述のままでは不変条件を確実に満たすと判断できません。

### 1. 使命との整合性

[Suggestion] 招待導線の安定化と確認メールの削減は、現場チームが早く撮影・運用へ入るための摩擦を下げます。North Star への寄与は直接機能ではないものの、組織オンボーディングの基盤改善として合理的です。

### 2. 禁止事項違反

[Suggestion] DTO / JsonResource を迂回する新しい API 応答や、LLM 経路の追加はありません。既存 Inertia 画面への合流を維持するため、禁止事項との衝突は見当たりません。

### 3. 実現可能性

[Critical] 施策 A の「招待行ロック下で組織生存を再確認」だけでは、論理削除と membership attach の競合を閉じられません。招待行をロックしても、組織削除は通常 `organizations` 行を更新するため、組織が生存確認の直後・attach の直前に削除され得ます。これは「削除済み組織への attach を構造的に防ぐ」という主張と一致しません。

修正提案: `joinOrganization()` の同一トランザクションで、招待行をロックした後に、通常スコープ付きの組織行を `lockForUpdate()` で取得し、そのロックを membership 作成まで保持してください。組織削除経路も同じ組織行を更新するため直列化されます。招待行・組織行のロック順序を明文化し、削除側を含むデッドロック方針も設計・テストに含めるべきです。

[Warning] `markEmailAsVerified()` は実装によって `Verified` イベントを即時発火します。登録トランザクション中に呼ぶと、Verified の listener がコミット前の状態を観測したり、外部副作用を出したりする危険があります。「確認メールを送らない」ことは満たせても、イベント整合性は未設計です。

修正提案: `Verified` イベントを必要とするなら、コミット後に発火することを保証してください。不要なら、初期作成した User に `email_verified_at` を明示設定して保存し、Verified イベントを発火させない理由を明記してください。いずれの場合も、`Registered` 後に確認メールが送られないことと、Verified 関連 listener の実行時機を Feature テストで固定してください。

### 4. 期待効果の妥当性

[Warning] i7 の「500 をなくし無効招待へ畳む」効果は合理的ですが、3 経路の早期判定だけでは並行削除時の安全性を保証できません。上記の組織行ロックが入って初めて、期待効果の「TOCTOU を閉じる」が成立します。

修正提案: テストは通常の論理削除ケースに加え、招待受諾と組織削除を並行実行する race テストを追加し、成功した受諾が削除済み組織へ membership を作らないことを固定してください。

[Suggestion] i16 の「確認メールを別送しない」は、メール通知の有無を fake notification 等で明示検証する設計へ具体化すると、Laravel/Fortify の将来変更にも強くなります。

### 5. リスク

[Warning] `InvitationContinuationKeySoTTest` が単引用符の `'invitation_token'` だけを検出対象にすると、二重引用符、定数、動的組み立てによる直書きを見逃します。一本化を「機械検査で恒久固定」と主張するには検出範囲が不足し得ます。

修正提案: `T_CONSTANT_ENCAPSED_STRING` を値として復元し、単・二重引用符の双方を検出してください。動的キーは検出保証外として docblock に明記し、少なくとも `session` API への動的キー渡しを許すか禁止するかを明文化してください。負例には二重引用符の直書きも加えてください。

[Suggestion] 無効招待への畳み込みでは、画面、HTTP ステータス、validation key、文言だけでなく、ログ・例外報告の扱いも揃えると運用上の識別子漏えいを避けやすくなります。

### 6. スコープの適切さ

[Suggestion] SSO 継続、署名 URL、アプリ内受諾を明示的に除外しており、v1 未充足 4 点に絞ったスコープは適切です。`landing()` を移植しない判断も、未使用の抽象化を増やさない点で妥当です。

### 7. 型安全性

[Warning] `InvitationContinuation` の公開契約と依存注入方式が未記載です。Laravel の session read は `mixed` なので、PHPStan level 10 で安全に扱うには `resolve(): ?string`、`remember(string $token): void`、`forget(): void` を明確にし、`mixed` の型絞り込みをクラス内部に閉じる必要があります。

修正提案: session 契約をコンストラクタ注入し、`resolve()` 内で `is_string()` と空文字判定を行ったうえで `?string` のみ返す設計を明記してください。呼び出し側に `mixed` が漏れないこと、空文字・配列・数値を投入すると削除して `null` を返すことを Unit テストで固定してください。
