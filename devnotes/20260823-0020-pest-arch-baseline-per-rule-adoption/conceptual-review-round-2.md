全体判定: **CHANGES_REQUESTED**

Round 1 の主要指摘はほぼ適切に解消されています。特に、S4 の走査範囲拡大、S2 の安全側への反転、走査責務の分離は妥当です。ただし、I3 の「例外は `ArchBaseline` だけが正本」という核心を機械的に保証する部分に、まだ 1 つ抜け道があります。

### 1. 使命との整合性

[Suggestion] AG-167 に従った家系共通機構の導入であり、使命への寄与は間接的ながら妥当です。UI・撮影フローへの直接効果と誤認させず、静的検査基盤の健全性として位置付けている点も適切です。

### 2. 禁止事項違反

[Warning] 「既存 131 本は変更しない」の根拠として「禁止事項 3」を挙げていますが、提示された禁止事項 3 は dev DB への破壊操作禁止です。既存テストとの併存根拠は AG-167 であり、禁止事項 3 ではありません。

修正提案: 該当箇所を「裁定 AG-167」に修正してください。

[Suggestion] 変更対象を新設 6 ファイルと乖離台帳 2 ファイルに明示したことで、前版のファイル数・I7 の矛盾は解消されています。

### 3. 実現可能性

[Critical] S4 は `ignoring` の出現ファイルと件数を固定しますが、引数が本当に `ArchBaseline::exceptionsOf($ruleId)` 由来であることを保証していません。

例えば、将来次のように変更されても、`ignoring` の出現ファイルと件数は変わりません。

```php
->ignoring([
    SomeUnregisteredClass::class,
])
```

この場合、`ArchBaseline::RULES` 側の例外一覧は S2・S3 を通過したまま残せるため、生の追加例外が実際の Pest 表明だけに入り、I3 が破られても検査は緑になり得ます。「許可ファイルを exact-fit に pin」だけでは、許可された口から渡される値の出所までは固定できません。

修正提案: S4 の構造契約に、次のいずれかを追加してください。

- `ignoring` の引数式が `ArchBaseline::exceptionsOf(...)` の直接呼び出しであることを token/AST で固定する。
- より単純に、arch 表明の生成を専用の薄いヘルパーへ閉じ、`ignoring` を呼ぶ箇所を 1 箇所だけにしたうえで、その引数を型付きの規則データからしか渡せない構造にする。
- 7 本を明示記述するなら、各 `ignoring` 呼び出しについて、直近の引数トークン列を期待形と照合する。

単なる `exceptionsOf` の出現件数 pin では、呼び出して戻り値を捨てる偽装が可能なので不十分です。

[Suggestion] `preset` を `tests/` の追跡 PHP 全数で 0 件とし、走査根の空振りも落とす設計は、Round 1 で指摘した別ファイルからの preset 再導入を防げています。

### 4. 期待効果の妥当性

[Suggestion] 効果を「Pest Arch が静的に解決できるシンボル使用」に限定し、動的呼び出し、tests、Blade、外部プロセス等を保証外としたことで、前版の過大な主張は解消されています。

[Warning] 文書上の実測日が「2026-08-23 時点 HEAD」ですが、レビュー時点は 2026-08-22 です。未来時点の実測記録になっており、観測の再現性を損ないます。

修正提案: 実際に観測した日付へ訂正してください。タイムゾーン差によるものなら、使用したタイムゾーンを併記してください。

### 5. リスク

[Warning] S2 の「狭く数える」という向きは正しいです。使用証明では、偽陽性が腐った例外を温存するため、曖昧なものを数えず赤へ倒すべきです。

ただし、素の `sha1()` を「グローバル関数呼び出し」と断定するには名前空間解決が残ります。名前空間内に同名関数が存在すれば、同じ字面でもグローバル `sha1` の呼び出しとは限りません。設計はこれを保証外としながら、素の `sha1()` 自体は数えるため、保証外の形が安全側ではなく使用証明に混ざっています。

修正提案: 次のいずれかにしてください。

- S2 は `\sha1()` のような完全修飾呼び出しだけを使用証明として数える。
- 素の `sha1()` も数える場合、対象ファイルの名前空間と同名関数宣言・`use function` を解決し、曖昧なら例外にする。
- Pest Arch の実際の検出意味論が名前解決後の関数ではなく字面のシンボル使用であるなら、S2 の名称と I4 を「グローバル関数の実使用」ではなく「Pest が対象シンボルとして検出する使用」へ合わせ、そのことを vendor 実装に対する負例・正例で固定する。

これは現在の4例外が誤っているという指摘ではなく、将来同名関数が追加された場合の逆向き証明の健全性に関する指摘です。

[Suggestion] `VendorArchPresetReader` が公開 API ではなく vendor ソース表現に依存すること、更新時の赤を仕様として受け入れること、0件・複数件を落とすことは適切です。

### 6. スコープの適切さ

[Suggestion] 6 ファイルへの分割は過大とは判断しません。役割はそれぞれ独立しています。

- 値の正本
- 使用証明用スキャナ
- サーフェス検査用スキャナ
- vendor 読み取り境界
- 実際の gate
- 走査器の正例・負例

特に S2 と S4 は安全側へ倒す向きが逆なので、1つの汎用スキャナへ統合すると契約が曖昧になります。`VendorArchPresetReader` も vendor の内部表現という別の不安定境界を持つため、分離が妥当です。

[Suggestion] ファイル数を減らす余地があるとすれば、3走査器の自己検査を1ファイルにまとめる現在案までです。走査器本体や gate をさらに統合しても、概念数は減らず責務だけが混ざるため、現案が実質的な最小構成です。Critical の引数由来検査も、可能なら `ArchSurfaceScanner` の責務拡張として収めれば、7本目の支援クラスは不要です。

### 7. 型安全性

[Suggestion] PHPStan 対象外である事実を明記し、「level 10 を通せる」という未検証の主張を取り下げた対応は適切です。配列 shape、`class-string`、Reflection・token・ファイル境界の runtime assertion を受入条件にした点も妥当です。

[Warning] `Webmozart\Assert\Assert` は不正値を落とす手段ですが、それだけで静的な配列 shape が保持されるとは限りません。特に vendor ソースから抽出する値と `token_get_all()` の戻り値は、PHPStan 上で型が広がりやすい境界です。

修正提案: 専用の戻り値 shape または小さな DTO/value object を使うか、各公開メソッドの戻り値を `list<string>` 等へ正規化した後に返すことを受入条件へ追加してください。コマンドラインで新設パスを解析する確認方針は妥当です。

Critical の一点、すなわち「許可された `ignoring` の引数が必ず台帳由来であること」を機械で固定すれば、全体として APPROVED に到達できる設計です。
