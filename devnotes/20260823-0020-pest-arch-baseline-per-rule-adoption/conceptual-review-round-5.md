主要な設計は承認可能な水準です。反射・未知の間接実行を明示的に保証外へ出す判断は共通規約 (b) を満たし、スコープも妥当です。ただし、0件固定する callable 関数について、識別子完全一致だけでは完全修飾名・別名 import を取りこぼすため、S4が主張する検出範囲にまだ具体的な抜け道があります。これは概念設計で契約を一文補うべき事項です。

### 1. 使命との整合性

[Suggestion] AG-167 に従った検査基盤の統一であり、使命への間接的な寄与として妥当です。アプリ機能や既存検査へ変更を広げていません。

### 2. 禁止事項違反

[Suggestion] アプリコード、既存131本、DB、LLM経路を変更しない範囲が明確で、提示された禁止事項への抵触はありません。

### 3. 実現可能性

[Warning] callable 実行語彙5種のうち、関数である次の4語彙は、PHPで完全修飾または別名 import できます。

```php
\call_user_func([$object, 'ignoring'], $exceptions);

use function call_user_func as invoke;
invoke([$object, 'ignoring'], $exceptions);
```

`identifierSites()` が単純な識別子トークン完全一致だけを見る場合、PHPバージョンとトークン化形によっては `\call_user_func` が `T_NAME_FULLY_QUALIFIED`、修飾名が `T_NAME_QUALIFIED` として一体化され、`call_user_func` という独立識別子が現れません。別名呼び出しも、呼び出し位置には `invoke` しか現れません。

このため「callable 実行語彙5種を0件で固定」という主張を現状の走査契約では満たせない可能性があります。

修正提案: 概念設計で次を明記してください。

- 4関数は `T_STRING` だけでなく、完全修飾名・修飾名を正規化して完全修飾関数名として照合する。
- `use function` と group use、別名 import を解決し、対象関数への alias 呼び出しも検出する。
- 解決できない関数 import・呼び出し形は未解決として失敗させる。
- `fromCallable` はメソッド名として別契約で検出する。
- 正例・負例に `\call_user_func(...)` と `use function ... as ...` を加える。

これは新しいファイルや機構を必要とせず、`ArchSurfaceScanner` の契約補足で済みます。したがって詳細な token 実装は詳細設計へ送れますが、「完全修飾名と別名 import も対象」という保証範囲は概念設計で確定させるべきです。

[Suggestion] 反射経路を保証外としてI3直下に明記した判断は適切です。「検出力を狭める」選択が明示されており、共通規約 (b) を満たします。

[Suggestion] Pest Arch 自体の検出限界と、S4の迂回可能性を(a)/(b)に分離したことで、保証範囲は明瞭になりました。

[Suggestion] I3表の「リポジトリ全体で1本」という表現も、直下の保証範囲によって限定されています。さらに明確にするなら、表自体を「S4が解決対象とする構文内で1本」に変更すると、単独で読んだ場合の誤解を防げます。

### 5. リスク

[Suggestion] 動的メンバ目録を「受容した未解決箇所」とし、安全証明ではないこと、同一ファイル内置換を検出しないことまで明記したため、保証の誇張は解消されています。

### 6. スコープの適切さ

[Suggestion] 新設6ファイルと乖離台帳2ファイルは適切です。完全修飾名・alias対応も既存の `ArchSurfaceScanner` とその自己検査へ収められるため、成果物を増やす必要はありません。

### 7. 型安全性

[Suggestion] array shape、正規化済みリスト、runtime assertion、限定的なPHPStan実行という受入条件は妥当です。

[Warning] callable 関数の名前解決を追加する場合、走査結果を単なる生の識別子ではなく、少なくとも「解決済み関数名」または「未解決」を区別できる型で返す必要があります。

修正提案: `ArchSurfaceScanner` の内部契約として、未解決名を候補から黙って除外せず例外または判別可能な結果にすることを明記してください。公開戻り値の既存array shapeを変えるかどうかは詳細設計へ送って構いません。
