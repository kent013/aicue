全体判定: **CHANGES_REQUESTED**

### 1. 使命との整合性

[Suggestion] 直接の撮影体験改善ではないものの、将来の安全なアーキテクチャ検査導入を標準化し、静かに保護が外れる検査上の欠陥を防ぐ点で、使命を支える基盤改善として妥当です。AG-167 により導入判断も済んでおり、目的の再議は不要です。

### 2. 禁止事項違反

[Warning] 「新規 2 ファイルのみ」としつつ、乖離台帳への登録と `LedgerPins::DIVERGENCE_ENTRY_COUNT` の更新を詳細設計で扱うとしています。後者を実装するなら、実際の変更対象は少なくとも 4 ファイルになり、I7 の「既存ファイルに触れない」という表現とも整合しません。

修正提案: 「アプリコード・既存 Architecture テストは変更しない」と制約を言い換え、乖離台帳更新をこの導入の必須付随変更として明記してください。あるいは、台帳登録を別 TODO にするなら、その理由と安全性を明記してください。

[Suggestion] `response()->json()`、LLM 経路、DB 操作、PHPStan baseline 化には抵触しない設計です。

### 3. 実現可能性

[Critical] I1/I3 の自己検査対象が `ArchBaselineTest.php` 自身だけでは不十分です。将来、別の `tests/` ファイルで `preset(...)->ignoring(...)` または生の `->ignoring(SomeClass::class)` を追加しても、設計上の自己検査は緑のままです。これは「例外一覧は ArchBaseline だけ」「preset に一括 ignoring を渡さない」という不変条件を、実際にはリポジトリ全体で守れていない状態です。

修正提案: `tests/` 配下の追跡 PHP ファイル全体を対象に、少なくとも以下を deny-by-default で検査してください。

- `preset(` の呼び出しを禁止する、または許可ファイル・許可形を明示的な inventory で固定する。
- `ignoring(` の呼び出しを `ArchBaselineTest.php` の規定された経路だけに限定する。
- 許可経路では例外クラス名の直書きではなく、`ArchBaseline::exceptionsOf()` 由来であることを固定する。

単なる文字列検索では別名 import やコメント等への耐性が不足するため、既存の走査器規約に従い token ベースで対象・保証範囲・未解決時の扱いを定義してください。

[Warning] S5 は vendor の preset 実装詳細に依存します。Pest/plugin の更新で preset クラス名・定数・配列表現が変わると、語彙変更ではなく「読み取り不能」で落ちる可能性があります。落ちること自体は fail-closed として正しい一方、どの vendor API／ソース表現を互換境界とするかが未定義です。

修正提案: S5 の入力元を「Pest Arch plugin のどのクラス・メソッド・定数」として明記し、解決不能時は明確な失敗メッセージを出す設計にしてください。vendor の公開 API が存在しない場合は、ソース解析への依存を明文化し、Composer 更新時にベースライン更新が必要となることを受け入れるべきです。

### 4. 期待効果の妥当性

[Warning] 「禁止関数 97 語彙に対する網が新設される」は、Pest arch の実際の検出意味論次第では強すぎる表現です。`toBeUsed()` が捕捉するのは Pest が解析できる使用形だけであり、動的呼び出し、文字列経由の呼び出し、外部プロセスなどまで防ぐものではありません。

修正提案: 「Pest Arch が検出対象とする静的なシンボル使用に対する網」と限定して記述してください。既存の token gate や SSRF・LLM 防御と代替関係ではない点も維持してください。

[Suggestion] 例外を持つ語彙を `sha1`、`tempnam`、`var_export` の単独規則へ隔離する設計は、問題としている例外波及半径を最小化しており、期待効果は合理的です。

### 5. リスク

[Warning] S2 の「例外クラスが対象関数を実使用している」証明は、関数呼び出し検出器の精度が重要です。`Foo::sha1()`、`$object->sha1()`、宣言、名前が部分一致する関数を除く方針は適切ですが、名前空間付き関数呼び出し、先頭の `\sha1()`、`use function`、可変関数呼び出しをどう扱うかが未定義です。

修正提案: S2 が保証する構文を docblock に明記し、保証範囲内で解決不能な形は fail-closed にしてください。少なくとも `sha1()` と `\sha1()` の扱い、名前空間内での関数解決方針を負例・正例として固定してください。動的呼び出しを保証対象外とするなら、その限界を明記してください。

[Suggestion] 層分離 preset を今回導入しない判断は適切です。現状で巨大 allowlist を作ることは、例外管理の空洞化を再導入するリスクがあります。

### 6. スコープの適切さ

[Warning] 「S2 の新規走査器」と「S4 の全 tests 走査」を同一テストファイルに密集させると、値の置き場である `ArchBaseline` と検査器・gate の責務が混ざり、将来の保守性が下がります。

修正提案: `ArchBaseline` は定数・純アクセサに限定したまま維持し、走査ロジックは既存の `tests/Support/` 規約に沿った小さな専用サポートクラスへ分離するか、少なくとも `ArchBaselineTest` 内で走査契約・限界・負例への参照を明瞭に区画してください。新規ファイル数を目的化せず、不変条件の検出力を優先してください。

[Suggestion] 既存 131 本を統廃合せず、禁止関数ベースラインだけを追加する範囲は、AG-167 と「今必要なものだけ作る」に整合しています。

### 7. 型安全性

[Suggestion] 実行コードではなくテスト支援コードであり DTO／JsonResource の適用対象ではありません。`RULES` の配列 shape は PHPDoc で厳密に定義し、`list<string>`、`list<class-string>`、規則 ID の型をアクセサの戻り値まで一貫させれば、PHPStan level 10 を通せる設計です。

[Warning] PHPStan の通常対象に `tests/` が含まれないため、「PHPStan level 10 を通せる」は実行検証ではなく設計上の見込みに留まります。

修正提案: 実装 TODO では、tests を含めた一時的または専用の静的解析方法を用意するか、少なくとも Pest API・`ReflectionClass`・token API 境界の型を PHPDoc と明示的な runtime assertion で閉じてください。型を `mixed` や曖昧な配列へ widen して回避しないことを受入条件に加えるべきです。
