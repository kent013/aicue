## 施策3: `ArchSurfaceScanner`

判定: APPROVE

### R2-1への回答

走査分離によって `arch` の穴は再発していません。

- `\arch()` は末尾セグメントで `call`
- `use function Pest\arch as x` は元名のセグメントで `import`
- `ignoring` / `toBeUsed` は静的なメンバ名なら `identifierSites()`
- 動的メンバ名は `dynamicMemberSites()` の母集団へ入る

既知の動的メンバ箇所を同一ファイル内で別用途へ置換する迂回は残りますが、設計自身が保証外として明記しており、主張との不一致ではありません。

### `unresolved` 撤去への回答

妥当です。現在の走査器は名前解決結果を作らず、名前トークンの各セグメントを完全一致で比較するだけです。有効なPHP構文で「解決不能」になる段階がありません。

- 不正構文は `TOKEN_PARSE` で例外
- 修飾名やnamespace差は拾いすぎる側
- 可変関数・文字列・Reflectionは明示的な保証外

したがって、概念設計の要求を黙って落としたのではなく、未解決状態を生む処理自体を撤去したものと評価できます。

## 施策5: `ArchBaselineTest`

判定: REQUEST_CHANGES

- [Warning] すべての例外クラスがPestのオブジェクト集合に含まれることを直接検査していません。

  現在の4クラスは「代表クラス4件」のpinにより実質的に確認されますが、将来5件目の例外を追加した場合、そのクラスがPest集合に入らなくても次を通る可能性があります。

  - `class_exists()`
  - PSR-4根配下の実パス
  - S2のソース内関数呼び出し
  - 接頭辞衝突なし

  修正案: 代表クラスpinとは別に、例外集合について一般化した包含検査を追加してください。

  ```php
  foreach ($exceptionNames as $exceptionName) {
      expect($allPestObjectNames)->toContain($exceptionName);
  }
  ```

  これを追加すれば、S3第6条のPSR-4実パス判定は原則として冗長です。Pest自身の集合に含まれることの方が、「Pestが実際に検査する対象」という不変条件を直接証明します。Reflectionの読取可能性はS2で別途閉じられます。

- [Warning] V6の根拠から確定できるのは「1ファイルにつき最初の1オブジェクトだけが独立したObjectDescriptionになる」までです。

  `findFirst()` だけでは、2つ目のクラス内の依存が次のどちらになるかは確定しません。

  1. 完全に無視される
  2. ファイル全体の依存として最初のオブジェクトへ帰属する

  修正案: `ObjectDependenciesDescription` が依存を収集するAST範囲までvendor実装を確認するか、2クラスを持つfixtureによるPest実測を追加してください。確認前は保証外の記述を次までに狭めます。

  > Pestは2つ目以降のクラスを独立したオブジェクトとして表現しない。依存が無視されるか最初のオブジェクトへ帰属するかは本gateでは保証しない。

  なお、どちらの挙動でも2つ目のクラス名は独立した除外対象にならないため、「接頭辞衝突の母集団としてPestのオブジェクト集合を使う」という設計判断自体は維持できます。

### `@internal` APIへの結合

許容できます。S5は既にvendorソース表現へ依存しており、更新時に赤くなることも仕様として明記されています。独自クラス走査器を増やすより小さい設計です。

### 母集団の非空検査

床値、代表クラス、全例外クラスの包含検査を組み合わせれば十分です。
