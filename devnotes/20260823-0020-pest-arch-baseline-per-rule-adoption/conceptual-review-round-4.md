全体判定: **CHANGES_REQUESTED**

Round 3 の2点は適切に解消されています。通常の arch チェーン、可変メンバ構文、通常の Pest `expect()` との混同は閉じました。ただし、S4 が保証外として明記する「文字列経由の呼び出し」から `ignoring` を実行でき、I3 の全域保証と再び衝突しています。

### 1. 使命との整合性

[Suggestion] AG-167 に沿った検査基盤の統一であり、使命への間接的な貢献として妥当です。アプリ機能や既存検査の統廃合へ範囲を広げていません。

### 2. 禁止事項違反

[Suggestion] アプリコード、既存131本、DB、LLM経路を変更しない範囲は明確です。提示された禁止事項への抵触はありません。

### 3. 実現可能性

[Critical] 動的メンバ構文は塞がれましたが、文字列を使う動的呼び出しが残っています。例えば次の形では、`ignoring` は識別子トークンにも動的メンバ構文にも現れません。

```php
call_user_func(
    [$archExpectation, 'ignoring'],
    [SomeUnregisteredClass::class],
);
```

同様に、`ReflectionMethod`、`Closure::fromCallable()`、配列 callable なども利用できます。設計自身が `ArchSurfaceScanner` の保証外に「文字列経由の呼び出し」を挙げていますが、その構文で保護対象操作を実行できるため、共通規約 (b) と I3 の「リポジトリ全体で1本だけ」が一致しません。

修正提案: 最小案は、I3 と S4 の保証を次のように限定することです。

> PHP の静的メンバ呼び出しおよび可変メンバ構文で構築される Pest arch チェーンについて、許可されたチェーンは1本だけである。文字列・Reflection・callable 経由の動的実行は保証しない。

ただし、この限定を採る場合、「その構文から同じ穴を作れる」という保証外をI3の直下にも明記する必要があります。

リポジトリ全体で本当に1本だけと主張するなら、少なくとも以下を未解決 inventory の対象に加える必要があります。

- `call_user_func` / `call_user_func_array`
- `Closure::fromCallable`
- `ReflectionMethod` 等の反射呼び出し
- callable 配列・文字列を実行する既知の経路

すべての動的実行を完全に証明するのはスコープ過大になりやすいため、正典 v1 が静的な arch API 使用面だけを対象としているなら、保証を正確に狭める方が妥当です。

[Suggestion] `arch` から文末までのチェーン完全一致により、通常のグローバル `expect()` との混同は解消されています。`arch`、`ignoring`、`toBeUsed` の件数 pin も静的なチェーンに対して有効です。

### 4. 期待効果の妥当性

[Suggestion] Pest Arch の走査範囲と動的関数呼び出し等の保証外が明記され、期待効果は過大に表現されていません。

[Warning] S4については、保証外である文字列経由の呼び出しが「Pest Arch 本体が検出しない対象」ではなく「S4自体を迂回する手段」です。現在は期待効果の保証外とS4の保証外が混在しています。

修正提案: 「Pest Arch の禁止語彙検出が保証しないもの」と「ベースライン構造を守るS4が保証しないもの」を分けて記載してください。

### 5. リスク

[Suggestion] tests 全803ファイルを母集団とし、語彙による事前絞り込みを避けた判断は正しいです。動的ディスパッチ自身が絞り込み条件を隠せるため、全数から未解決構文を拾う必要があります。

[Warning] 動的メンバ目録をファイル別件数だけで pin すると、同じファイル内で正当な既存箇所を危険な動的呼び出しへ置換しても件数が変わらない可能性があります。通常の exact-fit inventory としては理解できますが、「未解決を安全と証明するもの」ではなく、「未解決箇所の増減をレビューへ上げるもの」です。

修正提案: I3では、目録登録された7件を「安全と証明済み」と表現せず、「人手で用途を確認して受容した未解決箇所」としてください。必要なら各ファイルの件数に加えて、正規化した呼び出し形の fingerprint を pin できますが、正典が要求しないなら追加しなくて構いません。

### 6. スコープの適切さ

[Suggestion] 6ファイル構成は依然として妥当です。型付き array shape を採用したことで、値オブジェクト用の追加ファイルも不要になりました。

[Warning] 「動的メンバ名の目録が空でない」を母集団健全性として固定するのは不適切です。将来7件すべてが正当に除去された場合、望ましい状態である0件を拒否し、不要な動的構文を残す圧力になります。

修正提案:

- 非空を要求するのは `tests/` の走査母集団だけにする。
- `dynamicMemberSites()` の検出力は合成負例で固定する。
- 実コードの動的メンバ件数は目録との完全一致だけを要求し、目録自体は0件を許容する。

これにより「母集団ゼロ」と「違反・未解決箇所ゼロ」を正しく区別できます。

### 7. 型安全性

[Suggestion] array shape の公開契約、正規化済み戻り値、生の token 配列を外へ出さない方針は妥当です。6ファイル構成とも整合しています。

[Warning] 成果物一覧では `GlobalFunctionCallScanner` を「Pest の検出集合の部分集合だけを数える」としていますが、後段ではI4を純粋な構文上の契約へ変更し、「Pestが検出することは保証しない」としています。

修正提案: 成果物一覧の説明も「対象名と完全一致する素の関数呼び出しだけを狭く数える」へ統一してください。型の問題ではありませんが、公開契約の意味を一意にするために必要です。

静的・可変メンバ構文に関するRound 3のCriticalは解消済みです。残る主要判断は、文字列・callable・Reflection経由までS4で塞ぐのか、それらを明示的に保証外としてI3の主張を狭めるのか、です。後者を選び、動的目録の非空要求を外せば、スコープを増やさず承認可能な設計になります。
