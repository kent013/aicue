全体判定: **CHANGES_REQUESTED**

通常の `->ignoring(...)` に対する台帳迂回は塞がりました。`foreach` による単一生成点と引数トークン列の照合は有効です。ただし、S4 が保証外としている可変メソッド呼び出しで同じ保護対象操作を実行できるため、I3 の「リポジトリ全体で1箇所」という主張とはまだ一致していません。

### 1. 使命との整合性

[Suggestion] 使命への間接的・構造的な寄与という位置付けは妥当です。AG-167 に基づく導入であり、既存の撮影・生成機能へ不要な変更を広げていません。

### 2. 禁止事項違反

[Suggestion] 既存テストを維持する根拠が AG-167 と `app-design` 側の規約へ訂正され、AGENTS.md の禁止事項番号との誤対応は解消されています。

[Suggestion] アプリコード、DB、LLM 経路、レスポンス形式には触れず、既存 Architecture テストとも併存するため、提示された禁止事項への直接的な抵触はありません。

### 3. 実現可能性

[Critical] S4 は可変メソッド名を保証外としていますが、可変メソッド呼び出しでも `ignoring` を実行できます。

```php
$method = 'ignoring';

arch('unsafe')
    ->expect(['sha1', 'eval'])
    ->not->toBeUsed()
    ->{$method}([SomeClass::class]);
```

この形は、設計上の `ignoring` 識別子完全一致には現れず、別ファイルから一括例外を再導入できます。AGENTS.md の共通規約 (b) が定めるとおり、保証外構文で保護対象操作を書ける場合、単に docblock へ保証外と記載するだけでは不十分です。

修正提案: 次のいずれかで閉じてください。

- `tests/` の追跡 PHP 全数で、メソッド名を静的に解決できない可変メソッド呼び出しを検出したら S4 を fail-closed にする。
- 少なくとも arch API の戻り値に対する可変メソッド呼び出しを未解決として落とす。
- I3 を「静的な `ignoring` 呼び出しに限る」へ狭める。ただし、正典の穴を機械で塞ぐ目的からすると、この選択では保証が弱いため非推奨です。

一般的な可変メソッド呼び出しをすべて禁止すると既存テストへの影響が大きい可能性があるため、実装前に母集団を実測し、必要なら理由付き inventory にしてください。

[Warning] `expect` の検査範囲が曖昧です。`tests/` には通常の Pest assertion としての `expect(...)` が多数存在し得ます。また、自己検査5部でも通常の `expect()` を使う可能性があります。

修正提案: S4 が固定する対象を、単なる `expect` 識別子ではなく、単一の arch チェーンにある `->expect(...)` に限定してください。少なくとも以下を token 上で区別する必要があります。

- 通常のグローバル `expect(...)`
- arch の `->expect(...)`
- unrelated object の `->expect(...)`

そのうえで、`arch(...)` から始まり `->not->toBeUsed()->ignoring(...)` へ続く対象チェーンがちょうど1形だけ存在することを、正例・負例で固定してください。

### 4. 期待効果の妥当性

[Suggestion] 日付とタイムゾーン、コミット識別子が併記され、実測時点の曖昧さは解消されています。

[Suggestion] 「Pest Arch が静的に解決できる使用」に効果を限定し、動的呼び出しや tests、Blade などを保証外としているため、期待効果の表現は適切です。

### 5. リスク

[Warning] S2 の安全方向は正しく、現行 vendor 実装を前提とすれば「トークン完全一致する素の呼び出し」は Pest の接尾辞一致による検出集合の部分集合です。`mysha1()` を数えない判断も、使用証明の偽陽性を避ける点で妥当です。

ただし、vendor が接尾辞一致を変更した場合、「例外が保守的に余る」だけとは限りません。S2 は通る一方で、Pest がその呼び出しを対象シンボル使用と判断しなくなれば、I4 の「対象シンボルを実使用している」という意味上の契約が崩れます。I2 により他シンボルへの波及は防げますが、例外腐敗検出は機能しなくなります。

修正提案: 次のどちらかにしてください。

- I4 を「登録クラスに対象名と完全一致する素の関数呼び出しが存在する」という構文上の契約へ限定する。
- 「Pest の検出集合の部分集合」を保証するなら、vendor の実際の検出器へ正例を通す統合テスト、または依存している接尾辞一致の意味論を検出するトリップワイヤを追加する。

後者を追加するとスコープが増えるため、正典が求める逆向き証明が構文上の使用証明で足りるなら、前者が最小です。

### 6. スコープの適切さ

[Suggestion] 3走査器、値の正本、gate、走査器テストという6ファイル構成は、責務の違いから見て過大ではありません。S2 と S4 は安全側へ倒す向きが逆であり、統合しない方が明確です。

[Warning] `ArchSurfaceSite` を値オブジェクトとして導入する一方、成果物一覧に対応するファイルがありません。`ArchSurfaceScanner.php` に複数クラスを置くのか、7本目のファイルにするのかが未確定です。

修正提案: 小さな immutable array shapeで十分なら、既存ファイル内の型付き shapeとして返し、6ファイルを維持してください。独立した値オブジェクトが必要なら、成果物を新設7ファイルへ訂正してください。ファイル数より、autoload・静的解析・既存配置規約との整合を優先すべきです。

### 7. 型安全性

[Suggestion] 生の token 配列を公開境界から出さず、`list<string>` または正規化済みの型へ閉じる方針は適切です。CLI 引数で新設パスを PHPStan 解析する受入条件も妥当です。

[Warning] `ArchSurfaceSite` の配置と型が未確定なため、公開戻り値の型安全性も確定していません。

修正提案: 実装前に、次のいずれかを明記してください。

- `list<array{identifier: string, file: string, tokenIndex: int, argumentTokens: list<string>}>`
- 独立した `final readonly class ArchSurfaceSite`

前者ならファイル増加を避けられます。後者なら専用ファイルとコンストラクタ不変条件を成果物へ含めてください。

通常の静的呼び出しに関する Round 2 の Critical は解消済みです。残る承認条件は、可変メソッド呼び出しを未解決として落とすことと、S4 の `expect` 検査を arch チェーンへ正確に限定することです。
