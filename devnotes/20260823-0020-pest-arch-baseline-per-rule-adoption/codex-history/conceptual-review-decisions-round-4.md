# 対応マトリクス: conceptual-review Round 4

## [Critical] 3. 文字列 / callable / Reflection 経由の呼び出しで `ignoring` を実行できる

- 判断: **対応する**。助言どおり「**保証を正確に狭める**」を主軸に据えたうえで、
  **費用ゼロで塞げる分だけは塞ぐ**という 2 段構えにする。
- **母集団の実測** (`git ls-files -- 'tests/*.php'` の 803 ファイルを `token_get_all()` で走査):

  | 識別子 | `tests/` 全数での出現 |
  |---|---|
  | `call_user_func` | **0 件** |
  | `call_user_func_array` | **0 件** |
  | `forward_static_call` | **0 件** |
  | `forward_static_call_array` | **0 件** |
  | `fromCallable` | **0 件** |
  | `ReflectionMethod` | **40 件 / 多数の既存 Architecture テスト** |

- 対応内容 (2 段構え):
  1. **費用ゼロで塞げる分は塞ぐ** — S4 に検査を 1 本足し、
     `call_user_func` / `call_user_func_array` / `forward_static_call` /
     `forward_static_call_array` / `fromCallable` の識別子出現が
     **`tests/` 全数で 0 件**であることを deny-by-default で固定する。
     現状 0 件なので**目録すら要らず、既存テストへの影響もゼロ**である。
     将来これらを使いたくなったら目録へ理由付きで登録する形にする (aicue の既存作法)。
  2. **残りは保証を明示的に狭める** — `ReflectionMethod` / `ReflectionFunction` 経由の呼び出しは
     既存 Architecture テストが 40 か所で正当に使っており、目録にすると
     「本 gate と無関係な 40 件を本 gate が握る」形になって過大である。
     したがって I3 の直下に**保証外を明記**する:

     > **I3 が保証するのは、識別子として書かれた静的なチェーンと可変メンバ構文までである。**
     > `ReflectionMethod` などの反射経由・未知の間接実行経路からは同じ操作を書ける。
     > この構文について**検出力を主張しない** (共通規約 (b) の「検出力の主張をその構文を除く形へ
     > 明示的に狭める」側)。

  - 正典 v1 が塞ぐと定めたのは「**preset へ一括 ignoring を渡す**」という
    **人が普通に書く形**の穴であり、反射で arch の内部 API を叩く形は正典の想定外である。
    ここで完全性を追うと gate が肥大し、思考原則 2 に反する。

## [Warning] 4. 「Pest Arch の検出が保証しないもの」と「S4 が保証しないもの」が混在している

- 判断: **対応する**
- 根拠: 前者は「禁止語彙の網の限界」、後者は「ベースライン構造を守る仕組みの迂回路」で、
  読み手にとって意味がまったく違う。混ぜて書くと両方の限界が正しく伝わらない。
- 対応内容: 期待効果の「保証しないもの」節を **(a) Pest Arch の禁止語彙検出が保証しないもの** と
  **(b) ベースライン構造を守る S4 が保証しないもの** の 2 つに分けて書き直した。

## [Warning] 5. 動的メンバ目録は「安全の証明」ではなく「未解決箇所の増減をレビューへ上げるもの」

- 判断: **対応する**
- 根拠: 正しい。ファイル別件数の exact-fit は「同一ファイル内での置換」を検出しない。
  目録の意味を実態より強く書くのは、本リポジトリが繰り返し戒めている
  「保証範囲を誇張しない」に反する。
- 対応内容: 目録の説明を
  「**人手で用途を確認して受容した未解決箇所であり、安全であることの証明ではない。
  同一ファイル内での置換は検出しない**」へ改めた。
  呼び出し形の fingerprint 追加は**採らない** (正典が要求しておらず、費用に見合わない)。

## [Warning] 6. 「動的メンバ名の目録が空でない」を母集団健全性として固定するのは不適切

- 判断: **対応する**
- 根拠: 正しい。7 件がすべて正当に除去された状態 (= 望ましい状態) を赤にしてしまい、
  不要な動的構文を残す圧力になる。共通規約 (b) の「違反が 0 件」と「母集団が 0 件」の
  区別を、まさに取り違えていた。
- 対応内容:
  - 非空を要求するのは **`tests/` の走査母集団 (追跡 PHP の一覧)** だけにした。
  - 動的メンバ名の目録は **0 件を許容**する (実コードとの完全一致だけを要求)。
  - `dynamicMemberSites()` の検出力は**合成負例**で固定する (実コードの件数に依存させない)。

## [Warning] 7. 成果物一覧の `GlobalFunctionCallScanner` の説明が本文と食い違う

- 判断: **対応する**
- 根拠: 一覧は「Pest の検出集合の部分集合だけを数える」のまま、本文は構文上の契約へ変更済みだった。
  公開契約の意味は 1 つでなければならない。
- 対応内容: 一覧の説明を
  「**対象名と綴りがトークン完全一致する素の関数呼び出しだけを狭く数える**」へ統一した。
