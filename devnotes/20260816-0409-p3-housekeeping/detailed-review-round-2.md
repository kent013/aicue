## 施策 2: REQUEST_CHANGES

[Warning] 「絶対パスを返す」という保証が実装からは成立しない

`find_claude_extension` が返す値は次の組み立て結果であり、正規化されていない。

```sh
"$_root/anthropic.claude-code-$_version"
```

`_root` は `$HOME` 由来なので、通常の開発環境では絶対パスになるものの、POSIX sh として `$HOME` が絶対パスであることはこの関数自身では保証していない。設計本文と警告文の要件が「絶対パス」と断定しているため、実装の保証より記述が強い。

修正案はどちらかに統一する。

- `$HOME` が `/` で始まることをラッパの前提として明記し、テストでも絶対パスの偽 HOME を使って固定する。
- 実在候補へ `cd` して `pwd` の結果を返し、関数自身で絶対パス化する。

小さな掃除という範囲を考えると、前者が妥当。ただし「任意の POSIX 環境で絶対パスを返す」とは書かず、「絶対パスで設定された `$HOME` を前提に、その配下のパスを返す」と限定すべき。

[Suggestion] 関数コメントのスコープ説明を現在の呼び出し方まで含めると誤読しにくい

現在のコメントは「関数内の変数はグローバルになる」とだけ先に述べるため、直後の実装だけ読むと漏洩があるように見える。実際には、示された2つの呼び出しはいずれもコマンド置換の部分シェル内なので親シェルには漏れない。この判断自体は正しい。

例えば次のように一続きで書くと正確になる。

```sh
# POSIX sh に local は無いが、この関数はコマンド置換内でのみ呼ぶため、
# 変数代入は親シェルへ漏れない。将来の直接呼び出しとの衝突を避けるため
# 関数内の変数は `_` 始まりとし、呼び出し側では同じ名前を使わない。
```

W2 の修正は適切。「偽バイナリへの到達」と「実機での実行可能性」が明確に分離されている。`[ -x ]` と `exec` 成功を混同しておらず、保証範囲も過不足ない。

`sort -V` についても、既存依存であること、今回解消しないこと、テストがその前提を表面化させることが明記されており妥当。
