# 対応マトリクス: conceptual-review Round 1

Codex の全体判定は **APPROVED**。Critical は 0 件。Warning 3 件はすべて対応した。

## [Warning] 互換性の主張が「Laravel 12+ 一般」と読めてしまう

- 判断: **対応する**
- 根拠: 指摘のとおり。契約表と振る舞い検査は `laravel/framework` の実装そのものを pin する
  性質のもので、版をまたいだ一般的な互換を主張できる種類の設計ではない。
  aicue の `composer.lock` が移植元と同一の v13.18.0 であることは実読で確認済みなので、
  主張の範囲をそこへ限定すれば正確になる。
- 対応内容: 「移植の方針」節に引用ブロックを追加し、
  「主張するのは aicue の現行 `composer.lock` で動くことだけ」「framework / Carbon を更新したら
  赤くなるのが正しい振る舞いで、そのとき棚卸しするのが PR レビューの義務」と明記した。

## [Warning] 母集団に Mailable / Notification が入ることで、メール実装が原因で gate が赤くなりうる

- 判断: **対応する** (母集団は変えない。書き方を直す)
- 根拠: 母集団を `ShouldQueue` 実装の全数にするのは正典側の設計であり、
  aicue の `QueuedJobPopulation` も同じ集合を既に正本にしている。
  Mailable / Notification も同じキューに載り同じ試行回数の勘定を受けるので、
  対象から外すのは検出力の縮小になる。ただし「ジョブの gate なのにメールで落ちる」という
  読み違えが調査を遠回りにする、という指摘そのものは正しい。
- 対応内容: 「母集団に Mailable と Notification が入ることの意味」節を新設し、
  ここでの「ジョブ」がキューに載るもの全般を指すこと、メール由来で赤くなるのは
  誤検出ではなく設計どおりであることを書いた。あわせて
  **静的 gate の冒頭コメントと `aicue:D25` の本文に同じ説明を書く**ことを設計に組み込んだ。

## [Warning] `tests/` が PHPStan 対象外なので型安全性の観点への回答が弱い

- 判断: **対応する**
- 根拠: 指摘のとおり「対象外なので触れない」で終わると、読み手は
  「level 10 が新規 29 ファイルも見ている」と誤読しうる。誇張しない書き方を徹底する。
- 対応内容: 「既存の検査群との整合」節の PHPStan 項へ、
  本件について `composer phpstan` が主張できるのは**悪化していないこと**だけであると明記した。
  実質的な担保 (移植元が level 10 を通していること / gate 自身の正例・負例) も書いた。
  `tests/` の PHPStan 対象化は**独立した作業項目**へ切り出す方針として明記した
  (移植の byte 一致性と型検査の導入を 1 つの変更に混ぜないため)。
  受け入れ条件への検証コマンドの明記は詳細設計 §受け入れ条件で行う。
