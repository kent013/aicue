## 5. リスク

[Warning] 419 の戻り先決定契約が二通り存在します。

status 正本では、419 を次のように定義しています。

> ログイン + トップ（常に未認証扱い）

一方、「戻り先はサーバ側に固定した許可一覧から出す」では、次のように定義されています。

> 分岐の入力は認証状態のみ  
> 認証済み: ダッシュボード + トップ  
> 未認証（419 のセッション切れを含む）: ログイン + トップ

419 は必ずしも認証状態を失った場合だけ発生するとは限りません。認証済みセッションで CSRF token だけが不一致になる場合、どちらの規則を採るかで結果が変わります。

修正提案:

- 419 を常にログインへ誘導するなら、戻り先 resolver の入力を「status と認証状態」に変更する
- 優先順位を明記する:
  - status 419 → 認証状態にかかわらずログイン + トップ
  - その他 → 認証状態で分岐
- 「分岐の入力は認証状態のみ」を「リクエスト由来入力は使わず、status と認証状態のみ」に修正する
- 全 status × 認証状態のテストで、認証済み 419 もログインになることを固定する

逆に認証済み 419 をダッシュボードへ戻すなら、status 正本の「常に未認証扱い」を削除してください。どちらも技術的には成立しますが、現在の設計意図からは前者が自然です。

## 6. スコープの適切さ

[Suggestion] スコープは適切です。

フォーム POST の 429、Blade、多言語化、観測性を分離したまま、今回変更する API の不正 `Retry-After` だけは同一 PR で回帰固定しています。

なお、骨子の「次の3条件」は実際には4条件なので「次の4条件」へ修正してください。また、503 の待ち時間欄も「`Retry-After` が非負整数のとき」に統一すると正本が揃います。

## 7. 型安全性

[Suggestion] PHPStan level 10 を通すための境界は十分に定義されています。

419 の方針として status override を採用する場合は、`ErrorScreenDestinations` のシグネチャにも `InertiaErrorScreenStatus` を含め、認証状態だけを受け取る型のままにしないことが必要です。

419 の戻り先規則を一意にすれば、概念設計として APPROVED です。
