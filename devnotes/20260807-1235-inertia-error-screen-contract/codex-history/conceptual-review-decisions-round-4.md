## [Warning] 観点 5: 419 の戻り先決定契約が二通り存在する

- 判断: **対応する** (Codex 提示の 2 案のうち**前者** = status override を採る)
- 根拠: 指摘は正当で、設計内に矛盾があった。status 正本では 419 を「常に未認証扱い」と書き、
  戻り先の節では「分岐の入力は認証状態のみ」と書いていたため、
  **認証済みのまま CSRF token だけ不一致で 419** になるケースで結論が割れていた。
  採用するのは前者 (419 は認証状態を問わずログインへ)。理由は、認証済み 419 で
  ダッシュボードへ戻しても同じ token 不一致を踏み直すだけで**詰みが再生産される**ため。
  セッションを取り直せる導線が唯一の確実な脱出路であり、
  使命 (行き先のないエラーを作らない) と整合する。
- 対応内容:
  - 「戻り先はサーバ側に固定した許可一覧から出す」節を書き換え、
    **分岐の入力は `status` と認証状態の 2 つだけ**と定義。適用順序を D1 (419) →
    D2 (認証済み) → D3 (未認証) の表で正本化
  - status 正本の 419 行を「ログイン + トップ (**認証状態を問わない** = 戻り先規則 D1)」に修正
  - 型境界の表に `ErrorScreenDestinations::for(InertiaErrorScreenStatus $status, bool $authenticated):
    non-empty-list<ErrorScreenDestination>` を追加 (認証状態だけを受ける型にしない)
  - 「認証済み 419 もログインへ倒れる」ことを全 status × 認証状態のテストで固定すると明記
