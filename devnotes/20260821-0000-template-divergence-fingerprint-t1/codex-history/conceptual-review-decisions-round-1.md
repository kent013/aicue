# 対応マトリクス: conceptual-review Round 1

## [Critical] 生成器の入力が任意のローカル台帳で、正典の台帳であることを検証していない (観点 3)
- 判断: 対応する
- 根拠: 指摘どおり。指紋の値は「テンプレート側の内容」を名乗るので、入力の出自を縛らないと
  偽の基準線を混ぜられる。`role: app` の出力であることは何の保証にもならない
- 対応内容: §1 に「入力の出自 (provenance) を pin する」を新設。(1) 生成器が入力を
  fail-closed で検査する (`role: template` / schema / 40 桁 hex commit / entries 非空 /
  キーと値の書式)、(2) 出自の 2 値 pin (`TEMPLATE_LEDGER_SOURCE_COMMIT` /
  `TEMPLATE_LEDGER_SOURCE_SHA256`) を検査側へ置き、検査は自台帳の `generated_at_commit` が
  pin と一致することを見る / 生成器は入力ファイルの sha256 が pin と一致しなければ exit 3 で拒否する。
  載せ替えは `--adopt-new-template-ledger` の明示が必要で、新しい pin 値を標準出力へ出す
  (pin の更新が PR に必ず現れる)。手編集が止まらない点は原理的限界として明記

## [Critical] 採用時債務 178 件に再分類の運用契機が無く固定化する (観点 5)
- 判断: 対応する
- 根拠: 指摘どおり。「縮む方向にしか動かない」は規則であって契機ではない。
  テンプレート側の安全な修正を取り込まないまま温存する形が最悪の帰結である
- 対応内容: §3 に「債務を放置させない契機」を新設。新しい期限機構は作らず、登録簿が既に持つ
  `監視中` + 見直し期限 (期限切れ = CI 赤) に載せる。債務一覧を説明する登録 D34 を
  `監視中` / 見直し期限 2027-02-28 で置き、出口は登録簿の規約節の 4 通りをそのまま使う。
  加えて機械の結合を 1 本足す (債務一覧が空でない間、債務一覧のファイルが登録簿の対象パスとして
  登録されていること = D34 を消して債務だけ残す形が落ちる)。責任主体は D34 の `決めた人` が持ち、
  債務 1 件ごとの責任者欄は作らない (178 行に同じ値が並ぶだけで一次情報にならない)

## [Warning] 生成器が PHP なので strict_types・禁止文 gate の対象である (観点 2)
- 判断: 対応する
- 根拠: 事実。`scripts/*.php` は `StrictTypesDeclarationGateTest` と
  `ForbiddenStatementTokenInvariantTest` の母集団に入る
- 対応内容: §型と検査の境界 に「生成器も `declare(strict_types=1)` を持ち、`echo` と
  開始タグ付きの出力記法を使わない。標準出力・標準エラーは `fwrite()` で書く」を明記

## [Warning] generated_at_commit のコピーだけでは provenance が弱い (観点 3)
- 判断: 対応する (上記 Critical 1 の対応に含む)
- 根拠: 同じ論点。schema を増やさずに済む手段として、検査側の 2 値 pin を採った
- 対応内容: `TEMPLATE_LEDGER_SOURCE_SHA256` (正典台帳ファイル自身の sha256) を pin する。
  正典と schema を揃えたままで出自を縛れる (schema を独自拡張すると家系の可搬性が落ちる)

## [Warning] 「76 件の静かな分岐が閉じる」は不正確 (観点 4)
- 判断: 対応する
- 根拠: 指摘どおり。監視範囲は母集合 275 件 (+ 本機構のファイル) であり、76 は導入時点の内訳である
- 対応内容: §期待効果 を書き換え、76 件を「導入時点で byte 一致だった内訳」と位置付け、
  検査・台帳自身の改変が PR レビューの信頼境界であることを併記した

## [Warning] LedgerPins が形式検査の責務境界を曖昧にする (観点 5)
- 判断: 対応する
- 根拠: 妥当。pin は値であって機構ではない
- 対応内容: 実装方針の表に「不変の scalar 定数だけを持ち、解析・ファイル I/O・git 実行を
  一切持たない」と明記

## [Warning] t1 到達に t3 確認段と composer name 修正を混ぜている (観点 6)
- 判断: 対応する (分離はコミット単位で行い、TODO は 1 本のままにする)
- 根拠: 原因の切り分けの指摘は妥当。ただし TODO を 3 本に割ると、識別子の修正だけが入って
  役割の 2 重化が成立しない中間状態を main に残しうる (スコープの推奨も standalone 1 本である)
- 対応内容: §実装の分割と t1 の受入条件 を新設。C1 識別子 → C2 t1 機械層 → C3 t3 確認段 の
  3 コミットに分け、**t1 の受入条件は C2 だけ**であることを表で明示した

## [Warning] 型安全性の記述が不足 (観点 7)
- 判断: 対応する。ただし前提を 1 つ訂正する
- 根拠: 訂正点 — 本リポジトリの `phpstan.neon` の `paths` は `app` / `config` / `database` /
  `routes` の 4 つだけで、**`tests/` と `scripts/` は解析対象に入っていない** (実測)。
  したがって「PHPStan level 10 を通す」ことが本設計の品質保証にはならない。
  解析されない場所だからこそ境界の検証をコードで書く必要がある、という形で受けた
- 対応内容: §型と検査の境界 を新設し、(1) 解析範囲の事実、(2) 外部入力の境界 4 つを
  空集合へ潰さず例外にすること、(3) 不変 DTO と検証項目 (キー集合の完全一致 / schema_version /
  role の値域 / 40 桁 hex / 64 桁 hex / repo-relative / キー昇順 / 重複の不在 /
  `JSON_THROW_ON_ERROR`)、(4) 突合結果を種別ごとに分けた型で返すこと (共通規約 (d)) を明記

## [Suggestion] 突合結果を missingRegistrations / staleRegistrations 等に型で分ける
- 判断: 対応する
- 対応内容: §型と検査の境界 に「未登録の食い違い / 掃除漏れ / 一致へ戻った債務 / 二重宣言を
  種別ごとに分けた型で返す」と明記

## [Suggestion] テストファーストの明文化
- 判断: 対応する
- 対応内容: §型と検査の境界 の末尾に、負例を先に書いて赤を確認する手順を明記

## [Suggestion] 使命への寄与 / SharedPathRules を移植しない判断
- 判断: 対応不要 (肯定的評価)
