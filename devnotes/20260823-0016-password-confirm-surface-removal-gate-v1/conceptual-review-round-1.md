全体判定: **CHANGES_REQUESTED**

使命への整合性は高く、SSO-only 利用者を詰ませる step-up 機構の再流入防止は North Star に直接資する。一方で、現設計のままでは「正典 v1 の全要素を満たす」「implemented (v1) にできる」という結論は早いです。

1. 使命との整合性

[Suggestion] A の password-confirm 再流入は、現場作業者のログイン不能・撮影不能に直結するため、優先度は妥当です。B の OCR フラグも、常時有効という製品判断を戻さない目的が明確なら同じ枠に載せられます。

2. 禁止事項・型安全性

[Warning] `config('manual.ocr_analysis_enabled') === null` で「未定義」を判定すると、将来キーが `null` 値で復活しても通ります。設定値の判定ではなく、設定木にキーが存在しないことを検証してください。

修正案: `config('manual')` を配列として取得し、`Arr::has($manualConfig, 'ocr_analysis_enabled')` が false であることを固定する。配列でない場合も fail-closed にする。

[Suggestion] アプリコードを変更しないテスト追加だけなので、DTO / JsonResource や `response()->json()` 禁止には抵触しません。PHPStan level 10 にも、走査結果・設定木・Route 型を曖昧な `mixed` のまま扱わない実装であれば適合可能です。

3. 実現可能性

[Warning] `fortify.features` と `fortify-options` から `confirmPassword` キーを「生成して列挙する」仕様が曖昧です。Fortify の機能値、ネストした package 設定、PHP の配列キー／値のどれを探索対象にするかで結果が変わり、空の母集団が全件 false として通る危険があります。

修正案: 対象設定木、探索するキー・値の位置、見つかるべき最小件数、`false` と見なす許容値を明文化してください。依存パッケージ更新による新規キー検出を狙うなら、「探索母集団が最低 1 件あり、検出した全件が厳密に `false`」を要求します。

[Warning] A の「middleware 登録の形」の字句定義が不足しています。PHP 配列、設定配列、文字列 middleware、クラス middleware、YAML、将来の書式のどれを検出対象にするかが不明なため、正典の fail-closed 要件を満たしたとは言えません。

修正案: 違反とする構文を有限に宣言し、それ以外で production surface に `password.confirm` が現れた場合は、少なくとも未分類として失敗させるか、保証範囲をその構文に限定した gate 名・docblock に改めてください。正例は各対応構文を含めてください。

4. 期待効果

[Warning] 「CI 設定と運用スクリプトを走査するので、CI 全滅型の事故を予防できる」という主張は、A には合理的ですが、B の探索語が実際に CI／scripts へ流入し得ることは別途確認が必要です。また A の本番面では形を許すため、未知の再有効化形を完全には防げません。

修正案: 効果は「既知の再有効化形と、`.github/`・`scripts/` における token 再流入を防ぐ」と限定して記述し、未知構文は fail-closed 方針で扱える範囲まで拡張してから強い効果を主張してください。

5. リスク

[Warning] 根ごとのファイル数の「床値」は、内容とは無関係なディレクトリ整理・言語ファイル削除で gate を壊し、保守コストになります。空振り防止に必要なのは通常「根が存在し、対象ファイルの母集団が非空であること」であり、固定数値までは正典が要求していません。

修正案: 各根の存在確認と対象拡張子を含む追跡対象ファイルの非空確認を基本にしてください。数値の完全一致を置くなら、撤去防止の不変条件として必要な理由を明記してください。

[Suggestion] `git ls-files` による追跡ファイル限定は、AGENTS.md の走査器規約と整合します。ただし自己検証 fixture は production roots の外にあるため、通常の対象列挙とは別に、fixture 内容を直接 scanner に渡す経路を設ける必要があります。

6. スコープ

[Warning] B を追加する判断は妥当ですが、A と B の両方について、正典 (1) の非該当項目を完全に宣言していません。A では route 名・HTTP 404 だけでなく、メソッド×URI、クラス、テーブルについても「撤去対象が機構であり、該当する固有 surface がない」ことを理由付きで宣言すべきです。B も route／HTTP／クラス／テーブルに該当しない理由を明示すべきです。

修正案: 撤去物ごとに、実行時層の各観測軸を「検証する」または「該当なし（理由）」で埋めた対応表を設計に追加してください。

[Suggestion] 2 件だけに対して台帳駆動の汎用フレームワークを作らない判断は適切です。共有するのは走査根列挙と、必要最小限の字句 scanner に留めるべきです。

7. 正典 v1 適合性

| 正典要素 | 設計上の対応 | 判定 |
|---|---|---|
| (1) 実行時の不在 | A: middleware 不在・設定値、B: config key 不在 | **要修正** |
| (2) 静的字句走査・許可一覧なし | A: 形による許可、B: 0 件固定 | **概ね適合、形の定義が必要** |
| (3) 正例・負例の自己検証 | A scanner fixture を共有 | **要修正** |
| (4) 消しすぎない確認 | A: recent-auth、生存。B: 既存 T242 を参照 | **概ね適合** |
| (5) `.github/` と `scripts/` | 共通走査根に含める | **適合見込み** |
| 母集団生成・既定拒否 | `git ls-files`、根の存在・非空検査 | **適合見込み** |

[Critical] 自己検証が OCR の 3 語（設定キー、env 名、Inertia prop 名）を検出できることを保証していません。「同じ scanner を使う」だけでは、OCR 用の語境界・大文字小文字・記号・複数語の扱いが正しい証明になりません。

修正案: 共通 scanner の自己検証をパラメータ化し、A と B の各検索語について正例・負例を持たせてください。最低限、B は完全一致、接頭辞、接尾辞、否定形、複数ファイル・複数拡張子の検出を確認します。

[Critical] A の「該当なし」宣言が不完全です。正典の実行時不在の観測軸を黙って省略しているため、v1 完全適合の主張は成立しません。

修正案: A/B ごとの観測軸対応表を追加し、route 名、メソッド×URI、クラス、テーブル、HTTP 404・副作用について、検査または該当なし理由を明記してください。その上で、A は middleware 不在・再有効化設定不在・recent-auth 生存という機構に対応した実行時保証であることを宣言してください。

上記を直せば、目的・範囲・Laravel/Svelte 上の実現性はいずれも妥当で、v1 追従として承認可能な設計になります。
