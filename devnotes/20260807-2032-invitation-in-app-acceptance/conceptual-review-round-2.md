全体判定: **CHANGES_REQUESTED**

Round 1 の型表記上の矛盾は解消されています。ただし、`joinOrganization(): bool` への変更と既存呼び出し元の関係に、新しい重大な不整合があります。

### 1. 使命との整合性

[Suggestion] 使命との整合性は維持されています。

PWA 内で招待の発見から受諾まで完結させることは、現場作業者を実作業へ到達させる前提整備として妥当です。`project_role` 撤去も確定済み裁定に沿っています。

### 2. 禁止事項違反

[Warning] 操作系 POST の成功・失敗応答が明記されていません。

`POST invitations.accept-in-app` が禁止事項 7 に従うことを設計上固定する必要があります。

修正提案:

- 成功時は `back()->with('success', ...)` など、確定した遷移を明記する。
- `redirect()->intended()` は使用しない。
- 解決不能時だけ一律 404 とし、業務成功時の flash 契約を Feature テストに登録する。
- 受諾ボタンを事前条件で `disabled` にしないことも UI 契約に含める。

### 3. 実現可能性

[Critical] `joinOrganization(): bool` を既存経路が無視してよい、という整理は成立していません。

本文では次の二点が同時に主張されています。

- `false` は「ロック下で受諾不能だった」という意味を持つ。
- 既存の `acceptInvitation` / `acceptInvitationIfValid` は戻り値を無視するため互換。

戻り値を無視すると、競合で `false` になった既存 token 経路が成功画面や成功 flash を返す可能性があります。PHP の呼び出し互換性はあっても、業務上の互換性は保証されません。

修正提案:

- 既存公開メソッドも `joinOrganization()` の `false` を必ず処理する。
- token 経路の既存失敗契約に合わせて、invalid 画面、404、または既存ドメイン結果へ変換する。
- 全呼び出し元が結果を消費することを Architecture テストで固定する。
- あるいは `joinOrganization()` の戻り値変更をやめ、受諾可否を表す型付き結果を上位メソッドだけで扱う。

「戻り値を無視するため互換」という記述は削除が必要です。

[Warning] `acceptPendingInvitation()` の例外契約がまだ言葉として矛盾しています。

「例外を投げず `?Organization` を返す」と「インフラ障害を404に化けさせない」は両立しません。後者を採るなら、インフラ例外は伝播します。

修正提案:

> 業務上の受諾不能は例外にせず `null` を返す。DB・インフラ・プログラム不整合による例外は捕捉せず伝播させる。

と限定してください。

[Warning] ロック下再解決の説明が、取消処理とのロック契約まで固定できていません。

ユーザー行と組織行をロックしても、取消経路が同じロック規約を通らなければ、再解決後から招待行ロック取得前まで取消可能です。最終的に `joinOrganization()` が招待行ロック後に全条件を再評価するなら安全ですが、その条件が現在の文章では曖昧です。

修正提案:

- `joinOrganization()` が招待行を `lockForUpdate()` で取得した後、未受諾・未取消・期限内を再評価すると明記する。
- 組織の非削除状態も、最終判定で保証する主体を明記する。
- 取消経路とのロック順序を `MembershipWriteLockInventoryTest` の対象に含める。
- 「同じ行の再ロックは no-op」ではなく、デッドロック防止に必要な全経路の順序一致を保証する。

### 4. 期待効果の妥当性

[Warning] 背景 (2) に、修正前の過大表現が残っています。

「この3つに強い第2の入口」とありますが、列挙された3つには期限切れが含まれます。新経路は期限切れ招待を受諾できません。

修正提案:

> メール転送による第三者受諾と、本人がメールを見つけられない問題に強い第2の入口

などに限定し、期限切れについては「状態を明示して再招待判断へ導く」と分離してください。

### 5. リスク

[Warning] 通知 flash の旧表現が制約節に残っています。

対応マトリクスと期待効果では集合表現へ修正されていますが、「通知 payload に持たせない」節の末尾には次が残っています。

> 「この招待は現在有効ではありません」の flash

通知と招待を対応付けない設計では断定できません。

修正提案:

> 件数が0件なら「現在有効な招待はありません」と表示する

に統一してください。

[Warning] throttle の方式が未確定です。

現行規約では inline throttle は同一 actor の他 route と bucket を共有します。単に「throttle を貼る」だけでは、再認証など既存操作を巻き添えにする可能性があります。

修正提案:

- 同性質の既存 endpoint と同じ named limiter を使うか、新しい named limiter を設けるかを決める。
- limiter key、既存閾値の再利用、他 route と bucket を共有しないことを設計に記載する。
- 429 と正常受諾の Feature テストを追加する。

### 6. スコープの適切さ

[Suggestion] `project_role` 撤去を同一作業単位に含める判断は妥当です。

共有ファイルの重複改修を避けつつ、Default Project 全体の撤去は別作業に残しており、境界は明確です。

### 7. 型安全性

[Suggestion] Round 1 の DTO 指摘は解消されています。

`final readonly PendingInvitationForUserDto` で開示項目を4つに限定し、管理者視点 DTO と分離する設計は PHPStan level 10 と整合します。

ただし、`expiresAt` を文字列化する責務は DTO factory など一箇所へ固定し、nullable でないことをモデル条件と型の両方で保証してください。また、`pendingInvitationsQuery()` の戻り値は `Builder<OrganizationInvitation>|null` のジェネリック型を明記するのが適切です。

結論として、Round 1 の Criticalだった「戻り値型の記述矛盾」は解消済みです。一方で、`bool` を既存呼び出し元が無視するという新しい振る舞い上の Critical が生じています。ここを修正し、残存している期限切れ・flash表現を統一すれば、概念設計は承認可能な状態になります。
