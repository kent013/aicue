## [Warning] 施策 0: 「36 契約」と表の行数 (41) が一致しない
- 判断: **対応する**
- 対応内容: 補助番号 (`5b` / `12b` / `23b` / `32b`) を廃して**通し番号を 1〜41 に振り直した**。
  併せて「1 行に複数ケースを含む契約はケースごとに分けるので**実装時のメソッド数はこれ以上になる**。
  **実装完了報告で実件数を確定して書く**」と明記し、ここでは本数を主張しない形にした。

## [Warning] 施策 0: 原子性の障害注入が `os.replace` だけ
- 判断: **対応する**
- 対応内容: **temp 作成後・置換前**に失敗する経路 (`fh.write` / `os.chmod` の例外注入) を足した。
  これで「入力検証で落ちる / temp 作成後に落ちる / 置換時に落ちる」の 3 段階を覆う。
  一時ファイルが残らないことの確認も 3 経路すべてに掛ける。

## [Warning] hash 正規化方式の記述が設計内で食い違う (共通契約と `check_migration` の説明)
- 判断: **対応する**
- 根拠: 指摘のとおり `separators` の有無が食い違っており、
  実装者が後者を写すと期待 hash と一致しない。同じ式を 2 か所に書いたのが原因である。
- 対応内容: **単一関数 `canonical_machine_projection()` を正本**として定義し、
  生成器・テスト・移行台帳の pin がすべてこの戻り値で突き合わせる形にした。
  `check_migration` の説明からは式を消し、関数を指すだけにした。

## [Warning] 後続タスクの内容が append-only の契約と矛盾する
- 判断: **対応する**
- 根拠: 指摘のとおり。append-only なら既存 A-001〜A-003 の機械射影は変わらないので、
  hash や移行鍵を更新する理由が無い。移行鍵を後継へ動かすと
  「旧 spec-ledger.md のブロックが A-001 へ移った」という provenance まで書き換わってしまう。
- 対応内容: 後続タスクの内容を書き直した —
  **A-001 は機械項目・`context`・移行鍵・hash の pin をいずれも変更しない**。
  新登録を 1 行 append して A-001 を supersede し、修正済み `watch_globs` と `context` を
  新登録に持たせる。**新登録は移行時点に存在しないので pin 対象へ加えない**
  (pin に無い id は検査対象外という既定のとおり)。provenance も書き換えない。

## [Warning] TODO 登録を完了条件にしたのに施策一覧・波及変更に無く、末尾の文言も「候補」のまま
- 判断: **対応する**
- 対応内容: **施策 8「後続 TODO の登録 (`app-todo-add` 経由)」**を施策一覧へ足し、
  変更ファイルに `docs/TODO.md` を明記した。波及変更にも 1 行足した。
  「候補として申し送る」を「確定内容で必ず登録する」へ統一し、
  **採番された ID を実装完了報告に書く**ことを条件に加えた。実装順も 8 を末尾に置いた。
