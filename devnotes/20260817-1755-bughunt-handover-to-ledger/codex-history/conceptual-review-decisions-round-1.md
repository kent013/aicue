# 対応マトリクス: conceptual-review Round 1

## [Critical] 「registry に載ったのに文書に無い」は現設計では保証されない (観点 4)
- 判断: **対応する**
- 根拠: 指摘のとおり。`context` を任意にした時点で、参照実装のように「context を持つ登録だけ描く」と
  無 context の登録は文書に現れない。本設計が挙げた実測 (A-002 / A-003 が文書に無い) が
  そのまま再現する = 直そうとしている欠陥を新しい形で温存することになる。
- 対応内容: 概念設計に**生成物の完全性契約**を足した。
  (a) すべての `adjudication_id` を必ず生成物へ掲載する。
  (b) `context` がある登録は経緯つき、無い登録は機械項目だけの簡潔な項目として出す
      (「経緯は未記入」と明示する。黙って消さない)。
  (c) supersede 関係は掲載側に明示する。
  (d) テストで「全 `adjudication_id` が生成物に現れる」ことを固定する。

## [Critical] fail-closed 契約と「照合器は context を読まない」の両立条件が未定義 (観点 7)
- 判断: **対応する**
- 根拠: 本設計は「照合器に入れない」しか書いておらず、**では誰が context の壊れを見るのか**を
  書いていなかった。無検証だと生成物が静かに壊れる。
- 対応内容: 検証責務の二層分離を概念設計へ明記した。
  照合器 = 抑制判断に要る機械項目だけを fail-closed で検証 /
  生成器 = `context`・移行台帳・断片・完全性を fail-closed で検証し、失敗時は出力を 1 バイトも更新しない。
  併せて「context の不備は照合器の判定に影響しないが生成器は落ちる」をテストで固定すると宣言した。

## [Warning] `context` の検証契約が未定義 (空 object / 型不正 / 未知キー / 欠落) (観点 3)
- 判断: **対応する**
- 対応内容: `context` の欄を許可キーの閉じた集合とし、未知キーは拒否 (deny-by-default)、
  各値の型と非空を検証する、と概念設計に書いた。`context` 不在は許可、
  **存在して壊れているものは生成失敗**という非対称を明示した。

## [Warning] `context.spec_basis` の最低限の構造検査 (観点 7)
- 判断: **対応する** (実在検査はしない方針は維持)
- 対応内容: 「非空文字列の非空配列であることだけを生成器が検証する。パスの実在は検証しない」と明記した。
  実在検査をテスト側に置く既存方針は変えない。

## [Warning] 移行台帳の保証範囲の主張が過大 (観点 5)

- 根拠: 移行元を消したあとの台帳は「移行時に決めた断片と下限が保たれること」しか見られない。
  「全ブロックが移ったことを将来にわたり証明する」は言い過ぎである。
- 対応内容: 保証範囲を正確化し、**移行の commit ではもう一段** —
  旧 `spec-ledger.md` の F-1-02 の本文と移行後の `context` / 生成結果を人が突合する — を
  手順として入れた (以後は pin と断片照合で監視)。
