## 全体判定: CHANGES_REQUESTED

方向性は妥当です。二重正本を廃し、`adjudications.jsonl` を唯一の入力として `spec-ledger.md` を生成する設計は、既に生じているドリフトを構造的に防ぐため、家系の裁定・参照実装・AI-CUE の品質維持に整合します。

ただし、「registry に載ったのに文書に無い」を確実に防ぐための完全性契約と、任意 `context` の検証契約が概念設計として不足しています。

### 1. 使命との整合性

[Suggestion] 本変更は North Star への直接機能ではなく、bug-hunt の探索能力を維持する基盤整備です。その位置付けは適切です。期待効果の表現は「現場作業者が触る画面」に限定せず、SOP 起点のシナリオ作成・撮影・認可を含む全ユーザー導線の品質維持、とすると使命との接続がより正確になります。

### 2. 禁止事項違反

[Suggestion] 設計上、禁止事項への抵触は見当たりません。Python／Markdown／JSON の台帳資産のみを対象にし、PHP・TypeScript・LLM 実行経路・UI を変更しない範囲は明確です。

[Suggestion] テストファーストについては、「先に失敗するテストを確認する」と明記されており適切です。詳細設計では、各失敗ケースと対応テストを対応付けてください。

### 3. 実現可能性

[Warning] `context` を照合器の入力から外す判断自体は妥当ですが、生成器側でどこまで JSON スキーマ相当の検証をするかが未定義です。任意項目である以上、`context: {}`、型不正、空文字、空配列、未知キー、`narrative` だけ欠落、といった不完全データへの挙動が曖昧です。

修正提案: 生成器の契約として、`context` が存在する場合は許可キー、各値の型、必須項目、空白のみ不可、配列要素の型を fail-closed で検証すると明記してください。`context` 不在は許可しても、存在して壊れている登録は生成失敗にしてください。

[Suggestion] 原子的書き込みと `--check` の byte 比較は、既存の生成物と一貫し、実現可能です。差分が出た場合に再生成コマンドも表示すると運用ミスを減らせます。

### 4. 期待効果の妥当性

[Critical] 「以後、registry に載ったのに文書に無いは起こり得なくなる」という主張は、現状の設計では保証されません。`context` は任意であり、施策では A-002 ではなく A-003 にのみ `context` を追加します。生成器が `context` のある登録だけを表示するなら、A-002 は引き続き registry 上にはあっても文書に出ない可能性があります。

修正提案: 生成物の完全性を明文化してください。例えば、全 `adjudication_id` を必ず生成物へ掲載し、`context` がない登録も機械項目だけの簡潔な項目として出力する契約にします。supersede 済みの A-002 を本文で省略する必要があるなら、A-003 側に「A-002 を supersede」と明示し、テストで全登録 ID が「個別掲載または後継への明示的参照」のいずれかを満たすことを固定してください。

[Warning] 「手作業を 2 か所から 1 か所へ減らす」は、`context` の記入と生成確認を含めれば完全にゼロコストではありません。ただし、正本更新を一箇所に収束する効果は合理的です。

修正提案: 効果は「二重更新を廃止し、生成チェックで同期を機械化する」と表現してください。

### 5. リスク

[Warning] 移行台帳は移行後の内容の保持には有効ですが、削除済みの移行元そのものと再照合することはできません。したがって「移行元の全ブロックが移ったこと」を将来にわたって直接証明するものではなく、移行時に定めた断片・最小文字数が保持されることを検証する仕組みです。

修正提案: 保証範囲をこのように正確化し、移行コミット時のテストで旧 `spec-ledger.md` の F-1-02 内容と `context`／生成結果を突合するテストを一度実施してください。以後は migration JSON の pin と断片照合で保持を監視する設計でよいです。

[Warning] CI で Python テストが動かないため、生成物ドリフトの検出は人手依存のままです。これは既存の後退ではありませんが、生成物化によって `--check` の重要度が上がります。

修正提案: 今回のスコープ外として維持してよいですが、README の運用手順に `python3 -m unittest` と生成器の `--check` を明記し、「CI 保証ではない」ことも記載してください。

### 6. スコープの適切さ

[Suggestion] `spec-notes.jsonl`、`watch_globs` 実在検査、照合器の gate、CI 統合を外した判断は適切です。とくに `watch_globs` の実在検査を抑制機構へ混ぜない判断は、fail-closed の全面停止を避ける点で健全です。

[Suggestion] 読み手への導線追加を外すのも裁定への追従として妥当です。ただし、生成物が実行者向けの「使い方」を失うため、`spec-ledger.md` の役割を「人間向け運用手順」から「登録の可視化」に縮小することを README と生成ヘッダで明確にしてください。

### 7. 型安全性・機構の健全性

[Critical] 「`adjudications.jsonl` は一行でも不備があれば登録全体を無効化する」という fail-closed 契約と、「`context` は照合器が読まない」が両立する条件が未定義です。現設計のままでは、抑制判断に不要な散文の不備で照合器まで停止させる必要はない一方、生成器は壊れた `context` を見落として不完全な文書を出す危険があります。

修正提案: 検証責務を二層に分離して明記してください。

- `validate_findings.py`: 既存どおり、抑制判断に必要な機械項目だけを fail-closed で検証する。
- `render_spec_ledger.py`: 文書生成に必要な `context`、移行台帳、断片、完全性を fail-closed で検証し、失敗時は出力を更新しない。

さらに、テストで「`context` の不備は照合器の判定入力に影響しないが、生成器は失敗する」ことを固定してください。

[Warning] `context.spec_basis` にパス・行番号を持たせる場合、パスの実在検査をしない方針は合理的です。ただし、文字列としての最低限の構造まで無検証にすると、表示不能な根拠や空の根拠が蓄積します。

修正提案: 実在確認は行わず、非空文字列配列であることだけ生成器側で検証してください。これは通常のリファクタでの全面停止を避けつつ、壊れた表示データを防げます。
