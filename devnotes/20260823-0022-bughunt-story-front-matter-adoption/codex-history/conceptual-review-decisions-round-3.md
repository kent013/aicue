# 対応マトリクス: conceptual-review Round 3

## [Critical] 「route → 割当カード集合の一致だけで safe / 非 safe の誤振り分けも捕まえる」は成立しない

- 判断: **対応する**
- 根拠: 指摘のとおり。同じ route が同じカードに載ったまま `covers_screens` と `covers_operations` の
  間で移動しても `route → カード集合` は一致してしまう。こちらの主張が過大だった。
  対象外 route が「双方とも省略されたので一致した」になる余地の指摘も正しい。
- 対応内容: 検算を次の形へ直した。
  - 比較する関係を **画面側 / 操作側の 2 本**に分ける。
  - 期待の欄は**変換前の HTTP method から導く** (前付け側の値を根拠にしない。
    根拠にすると自分で自分を検算することになる)。
  - **母集合を対象内 route の全数で固定**し、対象外 (`kubun` = 外) の route は
    **両側とも空集合**であることを明示的に assert する。

## [Warning] 照合器が不正形式を寛容に正規化してはいけない

- 判断: **対応する**
- 根拠: 妥当。`str.split()` は前後空白も連続空白も黙って吸収するので、それだけで済ませると
  書式違反を見逃す。「値域が閉じているから食い違わない」という前回の根拠は、
  読み取り側が値域を検証して初めて成立する。
- 対応内容: 読み取り側は**まずセル全体を `^(S[1-9][0-9]*( S[1-9][0-9]*)*|-)$` で完全一致検証**し、
  一致しないセルを明確に失敗させる、と確定した。分解はその後に行う。
  テストケースを表にし、7 ケースそれぞれの期待 (索引される / 失敗する) を明記した。
