- 全体判定: **CHANGES_REQUESTED**

### 1. 使命との整合性

- [Warning] 解析結果の受理契約を厳格化し、失敗理由を観測可能にすることは、標準化された動画シナリオを安定して生成するという使命に整合します。ただし「後続の囲み差し込み経路を閉じる」という守りの効果はやや過大です。現行実装も複数ブロックを連結した結果を JSON として読もうとして失敗するため、任意の後続ブロックを採用してしまう挙動は提示されたコードからは確認できません。

  修正提案: 期待効果は「曖昧な復号を決定論的に拒否し、失敗理由を観測可能にする」と表現し、現行から新たに防げる具体的な受理ケースをテストで示してください。

### 2. 禁止事項違反

- [Suggestion] `invalid_json` と正規表現ベースの旧経路を同一変更で削除し、prompt 文言を YAML 側で変更する方針は、後方互換の並走・prompt のコード直書き禁止に適合しています。

- [Warning] `LlmOutputInvalidException` は内部 detail を `RuntimeException` の message に含めています。`userMessage()` が分離されていても、例外 message をそのまま report・ログ・画面表示する経路があれば i8/i9 の意図を損ねます。今回「本文非漏洩」を新規テストするなら、例外 message とログコンテキストの双方を対象にすべきです。

  修正提案: 利用者へ返す文字列と内部診断を明示的に別プロパティに分離し、例外 message を利用者向け固定文言にする、または例外 message が外部へ出ないことを呼び出し経路まで含めて固定してください。少なくとも応答本文・SOP本文が `getMessage()`、report context、ジョブ失敗通知に含まれないテストを追加してください。

### 3. 実現可能性

- [Critical] 構造走査の契約がまだ実装可能な水準まで一意に定義されていません。たとえば以下の分類・受理可否が曖昧です。

  - 開きの印の正確な文法（言語札の許容文字、`json5`、空白、行頭条件）
  - JSON 値の終端から閉じの印までに許す文字（空白のみか、説明文も許すか）
  - 値の中途終了と、閉じ印以前の余剰トークンの区別
  - 開き印、閉じ印、追加の囲みが同時に壊れている場合の reason の優先順位
  - 囲みの外側にある ````` の文字列をすべて `fence_multiple` とするのか、行としての囲み印だけを数えるのか

  このままでは実装者ごとに `syntax_broken`、`closing_fence_absent`、`fence_multiple` の選択が変わり、観測値も不安定になります。

  修正提案: 受理文法と失敗理由の優先順位を設計に明記してください。最低限、`opening → JSON value → whitespace-only → closing` の各区間を定義し、複合不正入力についても「どの reason を返すか」を表で固定してください。各境界ケースを単体テストへ追加してください。

- [Warning] Laravel/PHP で JSON の文字列・エスケープ・入れ子を追う構造走査自体は実現可能です。しかし自前 JSON パーサーへ膨らませると、`json_decode()` と差異を作るリスクがあります。

  修正提案: 構造走査の責務を「最初の JSON 値の終端候補を特定する」ことに限定し、JSON としての最終妥当性は `JSON_THROW_ON_ERROR` を付けた `json_decode()` に委譲してください。走査器の保証範囲・未対応構文・fail-closed 方針を docblock に記載してください。

### 4. 期待効果の妥当性

- [Warning] `value_incomplete_inferred` を切り詰めの推定として独立観測する効果は合理的です。一方で、これだけで `max_tokens` 不足を確定することはできません。ネットワーク断、提供元の生成停止、モデル側不具合も同じ観測になり得ます。

  修正提案: 運用上の記述を「max_tokens 不足の疑いを分離する」とし、`finish_reason` が未導入である以上、トークン予算変更の判断には失敗率・応答長・提供元情報など追加の観測が必要であることを明記してください。

- [Suggestion] reason 値に `inferred` を含める判断は、推定を断定として扱わない i6 に合っています。reason を観測カテゴリへ自動反映する既存設計とも整合します。

### 5. リスク

- [Critical] 全プロンプトを「囲み必須」へ一斉に切り替えるため、モデルまたは provider が素の JSON を返す実運用の割合次第では、従来成功していた解析が最大 3 回の試行後に失敗します。再試行があることは緩和策ですが、リリース直後の回帰を防ぐ根拠にはなりません。

  修正提案: リリース前に、対象 4 prompt の現行モデルで囲み付き指示への準拠率を評価してください。少なくとも feature/integration テストでは実 provider を使わず、canned 応答で「囲み必須」を固定します。リリース後は `fence_absent` と `fence_multiple` の率を既知の失敗カテゴリと並べて監視し、急増時のロールバックまたは prompt 修正手順を文書化してください。

- [Warning] `fence_multiple` を一律 retryable とする設計は、再サンプリングで改善し得るため妥当です。ただし、プロンプトや SOP の内容が恒常的に追加ブロックを誘発する場合、3 回分の LLM コストと待ち時間を消費します。

  修正提案: 区分別の retry 可否は分けないまま維持し、reason 別の試行回数・最終失敗数を観測できることを確認してください。これにより、後で prompt の問題と単発のモデル揺らぎを区別できます。

### 6. スコープの適切さ

- [Warning] i1 の gate 方針は必要ですが、提示範囲では迂回防止が不十分です。`app/Prompts/*.php` と `executeSync()` のみを母集団にすると、将来のサブディレクトリ、別の実行 API、非同期実行、または response を別サービスへ渡す経路を黙って見逃す可能性があります。また、指定ディレクトリ外の `json_decode()` が LLM 応答を読むことも検出できません。

  修正提案: prompt factory は再帰的に全数列挙し、LLM 実行は `GuardedPrompt` の全実行入口を完全修飾名で検出してください。さらに、応答テキストの型・変数フローを完全に追えないなら、少なくとも LLM 実行結果を受け取るクラス群を deny-by-default inventory にし、母集団の非空・走査根の存在・負例・未解決構文の fail-closed を gate に含めてください。

- [Suggestion] structured output 経路と診断 DTO をスコープ外に置くことは適切です。未使用の緩い入口も作らないため、現時点での公開面は最小です。

### 7. 型安全性

- [Warning] `array<array-key, mixed>` は復号直後の表現として許容できますが、`json_decode()` の失敗判定を `is_array()` だけに依存すると、JSON 例外・構造走査例外・トップレベル判定の責務分離が曖昧になります。PHPStan level 10 で例外 reason と戻り値契約を明確に保つ必要があります。

  修正提案: 復号内部では `JSON_THROW_ON_ERROR` を使用し、`JsonException` を `syntax_broken` または定義済みの優先 reason へ変換してください。公開戻り値は `array<array-key, mixed>` を維持し、DTO 側の narrow と `schemaViolation()` の path が引き続き観測専用であることをテストしてください。

- [Suggestion] enum の旧 case を削除し、新しい reason を型として一元化する方針は PHPStan と観測カテゴリの双方に適しています。enum を `match` している箇所があれば、網羅性テストまたは PHPStan により新 case 漏れが検出される状態にしてください。
