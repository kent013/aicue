# 対応マトリクス: design-review Round 1

## [Critical] 施策 7: 緩い公開入口を追加できない pin が検査に無い (`decodeLenient` を足しても緑)
- 判断: 対応する
- 根拠: 指摘が正しい。`DECODE_POINT_PATH` は検査 5 からファイル全体が除外されるので、
  緩い入口を後から足しても赤くならない。概念設計が「公開面をちょうど 1 つに機械で pin」と
  約束していたのに、詳細設計の検査群から落ちていた。
- 対応内容: **検査 7 (復号点の公開面の pin)** を追加した。Reflection で
  public メソッドの集合が `{decode, schemaViolation}` と完全一致すること、`decode` が
  `public static` / 必須 `string` 1 つ / 戻り値 `array` であること、`schemaViolation` の
  戻り値型を pin する。検出力は「公開面を 1 つ増やした fixture クラス」で裏取りする
  (負例 10)。概念設計の検査一覧も 8 件へ更新した。

## [Critical] 施策 7: 登録済み receiver が実際に `LlmJson::decode()` を呼ぶことを検査していない
- 判断: 対応する
- 根拠: 指摘が正しい。検査 3 は「応答が受け取り関数の引数に入る」ところまでで、
  その先で別のデコーダに差し替えても緑のままだった (i1 の主張が空になる)。
- 対応内容: **検査 8 (受け取り関数が復号点に直結していること)** を追加した。
  受け取り関数のスコープ内で (1) `App\Support\Manual\LlmJson::decode` の完全修飾で解決できる
  静的呼び出しがちょうど 1 件、(2) 第 1 引数の変数が本体でちょうど 1 回だけ現れ、
  (3) その出現がその呼び出しの直接引数であること、を検査する。
  実体の手順 (`PhpReferenceScanner` の `class` / `callable` スコープの利用・
  宣言部からの引数名の読み取り・本体の brace 追跡) を詳細設計に書いた。
  負例 9 (decode を消す / 別変数へ代入 / 2 回使う) で裏取りする。

## [Critical] 施策 7: `json_decode` 検出が完全修飾と関数 alias を見逃す
- 判断: 対応する
- 根拠: 指摘が正しい。`\json_decode(` と `use function json_decode as decodeJson;` は
  `T_STRING` のテキスト一致では拾えない。既存の負例 3 形 (接頭・接尾・メソッド呼び出し) は
  誤検出防止の裏取りであって、回避経路の検出力の証明ではない。
- 対応内容: 判定を**関数名の完全修飾解決**に変え、素の呼び出し /
  `T_NAME_FULLY_QUALIFIED` / `use function` の別名 / group use の別名の 4 形を違反にした。
  加えて**文字列リテラルの完全一致**も違反にして `call_user_func('json_decode', …)` /
  `array_map('json_decode', …)` を塞いだ。**動的な関数呼び出しは保証範囲外**として
  docblock に明記する方針を書いた。負例 7 で 4 形すべてを裏取りする。

## [Warning] 施策 7: 受け手解決アルゴリズムが不十分 (入れ子・配列・名前付き引数・クロージャ)
- 判断: 対応する
- 根拠: 「直前探索」では `X::make(foo(1), ['a' => 1], named: $c)` から `X` に戻れない。
- 対応内容: **後方への括弧の対応走査**を明文化した (5 段。正規化済みトークン列なので
  コメント・文字列中の括弧は現れない)。どの段でも条件を満たさなければ `unresolved` として
  gate を失敗させる。正例 (入れ子・配列・名前付き引数・クロージャ・複数行) と
  未解決例 (`$prompt->executeSync()` / `static::make()` / 対応の取れない括弧) を
  負例 8 として置いた。
