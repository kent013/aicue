# 対応マトリクス: conceptual-review Round 1

## [Critical] 構造走査の契約が実装可能な水準まで一意でない (受理文法 / reason の優先順位)
- 判断: 対応する
- 根拠: 指摘のとおり。囲みの印の文法・値の終端から閉じまでに許す文字・複合不正時の
  reason 優先順位が決まっていないと、観測値 (`llm_output_invalid_*`) の意味が実装者ごとに
  ぶれる。正典 i2 の「決定論」は「同じ応答なら常に同じブロック」だけでなく
  「同じ応答なら常に同じ区分」まで含めて初めて観測に使える。
- 対応内容: 概念設計に **§受理文法 (BNF 相当) と §区分の決定順序 (表)** を新設した。
  - 囲みの印を「行」ではなく「連続 3 個以上の逆引用符の並び」と定義し直した
    (行頭条件を外した。データ中の印を数えないことは**構造の走査で決まった値の区間の外だけを
    数える**ことで担保されるので、行頭条件は保証に寄与せず、`{...}``` ` のような
    同一行の閉じを不当に落とすだけだった)。
  - 開きの印の後の言語札を `[A-Za-z0-9_+.-]*` に固定し、値の開始は「札の後の最初の非空白」と
    定義した (同一行に値が続く形も受理する)。
  - 値の終端から閉じの印までは**空白のみ**を許す。それ以外の非空白が来たら `syntax_broken`。
  - 閉じの印の後は**囲みの印以外の文章を許す** (囲みの印があれば `fence_multiple`)。
    囲みの前の文章も同様に許す。採る値の位置は最初の印だけで決まるので決定論は保たれる。
  - 複合不正は**単一パスの到達順**で決まる (= 表の上から下)。とくに
    「値は完結したが、次に来た印が言語札つき (= 別ブロックの開き)」は
    `closing_fence_absent` ではなく **`fence_multiple`** に倒す (正典 i2 の
    「外にもう 1 つ囲みがあれば受け取らない」が守りの本体なので、そちらを優先する)。
  - 各境界ケースを単体テストの一覧 (受理 4 / 拒否 12) として詳細設計へ持ち込む。

## [Critical] 全依頼文を「囲み必須」へ一斉切替する回帰リスク
- 判断: 対応する (方針は維持し、緩和策を設計に組み込む)
- 根拠: 「再試行があるから大丈夫」は確かに回帰を防ぐ根拠にならない。ただし案 (b)
  (依頼文据え置き + 緩い入口) は正典 i4 が名指しで否定した形 (既定が緩い) を温存するので採らない。
  したがって方針は維持し、**準拠率を出荷前に実測する手順**と**出荷後の観測・巻き戻し手順**を
  設計に含める。
- 対応内容:
  - 出荷前の実測に**既存の `dev:pipeline-smoke`** (実 provider で 3 段を通す通し確認。
    費用が発生するため `BUGHUNT_ORCHESTRATOR=1` の親のみ実行可) を充てる。
    実装完了の条件に「`pipeline-smoke --check` (費用ゼロの preflight) が通ること」と
    「実走はユーザー承認のうえ 1 回行い、3 段すべてが囲みつきで返ることを確認すること」を入れた。
  - 自動テストは実 provider を使わず、canned / fixture を**囲みつきに固定**する
    (囲み無しを渡したら赤くなる = 契約がテストで固定される)。
  - **依頼文と受理契約の食い違いを機械で塞ぐ**: 新設 gate に「復号点を通す分類の依頼文 YAML は
    囲みちょうど 1 つを指示する所定の文を持つ」検査を追加した (依頼文を足したときに
    出力指示を書き忘れると赤くなる)。
  - 出荷後の観測と巻き戻し手順を `docs/architecture.md` の新節に書く
    (`llm_output_invalid_fence_absent` / `_fence_multiple` の率を既存の失敗分類と並べて見る。
    急増時の一手は**依頼文の出力指示の修正**であり、受理契約を緩める並走は作らない)。

## [Warning] 使命の節で「後続ブロックの差し込み経路を閉じる」が過大
- 判断: 対応する
- 根拠: 現行実装は先頭の印と末尾の印を剥がした結果を読むので、差し込まれた後続ブロックが
  **採用される**わけではなく壊れて落ちる。効果の記述として不正確。
- 対応内容: 期待効果を「曖昧な復号を決定論的に拒否し、失敗の理由を観測できるようにする」へ
  書き換えた。差し込みについては「採られる余地が構造として残っている」ではなく
  「**現行は落ち方が `invalid_json` に埋もれて区別できない**」を主張に変えた。
  新たに防げる受理ケースは拒否テストの一覧で示す。

## [Warning] 例外 message に内部 detail が入る (i8/i9 の意図)
- 判断: 対応する
- 根拠: `userMessage()` があっても `getMessage()` を記録・表示へ流す経路があれば漏れる。
  今回 6 区分を足すので、区分ごとの detail に応答本文を混ぜる改変が入る余地を先に塞ぐ。
- 対応内容: **復号点が渡す detail を区分ごとの固定文にする** (応答の断片も
  `json_last_error_msg()` も入れない)。あわせて sentinel 文字列を含む応答を 6 区分すべてに
  流し、`getMessage()` / `userMessage()` / 再試行ログの context / `analysis_jobs.error` の
  どこにも sentinel が現れないことをテストで固定する。

## [Warning] 自前 JSON パーサへ膨らむリスク
- 判断: 対応する
- 根拠: 妥当。走査器と `json_decode()` の判定が食い違うと、どちらが正かが不明になる。
- 対応内容: 走査器の責務を「**最初の JSON 値の終端候補を特定する**」に限定すると明記した
  (括弧の対応と文字列・打ち消しの解釈だけを行い、値の妥当性は判定しない)。
  最終妥当性は `json_decode(..., flags: JSON_THROW_ON_ERROR)` に委譲し、`JsonException` は
  `syntax_broken` へ写す。保証しない構文は docblock に書く。

## [Warning] `value_incomplete_inferred` から max_tokens 不足は断定できない
- 判断: 対応する
- 根拠: 妥当。ネットワーク断・提供元の停止・モデル不具合も同じ観測になる。
- 対応内容: 運用の効果の記述を「max_tokens 不足の**疑いを分離**できる」に弱め、
  提供元の停止理由が未導入である以上、予算変更の判断には追加の観測が要ることを明記した。

## [Warning] 区分別 retry 可否は分けないまま、区分別の試行回数・最終失敗数が観測できること
- 判断: 対応する (確認して明記)
- 根拠: 既存の再試行ログは試行ごとに `failure_category` を出しており、最終失敗ログも
  `observabilityCategoryFor()` で分類を出す。区分別の試行回数と最終失敗数は現行配線で数えられる。
- 対応内容: 概念設計にその事実 (どのログのどのキーで数えられるか) を明記した。

## [Warning] i1 gate の母集団が狭い (サブディレクトリ / 別の実行 API / 応答を別サービスへ渡す経路)
- 判断: 対応する
- 根拠: 妥当。とくに「応答を変数に受けて別クラスへ渡す」形が抜けると、gate の主張が空になる。
- 対応内容: gate の検査を 5 つに増やした。
  1. `app/Prompts/` を**再帰**で全数列挙 (根の不在は fail-fast、母集団の非空を検査)。
  2. `app/` 全体の `->executeSync(` 呼び出し点を全数列挙し、目録に完全一致で載っていること
     (`GuardedPrompt` の公開面は `PromptDefenseWindowGateTest` が `{__construct, executeSync}` に
     pin しているので、メソッド名で拾うと**拾いすぎる方向**にだけ倒れる = fail-closed)。
  3. **応答の流れの構造的封じ**: 「復号点を通す」分類の呼び出し点は、`executeSync()` の呼び出しが
     **登録済みの受け取り関数の引数として**現れなければならない。変数へ束縛する形
     (`$text = ...->executeSync();`) は登録済みの形に一致しないので赤くなる
     = 応答が別サービスへ渡る経路が構造で塞がる (データフロー解析を要しない)。
  4. `App\Support\Llm\GuardedPrompt` を**完全修飾名で解決して**参照するファイルは、
     登録済みの依頼文 factory か登録済みの受け取り側のどちらかであること。
  5. 登録済みの受け取り側のファイル群 + LLM 応答が触る走査根に `json_decode` と
     囲みの印の文字列リテラルが現れないこと (復号点自身だけを名指しで除外)。
  併せて (b) fail-closed の分岐・(c) 負例と正例・母集団の非空・走査根の実在・
  docblock の保証範囲を揃える (AGENTS.md 静的検査の共通規約)。

## [Warning] `is_array()` だけに依存した失敗判定 / 型安全性
- 判断: 対応する
- 根拠: 上の「自前パーサ」への対応と同じ。
- 対応内容: `JSON_THROW_ON_ERROR` + `JsonException` → `syntax_broken`、
  戻り値は `array<array-key, mixed>` 維持、`is_array()` は**多重防御としてだけ**残し
  (到達不能であることを docblock に書く) `top_level_not_container` へ写す。

## [Suggestion] enum を `match` している箇所の網羅性
- 判断: 対応する (確認のみ)
- 根拠: 実測すると `LlmOutputInvalidReason` を `match` している箇所は無い
  (`AnalysisPipeline` は `'llm_output_invalid_'.$reason->value` の連結で、区分を足すと
  語彙が自動で広がる)。網羅性の穴は無い。
- 対応内容: 概念設計にこの実測を明記した。
