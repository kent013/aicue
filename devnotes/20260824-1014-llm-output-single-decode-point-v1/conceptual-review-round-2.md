- 全体判定: **CHANGES_REQUESTED**

Round 1 の「受理文法と区分順序が一意でない」はほぼ解消しています。指定された4入力も一意に判定できます。一方、出荷前の実 provider 実走1回は互換性確認にはなりますが、「準拠率の実測」にはならず、4本すべての prompt を通る保証もありません。このため、回帰リスクに関する Critical はまだ完全には解消していません。

### 1. 使命との整合性

- [Suggestion] 効果を「後続ブロック採用の防止」から「曖昧な復号の決定論的拒否と理由別観測」へ修正したことで、使命への寄与が正確になりました。AI解析の安定性と運用上の改善判断を支える変更として妥当です。

### 2. 禁止事項違反

- [Suggestion] 旧 `invalid_json` と旧正規表現経路を同じ変更で削除し、緩い入口を並走させない方針は規約に適合しています。

- [Suggestion] detail を区分ごとの固定文にし、sentinel が例外、ログ、DBエラーへ漏れないことを固定する対応は、i8/i9を後退させない方法として十分です。

### 3. 実現可能性

- [Warning] §A-2は大幅に明確になりましたが、構造走査中に括弧の種類が対応しない場合の扱いが表にありません。たとえば次の入力です。

  ` ```json {"a":[} ``` `

  「括弧の対応を追う」なら不一致を検出するはずですが、深さだけを数える実装では値終端候補に到達し得ます。最終的には `json_decode()` が落とすとしても、走査を継続するのか、その場で `syntax_broken` にするのかが未定義です。

  修正提案: 表の構造走査部分に「期待する閉じ括弧と異なる `}` / `]` に遭遇したら `syntax_broken`」を追加してください。負例には `{]`、`[}`、余分な閉じ括弧を含めてください。

- [Warning] `OPEN` の言語札と `VALUE` の間に区切りが必須でないため、文字列によって言語札の解釈が変わります。たとえば `` ```null `` は `null` 全体が言語札になり、scalarではなく「値なし」として扱われます。現在の規則でも決定論的ではありますが、`top_level_not_container` の説明と一致しません。

  修正提案: 「札の直後に `{` または `[` が続く形、または札の後に1文字以上の空白がある形」のどちらを受理するか定義してください。あるいは、scalarの厳密な識別は行わず、「値開始文字が `{` / `[` でなければ `top_level_not_container`」という分類であることを明記してください。

### 4. 期待効果の妥当性

- [Suggestion] `value_incomplete_inferred` を max_tokens 不足の「疑い」に限定し、追加観測なしに予算を変更しないとした修正は妥当です。

- [Warning] 「`fence_absent` の件数がそのまま非準拠率になる」は、分母が定義されていないため正確ではありません。件数だけでは呼び出し量の増減と書式準拠率を区別できません。

  修正提案: 非準拠率を `fence_absent試行数 ÷ 対象LLM試行総数` のように定義してください。現行ログから分母を取得できないなら「件数・最終失敗数を観測できる」に留めてください。

### 5. リスク

- [Critical] 出荷前の実 provider 実走1回を「準拠率の実測」とするのは不十分です。確認できるのは、その1回のサンプルで対象経路が成功したことだけです。また、promptは4本ですが「3段すべて」の確認では、通常版とmedia版のSOP抽出の片方しか通らない可能性があります。

  修正提案:

  - 1回の smoke は「互換性確認」と呼び、準拠率の根拠とは分けてください。
  - 4本すべての prompt factory が実 provider 確認の対象になるかを明記してください。1回で通らない分岐は、別入力または別実走が必要です。
  - 準拠率を出荷条件にするなら、試行母数、対象モデル、4 promptごとの成功条件を事前に定義してください。
  - 反復実走を費用面で採らないなら、その判断を明記し、段階リリースまたはリリース全体のロールバック条件を設けてください。
  - prompt修正だけで回復しない場合に備え、「受理契約を緩める」のではなく、変更一式を戻す手順を用意してください。

- [Warning] 「モデルの地の振る舞いに逆らわない」という根拠に、既存テストとフェンス除去コードの存在を使うのは弱いです。それらは過去にフェンス付き応答を想定した証拠にはなりますが、現在の本番モデルの出力分布を示すものではありません。

  修正提案: この根拠は仮説として表現し、実 provider確認で検証する対象にしてください。

### 6. スコープの適切さ

- [Suggestion] i1 gateを、再帰的prompt列挙、全 `executeSync()` 分類、直接引数形の強制、FQN参照者分類、局所的な復号語彙検査へ分けた構成は適切です。データフロー解析を導入せずに、許可する構文を狭く固定する設計もスコープに合っています。

- [Warning] `->executeSync(` というメソッド名検索は拾いすぎる側に倒れますが、それだけでは未解決参照を検出できるとは限りません。別クラスの同名メソッドを分類対象に含めることと、呼び出し先を解決できないことは別問題です。

  修正提案: scannerの結果を「`GuardedPrompt` と解決済み」「別型と解決済み」「未解決」に分け、未解決は明示的にgateを失敗させてください。単なる同名呼び出しのinventory化で共通規約(b)を満たしたことにしないでください。

### 7. 型安全性

- [Suggestion] `JSON_THROW_ON_ERROR`、`JsonException`から型付きreasonへの変換、`array<array-key, mixed>`をDTO側でnarrowする境界は、PHPStan level 10と既存DTOパターンに適合します。

- [Suggestion] `is_array()` を多重防御として残すことにも問題はありません。ただし「到達不能」を主張するなら、その分岐を直接テストする必要はなく、通常の型・例外契約を優先してください。
