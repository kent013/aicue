全体判定: **CHANGES_REQUESTED**

Round 1 の指摘はすべて実質的に解消されています。特に AG-200 と組織 2FA 強制の区別、秘密情報の5面防御、DTO境界、always-JIT の効果限定は妥当です。

残る主な論点は、OIDC実装そのものより、新設する静的 gate が AGENTS.md の走査器共通規約を満たす設計になっていないことです。

## 1. 使命との整合性

[Suggestion] 「中核機能ではなく、導入と継続利用を支える入口の基盤」という位置づけに修正され、使命への貢献を過大評価しない記述になっています。問題ありません。

## 2. 禁止事項違反

[Critical] 新設する複数の静的 gate について、AGENTS.md が要求する走査器・gate変更時の4点が設計に含まれていません。

対象には少なくとも次が含まれます。

- `EnterpriseSsoEmailIdentityIsolationTest`
- `EnterpriseSsoOutboundHttpGateTest`
- `EnterpriseSsoSecretExposureGateTest`
- AG-200 の静的 gate
- メール昇格フロー専用検査

現設計には正規表現、禁止記法、走査名前空間などの判定内容はありますが、次が示されていません。

- 負例と正例、および先に赤を確認する方法
- 解決不能な構文・名前参照を fail-closed にする分岐
- 走査根・母集団が空でないことの検査
- docblock に記載する保証範囲と保証外
- 語彙判定をする場合の区切り文字、接頭辞・打消し・接尾辞の負例

修正提案: 各 gate の成果物に上記4点を明記してください。既存の正典 gate をそのまま移植する場合も、aicue の走査根や目録へ適合させる変更が発生するなら、この規約の対象です。単純な正規表現だけでクラス参照やメソッド呼出しを判定する場合は、別名 import や動的記法をどう扱うかも必要です。

[Suggestion] 「段 F でまとめてテストを追加するのではなく、各段でテストを揃える」と明記されたため、禁止事項1への整合は改善されています。

## 3. 実現可能性

[Warning] `state` の「取り出したら消す」は、get → delete の二操作だと同時 callback に対して競合します。一回限り性を保証するには、原子的な consume が必要です。

修正提案: `EnterpriseLoginAttemptStore` の契約を「状態を原子的に取得・削除する」に変更し、同一 `state` を並行または連続して使用した場合、一方だけが成功するテストを追加してください。キャッシュを使うなら、保存する値は AGENTS.md の規定どおり素の配列・スカラーだけに限定し、読み戻し時に DTO を再構築してください。

[Warning] 前段の受入条件は GET と body 付き POST を押さえていますが、OIDC endpoint がリダイレクトを返す場合の扱いが未定義です。HTTPクライアントが自動追従すると、最初のURLだけを検査して転送先を検査しないSSRF経路になり得ます。

修正提案: 正典実装の仕様に合わせ、自動リダイレクトを拒否するか、各 hop を SsrfPin で再検査するかを明記し、その挙動を前段または outbound HTTP テストで固定してください。

## 4. 期待効果の妥当性

[Suggestion] 入退社連動の効果が「次回ログイン不能」に限定され、既存セッションの即時失効をスコープ外としたため、期待効果は妥当です。

ただし「アカウント存在の探り当てが設計段階で消える」は少し強い表現です。OIDCのメール引当経路については消せますが、メール昇格時の重複エラーから既存メールの存在が判別できる可能性は別に残ります。「企業OIDCの身元解決経路から消える」と限定すると正確です。

## 5. リスク

[Warning] ID token の `aud` 検証が「`aud` = client_id」だけでは、OIDC Core の複数 audience を扱い切れません。また、身元の主キーとなる `sub` の必須・非空検証が表にありません。

修正提案: 正典が対応する claim 仕様をそのまま明記してください。一般には次が必要です。

- `sub` が存在し、許容長内の非空文字列である
- `aud` が文字列または文字列配列として client ID を含む
- audience が複数、または `azp` が存在する場合の `azp` 検証
- 許容する署名アルゴリズムと鍵種別の整合
- `nonce` は保存した試行との定時間比較
- 許容時刻ずれに上限を設け、顧客入力で自由に拡張できない

[Warning] 「失敗時: 恒久拒否」は、Discovery/JWKS取得の一時障害、IdPの5xx、未知 `kid` のローテーション途中などでも接続を恒久無効化する意味に読めます。これを実装すると可用性上の後退になります。

修正提案: 「現在のログイン試行を fail-closed で拒否する」と「接続状態を恒久的に無効化する」を分けてください。接続状態を変更してよい失敗条件が正典に定義されている場合だけ、状態遷移サービスを通して恒久無効化すべきです。

[Warning] メール昇格時に、確認済みメールが既存ユーザーのメールと衝突した場合の挙動が未定義です。「併合しない」だけでは、DB制約エラー、メール存在の漏えい、上書きのいずれになるか決まりません。

修正提案: 衝突時は既存ユーザーを変更・併合せず、昇格も行わず、外部応答を一様にすることを明記してください。競合実行を含め、確認完了時のトランザクションと一意性制約で固定する必要があります。

## 6. スコープの適切さ

[Suggestion] メール昇格を正典 boundary の一部として残す理由が、`MustVerifyEmail` を含む既存機能の詰み回避として説明されました。A〜D の完了後に着手する順序も適切です。

ただし段 E で新しいメール通知経路を追加するなら、テストレーンの外部HTTP出口だけでなく、メール送信の既存 fake・目録・レート制限への登録も実装時に確認すべきです。これは独自機構の追加を意味せず、既存作法への適合確認です。

## 7. 型安全性

[Warning] DTO境界の方針は PHPStan level 10 に適合し得ます。ただし「検証済み DTO」という名称だけでは、JWKS や claims 内の `mixed` をDTO内部へ押し込めただけになる可能性があります。

修正提案: DTO生成境界で次を契約にしてください。

- `json_decode(..., flags: JSON_THROW_ON_ERROR)` 等の失敗を明示的に扱う
- 必須フィールドの存在と具体的な型を検査してから構築する
- 任意フィールドは明示的な nullable 型にする
- JWKS の未知要素をそのまま `array<string,mixed>` として内側へ公開しない
- model の暗号化属性を画面 DTO へ渡す汎用変換を使わず、許可フィールドから明示構築する
- FormRequest の `validated()` を無型配列のまま Service 全体へ渡さず、入力 DTO に変換する

以上のうち、承認を妨げるのは **新設 gate と走査器共通規約の不整合**です。ここを設計へ追加し、state の原子的 consume、OIDC claim の完全な検証条件、メール昇格衝突時の挙動を明確化すれば、承認可能な状態です。
