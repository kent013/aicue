# 対応マトリクス: conceptual-review Round 2

## [Critical] 新設 gate が AGENTS.md「静的検査 (gate) と走査器の共通規約」を満たしていない

- 判断: **対応する**
- 根拠: 指摘のとおり。本設計は gate を 5 本新設・移植する
  （正典 3 本 + AG-200 の裏当て + 昇格フロー専用）。AGENTS.md は走査ロジック・走査対象・
  名前解決・判定条件・目録のいずれかを新設／変更するとき **同じ PR で 4 点を揃える**ことを
  発火条件つきで求めており、本件は全 gate が発火する。
  「正典からの移植」であっても aicue の走査根・目録へ適合させる変更が入る以上、対象外にはならない。
- 対応内容: 「新設する gate と走査器共通規約への適合」の節を新設。
  5 条（(a) 完全修飾名 / (b) fail-closed / (c) 負例で裏取り / (d) 集めた結果を必ず判定に使う /
  (e) 語彙一致はトークン完全一致）の**どの条がどの gate に掛かるか**を表で確定し、
  4 点（負例と正例で先に赤 / 解決できない形を落とす分岐 / 空振り検査 / docblock の保証範囲）を
  各 gate の必須成果物として明記した。走査根は `Tests\Support\TrackedPhpSourceFiles` を使う。

## [Warning] `state` の一回限り性が get → delete の二操作では競合する

- 判断: **対応する**
- 根拠: 正しい。同一 `state` の並行 callback で二重に通る余地がある。
- 対応内容: `EnterpriseLoginAttemptStore` の契約を
  「**取得と削除を一体で行う（原子的な consume）**」と明記し、
  保管先をセッション（同一ブラウザの往復であることが構造で保証される面）に置き、
  Laravel のセッションロックの下で consume する形にした。
  保存する値は**素のスカラーだけ**に限り、読み戻しは DTO へ明示的に組み立て直す
  （不変条件 11 と同じ規律をセッションにも適用する）。
  同一 `state` の 2 度目の使用が失敗するテストを必須成果物に追加。

## [Warning] リダイレクト追従の扱いが未定義（最初の URL だけ検査する SSRF 経路）

- 判断: **対応する**
- 根拠: 正しい。自動追従すると転送先が未検査のまま取得される。
- 対応内容: discovery / JWKS / トークン交換の 3 経路すべてで
  **自動追従を行わない**（2xx 以外は一様に拒否する）ことを明記し、
  外向き gate の固定対象に加えた。`SnsCertificateFetcher` が同じ判断を採っている（前例あり）。

## [Warning] `aud` 検証が「= client_id」だけでは足りない / `sub` の検証が表に無い

- 判断: **対応する**
- 根拠: OIDC Core は `aud` を文字列または文字列配列と定める。複数 audience 時は `azp` の
  検証が要る。`sub` は身元の主キーそのものなので非空検査が要る。
- 対応内容: #3 の検証項目を書き換え、`sub` の存在・非空・長さ上限、`aud` の
  文字列／配列の両形、複数 audience または `azp` 存在時の `azp` 検証、
  `nonce` の**定時間比較**、許容時刻ずれの**上限を設定値として持ち顧客入力で広げられない**ことを明記。

## [Warning] 「失敗時: 恒久拒否」が接続の恒久無効化と読める（可用性の後退）

- 判断: **対応する**
- 根拠: 正しい。IdP の 5xx・鍵ローテーション途中・DNS の一時障害で接続を殺すのは後退である。
- 対応内容: **「このログイン試行を fail-closed で拒否する」**と
  **「接続の状態を変える」**を明確に分離。後者は状態遷移サービスを通す**運営操作**であり、
  取得失敗を理由に自動で無効化はしない、と明記。表の「失敗時」列も書き換えた。

## [Warning] メール昇格の衝突時の挙動が未定義

- 判断: **対応する**
- 対応内容: 衝突時は **既存利用者を一切変更せず・併合せず・昇格も行わない**。
  外部応答は**一様**にして存在を漏らさない。一意制約と確認完了時のトランザクションで固定する、
  と明記。競合実行のテストも必須成果物に追加。

## [Warning] DTO 境界が「mixed を DTO の中へ押し込めただけ」になりうる

- 判断: **対応する**
- 対応内容: 「境界の型」に構築契約を追記
  （JSON の復号は失敗を明示的に扱う / 必須要素は存在と具体型を検査してから構築 /
  任意要素は nullable を明示 / 未知要素を `array<string,mixed>` のまま内側へ出さない /
  暗号化属性を画面用の型へ汎用変換で渡さない / `validated()` を無型配列のまま Service へ渡さない）。

## [Suggestion] 「アカウント存在の探り当てが設計段階で消える」は強い

- 判断: **対応する**
- 対応内容: 「**企業 OIDC の身元解決経路から**消える」と限定した。

## [Suggestion] 段 E が新しいメール送信経路を足すなら既存作法への適合確認が要る

- 対応内容: 段 E の成果物に「既存のメール送信の作法（送信基盤・目録・流量制限）への
