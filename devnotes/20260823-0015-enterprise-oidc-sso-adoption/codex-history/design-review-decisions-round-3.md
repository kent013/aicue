# 対応マトリクス: design-review Round 3

## [Critical] 接続の物理削除で身元だけが消え、アカウントが分裂する（A2 / D2）

- 判断: **対応する**
- 根拠: 正しい。接続を消すと `cascadeOnDelete` で身元が消え、**利用者は残る**。
  同じ IdP を再登録して同じ `subject` で入ると**新しい利用者が JIT で作られる**。
  企業 SSO でしか入れない利用者は元のアカウントへ戻れない。
- 対応内容: **身元が 1 件でもある接続の物理削除を禁じる**。
  削除できるのは**身元が 0 件の接続だけ**である。運用は「無効化 (`Disabled`)」で行う。
  UI は**ボタンを disabled にせず**、押下時に「無効化してください」とエラーを表示する（禁止事項 8）。
  組織そのものの削除に伴う連鎖は本設計の対象外（既存の組織削除の運用に従う）と明記する。

## [Critical] issuer / client_id を変えると身元の名前空間が壊れる（C2 / D1）

- 判断: **対応する**
- 根拠: 正しい。OIDC の身元は実質 `(issuer, subject)` であり、
  pairwise subject では `client_id` も名前空間を変えうる。
  同じ接続の issuer を別 IdP へ変えた後に偶然同じ `subject` が返ると、
  **以前の利用者へ誤ってログインさせる**。
- 対応内容: 更新の規則を 3 段に分ける:
  - **`issuer` / `client_id`**: **身元が 1 件でもあれば変更禁止**（新しい接続を作る）
  - **`client_secret`**: `Draft` へ差し戻し + `verified_at` を消して更新可
  - **表示名**: 状態を変えない

## [Critical] PostgreSQL の aborted transaction 内で再検索できない（C1）

- 判断: **対応する（提示された案 1 を採る）**
- 根拠: 正しい。pgsql は一度 SQL エラーが出るとトランザクション全体が aborted になり、
  savepoint まで戻さない限り次の SELECT も失敗する。
  さらに C2 が**接続の行をロックしている**ので、同一接続の callback は既に直列化されており、
  そもそもこの競合は正規経路では起きない。
- 対応内容: **接続の行ロックを唯一の競合制御にする**。
  C1 から一意制約の回復処理を**削除**し、予期しない違反は**再送出**する。
  一意制約そのものは**最後の防波堤として残す**（多層防御。ただし捕まえない）。

## [Critical] B4 の結果分類がセッションの秘密の破棄まで届かない

- 判断: **対応する**
- 根拠: 正しい。`consume()` が一様な例外を投げてしまうと、呼び出し側は
  「行が消えた失敗（秘密も消す）」と「行を保持した失敗（秘密も保持）」を区別できない。
- 対応内容: `consume()` は**投げずに分類結果を返す**。
  セッションの秘密の始末は `EnterpriseCallbackAuthenticator`（application service）が行い、
  **その後で外向きの一様な例外へ変換する**。
  「HTTP の応答が一様であること」と「内部で理由を区別すること」は両立する。

## [Critical] メール昇格に「メールのリンク → 確認画面 → POST」の導線が無い（E1）

- 判断: **対応する**
- 対応内容: **認証必須・`no-store` の GET の確認画面を 1 本足す**（route は **14 本**になる）。
  メールのリンクはその画面を開くだけで、**状態を変えるのは POST に限る**
  （メールの先読みでは画面が開くだけで確定しない）。

## [Critical] E1 の route に `auth` が見えない

- 判断: **対応する**
- 対応内容: **既存の認証済み group の中**に置くことを明記し、コード例にも group を示す。

## [Critical] 確認トークンが `dontFlash` の対象にない（E1）

- 判断: **対応する**
- 対応内容: 確認トークンを機密の入力として扱い、
  **失敗時に入力を flash しない**（`withInput()` を使わない）形にする。
  `#[SensitiveParameter]` を付け、ログ・例外・監査の漏洩テストの対象に加える。

## [Critical] G2 の保証範囲が実際の型解決能力より広い（F1）

- 判断: **対応する（主張を狭め、主証明を移す）**
- 根拠: 正しい。局所変数や factory の戻り値に入った HTTP クライアントの
  `request()` は動的構文ではないが、字句走査では受け手の型を解決できない。
- 対応内容:
  - **保護対象らしい固定のメソッド語彙**（`request` / `get` / `post` / `send` / `fetch` 等）で
    **受け手の型が解決できない場合だけ fail-closed** にする
  - G2 自身の主張を「**既知の禁止型・ファサードの参照が無い**」+
    「**動的な呼び出しの形が無い**」+「**未解決の保護対象語彙が無い**」まで明示的に書く
  - **I3 の主証明を DI の結線テストと `PinnedHttpClient` の実挙動テストへ移す**と gate が宣言する

## [Critical] B2 の漏洩テストが実送信要求と両立しない

- 判断: **対応する**
- 根拠: 正しい。Basic なら Authorization ヘッダに、post なら body に**必ず値が在る**。
  「要求の記録」が実送信を指すのか診断用の履歴を指すのか曖昧だった。
- 対応内容: 2 つに分離した:
  - **transport seam が捕らえる実送信要求**: 資格情報が**正しく含まれる**ことを検査する
  - **ログ / 監査 / 例外 / 診断用の HTTP 履歴**: 平文・base64・form-urlencoded の
    **いずれの形でも残らない**ことを検査する

## [Warning] `id_token_signing_alg_values_supported` が metadata に無い（B1 / B3）

- 判断: **対応する**
- 対応内容: metadata DTO に**広告された署名方式の集合**を持たせ（必須・非空・具体型を検査）、
  B3 で **`alg` がアプリの許可集合と IdP の広告集合の両方に含まれる**ことを要求する。
  広告外の `alg` で署名されたトークンを拒否する負例を追加する。

## [Warning] 不変条件表 I1 と C1 の docblock に「指紋」が残っている

- 判断: **対応する**
- 対応内容: 「接続 × `COLLATE "C"` の subject」へ全箇所を統一した。

## [Warning] `subject` の入力検査（文字集合・長さの単位）が曖昧（A2）

- 判断: **対応する**
- 対応内容: DTO の構築時に**許容文字と最大長（バイト単位）**を固定し、
  DB の `varchar(255) COLLATE "C"` と**同じ境界**をテストする。

## [Warning] `Deadline::of(connect:, total:)` が未確定の API のまま（B2）

- 判断: **対応する**
- 対応内容: **着手条件に「^0.4 の確定 API へ詳細設計を追随済みであること」を追加**し、
  コード例は「実装時に確定する」と明示する（存在しない API を確定形として残さない）。

## [Warning] `dontFlash` が `client_secret` だけでは不足（D2）

- 判断: **対応する**
- 対応内容: グローバルには `client_secret` を登録し、
  **callback と確認は失敗時に入力を flash しない**形にする
  （`code` / `state` / `token` のような一般名をグローバルに登録すると
  他のフォームの入力復元まで黙って変えるため、経路側で閉じる）。

## [Warning] `organizations.sso.index` の認可の記述が紛らわしい（F2）

- 判断: **対応する**
- 対応内容: 「**`Gate::authorize` あり**／`ControllerAuthorizationGateTest` の**母集団外**（GET）」と

## [Warning] D37 の説明と `FingerprintPurpose` の実態が一致しない（F3）

- 判断: **対応する（D37 の理由を書き直す）**
- 根拠: `FingerprintPurpose` はメール昇格でも使うので、
  「ログイン試行方式の固有資産」という説明と合わない。
- 対応内容: D37 の逸脱を「**一時トークンの指紋方式（機構横断）と、
  それを使う DB のログイン試行の保管**」として書き直した。
