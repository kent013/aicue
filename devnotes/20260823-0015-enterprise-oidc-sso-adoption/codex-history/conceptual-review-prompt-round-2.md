## 対応マトリクス

# 対応マトリクス: conceptual-review Round 1

## [Critical] AG-200 と既存 2FA 強制 (`RequireTwoFactorForEnforcedOrganizations`) の整合

- 判断: **対応する（ただし指摘の前提は事実で否定される）**
- 根拠:
  - `app/Http/Middleware/RequireTwoFactorForEnforcedOrganizations.php` を実読した。
    契約は「未準拠ユーザーを **`settings.security` (2FA の *設定* ページ)** へ 302 する」であり、
    **2 要素の *入力* 画面 (challenge) へ送るものではない**。
  - 正典の観測文も同じ区別を明記している —
    「組織義務づけの関門の転送先は 2 要素の**設定画面**であって**入力画面**ではない」。
  - したがって AG-200 が禁じる「共通ログイン経路にアプリ側の 2 要素認証を挟む」には該当しない。
    AG-200 自身が「守りは消えない — 組織が全員に義務づける強制は別の関門が担い、
    共通ログイン経由でも効く」と明言している。
- 対応内容: 誤読の余地を消すため概念設計に
  (a) 「挟む = ログイン確定前に challenge を挟むこと」「強制 = ログイン確定**後**のアカウント全体ゲートで
  設定ページへ送ること」の区別を明文化、
  (b) 実挙動テスト 2 本（2FA 有効な利用者も企業ログインでそのままログインが確定する /
  組織義務づけの下でも企業ログイン後に設定ページへ到達できる）を必須成果物として追加、
  (c) 静的裏当て gate 1 本（企業・ソーシャル両 controller に待機ログインを作る記述が無い）を明記。

## [Critical] OIDC プロトコル検証責務の明文化とテスト化

- 判断: **対応する**
- 根拠: 指摘のとおり、概念設計はサービス 7 クラスを「機能名」でしか列挙しておらず、
  信頼境界（issuer 同一性 / state・nonce の一回限り性 / claim 検証 / 鍵選択とローテーション）が
  読み取れない。SSRF 窓口を通しても、この層が緩ければ認証そのものが崩れる。
- 対応内容: 「サービス 7 クラスの責務と検証項目」の節を新設し、各クラスの責務・
  検証項目・失敗時の扱いを表で明示。あわせて Feature/Architecture テストで固定する項目を列挙。

## [Warning] 「Auth 名前空間へ置く = 検査回避」と読める

- 判断: **対応する**
- 根拠: 配置そのものは正典の設計判断（引き継ぎ対象）だが、**なぜ範囲外でよいのか**の
  積極的な理由が書かれていないと、指摘のとおり回避に読める。
- 対応内容: 「昇格フローはメールで**利用者を引かない** — 引くのは常に *認証済みの自分自身* であり、
  引き当ての鍵は `Auth::id()` である。走査から外すのは『メール文字列を扱う正当な唯一の場所』を
  禁止語の走査に巻き込まないためであって、引き当ての禁止を緩めるためではない」を明記し、
  **昇格フロー専用の検査**（メールから利用者を引かない / 既存アカウントとの併合をしない）を成果物へ追加。

## [Warning] 前段 TODO の受入条件（body 付き POST と GET の両方）

- 判断: **対応する**
- 根拠: 正典が「v0.2 系は要求 body を運べず実装そのものが成立しない」と書いており、
  前段の受入条件が曖昧だと本設計が着手できない状態で TODO が閉じうる。
- 対応内容: 依存の節に受入条件を明記（Discovery/JWKS の GET と token 交換の body 付き POST が
  いずれもピン留め経路で通ること）。

## [Warning] always-JIT の効果を過大に書いている（入退社の自動化）

- 判断: **対応する**
- 根拠: SCIM をスコープ外にしている以上、「開け閉めが自動化される」は言い過ぎである。
- 対応内容: 効果を「IdP 側でアクセスを失った利用者は**次回ログインできなくなる**」に限定し、
  既存セッションの即時失効は**期待しない**ことをスコープ外へ明記。

## [Warning] 接続の秘密は「DTO に載せない」だけでは不十分

- 判断: **対応する**
- 根拠: 保存・読み戻し・ログ・例外・Inertia props の 5 面すべてを塞がないと漏れる。
- 対応内容: 秘密の扱いを 5 面で明記（暗号化キャスト / 伏字での再表示 / props と DTO と
  JsonResource から除外 / 例外は機械可読な理由文字列のみ / ログに code・token・secret を出さない）。

## [Warning] 段 E（メール昇格）の必要性が本文から判定できない

- 判断: **対応する（スコープには残す）**
- 根拠: 正典の boundary が「含む」と明記している要素であり、外すと乖離になる。
  かつ **企業 SSO でしか入れない利用者は使えるメールを 1 件も持たない**ため、
  通知・パスワード再設定・退会確認の全経路が詰む（aicue は `MustVerifyEmail` 実装）。
  これは OIDC 本体の安全性ではなく**詰みの回避**として必要である。
- 対応内容: 「なぜ E が要るか」を詰みの回避として明記し、
  昇格の条件（本人確認 = 確認メールのトークン / 認可 = 自分自身のみ / 監査 = 変更の記録）を書く。
  ただし段 F より後には置かず、**A〜D が緑になってから着手する最後の段**とする。

## [Warning] DTO/JsonResource の採用方針が成果物に現れていない

- 判断: **対応する**
- 根拠: 禁止事項 4 と PHPStan level 10 の両方に直結する。
- 対応内容: 「境界の型」の節を新設し、外部応答（discovery / JWKS / token / claims）を
  検証済み DTO へ畳んでから内側へ渡すこと、controller は FormRequest → Service → Inertia の
  薄い境界に限ること、秘密を画面側の型に載せないことを明記。

## [Suggestion] 使命への貢献の表現を「基盤」として書く

- 判断: **対応する**
- 対応内容: 期待効果の書き出しを「中核機能ではなく、導入と継続利用を支える入口の基盤」と改める。

## 改訂後の概念設計（全文）

# 概念設計: enterprise-oidc-sso-adoption

家系の機能台帳 lctl の feature `auth-enterprise-oidc`
(canonical_version **v1 / AG-200 適合**、feature_revision `23-30a9407c8f19`) への追従。
aicue のセルは `status: pending`（裁定 2026-08-04 で全アプリ導入決定済み・実装 0 行）である。

## 背景・課題

### 正典が求めていること

企業契約の顧客が **自社の認証基盤 (会社の共通ログイン) でそのまま aicue に入れる** 受け口。

- 組織ごとに OIDC 接続を登録する（接続先 URL は**顧客自身が入力する**）
- その組織の社員が初めて入ってきたら **その場でアカウントを作る (always-JIT)**
- **メールアドレスを本人の同定に使わない** —
  これは「登録済みメールかどうかが応答から読み取れる (アカウント存在の探り当て)」と
  「他所で確認済みと主張されたメールで乗っ取る (nOAuth)」の 2 つを同時に塞ぐ本体であり、
  正典が**削減不可**と明記している要件である。
- 裁定 **AG-200 (2026-08-18)**: 企業ログイン・ソーシャルログインの経路に
  **アプリ側の 2 要素認証を挟まない**。追加の本人確認は認証基盤側の責務、
  組織義務づけの強制は別関門 `auth-2fa-org-enforcement` に任せる。

正典実装は **laravel-claude-template** が保持する（7 サービス + 2 モデル + config + route 群 +
gate 3 本）。**aigenba** が AG-200 適合の参照実装を v1 で完了している（家系で最初）。

### aicue の現状（実読で確認）

| 正典の資産 | aicue |
|---|---|
| `app/Services/EnterpriseSso/` (7 クラス) | **0 件** |
| `config/enterprise-sso.php` | **無し** |
| `OrganizationOidcConnection` / `EnterpriseIdentity` モデル・移行 | **0 件** |
| ログイン導線 3 route / 組織側の接続管理 7 route | **0 件** |
| gate 3 本 | **0 件** |
| メールアドレス昇格フロー | **0 件** |

一方で **土台は揃っている**:

- `Kent013\SsrfPin\UrlSafetyInspector` の利用実績が 1 件ある
  (`app/Services/Mail/Sns/SnsCertificateFetcher.php` — 無認証入力が誘発する外部取得の準拠実装)
- 組織まわりの `MembershipScopedOrganizationBinder` / `{organization:slug}` 解決、
  `recent-auth` middleware、`not-pending-deletion` group、named limiter、
  `ExternalFakeDeclaration` / `ExternalSeamInventory`（外部到達点の目録）が既に稼働している
- **ソーシャルログインは既に AG-200 の形である** —
  `SocialAuthController::callback()` は `Auth::login()` で**その場でログインを確定**しており、
  2 要素認証の入力画面へ送る分岐を持たない（実読で確認）。
  つまり aicue は AG-200 に**是正ではなく維持**で臨める。

### 課題

1. 企業契約顧客が自社の共通ログインで入れない。社員の入退社に合わせた開け閉めが手作業のまま残る。
2. 前段条件が未達 — `kent013/laravel-ssrf-pin` が `^0.2` (解決版 v0.2.0)。
   正典の接続先情報の取得・トークン交換は **要求 body を運べる版 (v0.3 以降) が必須**で、
   v0.2 では実装そのものが成立しない。
3. AG-200 の形が **現状は「たまたま」保たれているだけ**で、機械で固定されていない。
   企業ログインという 2 本目の経路が増える瞬間が、分岐の複写が生まれる最大の危険点である
   （起源 spirux は実際に 2 経路へ同じ分岐を複写して update_pending になっている）。

## 改善アイデア

**正典テンプレートの実装を土台に、aicue の既存作法へ写して一式を導入する。**
独自の作り直しはしない（家系で 1 つの形を共有する feature である）。

方針は 4 本:

1. **メールで人を引かない設計を、実装と gate の二層で持つ。**
   身元表は「接続 × IdP の subject」で一意に引く。申告メールは暗号化して持つが
   **索引を意図的に持たせない**（索引があると「メールで引ける」経路が復活する）。
   これを `EnterpriseSsoEmailIdentityIsolationTest` が正規表現と**索引 0 本の実行確認**で固定する。
2. **外部取得は必ず SsrfPin の窓口を通す。**
   接続先情報の取得・鍵の取得・トークン交換の 3 経路すべて。
   `EnterpriseSsoOutboundHttpGateTest` が名前空間配下の素の HTTP 呼び出しを許可一覧なしで弾く。
3. **接続の秘密は受け渡しの型に載せない。**
   前面で秘密を扱ってよいのは**接続の登録・更新フォーム 1 本だけ**。
   `EnterpriseSsoSecretExposureGateTest` が固定する。
4. **AG-200 を「維持」として機械に持たせる。**
   企業ログインの戻り口もソーシャルログインの戻り口も、確認できた時点でログインを確定させる。
   待機ログイン（2 要素入力画面への転送）を**どちらの経路にも作らない**ことを
   静的 gate で裏当てし、主たる証明は実挙動テストに置く（aigenba の `T1220` が参照実装）。

#### AG-200 の「挟む」と、組織義務づけの「強制」は別物である（誤読を消すための明文化）

| | 挟む（AG-200 が**禁じる**） | 強制（AG-200 が**残すと明言**） |
|---|---|---|
| いつ | ログインが**確定する前** | ログインが**確定した後** |
| 何を | 6 桁の**入力画面 (challenge)** へ転送し、待機ログインを作る | アカウント全体のゲートで **2 要素の *設定* ページ**へ転送する |
| aicue の現物 | **存在しない**（`SocialAuthController` は `Auth::login()` で即時確定。企業側も同じ形で作る） | `RequireTwoFactorForEnforcedOrganizations` が `settings.security` へ 302（実読で確認） |

正典の観測文も同じ区別を明記している —
「組織義務づけの関門の転送先は **2 要素の設定画面であって入力画面ではない**」。
したがって既存の強制ゲートは **AG-200 に適合したまま企業ログイン経由でも効く**。
本設計はこの区別を、次の 3 点で機械に持たせる:

- 実挙動テスト①: **2 要素認証が有効な利用者**が企業ログインで**そのままログインが確定する**
- 実挙動テスト②: **組織義務づけの下**でも企業ログイン後に **2 要素の設定ページへ到達できる**
- 静的裏当て gate: 企業・ソーシャル**両方**の戻り口に、待機ログインを作る記述・
  2 要素の入力画面への転送が**存在しない**（許可一覧を持たない）

### aicue 固有の適合（テンプレートをそのまま置けない箇所）

| 論点 | aicue での形 |
|---|---|
| 外部到達点の目録 | テンプレートには無い `ExternalSeamInventory` / `ExternalFakeDeclaration` に、企業 OIDC の到達点と試験用の差し替えを登録する（同じ事実を 2 か所に書かない規約に従う） |
| テストレーンの外向き HTTP 既定拒否 | 実 IdP へ出ない。試験用の接続先（偽の IdP）は `ExternalFakeDeclaration` の枠組みへ載せ、許可環境は外部ログインと同じ `testing` / `bughunt.local` に絞る |
| route の目録 | `RecentAuthRouteTest` / `ThrottleCoverageInventoryTest` / `ControllerAuthorizationGateTest` / `NestedRouteIdorDefenseTest` / `TenantBoundaryOrderingTest` / `AccountDeletionFreezeRouteGateTest` へ新 route を登録する（aicue は deny-by-default の目録が多く、登録漏れは赤になる） |
| 組織 route の引数解決 | 既存どおり `{organization:slug}` + `MembershipScopedOrganizationBinder`（テンプレートの識別名解決と同じ思想） |
| PII | `EnterpriseIdentity` の申告メールは CipherSweet で暗号化する（不変条件 6）。ただし **blind index は付けない**（不変条件 6 の「検索は whereBlind」は**引く必要がある PII** の話であり、ここは引かないことが要件） |

## サービス 7 クラスの責務と検証項目（信頼境界の明文化）

正典が持つ 7 クラスを機能名だけで並べると、**認証の信頼境界がどこで閉じるのかが読めない**。
SSRF 窓口を通していても、下表の検証が緩ければ「取りに行く先は安全だが、
返ってきたものを信じてよい理由が無い」状態になる。したがって責務と検証項目を先に確定する。

| # | クラス（正典名） | 責務 | 必ず行う検証 | 失敗時 |
|---|---|---|---|---|
| 1 | `OidcDiscoveryService` | 接続先情報（discovery 文書）と鍵（JWKS）の取得 | **SsrfPin 経由**での取得 / 文書の `issuer` が登録済み issuer と**完全一致** / 取り出す endpoint (`authorization` / `token` / `jwks_uri`) が **issuer と同一 origin** / 取得結果は検証済み DTO へ畳む | 恒久拒否（機械可読な理由文字列のみ） |
| 2 | `OidcTokenExchanger` | 認可コードとトークンの交換（**body 付き POST**） | **SsrfPin 経由** / token endpoint は #1 が検証した値のみ / client secret は要求にだけ載せ、応答・ログ・例外に出さない / 応答は検証済み DTO へ畳む | 恒久拒否 |
| 3 | `EnterpriseIdTokenVerifier` | ID トークンの検証 | 署名（**JWKS の `kid` で鍵選択**。未知 `kid` は**鍵の再取得を 1 回だけ**行う = ローテーション追従） / `alg` は**署名方式の許可集合のみ**（`none` と対称鍵は拒否） / `iss` 一致 / `aud` = 自分の client_id / `exp` `iat` `nbf`（時刻ずれの許容は設定値） / **`nonce` の一致** | 恒久拒否 |
| 4 | `EnterpriseLoginAttemptStore` | ログイン試行（`state` / `nonce` / PKCE の検証子 / 接続 id）の保管 | `state` と `nonce` は**十分な乱数長** / **一回限り**（取り出したら消す） / **有効期限**あり / 認可コードも一回限り | 恒久拒否 |
| 5 | `EnterpriseUserProvisioner` | 初回ログイン時の利用者の自動作成 (always-JIT) | 引き当ての鍵は **(接続 id, IdP の subject)** のみ。**メールでは引かない** / 申告メールは暗号化して保存し**索引を持たせない** / 組織への所属は**接続が属する組織のみ** | 例外（存在を漏らさない一様な応答） |
| 6 | `EnterpriseCallbackAuthenticator` | 戻り口の組み立て（#1〜#5 の合流とログインの確定） | ログインは**確定させる**（待機ログインを作らない = AG-200） / セッション固定化対策（`session()->regenerate()`） / 接続が有効なときだけ通す | 一様な失敗応答 |
| 7 | `OidcConnectionTransitionService` | 接続の状態遷移（下書き → 確認済み → 有効 / 無効） | 遷移は**定義した組**のみ許す / 確認（外向きの取得を伴う）は**専用の流量制限** / 変更は再認証 (`recent-auth`) の下でのみ | 例外 |

### 境界の型（DTO / PHPStan level 10）

- 外部から返ってきたもの（discovery 文書 / JWKS / トークン応答 / claims）は
  **配列のまま内側へ流さない**。各サービスが**検証済みの DTO**へ畳んでから返す
  （`mixed` の伝播を境界で止める = level 10 を素直に通す）。
- controller は **FormRequest → Service → Inertia** の薄い境界に限る。
  `response()->json()` は書かない（禁止事項 4）。
- **接続の秘密（client secret）・認可コード・各種トークンは、
  画面用 DTO・JsonResource・Inertia props・例外文言・ログのいずれにも載せない。**
- 組織 id・所有者キーは payload から受けない（不変条件 1）。
  接続は必ず **URL の組織 → 接続** の親子で解決する（不変条件 2）。

### 接続の秘密を守る 5 面

| 面 | 形 |
|---|---|
| 保存 | 暗号化キャストで保存する。**索引は持たせない** |
| 再表示 | 画面へ返すのは**伏字**のみ（原文は返さない） |
| 受け渡し | DTO / JsonResource / Inertia props に**存在しない**（gate が固定する） |
| 例外 | **機械可読な理由文字列のみ**（値を含めない。gate が固定する） |
| ログ | client secret / 認可コード / トークンを出さない |

## 期待効果

- **使命への貢献（中核機能ではなく、導入と継続利用を支える入口の基盤）**:
  AI-CUE は「現場作業者が専門知識ゼロで標準化されたマニュアル動画を作れる」ことを使命に持つ。
  企業導入では**現場の作業者が自分でアカウントを作る／パスワードを覚えること自体が最初のハードル**であり、
  勤め先の共通ログインでそのまま入れることは「思考ゼロ」を入口へ広げる。
  動画シナリオ生成・ナビ撮影という中核の価値そのものを増やすものではない。
- **運用の前進（限定して主張する）**: IdP 側でアクセスを失った利用者は
  **次回ログインができなくなる**。**即時停止でも既存セッションの失効でもない**
  （それらは SCIM / デプロビジョニングの領分でスコープ外）。
- **セキュリティの前進**: 顧客入力 URL を取りに行く経路が SSRF 窓口の下で 1 本道になる。
  メールでの引き当てを構造的に禁じることで、アカウント存在の探り当てと nOAuth 型の
  乗っ取りが**設計段階で**消える。
- **家系整合**: pending 4 リポジトリのうち aicue が AG-200 適合で追従し、
  正典との乖離が 1 件減る。

## 実装方針（概要）

### 段構成（直列。前段が緑になってから次へ）

| 段 | 内容 | 主な成果物 |
|---|---|---|
| 前段 | `kent013/laravel-ssrf-pin` を `^0.4` へ | **別 TODO `ssrf-pin-v04-upgrade` の責務**（本設計は依存するだけ） |
| A | 器 — 設定・モデル・移行・Factory | `config/enterprise-sso.php`, 2 モデル + 移行 2 本 + Factory 2 本 |
| B | 取得と検証 — サービス 4 クラス | 接続先情報の取得 / トークン交換 / ID トークンの検証 / ログイン試行の保管 |
| C | ログイン導線 — サービス 3 クラス + controller + route 3 本 | 利用者の自動作成 / callback の組み立て / 接続の状態遷移, `EnterpriseSsoLoginController` |
| D | 組織側の接続管理 — controller + route 7 本 + 画面 | `OrganizationSsoConnectionController`, Svelte 画面 1 枚 |
| E | メールアドレスの昇格フロー（**A〜D が緑になってから**） | `App\Services\Auth\EmailPromotionService` ほか（**Auth 名前空間**） |
| F | gate + 目録登録 | 正典 gate 3 本 + AG-200 の裏当て 1 本 + 昇格フロー専用の検査 1 本、および aicue 側の目録登録 |

段 F の gate は「最後にまとめて足す」ものではない。**各段が自分の gate を同じ変更で持って
緑にする**（禁止事項 1「不変条件は対応するテストへの登録まで含めて実装済み」）。
F はそれらを取りまとめ、目録（`RecentAuthRouteTest` / `ThrottleCoverageInventoryTest` /
`ControllerAuthorizationGateTest` / `NestedRouteIdorDefenseTest` / `TenantBoundaryOrderingTest` /
`AccountDeletionFreezeRouteGateTest` / `ExternalSeamInventory`）の登録漏れを閉じる段である。

### 段 E（メールアドレスの昇格）が要る理由 — 詰みの回避

企業 SSO でしか入れない利用者は、**使えるメールアドレスを 1 件も持たない**。
aicue の `User` は `MustVerifyEmail` を実装しており、通知・パスワード再設定・
退会の確認といった経路がすべてメールを前提にしている。昇格フローが無いと、
企業 SSO 利用者は**アプリを離れた連絡手段を一切持たないまま固定される**。
段 E は OIDC 本体の安全性のためではなく、この**詰みの回避**のために要る。

昇格の条件は 3 点に限る:

- **本人確認**: 確認メールのトークンを踏んだときにだけ確定する
  （IdP の申告メールをそのまま昇格させない = nOAuth の再現を防ぐ）
- **認可**: 対象は**認証済みの自分自身のみ**。他人のメールは扱わない
- **監査**: 変更を記録する（既存の監査基盤へ載せる）

### 名前空間の配置（正典の設計判断ごと引き継ぐ）

メールアドレスの昇格フローは `App\Services\EnterpriseSso` ではなく **`App\Services\Auth`** に置く。
これは「メールで引き当てることを禁じる設計検査の走査範囲へ入れないための意図的な配置」であり、
テンプレートの検査自身がそう説明している。aigenba も同じ名前空間を採った。
**この判断ごと引き継ぐ**（起源 spirux は別配置だが、正典はテンプレート側である）。

**これは検査の回避ではない。** 昇格フローも**メールで利用者を引かない** —
引き当ての鍵は常に `Auth::id()`（自分自身）であり、メール文字列は
「その利用者に紐づける値」としてしか現れない。走査から外すのは、
**メール文字列を正当に扱う唯一の場所**を禁止語の走査へ巻き込まないためであって、
引き当ての禁止を緩めるためではない。この主張を空手形にしないため、
**昇格フロー専用の検査**を成果物に含める:

- 昇格フローがメールから利用者を引く記法を持たない（`whereBlind('email', …)` を含む）
- 昇格が**既存アカウントとの併合を行わない**（他人のアカウントを吸収しない）

## 制約・前提

### 正典の不変条件（削減不可）

1. **メールアドレスで利用者を引かない**。身元表に索引を付けない。
2. **外部取得は必ず SsrfPin の窓口経由**（接続先情報 / 鍵 / トークン交換の 3 経路）。
3. **接続の秘密を扱う前面は登録・更新フォーム 1 本のみ**。受け渡しの型に秘密を載せない。
4. **共通ログイン経路に 2 要素認証を挟まない**（AG-200）。
5. **初回ログインでその場で利用者を作る (always-JIT)**。

### AGENTS.md 側の制約

- セキュリティ不変条件 **8**（外部 URL 取得は SSRF 検査経由 / 境界は `config/ssrf-pin.php` に pin）
- セキュリティ不変条件 **6**（PII は CipherSweet）
- セキュリティ不変条件 **9**（変更系 route は `Gate::authorize` を通すか exemption 登録）
- セキュリティ不変条件 **2 / 10**（子は親に属する = 認可より前に 404。層 2 は binding 直後）
- 禁止事項 **1**（テストなしの実装完了報告）・**2**（PHPStan の widen / baseline）・**4**（`response()->json()` 直書き）

### 依存

- **前段**: `kent013/laravel-ssrf-pin` `^0.4`（別 TODO `ssrf-pin-v04-upgrade`）。
  正典が要求するのは v0.3 の「要求 body 付き取得」だが、aicue は判定層の穴を塞ぐ
  v0.4 を先行させる方針が既に設計済みなので、**^0.4 に依存する**（v0.4 は v0.3 の機能を含む）。
  **本設計が着手できるための受入条件**（前段が満たしていなければ本設計は始められない）:
  1. discovery 文書と JWKS の **GET** がピン留め経路で取得でき、**本文を読める**
  2. トークン交換の **body 付き POST** がピン留め経路で送れ、**応答の本文を読める**
  3. 1・2 がいずれも SSRF 判定を通ったうえで行われる（判定を迂回する経路が無い）
- 別関門 `auth-2fa-org-enforcement` は aicue に実装済み
  (`RequireTwoFactorForEnforcedOrganizations`)。企業ログイン経由でも効く形を保つ。

## スコープ外

- **ソーシャル SSO の作り替え** (`auth-sso-social`)。既に AG-200 の形なので**変更しない**。
  本設計が触るのは「その形を機械で固定する gate を 1 本足す」ことだけである。
- **運営側 SSO** (`auth-admin-sso`)。
- **`acr_values` による認証強度の要求**。AG-200 が「強度を上げたい要件はこれで行う」と
  明記しているが、aicue に該当要件は無い（思考原則 2「今必要なものだけ作る」）。
- **SCIM / 自動デプロビジョニング**、および **IdP 側の停止に連動した既存セッションの即時失効**。
  入退社連動は「次回ログインができなくなる」までとする（効果もそこまでしか主張しない）。
- **IdP 起点のログイン (IdP-initiated SSO)**。RP 起点のみ。
- **接続を無効にした後の猶予窓**（spirux にだけ設定値があるが強制する仕組みは未実装で、
  正典の形ではない）。
- **`ssrf-pin` の版上げそのもの**（別 TODO）。
- **既存ログイン手段の削除・変更**（`EnsureLoginMethodRemains` の意味論は変えない）。
