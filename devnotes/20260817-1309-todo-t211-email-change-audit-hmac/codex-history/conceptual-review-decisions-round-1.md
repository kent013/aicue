# 概念設計レビュー Round 1 への対応マトリクス

Codex 判定: **APPROVED** (Critical 0 / Warning 3 / Suggestion 4)

| # | 分類 | 指摘 | 判断 | 対応内容 |
|---|---|---|---|---|
| 1 | Warning | `APP_KEY` 依存 (漏えい時の照合可能性・ローテート時の突合不能)。監査専用鍵への切り出しの判断材料が要る | **対応する** | 概念設計の「スコープ外」に**再評価の契機**を書き足した — 「`APP_KEY` のローテーション運用が具体化したとき」に監査専用鍵を再評価する。今回は実装を増やさない (裁定も任意の改善と位置づけている) |
| 2 | Warning | 「平文アドレスが現れない」を cast 後の配列だけで見ると不十分。DB に保存された JSON 文字列を見るべき | **対応する** | 詳細設計のテスト計画で `DB::table('security_audit_events')->value('metadata')` の**生の JSON 文字列**に対して局所部・ドメインの不在を検査する形に確定した。走査根が `app/` と `routes/` の目録 (`DirectFetchInventory`) には掛からない (テスト側のクエリであり主キー同一性でもない) ことを実読で確認済み |
| 3 | Warning | metadata の形が配列リテラルに埋もれると将来の崩れを PHPStan で拾えない。テストで exact shape を固定せよ | **対応する** | 詳細設計の受け入れ条件 A1/A2 を「キーは 2 つちょうど」「両方 64 桁 hex」「`EmailHash::compute()` の戻り値と一致」の 3 点に分けて機械検証可能な形で書いた。private helper / 定数化は**しない** (呼び出し 1 箇所のための間接層はオーバーエンジニアリング。指摘も「任意」としている) |
| 4 | Suggestion | 使命への寄与の位置づけ・実現可能性・効果の妥当性・スコープは妥当 | 反映不要 | 現行のまま |
