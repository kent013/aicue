# 対応マトリクス: design-review Round 1

## S2 [Critical] `claudeHooksInnerLimits()` がコメント・重複・囮の記述を実値として拾える
- 判断: 対応する
- 根拠: 指摘のとおり。`preg_match()` の最初の 1 件だけを見る形は「本文から実際の上限を取り出す」
  という主張を満たさない (コメントに正しい値を残して実行行を変数展開へ変えられる)。
- 対応内容: 抽出を `preg_match_all()` + **行全体の正準形** (`^…$` の複数行モードで、コメント行を
  候補にしない) へ変え、申告で必要な形は**ちょうど 1 件**、不要な形は**0 件**を要求する。
  重複行・同じ語彙を持つ別行は違反にする。docblock に「shell の制御フローは見ないので
  『実行時の上限を証明する』とは書かない」を明記した。

## S2 [Critical] S13c が S13 の比較ロジックを通っていない (負のコントロールになっていない)
- 判断: 対応する
- 根拠: 指摘のとおり。S13c が自前で比較していたので、S13 の比較を消しても S13c は緑のままだった。
- 対応内容: 関係判定を純関数 `claudeHooksInnerLimitRelationViolations(array $limits, int $harness): list<string>`
  へ抽出し、S13 と S13c の**両方が同じ関数を呼ぶ**形にした。

## S2 [Warning] 0 秒を有効な上限として受理する
- 判断: 対応する
- 根拠: `\d+` は 0 を通し、`-k 0` は KILL 猶予の保証を失わせるのに合計は小さくなる = 検査に有利に働く。
- 対応内容: 抽出後に**各値が正の整数であること**を検査し、0 以下を違反にした。

## S2 [Warning] shape の未知キー・余剰キーが fail-closed でない
- 判断: 対応する
- 根拠: 走査の母集団が黙って狭くなる形である。
- 対応内容: `array_key_exists()` を先に見て未知のスクリプトは違反として返し、
  S13 で**台帳のスクリプト集合と shape のキー集合の完全一致**を検査する。

## S2 / S6 [Warning] 「最悪 27 秒」は誇張 (前処理とプロセス起動時間を含まない)
- 判断: 対応する
- 根拠: 3 上限の和は「明示された待ちの合計」であって全体の最悪時間ではない。
  AGENTS.md 側にも同じ誇張が伝播していた。
- 対応内容: 文言を「**明示的に抽出する 3 上限の和は 27 秒で、配線の時間切れ 30 秒より小さい**」へ限定し、
  スクリプトのコメント・AGENTS.md・検査の docblock の 3 か所を同じ表現に揃えた
  (全体の最悪時間を保証する設計 = 前処理ごと内側 timeout で囲む形は、i8 が求めていないので採らない)。

## S2 [Warning] B18 の `< inner + 25 秒` は実測ゲートとして弱い
- 判断: 対応する
- 根拠: 20 秒設定で 40 秒かかっても通る。
- 対応内容: 上限を `body + kill + 5.0` 秒 (現行値で 27 秒) へ締めた。標準入力は即座に閉じる
  (テストが payload を渡す) ので待ちは乗らない。KILL 猶予の実効性そのものは非保証のまま明記する。

## S1 [Warning] 禁止トークン検査の負例が、その分岐を検証していない (規約 (c) と (e) 未達)
- 判断: 対応する
- 根拠: S06c の全ケースは正準形の不一致だけで赤になるので、語彙判定を削っても緑にならない。
  区切りトークンの 3 形 (接頭辞・打ち消し・接尾辞) も無かった。
- 対応内容: 語彙判定を別の純関数 `claudeHooksLauncherForbiddenTokens()` へ分離し、
  **語彙判定だけを直接検査する**テスト (S06e) を新設した。負例は `-c` / `if` / `exit` を含む形、
  正例は `xif` / `!if` / `ifx` を含むが違反にならないこと (トークン完全一致の裏取り)。
  正準形の判定と語彙の判定は別々に検査する。

## S3 [Suggestion] テストファーストの説明が不正確 (赤の理由が「純関数が無い」になっている)
- 判断: 対応する
- 根拠: 指摘のとおり。旧挙動との差を実証する順序に直すべき。
- 対応内容: 3 段の順序へ書き直した — (1) 現行挙動 (`hooks` 不在だけ) を純関数へ移して緑

## S5 [Suggestion] 文書は「構文エラー」より一般化して書く
- 判断: 対応する
- 根拠: 実際の意味論は「内側が 2 を返せば理由に関わらずブロック」である。

## S6 [Warning] i15 の「差分方式だから回収される」の根拠の所在と保証レベルが不明確
- 判断: 対応する
- 根拠: 差分方式であることだけでは自動的に導けない (除外規則・差分基準・索引状態の更新方法に依存)。
- 対応内容: 根拠を「`code-review-graph==2.3.7` の `update` が直前の索引時点からの差分を見る仕様」と
  明示し、**台帳テストでは機械検証していない外部ツール仕様上の前提**であることを書いた。
  併せて「索引ツールを更新したら人手で再確認する対象」に matcher の意味論だけでなく
  **この差分回収の前提**も加えた (AGENTS.md と検査の docblock)。統合テストは
  正典が文書化のみを要求しているため本件では持たない (思考原則 2)。

## S7 [Warning] D18 の見出しが「2 本のスクリプトを外部コマンド非依存」と読めるが実装と矛盾する
- 判断: 対応する
- 根拠: 索引更新 hook は契約上 `flock` / `timeout` / `code-review-graph` に依存する。
  外部コマンド非依存なのは bug-hunt 検問の判定だけである = 保証範囲の誇張。
- 対応内容: 見出しを「hook の起動子に特権モードを足し、bug-hunt 検問の判定を外部コマンド非依存で持つ」へ。
  本文の比較表も「検問の判定」と「索引更新の実装」を分けて書き直した。
