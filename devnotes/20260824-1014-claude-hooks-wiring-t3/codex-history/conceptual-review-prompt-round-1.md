## 使命 (North Star)

<!-- app-codex-review スキルはこのセクションをレビュー使命として参照する。 -->

**AI-CUE** は、現場に既にある**作業手順書(SOP)を起点に**、AI が撮るべきカットを設計した**動画シナリオ**を生成し、そのシナリオを**スマホ(PWA)でナビゲーション撮影**することで、専門知識ゼロの現場作業者でも**標準化されたマニュアル動画**を作れるようにする。

- 「思考ゼロ・編集ゼロ」— 台本作成・撮影判断・編集の 3 ハードルを AI とナビ撮影で肩代わりする。
- 競合(OJT を撮って形式化する tebiki)と異なり、**標準作業を起点に AI が教材設計し撮影を指示する**（撮影者・教える人のスキルに品質を依存させない）。
- 熟練者の暗黙知を動画マニュアルという形式知へ変換する装置（SECI）。

> 詳細な設計は本リポジトリの `doc/`（01〜10）に置く。ドメインをテンプレート構造へどうマップしたかは `doc/08`〜`doc/10`（特に `doc/10 §10.8` に設計レビュー反映済み）。
> **v1 スコープ**: 字幕のみ(TTS 後回し) / 撮影は PWA(同一オリジン・セッション認証) / 動画合成は自前 ffmpeg / 単一 Default Project。

## 禁止事項

1. テストなしの実装完了報告(不変条件は対応する Architecture/Feature テストへの登録まで含めて「実装済み」)
2. PHPStan エラーの widen(型を緩めて黙らせる)・baseline 化
3. dev DB への破壊操作(`migrate:fresh` 等)をエージェント判断で実行すること
4. `response()->json()` の直書き(DTO / JsonResource / Inertia を使う。仕様固定 endpoint のみ例外)
5. LLM 呼び出しの Prism 直呼び(`app/Prompts/` の factory → 窓口 (`PromptDefense`) →
   実行単位 (`GuardedPrompt`) の**1 本道のみ**。`PromptGuardrailTest` が
   app/ routes/ database/ config/ bootstrap/ の 5 走査根で検出する)。
   **実行経路を持つ prompt factory は `LlmCallContextData` を必須引数で受け、
   `PromptDefense::load()` へ渡して帰属 (organization / subject) を付ける** — 付け忘れは
   PHPStan level 10 が落とす。帰属の対象を持たない見本 (`ExampleSummaryPrompt`) だけが
   `PromptDefense::loadUnattributed()` を使え、窓口 gate が**この 1 件を名指しで pin** する。
   併せて `PromptUntrustedInputContractTest` の inventory へ**帰属キーを空配列で exempt 登録**する
   (deny-by-default なので exempt にする操作がレビューで必ず見える)。
   欠けると `llm_call_logs.metadata_missing` になり組織別・対象別の費用が出せない
6. prompt 文字列のコード直書き(`resources/prompts/*.yaml` に置く)
7. 操作系 POST の応答での `redirect()->intended()`(ログイン直後フロー専用。
   招待送信等は `back()->with(...)` で完結させる)
8. 必須条件未充足を理由にボタンを disabled にする UI(押下時にエラー表示する。DESIGN.md)
9. Artifact の使用(Artifact ツールでの成果物公開を行わない。成果物はリポジトリ内のファイルとして出力する)

【思考原則 — 全議論に適用】
まず仮説を立てろ。何を検証したいのか、なぜそう考えるのか、どうなれば成功と判断するのかを明確にしてから手を動かせ。仮説なき改善はただの試行錯誤であり、結果から学ぶことができない。

先人の知恵を探せ。自分たちだけで登る必要はない。乗るべき巨人の肩があるなら乗れ。

## 背景・課題

lctl 機能台帳 feature `claude-hooks-wiring` は 2026-08-22 に settle し、正典の版が **t3** で確定した
(feature_revision 30-341e19080a6f / ledger_revision 54dc1102 / design doc_sha f75752ce3010)。
aicue のセルは `status=update_pending` / `version=pre-t3` / `target_version=t3` で、
不足は台帳側の記述が 4 点 (i5 / i7 / i8 / i10)、本設計の実読で追加確認した不足が 2 点 (i14 / i15) である。

実読で裏を取った現状 (2026-08-24 / main b207bafa):

| 正典の不変条件 | 正典が要求する形 | aicue の現状 (実読) |
|---|---|---|
| i5 起動子は直呼び | `/bin/bash -p "$CLAUDE_PROJECT_DIR/scripts/<name>"` | `.claude/settings.json` の 2 本とも `/bin/bash -p -c '…'` のインライン形 |
| i7 起動子の純粋さ | 「スクリプトを起こす」以外の仕事を持たない | 起動前の 7 条件検証 + `if [ "$s" = 97 ]; then exit 2; fi` + 既定 `exit 0` を持つ。検査 S06b が逆に「3 役をすべて持つこと」として固定し、B41〜B50 が写像を実起動で pin している (**正典と真逆の向きに固定されている**) |
| i8 内側 < 外側 の数値比較 | 配線の timeout と起動先の内側上限を**両方から数値で取って比較**する | 比較する検査は 0 件。`INNER_TIMEOUT_SECONDS=20` は S11 の隣にも出てこず、B17 は `30.0` をテスト内に直書き |
| i10 設定 2 層の全数申告 | `settings.json` と `settings.local.json` の**両方**のトップレベルを全数申告し、ローカル層の申告に `hooks` を含めない | S03 は `settings.json` だけ。S07 はローカル層の `hooks` 不在だけを見て、他のトップレベル項目には沈黙 |

満たしている分 (i1 常設 / i2 必須 2 配線と `Write|Edit` / i3 照合条件の語彙 / i6 `-p` / i9 既定拒否の台帳 /
i11 配線文字列そのものの実起動 (B41〜B51) / i13 ファイル名) は動かさない。i4 (第 3 の配線) は任意であり、
本追従では**採らない** (採らないことも逸脱ではない)。i12 は独自の検査器を持つ実装にだけ課される条件で、
t3 追従後の突き合わせは構造の完全一致 1 本 + 台帳側の組み立て 1 行に閉じるため対象外である。

放置した場合の損失は 2 つある。(1) **家系 6 リポジトリで同じ規律が効く**という前提が崩れる

「起動子が写像器であること」を**積極的に固定している**ため、追従は検査の書き換えを伴い、
先延ばしすると差が固定化していく。

## 改善アイデア

**起動子を「スクリプトを起こすだけの 1 行」へ戻し、配線層の保証と非保証を検査側の台帳に集約する。**

1. 起動コマンド文字列を `/bin/bash -p "$CLAUDE_PROJECT_DIR/scripts/<name>"` の直呼び 1 行にする
   (i5 / i6 / i7)。起動前の 7 条件検証とインラインのシェル片を落とす。
2. 終了コードの写像を落とす帰結として、bug-hunt ガードの拒否コードを **97 → 2** (harness の拒否信号) に
   変える。これは `scripts/bughunt-worktree-hook.sh` の中身 = 隣接 feature (bug-hunt-exec-infra) の
   領分に触れるが、i7 の帰結として避けられない**従属変更**である。
3. 配線台帳検査 `ClaudeHooksWiringTest` の向きを正典側へ反転する。
   - S06b: 「3 役をすべて持つこと」→「直呼びであり、引数も条件分岐もインラインのシェル片も持たないこと」
   - B41〜B50: 「97 だけを 2 へ写し他を 0 に畳む」→「内側の終了コードがそのまま返ること」
   - B51 (`-p` の実証) と、設定の起動コマンド文字列そのものを起こす形 (i11) は正典に採られたので維持
4. i8: 配線の timeout (10 / 30) と起動先が自分で諦める内側の上限を**両方から数値で抽出して比較**する
   検査を新設する。B17 / B18 のテスト内直書き (`30.0` / `'20 秒'`) も台帳・スクリプト由来に直す。
5. i10: ローカル層のトップレベルを全数申告制にする (申告に `hooks` を含めない)。
6. i14 / i15: 塞がない脅威 3 点と、シェル経由の編集が次の `Write` / `Edit` で回収される根拠 +
   撤回規則を、**検査ファイルの台帳の傍ら**に書く (正本は 1 か所。AGENTS.md には写さず参照だけ置く)。
7. AGENTS.md の `CLAUDE_HOOKS_WIRING` マーカー区間を新しい契約へ書き換える
   (現行は「起動子は終了コードの写像器を兼ねる」「ブロックできるのは 97 だけ」と書いてあり、
   実装を変えると**文書が嘘になる**。S12a がマーカー区間の実在を固定しているので区間ごとは消せない)。
8. `docs/template-divergence.md` D18 を**縮小**し、`ClaudeHooksWiringTest.php` の採用時債務を
   逸脱の登録へ移す (下記「制約・前提」)。

### 保証の反転を明文で受け入れる

現行の写像器は「hook の 1 文字のタイプミスがセッションの Bash 操作を全滅させない」ための安全網であり、
D18 と T172 がその存在理由を明記している。**t3 はこの安全網を意図して捨てる**。
正典の理由は「写像は harness の唯一の制御信号を潰し、配線ミスと実行時の異常が区別できなくなる」ことで、
実際に家系では起動先が配線ミスを非 0 で知らせる設計が写像器のせいで 0 に畳まれた事例がある。

追従後は `scripts/bughunt-worktree-hook.sh` の構文エラー (bash が返す 2) が**そのまま Bash ツールの
ブロックになる**。この交換を受け入れる代わりに、次の 2 つを埋め合わせとして持つ (どちらも既存)。

- **着地前の検査**: 同じ検査ファイルの S09 が 2 本のスクリプトに `bash -n` をかける
  (構文エラーは main に着く前に赤くなる)
- **実挙動の検査**: B26〜B40b が実プロセスで拒否・通過の判定を実証する

## 期待効果

- 使命への貢献は間接である (開発の進め方の層)。効くのは「**現場作業者向けアプリの品質を守る規律が
  6 リポジトリで同じ形で効く**」という一点で、hook が止める操作 (bug-hunt の main 直叩き) と
  hook が回すもの (コード索引) はどちらも開発時のみの機構である。
- 具体の改善は 3 つ。(a) 配線ミスと実行時の異常が harness と人の両方から区別できるようになる。
  (b) ローカル層から常設配線を殺す経路と、未知のトップレベル項目が既定拒否になる。
  (c) 内側の上限と外側の timeout の**数値の関係**が壊れたことを機械が検出する
  (現状は文字列一致すら無い)。
- 台帳のセルが `update_pending (pre-t3)` → `implemented (t3)` になり、家系で t3 到達の 1 本目になる
  (正典 t3 の全数を満たす実装は現時点で家系に無い)。

### 乖離台帳 (D18) と採用時債務の決着

`docs/template-fingerprints.json` の母集合に本件の 5 パスが在る (実測)。

### その他の前提

- 実装は worktree 必須。着手前に `/app-todo-add` (概念設計 + 詳細設計が devnotes に揃っていることが条件)。
- 配線を変えても**新しいセッションを開始するまで反映されない** (設定はセッション開始時に 1 度だけ読まれる)。
