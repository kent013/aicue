## S1: REQUEST_CHANGES

[Warning] 禁止トークン検査の負例が、その分岐を実際には検証していません。

S06c の全ケースは、禁止トークン検査を丸ごと削除しても「正準形と不一致」という理由だけで赤になります。したがって `in_array($forbidden, $tokens, true)` の検出力が裏取りされておらず、走査器共通規約 (c) を満たしません。また、規約 (e) が求める接頭辞・打ち消し・接尾辞付きのケースもありません。

修正案:

- トークン分類を別の純関数へ分離するか、返却する違反メッセージを種別付きにする。
- `-c` や `if` について、禁止トークン違反が実際に含まれることを直接検査する。
- `xif` / `!if` / `ifx` のような3形が禁止トークンとして誤認されないことも固定する。
- コマンド全体としては正準形違反になることと、語彙判定の結果を分けて検査する。

[Warning] PostToolUse の pass-through テストから重要な値が後退しています。

現行 B50 は `2` と `127` を含みますが、変更後 B42 は `[0, 1, 3, 97]` だけです。「終了コードを一切畳まない」が契約なら、特に `2` と `127` を落とす理由はありません。

修正案: B42 を少なくとも `[0, 1, 2, 3, 97, 127]` にしてください。

[Warning] 「旧7条件の検証を撤去した」という説明に対し、`scripts` ディレクトリ自体が symlink のケースが消えています。

変更後 B45 は起動先ファイルの symlink は見ますが、既存 B48 の「`scripts` が symlink」を引き継いでいません。部分的な検証が将来復活しても検出できないため、説明より実証範囲が狭くなります。

修正案: `scripts` ディレクトリが symlink のケースも B45 に残してください。B45 の説明も「明示的に実証している非保証」に限定すると明確です。

[Suggestion] `CLAUDE_PROJECT_DIR` 未設定時の B44 はホストの `/scripts/bughunt-worktree-hook.sh` が存在しないことに依存します。少なくともその前提を明示的に検査すると、環境依存の不可解な失敗を避けられます。

## S2: REQUEST_CHANGES

[Critical] `claudeHooksInnerLimits()` はコメント・重複・囮の記述を実値として拾えます。

現在は `preg_match()` の最初の1件だけを見るため、例えばコメントに正しい値を残し、実行行を変数展開へ変えても通る可能性があります。

```bash
# read -r -N 1048576 -t 5 input
IFS= read -r -N 1048576 -t "${UNBOUNDED}" input
```

`timeout -k` についても同様です。これは「本文から実際の上限を取り出す」「解決できない形は fail-closed」という主張に反します。

修正案:

- `preg_match_all()` で候補数を取得し、必要な形は完全一致でちょうど1件、不要な形は0件と検査する。
- 行頭・行末を固定し、コメント行を候補にしない。
- `read`、定数宣言、`timeout` の実行行をそれぞれ正準形として検査する。
- 同じ語彙を持つ別行や重複があれば違反にする。
- shell の制御フローまでは保証しないなら、その限界を docblock に明記し、「実行時の上限を証明する」とは書かない。

[Critical] S13c は S13 の比較ロジックを検査していません。

S13c は自分で `toBeGreaterThanOrEqual(30)` を実行しているだけです。S13 本体から `toBeLessThan()` を削除したり、比較方向を逆にしたりしても S13c は緑のままです。「数値関係の負のコントロール」にはなっていません。

修正案: 関係判定を純関数へ抽出し、S13 と S13c の双方から同じ関数を呼んでください。

```php
/**
 * @param array{stdin: ?int, body: ?int, kill: ?int} $limits
 * @return list<string>
 */
function claudeHooksInnerLimitRelationViolations(array $limits, int $harness): array
```

S13c は変異値を渡し、この関数が違反を返すことを検査します。

[Warning] 0 秒を有効な上限として受理します。

`\d+` は `0` を受理します。GNU `timeout` では duration 0 が期待した時間制限にならない場合があり、`-k 0` も KILL 猶予の保証を失わせます。それでも合計値は小さくなるため、静的検査上は有利に働きます。

修正案: 抽出後に各申告値が正の整数であることを検査し、0 以下を違反にしてください。

[Warning] `CLAUDE_HOOKS_INNER_LIMIT_SHAPE[$script]` は未知のキーを fail-closed に処理していません。また、shape 側の余剰エントリも使われません。

修正案:

- `array_key_exists($script, CLAUDE_HOOKS_INNER_LIMIT_SHAPE)` を先に確認し、未知のスクリプトは違反として返す。
- 配線台帳から得たスクリプト集合と shape のキー集合を完全一致で比較する。

[Warning] 「最悪27秒」は保証範囲を誇張しています。

5 + 20 + 2 は明示された待機上限の和ですが、標準入力後から `timeout` 起動前までの処理時間やプロセス起動時間は含みません。したがって「必ず27秒以内」「必ず30秒より内側」とまでは証明できません。

修正案:

- 文言を「明示的な3上限の和は27秒で、配線 timeout 30秒より小さい」に限定する。
- 本当に全体の最悪時間を保証するなら、前処理を含む全体を別の内側 timeout で囲む設計が必要です。

[Warning] B18 の `< inner + 25秒` は実測ゲートとして弱すぎます。20秒の設定なのに40秒かかっても、固定メッセージさえ出れば通り得ます。

修正案: 抽出した stdin/body/kill の合計に、CI 揺らぎ用の明示的な小さい余裕を足した値で検査してください。KILL 猶予の実効性を主張しない方針なら、その点は引き続き非保証と明記して構いません。

## S6: REQUEST_CHANGES

[Warning] 「次の Write / Edit でシェル変更も回収される」が、i15 の中核的な根拠である一方、根拠の所在と保証レベルが明確ではありません。

差分方式であることだけでは、未索引の変更が必ず次回更新へ含まれることまで自動的には導けません。除外規則、差分基準、索引状態の更新方法にも依存します。

修正案:

- `code-review-graph==2.3.7` のどの実装・仕様を根拠にしているかを記録へ明示する。
- 「台帳テストでは機械検証していない外部ツール仕様上の前提」であることを書く。
- ツール更新時の再確認対象に matcher 意味論だけでなく、この差分回収の前提も含める。
- 可能なら、一度 Bash 相当の経路でファイルを変更した後、次の更新で索引へ反映される統合テストを別途持つ。ただし本件の正典が文書化のみを要求するなら必須とはしません。

[Warning] S2 の「最悪27秒」問題が、そのまま AGENTS.md の「内側の上限は配線の時間切れより小さい」という強い保証へ伝播しています。

修正案: S2 と同時に「明示的に抽出する3上限の和」に保証を限定してください。

## S7: REQUEST_CHANGES

[Warning] D18 の見出しが実装と矛盾しています。

> 2 本の hook スクリプトを外部コマンド非依存で持つ

`code-review-graph-update-hook.sh` は契約上も `flock`、`timeout`、`code-review-graph` に依存します。外部コマンド非依存なのは bug-hunt ガードの判定部分です。保証範囲を誇張しない規約に抵触します。

修正案: 例えば次のように限定してください。

> hook の起動子に特権モードを足し、bug-hunt 検問の判定を外部コマンド非依存で持つ

本文中も「2本のスクリプトが外部コマンド非依存」と読める表現がないか統一して確認してください。

[Warning] D50 は S13c を「数値関係の負例」として保証根拠に挙げていますが、現在の S13c は本番の比較ロジックを通っていません。

修正案: S2 で比較述語を共通化してから、この記述を維持してください。共通化しない場合は、D50 から検出力の主張を外す必要があります。
