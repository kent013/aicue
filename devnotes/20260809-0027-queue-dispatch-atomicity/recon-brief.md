## 設計で最初に決めるべき論点

config/queue.php の sync 接続に after_commit => true を入れるか否か。ここが前回見送りの実体で、入れないと tx 内 dispatch がテストレーンで即時インライン実行され AnalysisPipeline / RenderPipeline の startJob が自分のロック下で成立してしまう。入れる場合も Queue::fake が enqueueUsing を素通りする件 (BillingCustomerSynchronizerTest:49 の docblock が既に警告済み) と併せ、レーンごとの実行意味論を先に確定させる。次に AG-127 の除外対象 (低残高通知等) を先に線引きし、除外は『tx 外 dispatch のまま + 失敗を観測へ』であって afterCommit 温存ではない点を設計に明記する。

## 台帳が確定させた標準形

標準形 v1 の必須は AG-114 の確定 1・2 のみ。確定 1 = キュー投入を業務トランザクションの中で行い afterCommit 依存を廃す。到達基準は AG-126 で「適用除外ゼロ (残存 0 件 pin)」に確定、検出器は aigenba の目録型 (afterCommit()/DB::afterCommit/ShouldQueueAfterCommit/config の 4 種) を推奨形とする。確定 2 = 原子性の前提 (driver=database / キュー DB 接続が業務 DB と同一 / after_commit が偽) を起動時に fail-closed 検査する。検査項目は使っている機能に応じて選び根拠を docblock に書く (Bus::batch 不使用なら束台帳の検査は不要)。AG-127 で「付随的副作用 (通知等) の enqueue 失敗で業務 tx を巻き戻さない」を確定 1 の適用除外基準として明文化。専用機構 (outbox 表・経路一本化・所有権取得) は各リポジトリ任意の上積みで必須でない。

## リスク

最大のリスクは config/queue.php の sync 接続に after_commit => true を入れることの全レーン波及。これを入れないと tx 内 dispatch がテストで即時インライン実行され、RunManualRender / RunManualAnalysis が trigger の tx の内側で走って AnalysisPipeline / RenderPipeline の startJob (lockForUpdate + status===queued) が自分のロック下で成立し、finalize の terminal tx が外側 tx の savepoint 化する (前回見送りの理由そのもの)。入れた場合も Queue::fake は enqueueUsing を経由しないため afterCommit の解決を素通りする (tests/Feature/Billing/BillingCustomerSynchronizerTest.php:49 が既にこの落とし穴を docblock で警告している) — fake ベースのアサーションが偽グリーンになりうる。次に、既存の 4 契約と正面衝突する: BillingSyncDispatchInvariantTest の「必ず transaction 内から afterCommit で発火する (IV-3)」、BillingCustomerSynchronizer.php:22-24 の「tx の外で呼ぶと afterCommit が即時実行になり遅延保証が崩れるため禁止」、TicketBalanceLowNotificationTest:104 と AutoRechargeTriggerTest:76 の「rollback したら発火しない」pin。これらは削除でなく aigenba 方式の「反転 (旧主張・旧目的・新主張・新前提・前提を守る機構・反転根拠の 6 行 docblock)」で扱わないと、保護対象を消す変更と区別がつかなくなる。加えて StripeWebhookProcessor の 3 箇所を tx で括ると webhook 処理の tx が伸び、既存の冪等マシン (:129 の tx) と入れ子になる。BillingCustomerSynchronizer の afterCommit 撤去は Stripe への stale read 防止 (IV-3) が目的なので、tx 内 dispatch へ変えるとジョブが commit 前の値を読む窓が復活しうる — ジョブ側が organization を再取得する形かを確認しないと退行する。ProductionEnvGuard 相当の fail-fast を足すと bug-hunt / preflight など env の薄い起動経路が落ちる (aigenba が実際に踏んで probe env へ QUEUE_CONNECTION=database を足して回避した)。aicue には scripts/bug-hunt-shard.sh の別プロセス起動があるため同じ衝突を想定すること。

## 実装者への申し送り (台帳と実コードの食い違いを含む)

【台帳と実コードの食い違い 2 点】(1) 台帳の aicue note は「現状の事後回収 (投入待ちのまま 10 分進んでいないものを 5 分ごとに拾う) は維持してよい」と書くが、実装の拾い方は再投入ではない — RenderJobService::recoverStale (app/Services/Manual/RenderJobService.php:266) と AnalysisJobService::recoverStale (:171) は queued 閾値超過を failJob へ倒す (docblock 明記: 「dispatch 喪失。render は enqueue 時点で編集を止めるため短 SLA で fail させる」)。つまり dispatch 喪失は現状「予約解放 + 失敗表示 + ユーザーが再実行」であって自動前進しない。確定 1 を入れる価値は台帳の記述より大きい。(2) 台帳は aicue の ShouldQueueAfterCommit に一切触れていないが、app/Notifications/Billing/ の 6 クラスに実在する。spirux の家系申し送り (2) 「grep afterCommit は interface 名に一致しないので宣言的迂回が丸ごと見えない」が aicue にそのまま当たり、AG-126 の 0 件 pin の主たる対象はここになる。【実装者への申し送り】(a) AG-127 の除外基準を先に適用対象へ当てること。app/Actions/Inquiry/CreateInquiryAction.php:60-89 は既に try/catch + report で「通知 dispatch の失敗が受付を巻き込まない」形になっており除外の先例として使える。TicketLedgerService:426 の低残高通知も docs/architecture.md:743-744 が「配信保証は at-most-once、通知は補助チャネル、outbox 台帳は作らない」と明記済みで除外根拠が既に文書にある。除外は「tx 外 dispatch のまま + 失敗を観測へ」であって afterCommit の温存ではない点に注意。(b) 確定 2 の検査項目は AG-126 どおり「使っている機能に応じて選ぶ」。aicue は Bus::batch / Bus::chain が app/ に 0 件なので束台帳の検査は対象外とし、その根拠を guard の docblock に書く。config/queue.php の batching.database は env('DB_CONNECTION') 参照で既に既定 DB と一致している。(c) 検査は driver=database の 4 接続すべてを対象にすること。既定接続だけ見ると database-analysis / database-render / database-media が抜ける。(d) 目録の母集団は tests/Support/QueuedJobPopulation.php を必ず再利用する (同ファイル docblock が「2 実装に分かれると片方だけ更新される drift が起きる」と明記し、既存 2 gate が共用している)。(e) AGENTS.md の禁止事項 1 (不変条件は Architecture/Feature テストへの登録まで含めて実装済み) と思考原則 3 (後方互換の並走を残さない) から、afterCommit 系の記述は同じ PR で全撤去・全反転すること。
