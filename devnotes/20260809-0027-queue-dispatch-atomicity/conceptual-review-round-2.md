全体判定: **CHANGES_REQUESTED**

Round 1 の主要論点はかなり整理されています。ただし、`AutoRechargeTriggerJob` の unique lock 問題は、ネストされたトランザクション経路では解消していません。「内側の `DB::transaction()` を抜けた直後」と「全トランザクションの外」は同義ではないためです。

**1. 使命との整合性**

[Suggestion] 分析・レンダー等の必須ジョブを原子的に投入する方針は、手動再実行を減らし North Star に直接貢献します。

一方、AG-127 の判定基準を「cron 回収が存在するか」だけにすると、15分待ちを許容する機能が増え、結果的に「思考ゼロ」を後退させる可能性があります。少なくとも次の条件をすべて満たす場合に限定すべきです。

- 回収処理が本番で定期実行される運用契約を持つ
- 回収条件が dispatch 喪失状態を確実に包含する
- 永続状態遷移が結果の一回性を保証する
- 回収までの最大遅延が当該機能の SLA と整合する
- 取りこぼしと回収失敗が観測される
- 回収待ち中の状態がユーザー操作や課金を不当に阻害しない

この条件は exemption enum と premise test に落とせます。「cron があるか」ではなく「喪失を安全に回収できる契約が機械的に確認できるか」を基準にしてください。

**2. 禁止事項違反・不変条件**

[Critical] `AutoRechargeTriggerJob` の rollback 時 unique lock 残留は、ネスト経路で残っています。

`reserve()` の内側トランザクションを抜けても、呼び出し元の `AnalysisPipeline` / `RenderPipeline` の外側トランザクション内です。この時点で dispatch すると以下になります。

1. `PendingDispatch` が unique lock を取得
2. database queue の jobs 行は外側トランザクションへ参加
3. 外側 rollback で jobs 行は消える
4. unique lock は残る

つまり、今回の AG-127 移動だけでは Round 1 の Critical は閉じません。

修正提案: 次のいずれかを設計として選び、ネスト経路の behavioral test を追加してください。

- `DB::transactionLevel() > 0` なら即時 dispatch を行わず、reconcile に委ねる
- 最外層の呼び出し元まで dispatch intent を返し、全トランザクション終了後に dispatch する
- `ShouldBeUnique` を外し、既存の org lock・pending 検査・partial unique を結果の一回性の正本にする

最小変更は1つ目ですが、ネスト経路では最大15分遅れるため、その SLA を明示する必要があります。

[Warning] 低残高通知についても、「organizations 行ロックの保持時間が伸びない」はネスト経路では成立しません。外側トランザクションが保持しているロックの最中に通知 INSERT が走ります。

修正提案: 記述を「最外層の `reserve()` では伸びない。ネスト時は外側トランザクションのロック保持中に実行される」に訂正してください。また、PostgreSQL で通知 INSERT が失敗すると、`safely()` が例外を捕捉しても外側トランザクションが abort 状態になり得ることを behavioral test で固定してください。

**3. 実現可能性**

[Warning] `sync.after_commit=true` 自体の結論は、提示された vendor 実測に照らして妥当です。ただし R-10 は単なる「保証しないもの」ではなく、テスト・dev で業務クロージャが再実行され得る動作リスクです。

修正提案: sync job が concurrency exception 相当を投げた場合に、業務クロージャが二度実行されるかを vendor バージョン固定のテストで実測してください。再実行されるなら、テスト用 sync レーンで副作用を伴う job を動かす設計を受容するだけでは不十分で、少なくとも対象ジョブの永続ガードが再実行に耐えることを確認対象に含めるべきです。

**4. 期待効果**

[Warning] §9 の「6本消える」は、列挙経路との対応が曖昧です。背景表にはそれ以上の経路があり、AG-127 除外や reconcile 保有経路も混ざっています。

修正提案: 6本を名称で列挙し、「commit済み・未投入の窓を除去」「reconcileまで残る」「at-most-onceとして受容」の3分類に対応させてください。件数表現のドリフトも Architecture test または設計上の正本で防げます。

**5. リスク**

[Critical] R-6 の「除外にすることで回避済み」は現状では誤りです。前述のとおり、ネストされた外側トランザクションの rollback では再現します。

修正提案: R-6 を「最外層では回避、ネスト時は未解決」に戻し、解決方式を確定してから「回避済み」としてください。

[Warning] §8 の `ShouldBeUnique` 項目も一般論のままで、今回対象の trigger job について解決済みなのか未解決なのかが矛盾しています。

修正提案: 一般的な非保証と、`AutoRechargeTriggerJob` に採用する具体策を分離してください。

**6. スコープ**

[Suggestion] 分割しない判断の根拠は成立しています。0件 pin、既存契約の反転、旧実装撤去を同一PRにまとめることには一貫性があります。

ただし §11-2 の順序は、M1の設定変更をテストより先に置くよう読めます。各施策について「テスト追加・赤化確認 → 実装」の順に書き換えてください。PRを分ける必要はありません。

**7. 検査が空振りしない保証**

[Warning] 検出器単体の負のコントロールは改善されていますが、走査母集団から一部ファイルが脱落する故障は検出できません。母集団が1件以上あれば通るため、特定ディレクトリや特定クラスだけ欠落しても0件 pinは緑です。

修正提案:

- 一時 fixture ツリーにD1/D2対象ファイルを置き、「列挙→読み込み→検出」の統合経路を通す
- D3もダミークラスを判定器へ直接渡すだけでなく、母集団発見から検出まで通す
- production母集団について、既存の独立した inventory が完全性を保証しているなら、その契約を明記して対応テストを参照する
- D4は runtime config 判定だけでなく、`sync` だけが `true` を許されることを全接続集合で検証する

これで「検出関数は生きているが、実ファイルが渡されていない」偽グリーンまで閉じられます。

**8. 型安全性**

[Suggestion] `mixed` から `is_array` / `is_string` / `is_bool` で狭め、違反DTO相当の明確な型へ変換する方針なら PHPStan level 10 は実現可能です。violations を素の連想配列で回すより、既存流儀が許せば小さな value object または明示的なarray shapeを使う方が、接続名・規則ID・実値の型を保ちやすくなります。
