## 全体判定: CHANGES_REQUESTED

v3 の目的・実測・実ドリフトを同一変更で是正する方針は妥当です。ただし、逆走査の検出力を不変に保つための「除外」と「派生扱い」に、現状では静かな見逃しを許す穴があります。

### 1. 使命との整合性

[Suggestion] 承認方向です。画面・撮影導線・CLI の値集合ずれを早期に検出するため、North Star の「撮影判断を標準化する」品質基盤に本質的に寄与します。特に既存の `ApiErrorCode` ドリフトを見つけた実測は、期待効果の根拠として強いです。

### 2. 禁止事項・gate 規約

[Critical] 決着 1 の除外根が広すぎます。「見本置き場だけを除く」と説明しつつ、除外対象は `tests/js/support/enum-ts-sync/` 配下全体です。この配下には将来、正常な検査器コードや有効な候補が置かれ得るため、i8 の全数走査に対する静かな見逃しになります。

修正案: 除外は `fixtures/candidates-broken/broken.ts` のような、意図的に構文破壊された見本ファイルの明示的・最小の集合に限定してください。除外リストの実在・重複・件数 pin に加え、「除外先に正常な候補を書いても母集団から消えるため赤になる」負の対照を置くべきです。可能なら、除外対象は構文破壊見本専用ディレクトリに限定し、通常コードを置けない命名・配置にします。

[Critical] 決着 2 の「束縛先の型が必ず候補になる」という根拠は、まだ検査で保証されていません。例えば束縛先が import された型、`keyof`、条件型、mapped type、別の有限型の合成、候補抽出の4形に該当しない型だった場合、対応表を除外しても代替候補が存在せず、検出力が落ちます。

修正案: 対応表を派生として除外する条件に、「TypeChecker 上で解決した束縛先の値集合と同一の、追跡対象内・非除外・候補化済みの宣言を一意に参照できる」を追加してください。その参照先の候補 ID と値集合一致を検査・保持し、満たせない場合は候補として残す fail-closed 設計にしてください。`Record<string, …>` を除くだけでは不十分です。

[Warning] 実測用 `probe` の結果を、本番 gate の負の対照・故障注入へ移植する責務を明示したほうがよいです。i12 は測定記録ではなく、継続的に赤くなる検査を要求します。

修正案: 少なくとも「除外根を空にする／広げる」「派生除外判定を常に true にする」「全 tracked files の列挙を空にする」「免除適用前 stale 判定を外す」を故障注入し、それぞれが赤くなるテストを追加してください。

### 3. 実現可能性

[Warning] Laravel 12 / Svelte 5 / Inertia の制約とは衝突しません。ただし `.svelte` を仮想 TS 化する箇所は、実装の難所です。instance script と module script、`lang="ts"` の有無、複数 script、import 解決、元ファイルの行・列対応、読み取り不能・構文不正時の fail-closed を詳細設計で固定しないと、i6・i13・i14 が空文化します。

修正案: 仮想ファイルのパス規則、script ごとの合成規則、行・列の保存方式、対応できない script 属性を不合格にする条件を決め、各ケースの正例・負例を置いてください。

### 4. 期待効果の妥当性

[Suggestion] 妥当です。候補数の増加ではなく、実際に未検出ドリフトを1件発見し、誤検出の規模も把握している点がよいです。「10件未満」は将来保証ではなく、この時点の観測値として記載し続けるのが適切です。

[Warning] `ApiErrorCode` の修正は、単なる型名の分割では終われません。CLI の API 応答処理、未知コードの扱い、利用者に返すエラー表現まで、サーバ enum を正本とする契約が一貫している必要があります。

修正案: サーバ写し・CLI 固有コード・合成公開型それぞれの用途を明示し、既存の CLI テストでサーバ固有値、CLI 固有値、未知値の各処理を固定してください。

### 5. リスク

[Critical] 決着 3 の「メッセージの語を保持して既存テストを触らない」は脆いです。`resources/js/ 配下だけ` が現在の受理範囲・走査範囲を表す診断文に残るなら、i13/i15 の要求する正確な失敗案内と矛盾します。指紋・採用時債務の都合を、検査の正しい仕様より優先してはいけません。

修正案: その語が実際の失敗メッセージではなく既存負例の入力であることを明確化し、利用者へ出る診断は v3 の実態に更新してください。もしテスト本体の変更が不可避なら、提示された退避路どおり template divergence への意図的逸脱登録と adoption debt からの除去を同じ変更で行うべきです。

[Warning] 「登録済み型で束縛された分岐」を申告する #5 は、将来 enum 値が追加されたときに UI の既定枝へ落ち続ける可能性があります。これは gate 上は申告されても、業務上は表示・操作の欠損になり得ます。

修正案: 既定枝を持つことだけで恒久申告にせず、分岐が全値を意図的に扱わない理由、既定枝のユーザー影響、追加値時の期待動作を申告理由に含めてください。

### 6. スコープの適切さ

[Suggestion] PHP 側の発見器を触らず、逆走査の不足分に集中している点は適切です。#1 の実ドリフトと #2/#3 の事実に反する分類理由を同一変更で是正することも、gate 導入で露見した現物不整合への必要最小限の追従です。

[Warning] `AGENTS.md` と `docs/architecture.md` の更新は、実装後の仕様に限って行うべきです。正典の文言を重複転載して二重の正本を作らないよう注意が必要です。

修正案: アプリ固有の受理形・除外集合・保証外だけを記録し、正典 v3 自体は参照先と版で指す形にしてください。

### 7. 型安全性・規則 2b の設計穴

[Warning] DTO / JsonResource は対象外であり、PHPStan level 10 への直接的な影響も限定的です。一方、TypeScript 側は Program + TypeChecker を唯一の意味論として扱う必要があります。構文だけで `Record` や `satisfies` を判定すると、型エイリアス越しで誤分類します。

修正案: 派生判定・値集合抽出・必須プロパティ判定のすべてを TypeChecker の解決結果で行い、型解決不能は候補除外ではなく gate 失敗にしてください。

[Warning] 規則 2b は概念として十分ですが、以下は詳細設計に入る前に決める必要があります。

- トークン分割規則: camelCase、PascalCase、数字、略語、`_`、`-`、複数形・語尾変化をどう正規化するか。
- 「頭の名詞」の定義: 先頭語か末尾語か。実測の `DashboardJobStatus` では `head=statu` とあり、用語と挙動の整合が必要です。
- 閾値: `ceil(|A| / 2)` と `ceil(|B| / 2)` の両方を満たすのか、重複値を集合化するのか、空集合をどう扱うのか。
- 名前を持たない候補: switch 分岐では何を比較名にするか。式・変数名が取得不能なら fail-closed にするか。
- 2a/2b の判定理由: 両方に該当する場合も、どの規則・どの語・どの値交差で鳴ったかを診断に残すこと。

これらを定義し、接頭辞・打消し・接尾辞を含む負例と、意図した一致の正例で固定すれば、AGENTS.md の (b)(c)(e) と i10〜i13 に整合します。
