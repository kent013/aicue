# 対応マトリクス: design-review Round 4

すべて「対応する」。Critical 2 件はどちらも locator の詰めである。

## [Critical] S4: `occurrence` を割り当てる母集団が曖昧 (三値ごとに採番すると衝突・ずれが起きる)
- 判断: 対応する
- 根拠: 指摘のとおり。候補だけを採番すると「同名で片方が判定保留・片方が候補」のときに
  どちらも `occurrence: 0` になり、非候補を採番から外すと分類が変わっただけで番号が動く。
- 対応内容: **採番 → 分類の順**へ確定した。
  1. `enumerateDeclarationSites` が**構文上の宣言の場所**を数え上げる
     (型別名の全宣言 / 包みを剥がして該当する形になる全変数宣言 / 全 `switch` 文)。三値の判定はまだしない
  2. `(file, shape, name)` ごとにソース位置の順で `occurrence` を振る (`locatorOf`)
  3. そのあと各場所を `candidate` / `not-a-catalogue` / `indeterminate` へ分類する
  候補・判定保留・非候補は**同じ採番空間を共有する**。
  負例に「判定保留が先・候補が後」「非候補が先・候補が後」「片方の申告が他方へ効かない」を足した。

## [Critical] S7/S8: 目録の行から locator をどう解決するかが未定義
- 判断: 対応する
- 根拠: 指摘のとおり。行が持つのは `ts + declaration` だけで `shape` と `occurrence` が無く、
  同名の入れ子が最上位より前にあると最上位でも `occurrence` は 0 とは限らない。
- 対応内容: **前向きの解決の時点で AST から locator を計算する**形にした。
  `ResolvedEnumTsRelation { entry, tsLocator, phpValues, tsValues }` を導入し、
  処理の順序 (最上位から受理できる宣言をちょうど 1 つ解決 → **S4 と同じ採番器**で locator を求める →
  `declaredTsLocators()` は解決済みの関係から作る → 逆走査は locator 完全一致だけを外す) を明記した。
  **採番器を S4 と S7 で別に持たない**ことも書いた (正典 i4 と同じ理由)。
  必須の負例 (入れ子が先・最上位が後 / 登録は最上位だけ / 入れ子候補は逆走査に残る) を足した。
  S8 にも「locator は 1 本の採番器だけが作り、候補・判定保留・解決済みの関係・申告・stale・
  重複・診断がすべて同じ採番空間を使う」と書いた。
