## 全体判定: CHANGES_REQUESTED

Round 1 の Critical 3件への対応方針は妥当です。ただし、新しい「証人」方式に循環除外の穴があり、規則2の名前解決不能時も fail-closed になっていません。また、再測定値に算術上の不整合があります。

### 1. 使命との整合性

[Suggestion] 問題ありません。実ドリフトの是正まで含め、UI・CLI の無言の分岐欠損を防ぐ改善として North Star に整合しています。

### 2. 禁止事項・gate 共通規約

[Critical] 「証人」が別の派生対応表でもよい設計だと、対応表同士が互いを証人にして全件除外される可能性があります。

例えば同じキー集合を持つ型付き対応表 A/B があり、独立した型別名等が候補に存在しない場合、A が B を、B が A を証人として除外できてしまいます。自分自身を証人にする経路も、明示的に禁止されていません。

修正案:

- 自分自身は証人にできない。
- 「派生除外の対象になり得る対応表」は証人にできない。
- 証人は最終候補集合に必ず残る候補に限定する。
- 除外判定を相互参照可能な一括判定にせず、非派生候補を種にした単調な到達判定にする。
- 「自己証人」「2対応表の相互証人」「3件の循環証人」を負例に追加する。

最も単純なのは、証人をリテラル型合併・定数配列・分岐ラベルなど、対応表キー以外の候補に限定することです。

[Critical] 名前を持たない候補について、「候補に残すが名前対応を不成立にする」は fail-closed ではありません。完全一致しない真の部分写しは規則1に該当せず、規則2も名前不成立となり、無言で通過します。

修正案: 型名も式名も解決できない候補は、規則2の対象から静かに外さず「名前解決不能」という解析失敗として gate を赤くしてください。保証範囲外とするなら、i9 の分岐ラベル全体を扱うという主張を明示的に狭める必要がありますが、v3 追従では前者が適切です。

### 3. 実現可能性

[Warning] `.svelte` の複数 script は、単純に1本の仮想 TS へ連結すると module script と instance script の別スコープが混ざり、重複宣言や名前解決に偽の結果が出ます。

修正案: 詳細設計の成功条件に「module/instance のスコープ分離を維持する」を追加してください。別仮想ファイルにするか、意味論を保持できる変換方式にする必要があります。行番号だけでなく、診断位置を元 `.svelte` に逆写像できることも固定対象です。

### 4. 期待効果の妥当性

[Warning] 再測定値と期待効果の数値が一致していません。

- 再測定の母集団は `378 + 130 = 508` 本ですが、期待効果には旧値の `478` 本が残っています。
- 候補内訳は `106 + 110 + 13 + 22 = 251` 件であり、記載された `301` 件になりません。
- 旧値の `199` 件も期待効果に残っています。
- `301 - 251 = 50` は `witnessless returned to candidates=50` と一致するため、50件を総数へ二重加算したか、`object-keys` の出力件数が誤っている可能性があります。
- program 構築時間も本文の `3.6秒`、改善アイデアの `3.9秒`、ログの `2774ms` で揺れています。

修正案: 集計式を probe 内で一元化し、`total === 各形の合計` を assertion にしてください。そのうえで再測定値へ全文を同期してください。現状のログは内部的に成立しないため、301件を母数とした評価は根拠に使えません。

### 5. リスク

[Warning] #5 の申告が enum 値追加時に「自動的に stale になる」という主張は、申告の同一性に規則番号を含む場合にしか成立しません。同じ PHP/TS 候補対が規則1から規則2aへ移るだけなら、候補自体は生存しており、申告も生き続ける設計になり得ます。

修正案: 申告の identity に適用規則を含めるか、申告時に `expectedRule` と期待する値関係を pin してください。規則1から2aへの遷移で実際に赤くなる負例も追加してください。「詳細設計で確認する」までは、自動 stale を確定効果として記述しないほうが安全です。

### 6. スコープの適切さ

[Suggestion] 適切です。実ドリフト、誤った分類理由、台帳の整合を同じ変更で扱うことは、gate を正しく着地させるための直接的な作業です。D50 への移行も、診断の正確性を優先する順序になっています。

[Suggestion] スコープ外に「`.svelte` への値集合の直書きを禁止する」が重複しているため、片方を削除してください。

### 7. 型安全性

[Suggestion] TypeChecker の解決結果を使い、型解決不能時に派生除外しない方針は適切です。DTO / JsonResource への影響もありません。

[Warning] 「必須プロパティが存在する」だけでは、型検査が対応表の過不足を確実に落とすことの証明としては少し弱いです。交差型や union、特殊な mapped type では、取得したプロパティ集合と代入検査の意味が一致しない場合があります。

修正案: 少なくとも正例・負例に、型エイリアス越しの `Record`、`Partial`、union、intersection、`keyof`、import 型、`satisfies` を含めてください。判定不能な型は候補へ戻すという原則は維持してください。

以上のうち、証人の循環防止、名前解決不能時の扱い、測定値の整合が解消されれば、概念設計として APPROVED に進めます。
