全体判定: **CHANGES_REQUESTED**

1. 使命との整合性

- [Suggestion] 本件は製品機能を直接増やすものではないが、PWA 撮影を含む顧客導線の未検査を「検査済み」と誤認しないための品質基盤として、North Star に間接的かつ妥当に貢献します。`AcceptInvitationInAppController` と `SessionStatusController` を対象外へ逃がさない判断は、特に使命と整合します。

2. 禁止事項違反

- [Suggestion] 提案範囲には禁止事項への抵触は見当たりません。製品コードの LLM、HTTP 応答、UI、DB、Artifact は対象外です。
- [Suggestion] Python 検証器を追加する場合も、「文書・データの検証」という役割に閉じ、製品実行経路へ混入させないことを明記すると境界がより明確です。

3. 実現可能性

- [Warning] `out-of-scope.json` の検証契約がまだ不足しています。「実在パス接頭辞」の確認だけでは、空配列、重複 ID、重複・包含関係にある prefix、`app/` 外、意図しない広すぎる prefix、代替検証が実在しない記述を防げません。

  修正提案: 詳細設計で少なくとも以下を fail-closed の契約として固定してください。

  - `id` の一意性、必須キー、未知キーの扱い
  - `title`、`reason`、`alternative_verification` の空白禁止と最低限の内容要件
  - `path_prefixes` は空でない配列、`app/` 配下の実在ディレクトリまたはファイルのみ
  - prefix の重複・包含を禁止するか、許容時の明示的な理由を持たせるか
  - `alternative_verification` は単なる説明ではなく、既存テスト・検査・文書への追跡可能な参照を含むこと
  - JSON の UTF-8、配列トップレベル、安定した出力順序

- [Suggestion] Laravel 12 / Svelte 5 / Inertia.js との技術的な相性問題はありません。既存の PHP self-test から標準ライブラリのみの Python テストを起動する案も妥当です。

4. 期待効果の妥当性

- [Warning] 「未到達 46 を毎回散文で言い直す必要がなくなる」は、そのままでは過大です。対象外宣言は未到達コードの理由を恒久化しますが、走行ごとの未到達件数・新規未到達・対象外ではない穴の確認自体は依然として必要です。

  修正提案: 期待効果を「既知の設計上の対象外について、理由と代替検証を再記述せず参照できる。新規・未宣言の未到達を穴として識別しやすくする」に限定してください。

- [Suggestion] `merge_pcov.py` へ選別機能を入れない判断は現時点では妥当です。まず宣言と検証器が機能することを確認してから、走行レポートとの統合を別仮説として扱うべきです。

5. リスク

- [Critical] この設計の最大リスクは、対象外宣言が「未到達を正当化する台帳」へ変質することです。`reason` と自由文の `alternative_verification` だけでは、代替検証が対象コードを本当に守っているか、prefix 拡張が偶発的に顧客導線を覆っていないかを検出できません。

  修正提案: 各宣言に、代替検証の具体的な根拠を機械的またはレビュー可能な形で持たせてください。例えば `verification_references` として既存テストファイル、Architecture テスト、公式に管理された検証コマンド、または根拠文書への相対パスを列挙し、全参照先の実在を検証します。テストの意味的十分性までは自動保証できないため、監査文書には「存在確認はするが、代替検証の妥当性はレビュー対象である」と保証範囲を明記すべきです。

- [Warning] 「1件 = 1面」の“面”が未定義です。サービス境界、コントローラ群、認証外部連携、Filament のような分類単位が混在すると、将来の追加者が粒度を揃えられません。

  修正提案: 面を「同一の、ブラウザ走行で検査できない理由と代替検証を共有する `app/` 内コード群」と定義し、prefix が複数必要な場合の条件も定めてください。

6. スコープの適切さ

- [Suggestion] 正典 t1 に沿って「集計器は現状維持」「対象外の理由と代替検証だけをデータ化」とする範囲は適切です。aigenba やテンプレートの 400〜1300 行の PHP Architecture 検査を移植しない判断も、既存の Python 自己テストと PHP 配線テストで必要な不変条件を表現できる限り、過剰実装を避ける選択として妥当です。
- [Warning] ただし「参照実装を持ち込まない」こと自体は根拠になりません。必要な不変条件が Python 検証器で何であり、既存の `BughuntCoverageToolSelfTest` が何を起動・失敗検出するのかを詳細設計とテストケースで対応付ける必要があります。

  修正提案: 参照実装の行数比較ではなく、「本リポジトリで必要な不変条件一覧」と各テストの対応表を短く作成してください。未採用の検査は、対象外である理由を一文で残せば十分です。

7. 型安全性

- [Suggestion] 製品 PHP の DTO / JsonResource 境界は本件に直接関係しません。PHP の変更が既存 Architecture テストのモジュール列挙だけなら、PHPStan level 10 への影響は限定的です。
- [Warning] Python データ契約は PHPStan の対象外なので、型安全性を「JSON を読めた」だけで済ませない必要があります。

  修正提案: Python 側で JSON 値を `dict` のまま無秩序に扱わず、標準ライブラリの `dataclass` 等で検証済みの宣言モデルへ変換してください。境界で型・必須値・パス制約を確定させ、以後の処理は検証済みモデルだけを受け取る構造にしてください。

結論として、二つの台帳を「route の操作到達」と「`app/` のコード到達」で分ける設計判断、未到達の顧客 UX を対象外化しない判断、集計器を変えない判断はいずれも良好です。一方で、対象外宣言のスキーマ・代替検証の追跡可能性・prefix の重複規則が未確定のままでは、監査の中心目的を機械的に守れません。そこを詳細設計とテストファーストで固定できれば、承認可能です。
