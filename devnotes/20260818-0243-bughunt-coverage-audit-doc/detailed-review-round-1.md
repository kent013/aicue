## 全体判定: CHANGES_REQUESTED

仮説は妥当です。t1 の範囲を「集計器は変更せず、対象外の理由と代替検証だけをデータ化」に限定する方針は、二重管理と過剰実装を避けています。

ただし、現状は以下が成立していません。

- CLI の負のテストに必要な入力インターフェースがない
- パス検証を迂回できる
- 監査文書とテスト 17 が自己矛盾している
- 既存 README の説明が新しい監査文書と明確に食い違う
- pcov について、古い未検証の断定を別の未検証の断定へ置き換えようとしている

提供されたテキストのみを対象にレビューしています。コマンド実行・ファイル書き込みは行っていません。

## 施策 1: 対象外宣言の新設

**判定: REQUEST_CHANGES**

[Critical] パスの字句正規化とリポジトリ境界の契約が不足しています。

たとえば `app/../tests` は先頭が `app` で、`repo_root / value` も実在し得ます。単純な先頭セグメント検査と `exists()` だけでは、`app/` 外のパスを対象として登録でき、循環参照検査も迂回できます。絶対パス、`..`、`.`、バックスラッシュ、連続区切り、末尾スラッシュ、シンボリックリンクも未定義です。

修正案:

- JSON 上のパスを canonical な POSIX 相対パスに限定する
- 絶対パス、空要素、`.`、`..`、`\` を拒否する
- `resolve()` 後も `repo_root` 配下、`path_prefixes` はさらに `repo_root/app` 配下であることを確認する
- シンボリックリンクを拒否するか、解決先もリポジトリ内であることを契約化する
- 同じ正規化関数を実在検査、循環検査、包含検査、`covers()` で共用する

[Warning] 「追跡下に実在する」と「`exists()` で検査する」が一致していません。

実在だけなら、未追跡の一時ファイルや生成物も代替検証として通ります。

修正案: `git ls-files` の結果を追跡ファイル集合として読み、ファイルは完全一致、ディレクトリはその配下に追跡ファイルが最低 1 本あることを検査してください。そこまで行わないなら、スキーマの表現を「リポジトリ内に実在する」へ弱め、追跡下という保証を削除すべきです。

[Warning] `covers()` が単一の `OutOfScopeEntry` を返すのに、面を跨いだ重複・包含関係が明示的に禁止されていません。

別 entry に `app/Foo` と `app/Foo/Bar` があれば、結果が `entries` の順序に依存します。

修正案: `path_prefixes` は宣言全体で重複禁止かつ antichain とし、同一 entry 内だけでなく全 entry の直積で包含関係を拒否してください。

[Warning] 詳細設計の中心である `reason` と `alternative_verification` の初期値が、6 面すべてについて提示されていません。

これらの意味的十分性は機械ではなく人がレビューする設計なので、詳細設計段階で省略すると、最も重要な部分をレビューできません。また `machine-interface` は MCP、REST API、OAuth 認可をまとめていますが、「理由か代替検証が違えば別の面」という定義と衝突する可能性があります。

修正案: 6 件すべての完成形 JSON、少なくとも理由・代替検証の全文を提示してください。各 `path_prefix` が同じ理由と代替検証を共有することを確認し、違う場合は面を分割してください。

[Warning] 無内容判定が既存の route 対象外宣言より弱いです。

`対象外です`、`別テストで確認` のような値は拒否集合に完全一致せず通ります。既存の `annotations.toml` は理由を 30 文字以上にしています。

修正案: 少なくとも `reason` は既存規約と同じ trim 後 30 文字以上に揃えてください。`alternative_verification` は `verification_refs` があるため同じ閾値を必須にするかは選べますが、短すぎる説明をどう扱うかは明文化が必要です。

## 施策 2: 読み取り器・検証器・出力器

**判定: REQUEST_CHANGES**

[Critical] CLI に宣言ファイルと `repo_root` を差し替える引数がありません。

公開 CLI は `--emit` しか定義されていない一方、テスト 15 は「不正な宣言を渡す」としています。現状の設計では、実ファイルを変更せず一時ディレクトリの不正宣言を CLI に渡せません。

修正案:

```text
--declaration PATH
--repo-root PATH
--emit {markdown,json}
```

を定義してください。`--declaration` は隣接する `out-of-scope.json`、`--repo-root` はリポジトリルートを既定値とし、テストでは両方を明示して一時データを渡します。

[Warning] 既定のルート算出は添字まで固定しないと off-by-one が起きやすい設計です。

対象ファイルからなら `Path(__file__).resolve().parents[4]` がリポジトリルートです。

修正案: 算出式を設計に明記し、実宣言を引数省略で読める正のテストと、誤ったルートでは落ちる負のテストを追加してください。

[Warning] Markdown 出力に値のエスケープ契約がありません。

理由や代替検証に `|` や改行が入ると表が壊れます。

修正案: セル内の `|` と改行の正規化方法を決め、特殊文字を含む fixture で表構造が壊れないことを検査してください。JSON は UTF-8、末尾改行、キー順または意味比較のどれを安定契約にするかも明記するとよいです。

## 施策 3: 自己テスト

**判定: REQUEST_CHANGES**

[Critical] テスト 17 は提案された監査文書自身を必ず落とします。

「表の区切り行が現れない」とありますが、監査文書には「対象外の正本は 2 本ある」という Markdown 表があり、区切り行を持ちます。

修正案: 一般的な表区切りを禁止せず、対象外一覧固有の複製だけを検出してください。たとえば以下です。

- 宣言から読み取った `id` と `path_prefixes` が監査文書に現れない
- 対象外一覧固有のヘッダー組み合わせが現れない
- 必要なら `title` の全件列挙も禁止する

宣言を読み取って複製を検出することは、この用途では自己参照による空振りではありません。宣言と文書を同時に更新しても複製を検知できるからです。

[Critical] スキーマの型契約とパス境界の負の対照が不足しています。

必須キー欠落だけでは、トップレベルが配列、`entries` が object、各文字列フィールドが数値、配列要素が非文字列、といった入力を十分に検査できません。

修正案: 最低限、以下を追加してください。

- トップレベルと各フィールドの型違反
- 空白だけの文字列
- 重複した `verification_refs` / `path_prefixes`
- entry を跨ぐ完全重複・包含関係
- 絶対パス、`.`、`..`、バックスラッシュ、リポジトリ外への逸脱
- canonical でないが実在するパス
- `covers()` に対する同じ canonical-path 契約

[Warning] `DeclarationError` へ変換すると宣言した入力障害に、直接対応するテストがありません。

修正案: 少なくとも不存在ファイル、不正 UTF-8、壊れた JSON、過剰にネストした JSONを検査し、`DeclarationError` または CLI の exit 2 へ必ず収束することを確認してください。権限エラーは実行ユーザー依存なので、移植性を考慮して無理に fixture 化しなくて構いません。

[Warning] CLI 正常系は終了コードしか見ていません。

出力器が空文字列を返してもテスト 14 は通り得ます。

修正案: JSON は parse 後に期待する正規化データと比較し、Markdown は全 entry の `title`、`reason`、`alternative_verification`、対象パスが各 1 回以上現れることを確認してください。

[Warning] リスク欄で約束した「基点が違うと落ちる」検査がテスト一覧にありません。

修正案: 明示的な負の対照として追加し、CLI の `--repo-root` からも同じ検証経路を通してください。

[Suggestion] 凍結値は「期待値の正本」ではなく「レビュー承認済みスコープのスナップショット」と呼ぶ方が、JSON を唯一の運用上の正本とする説明と衝突しません。

## 施策 5: 監査文書の新設

**判定: REQUEST_CHANGES**

[Critical] 「既存の参照 3 か所は書き換え不要」という判断は、提示された現行 README と矛盾します。

現行 README は監査文書を次のように説明しています。

```text
coverage-audit.md（route/operation の机上対応表）
```

新しい監査文書は route/operation の一覧を持たず、「対象外の理由と代替検証」だけを扱います。したがって、この説明は明確に古くなります。

修正案: `coverage/README.md` の該当箇所を同じ変更で更新し、次の責務分担に揃えてください。

- `coverage-audit.md`: コード到達で対象外と判断する面、その理由、代替検証
- `inventory/annotations.toml`: route 単位の探索対象外
- `correlate.py` / `merge_pcov.py`: 走行ごとの動的な突合結果

`ledger/README.md` と `ledger/validate_findings.py` についても、同じ「route/operation の対応表」という説明が残っていれば更新対象です。

[Warning] テスト 17 の修正後、文書に一覧を持たないという保証対象を明確にしてください。

修正案: 「Markdown 表を一切禁止」ではなく、「対象外 entry の id/title/path 一覧を複製しない」と定義してください。軸の比較表や責務表は許可されるべきです。

## 施策 6: pcov の古い前提の訂正

**判定: REQUEST_CHANGES**

[Warning] 「CI と本番には pcov が無い」という断定の根拠が不足しています。

GitHub Actions に導入記述がないことから CI の一部は推測できますが、AGENTS.md は本リポジトリにデプロイ定義がないと明記しています。その状態では、本番ランタイムに拡張が存在しないとは証明できません。また、開発用 Dockerfile が本番イメージの基礎になっている可能性も文面だけでは排除できません。

修正案: 「インストールされているか」と「coverage 取得が有効か」を分けて記述してください。

- 開発コンテナでは pcov を利用できる
- bug-hunt runner は serve 起動時だけ明示的に有効化する
- CI・本番は bug-hunt coverage の取得対象として構成していない
- 拡張の有無にかかわらず、設定 guard を満たさなければ middleware は no-op
- 本番への pcov インストール有無は、このリポジトリからは保証しない

[Warning] 今回の目的が「古い前提の除去」なのに、同じ文言が戻ることを落とす検査がありません。

修正案: `test_naming_no_stale.py` の責務に合うなら、少なくとも次の古い断定を禁止語として登録してください。

- `pcov は本環境未導入`
- `本環境/CI/本番には pcov が入っていない`
- `実 coverage は取得できない`

正しい新文章全体を完全一致で pin する必要はありません。古い断定の再混入だけを検出する方が腐りにくいです。

## 修正後に必要な再レビュー対象

再レビューでは、少なくとも次の差分が確認できれば承認可能です。

1. canonical path・リポジトリ境界・全 entry 横断の包含禁止
2. CLI の `--declaration` / `--repo-root`
3. テスト 17 の自己矛盾解消
4. 型違反、パス逸脱、I/O 失敗、出力内容の負の対照
5. 6 面すべての実際の理由・代替検証
6. `coverage/README.md` の役割説明更新
7. pcov の「有無」と「有効化」を分けた事実ベースの記述

製品コードの挙動、Laravel の認可・tenant 境界、PHPStan level 10 に対する直接的な後退リスクは、この設計範囲では見当たりません。主なリスクは監査データの fail-closed 性と、説明文書の正本間不整合です。
