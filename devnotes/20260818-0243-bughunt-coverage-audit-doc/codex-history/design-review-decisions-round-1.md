# 対応マトリクス: design-review Round 1

## [Critical] 施策 1: パスの正規化とリポジトリ境界の契約が不足 (`app/../tests` で迂回できる)
- 判断: 対応する
- 根拠: 指摘のとおり。先頭セグメントの一致と `exists()` だけでは、対象外の範囲を `app/` の外へ
  広げられ、循環参照の検査も抜けられる。検査の要は「範囲を無制限に広げられないこと」なので致命。
- 対応内容: パスの正規形の契約を 1 節足した。絶対パス / `.` / `..` / 空セグメント / 末尾スラッシュ /
  バックスラッシュ / 先頭スラッシュを拒否し、`repo_root` を基点に解決した結果が repo の外へ出るものを
  拒否、`path_prefixes` はさらに `repo_root/app` の内側であることを要求、シンボリックリンクは拒否。
  **同じ正規化関数を実在検査・包含検査・循環検査・`covers()` の 4 か所で共用する**と明記。
  自己テスト 9 番で「実在するが正規形でない」「repo 外へ出る」「シンボリックリンク」を負の対照にした。

## [Warning] 施策 1: 「追跡下に実在」と `exists()` が一致していない
- 判断: 対応する (両取り)
- 根拠: 生成物や一時ファイルを代替検証にできてしまうのは避けたい。一方で loader に git を
  必須にすると、読み取り器が実行環境を選ぶ。
- 対応内容: **loader の契約は「リポジトリ内に実在する」まで**に弱め、**追跡下かどうかは自己テスト
  (14 番) が `git ls-files` で見る**形にした。git が使えない環境は skip ではなく fail
  (既存 `BugHuntInventoryCheckInvariantTest` の先例に合わせる)。

## [Warning] 施策 1: `covers()` が単一 entry を返すのに面を跨いだ包含が禁止されていない
- 判断: 対応する
- 根拠: 並び順に依存する結果はテストで固定できても意味が無い。
- 対応内容: `path_prefixes` は**全 entry の直積で**包含関係と完全重複を禁止 (antichain) にした
  (自己テスト 10 番)。

## [Warning] 施策 1: 6 面の理由と代替検証の全文が無い
- 判断: 対応する
- 根拠: 意味の妥当性は人が読むしかない設計なので、詳細設計で省略すると最重要部分がレビューできない。
- 対応内容: **8 面の全文**を書いた。`machine-interface` は指摘のとおり定義と衝突していたので
  `mcp-oauth-interface` と `rest-api` に分割。`out-of-process-execution` も代替検証が違うので
  `artisan-command` と `queued-job` に分割 (理由か代替検証が違えば別の面、という定義に従った)。

## [Warning] 施策 1: 無内容判定が既存の route 対象外宣言より弱い
- 判断: 対応する
- 根拠: `annotations.toml` は理由 30 文字以上必須。2 つの正本で閾値が違うと説明できない。
- 対応内容: `reason` と `alternative_verification` の両方に **trim 後 30 文字以上**を課し、
  完全一致の無内容 denylist と併用する形にした (自己テスト 7 番)。

## [Critical] 施策 2: CLI に `--declaration` / `--repo-root` が無く負のテストが書けない
- 判断: 対応する
- 根拠: 実ファイルを壊さずに終了コード契約を実プロセスで確かめる手段が無い = 検査が空振りする。
- 対応内容: CLI に `--declaration` / `--repo-root` を足し、既定値も明記した。

## [Warning] 施策 2: 既定ルートの算出が曖昧 (off-by-one)
- 判断: 対応する
- 対応内容: `Path(__file__).resolve().parents[4]` と階層の内訳を表に明記。引数省略で実宣言が読める
  正のテスト (1 番) と、誤った基点では落ちる負の対照 (22 番) を追加した。

## [Warning] 施策 2: markdown 出力のエスケープ契約が無い
- 判断: 対応する
- 対応内容: セル正規化 (`\` と `|` の退避・改行を空白へ) を契約にし、`|` と改行を含む検体で
  列数が保たれることを自己テスト 19 番で見る。JSON 側も UTF-8 / `ensure_ascii=False` / `indent=2` /
  末尾改行 / 宣言順維持を明記。

## [Critical] 施策 3: テスト 17 が監査文書自身を必ず落とす (文書には軸の対応表がある)
- 判断: 対応する
- 根拠: そのとおりで、設計内で自己矛盾していた。表そのものを禁じるのは目的に対して過剰でもある。
- 対応内容: 23 番へ作り直した。**宣言から読んだ** `id` / `title` / `path_prefixes` が監査文書に
  現れないことだけを検査する (表の区切り行は禁じない)。宣言を読むのは 17 番 (承認済み範囲の
  スナップショット) と目的が違うので自己参照にならない、という理由も設計に書いた。

## [Critical] 施策 3: 型契約とパス境界の負の対照が不足
- 判断: 対応する
- 対応内容: 型違反 (トップレベルが配列 / `entries` が object / 文字列欄が数値 / 配列要素が非文字列 /
  空白だけ)、`verification_refs` と `path_prefixes` の重複、entry を跨ぐ完全重複と包含、
  パスの逸脱一式、`covers()` の正規形契約を自己テストへ追加した (4 / 9 / 10 / 12 / 15 番)。

## [Warning] 施策 3: 入力障害の収束に対応するテストが無い
- 判断: 対応する
- 対応内容: 16 番 (ファイル不在 / 不正 UTF-8 / 壊れた JSON / 過剰なネスト) を追加。権限エラーは
  移植性のため検体化しない旨も明記した。

## [Warning] 施策 3: CLI 正常系が終了コードしか見ていない
- 判断: 対応する
- 対応内容: 18 番 (JSON を parse して正規化データと一致) と 19 番 (markdown に全 entry の
  title / reason / 代替検証 / 対象パスが現れる) へ分けた。

## [Warning] 施策 3: 「基点が違うと落ちる」検査が一覧に無い
- 判断: 対応する
- 対応内容: 22 番として追加 (CLI の `--repo-root` から同じ経路を通す)。

## [Suggestion] 施策 3: 「凍結値」ではなく「レビュー承認済み範囲のスナップショット」と呼ぶ
- 判断: 対応する
- 対応内容: 用語を差し替え、運用上の正本は JSON であると明記した。

## [Critical] 施策 5: 「既存の参照 3 か所は書き換え不要」は現行 README と矛盾する
- 判断: 対応する
- 根拠: 現行 README は監査文書を「route/operation の机上対応表」と説明しており、新設文書は
  その対応表を持たない。放置すると正本間の不整合を新規に作る。
- 対応内容: 波及変更を表に作り直し、`coverage/README.md` を同じ変更で更新する (3 者の責務分担を
  README 側で 1 か所にそろえる) こと、`ledger/README.md` と `validate_findings.py` も読み直すことを
  施策に明記した。

## [Warning] 施策 5: 一覧を持たないという保証対象の明確化
- 判断: 対応する
- 対応内容: 「対象外の面の一覧の複製だけを禁じる。軸の対応表は許す」と設計に書いた。

## [Warning] 施策 6: 「CI と本番には pcov が無い」は断定できない
- 判断: 対応する
- 根拠: 本リポジトリにデプロイ定義が無い以上、本番実行環境の拡張の有無は分からない。
  古い断定を別の断定へ置き換えるのは同じ誤りの再演である。
- 対応内容: 「拡張の有無」と「収集の有効化」を分け、書ける 5 点だけを書く形へ改めた
  (本番については本リポジトリからは保証しない、と明記する)。

## [Warning] 施策 6: 古い文言が戻ることを落とす検査が無い
- 判断: 対応する
- 対応内容: `test_naming_no_stale.py` の禁止語へ古い断定 3 つを追加する施策にした。新しい文面を
  完全一致で pin する形は採らない (腐りにくい側を選ぶ)。射程が skill 配下の `.md` / `.py` に限られ、
  `app/` の docblock は見えないことも保証しない範囲として明記した。

## [Suggestion] 施策 7: D20 が既に軸の分離を正本化していないか最終確認
- 判断: 対応する
- 対応内容: 実装時に D20 の本文を読み直し、既に記録されているなら新規登録ではなく D20 の更新に
  切り替える、と施策へ明記した (本設計は新規登録を既定案とする)。
