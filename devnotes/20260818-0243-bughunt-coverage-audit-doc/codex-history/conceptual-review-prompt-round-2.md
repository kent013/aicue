Round 1 の指摘への対応を報告します。概念設計を以下のとおり改訂しました。再判定をお願いします。

## [Critical] 対象外宣言が「未到達を正当化する台帳」へ変質するリスク → 対応

宣言のスキーマを次のとおりにしました (1 件 = 1 つの面)。

- `id` / `title` / `reason` (なぜブラウザ走行では検査できないか) /
  `alternative_verification` (代わりに何が検査するか。散文) /
  `verification_refs` (代替検証の実体。リポジトリ相対パスの列。**実在を機械で検査する**) /
  `path_prefixes` (`app/` 配下の実在パス接頭辞)

さらに「対象外を静かに広げられない」ための検査として、**宣言済みの面 (id) と接頭辞を凍結値と
完全一致で pin** します (増減のどちらでも赤くなる)。これは本リポジトリが既に多用している
deny-by-default の目録の形と同じで、対象外の追加は必ずレビューに見える形になります。

同時に**保証範囲を誇張しない**ことを監査文書へ明記します: 機械が見るのは宣言の形式と参照先の
**実在**までであり、代替検証がその面を本当に守っているか (テストの意味的十分性) は人のレビューの
担当である、と自分から書きます。

## [Warning] 検証契約の不足 → 対応

fail-closed の契約として次を固定します (詳細設計で 1 テスト 1 契約へ割ります)。

- 必須キーの存在と非空 / **未知キーの拒否** / `id` の一意性と書式
- 無内容な値 (「対象外」「なし」等) の拒否
- `path_prefixes`: 非空 / `app/` 配下 / 実在 / 包含関係の禁止 / 幹 (`app` や `app/Http` のような
  浅い節) の禁止
- `verification_refs`: 非空 / 実在
- JSON は UTF-8・トップレベルは object・出力順は宣言順で安定

## [Warning] 期待効果が過大 → 対応

「走行報告が未到達を毎回散文で言い直す必要がなくなる」を撤回し、
「**既知の設計上の対象外について理由と代替検証を書き直さず宣言を指せる。走行ごとの未到達の確認
自体は無くならない (件数も新規の未到達も毎回見る)。効果は宣言済みの面と説明の無い穴を分けて
読めるようになることに限る**」へ書き換えました。

## [Warning] 「面」が未定義 → 対応

面を「**ブラウザ走行では検査できない理由と代替検証を共有する `app/` 配下のコード群**」と定義し、
理由か代替検証が違うなら別の面にする、と明記しました (粒度をこの一文で揃える)。

## [Warning] 「参照実装を持ち込まない」は根拠にならない → 対応

行数比較をやめ、詳細設計で「**守るべき不変条件 ↔ それを落とす検査**」の対応表を作ることにしました。
採らなかった検査は理由を 1 文で残します。

## [Warning] Python の型安全性 → 対応

(依存は標準ライブラリのみ)。
