# 対応マトリクス: conceptual-review Round 1

## [Critical] 対象外宣言が「未到達を正当化する台帳」へ変質するリスク
- 判断: 対応する (一部は反論を添える)
- 根拠: 指摘のとおり、散文の理由と代替検証だけでは「代替検証が実在するのか」すら分からない。
  一方で「代替検証がその面を本当に守っているか」は機械で決められない (テストの意味的十分性)。
  そこで**実在は機械で・妥当性は人で**と役割を分け、保証範囲を文書に自分から書く。
- 対応内容: 宣言に `verification_refs` (リポジトリ相対パスの列) を追加し、実在を検査する。
  加えて「宣言済みの面と接頭辞を凍結値と完全一致で pin する」検査を入れ、対象外を静かに広げられなくする
  (増減のどちらでも赤くなる。本リポジトリが既に多用している deny-by-default の形)。
  保証範囲 (実在まで。意味の十分性はレビュー) を監査文書に明記する。

## [Warning] `out-of-scope.json` の検証契約が不足
- 判断: 対応する
- 根拠: fail-closed の契約を先に決めないと「書けば通る」宣言になる。
- 対応内容: 必須キー / 未知キー拒否 / id 一意性と書式 / 無内容な値の拒否 / prefix の実在・包含禁止・
  幹 (浅い節) の禁止 / `app/` 配下限定 / 参照先の実在、を概念設計へ明記し、詳細設計で 1 テスト 1 契約へ割る。

## [Warning] 期待効果「毎回散文で言い直す必要がなくなる」は過大
- 判断: 対応する
- 根拠: 走行ごとの未到達の確認自体は消えない。過大な効果を書くと後の判断材料が濁る。
- 対応内容: 効果を「宣言済みの面と説明の無い穴を分けて読めるようになる」に限定して書き直した。

## [Warning] 「1 件 = 1 面」の面が未定義
- 判断: 対応する
- 根拠: 粒度が揺れると、後から足す人が理由の違う面を 1 件にまとめてしまう。
- 対応内容: 面を「ブラウザ走行では検査できない理由と代替検証を共有する `app/` 配下のコード群」と定義し、
  理由か代替検証が違えば別の面にする、と書いた。

## [Warning] 「参照実装を持ち込まない」は根拠にならない
- 判断: 対応する
- 根拠: そのとおりで、行数比較は判断材料ではない。
- 対応内容: 詳細設計に「守るべき不変条件 ↔ それを落とす検査」の対応表を作ることを概念設計へ明記した。
  採らなかった検査は理由を 1 文で残す。

## [Warning] Python 側の型安全性 (dict の持ち回り)
- 判断: 対応する
- 根拠: 検証済みかどうかが型で分からないと、検証を通らない経路が後から生える。
- 対応内容: 境界で `dataclass` へ変換し、以後は検証済みの型だけを扱うと明記した (標準ライブラリのみ)。

## [Suggestion] Python 検証器を製品実行経路へ混入させない旨の明記
- 判断: 対応する (詳細設計で扱う)
- 対応内容: 置き場所は `.claude/skills/` 配下のみで、`app/` からは参照しない。詳細設計の制約へ書く。

## [Suggestion] 集計器 (`merge_pcov.py`) への選別機能は入れない
- 判断: 見送る (現状維持でよい、という指摘に同意)
- 根拠: 概念設計のスコープ外のままでよい。
