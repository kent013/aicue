# 対応マトリクス: conceptual-review Round 1

## [Warning] 禁止事項: 候補 0 人でも「押せるのに成立しない destructive 操作」が確認ダイアログまで進む
- 判断: 対応する
- 根拠: 成立し得ない移譲を ConfirmDialog まで進めるのは説明責任として弱い、という指摘は妥当。禁止事項 8 の趣旨は「無言で塞がない」ことであり、押下時に即エラー表示すれば満たされる。
- 対応内容: 施策 2 に「submit ハンドラで候補 0 人 or 未選択なら ConfirmDialog を開かず即 `setError`。ダイアログが開くのは有効な移譲先選択時のみ」を明記。候補 0 人時の専用エラー文言も定義。

## [Warning] 実現可能性: F-10 の POST 成功 / GET 失敗分岐が未定義 (旧コード残存 + 成功トーストは誤案内)
- 判断: 対応する
- 根拠: 再生成 POST の時点で旧コードは失効済み。旧コードを画面に残したまま成功を報じると自己ロックアウトを誘発する。
- 対応内容: 施策 1 に 3 段階の状態遷移を明記 — (1) POST 確定で旧コード即クリア + 再取得中状態、(2) GET 成功時のみ成功トースト + 新コード一覧へフォーカス、(3) GET 失敗時は「旧コードは既に無効」を明示する error トースト + 既存「リカバリコードを表示」ボタンが再試行導線として残る。

## [Warning] 期待効果: 「finding 2 件のクローズ」は強すぎる

- 根拠: F-12 は未実装ではなく発見可能性/空状態説明の問題であり、成功条件を UI 到達性で言い換えるべき。
