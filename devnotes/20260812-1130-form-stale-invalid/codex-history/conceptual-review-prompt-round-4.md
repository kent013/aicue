## [Critical] page props のオブジェクト同一性は、このフォームの送信と相関していない

## 背景・課題

### 観測された症状 (2 画面)

| finding | 画面 | エラーの出所 | 症状 |
|---|---|---|---|
| F-1-01 (Low) | `/projects/create` | `useForm` の `form.errors` | 必須エラー表示後に有効値を入力してもエラーが消えない。**その状態で送信すると成功する** (表示だけが古い) |
| F-3-02 (Medium) | 請求先情報フォーム (`BillingContactForm`) | **page props の `errors`** (`useForm` ではない) | メールアドレスの invalid 表示が、値を直しても再送信するまで消えない |

### なぜ既定が「消えない」のか

表示は `resources/js/components/molecules/FormField.svelte` が `error` prop をそのまま描くだけで、
消す責務は**呼び出し側**にある。消しているのは、呼び出し側が書いた次の定型句だけ:

```svelte
oninput={() => { if (form.errors.title) form.clearErrors("title"); }}
```

実査: `<FormField` の呼び出しは **65 箇所 / 28 ファイル**、`clearErrors` を持つのは **9 箇所**。
**つまり既定は「消えない」で、消えるのは書いた人が覚えていた箇所だけ**である。

### なぜ直す価値があるか

「入力を直したのにエラーが出たまま」は、**送れば通るのに送るのをやめる**行動を誘発する。
F-1-01 は「送信すれば成功する」ことを実測しており、**表示だけがユーザーを止めている**。

## 改善アイデア

**観測された 2 箇所を、それぞれのエラー出所に合った機構で直す。**

| 対象 | 機構 | 同じ文言が 2 回返っても再表示される根拠 |
|---|---|---|
| `Projects/Create` (`useForm`) | 既存 9 箇所と同じ `form.clearErrors(field)` を `oninput` で呼ぶ | **値そのものを消す**ので、次の応答で再設定されれば必ず出る |
| `BillingContactForm` (page props) | フィールドごとの「編集済み」フラグで表示を抑制し、**このフォーム自身の `router.patch` の結果 (`onError` / `onSuccess`) で解除**する | 解除契機が**自分の送信そのもの**なので、同じ文言が返っても `onError` が呼ばれて必ず再表示される |

2 つの機構になるのは **エラーの出所が違うから**である
(値を保持する `useForm` と、読み取り専用の page props)。
同じ問題に 2 つの機構を並べているのではない。

**`BillingContactForm` の解除契機を「page props のオブジェクト同一性」にしない**
(Round 3 [Critical])。それは `router.on('finish')` と同じ欠陥を形を変えて持ち込む —
無関係な visit / partial reload で参照が入れ替われば、請求先を再検証していないのに解除されて
古いエラーが復活する。逆に partial reload で `errors` が応答対象外なら参照が保たれ、
再表示が起きない可能性もある。**どちらにも倒れうる前提には依存しない。**
このフォームは自分で `router.patch` を呼んでいるのだから、**その結果を相関点にする**のが正しい:

- 入力時に該当フィールドを編集済みにする
- **その `router.patch` の `onError`** で編集済みを解除する (= 新しい検証結果が届いた)
- `onSuccess` でも初期化し、次の操作へ持ち越さない
- `onFinish` **単独は使わない** (キャンセルや通信失敗でも動くため再表示の根拠にならない)
- 並行送信に備えて**送信世代**を持ち、古い応答が新しい編集状態を解除しないようにする

### 共通化を採らなかった理由 (合議の記録)

当初案は「`FormField` が subtree の `input` / `change` で表示を抑制し、
Inertia の visit 完了で戻す」で、65 箇所を一度に直すものだった。**棄却した**。

- **[Critical] `router.on('finish')` は「そのフィールドの再検証結果の到着」と対応しない。**
  無関係な部分リロード・画面遷移・失敗した visit でも発火するため、
  「入力して消えた古いエラーが、無関係な遷移で復活する」= **stale 表示の再発**を非決定的に作る。
- **[Critical] `error` prop からは「新しい応答が来た」ことを識別できない。**
  同じ文言が再設定されても props 上は不変で、`setError` 等の非 visit 経路も塞げない。
- **[Warning] 65 箇所の分類が閉じない。** control 内訳の合計は 63 で **2 箇所が未分類**だった。
  「全 65 箇所が `input`/`change` で扱える」という一括適用の前提が成立していない。
- **[Warning] 単数の `error` prop は「どの子を触っても隠してよい」ことを証明しない。**
  確認入力の不一致・日付範囲など、複数値に依存する 1 メッセージがありうる。
- **[Warning] 9 箇所の `clearErrors` 撤去は同等置換にならない。** `clearErrors` は値を消すので
  後続の visit で復活しないが、表示抑制方式は値を残すため復活しうる。

共通化するなら「送信との相関」を表現する入力 (フォーム束縛 or エラー世代) が要る。
それは **props インターフェースの変更 + 65 箇所の移行**を伴い、
観測された事実 (2 件) に対して大きすぎる (思考原則 2)。**本 TODO では採らない。**

  これは意図した限定であり、無関係な visit で古いエラーを復活させないための代償である。
