# 対応マトリクス: design-review Round 1

判定 REQUEST_CHANGES。Critical 1 / Warning 2 / Suggestion 2。**すべて対応**(反論なし)。

## [Critical] `submissionId` は守りたい競合を守れていない

- 判断: **対応する** (機構を差し替え)
- 根拠: 完全に妥当。`submissionId` が検知するのは「後続 submit」だが、`submitting` ガードがある以上
  それは通常起きない。実際の危険は「**送信 → 応答待ちの間に編集 → 古い値への検証結果が返る**」で、
  現案はそこで `attempt === submissionId` が成立してしまい**解除してしまう** = 最新入力に対して
  stale なエラーを出し直す。
- 対応内容: 送信世代を捨て、**フィールドごとの編集世代 (`emailEditVersion` / `nameEditVersion`)** に
  変更した。送信時に世代を控え、**応答時に世代が変わっていないフィールドだけ**解除する。
  契約 11 と mutation M7 も「編集世代の一致判定」を対象に書き換えた。

## [Warning] 「送信成功したが、その間に値が変わっていた」ケースを明示せよ

- 判断: **対応する** (上記の変更が同時に解決する)
- 対応内容: 編集世代の判定は `onSuccess` にも効くため、送信中に編集されたフィールドは
  成功応答でも解除されない。**画面の値とサーバ保存値の食い違いを「検証済み」に見せない**ことを
  設計判断として明記した。

## [Warning] `onError` / `onSuccess` の両方で解除する設計は妥当

- 判断: **対応不要** (肯定的評価)。`onFinish` を解除に使わない判断も是認された。

## [Suggestion] Projects/Create は DOM からエラーが消えることも 1 本見る

- 判断: **対応する**
- 対応内容: 契約 0 として「エラー文言が DOM から消える」を追加した
  (`FormField` / `Input` 連携ごと固定できる)。

## [Suggestion] mutation M6 の観測設計が弱い

- 判断: **対応する**
- 対応内容: 契約 9 に「**テストでは page props のエラーを据え置いて観測する**」と明記した
  (実運用では成功応答で errors が消えるため、観測可能にするための約束事であることも書いた)。
