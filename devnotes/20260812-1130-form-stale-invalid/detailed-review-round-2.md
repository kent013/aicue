## 全体判定: REQUEST_CHANGES

編集世代方式そのものは正しく、Round 1 の競合は閉じています。実装ロジックは着手可能な水準です。ただし、テスト計画にフィールド別解除の重要な分岐が1つ不足しているため、契約追加後に着手するのが妥当です。

### 施策1: Projects/Create

**APPROVE**

[Suggestion] fail先行の記述に契約0が抜けています。

実装前はDOM上のエラーも消えないため、赤になる対象は「契約0..3」です。契約4だけが既存実装でも緑になる想定です。

M1は契約3だけでなく、引数を直接検証する契約1でも確実に検出されます。表は次の記載が正確です。

| mutation | 赤くなる契約 |
|---|---|
| M1 | 契約1、3 |
| M2 | 契約0、1 |

`useForm` stubは、`clearErrors("name")`で実際に`errors.name`を削除し、Svelteから観測可能な状態にする必要があります。呼び出し記録だけのstubでは契約0を検証できません。

### 施策2: BillingContactForm

**APPROVE**

[Suggestion] 変数名の`emailAtSubmit` / `nameAtSubmit`は値のスナップショットに見えます。`emailVersionAtSubmit` / `nameVersionAtSubmit`の方が誤読を防げます。

Round 1の競合は閉じています。

```text
email version = 1
送信時に 1 を保存
送信中の入力で version = 2
応答時: 2 !== 1
emailEdited は解除されない
```

主要な分岐も正しく処理されます。

| 状況 | email | name |
|---|---|---|
| 送信前に未編集 | 世代一致、解除 | 世代一致、解除 |
| 送信前に編集、送信後は未編集 | 世代一致、解除 | 世代一致、解除 |
| 送信中にemailだけ編集 | 世代不一致、維持 | 世代一致、解除 |
| 送信中に両方編集 | 世代不一致、維持 | 世代不一致、維持 |
| cancel・通信失敗でonFinishのみ | 維持 | 維持 |

`onError`と`onSuccess`の双方に同じ`release`を渡すことにも新しい穴はありません。通常は排他的に呼ばれますし、仮にstubが両方を呼んでも、編集世代による判定は冪等です。両方とも呼ばれない場合も`onFinish`だけでは解除しないため、設計意図と一致します。

Atomic Design、DESIGN.md、禁止事項8にも抵触しません。既存atomへのイベント追加だけで、import階層やDS tokenへの波及もありません。

### 施策3: 契約テスト

**REQUEST_CHANGES**

[Warning] 「送信中に片方だけ編集した場合、もう片方は解除される」という契約がありません。

契約11は編集されたフィールドが維持されることしか要求していません。実装を誤って「どれか1フィールドが更新されたら両方とも解除しない」としても通る可能性があります。次の契約を追加してください。

> 送信中にemailだけ編集した場合、応答後もemailのエラーは抑制されたままだが、編集していないnameの抑制は解除される。

これはフィールドごとの編集世代を採用した中核的な理由であり、M4とは別の分岐です。

[Warning] 契約11の`onError / onSuccess`は両経路を実際に試す必要があります。

パラメータ化テストで同じシナリオを両callbackに適用すれば十分です。片方だけ試して「両方を保証」とすると、片方から世代判定を削除するmutationが生き残ります。

[Suggestion] 契約8〜11ではcallback順序を明示してください。

```text
入力 → submit → onStart → 送信中の追加入力 → onError/onSuccess → onFinish
```

jsdomで問題なく書けます。`router.patch`のoptionsを捕捉し、保存したcallbackを任意順で同期的に呼べばよく、古い応答を再現する特殊なブラウザ機能は不要です。

mutation対応は、上記追加を除けば妥当です。

| mutation | 判定 |
|---|---|
| M1 | 妥当。契約1と3が検出 |
| M2 | 妥当。契約0と1が検出 |
| M3 | 妥当。契約6が検出 |
| M4 | 妥当。契約7が検出 |
| M5 | 妥当。契約10が検出 |
| M6 | 妥当。errors据え置きなら契約9が検出 |
| M7 | 妥当。契約11の両callback試験で検出 |

結論として、実装方式の再設計は不要です。契約0のfail先行対象修正、契約11の両callback化、片方だけ送信中編集した場合の契約追加を詳細設計へ反映すれば、実装着手可能です。
