[Critical] `router.on('finish')` は「再検証結果の到着」と対応していない

Inertia の `finish` は対象フィールドを送信した visit だけでなく、無関係な部分リロード、画面遷移、キャンセル・失敗した visit でも発生し得ます。

そのため次の回帰が生じます。

1. サーバエラーが表示される
2. ユーザーが入力して表示が消える
3. 無関係な Inertia visit が完了する
4. `form.errors` に残った古いエラーが再表示される

これは元の「直したのにエラーが残る」を、非決定的なタイミングで復活させます。「安全側」とありますが、入力済みの古いエラーを再表示するのは安全側ではなく stale 表示の再発です。

また、`finish` は成功したレスポンス適用だけを表すとは限らないため、「同じエラーが再到着した」という証拠にはできません。

修正提案:

- グローバルな visit 完了を再表示契機にしない。
- 再表示は、そのフィールドを含む送信の開始時に抑制解除するか、対応する `error` の更新世代を明示的に渡す。
- props を増やさない制約を維持するなら、共通化は抑制処理までに留め、送信との相関が必要な箇所は呼び出し側で管理する。
- この相関を表現できないままなら、まず観測済み2画面を `clearErrors(field)` で直す方が正しい。

[Critical] 65箇所の分類件数が一致していない

提示された control 内訳は以下の合計です。

`Input 39 + Select 10 + Textarea 7 + PasswordInput 7 = 63`

分類表も `text系 53 + Select 10 = 63` です。呼び出し総数65に対して2箇所が未分類です。したがって、「65箇所すべてが `input` / `change` で扱える」という一括適用の前提は、現時点では成立していません。

修正提案:

- 残り2箇所について、実際の children、発火イベント、エラーの意味を特定する。
- `FormField` 呼び出し数ではなく、各インスタンスが内包する操作可能要素の一覧として分類する。
- 合計が65になり、全件が抑制契約に適合するまで全域適用しない。

[Warning] visitを伴わないエラー更新経路への保証がない

「サーバエラーは Inertia visit で届く」が正しくても、`FormField.error` の契約は「Inertiaのサーバエラー」に限定されていません。少なくとも次の更新候補があります。

- `form.setError()` などによるクライアント側設定
- 親コンポーネントの派生状態
- preserved component 内での状態更新
- テストや将来実装からの直接的な `error` prop 更新
- Inertia以外のXHR結果を親が反映する経路

抑制中に同じ文言が設定されると、propsだけでは再到着を識別できません。

修正提案:

- `FormField` の契約を「Inertia visit由来のエラー専用」と明記し、Architectureテスト等で強制するか、エラー世代を表す入力を追加する。
- 少なくとも `error` が別値になった場合と、空になってから再設定された場合は再表示する契約をテストする。

[Warning] `input` + `change` でもすべての値変更を表せない

既存の通常操作は概ね拾えますが、以下は残ります。

- JavaScriptによる programmatic value 変更
- `form.reset()` / DOMの `reset` イベント
- ブラウザやパスワードマネージャーの autofill
- `input` / `change` を転送しないカスタムcontrol
- subtree外のUIが同じ値を変更するケース

programmatic変更で自動的に隠すべきとは限りませんが、「値変更を検出する機構」とは表現できません。

修正提案:

- 契約を「subtree内のユーザー操作に由来する `input` / `change` で抑制する」と限定する。
- `reset` 後の期待挙動、autofill、カスタムcontrolについてテストまたは非保証事項を追加する。

[Warning] 単数の `error` prop はエラーのフィールド所有を証明しない

`error` が1個であることから、「どの子controlを触っても隠してよい」とは導けません。単一メッセージでも、確認入力との不一致、日付範囲、住所グループなど複数値に依存できます。また、subtree内に補助controlがあれば、その操作だけで主エラーが消える可能性があります。

修正提案:

- 65箇所についてcontrol種別だけでなく、`error` と編集対象の意味的対応を分類する。
- 複数の操作可能要素を含む `FormField` は別枠で確認する。
- FormField全体のエラーなら、どの変更でstaleになるかを呼び出し側が指定できる設計を検討する。

[Warning] 9箇所の `clearErrors` 撤去は同等置換になっていない

値依存が0件でも、動作は同等ではありません。`clearErrors` は古いエラーを消すため、後続の無関係なvisitで復活しません。新機構では値を保持したまま `finish` で抑制解除するため、古い表示が復活します。

修正提案:

- `finish` 方式を採用したまま9箇所を撤去しない。
- 9箇所ごとに「編集後、無関係な部分reloadや遷移が起きた場合」を確認する。
- 表示層だけで完結させるなら、エラー世代との相関を導入してから撤去する。

[Suggestion] グローバルイベント購読のライフサイクルを契約に含める

各 `FormField` が `router.on()` を購読する場合、最大65個のグローバルlistenerが作られます。破棄時のunsubscribeが必須で、再描画による多重購読もテスト対象です。moleculeをInertiaへ直接結合する設計上のコストもあります。

[Suggestion] 一括適用の判断

65箇所への共通化という方向自体は妥当です。観測が2件だけでも、同じコンポーネント契約が原因なら2箇所限定にする必然性はありません。

ただし現案は、未分類2箇所と `finish` の非相関という機構上の問題が残っています。したがって現時点では一括適用を受容できません。まず「対象送信との相関をどう表すか」を解決し、65箇所の分類合計を閉じたうえで、共通化を再評価すべきです。
