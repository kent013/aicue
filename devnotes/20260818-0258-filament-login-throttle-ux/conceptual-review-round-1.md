全体判定: **CHANGES_REQUESTED**

### 1. 使命との整合性

[Suggestion] 管理画面のログイン復旧性を上げる改善であり、North Star への直接効果は小さいものの、SOP・組織・課金設定を担う運用者を不要な復旧操作から守る点で妥当です。v1 の撮影体験を広げず、既存運用の詰まりを解く最小変更になっています。

### 2. 禁止事項違反

[Warning] 「テストファースト」を掲げていますが、現状の記述は実装後の固定テストにも読めます。先に現行 vendor Login で「5 回失敗後、6 回目で旧 `data.email` エラーが残る」ことを赤で再現し、その後に独自クラスを導入して緑にする順序を明記してください。

修正提案: テスト計画を「現行実装で failing test を確認 → 独自 Login 導入 → 回帰テストを緑化」と明文化する。

[Suggestion] `response()->json()`、Prompt、操作 POST のリダイレクト、disabled UI 等の禁止事項には抵触しません。

### 3. 実現可能性

[Critical] `ThrottleExemptionPremiseTest` の追随方針に技術的な誤りがあります。既存検査がクラスのソース文字列から `Login::authenticate()` 内の `rateLimit(` を探す方式なら、対象を独自の子クラスへ替えた時点で、その子クラスのファイルには継承元の `authenticate()` 本文が存在しません。「継承のままなので走査は成立する」は成り立ちません。

修正提案: panel が実際に使う Login クラスを解決したうえで、Reflection により `authenticate()` の宣言元を取得し、その宣言元が vendor Login であること、かつ宣言元の実装に `rateLimit(` が存在することを検査してください。加えて、独自 Login が `authenticate()` を override していないことを固定すると、将来の閾値・判定順序の複写も防げます。

[Warning] `getRateLimitedNotification()` の厳密な可視性、引数型、戻り値型は対象 Filament バージョンの実装と完全一致させる必要があります。特に `TooManyRequestsException` の import と nullable な Notification 型は、親メソッドとの互換性を外すと PHP のロード時に失敗します。

修正提案: 設計に「vendor 親メソッドのシグネチャをそのまま踏襲する」と追記し、Reflection または直接の型検査で override 互換性をテストする。

### 4. 期待効果の妥当性

[Warning] 「通知だけが残る」は、通知が数秒で消えるという背景説明と両立しません。正確には、矛盾する古い入力エラーを除去し、上限到達直後には既存通知だけが提示される、です。通知消滅後に恒久的な説明を残す改善ではありません。

修正提案: 期待効果を「古い認証失敗エラーを残さず、既存の rate-limit 通知による説明を妨げない」と修正する。

[Suggestion] 閾値、判定順序、通知文言を vendor に委ねる方針は合理的です。`authenticate()` を複写しない選択も、アップデート追従性の観点で適切です。

### 5. リスク

[Warning] 独自 Livewire コンポーネント化により rate-limit キーが変わり、デプロイ時点で既存の失敗回数が一度リセットされます。これは「鍵の意味や書式は変えない」としても、短期間の実効的な防御低下です。

修正提案: これを単なる制約ではなく、デプロイ時の受容済みセキュリティ影響として明記してください。認証経路の変更として、低トラフィック時間帯の反映、リリースノート、必要なら監視確認を運用手順に含めるべきです。

[Warning] `resetErrorBag()` 相当で全エラーを消す場合、上限到達時に残すべき別種のフォームエラーまで消えないことを確認する必要があります。特に MFA チャレンジでのフォーム構成とエラーキーを実測で確認すべきです。

修正提案: MFA を含むテストで、「rate-limit による旧エラーは消える」ことに加え、当該画面で本来維持すべき状態・入力値・画面遷移が変わらないことを固定する。

### 6. スコープの適切さ

[Suggestion] 入力欄への重複表示、閾値変更、一般ユーザー側への横展開を除外した判断は適切です。原因が「説明不足」ではなく「古い説明との矛盾」である、という問題設定に対して最小です。

[Suggestion] `getRateLimitedNotification()` が副作用を持つ点は設計上の違和感ですが、vendor が用意する唯一の狭い拡張点であり、理由を日本語コメントで残すなら許容できます。

### 7. 型安全性

[Warning] PHPStan level 10 を通すには、親の正確な戻り値・引数型・可視性を守ることに加え、エラー消去 API の存在と型を前提にしない実装が必要です。vendor 間接依存の例外型を使うこと自体は、Filament の公開 override 契約に含まれる限り問題ありません。

修正提案: 親シグネチャを完全一致で override し、`parent::getRateLimitedNotification($exception)` をそのまま返す形に限定してください。PHPStan、Pint、該当 Feature/Security テストを完了条件に含めるべきです。

主たる差し戻し理由は、既存の throttle 免除検査を子クラスへ単純に差し替える案が、継承メソッドの実装本文を検査できず成立しない点です。ここを Reflection を用いた「実使用クラス → 実際の宣言元」検査へ設計変更できれば、全体としては承認可能な最小改善です。
