# 対応マトリクス: design-review Round 1

## [Critical] 実装前は独自クラスが存在せず、意図した赤を観測できない (施策 1)

- 判断: 対応する
- 根拠: 指摘のとおり。`use App\Filament\Auth\Login;` を書くと実装前はクラス解決の失敗になり、
  「上限到達で入力エラーが残る」という不具合を観測できない。
- 対応内容: 振る舞いの 3 ケースは `Filament::getPanel('admin')->getLoginRouteAction()` で
  実行時に解決したクラスに対して検査する形へ変更した (`adminLoginPageClass()` ヘルパ)。
  独自クラスへの配線は最後の配線検査だけが名前で固定する
  (`::class` はオートロードを起こさないため、実装前でも失敗するのは比較であってクラス解決ではない)。

## [Warning] RateLimiter の状態分離がテスト環境の cache store に依存している

- 判断: **反論する (事実で限定し、設計に根拠を明記)**
- 根拠: `phpunit.xml` が `CACHE_STORE=array` を **`force="true"`** で固定している。
  array store はテストごとに作り直されるアプリのコンテナに属するため、テスト間でも
  並列 worker 間 (別プロセス) でも共有されない。したがって現状の構成で衝突は起きない。
  キーを自前で再計算して後片付けする形は、vendor の鍵生成規則 (sha1 の組み立て) を
  テスト側へ複写することになり、むしろ壊れやすい。
- 対応内容: 「流量制限の計数はテスト間で共有されない」ことを根拠つきで確認点の表に追記した。

## [Warning] MFA 専用 limiter を通っていない (施策 1)

- 判断: 対応する
- 根拠: 指摘のとおり。従来案では通常の上限が先に発火し、多要素チャレンジ専用の経路は
  一度も上限に達しない。上書きした拡張点は両方から呼ばれるため、未検査の波及が残る。
- 対応内容: 多要素のケースを「通常側は上限未満のまま、`filament-multi-factor-challenge:{id}` の
  計数だけを上限まで積んでから送る」形に書き直し、通知・エラー消去・チャレンジ状態の保存を固定した。

## [Warning] `000000` はまれに正しい TOTP になり得る

- 判断: 対応する (指摘より簡単な形で解消)
- 根拠: `codeWindow(1)` で前後の窓も有効なため、固定値の詐称は確率的に不安定。
- 対応内容: コードを**未入力**にして `required` を踏ませる形へ変更した
  (`AppAuthentication::getChallengeFormComponents()` の `code` は復旧コードが空なら必須)。
  固定 secret にも時刻凍結にも依存しない。

## [Suggestion] page route の完全一致は目的より広い

- 判断: 対応する
- 根拠: 正当な管理ページが 1 つ増えただけで無関係に赤くなるのは、検査の目的
  (置き場所の誤りの検出) に対して広すぎる。
- 対応内容: `filament.admin.pages.*` の名前に `login` を含むものが無いことの確認に絞った。

## [Warning] クラスコメントが不正確 (MFA 専用 limiter からも呼ばれる / error bag 全体を消す) (施策 2)

- 判断: 対応する
- 根拠: 指摘のとおり。拡張点の呼び出し元は 2 か所であり、`resetValidation()` は error bag 全体を消す。
- 対応内容: docblock を「呼び出し元は 2 か所」「error bag を丸ごと空にする」「どちらの経路でも
  この要求が新たに立てたエラーは無い (通常側は上限評価が検証より前、多要素側はログイン欄の検証を
  通過して到達する)」と正確に書き直した。設計本文にも両経路が対象であることを明記した。

## [Warning] 完了条件が AGENTS.md の検証コマンド集合を満たしていない

- 判断: 対応する
- 根拠: 規約どおり。フロント無変更は省略の理由にならない。
- 対応内容: 完了条件を検証コマンド 10 本すべてに書き換えた。
