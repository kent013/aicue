Round 1 の主要論点は概ね解消されています。アプリ側観測器の採用、生成器と照合器の両端 fail-closed、固定出力先、run/shard 検証、Python テストの実行レーンへの接続は妥当です。

ただし、`ok` が 0 件であることを「主入力の可用性違反」とする設計は、記録の健全性と探索結果を混同しています。ここは修正が必要です。

## 1. 使命との整合性

[Suggestion] 改善の主効果を「カバレッジ報告の信頼性回復」に限定した整理は適切です。

North Star への寄与は間接的ですが、操作詰みや認可問題を探索する基盤の観測結果を信用可能にするため、開発基盤として合理的です。二次効果を成否条件から外した点も妥当です。

## 2. 禁止事項違反

[Warning] 成功条件 3 とスコープ外の記述に若干の不整合があります。

成功条件では「bug-hunt を1回走らせる」としていますが、スコープ外では並列実走行を行わず、fake provision と自己テストで閉じるとしています。「1 shard の非課金 fixture/fake 走行でパイプラインを確認する」のか、「次回の実 run を受入条件とする」のかが不明です。

修正提案: 今回の完了条件を次のように分離してください。

- 自動テストで middleware → JSONL → executed.json → correlate の一連を固定する
- 実 bug-hunt run はリリース後の運用確認であり、本 TODO の完了条件にはしない

テスト登録を施策6まで含めているため、上記以外に明確な禁止事項違反はありません。

## 3. 実現可能性

[Warning] JSONL 追記の排他制御が概念設計にありません。

Laravel middleware から同じ shard ファイルへ複数リクエストが同時追記されると、実行環境や起動方式によっては行が混線し、JSON が破損します。破損時に builder が終了コード3になるため嘘はつきませんが、正常な探索を観測基盤側の競合で失敗させます。

修正提案: 1レコードを改行込みで組み立て、`flock(LOCK_EX)` を伴う単一追記として扱う契約を詳細設計に置いてください。排他・追記・flush の失敗はいずれも失敗マーカーの対象です。

[Suggestion] `terminate()` 方式は Laravel 12 で実現可能です。ただし route recorder が global web middleware として必ず terminable middleware の実行対象になることを Feature テストで固定してください。単体で `terminate()` を直接呼ぶだけでは配線検証になりません。

## 4. 期待効果の妥当性

[Critical] `correlate.py` の「`ok` の行が1件もなければ終了コード3」は不適切です。

これは観測不能と、観測できたが操作が成立しなかった状態を同一視します。

具体例:

```text
POST manuals.store -> 422
POST takes.adopt    -> 403
GET capture.show    -> 500
```

全行の `run_id`、shard、route、method、HTTP status が正しく記録されていても、`ok` がないため終了コード3になります。しかしこの走行で主入力は利用可能です。正しい結果は終了コード0で、3操作すべてを未達または blocked として worklist に残すことです。

特に今回、「422 は過小申告として未実行側に残す」と定義しているため、`ok=0` をエラーにするとその方針と矛盾します。

修正提案:

- 終了コード3の条件を「有効な観測行が0件」にする
- `ok` と `blocked` の合計が1件以上なら入力は成立とする
- `ok=0` は正常な探索結果として、全対象を worklist に残す
- 必要なら結果メタデータに `ok_count` と `blocked_count` を出すが、終了コードには反映しない

## 5. リスク

[Warning] 制約欄の「書き込み失敗は警告ログのみ」が、改訂した失敗マーカー契約と食い違っています。

実装者が文字どおり読めば、マーカーを作らずログだけで握り潰す可能性があります。

修正提案: 次のように統一してください。

> アプリ応答には影響させない。書き込み失敗は警告ログを出し、同時に失敗マーカーを best-effort で記録する。生成器がマーカーを検出した場合は終了コード3とする。

[Suggestion] `unresolved_count` は shard ごとに保持するのが適切です。run 全体の合計だけだと、特定 shard の設定不良や大量404を切り分けられません。

## 6. スコープの適切さ

完全性証明や有償の4 shard 実走を今回に含めない判断も妥当です。保証しない範囲が明記されているため、主張の過大化も避けられています。

## 7. 型安全性

[Suggestion] DTOを作らない判断を承認します。

この設計がDTOなしで具体的に壊れる入力は示されていません。以下を満たせば、private helper と配列 shape でも PHPStan level 10 に対応できます。

- route を `Route|null` として絞り込む
- route name を `is_string()` と完全一致の検査後に使用する
- method、run、shard、statusを組み立て前に確定型へ絞る
- JSON化失敗を明示的に処理する
- PHPDoc array shape、または局所的に推論可能な配列リテラルを使う
- `mixed` のまま `preg_match`、パス結合、JSON化へ渡さない

HTTP endpointを追加しないため、DTO/JsonResource規約も直接は適用されません。

- `recorded_at` を持たない: **承認**。run単位ファイルと初期化境界が契約になっており、時刻を使う消費者もありません。
- `build_executed.py` に `operations.md` を読ませない: **承認**。分母の解釈を照合器に一元化する方が整合的です。
