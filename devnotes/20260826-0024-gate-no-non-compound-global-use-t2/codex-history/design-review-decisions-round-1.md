# 対応マトリクス: design-review Round 1

## [Critical] 施策2: 検出側検体が個別に発火することを保証していない
- 判断: 対応する
- 根拠: 指摘どおり。合計 > 0 の床では新検体の真値と走査が両方 0 件でも緑になり得る。
  `GLOBAL_USE_FIXTURES` の `true` は「php -l が警告を出す形」という契約であり、
  契約は検体ごとに検査すべき。
- 対応内容: 既存の「真値が空振りしていない」検査を「検出側の各見本から真値が取れている」
  (検体ごとの非空) へ置き換える設計にした。警告数の検体ごとの数 pin は、既存の
  名前・行の完全一致照合が真値との件数一致まで固定するため追加しない (二重化の回避)。

## [Warning] 施策1: fail-first の手順が再現不能 (buildProcess 未定義で落ちる)
- 判断: 対応する
- 根拠: 指摘どおり。未定義メソッド呼び出しの失敗は「env 未配線を検出した」裏取りにならない。
- 対応内容: 3 段の手順へ書き換えた — (1) env なしの `buildProcess()` を振る舞い変更なしで
  抽出 (緑のまま) → (2) 配線検査を追加して `[]` vs `['LC_ALL' => 'C']` の不一致で赤を確認 →
  (3) 明示 env を追加して緑化。

## [Suggestion] 施策1: 保証範囲の表現を builder に限定
- 判断: 対応する
- 対応内容: テスト名を「php -l の Process 組み立てが LC_ALL=C を明示している」へ変更し、
  docblock・D54・リスク欄に「機械保証は builder の明示 env まで。inspect() の経由は
  コードレビューで見る (迂回はこの検査に映らない)」と明記した。テスト用 DI は足さない。

## [Warning] 施策2: 追跡下ファイルの読み込み失敗が fail-open
- 判断: 対応する
- 根拠: 規約 (b)「無言で候補から外さない」への既知の不適合であり、本 PR は同関数を含む
  gate を変更するので同じ変更で直すのが規約の発火条件に合う。
- 対応内容: `globalUseScanTrackedTree()` に注入 seam (`?array $targets = null`) を設け、
  読み込み失敗を `RuntimeException` で走査ごと落とす (追跡下が読めない作業ツリーは異常)。
  自己検査 (存在しないパスの注入 → 例外) を fail-first で先に置く手順を実装手順へ追加した。

## [Warning] 施策2: 旧実装の赤で両方向 (unresolved / 検出漏れ) を同時観測できない
- 判断: 対応する
- 対応内容: 検体照合テストを unresolved と整列済み violations の 1 つの構造比較へまとめ、
  初回の赤で双方の差分が同時に観測できる形にした (無違反側も同形)。

## [Warning] 施策3: D54 の「検査群が保証する」が実強度より広い

  母集団の縮退検査 + 読めないファイルでの失敗) へ書き直した。
