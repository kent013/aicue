全体判定: **CHANGES_REQUESTED**

Round 1 の主要指摘は概ね適切に解消されています。特に「コード到達点」と「宛先集合」の分離、保証範囲の縮小、Stripe 抑制件数ゼロの固定は妥当です。一方、委譲の機械検証と標準形 (1) の説明には、まだ保証と実装のずれがあります。

### 1. 使命との整合性

[Suggestion] 本改善は North Star への直接機能ではありませんが、bug-hunt の継続利用を支える品質基盤として妥当です。

「本 PR 後も SSO 外部遷移が残る」と明示されたため、使命への寄与も過大ではありません。

### 2. 禁止事項違反

[Suggestion] 明示的な禁止事項違反はありません。Architecture テストへの登録、PHPStan level 10、DTO相当の readonly value object 採用も規約に沿っています。

管理外の `.env.bughunt.local` は同一 PR で確実に修正できる成果物ではないため、実装完了条件は追跡対象の example と `config/testing.php` に限定してください。

### 3. 実現可能性

[Warning] 委譲先の「ファイルが存在し、識別子を含む」検査だけでは、委譲先がdeny-by-defaultであることを保証できません。

`SocialProviderTrustPolicyTest.php` に `socialProvidersConfig` という文字列だけ残り、空振り防止や列挙検査が削除されても、結線テストは緑になります。

修正提案: 委譲先が公開する安定した契約を参照してください。例えば、委譲先に型付きの policy descriptor または専用 inventory API を置き、少なくとも次を呼び出して検査します。

- 走査・列挙対象が空でない
- provider 集合と検査済み集合が一致する
- 必須宣言項目が列挙されている

単なるソース文字列検索を結線保証と呼ぶ場合は、「委譲先の意味的な検査内容までは保証しない」と保証範囲を下げる必要があります。

### 4. 期待効果の妥当性

[Warning] SSO provider 追加時に `capability` / `email_trust` を要求することは「明示登録」の強制として妥当ですが、「宛先の信頼性」や「bug-hunt での外部遷移許可」を審査するものではありません。

任意の新 IdP に既存 enum 値を付ければ gate は通るため、「SSO の宛先集合を検知する」は妥当でも、「宛先を許可制にする」とは言えません。

修正提案: §3 を「provider 集合の増加と信頼属性の宣言漏れを検知する」に限定してください。外向き宛先の allowlist や bug-hunt 遷移可否は保証しないと明記すれば十分です。

### 5. リスク

[Suggestion] Stripe の抑制件数をゼロ固定する変更は妥当です。23 site の行・件数固定よりリファクタ耐性があり、抑制による偽陰性を直接可視化できます。

詳細設計では、scanner が「採用結果」と「抑制結果」を別の型付きコレクションとして返し、抑制後に情報を復元しない構造にしてください。

### 6. スコープの適切さ

[Warning] 標準形 (1) の説明がまだ実装内容より強いです。

「`SocialAuthController` 1クラスへの exact-fit 固定」と「新しい到達点は登録すれば通る目録」は別の契約です。後者では、別クラスからの `Socialite::driver()` を新規 entry として登録できるなら、直呼び禁止や1クラス集約にはなりません。

修正提案: 次のどちらかを明示してください。

- Socialite 規則は `SocialAuthController` だけを許可し、他クラスは exemption を含め登録不能にする
- 本 PR は集約・直呼び禁止を保証せず、標準形 (1) の充足は別課題とする

「目録への登録」と「正規経路への集約」は同値ではありません。

### 7. 型安全性

[Suggestion] `ExternalSeamEntry` / `ExternalSeamExemptionEntry` の readonly value object 化は妥当です。

詳細設計では `classification` や「次元」も文字列ではなく enum にし、委譲表にも array shape を残さない構成がPHPStan level 10と整合します。

### 8. 既定拒否

[Warning] Round 1 の反論は、走査根を一般的に `config/` / `routes/` へ広げない点については妥当です。実在する目印に基づいて規則を作る方針は、スコープ原則にも合っています。

ただし「種別 × 次元」の必要次元を人手で定義するだけでは、新しい次元そのものの登録忘れは検出できません。これは仕組み上避けられないため、保証を「既知の次元の網羅」に限定してください。「次元の数え落としを検出可能」は過大です。

修正提案: §3を「登録済みの種別・次元対応に対する欠落を検出する」に変更し、未知の設定面や新SDK表面は検出対象外と§6へ明記してください。

### 9. 二重管理

[Suggestion] 既存目録への委譲、SSO provider 正本の再宣言回避、`AppServiceProvider` の別到達事実という整理は妥当です。Round 1 の指摘は解消されています。

### 10. 保証範囲の誠実さ

[Warning] §6は大幅に改善されていますが、次の2表現だけ修正が必要です。

- 「種類の数え落としが検出可能」→「登録済みの種別・次元対応の欠落が検出可能」
- 「標準形 (1) と同値」→ Socialite の他クラス登録を禁止する場合に限って使用

修正提案: 委譲検査の意味的限界も§6へ追加するか、観点3のとおり委譲契約を構造化してください。

結論として、Round 1 の `config/` 一般走査不要という反論と、23 site固定を採らない反論は妥当です。残る変更要求は、**委譲を文字列存在確認より強い契約にすること**と、**目録登録を直呼び禁止・集約と同一視しないこと**です。
