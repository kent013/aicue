# 対応マトリクス: conceptual-review Round 1

Round 1 の全体判定は **APPROVED**。Critical は 0 件。Warning 3 件・Suggestion 5 件を以下のとおり捌いた。

## [Warning] 到達条件同一の主張は、Feature テストで機械保証せよ (Codex は実読していない)

- 判断: **対応する**
- 根拠: Codex はツール制限に従いリポジトリを実読していないと自己申告しており、こちらの実読結果
  (routes/web.php:189 / :453 / :593、両 controller の `Gate::authorize('view', $manual)`、
  `VideoManualPolicy::view()` の委譲) を検証していない。主張の根拠が人間の実読 1 回だけなのは弱い。
- 対応内容: 実装方針のテスト欄を書き換え、**撮影者 (project_member) が
  `capture.manuals.show` と `projects.manuals.show` の両方を 200 で開ける**ことを 1 本の
  Feature テストで固定する形にした (片方だけでは「同じ条件である」ことを言えない)。
  概念設計の「出し分けをしない — その根拠」にも、この主張がテストで固定される旨を追記。

## [Warning] 復路用の新しい状態述語も作らず、認可はサーバに任せて単純リンクに留めよ

- 判断: **対応する** (既に設計の方針と一致。明文化して固定する)
- 根拠: 指摘のとおり。復路のために新しい述語を作れば、それ自体が次の二重管理になる。
- 対応内容: 「出し分けをしない」節に **復路専用の述語も新設しない**ことを明示的に追記した
  (「`isCaptureNavigable` を流用しない」だけだと、代わりに新述語を作る読み方が残るため)。

## [Warning] PWA scope の推論は設計根拠として弱い。効果の前提にしすぎるな

- 判断: **対応する**
- 根拠: 妥当な指摘。manifest に `scope` 宣言が無いことは実読で確定しているが、
  「既定 scope が `/` になる」は仕様の読みであり、ブラウザ実装の実挙動を測っていない。
  これを効果の前提に据えると、実機で外部ブラウザに飛んだ場合に設計の主張ごと崩れる。
- 対応内容: 「制約・前提」から**効果の前提としての記述を外し**、「保証しないもの」節を新設して
  そちらへ移した。あわせて期待効果の文からも standalone 前提の断定を外し、
  「ブラウザの戻るボタンに依存しないで済む」という、scope の解釈に依存しない言い方へ改めた。
