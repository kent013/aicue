# 対応マトリクス: conceptual-review Round 3

## [Critical] global `downloaded_at` × `downloaded===false` 限定 → 別端末で ACK 済みテイクは新端末に自動取得されず、doc/05 §5.3 を「端末ごと」に読むと満たさない
- 判断: **対応（Codex 提案の選択肢 1 を採用 = v1 プロダクト不変条件を明記）**
- 根拠（コード事実で裏付け）:
  - `downloaded_at` の**唯一の書き込み経路は `CaptureTakeService::markDownloaded`**（撮影 PWA の署名 ACK 経由）。PC 側（doc/04）の「ダウンロード」は**完成 mp4 マニュアルの DL** であって `downloaded_at` を触らない（別概念）。よって `downloaded_at` は撮影 PWA のみが立てる同期状態。
  - doc/02 §2.3 が定める**強制されるべき不変条件は「PC↔アプリ二重登録防止」**であり、これは**ワークフロー全体（manual/take 単位）でグローバル**な性質。doc/05 §5.3 の「端末へ」は達成メカニズムの記述。
  - 加えて本設計は v1 で**バイトの端末永続保存を行わない**（スコープ外）。従って「端末ごとに取得」しても**端末固有の durable な便益は無い**。一方で端末別状態を導入すると端末識別 + 端末別 ACK レコードが必要でスコープ爆発。
  - v1 は**単一 Default Project**、かつ 1 つの manual を複数端末が同時撮影する運用は v1 の想定外。
- 対応内容:
  - 概念設計に**プロダクト不変条件**を明記: 「v1 では撮影の download/sync 状態（`downloaded_at`）は**ワークフロー全体（take 単位）の "取得済み・同期済み" 状態**であり端末単位ではない。1 manual に対する撮影クライアントは実質単一を想定。強制する不変条件は doc/02 §2.3 の『PC↔アプリ二重登録防止』でありグローバル状態で満たされる」。
  - doc/05 §5.3 の「端末へ」を上記意味に沿って改訂（「端末へ取得（ワークフロー同期状態として記録）」）。
  - 複数端末での入室毎取得（per-device 再取得）は**v1 スコープ外**として明記（将来必要になれば端末別 ACK を別設計）。
  - 監査ギャップ #6 は「入室時に採用済みテイクを自動取得し同期状態を UX に反映する」＝**このグローバル同期モデルで解消**とする（correctness の二重登録は元々冪等キーで防止済み）。

## [Warning] Content-Length と drain バイト数比較は Content-Encoding 付きレスポンスで不一致になり得る
- 判断: **対応**
- 根拠: fetch body は復号後、`Content-Length` は転送時表現サイズになり得る。
- 対応内容: サイズ一致判定は **`Content-Encoding` ヘッダが無く、かつ `response.body` が非 null の場合のみ**適用する。`body === null` は取得失敗として扱う旨を明記。

- 判断: **対応済み**（doc caveat + 不変条件明記で条件を満たす）
