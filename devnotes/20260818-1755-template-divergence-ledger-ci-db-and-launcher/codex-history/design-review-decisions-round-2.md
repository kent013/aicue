# 対応マトリクス: design-review Round 2

## [Warning] D30 の「同じ DROP の境界へ合流する」と挙げたテストの対応が読めない (施策 2)

- 判断: 対応する (合流を固定するケースが実在したので特定した)
- 根拠: `tests/Unit/Ci/DropTestDbScriptTest.php` を読み直すと、合流はケース名で固定されていた。
  - `wires the drop outcome into the --apply exit code end to end` —
    `--apply` の削除が `dropTestDbDropAll()` (通常の回収と同じ guard ループ) を通り、
    その結果から終了コードが決まることを、注入した実行境界で通しで見る
  - `exits non-zero from --apply if a dev database somehow reached the approved target list` —
    分類側が壊れて承認済みの一覧に dev DB が紛れても、末端の guard が skip して
    実行境界へ 1 件も到達しないことを見る
  - 実行境界へ何が渡るかを見る 3 ケース (`never passes the dev database to the SQL executor` ほか) は
    この 1 本の guard ループを対象にしている
- 対応内容: 登録メタ表の保証機構を「`--orphans --apply` の削除も通常の回収と同じ guard ループ
  `dropTestDbDropAll()` を通り、そこへ dev DB と allowlist 外の名前が到達しない」へ具体化し、
  本文の不変条件にケース名を明記した。テスト計画の「新規テスト不要」の根拠にも同じケース名を書いた。

## [Warning] D31 の「同じタイミング」と警告タイミングの差が同居している (施策 3)

- 判断: 対応する (Codex の修正案 1 と 2 の両方を採る形で書き分けた)
- 根拠: 指摘のとおりである。警告のタイミングの差は**振る舞いとして観測できる**ので、
  構文差とは言えない。「揃えている不変条件」と「揃っていない振る舞い」を混ぜて書いていた。
- 対応内容:
  - 「なぜ正当な差分か」を、揃っているものと揃っていないものの 2 つの箇条書きへ分けた。
    揃っているのは「代替を探すこと」「採用したことを知らせること」「完全一致では黙って起動すること」
    「実体が無ければ明示エラーで止めること」まで。揃っていないのは
    **拡張が 1 つも入っていない環境での知らせ方**と、関数が版を返すかパスを返すかである
  - 揃っていない側について、本アプリがこの形を保つ理由を書いた
    (分かりきった失敗に警告を足しても読み手の判断は増えず、警告が出ない状態を
    負のコントロールとして固定してある)。同時に、どちらを正典とするかは本アプリだけでは
    決められないので `監視中` にすると続けた
  - 比較表の行を「拡張が 1 つも入っていない環境」と「代替を採用したときの知らせ方」の 2 行へ割った
  - 「保証しないもの」の先頭に「警告をいつ出すかは正典と揃えていない」を足した
  - 登録メタ表の不変条件も「完全一致が無ければ代替を探して採用したことを警告で知らせること、
    完全一致のときは黙って起動すること」へ書き直した

## [Warning] D31 のメタ表の理由が、現在の理由ではなく T181 当時の経緯に寄っている (施策 3)

- 判断: 対応する
- 根拠: 指摘のとおりである。正典は今なら読めるので「読めなかった」は現在の登録理由にならない。
- 対応内容: メタ表の説明を現在形へ直した — 「起動ラッパは開発で必ず通る経路で、拡張の置き場も
  接尾辞の綴りも環境で変わるため完全一致だけを見る形では起動できない環境が残る。この経路は
  正典に無い時点で別実装として先に固定したもので、正典が同じ目的の経路を別の形で持った今も、
  家系の正典形が決まるまでは検証済みの挙動を裁定なしに変えないため期限付きで現状を保つ」。
  T181 当時の事情は本文の経緯として残した。

## [Warning] 実装モードの説明が「実装は必ず worktree で行う」と矛盾する

- 判断: 対応する
- 根拠: 指摘のとおりである。`incremental` / `standalone` は「他の施策と並行できるか」の軸
  (`app-todo-add` スキルの定義) であって、worktree を使うかどうかの軸ではない。
  規模を理由に worktree 運用を外すと読める書き方になっていた。
- 対応内容: 判断根拠を「実装そのものは AGENTS.md §worktree 運用ルールどおり `todo/<task-id>` の
  worktree で行う (ここは規模で外さない)。`incremental` は他施策と並行できるという意味である」
  へ直した。
