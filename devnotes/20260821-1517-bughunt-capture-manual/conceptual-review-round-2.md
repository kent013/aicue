全体判定: **APPROVED**

Round 1 の主要な問題は解消されています。特に F-1-02 を「未確認のガード実装」ではなく、「Phase A で原因を確定し、確認されたアプリ経路だけを Phase B で直す」構造に変更した点は妥当です。以下は詳細設計で詰めるべき残存事項です。

### F-1-02

[Warning] `409 + X-Inertia-Location` の遷移先が常に現在 URL とは限りません。アセットバージョン不一致では現在 URL の再読込になりますが、アプリが `Inertia::location()` を返す場合は別 URL も指定できます。現在の記述は両者を一括りにしています。

修正提案: 次のように分類してください。

- アセットバージョン不一致による 409: 現在 URL のハードリロード
- アプリが明示する `Inertia::location()`: ヘッダ値で指定された URL へのハードビジット
- `window.location` やハーネス操作: Inertia 外の document navigation

Phase A では、ステータスコードだけでなく `X-Inertia-Location` の実値も記録してください。

[Warning] Phase B のガード条件に若干の不整合があります。「確認できた既知の programmatic visit に限定」と「`/app/` 外への programmatic visit を既定拒否」では、後者の方が広い契約です。また認証失効・権限変更・エラー応答を、`before` 時点で常に識別できるとは限りません。

修正提案: 詳細設計ではガードを次のどちらかに確定してください。

- 検出された発火元または visit 種別だけを拒否する。
- Capture が発行する visit を許可リスト化し、それ以外を拒否する。

後者を採る場合、サーバ応答後に発生するハードビジットはガードの保証対象外と明記してください。「認証失効等を判定して通す」と、実際には判定できない契約にしないことが重要です。

[Warning] 一回限りの明示遷移トークンは実現可能ですが、「短命」の時間だけに依存すると、別の非同期 visit がトークンを消費する競合が起こり得ます。

修正提案: トークンは時間だけでなく、遷移先、HTTP method、単一消費を組み合わせてください。リンク押下時に設定し、対象 visit の成否にかかわらず直ちに破棄し、unmount 時にも必ず破棄する設計が必要です。PC 詳細リンクを削除できるなら、その方が小さい設計です。

[Warning] ハードロード後にすべての一時状態を「復帰」できるわけではありません。特に、まだ IndexedDB キューへ保存されていない `<input type="file">` の選択内容は、ブラウザの安全境界上、自動復元できません。

修正提案: 状態ごとに保証を分けてください。

- キュー保存前のファイル選択: 再選択を明確に案内する
- キュー保存後のアップロード: IDB から再開する
- サーバ保存済み・未採用 take: 再取得して採用操作へ戻せる
- UI 状態のみ: 安全な初期状態へ戻す

「復帰導線」と「元の状態の自動復元」を同義にしない表現にすると正確です。

[Suggestion] 通常フローで document navigation が起きないテストと、意図的に reload を発生させて復帰性を確認するテストは分けると、失敗原因が明瞭になります。通常テストだけではハードロード後の回復経路を通りません。

[Suggestion] Playwright の通常の request/navigation イベントだけでは、ブラウザ内部の initiator を十分取得できない場合があります。initiator を必須証跡にするなら Chromium の CDP イベントを使うのか、Playwright で取得可能な範囲に限定するのかを詳細設計で定義してください。

### F-1-01

[Warning] 「最新」の決定規則を明示する必要があります。日時だけの並び替えでは、同一時刻の行がある場合に結果が非決定的になり得ます。

修正提案: 既存のドメイン規則に従い、例えば `created_at DESC, id DESC` のような安定した順序を relation に固定してください。Feature テストにも複数行を置き、最新 1 件だけが公開されることを含めてください。

[Suggestion] `uploadedAt` は ISO 8601 に加えてタイムゾーンを含む形式に固定してください。PHP DTO、Feature テスト、TypeScript 型の境界がさらに明確になります。

### F-1-03

[Warning] 404・422・403を個別に確認するだけでは、「テナント境界が FormRequest より前」という実行順を固定できません。保護キーを含む不整合 nested route が 422 を返しても、個別テストはすべて通る可能性があります。

修正提案: 少なくとも次の組み合わせテストを追加してください。

- 別 manual／別 cut／別組織の nested route ＋ 保護キー payload → 422 ではなく 404
- 正しくネストされた未認可対象 ＋ 保護キー payload → 運用契約に従い 403
- 正しくネストされ認可済み ＋ 保護キー payload → 422

これにより、binding → テナント境界 404 → FormRequest → 認可という実際に求める順序を検証できます。既存アプリの認可と FormRequest の正規順序が異なる場合は、その正本に合わせて期待値を確定してください。

### 総括

使命との整合、Laravel/Svelte での実現可能性、DTO の型契約、スコープ制御はいずれも承認可能です。ハーネスのノイズを認めつつ Phase A をアプリ側の回帰テストとして残す判断にも価値があります。一方、原因未確認のままガードを必須実装しない条件が重要なので、Phase A でアプリ起因経路が確認されなければ Phase B は実装しない、という判断基準を維持してください。
