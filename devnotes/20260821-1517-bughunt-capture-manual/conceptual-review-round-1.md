全体判定: **CHANGES_REQUESTED**

主な理由は F-1-02 です。報告された「フルドキュメント遷移」を、提案する Inertia `before` ガードでは防げず、かつ「明示操作由来」の判定方法が設計されていません。計測段は妥当ですが、恒久ガードは対象・保証範囲を組み直す必要があります。

### 1. 使命との整合性

[Warning] F-1-02、F-1-01 は「スマホで迷わず撮る」「SOP 登録を確信をもって進める」という North Star に直接寄与します。特にアップロード後・採用前の中断は、撮影ナビゲーションの連続性を壊すため優先度は妥当です。

修正提案: F-1-02 の成果を「意図しない離脱を防ぐ」と広く表現せず、「Inertia 経由の想定外の `/app/` 外遷移を防ぐ」と限定し、フルロードについては計測・原因是正の対象として分離してください。

[Suggestion] F-1-01 の最新 SOP 表示は、単なるファイル名表示でなく「現在この手順書をもとにシナリオを作成する」という意味づけがあると、SOP 起点という製品の核がより明確になります。

### 2. 禁止事項違反

[Suggestion] 設計上、`response()->json()` 直書きや Prism 直呼び、disabled UI は提案されておらず、禁止事項との明白な衝突はありません。

[Warning] 「実装の最初に計測」とありますが、新規ガード・DTO・FormRequest の実装はテストファースト原則の対象です。計測コードだけを先行させるなら、それが一時的診断なのか恒久テレメトリなのかを明示しないと、未検証の恒久コードが残り得ます。

修正提案: 計測を開発時の再現手順／Browser テストの観測として扱うか、製品コードに残すなら計測の保存先・個人情報・削除条件・テストを詳細設計に追加してください。ガード、DTO、FormRequest はそれぞれ失敗テストを先に置いてください。

### 3. 実現可能性

[Critical] Inertia の `before` は Inertia visit のキャンセル機構であり、報告された `window.location`、ブラウザ外部操作、`409 + X-Inertia-Location` によるハード遷移を止められません。しかもコード調査では PC 詳細への決定的な Inertia 経路は見つかっていません。したがって、現設計の恒久ガードは主要障害の再発防止策としては成立しません。

修正提案: 次の二段に明確に分離してください。

- Browser テストを含む単一セッション計測で、実際の document request、Inertia visit、URL、initiator を確定する。
- アプリ起因の Inertia 外部遷移が確認できた場合のみ、その具体的な発火元を修正する。恒久ガードを残す場合も、「検出済みの programmatic visit に対する回帰防止」に限定する。

[Critical] 「明示リンクの押下由来 visit」を `before` イベントだけで堅牢に判定する設計が欠けています。visit の URL だけでは、利用者クリックと同じ URL への programmatic visit を区別できません。安易に `/projects/...` を許可すると、まさに止めたい programmatic 遷移も許可されます。

修正提案: 原則として Capture 画面からの `/app/` 外への programmatic visit を禁止し、PC 詳細への遷移を許す必要があるなら、そのリンクのクリックハンドラで短命・一回限りの明示遷移トークンを設定するなど、利用者操作を明確に帰属させてください。可能なら、画面遷移を許可するリンク自体を最小化し、Capture 画面に不要な PC 詳細リンクを置かない判断も検討対象です。

[Warning] `beforeunload` はフルページ離脱の観測補助にはなりますが、遷移先・発火元・ネットワーク種別を十分に特定できません。

修正提案: Browser テストまたは検証ハーネス側で、document navigation と XHR/fetch を分けて記録し、リクエスト URL・レスポンスの `X-Inertia`／`X-Inertia-Location`・initiator を残してください。

### 4. 期待効果の妥当性

[Critical] 「ハードビジットは同一 URL 着地で撮影データは失われず、実害が小さい」は根拠不足です。同一 URL でも、選択中カット、ファイル選択、進行中のアップロード UI、未採用 take など、クライアント上の一時状態は失われ得ます。さらに報告の PC 詳細への遷移は、この前提では説明できません。

修正提案: ハードリロード時に失われる状態を列挙して確認してください。失われるなら、原因を直すまで「実害が小さい」とは扱わず、少なくとも復帰導線・未採用 take の可視性・アップロード再開の挙動を Browser テストで固定してください。

[Suggestion] F-1-01 の表示改善効果は合理的です。ただし「選択済み」はアップロード済みではありません。create 画面では「選択したファイル」、show 画面では「現在登録されている手順書」と文言を明確に分けるべきです。

### 5. リスク

[Warning] URL 空間で広く `/app/` 外への遷移を止めると、認証失効、権限変更、障害ページ、将来の正規遷移まで覆い隠し、利用者を Capture 画面に閉じ込める危険があります。さらに `reloadManual()` の visit 形態や Inertia のイベント契約を誤解すると、更新・復帰フローを止める後退になります。

修正提案: ガードの対象を「Capture/Show が自ら起こし得ない、既知の外部 programmatic visit」に狭め、認証・エラー応答・外部リダイレクト時の挙動を明文化してください。`reloadManual()`、明示リンク、ブラウザ戻る／進む、offline/online 復帰を含む回帰テストを置いてください。

[Warning] SOP メタデータは、ファイル名に業務情報・個人情報が含まれる可能性があります。既存の `hasDocument` より露出範囲が増えます。

修正提案: `VideoManualController::show` の既存認可・組織境界の内側で、当該 manual に属する最新 source document のみを relation 経由で取得してください。DTO は必要最小限の `name`、`size`、`uploadedAt` に限定し、他組織・他 manual のメタが出ない Feature テストを追加してください。

### 6. スコープの適切さ

[Warning] F-1-02 は原因未確定のまま恒久ガードまで入れるため、現状では過大です。一方、ハーネス多重実行が真因ならアプリ修正だけでは再現性のある bug-hunt を回復できず、計測結果の orchestrator への申し送りだけでは不十分になり得ます。

修正提案: 今回の必須成果を「単一セッションでの再現・分類・回帰テスト」に置き、恒久コードは確認したアプリ起因経路だけに限定してください。ハーネス側はスコープ外でよいですが、重複実行を検出・失敗させる責任者とチケットを明記してください。

[Suggestion] F-1-01 を最新 1 件の表示に絞るのは v1 と immutable SOP の前提に合っており、適切です。履歴 UI や複数文書管理を含めない判断も妥当です。

### 7. 型安全性・Laravel パターン

[Warning] `SourceDocumentSummaryData` を Inertia props に載せる方針は適切ですが、nullable 条件、日時の表現、ファイルサイズの型・単位を契約化しないと Svelte 側との型ずれが起きます。

修正提案: `SourceDocumentSummaryData` を `name: string`、`sizeBytes: int`、`uploadedAt: string` のような API 向け不変 DTO とし、未添付時は DTO を `null` にしてください。PHP の `toArray()` と TypeScript Props 型、Feature テストで同一契約を固定してください。表示用のサイズ・日時整形は Svelte 側で行い、DTO に表示文言を混ぜない方が保守しやすいです。

[Suggestion] `AdoptCaptureTakeRequest` と `ProhibitsProtectedKeys` の採用は、既存の保護キー防御に整合しています。body を使わない操作に最小限の検証だけを追加するのも妥当です。加えて、保護キー混入時の 422、正常採用、別 manual／別 cut／別組織の 404、認可 403 の順序を Feature テストで固定してください。

結論として、F-1-01 と F-1-03 は概ね承認可能です。F-1-02 は「観測できない種類の遷移を Inertia ガードで防ぐ」としている点を修正し、発生源の確定、ユーザー操作の帰属方法、ハード遷移で失われる状態の評価を詳細設計に反映すれば、使命に沿った堅実な改善になります。
