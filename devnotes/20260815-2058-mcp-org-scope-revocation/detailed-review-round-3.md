### 施策 5: APPROVE

検査 E は承認できます。

正当な実装を誤って落とす可能性については、`PhpTokenScan::normalize()` が空白・コメントを除外し、文字列内部の `$reason` を `T_VARIABLE` として扱わないため、次のケースは問題になりません。

- PHPDocや行コメントで `$reason` を説明する
- エラーメッセージなどの文字列内に `$reason` と書く
- 空白や改行、コメントをトークン間に入れる
- シングルクォートとダブルクォートの表記差を、トークン値の正規化側で適切に扱う場合

迂回についても、通常の実装手段は閉じられています。

- `if` / `match` / `switch` で使うと参照回数または位置で失敗する
- helper へ `$reason` を渡すと位置検査で失敗する
- metadata 以外で alias 化すると位置検査で失敗する
- metadata を固定値にして別用途で使っても失敗する

`func_get_args()` や `debug_backtrace()` で引数を間接取得するような意図的な字句検査回避までは防ぎません。しかし、それはこの不変条件が対象とする通常の保守変更ではなく、あらゆる動的言語上の迂回を静的検査で禁止するのは現実的ではありません。保証範囲を「`$reason` の直接参照」に限定して書けば十分です。

[Suggestion] 設計書の「文字列リテラルは正規化で除外される」は少し曖昧です。`'reason'` キーの照合には文字列トークンが必要なので、次のように表現すると正確です。

> コメントと空白は除外され、文字列内部の `$reason` は `T_VARIABLE` として数えない。metadata キーの文字列トークンは照合対象として保持する。

実装がこの意味になっていることが前提です。
