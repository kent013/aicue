- MCP サーバ `app/Mcp/Servers/AppMcpServer.php` に登録された道具は 4 本、すべて読み取り

- 外部 API (`routes/api.php`) には**変更系が 3 本ある** (items の作成・更新・削除)。
  これらは `auth:api-key,api-oauth` → `throttle` → `resolve.api-actor` →

- `McpAuthorizationContext::for()` は毎リクエスト、トークンの `organization_id` 解決と

- `OrganizationMembershipService` の `changeRole` / `removeMember` / `transferOwnership` /

  失効の呼び出しは 1 件も無い。

  `IdempotentRouteCoverageTest`、`McpWriteToolIdempotencyEnforcementTest` (書き込み道具 0 本の

  `ProjectMemberPivotWritePathTest`。
- `config/laratrust.php`: 役割キャッシュは `APP_ENV === 'production'` で有効・3600 秒。
- `OauthSession::revoke()` は既に行ロック + 冪等 + 配下トークン失効を持つ。

# 概念設計: mcp-org-scope-revocation (組織の役割変更に同期したトークン失効)

## 背景・課題

### 何が無いのか

機能台帳 lctl の feature `mcp-org-write-scope` は、正典 v2 を
「**組織の役割を変える処理と同じデータベース処理のひとまとまりの中で、その人に発行済みの
機械クライアント向け資格情報を失効させる**」と定めている (裁定 AG-027 / AG-125)。
家系 6 リポジトリのうち laravel-claude-template / aigenba / spirux の 3 本が実装済みで、
aicue は pending である (観測点 aicue@a5553b5)。

本リポジトリの現況を HEAD で実読した結果は次のとおり:

| 要素 | 現況 |
|---|---|
| トークンと組織の結び付け | **有る** (`oauth_access_tokens.organization_id` / `session_id`、`oauth_sessions`) |
| 要求ごとの権限再評価 (MCP) | **有る** (`McpAuthorizationContext::for()` が所属を、`authorizeTool()` が権限を毎回評価) |
| 要求ごとの権限再評価 (外部 API) | **有る** (`ResolveApiActor` が所属とセッション生存を毎回評価、`ItemPolicy` が権限を毎回評価) |
| 更新用トークン発行時の再評価 | **有る** (`McpRefreshTokenGrant::assertSessionRefreshable()`) |
| **役割変更に同期した失効** | **無い** (`OrganizationMembershipService` の 3 経路に失効の呼び出しが 1 件も無い) |
| **失効の監査記録** | **無い** (`SecurityEventType` に該当する種別が無い) |
| **上記の再評価を守る検査** | **無い** (先置きの検査 3 本に相当するものが 0 件) |

### いま実際に起きていること (誇張しない)

**組織から外された利用者が現に読み書きできる状態にはならない**。所属の再評価が MCP・
外部 API・更新用トークン発行の 3 か所すべてに入っているため、失効させなくても要求は拒否される。
これは正直に認めた上で、それでも残っている実害は次の 3 つである。

1. **管理画面が嘘を表示する**。組織の「接続セッション」一覧
   (`/organizations/{slug}/api-keys/sessions`) は `oauth_sessions.revoked_at` が空の行を
   「生きているセッション」として並べる。メンバーを外しても `revoked_at` は空のままなので、
   **管理者は退会済みの人の接続が今も生きていると読む**。管理者にできる操作は
   「1 件ずつ手で失効させる」だけで、外した時点で自動的に片付く経路が無い。
2. **未交換の認可コードが生き残る**。`oauth_auth_codes` は所属が変わっても無効化されない。
   正典の説明文はこの家族を落とすと「失効の直前に発行された認可コードを失効後に交換して
   新しいトークンを得る経路が残る」と名指ししている。本リポジトリでも
   `McpAuthorizationCodeGrant` は交換時に所属を確認しない (確認しているのは更新用トークンの
   経路だけである) ため、外された直後でも交換は成立して新しいトークンと更新用トークンが手に入る。
   得たトークンは使用時に拒否されるので読み書きはできないが、**失効させたはずの資格情報が
   増える**という状態そのものが正典の閉じた穴である。
3. **監査に残らない**。誰の資格をいつ何件失効させたかの記録が無い。組織管理者が
   「本当に切れたのか」を後から確かめる手段が、セッション一覧の目視しか無い。

### いちばん重い問題 — 唯一の防壁が構造的に守られていない

現在の安全は、**要求ごとの再評価 3 か所だけ**に載っている。この 3 か所は
どれも検査 (Architecture テスト) に守られていない。つまり:

- `ResolveApiActor` から所属再評価の 4 行を「毎リクエストのクエリを減らす」目的で外しても、
  テストは 1 本も赤くならない
- MCP の道具に書き込み系を足すとき、`AppMcpTool::handle()` の認可の呼び出しを迂回する
  実装を書いても、テストは 1 本も赤くならない
- 外部 API に新しい変更系の経路を足すとき、`api-key.ability:write` を付け忘れても、
  テストは 1 本も赤くならない (読み取り専用のトークンで書き込める)

正典が「先置きの検査 3 本」を持っているのは、まさにこの状態を作らないためである。

## 改善アイデア

正典 v2 を本リポジトリの形に合わせて導入する。3 本柱:

### A. 失効の唯一の窓口を作る

`App\Services\OAuth\OrganizationAccessRevoker` を新設し、
「**ある組織における、ある利用者の、人に委ねられた資格情報**」を 3 家族まとめて失効させる。

- 家族 1: `oauth_sessions` (未失効のもの) と、その配下の利用トークン・更新トークン
- 家族 2: `oauth_access_tokens` のうち `session_id` が空のもの (セッション行を持たない
  古い MCP トークン。**接続セッション一覧に現に並んでいる**) と、その更新トークン
- 家族 3: 未交換の `oauth_auth_codes`

**途中で打ち切らない**。家族 1 が 0 件でも家族 2・3 は必ず撃つ。

失効の境界は「**役割を変える操作が成功したこと**」に置き、**役割の集合の差分は取らない**。
差分を取ると、権限ライブラリの役割キャッシュ (本番では 1 時間有効) に依存した判定になり、
取りこぼしたときに通してしまう側に倒れるためである。

組織が持つ API キー (`api_keys`) は**失効させない**。API キーは組織の資産で、
人の所属が変わっても組織のものであり続けるためである (実行時の判定は
`ResolveApiActor` が発行者の所属を毎回見ることで担保されている)。この境界は
正典 3 本と同じである。

### B. 役割を変える経路へ配線する

`OrganizationMembershipService` の役割を変える経路に、**同じデータベース処理の
ひとまとまりの内側で、役割の入れ替えの後に**失効の呼び出しを置く。

- `changeRole()` — 役割の入れ替えの直後
- `removeMember()` — 除名の直後
- `transferOwnership()` — 旧オーナーと新オーナーの**両方**に対して
- `normalizeOrganizationRole()` の修復経路 (役割未付与の異常行へ直接付与する枝)

「ロックの内側に入れるか後に置くか」は**内側**とする。理由は 3 つ:

1. 役割の変更が巻き戻れば失効も巻き戻り、失効が失敗すれば役割の変更も巻き戻る
   (「役割は下がったのにトークンは生きている」「トークンは切れたのに役割は元のまま」の
   どちらの中間状態も作らない)
2. 外に出すと、ひとまとまりが確定してから失効するまでの間にプロセスが落ちると
   失効が無言で消える (正典 v1 が非同期の購読で失効させて作ってしまった隙間そのもの)
3. 本リポジトリの既存規約 (ドメイン規約 11「業務状態の保存とキュー投入は同一トランザクション内」)
   と同じ考え方であり、新しい流儀を持ち込まない

さらに、窓口の側で「ひとまとまりの外から呼ばれたら例外で拒否する」実行時の強制を持つ
(家系では aigenba だけが持つ形)。説明文とテストだけで守るより確実で、追加費用は 1 行である。

### C. 先置きの検査 (既定拒否) を 3 本置く

**既存の検査と重ねない**ことを設計条件にする。本リポジトリには既に
`MembershipWriteLockInventoryTest` (メンバーシップ書き込みのロック規約と役割付与の単一窓口)、
`ApiGuardAllowlistInvariantTest` (外部 API の認証分類)、
`McpWriteToolIdempotencyEnforcementTest` (書き込み道具の冪等キーの据え置きの目印)、
`ToolNameInvariantTest` があるので、足すのは**そこに無い次の 3 つ**に限る。

1. **失効の配線の検査**: 役割を変えるメソッドを全数列挙し、「失効を呼ぶ」か
   「根拠 30 文字以上を添えて免除に登録する」かの二択を強制する (既定拒否)。
   呼ぶ側には「同じメソッドの中」「ひとまとまりの内側」「役割の入れ替えより後」の 3 条件を課す。
   併せて、失効に使う列 (`oauth_*` の失効列) へ書き込めるクラスを窓口 1 本へ固定する。
2. **外部 API の書き込み経路の検査**: 変更系の route が書き込みの資格検査
   (`api-key.ability:write`) をちょうど 1 本持つことを強制し、持たないものは
   根拠付きで目録へ登録させる。併せて、主体の解決が資格検査より前に走ることを固定する。
3. **MCP の認可の関門の検査**: 登録された道具がすべて基底を通り、基底の実行部が
   認可の再評価を**業務処理より前に**呼ぶこと、認可の文脈クラスが差し替え不能であること
   (final) を固定する。

書き込み道具が増えたときの目印は既存の `McpWriteToolIdempotencyEnforcementTest` が
すでに持っているので、**そこには作らない**。失敗時の案内文に 1 行足すだけにする。

## 期待効果

- **使命への貢献**: 現場の作業手順書と撮影素材は顧客の業務そのものである。
  組織から外れた人の手元に生きた鍵が残らないことは、この預かりものを扱う前提条件になる。
  「外した」という管理操作が実際に効いたことを管理画面と監査記録で確認できるようになる。
- 接続セッション一覧が現実と一致するようになる (退会済みの人の接続は失効済みとして表示される)。
- 未交換の認可コードから新しいトークンが生まれる経路が閉じる。
- 現在ただ 1 つの防壁である「要求ごとの再評価」が構造的に守られ、
  性能改善や新経路の追加で無言で外れることが無くなる。

## 制約・前提

- 権限ライブラリの役割キャッシュは**本番で有効** (`config/laratrust.php` の
  `enabled` が `APP_ENV === 'production'`、保持 3600 秒)。差分判定を採らない理由の実測根拠。
- `OauthSession::revoke()` が既に「行ロック + 冪等 + 配下トークンの失効」を持っている。
  窓口はこれを**作り直さず再利用**する (思考原則 1)。
- `SecurityEventRecorder::record()` は例外を握り潰す既定 (best-effort)。失効の監査は
  「書けなければ役割変更ごと巻き戻る」必要があるので、**既存メソッドは変えず**別メソッドを足す。
- `SecurityEventType` に種別を足すと `SecurityEventCoverageTest` の対応表と担保テストの
  追加が必須になる (既定拒否)。
- 失効はテナント境界を跨がない。窓口は必ず (組織, 利用者) の 2 つで絞る。

## 代償 (受け入れる)

**役割が上がる変更でも接続はいったん切れる**。差分を取らないので、メンバー → 管理者の
昇格でも、オーナー移譲の受け手側でも、機械クライアントの接続はやり直しになる。
これは正典 3 本が共通で受け入れている代償で、「差分の取りこぼしで通してしまう」より
「余分に切れる」を選ぶ判断である。`docs/mcp-oauth.md` へ既知の仕様として書く。

## 保証しないこと (先に書く)

- **失効の選択と確定の間に新しいトークンが発行される隙間は閉じない**。
  トークン発行の経路は組織行・利用者行のロックを取らないため、
  ひとまとまりの中で失効させても、その最中に発行された資格情報は取り逃す。
  最後の拒否線は要求ごとの再評価が受け持つ (だから C の検査が要る)。
- **プロジェクト単位の役割変更 (`ProjectMemberController`) は失効の対象にしない**。
  トークンが結び付いているのは組織であり、その人はまだ組織のメンバーである。
  プロジェクト単位の権限は要求ごとに `ProjectPolicy` が評価し直すため、
  資格情報そのものを切る理由が無い。「権限が少しでも変わったら全部切る」へ広げない。
- 組織が持つ API キーは失効しない (上記 A の境界)。
- 検査は**字句と反射に基づく静的な検査**であり、失効が実際に走ったことは
  振る舞いのテストが担う。両者は役割が違うので併存させる。

## スコープ外

- **発行時の書き込み範囲の絞り込み** (`McpScopeMinter` 相当)。裁定 AG-027 が
  「実装依存が強い」として推奨パターンの記述に留めており、家系でも aigenba だけが持つ。
  本リポジトリは MCP の書き込み道具が 0 本なので、作る理由が無い (思考原則 2)。
- MCP の書き込み道具そのものの追加。
- MCP の冪等キーの再生判定の位置 (T109。据え置きの目印は機械化済み)。

## Open か Conditional か

**Open とする** (優先度 Medium)。同じく「書き込み道具が 0 本」を理由に条件付き待機に
なっている T109 とは、次の 2 点で構造が違う。

1. **T109 は引き金が到達不能**。MCP の書き込み道具が 1 本も無いので、
   再生判定の位置がずれていても踏みようがない。本件の引き金は
   「役割を変える / メンバーを外す」であり、**今日ふつうに起きる操作**である。
   接続セッション一覧の食い違いと未交換の認可コードは、新機能を 1 つも足さずに現に起きる。
2. **条件付きにすると引き金が書けない**。本件のいちばん重い問題は
   「唯一の防壁が構造的に守られていない」ことで、その引き金は
   「誰かが防壁を無言で外したとき」である。外れたことを検出する仕組みが無いから困っている
   のに、それを待機条件に据えるのは成立しない。

優先度を Critical / High にしないのは、**現に読み書きされる穴は開いていない**からである
(要求ごとの再評価 3 か所が効いている)。この非対称を正直に書き、Medium とする。
