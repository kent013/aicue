全体判定: **APPROVED**

概念設計としては妥当です。現時点で「即読み書きできる穴」と誇張せず、管理画面の不整合・未交換認可コード・構造的防壁の未検査という実害に絞っている点もよいです。実装前に潰すべき点はありますが、設計の方向を差し戻すほどではありません。

**使命との整合性**

[Suggestion] North Star への貢献は本質的です。SOP・撮影素材・動画マニュアルは顧客業務の機密性が高く、退職・異動・権限変更時に「外した操作が本当に効いた」と管理者が確認できることは、PWA 撮影や AI 生成以前の信頼基盤です。

**禁止事項違反**

[Warning] 現時点の設計文には明確な禁止事項違反はありません。ただし実装時に注意が必要です。

修正提案:
- 失効結果の返却は `OrgAccessRevocationResult` DTO に閉じる。
- API 応答で `response()->json()` を増やさない。
- 監査記録の失敗を握り潰さない新メソッドは、既存 `record()` の意味を変えず別名で追加する。
- Architecture/Feature テストを先に赤にしてから実装する。

**実現可能性**

[Warning] 「行ロック下の同一トランザクション内・役割入れ替えの後」は妥当ですが、落とし穴があります。

修正提案:
- `OrganizationAccessRevoker` は外側トランザクション必須を `DB::transactionLevel() > 0` で実行時検査する。
- `OauthSession::revoke()` が内部で `DB::transaction()` を張る場合、Laravel の savepoint 前提で問題ないかを Feature テストで確認する。
- ロック順序は既存の `users 昇順 → organizations 昇順` を崩さず、失効側で追加ロックするなら `oauth_sessions` / `oauth_access_tokens` / `oauth_auth_codes` の順序を固定する。
- 監査イベントの書き込みも同一トランザクション内に入れ、失敗時は役割変更ごと rollback する。

デッドロックについては、手動セッション失効が membership の user/org ロックを取らないならリスクは限定的です。ただし「役割変更中に手動失効」「同一ユーザーへの並行 role change/remove/transfer」は振る舞いテストか低レベルテストで押さえるべきです。

**期待効果の妥当性**

[Warning] 効果は合理的ですが、「未交換の認可コードから新しいトークンが生まれる経路が閉じる」は少し強く見えます。設計自身が「失効の選択と確定の間に新しいトークンが発行される隙間は閉じない」と書いているためです。

修正提案:
- 期待効果は「失効時点で既に存在する未交換認可コードを閉じる」と表現を弱める。
- 可能なら別 TODO として `McpAuthorizationCodeGrant` の交換時にも所属確認を入れる検討を残す。これは本件の主眼ではないですが、現在の穴の説明と自然につながります。

**リスク**

[Warning] 「差分を取らない、昇格でも切る」はセキュリティ側に倒す判断として妥当です。ただし利用者影響はあります。

修正提案:
- 管理画面またはドキュメントに「組織ロール変更時は MCP / OAuth 接続が再認可になる」ことを明記する。
- `transferOwnership()` で新オーナー側も切る仕様は特に驚きが大きいので、テスト名・docs・監査 reason で明示する。
- 失効件数を監査イベントに残し、サポート時に「なぜ切れたか」を追えるようにする。

(c) については、このアプリの利用者にとって受け入れ可能です。頻繁な現場作業ではなく管理操作に伴う再接続であり、「取りこぼして通す」より「余分に切る」を選ぶ方が業務データの性質に合っています。

**スコープの適切さ**

[Warning] スコープ外 3 点の線引きは概ね正しいです。ただし API キーの説明は少し補強した方がよいです。

修正提案:
- 発行時の絞り込み: MCP 書き込み道具 0 本ならスコープ外で妥当。
- プロジェクト単位の役割変更: 失効させない判断で妥当。トークンが組織単位で、プロジェクト権限は `ProjectPolicy` が毎回評価するなら防御の穴ではありません。
- API キー: 「組織資産だから失効しない」だけだと弱いです。`ResolveApiActor` が発行者の所属を毎回見るため、退会者由来の API キーは実行時に拒否される、という実効防御を明記してください。

(d) の答えとして、特に「プロジェクト単位の役割変更は失効させない」は穴ではありません。ただし、将来プロジェクト権限を token claim や ability に焼き込む設計へ変えた場合は再検討条件になります。

**型安全性**

[Suggestion] DTO/Enum/Service の切り分けは PHPStan level 10 と相性がよいです。`OrgAccessRevocationResult` は family ごとの件数を `int` で持つ immutable DTO にし、reason は `OrgAccessRevocationReason` enum に閉じるのがよいです。

**固有判断**

(a) **Open / Medium は妥当**です。T109 は MCP write tool が無いため実行経路が未到達ですが、本件は既存の role change/remove/transfer で今日発火します。区別に大きな穴はありません。

(b) **同一トランザクション内・役割入れ替え後で妥当**です。注意点は nested transaction、追加ロック順序、監査記録の rollback 連動です。

(c) **差分を取らない代償は妥当**です。ロールキャッシュや判定漏れに依存するより、安全側に倒す方がこのアプリの性質に合います。

(d) **スコープ外の線引きは妥当**です。プロジェクト単位の変更を失効対象にしないことは、現設計では防御の穴ではありません。

(e) **先置き検査 3 本は妥当**です。既存検査とは役割が違います。ただし 1 本目の「同じメソッド内・トランザクション内・役割変更後」を静的検査だけで完全保証するのは難しいため、Architecture は構造の固定、Feature は実際の失効順序と rollback を担う、と明記すると堅いです。
