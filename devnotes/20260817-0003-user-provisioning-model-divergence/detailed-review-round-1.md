前提: 今回は指定どおり、提供テキスト内の整合性レビューです。実リポジトリのコード裏取りはしていません。

**A. 見送り判断**
判定: **APPROVE**

[Warning] 見送り判断自体は支持できますが、「情報は満たされている」「日常ログインは入力ゼロ」といった表現はやや強いです。  
修正案: 「最終ログインは監査イベントから導出可能。ただし管理画面要件としては未表示」「パスキー条件が揃う場合は入力負担を下げられる」に弱めるべきです。

[Suggestion] 「削除 = 組織からの除名で満たす」は、要件が users 行削除を意味していた場合に争点になります。「v1 の組織運用上は除名で足りる」と限定すると安全です。

**B. Conditional 昇格条件**
判定: **REQUEST_CHANGES**

[Warning] 適格条件 C「TOTP 2FA を強制しないこと」を昇格の必須条件にするのは厳しすぎます。メールなし参加の問題と、パスキーで入力を減らす問題が混ざっています。  
修正案: C は「認証 UX / 2FA 方針の追加決定点」に落とし、TOTP 強制でもメールなし入口の必要性は昇格可能にしてください。

[Warning] 適格条件 D「メールなしで本人だけが回復する手段は存在しない」は断定が強いです。リカバリコード、管理者承認付き再発行、端末・パスキー再登録など代替設計はあり得ます。  
修正案: 「現行の Fortify email broker では自力回復できない。採るなら代替回復方式を別途設計する」と書き換えるべきです。

**C. 将来実装する場合の参照設計**
判定: **REQUEST_CHANGES**

[Critical] 第1段「招待リンク手渡し + メール検証免除」は、現状のままだと本当に「メールを1通も送らずに撮影者を増やす」を成立させる設計として不足しています。email 識別子を維持しつつ「ダミーでよい」とすると、パスワードリセット、通知、検証メール、誤配送、実在ドメインへの送信が未整理です。  
修正案: 第1段に最低限、以下を決定点として追加してください: synthetic email のドメイン規則、メール送信抑止、password reset の扱い、verification notification の抑止、通知経路、初回パスキー登録強制の有無。

[Critical] 平文 token の画面表示リスク評価が不足しています。肩越し・スクショだけでなく、Inertia props、ブラウザ履歴、サーバーログ、Referer、キャッシュ、bfcache、コピー後の再表示、監査対象が問題になります。  
修正案: 「発行直後1回のみ」「保存しない」「短 TTL」「single-use」「再表示不可」「no-store」「外部 Referer 漏れなし」「閲覧/コピー/再発行/失効の監査」を第1段の必須設計にしてください。

[Warning] `email_verified_at` を立てる設計は、「メール所有確認済み」と「招待手渡しで業務利用を許可」を同じ状態に畳みます。  
修正案: 既存 middleware との兼ね合いでやむを得ず `email_verified_at` を使う場合も、別カラムまたは監査イベントで `verified_by_invitation_handoff` 相当の由来を残すべきです。

**D. template-divergence 判断**
判定: **REQUEST_CHANGES**

[Warning] 「新規エントリは機械検査で作れない」は根拠として弱いです。記録すべき逸脱なら、台帳構造や既存 D8 を直してでも記録すべきだからです。  
修正案: 根拠 3 は削るか、「補助的事情」に格下げしてください。

[Warning] 「台帳対象外」と「該当部分は D8 登録済み」が少し噛み合っていません。D8 が管理 UI / ロール語彙の逸脱なら、認証識別子そのものを D8 がカバーしているとは言い切れません。  
修正案: 主根拠を「テンプレートからの逸脱ではない」に一本化し、D8 は「関連する管理画面差分は既に記録済み」と限定してください。

**E. 最終ログイン日時表示の切り離し**
判定: **APPROVE**

[Suggestion] 独立小改善として切り離す判断は妥当です。ただし「要件未充足の体感の相当部分が消える」は過大評価の可能性があります。ユーザー登録方式の不満とは別物なので、「一覧要件の一部を満たす小改善」に留める方がよいです。

**F. 波及変更の網羅性**
判定: **REQUEST_CHANGES**

[Warning] 将来実装時の波及リストに、メール送信系と回復系が足りません。  
修正案: `Registered` event / verification notification / password reset broker / mail notification suppression / SES suppression / notification fallback / accept URL logs / route middleware tests / no-store 系の確認を追加してください。

[Warning] 第3段の識別子置換は「特大」とありますが、データ移行、既存ユーザーの login_id 採番、SSO 紐付け、サポート運用、監査ログ上の識別子表示、既存セッション・remember token への影響が明示されていません。  
修正案: 第3段は別設計必須とし、移行計画を決定点に追加してください。

**G. セキュリティ整合**
判定: **REQUEST_CHANGES**

[Critical] 招待 token の秘匿設計は、現行の「平文は DB に無い / メールにしかない」から大きく後退します。§6 はその危険を認識していますが、実装条件としての最低ラインがまだ曖昧です。  
修正案: token 表示は「credential disclosure」と明記し、TTL 短縮、single-use、失効、監査、再表示不可、キャッシュ禁止、ログ漏れ対策を昇格時の必須条件にしてください。

[Warning] 共有メールボックス案 A は、責任者が恒久的にパスワードリセットでなりすませる点が重いです。「管理者初期パスワード発行と同等以下」と言い切るのは危険です。  
修正案: 「同等以下」は削り、案 A は「監査上許容される場合だけ採れる運用仮説」として扱うべきです。

**全体判定**
**CHANGES_REQUESTED**
