## [Warning] (C)(G) 引換コードが招待 token と同等の bearer credential として扱われていない

- 判断: **対応する**
- 根拠: 指摘が正しい。§6-2d 方式 1 で新設した「引換コード」は
  **それ 1 つで組織への参加が成立する資格情報**なのに、§6-2c の秘匿条件が
  招待 token だけを対象にしていた。方式 1 を「推奨」と書きながら、
  推奨した側の保護要件が薄いという逆転が起きていた。
  とくに **「短いコードは named limiter で守る」は誤り** — 流量制限は
  エントロピーの代替にならず、共有 NAT (工場・事業所の一括 NAT) では
  正規利用者を巻き添えにし、分散試行には効かない。
- 対応内容:
  - **§6-2c の冒頭に「本節の対象は招待 token だけではない」注記を追加**し、
    引換コードにも 10 条件を同じく適用すると明記。
  - **§6-2e「引換コードを資格情報として保護する」を新設**し、6 要件を定義:
    (1) **CSPRNG 生成 + 最低エントロピーを設計値として明示的に決める**
        (「短いから limiter で守る」を禁止) /
    (2) **平文を保存せず hash のみ** (現行 `OrganizationInvitation` の `token_hash` と揃える) /
    (3) TTL / single-use / 再発行時の旧コード失効 /
    (4) **検証と失効を原子的に行う** — 同時 POST での二重交換を防ぐ。
        本アプリ既存の `joinOrganization` (行ロック + ロック下再検証) と同じ形にする /
    (5) **POST body / validation 例外 / 監査 metadata に平文を残さない**
        (「URL に載らない」だけでは不足) /
    (6) **named limiter を IP 単独依存にしない**。共有 NAT と分散試行の両方を設計時に評価し、
        キーは `{レーン}:{種別}:{値}` 規約に従う。
  - 要件 6 に、本アプリのレート制限規約 (「新しい面には同性質の本番稼働中エンドポイントと同値」)
    との接続を注記。引換コードの面には同性質の既存が無いため
    **新レーンとして `ThrottleLaneAssignmentTest` / `RateLimiterKeyConventionTest` の契約に載せる**
    ことを明記した。
  - §6-2d 方式 1 の代償欄も「§6-2e をすべて満たす必要がある /
    **named limiter はエントロピーの代わりにならない**」へ書き換えた。

## [Warning] (F)(G) §6-7 の「平文 token が URL に出ないこと」は方式 2 では成立しない

- 判断: **対応する (再び本文とテスト計画が矛盾していた)**
- 根拠: 指摘が正しい。§6-2d 方式 2 は
  **「初回受諾要求の URL に token が載ることを許容し、直後に session 退避して
  token なし URL へ redirect する」**方式である。
  それなのにテスト計画が「URL に出ないこと」を共通条件として要求していた =
  方式 2 を選ぶと**設計書の中で期待値が衝突する**。
  Round 2 で本文は直したが、**テスト計画側の同期が漏れていた**。
- 対応内容: §6-7 の露出面テストを**方式別の表**に差し替えた。
  - 方式 1: token も引換コードも **URL に 0 件**。
  - 方式 2: **初回受諾要求の URL に token が載ることだけを限定的に許容**。
    redirect 後の URL には含まれない / 遷移後の `Referer` に出ない /
    **アクセスログ・例外ログには残らない** (「URL に載ること」と「ログに残ること」は別、と明記) /
    Inertia history・bfcache 復元に残らない。
  - **共通**: POST body / validation 例外 / 監査 metadata を含め、
    資格情報がアプリケーションログに保存されないこと。

## [Warning] (F) 方式 2 では「既存メール招待経路が一切変わらない」テストも成立しない

- 判断: **対応する**
- 根拠: 指摘が正しい。方式 2 は既存の受諾 route を通るため、
  安全化 (session 退避 / redirect / ログマスク) が**既存のメール招待にも掛かる**。
  Round 2 で注記は足したが、**箇条書きの期待値自体が旧のまま**だった。
- 対応内容: 独立した箇条書き「既存のメール招待経路が一切変わっていないこと」を削除し、
  上の方式別表の最終行へ統合:
  **方式 1 = 一切変わらない / 方式 2 = 意図した安全化以外の既存挙動が変わらない**。

## [Suggestion] (F) §6-4 の回復系に「送信しましたと嘘をつかない」の旧表現が残っている

- 判断: **対応する**
- 根拠: §6-2a(e) を Round 2 で「応答を分けない = 列挙オラクルを作らない」へ直したのに、
  波及変更表の 1 セルが旧表現のまま残っていた (同期漏れ)。
  旧表現のままだと、実装者が波及表だけ見て**列挙オラクルを作ってしまう**。
- 対応内容: 該当セルを
  **「一般化応答を維持し、列挙を生まない経路で回復方法を事前提示する。応答を利用者ごとに分けない」**
  へ統一した。
