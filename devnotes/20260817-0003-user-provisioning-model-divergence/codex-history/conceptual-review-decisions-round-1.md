# 対応マトリクス: conceptual-review Round 1

**Codex 全体判定: APPROVED** (Critical 0 / Warning 4 / Suggestion 6)。
判定は APPROVED だが、Warning 4 件はすべて「主張が強すぎる」型の指摘であり、
見送り結論の説得力に直結するため**全件対応**した。

## [Warning] (b) 案 A の評価がやや強い — 「成立しうる運用」であって「現場で成立する」とは言えない

- 判断: **対応する**
- 根拠: 指摘が正しい。共有メールボックス + パスキーは**技術的に成立する**ことしか
  確認できておらず、規程・監査・端末・退職時回収まで含めた実地成立は未検証である。
  「解決した」と書くと、見送り結論が未検証の仮説に依存することになる。
- 対応内容:
  - §3 の見出しを「現行のまま成立**しうる**運用があるか (現場検証前の第一候補)」に変更し、
    冒頭に「運用仮説であって実証ではない」旨の枠を追加。
  - **§3-4「案 A が成立するための条件 (現場検証で確かめること)」を新設**し、
    Codex が挙げた 3 条件 (責任者がメールを受け取れる / 作業者ごとにパスキー登録 /
    端末 PIN・OS アカウント運用で本人性を許容) に、
    代行登録の監査上の許容・TOTP 非強制・**退職異動時の回収手順**を足した 6 条件を列挙。
  - §6 の案 A 行と §7-1 根拠 3 を「参加できる**可能性がある**」「未検証」へ書き換え。

## [Warning] (c) T-1 適格条件 B「案 A が実地で不成立」の判定基準が未定義

- 判断: **対応する**
- 根拠: 指摘のとおり主観で揺れる。判定不能な条件は Conditional として機能しない。
- 対応内容: 適格条件 B を「**§3-4 の 6 条件のうち少なくとも 1 つが崩れている**ことが
  具体的な事実として記録されている」へ書き換え、さらに**判定例の表**を新設。
  Codex の例 (規程で禁止 / catch-all 提供不可 / 代行が監査上禁止 / PIN 共有禁止かつ端末分割不可) を
  「はい」側に、**「個人メールがないだけ」を「いいえ」側に明記**した。

## [Warning] (e) 「毎日のログインには ID もメールもパスワードも要らない」が強すぎる

- 判断: **対応する**
- 根拠: `PasskeyLoginPolicy` の TOTP 制約、端末・ブラウザ対応、パスキー登録済みであること、
  端末本人性の許容がすべて前提であり、無条件の主張は保証範囲の過大主張になる
  (AGENTS.md が繰り返し要求する「保証範囲を誇張しない」に反する)。
- 対応内容: §3-1 の見出しを「日常ログインの入力を大きく減らせる」に変更し、
  本文に**成立条件 4 つ**を明示。「無条件に書くことはできない」と自ら明記した。
  §7-1 根拠 2 も同様に条件付きへ弱めた。

## [Warning] リスク: 「要件どおりの管理者発行方式と同等以下」と言い切れない (監査要件次第)

- 判断: **対応する**
- 根拠: 指摘が正しい。比較しているのは「なりすまし可能性の大きさ」だけであり、
  「アカウント受け渡し経路にメールを介在させない」型の監査要件は、
  代償の大小と無関係に案 A を不可にする。
- 対応内容: §3-3 に「**『同等以下』と言い切れるのはなりすまし可能性の大きさの比較においてだけ**」
  という段落を追加し、経路そのものを禁ずる監査要件の下では案 A が採れないこと、
  その場合 T-1 が発火することを明記。§6 の案 A 行の代償欄も同様に修正。

## [Suggestion] 群 (使命整合 / 禁止事項 / 実現可能性 / 期待効果 / スコープ / 型安全性)

- 判断: **見送る (追加対応不要)**
- 根拠: いずれも本設計の記述への同意、もしくは「将来案 C / E を作る場合の注意」であり、
  現時点で実装しない本設計に追加すべき内容が無い。
  ただし「案 C / E へ進む場合は FormRequest / DTO / Resource 境界を先に設計対象へ入れる」は
  有用なので、**詳細設計 §将来実装する場合の参照設計に反映する** (Phase 2 で消化)。
