## [Suggestion] (F) §6-4 の DTO 欄「手渡し URL の 1 回表示」が方式 1 と整合しない

- 判断: **対応する**
- 根拠: 指摘が正しい。§6-2d 方式 1 (推奨) では表示対象は**引換コード**であって URL ではない。
  波及表が方式 2 の語彙で固定されていると、方式 1 を選んだ実装者が
  「この行は自分には関係ない」と読み飛ばしうる。
- 対応内容: **「手渡し資格情報の 1 回表示 (方式 1 なら引換コード、方式 2 なら受諾 URL)」**へ一般化した。

## [Suggestion] (G) §6-7 の「`Notification::fake()` で 0 件」がアプリ内通知まで 0 件と読める

- 判断: **対応する**
- 根拠: 指摘が正しく、そのまま実装されると**設計意図と逆の結果**になる。
  §6-2a(f) は「メールが届かない層にはアプリ内通知センターが唯一の経路になる」と書いており、
  通知を全部 0 件にすると**その層への通知手段が完全に消える**。
  抑止したいのは **mail channel だけ**である。
- 対応内容: 期待値を **「合成 email 宛ての mail channel 送信が 0 件」**へ限定し、
  **「アプリ内通知 (通知センター) は別に期待件数を検証する」**を併記。
  さらに目的を 1 行で明示した —
  「通知を 0 件にするのではなく、メールだけを 0 件にし、代替経路には届ける」。

## [Suggestion] (G) §6-8 の「『送信しました』と表示して届かない導線は詰ませる」が一般化応答方針と緊張する

- 判断: **対応する**
- 根拠: 指摘が正しい。Round 2 で §6-2a(e) を
  「応答を分けない (列挙オラクルを作らない)」へ直したのに、
  リスク節には**それ以前の言い方 (「嘘の成功が悪い」)** が残っていた。
  そのまま読むと「応答を分けて正直に伝えるべき」と誤読されうる = 列挙オラクルを作る方向。
- 対応内容: **「列挙対策として一般化応答は維持するため、利用可能な回復経路を
  事前提示しなければ利用者が復旧不能になる」**へ書き換え、
  「応答を分けて教えるのは列挙オラクルになるので採れない」と明示した。
