## [Critical] (C)(G) 「URL に載せない」と「招待リンクを手渡す」が両立していない

- 判断: **対応する (指摘が完全に正しい。設計の自己矛盾だった)**
- 根拠: 旧 §6-2c の条件 6 は「URL に載せない」とだけ書いていたが、
  **リンクを渡して受領者がそこへ遷移する以上、受領者側の最初の HTTP 要求には何かが載る**。
  現行のメール招待も `/invitations/accept?token=…` = **クエリに平文 token が載っている**。
  「管理画面の URL に載せない」だけでは、受領者側のブラウザ履歴・最初のリクエスト・
  リバースプロキシ / アクセスログへの露出を 1 つも防げない。
  「10 条件を満たせば安全」という参照設計として自己矛盾していた。
- 対応内容:
  - 条件 6 を **「URL に載せる場所を 2 つに分けて扱う」** へ書き換え
    (管理者側の表示ページ URL = 無条件で載せない / 受領者側の受諾要求 = 方式で決める)。
    旧版が自己矛盾していたことを注記として明示的に残した。
  - **§6-2d「受領者が token をどう消費するか」を新設**し、
    **2 方式のどちらかを選ぶ (並走させない)** 形にした:
    - **方式 1 (推奨) 引換コード方式**: 受領者に渡すのは短い一回限りの引換コードで、
      **フォーム入力 → POST で交換**する。**URL には何も載らない**。
      代償として、短いコードは総当り可能なので **named limiter + コード長 + TTL で有界にする**
      (現行の 64 文字 token と違い、総当りが現実的になるため) と明記。
    - **方式 2 URL 方式**: 採るなら Codex の挙げた 5 点を**すべて必須**にした —
      初回要求で session 退避 → **token なし URL へ redirect** /
      アクセスログの query 除外またはマスク / 例外コンテキストのマスキング /
      **`Referrer-Policy: no-referrer`** / **戻る操作で Inertia props に平文が
      再表示されないことのテスト** (ドメイン規約 3 の (B)(C) の射程確認)。
  - **既存のメール招待との関係**を明記: 本タスクでは変更しない。ただし方式 2 は同じ route を
    通るので既存経路にも対策が掛かり、§6-7 の「既存経路は一切変わらない」という
    回帰テストの期待値を先に見直す必要がある、と申し送った。
  - §6-8 リスクを「発行側と受領側は別の露出面であり、片方だけ閉じても意味が無い」へ更新。

## [Warning] (C) 合成 email の「MX を持たない自社サブドメイン」は配送不能を保証しない

- 判断: **対応する**
- 根拠: 指摘が技術的に正しい。**SMTP は MX が無いときに A/AAAA へフォールバックしうる**ため、
  将来そのサブドメインに A レコードが付いた瞬間に実配送が始まる = 無言で誤配送が起きる。
  「MX が無いから安全」は保証にならない。
- 対応内容: §6-2a の (a) を書き換え。**既定を予約済みの `.invalid` に限定**。
  自社ドメインを許す場合は MX 不在ではなく
  **送信経路での明示拒否と外部配送不能を構成し、テストで固定する**ことを要求。
  `.test` は開発・テスト用途との混同を招くため**採るかを明示判断する**と記載。

## [Warning] (C)(G) `/forgot-password` で応答を分けるとアカウント列挙オラクルになる

- 判断: **対応する (自分の誤りを訂正)**
- 根拠: 指摘が正しく、こちらの設計が**セキュリティを後退させる方向**だった。
  旧版は「合成 email には送れないので嘘の成功を返さない」と書いていたが、
  **利用者ごとに応答を変えることがそのまま列挙オラクル**になる。
  Fortify が一般化した成功応答を返すのは意図された挙動であり、崩してはならない。
  本アプリは登録・招待の各所で「中立メッセージによる列挙対策」を不変条件として持っており
  (`UniqueEncryptedEmail` / `inviteMember` の中立メッセージ)、それとも矛盾していた。
- 対応内容: §6-2a の (e) を全面書き換え。
  **「応答を変える」ではなく「回復経路を事前に明示する」**が解であると定義し、
  提示場所を**列挙を生まない経路** (ログイン画面の常設案内 / 管理者から渡す手順書 /
  認証済みの設定画面) に限定した。
  §6-7 のテスト計画も
  「嘘の成功を返さない」→**「応答がアカウントの存在・配送可否で区別できないこと」+
  「回復経路が列挙を生まない場所に事前提示されていること」**へ差し替えた。

## [Warning] (F) 波及変更に token を受領者へ渡して消費する境界が不足

- 判断: **対応する**
- 対応内容: §6-4 に 2 行追加 —
  **受領者側の消費境界** (`InvitationAcceptanceController` と受諾 route /
  引換コードの交換処理 または session 退避 + token なし redirect /
  アクセスログ・例外ログの query・token マスキング / `Referrer-Policy: no-referrer` /
  引換コードを新設するなら CSRF と named limiter の境界) と、
  **受領者側のテスト** (戻る操作・履歴復元で平文が再表示されないこと /
  **発行者と受領者が別端末である受け渡しの E2E**。Browser lane は Chromium + WebKit の 2 レーンが契約)。

## [Suggestion] (B) 適格条件 C の本文と「満たさないときの行き先」に不整合

- 判断: **対応する**
- 根拠: 指摘が正しい。本文は「代替回復方式を設計対象に含めること」を必須にしているのに、
  行き先は「管理者リセットで足りるなら進める」と書いており、判定がぶれる。
- 対応内容: **「代替回復方式には、権限集中を明示的に受容した管理者リセットも含む」**と明記し、
  **不昇格になるのは「回復方式を決めていない」ときだけ**であることを詳細設計・概念設計の両方に反映。

## [Suggestion] (D) 「そのときは登録が要る」と「登録の要否を判定する」が混在

- 判断: **対応する**
- 根拠: 指摘が正しい。断定と再判定が同じ段落に同居しており、読む人がどちらに従うか決められない。
- 対応内容: **「その変更の中で登録の要否を再判定し、要るなら同じ変更で登録する」に統一**。
  断定しない理由を 2 点明記した — (1) テンプレート側も更新されるため実装時点で
  テンプレートが同じ機能を持っている可能性がある (そのときは逸脱ではない)、
  (2) 逸脱の有無は変更の内容が確定してからしか判定できない。
  第 1 段・第 3 段を実装する PR の**完了条件**に含める形にした。
  概念設計 §7-3 と §7-1 の Conditional 本文も同じ表現へ同期した。
