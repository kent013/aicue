全体判定: **CHANGES_REQUESTED**

Round 1 の主要論点は概ね解消されています。特に DTO 導入、Router 直接参照、`generate` / `check` の責務分離、中間 JSON 廃止は妥当です。ただし、母集合の定義と原子的更新について、設計上の矛盾が残っています。

## 1. 使命との整合性

[Suggestion] 「間接・補助的な貢献」への限定は適切です。探索分母の信頼性向上が、撮影 PWA の品質保証を通じて North Star に寄与する因果関係も無理がありません。

本件をプロダクト機能そのものとして扱わず、開発支援基盤として位置づけているため、使命との整合性に問題はありません。

## 2. 禁止事項違反

[Warning] 「2 ファイルを `os.replace()` で差し替え、途中で落ちたら 0 ファイル」という保証は成立しません。

`os.replace()` は1ファイル単位では原子的ですが、2回の置換をまとめたトランザクションにはなりません。1個目の置換後にプロセスが停止すれば、1ファイルだけ更新された状態になります。

修正提案:

- 保証を「各ファイルの書き込み途中の内容は露出しない」に弱める。
- 2ファイル間の同時更新までは保証せず、部分更新は次回の `check` が exit 3 で検出すると明記する。
- 複雑なロールバック機構は、この生成物の性質に対して過剰なので追加しない。

[Suggestion] テストファーストについて、列挙した自己テストを実装前に fail させる順序を詳細設計で明記すると、リポジトリ原則との対応がさらに明確になります。

その他の禁止事項への抵触は見当たりません。CLI の JSON 出力は HTTP endpoint の `response()->json()` 禁止とは別物です。

## 3. 実現可能性

[Critical] route 件数の実測値が算術的に一致していません。

記載は「web 面 148 route」ですが、内訳は次の合計で159件です。

```text
72 + 57 + 17 + 10 + 3 = 159
```

この実測は「GET と非 GET の併存が0件」「method から排他的に分類できる」という重要な設計判断の根拠です。単なる誤記として扱わず、集計単位を確認する必要があります。

修正提案:

- 「route オブジェクト数」「method 展開後の行数」「HEAD を独立して数えるか」を定義する。
- 同一の scan 結果から、母集合件数・画面件数・操作件数・method 別件数を算出する。
- 次の不変条件を自己テストに登録する。

```text
全 route 集合 = 画面 route 集合 ⊎ 操作 route 集合
```

method 別件数は複数 method を許すため、route 総数との単純加算比較には使わない方が安全です。

[Critical] in-scope route の名前が空の場合の契約がありません。

`operations.md` と `correlate.py` の join key は route name です。Laravel は unnamed route を許すため、in-scope の unnamed route が混ざると「実在 route 名が構造的に保証される」という主張が崩れます。

修正提案:

- scan した in-scope route は、空でない一意な route name を必須とする。
- unnamed route または name 重複を段1の抽出契約違反として exit 2 にする。
- 空 name・重複 name のテストを DTO/Command 側と Python 側のどちらが担当するか明記する。

[Warning] 「`web` middleware の機械判定」の取得方法を固定する必要があります。

`Router::gatherRouteMiddleware()` は middleware group を展開するため、結果に文字列 `web` が残るとは限りません。展開後の個別 middleware の組合せを `web` 面の識別子として使うと、Laravel設定変更に弱い推測になります。

修正提案:

- route に宣言された middleware 名から `web` group 所属を判定するのか、登録元を別の方法で識別するのか、詳細設計で固定する。
- 実際の登録方式に対して `web` route、API route、middleware を個別付与した route の境界テストを置く。
- Laravel の内部 middleware 構成を推測して `web` とみなす方式は避ける。

[Warning] URI prefix による除外は、名前の正規表現を別の暗黙規則に置き換える危険があります。

`api/` や `admin` などを scan 前に落とすと、それらには理由付き注釈を要求できません。一方で設計は「対象外は route ごとの注釈で理由付き宣言」と述べています。

修正提案:

- 「別 surface なので抽出前に除外」と「web surface 内だが bug-hunt 対象外なので `外` 注釈」を明確に分ける。
- URI prefix 集合には、各 prefix が別 surface である根拠を設計内に持たせる。
- prefix 判定は境界一致にする。例えば `administer` を `admin` と誤判定しない契約が必要です。

## 4. 期待効果の妥当性

[Warning] 「偽緑3種が消える」は、母集合抽出が正しい範囲に限定すべきです。

空母集合と双方向差分の偽緑は解消しますが、surface predicate が route を誤って除外した場合、その route は注釈の定義域にも入りません。

修正提案:

「定義した web surface predicate が抽出した母集合について、既知の偽緑3種を解消する」と限定してください。

[Suggestion] 30文字制約は理由の不在や極端な短文を防げますが、妥当性までは保証しません。「形式のみを検証する」と保証しないものに書かれているため、現在の整理で問題ありません。

## 5. リスク

[Warning] 画面・操作の排他的分類は現在の実測には合いますが、将来の複合 method route を黙って画面分母から落とします。

保証外への記載だけでは、将来その状態が発生しても CI は緑のままです。分母生成器としては危険な退行です。

修正提案:

- GET/HEAD と非GETを併せ持つ route を段2の drift として拒否する。
- 実際に必要になった時点で注釈モデルを拡張する。

現時点で0件なら、未対応状態を許容するより fail-closed にする方が「今必要なものだけ作る」と両立します。

[Warning] 画面題名を空欄で許容する判断は可能ですが、`画面` 種別でも空欄を許すと、bug-hunt の画面一覧として情報品質が後退する可能性があります。

修正提案:

- 少なくとも `画面` と分類された route の現行タイトル充足率を確認する。
- 現在100%なら、欠落を許容する積極的理由がないため drift にする。
- 不足が実在するなら、空欄許容を維持し、その件数を概念設計の事実として示す。

これは閾値を先に決める問題ではなく、既存データを見て契約を決める問題です。

## 6. スコープの適切さ

[Suggestion] `inventory.json` の廃止は適切です。利用者のない中間成果物と、その一致検査を維持する必要はありません。

[Suggestion] 段4を同一PRに残す理由も成立しています。独立関数・独立テストに分離するなら、生成処理との不要な結合も抑えられます。

[Warning] 改善アイデア冒頭の図には、廃止した `inventory.json` がまだ残っています。

修正提案:

```text
[抽出] scan JSON
   ↓
[合成] 機械事実 × 注釈 × 散文ノート
   ↓
[描画] screens.md / operations.md
   ↓
[検査] メモリ上で再生成して byte 比較
```

また、制約・前提には「生成物に環境名を書き込み」と残っていますが、本文では「環境名ではなく抽出条件ラベル」としています。後者へ統一してください。

## 7. 型安全性

[Warning] 2 DTO への限定は妥当ですが、「連想配列として持つ」部分の型を明示する必要があります。

PHPStan level 10 では裸の `array` では不十分です。特に `config('seo.app_titles')` は `mixed` になりやすく、DTO 境界まで未検証の値が流れる可能性があります。

修正提案:

- `InventoryRouteData` の method、middleware、titleなどを具体的な generic/shape で定義する。
- `InventoryScanData::toArray()` に完全な array shape を付ける。
- config 値は Command 境界で `is_array`、キー、値型を検証してから DTO に渡す。
- JSON 化は `JSON_THROW_ON_ERROR` を使い、失敗を exit 2 に写像する。
- DTO の `toArray()` 契約と JSON schema 相当の形を Feature/Unit テストで固定する。

DTO を env/title ごとに細分しない判断自体は、現時点のデータ構造なら過剰設計を避けるものとして妥当です。

結論として、設計の方向性は承認可能なところまで改善されています。承認に必要なのは、route 件数・命名・surface 判定という母集合の契約を確定し、複数ファイル更新の保証表現と文書内の残存矛盾を修正することです。
