# 対応マトリクス: conceptual-review Round 2

## [Critical] §3 route 件数が算術的に合わない (148 vs 72+57+17+10+3=159)

- 判断: 対応する (指摘は正しい。集計単位が混ざっていた)
- 根拠: 148 は「uri prefix 除外 + web middleware」の集合、159 は「web middleware を持つ全 route」の集合で、
  別の母集合の数字を並べていた。同一の判定で数え直した。
- 対応内容: 集計単位を「route オブジェクト 1 件 = 1 行」と定義し、実測を入れ替えた。
  全 route 211 / **web 面 147** / 画面表 68 / 操作表 79 (POST 51 / DELETE 15 / PATCH 10 / PUT 3)。
  **画面表 ⊎ 操作表 = web 面** を自己テストの不変条件として登録する。
  併せて、この判定だと現行表に無い `webhooks.ses` が操作表へ入る (現行シェルは名前に `webhook` を
  含む route を暗黙に落としていた) ことも明記した。`cashier.webhook` は web middleware を持たないので
  面の判定で自然に外れる。

## [Critical] §3 名前の無い / 重複する route の契約が無い

- 判断: 対応する
- 対応内容: web 面の route に**空名または重複名があれば段 1 で exit 2**。実測では 0 件 / 0 件。
  判定は Python 側 (段 1) が持つ (抽出結果全体を見ないと重複は判定できないため)。
  PHP 側は「名前が無い route も抽出結果に含めて出す」責務にとどめる (握り潰さない)。

## [Warning] §3 `web` 面の判定方法を固定する

- 判断: 対応する
- 根拠: `Router::gatherRouteMiddleware()` は group を展開して `web` を消す。
  `route:list --json` が `web` を残すのは route 宣言のままの一覧を出しているためである (実データで確認)。
- 対応内容: 判定は **`$route->gatherMiddleware()` が返す宣言のままの middleware に group 名 `web` が
  含まれること**とし、解決済みクラス列からの推測はしないと明記。境界テストを詳細設計に置く。

## [Warning] §3 uri prefix 除外が暗黙規則になる / 境界一致

- 判断: 対応する
- 対応内容: 対象外を 2 層に分けて表にした。(a) 面が違う = 抽出前に除外 (根拠は面の定義)、
  (b) web 面内の対象外 = 注釈 `外` + 30 文字以上の理由。prefix 判定は**セグメント境界一致**にする
  (`administer` を `admin` と誤判定しない)。

## [Warning] §5 複合 method route を黙って画面分母から落とす

- 判断: 対応する (fail-closed へ)
- 対応内容: GET/HEAD と非 GET を併せ持つ route は**段 2 で drift (exit 3)** として拒否する。
  必要になった時点で注釈モデルを広げる。

## [Warning] §5 画面題名の空欄許容はデータで決めるべき

- 判断: 対応する (実測して空欄許容を維持)
- 根拠: 現行の対象内 50 画面 (付随 JSON GET 5 本を除く) のうち `app_titles` に題名があるのは **33 件**、
  17 件は無い。無い側は公開ページ (`home` / `pricing` / `legal.*`) と、controller が実行時に
  固有名を供給する画面 (`projects.show` / `projects.manuals.show` 等) である。
- 対応内容: 空欄許容を維持し、**17 件という実測値を設計に事実として明記**した。
  `config/seo.php` はタブ題名のための設定であって目録の表ではないので、目録の都合で記入を強制しない。

## [Warning] §2 2 ファイルの `os.replace()` は原子的ではない

- 判断: 対応する
- 対応内容: 保証を「各ファイルについて書きかけの内容が露出しない」に弱め、
  2 ファイル間の同時更新は保証しないこと、部分更新は次の `check` が段 3 で exit 3 として検出することを明記。
  ロールバック機構は作らない。

## [Warning] §4 偽緑 3 種の解消は母集合の定義に依存する

- 判断: 対応する
- 対応内容: 「定義した web 面の判定が抽出した母集合について」と限定し、
  面の判定そのものが取りこぼす可能性が残ることを併記した。

## [Warning] §6 図と制約に旧記述が残っている

- 判断: 対応する
- 対応内容: 図から `inventory.json` を削除。制約の「生成物に環境名を書き込み」を
  「抽出条件のラベルを書く」へ統一した。

## [Warning] §7 連想配列の型を明示する

- 判断: 対応する
- 対応内容: array shape 宣言 / `config('seo.app_titles')` を Command 境界で `is_array` + キー・値型検証 /
  `JSON_THROW_ON_ERROR` と非 0 終了への写像を制約へ追記。`toArray()` の形は Feature テストで固定する
  (詳細設計に施策として書く)。

## [Suggestion] §2 テストを先に fail させる順序
