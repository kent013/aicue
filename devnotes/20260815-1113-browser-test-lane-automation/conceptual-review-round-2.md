ただし「Browser レーンが唯一の自動防波堤」という表現は強すぎます。Architecture／Feature／JS テストも回帰防止に寄与するため、「実ブラウザ固有の挙動を検証する防波堤」程度に限定するのが正確です。

### 3. 実現可能性

[Critical] 自動導入をグローバルテストロック取得前に実行すると、複数 worktree から同時に Browser レーンを起動した場合、同じ Playwright キャッシュと OS パッケージ管理機構へ並行して書き込む可能性があります。

現在の設計では、両プロセスが「未導入」と判断した後、同時にブラウザを取得したり、Linux で `apt`／`dpkg` 系処理を競合させたりできます。「数百 MB の取得中にテストロックを保持しない」ことと引き換えに、導入処理そのものの排他が失われています。

修正提案: ホスト共有の専用 provisioning lock を導入してください。

1. 無変更で抜けられる充足確認はロック外で行う。
2. 導入が必要な場合だけ provisioning lock を取得する。
3. ロック取得後に充足を再確認する。
4. まだ不足している場合だけ導入する。
5. provisioning lock 解放後、既存のグローバルテストロックへ進む。

専用ロックを増やさない場合は、導入を既存グローバルロック内へ戻す必要があります。少なくとも、共有資源への並行書き込みを無防備に許す現設計のままでは承認できません。

[Warning] `playwright install-deps --dry-run` の出力を「不足ライブラリの有無」として利用できることが設計上まだ立証されていません。dry-run が単に実行予定コマンドや必要パッケージ集合を表示する仕様なら、既に充足している環境でも「要求あり」と判定する可能性があります。出力を解析できることと、不足状態を正しく判別できることは別です。

修正提案: 詳細設計前に、最低でも次の状態を fixture／smoke の受入条件として定義してください。

- 依存充足済み Linux
- 依存不足 Linux
- 権限あり／なし
- ブラウザ実体あり／なし

実 CLI smoke も「2件のパスを抽出できる」だけでなく、充足済み環境で不要な特権処理へ進まないことを検証対象に含める必要があります。CLI 出力だけで不足を識別できない場合は、Playwright が提供する実行可能ファイルの起動検査など、判定方式そのものを再検討してください。

### 4. 期待効果の妥当性

[Warning] 「充足していれば数秒で何もせず抜ける」という効果は、上記の要求判定が正確であることに依存します。現時点では設計上の仮説であり、成立条件が未検証です。

修正提案: この主張を成功条件として明示し、充足済み環境で次を確認する契約テストを計画してください。

- `sudo` を起動しない
- `install-deps` の実処理を起動しない
- ブラウザの再取得を行わない

[Suggestion] キャッシュ効果を `pnpm-lock.yaml` 不変時に限定した修正は妥当です。キーには将来の runner 変更による異種キャッシュ混入を防ぐため、`runner.os` と必要なら architecture も含めるのが堅実です。

### 5. リスク

[Warning] レーン失敗後の証跡退避方法がまだ不十分です。`run-browser-test.sh` が `set -e` 相当で動いている場合、Pest の非ゼロ終了直後にスクリプトが終了し、退避処理まで到達しない可能性があります。

修正提案: 各レーンについて終了コードを明示的に保持し、退避を必ず実行してから最終的な失敗を返す設計を明記してください。例えば「実行 → status 保存 → 証跡退避 → 次レーンまたは最終 status 判定」という順序を契約テストで固定します。

[Warning] `storage/browser-test-artifacts/<lane>/` の前回実行分をいつ消すかが未定義です。残存物があると、今回生成されていない古いスクリーンショットを CI がアップロードし、診断を誤らせます。

修正提案: レーン開始前または一連の実行開始時に、対象ディレクトリだけを明示的に初期化してください。その初期化がグローバルロック取得後に行われ、並行する別実行の証跡を消さないことも固定してください。

### 7. 型安全性

[Suggestion] アプリケーションの DTO／JsonResource 境界には触れないため、本件で直接の型安全性問題はありません。PHP Architecture テストで `list<string>` 等を明示する方針も妥当です。
