全体判定: CHANGES_REQUESTED

Round 1 の大半は適切に解消されています。ただし、環境変数の優先順位に実現不能な契約が残り、一元化 gate の保証にもまだ論理的な飛躍があります。

## 1. 使命との整合性

- [Suggestion] 信頼性の基盤整備という位置付けに修正され、使命への間接的な貢献として適切になりました。効果の過大主張も概ね解消されています。

## 2. 禁止事項違反

- [Warning] fail-first の段4は赤になりません。設計自身が「旧実装も制限時間超過時に `ProcessTimedOutException` を投げる」と説明しているため、「制限時間超過を例外にする」という観測では旧実装も通ります。

  修正提案: runner 固有の契約、例えば「`BootProbeResult(timedOut: true, exitCode: 124)` を受け取った呼出側が実測不能例外へ変換する」分岐を、runner の差し替え可能な境界または純粋な変換メソッドに対して先にテストしてください。例外クラスだけを変えて赤にする場合は、意味ではなく実装詳細を固定する理由も明記してください。

## 3. 実現可能性

- [Critical] `APP_KEY` の優先順位に矛盾があります。runner の基底環境に `APP_KEY` が存在し、Dotenv が既存のプロセス環境を上書きしないなら、0600 の環境ファイルに置いた使い捨て `APP_KEY` は効きません。「使い捨て鍵が子で効くこと」を受入条件にしながら、現在の4段表ではそれを実現できません。

  修正提案: 3段合成の「ケース別上書きが最後に効く」契約を使い、使い捨て `APP_KEY` を `BootProbeRunner::run()` のケース別環境へ渡してください。表も次のように修正する必要があります。

  - ケース別環境: `FAKE_WIRING_PROBE_ENV_DIR`、`FAKE_WIRING_PROBE_ENV_FILE`、使い捨て `APP_KEY`
  - 環境ファイル: `APP_KEY` を除外
  - P-7 の期待集合: ケース別2件ではなく3件
  - P-8: 子で観測した `APP_KEY` が生成した使い捨て値と一致し、親の値とは一致しないこと

  もし runner が `APP_KEY` のケース別上書きを禁止しているなら、バイト一致取り込みとの両立方法を先に確定する必要があります。

## 4. 期待効果の妥当性

- [Warning] P-14 の「エントリ集合とタイムスタンプ」の比較は、内容変更を十分に検出できません。同一ファイルの内容が変わってタイムスタンプが同一粒度に収まる場合や、時刻を復元された場合を見逃します。

  修正提案: 監視対象について、相対パス、ファイル種別、サイズ、内容ハッシュを含む snapshot を起動前後で比較してください。mtime は補助情報に留めるべきです。

- [Warning] P-14 を `--parallel` で動かすと、別 worker が同じ監視対象へ触れた場合に偽陽性になります。

  修正提案: このテスト中は対象ディレクトリへ他テストが書かないことが既存不変条件で保証されている、と根拠を示してください。保証できない場合は、P-14 を非並列グループで実行するか、リポジトリ側の書込みを発生させる専用負例によって検出力を固定してください。

## 5. リスク

- [Critical] 軸Aと軸Bから「軸Bのファイルを起こせるのは軸Aの申告ファイルだけ」とは導けません。例えば新しいファイルが次のいずれかを使えば、既存の軸Bファイルを起動しつつ軸Aにも軸Bにも現れません。

  - 文字列の `php`
  - `env php`
  - シェルスクリプト経由
  - 実行ファイルパスを変数や設定から取得
  - 既存の子入口スクリプトを指定するが、自身には `bootstrap/app.php` を書かない経路

  したがって「アプリを起こす経路は共通 runner ちょうど1本」という主張は、現在の機械検査では保証されません。

  修正提案: 次のどちらかを選んでください。

  1. `tests/` 配下のプロセス起動 API 使用箇所すべてを第3軸として全数申告し、未登録の `proc_open`、Symfony `Process`、シェル起動等を赤にする。既存3経路も理由付きで登録する。
  2. gate の主張を「`PHP_BINARY` を明示する起動能力と、リテラルで検出できるアプリ起動点は申告なしに増えない」まで縮小し、「アプリ起動経路が runner 1本に閉じる」とは主張しない。

  正典への合格条件として本当に「アプリ起動経路1本」が必要なら、1が必要です。

## 6. スコープの適切さ

- [Warning] スコープ外5は「P-13だけが例外」としていますが、改訂設計ではP-14も新しい観測です。本文とスコープ定義が食い違っています。

  修正提案: 「P-13・P-14は正典(5)の実働証明として追加する」に修正してください。

- [Warning] 受入条件の `git status --porcelain が空` は、実装による追加・変更ファイルが未コミットの状態では成立しません。また、作業開始前からあるユーザー変更も失敗扱いになります。

  修正提案: 作業開始時の未追跡ファイル集合を保存し、走行後との差分が空であることを条件にしてください。目的が生成物だけなら、`git ls-files --others --exclude-standard` の前後差分に限定するのが適切です。

## 7. 型安全性

- [Suggestion] `BootProbeResult` を唯一の結果境界とし、`timedOut` と124を通常の非ゼロ終了から分離した契約は適切です。PHPStanの保証対象外であることも正直に限定されています。

- [Suggestion] `timedOut === true` と `exitCode === 124` の同値関係は、readonly DTO の生成時不変条件として自己検査に固定すると、呼出側が矛盾した状態を考慮せずに済みます。バイト一致の `BootProbeResult` が既にこの不変条件を持つなら追加対応は不要です。

結論として、Round 1 の指摘に対する方向性は妥当です。承認までに必要なのは、主に次の3点です。

- 使い捨て `APP_KEY` をケース別上書きとして実際に効かせる
- inventory gate の保証を第3軸で補うか、主張を検出力に合わせて縮小する
- fail-first 段4と、P-14・作業ツリー検査の実行可能性を修正する
