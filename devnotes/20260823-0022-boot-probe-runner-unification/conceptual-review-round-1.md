全体判定: CHANGES_REQUESTED

1. 使命との整合性

- [Suggestion] 外部 fake が実起動した Laravel に効くことを安全に観測する基盤は、本番の LLM・ストレージ等への誤接続防止に寄与するため、North Star を支える改善として妥当です。ただしこれはユーザー機能の直接改善ではなく、信頼性の基盤整備です。期待効果の記述もこの位置付けに留めると正確です。

2. 禁止事項違反

- [Warning] 「テストファースト」の証跡が設計上明示されていません。既存 runner の取り込みでも、aicue 側の統合変更（2 経路の載せ替え、P-13、inventory gate）には、先に失敗を確認する対象が必要です。

  修正提案: 実装順に「既存経路の旧実装を一時的に残した状態で新しい統合テスト／負例が失敗することを確認し、その後に載せ替える」を明記してください。

- [Suggestion] `app/` 非変更、JSON 直書き・Prism 直呼びなし、DB 破壊操作なしというスコープは、禁止事項と整合しています。

3. 実現可能性

- [Warning] テンプレートの3ファイルをバイト一致で導入する方針は堅実ですが、aicue のテスト起動設定・autoload・Pest 設定と完全に互換であることは、「手動で環境合成した子プロセスが起動した」だけでは十分に保証されません。

  修正提案: 導入後に、取り込んだ `BootProbeRunnerTest` の14本を aicue の通常テストコマンドで実行し、さらに `ExternalFakeBootProbeTest` と `StrictTypesDeclarationScannerTest` を実行することを受入条件にしてください。

- [Suggestion] Unix/POSIX 前提、DB 非使用、並列実行時の一時ディレクトリ衝突回避を明記している点は適切です。

4. 期待効果の妥当性

- [Warning] 「リポジトリを1バイトも汚さない」の実証が、P-13 の「一時ディレクトリに印が現れる」だけでは不十分です。これは `storage_path()` が退避されたことは示しますが、別の既定パスへの書込みがなかったことまでは示しません。

  修正提案: runner の自己検査または呼出側 gate で、子起動前後に監視対象となるリポジトリ内の既定書込み先（少なくとも `storage/logs/laravel.log`、bootstrap cache、view cache）に変化がないことを確認してください。監視範囲外を含む「完全に1バイトも汚さない」とは主張せず、保証対象の書込み先を明記してください。

5. リスク

- [Critical] 新設 inventory gate の「アプリを起こす entry はちょうど1件」という判定は、`PHP_BINARY` の参照全数を列挙するだけでは自己申告に留まります。分類を誤って `PHP を起こさない` と登録しても、gate が緑のままになる設計では、目標不変条件を機械的に守れません。

  修正提案: inventory の各 entry に対象ファイル・`PHP_BINARY` 使用箇所・起動種別・runner 経由の要否を固定し、少なくとも「アプリ起動」と分類されたものは `BootProbeRunner` 呼出しを構文上確認してください。また分類の変更・未登録参照・runner を迂回した直接起動が失敗する負例を追加してください。

- [Warning] `FakeWiringProbeRunner` に残す環境ファイルの組立てと、共通 runner の3段環境合成との責務境界が曖昧です。特に `APP_CONFIG_CACHE` が予約鍵であるため渡さない点は正しいものの、既存の `env -i` が保証していた「開発者ローカル環境を遮断する」性質を失う危険があります。

  修正提案: 許可継承キー、runner 基底キー、ケース別キー、予約キーを表で確定し、既存の `env -i` から維持される安全性と意図的に変わる値を明示してください。`TESTING_FAKE_*`、環境ファイル位置、使い捨て鍵が最終的な子環境に存在することもテストで固定してください。

6. スコープの適切さ

- [Warning] 「全数申告 gate」は必要ですが、AGENTS.md の走査器規約に対する実装・検証要件が設計に不足しています。既存の `PhpTokenScan` を使うだけでは、走査根の存在確認、母集団非空、未解決構文の fail-closed、正例・負例の両方が満たされるとは限りません。

  修正提案: 新規 gate の受入条件に以下を追加してください。

  - `tests/` の走査根が存在し、母集団が非空であること。
  - 未登録の `PHP_BINARY` 参照を検出する負例。
  - `PHP_BINARY` を含まない／コメント・文字列のみの正例を誤検出しないこと。
  - runner を迂回した直接の PHP 子起動を検出する負例。
  - gate の docblock に走査対象・字句走査の限界・保証しない構文を明記すること。

7. 型安全性

- [Warning] `BootProbeResult` を導入するなら、呼出側の失敗経路も含め、終了コード・標準出力・標準エラー・一時ディレクトリ・PID の型と不在値の表現を aicue 側で崩さないことが必要です。テストコードは現状 PHPStan 対象外でも、型を曖昧にすると将来の解析対象化を阻害します。

  修正提案: `BootProbeResult` を唯一の結果境界として扱い、配列や `mixed` の補助結果を呼出側へ漏らさないこと、`124` を通常失敗と区別できる例外／結果契約にすることを設計上明記してください。

テンプレート実装をバイト一致で採用し、2つの無関係な子PHP実行経路を同じ runner に寄せる主方針は妥当です。上記のとおり、特に inventory gate の実効性、環境遮断の維持、書込み退避の実証範囲を具体化すれば、正典 v1 への追従設計として承認可能です。
