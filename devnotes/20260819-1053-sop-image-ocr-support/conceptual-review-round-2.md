全体判定: **CHANGES_REQUESTED**

Round 1 の指摘は概ね適切に反映されています。使命、パイプライン維持、型境界、資源上限、ログ、コスト観測の方向性は妥当です。ただし、窓口迂回を機械的に塞ぐ設計にまだ 1 か所穴があり、実効性確認の記述にも矛盾が残っています。

### 1. 使命との整合性

[Suggestion] 使命への整合性は十分です。画像とテキスト抽出品質ゲートに失敗した PDF を救うことで、「既存 SOP を起点にする」という機能名・使命を直接満たします。

[Suggestion] OCR 結果を「正確さを保証した完成物」ではなく「人が確認・修正する下書き」と明記した点も適切です。

### 2. 禁止事項違反

[Critical] vendor 媒体型の生成箇所と prompt 型の継承宣言を固定しても、専用派生 prompt の**インスタンス生成箇所**はまだ固定されていません。

派生 prompt が public に生成可能なら、別のコードが `new 専用Prompt(...)` して `GuardedPrompt` へ渡す、または将来取得した vendor 媒体型を再利用することで、`PromptDefense` を迂回できます。「factory は窓口へ渡す」という規約だけでは、禁止事項 5 の一本道を機械保証できません。

修正提案:

- 専用派生 prompt の生成箇所も `PromptDefense.php` のみに完全一致で pin する。
- `app/` 全体で専用 prompt の `new`、静的 factory 呼び出し、型名の別名 importを完全修飾名へ解決して検査する。
- 可能なら専用 prompt のコンストラクタを非 public にし、窓口だけが利用できる生成方式にする。ただし PHP の可視性上それが不自然なら、静的 gate を正本とする。
- vendor 媒体型生成、派生宣言、派生 prompt 生成の3経路を、同じ責務境界の不変条件として文書化する。

これを塞げば、Round 1 の Critical だった窓口責務境界は解消できます。

### 3. 実現可能性

[Warning] 検証済み DTO が「保存先」を保持する設計では、検証から LLM 送信までの間にファイルが差し替わる TOCTOU が残ります。型が検証済みでも、参照先の内容が検証時と同一である保証にはなりません。

修正提案:

- DTO に検証時の容量・SHA-256などの内容同一性情報を保持する。
- vendor 媒体型へ変換する直前に、ファイルの存在、容量、ハッシュを再確認する。
- 不一致・消失・読取失敗は LLM を呼ばず、既存の `failJob` 経路で release する。
- source document が既存仕様上不変であるなら、その不変性を担保する実装とテストを根拠として明記し、重複検証を省略してよい条件を固定する。

[Warning] `ページ数 × ページあたり token 見積り ≤ budget` は、単なる経験値では token budget の上限を保証しません。PDF の視覚入力コストはページ内容やプロバイダの変換仕様、モデルにより変わり得ます。

修正提案: `AnalysisTokenBudgetInvariantTest` が保証するものを次のいずれかにしてください。

- provider/model の公式な最大計算式に基づく保守的上限として固定する。
- 正式な上限が得られない場合は「設定値間の整合を検査する見積り」であり、実 token の上限保証ではないとテスト名・docblock・設計文書で明記する。

モデルや provider を変更したときに見積式の再確認を要求する pin も必要です。

### 4. 期待効果の妥当性

[Suggestion] 「空・schema 違反・日本語不足は検出できるが、捏造は検出できない」という効果範囲は正確になりました。

[Suggestion] 日本語比率の計算対象は、JSON 全体やフィールド名ではなく、SOP の本文フィールドを決定的な順序で連結した文字列に限定すると実装時の揺れを防げます。対象フィールドを DTO または検査サービスで一意に定義することを推奨します。

### 5. リスク

[Warning] prompt injection の実効性確認について、設計内に矛盾があります。

一方では「実効性の確認は実課金の走行（bug-hunt レーンの通し確認）でしか行えない」とし、他方では bug-hunt レーンも `CannedPromptFakeRegistrar` 上で動作し、LLM を呼ばないとしています。fake 応答では画像内命令に対するモデルの挙動を確認できません。

修正提案:

- 「bug-hunt レーンの通し確認」を実効性確認手段から削除する。
- オフラインテストが保証する範囲を、配線、防御指示、schema、canary、後段の untrusted 経路に限定する。
- 実効性を確認する場合は、通常テストレーン外の明示的な手動評価または課金あり eval と定義する。
- `dev:pipeline-smoke` への追加をスコープ外とするなら、「本変更では実モデル上の実効性を確認しない」と明記する。リリース条件にするなら、限定 fixture による手動評価手順だけを本設計へ含める。

[Warning] 法務文面を別 TODO にする判断には合理性がありますが、画像では顔・印影など送信範囲が materially に広がります。単に TODO を起票するだけでは、未整備のままリリースされる可能性があります。

修正提案: 法務文面そのものを本実装へ含める必要はありませんが、次のどちらかを決めてください。

- OCR 機能の production 有効化前に外部送信の明示を完了する rollout dependency とする。
- 現行の契約・同意で画像を含む文書送信までカバー済みであることを、責任者が確認した記録を残す。

これはコード実装のスコープではなく、機能公開の前提条件として扱うのが適切です。

### 6. スコープの適切さ

[Suggestion] JPEG/PNG、対象 PDF、HEIC 除外、補正・複数画像・専用 OCR エンジン除外の線引きは適切です。

[Suggestion] チケット単価を今回は維持し、専用 template 名で実費を観測してから再検討する判断も妥当です。再検討条件の「大きく上回る」「想定より多い」は運用開始前に評価期間と比較指標を決めておくと、都合のよい事後解釈を避けられます。

### 7. 型安全性

[Suggestion] 検証済み媒体 DTO、text/media union、理由 enum は PHPStan level 10 と相性がよく、メッセージ文字列分岐も避けられています。

[Warning] DTO の「ページ数か画素数」を nullable な複数プロパティで表すと、不正状態を型で作れてしまいます。

修正提案: 共通 interface または sealed に近い union として、例えば画像 DTO と PDF DTO を別型にしてください。

- 画像 DTO: MIME、保存先、容量、幅、高さ、画素数、内容同一性情報
- PDF DTO: MIME、保存先、容量、ページ数、内容同一性情報

これにより「画像なのにページ数だけある」「PDF なのに画素数がある」といった状態を PHPStan 上でも排除できます。

窓口以外からの専用 prompt 生成を塞ぎ、実モデル評価に関する矛盾と DTO の内容同一性を修正すれば、概念設計として APPROVED にできます。
