全体判定: CHANGES_REQUESTED

Round 4 の主要指摘には概ね適切に対応されています。特に、型判別を `instanceof` に直した点、予約前の provider 判定、再評価条件、アップロード前の案内追加は改善です。ただし、費用評価指標と DTO の「検証済み」保証には、実装判断を誤らせうる未解決点があります。

### 1. 使命との整合性

[Suggestion] 紙・写真・スキャン PDF しかない現場を受け入れるため、North Star への貢献は本質的です。「既にある SOP を起点に」という入口の制限を解く改善になっています。

[Suggestion] OCR 結果を確定情報ではなく、既存の編集機能で確認・修正する下書きと明示した点は適切です。

### 2. 禁止事項違反

[Suggestion] LLM 経路を factory → `PromptDefense` → `GuardedPrompt` に維持し、YAML 化・帰属必須・媒体型生成の窓口集中を設計しているため、禁止事項 5・6 との整合は取れています。

[Warning] `fromValidated()` を public な named constructor にする限り、「検証済みの値だけを受ける」は PHP の型・可視性だけでは保証できません。呼び出し箇所の deny-by-default gate は有効な補完策ですが、設計文の保証表現は強すぎます。

修正提案: 「検証済み DTO だけを生成できる」ではなく、「生成経路を `AnalysisMediaValidator` に限定し、全呼び出し箇所を deny-by-default gate で固定する」と表現してください。可能なら named constructor を `private` にし、DTO ごとの生成を validator 専用の factory に閉じる案も比較してください。

### 3. 実現可能性

[Warning] `match (true)` と `instanceof` の形は PHP として成立します。ただし「union に第3型を足せば、default がないため PHPStan が必ず該当箇所を落とす」という保証は、PHPStan のバージョン・設定・分岐解析能力に依存します。PHP 言語自体は実行時に `UnhandledMatchError` になるだけで、型の sealed union を持ちません。

修正提案: この性質を PHPStan の期待動作として断定せず、実際に第3 DTO を加えた fixture または型検査用テストで PHPStan が失敗することを確認し、PHPStan の固定バージョンを前提にしてください。確認できない場合は、明示的な到達不能例外と、union 拡張時に変換器更新を要求する契約テストで守ってください。

[Warning] Anthropic の mapper を直接通す契約テストは、vendor の内部構造・クラス名に強く結合します。意図した content block の検証としては合理的ですが、Prism 更新時にアプリの責務外の内部変更でも壊れます。

修正提案: mapper を通すテストは維持しつつ、Prism/Anthropic のバージョンを明示的に pin してください。また、アプリ側の責務である「DTO → `UserMessage` の媒体種別・MIME・順序」のテストと分離し、失敗原因を切り分けられるようにしてください。

### 4. 期待効果の妥当性

[Critical] 評価指標 (a)(b) は「1解析あたり」または「解析件数」を掲げながら、`llm_call_logs` だけで集計できるとしています。しかし `llm_call_logs` は呼び出し単位であり、再試行により同一解析ジョブが複数行になり得ます。OCR の専用 YAML は extract 段階だけなので、テキスト経路との比較対象・再試行・LLM 呼び出し前失敗の扱いが一意ではありません。このままでは 4 週間後の判断が恣意的になり得ます。

修正提案: (a)(b) も `analysis_jobs` を主キーにしたジョブ単位の定義へ統一してください。最低限、以下を事前に固定してください。

- (a) は「各ジョブの OCR extract 呼び出し群の入力 token 合計」の中央値か、「最終成功試行だけ」の中央値か。
- (b) の分母を、受理済み解析ジョブ・`startJob` 済みジョブ・extract 開始済みジョブのどれにするか。
- provider 判定、上限判定、構造検証前などで LLM 呼び出しに至らない OCR 対象を分母に含めるか。
- OCR extract が再試行された場合のテンプレート判定と成功・失敗の帰属方法。

[Warning] 「現在成功している解析の挙動は1件も変わらない」は、PDF の既存品質ゲート失敗を OCR に回すことで、以前は即時エラーだった入力に外部送信・LLM 呼び出しが発生するため、入力の処理挙動としては変わります。

修正提案: 「既存のテキスト品質ゲートを通過する PDF・Excel・テキストの経路は変えない」と限定して記述してください。

### 5. リスク

[Warning] 画像内 prompt injection への対策は、静的な配線保証と手動評価に分離されており、過剰な保証をしていない点は適切です。ただし再評価・再承認は運用条件だけで、コード上は provider/model や YAML の変更を止められません。

修正提案: provider/model pin、媒体 YAML、防御指示、Prism/Anthropic の依存更新を「OCR 有効化状態では再評価記録なしに変更不可」とするリリースチェックリストまたは変更管理手順へ落としてください。少なくとも、変更対象を機械的に列挙するテストを置き、再評価対象の見落としを減らしてください。

[Warning] 利用者向けの案内は進展ですが、画像・PDF 以外の既存テキスト経路も外部 LLM に送信されるなら、画面上の文言が実態より狭く読めます。

修正提案: 法務確認の範囲で、「アップロードした手順書は AI 解析のため外部 LLM provider に送信される。画像・PDF では写り込みに注意」と、媒体共通の送信事実と画像特有の注意を分けてください。

### 6. スコープの適切さ

[Suggestion] ローカル OCR、画像変換、複数画像束ね、HEIC 対応を外した判断は適切です。既存の Prism/Anthropic 拡張点を使い、パイプライン段数を増やさない範囲に閉じています。

[Suggestion] PDF の「スキャンだけ」ではなく既存テキスト品質ゲートに失敗した PDF を救う、と定義した点も一貫しています。

### 7. 型安全性

[Warning] DTO を画像・PDFに分割し、nullable フィールドを避け、媒体変換を窓口に限定する設計は PHPStan level 10 に適しています。一方で、共通 interface を「読み取り専用情報」に限るという規約は、将来 `bytes()` や MIME を interface に積み始めたときに、媒体種別固有の検証境界が曖昧になる余地があります。

修正提案: interface に許すメンバーを具体的に列挙し、媒体変換は常に union 型を受ける窓口メソッドだけで行う、と固定してください。`ImageAnalysisMediaData|PdfAnalysisMediaData` を interface に置換する変更を検出する静的 gate も対象に含めてください。

上記の Critical、特に評価指標を解析ジョブ単位で確定すれば、設計は承認可能な水準です。
