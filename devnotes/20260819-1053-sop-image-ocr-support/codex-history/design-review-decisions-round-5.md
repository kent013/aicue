# 対応マトリクス: design-review Round 5 (最終ラウンド)

Round 5 はスキル規定の上限 (最大 5 ラウンド) に達したラウンドである。9/11 施策が
APPROVE、残り 2 施策 (施策 6・施策 10) は具体的な Warning のみで、以下の対応を
反映して確定させる。施策 9 (token budget) は施策 9a (一次情報調査) の完了待ちという
明示的な前提条件のまま残す (これは設計の欠陥ではなく、実装着手前に完了すべき
別タスクとして意図的に切り出したものであり、Codex も「9a を独立タスクにした判断は
妥当」と評価している)。

## [Warning] LLM 呼び出し段階の失敗で検証済み媒体メタデータが失われる (施策 6)
- 判断: 対応する
- 根拠: 指摘のとおり。catch 節が常に `null` を渡していたため、媒体検証成功後の
  LLM 呼び出し失敗では `media_size_bytes`/`media_pages`/`media_pixels` が全て
  失われ、失敗率と入力規模の相関が評価期間中に見られなかった。
- 対応内容: `$input` を `runExtractStage()` のスコープで保持し、catch 節でも
  検証済みの値をそのまま `logExtractStageTerminal()` へ渡す設計にした。
  4 パターン (media 検証前失敗・画像 LLM 失敗・PDF OCR LLM 失敗・text 失敗) の
  媒体メタデータをテスト計画に追加した。

## [Suggestion] `JobOwnershipLostException` の例外が「ちょうど 1 回」の保証に含まれない
- 判断: 対応する
- 対応内容: `logExtractStageTerminal()` の docblock に、この 1 件だけ早期 return して
  ログを出さない例外であることを明記した。

## [Warning] 一般的な外部 LLM 送信案内まで OCR フラグで出し分けている (施策 10)
- 判断: 対応する
- 根拠: 指摘のとおり。「手順書は AI 解析のため外部の LLM provider に送信される」という
  事実自体はテキスト・Excel・通常 PDF にも当てはまるため、フラグ false でこの一般案内
  まで消えるのは不正確だった。
- 対応内容: 「常時表示する一般案内」と「`imageSourceDocumentsEnabled` が true のときだけ
  追加する OCR 固有警告」に分離した。既存画面に同種の一般案内があれば重複させず、
  それを正本にすることも明記した。

## [Warning] 波及変更総括が本文と不一致 (施策 10)
- 判断: 対応する
- 対応内容: ドキュメント末尾の「波及変更の総括」へ `imageSourceDocumentsEnabled` と
  確定済みの UI 変更対象ファイルを追記した。施策一覧表の施策 10 の変更ファイル欄も
  具体的なパスへ更新した。

## [Suggestion] `SourceDocumentSizeLimit` の上限超過文言が両 FormRequest で揃うか未検証
- 判断: 対応する
- 対応内容: 共通 Rule (1 インスタンス) を両 FormRequest が使う設計により文言は
  自然に揃うが、これをテストで裏取りすることをテスト計画に含める前提とした。

## [Suggestion] `PipelineSmokeCommand` のフラグ有効化が fixture アップロードより後
- 判断: 対応する
- 対応内容: フラグ設定を fixture アップロードの**前**に行う順序を明記した。
  `--source-kind` の不正値拒否もテスト計画に追加した。

## [Suggestion] 静的 gate 実装 PR での既存動的 static call の棚卸し
- 判断: 対応する (実装時の作業として明記)
- 対応内容: 実装 PR では既存 `app/` の動的 static call 母集団を実測し、
  想定外の候補は黙って除外せず exact-fit inventory で扱うことをリスク欄に明記する
  (施策 8 は概念としては Round 5 で APPROVE 済みのため、この対応は実装時のチェック
  項目として残す)。

## [Suggestion] docblock の「日本語比率だけ」が marker-only 構造検査を書き漏らしている
- 判断: 対応する
- 対応内容: 施策 7 の `validateOcrResult()` docblock を「判読可能な本文の存在と
  日本語比率」に訂正する (実装時に反映)。

## [Suggestion] synthetic 確認後のテストデータ削除が生 DB 操作に読める
- 判断: 対応する (実装時の運用手順として明記)
- 対応内容: 生成した検証用データの削除は既存の通常削除・管理経路 (Service 層) を使い、
  直接 DB 操作をしないことを rollout 手順に明記する。監査ログ・課金 ledger は
  削除対象にしない方針を維持する。

## 施策 9 (token budget) — 未承認のまま確定
- 判断: 施策 9a (一次情報調査: Anthropic 公式ドキュメントの参照・導出式・provider
  hard limit の確認) の完了を実装着手の前提条件として明記したまま、本ラウンドでは
  これ以上の対応を行わない。
- 根拠: 一次情報の取得には外部ドキュメントの参照が必要であり、設計レビューの
  範囲 (提供テキストの分析) を超える。Codex 自身も「このレビューでは提供テキストのみを
  対象としているため、Anthropic の現行仕様値そのものは検証していない」と明記しており、
  設計側で解決できる論点ではない。9a 完了までは施策 3・9 の設定値を確定扱いにしない、
  という条件は既に本文に明記済みである。

## ラウンド上限についての記録
- 本スキルの規定 (`.claude/skills/app-design/SKILL.md`) は詳細設計レビューの合議を

  Round 6 相当の Codex 再確認は行っていないことをここに明記する。
