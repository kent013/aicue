# 対応マトリクス: conceptual-review Round 2

## [Critical] 専用派生 prompt のインスタンス生成箇所が固定されていない
- 判断: 対応する (既存記述を補強)
- 根拠: 「窓口内側は無名クラス」「無名・記名を問わず extends 宣言を数える」までは
  Round 1 対応時点で設計に入っていたが、**なぜ無名クラスなら生成箇所の目録が不要なのか**
  ("宣言" と "生成" が同一箇所である言語上の理由) を明文化していなかった。
  指摘のとおり、これを書かないと「記名クラスに戻したときに生成箇所の目録が要る」条件が
  レビュー可能な形で残らない。
- 対応内容: `new class (...) extends TextPrompt { ... }` は宣言と生成を同一式が兼ねるため、
  継承宣言の出現数を 1 件に pin することと生成箇所を 1 件に pin することがこの構文に限り
  等価であることを明記した。負例に「無名クラスの extends」と「記名クラスの extends」の
  両方を置き、走査器がどちらの構文でも検出できることを裏取りする条件を足した。

## [Warning] 検証済み DTO の TOCTOU (検証と送信の間でファイルが差し替わる)
- 判断: 対応する (既存のバイト列保持方針を補強)
- 根拠: 「DTO はパスでなくバイト列を持つ」という設計は Round 1 時点で既に TOCTOU を
  塞ぐ意図だったが、**読み込みが 1 回であること自体を明示的な不変条件・テスト対象に
  していなかった**ため、実装時に「検証用に 1 回、vendor 変換用にもう 1 回」読み直す
  退行が起こりうる形のままだった。
- 対応内容: 「読み込みは検証の直前に 1 回だけ行い、検証と vendor 媒体型への変換は
  同じバイト列に対して行う」ことを明記し、`SourceDocument` の既存の追記型 immutable 契約
  (更新・削除 API を持たない) を補強材料として引用しつつ、**TOCTOU を消しているのは
  契約ではなく読み込みが 1 回しかない構造の方である**と明確化した。
  テスト計画に「検証から vendor 媒体型生成までの間の読み込みが 1 回であることを
  `Storage::fake()` の呼び出し回数で固定する」を追加した。

## [Warning] token budget 見積りの保証範囲とモデル変更時の再確認
- 判断: 対応する
- 根拠: 「設定値どうしの整合の検査であって実 token 上限保証でない」という誇張しない記述
  自体は Round 1 対応時点で既にあったが、「provider / モデルを変えたら見積り式を
  再確認する」がテストで強制されない努力目標のままだった。
- 対応内容: 見積り式が前提にする provider/モデル名を定数として書き出し、
  `config/prism-prompt.php` の実行時値と一致することを検査する分岐を
  `AnalysisTokenBudgetInvariantTest` に足す設計にした。
  `config/prism-prompt-pricing.php` の `pricing_source` 文字列 pin という既存の前例に倣う形。
  値が食い違ったら見積り式を新しい制約に照らして見直したことを示してから定数を更新する、
  という運用まで明記した。

## [Warning] prompt injection 実効性確認の矛盾 (bug-hunt レーン)
- 判断: 見送る (既に対応済みと判断)
- 根拠: 「保証しないもの」節は既に「実モデルが画像内の命令に従わないことは
  実課金の手動評価でしか測れないので、必要になったらそのときに評価として別に行う
  (`dev:pipeline-smoke` へのOCR経路追加は今回スコープ外)」と明記しており、
  bug-hunt レーン (fake 前提) を実効性確認の手段として挙げていない。
  指摘が読んだ版と現行版で矛盾は既に解消されている。
- 対応内容: 変更なし (文言はそのまま維持)。

## [Warning] 法務文面の rollout dependency
- 判断: 見送る (既に対応済みと判断)
- 根拠: 「ログと外部送信の範囲 (PII)」節に「OCR 機能を production で有効にする前に、
  外部送信の明示を完了しているか、現行の契約・同意で画像を含む文書の送信までカバー済み
  であることを責任者が確認した記録を残す」という rollout dependency が既に明記されている。
- 対応内容: 変更なし。

## [Suggestion] 画像 DTO / PDF DTO の分離 (Warning 型安全性)
