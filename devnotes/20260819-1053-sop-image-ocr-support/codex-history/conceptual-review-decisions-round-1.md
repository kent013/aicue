# 対応マトリクス: conceptual-review Round 1

## [Critical] 媒体添付の責務境界が曖昧 (窓口 / 派生 prompt / factory)
- 判断: 対応する
- 根拠: 指摘のとおり。「窓口の内側だけ」と書いただけでは、派生 prompt が vendor 媒体型を
  自分で生成してよいのかが決まらず、1 本道の gate が形骸化する。
- 対応内容: 責務を 3 行で固定した。
  (1) factory は**ファイルの実体を持たず**、検証済み DTO を窓口へ渡すだけ。
  (2) **vendor 媒体型 (`Media\Image` / `Media\Document`) を生成してよいのは窓口 1 ファイルだけ**。
  (3) 派生 prompt は受け取った媒体を `UserMessage` へ載せるだけで、分岐も検証も持たない。
  併せて静的検査を 2 本足す (vendor 媒体型の生成箇所 = 1 件 pin / vendor prompt 型の継承宣言 = 1 件 pin)。
  いずれも deny-by-default + 件数の完全一致 + 負例で、走査器の共通規約に沿わせる。

## [Critical] 画像・PDF 内の命令が新しい prompt-injection 面である
- 判断: 対応する
- 根拠: `UserInput` のタグ境界化は文字列にしか効かない。合言葉は「system 側の内容が応答に出た」
  ことしか検知しないので、捏造・出力形式の書き換えは素通りする。
- 対応内容: 媒体向けの防御指示 4 項目を YAML の system prompt に明記し、その存在を静的検査で固定する
  (既存の `DefensiveInstructionsPresenceTest` と同じ形)。加えて出力側の構造検証を強め
  (下記 Warning と合流)、**画像内インジェクションの実効性はオフラインでは検証できない**ことを
  「保証しないもの」として明記した (誇張しない)。

## [Warning] 「読めなければ空の構造が返る」は保証ではない (捏造の可能性)
- 判断: 対応する
- 根拠: そのとおり。LLM は空ではなく、もっともらしい嘘を返しうる。
- 対応内容: 記述を「空または構造検証に失敗した結果を終端エラーにする」へ改めた。
  OCR 経路の成功条件として「手順が 1 件以上」と「読み取れた本文の日本語比率が既存の下限以上」を課す
  (既存のテキスト経路のゲートを、抽出後の JSON に対して同じ基準でかけ直す)。
  誤読の是正は既存の「編集する」機能が担う下書きであることも明記した (doc/03 §3.4 の運用前提)。

## [Warning] vendor 組合せでの受理可否を契約テストで確かめるべき
- 判断: 対応する
- 根拠: 「mapper が存在する」と「今 pin している版で意図した content block になる」は別物。
- 対応内容: **LLM を呼ばずに** 組み立て済みメッセージを Anthropic の MessageMap まで通し、
  content block の種別・MIME・順序を検証する契約テストを施策に入れた。

## [Warning] ページ数だけでは資源消費を閉じられない (画素数・破損 PDF)
- 判断: 対応する
- 対応内容: 画像に**画素数と辺長**の上限を追加 (`getimagesize` = 既存 gd/exif の範囲)。
  PDF はページ数を数えられなかったら OCR 経路へ回さない (fail-closed) ことを明記した。

## [Warning] 外部へ出る情報の範囲が広がる (PII) / ログへの base64 保存
- 判断: 対応する (ただし法務文面の整備は本設計のスコープ外)
- 根拠: 手順書本文は既存のテキスト経路でも外部 LLM へ出ているが、写真は顔・氏名・印影が
  そのまま写り込む。ログ面は設計で閉じられる。
- 対応内容: 「媒体のバイナリと base64 をログ・例外・ジョブ行に残さない」を不変条件として明記し、
  検査で固定する。法務文面 (`resources/views/legal/privacy.blade.php` は現在**雛形のまま**で、
  既存のテキスト経路の外部送信すら書かれていない) は別 TODO として起こすことを記録した
  (本設計で雛形を書き換えると、既存経路の未記載を放置したまま片側だけ書くことになる)。

## [Warning] 対象の定義が「スキャン PDF」の説明と一致していない
- 判断: 対応する
- 対応内容: 対象を「**既存のテキスト抽出の品質ゲートに失敗した PDF**」と定義し直した。
  併せて「PDF 本体だけを正本として渡し、抽出できた断片テキストは同時に渡さない」と明記した
  (二重入力による矛盾を作らない)。

## [Warning] チケット 1 のままだとコスト上限として機能しない可能性
- 判断: 対応する (値は変えない)
- 根拠: 予約は `startJob` の 1 回きりで、スキャン PDF かどうかは抽出後にしか分からないため、
  経路依存の可変コストは 2 フェーズ予約の不変条件を壊す。値を動かすのは実データが出てから。
- 対応内容: OCR 経路に**専用の YAML 名**を与えることで、`llm_call_logs.prompt_template`
  (索引済みの既存列) だけで経路別の実 token / 実費が集計できることを明記し、
  **再検討条件**(ページ数・失敗率・1 解析あたりの実費) を設計に置いた。

## [Suggestion] 使命との整合・スコープの線引きは妥当
- 判断: 反映不要 (肯定的評価)

## [Warning] 型安全性 (素の配列で媒体情報を持ち回らない)
- 判断: 対応する
- 対応内容: 不変 DTO で媒体を表し、**生成できるのは MIME sniff・サイズ・画素数・ページ数の
  検証を通った後だけ**にする。1 段目の入力は「テキスト」か「媒体」かの union で表し、
  抽出失敗の種別は既存の慣行 (`LlmOutputInvalidException::$reason` /
  `UntrustedInputRejectionReason`) に倣って**理由 enum** で型として渡す
  (メッセージ文字列で分岐しない)。
