全体判定: **CHANGES_REQUESTED**

**1. 使命との整合性**
- [Warning] **T090-b の「`/billing` にだけ超過可視化を足す」では、現場の詰まりを十分には減らし切れません。** 実際に止まるのはプロジェクト作成とアップロードであり、利用者はその場で失敗を体験します。`/billing` を見に行った人だけが理由を理解できる設計だと、「気づいたら止まっていた」の主問題は残ります。  
  修正提案: `/billing` を単一の正本にする方針は維持しつつ、**ブロック発生地点のエラー文言に `/billing` への誘導を必須化**してください。少なくとも「既存の失敗導線が理由と回復先を明示する」ことを設計に明記し、Feature/Vitest で固定すべきです。
- [Suggestion] **T089-a を許容する判断自体は妥当です。** 「撮影成果を落とさない」を優先しており、North Star との整合はあります。受容するなら、共有端末の運用上の補完策も一文入れておくと判断が強くなります。

**2. 禁止事項違反**
- [Warning] **`AGENTS.md` への追補は過剰です。** 今回の論点は恒久判断ではあるものの、`AGENTS.md` は repo 全体の開発規約であり、個別残存リスクの理由書きを積む場所ではありません。ここに「popstate プローブを採らない理由」まで入れると、将来の設計変更時に規約と実装判断が不必要に結合します。  
  修正提案: 恒久化先は **`docs/supported-browsers.md`、`docs/architecture.md`、対象コードの docblock** に限定し、`AGENTS.md` は触らない方がよいです。
- [Suggestion] DTO/JsonResource パターンに寄せる方針は守れており、`response()->json()` 直書きへ流れていない点はよいです。

**3. 実現可能性**
- [Warning] **T089-b の `AuthenticationException` フックは技術的には成立しますが、適用範囲の設計がまだ粗いです。** 現状文面だと `bootstrap/app.php` で全 `AuthenticationException` を拾うため、Inertia 面だけのつもりが admin/非 Inertia 面にも副作用が及ぶ設計に見えます。  
  修正提案: 「どの条件で `Inertia::clearHistory()` を積むか」を明文化してください。最低でも **session-backed web request / 非 `expectsJson()` / Inertia 着地がある経路** のような判定方針を設計に書き、**非 Inertia の unauthenticated 応答では積まれない負のテスト**を追加すべきです。
- [Suggestion] **T089-b で popstate プローブを却下した判断は妥当です。** 主要導線にネットワーク依存を入れる副作用の方が大きい、という評価は一貫しています。
- [Suggestion] **T090-d で Plan Factory を作らない判断も妥当です。** 参照データの第二真実源を増やさない、という理由が明確です。

**4. 期待効果の妥当性**
- [Warning] **T089-b の期待効果は「セッション終了をアプリが認識した後」に限定されることを、もう一段強く前面化した方がよいです。** 現文でも書かれていますが、効果説明の見出しだけ読むと「履歴復元を塞ぐ」と広く読めます。  
  修正提案: 期待効果と docs 側の要約文を **「認証失敗を契機に以後の戻るを無効化する」** へ言い換え、未解決範囲を対で書いてください。
- [Suggestion] **T090-a の「金銭挙動を変えない」判断は合理的です。** 見積りも state/webhook/UI まで分解できており、単なる慎重論ではなく不足器の列挙になっています。

**5. リスク**
- [Warning] **`business` / `enterprise` の quota 定義欠落を open question のまま流すのは弱いです。** 今回の主題外でも、プラン変更設計に隣接する実害リスクであり、「後で誰かが気づくはず」に見えます。  
  修正提案: 今回の実装スコープに入れないのは許容できますが、**`docs/TODO.md` など追跡可能な恒久台帳へ明示登録**してください。「open question」だけでは再燃防止の目的を満たしません。
- [Suggestion] **T089-a の残存リスク受容は、再検討条件が具体的で良いです。** 特に push 基盤導入時をトリガにしているのは妥当です。

**6. スコープの適切さ**
- [Suggestion] **全体としては最小変更寄りで、作りすぎにはなっていません。** 特に T090-c をコード変更なしの確定に留めているのは良いです。
- [Suggestion] **T090-b で Dashboard 側に同種 UI を増やさない判断も妥当です。** ただし前述の通り、失敗地点からの誘導は別途必要です。

**7. 型安全性**
- [Suggestion] **`QuotaLimitsDto` 拡張の方向性は型安全に乗せやすいです。** `usage` と `over_limit_dimensions` を DTO で厳密型にし、TS 側も同じ shape に同期すれば PHPStan level 10 は十分狙えます。
- [Suggestion] **T090-d は enum 全 case 網羅で固定する案が型安全です。** 文字列比較を UI 側へ漏らさず、PHP enum と TS 型の対応を崩さない前提で進めるべきです。

結論として、**判断の筋は全体に良い**です。特に `T089-a 許容`、`T089-b で popstate を採らない`、`T090-a 現状維持`、`T090-d で Plan Factory を作らない` は概ね妥当です。  
ただし **`/billing` だけで超過認知を完結させる点**、**`AuthenticationException` フックの適用範囲**、**AGENTS.md へ判断理由を持ち込む点**、**business/enterprise quota gap の追跡不足** は、設計として詰めてから進めるべきです。
