# 対応マトリクス: conceptual-review Round 1

## [Critical] PreToolUse の失敗モード (stdin 空 / 非 JSON / 抽出不能 / 巨大 / エスケープ / CLAUDE_PROJECT_DIR 不正) が曖昧

- 判断: **対応する**（指摘は正しい。ここが本設計の急所である）
- 根拠: PreToolUse の終了コード 2 だけが Bash ツールをブロックする。したがって「2 を返す条件」を
  スクリプトの正しさに委ねている限り、**構文エラー 1 つでセッション全体の Bash が止まる**
  (bash は構文エラーで終了コード 2 を返す)。表を書くだけでは、この経路は閉じない。
- 対応内容:
  1. **起動子を終了コードの写像器にする**。`.claude/settings.json` に固定する起動文字列を
     `/bin/bash -p -c '/bin/bash -p "$1"; s=$?; if [ "$s" -eq 97 ]; then exit 2; fi; exit 0' _ "$CLAUDE_PROJECT_DIR/scripts/bughunt-worktree-hook.sh"`
     とする。**スクリプトが意図して 97 を返したときだけ 2 になる**。構文エラー (2)・ファイル不在
     (127)・検索パス破壊 (126/127)・予期しない失敗はすべて 0 に畳まれ、ブロックしない。
     写像器は設定ファイルに直書きされ、台帳テストが完全一致で固定するので、スクリプト側の
     退行から独立している。外部コマンドは 1 つも使わない (`[` `exit` は組み込み)。
     PostToolUse 側も同型に `…; exit 0'` で常に 0 に畳む。
  2. 失敗モードの表を概念設計へ追加し、各行に allow / deny を明記する。
  3. 巨大入力は先頭 1 MiB だけを読んで判定する (組み込み `read -N` の上限)。
  4. 照合は `LC_ALL=C` のバイト列比較。JSON のエスケープは我々が探すバイト列を**消さない**ので
     抽出に失敗しても検出力は下がらない (増える方向にしか働かない)。ただし
     `bug-hunt-shard.sh` と `provision` の間の空白が `\n` 等のエスケープで来る形は
     照合パターン側で受ける。

## [Warning] bash 組み込みだけの JSON 抽出は脆い簡易パーサになりやすい

- 判断: **対応する**（方針は維持するが、壊れた入力時の判断を明文化する）
- 根拠: 完全な JSON パーサを bash で書くのは過剰であり、そもそも**必要ない**。必要なのは
  「この払い出しは `bug-hunt-shard.sh provision` の実行か」という 1 つの述語だけである。
  一方で `python3` に判定を委ねると、検索パスが壊れているだけで拒否対象が黙って通る
  (追従元で実測された欠陥)。
- 対応内容: 判定を 3 段に分け、各段の失敗の倒し方を固定する。
  - 段 0: 生の入力に `bug-hunt-shard.sh` というバイト列が無ければ **通す**
    (外部コマンドを 1 つも起こさない。無関係なコマンドは構造的に影響を受けない)。
  - 段 1: `"command"` の値を bash 正規表現で抽出できたら、その文字列で判定する (現行と同じ意味)。
  - 段 2: 抽出できなければ**生の入力全体**で判定する。許可シグナルが無く
    `bug-hunt-shard.sh <空白> provision` を含むなら拒否側へ倒す。
    影響半径は「`bug-hunt-shard.sh` に言及する払い出し」に限定され、かつ拒否は
    `BUGHUNT_ALLOW_MAIN=1` を先頭に付けるだけで解除できる (詰みを作らない)。

## [Warning] CLAUDE_PROJECT_DIR が常に期待どおりである前提

- 判断: **対応する**
- 根拠: 起動子だけがこの環境変数を使う。未設定ならスクリプトのパスが `/scripts/…` になり
  bash が 127 で終わる。上記の写像器により 127 は 0 に畳まれるのでブロックはしない。
  hook 本体はこの変数を読まず、リポジトリルートを自分の位置から解決する。
- 対応内容: 失敗モード表へ 1 行追加し、台帳テストに
  「`CLAUDE_PROJECT_DIR` を外した状態で固定起動文字列を実行しても終了コードが 2 にならない」
  ケースを入れる。

## [Warning] 告知をどのチャネルに出すか

- 判断: **対応する**
- 根拠: 標準出力はセッションに混入しうる。告知は診断であって成果物ではない。
- 対応内容: 「**告知は標準エラーに 1 行だけ。標準出力は常に空**」と明記する。
  重複抑止はセッションごと・理由ごとに 1 回で、理由の総数が 1 セッションあたりの上限になる。

## [Warning] symlink 拒否の親ディレクトリ / traversal / TOCTOU

- 判断: **対応する**
- 対応内容: 作業ファイル置き場をリポジトリ配下の固定パス
  `.claude/code-review-graph-update-hook/` に決め打ちし、**リポジトリルートから
  その置き場までの各段**が symlink でないことを確認する。作成の前後 2 回検査する。
  セッション識別子は `^[A-Za-z0-9._-]{1,64}$` に合致し `.` / `..` でないものだけを
  ファイル名に使う (合致しなければ固定語 `unknown` に落とす)。安全に作れないと判定したら
  **何も書かずに終える**。

## [Warning] Dockerfile 変更と hook 配線は性質が違う (受け入れ条件を分ける)

- 判断: **対応する**
- 対応内容: 受け入れ条件を 2 系統に分けて概念設計へ書く。
  - 配線系: 索引ツールが**未導入でも**編集が止まらない・告知が 1 行だけ出る。
  - 導入系: コンテナを作り直した後に告知が消え、索引が実際に前進する
    (これは統合後の新しいセッションでしか確認できない = 申し送り事項)。

## [Warning] 実起動層のケースが詳細設計送り / 台帳テストの責務が未明文

- 判断: **対応する**
- 対応内容: 概念設計に「受け入れ条件」節を新設し、静的層 9 項目・実起動層の必須ケースを列挙する
  (網羅的なケース表は詳細設計で書く)。
