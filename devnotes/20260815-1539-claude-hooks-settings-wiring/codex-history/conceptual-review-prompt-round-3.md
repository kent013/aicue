# Round 3: 概念設計の修正

Round 2 の Critical 1 件と Warning 3 件に対応した。

## [Critical] `CLAUDE_PROJECT_DIR` が空・相対・不正 → 対応した

指摘のとおりで、写像器の不変条件が破れていた。写像器が**内側を起動する前に**起動先を検証する形に変えた。

```
d=${CLAUDE_PROJECT_DIR:-}; f=$d/scripts/bughunt-worktree-hook.sh; s=0
if [ -n "$d" ] && 絶対パス($d) && ".." を含まない($d) && [ -f "$f" ] && [ ! -L "$f" ]; then
  /bin/bash -p "$f"; s=$?
fi
if [ "$s" = 97 ]; then exit 2; fi
exit 0
```

- 空 / 相対 / `..` を含む / 通常ファイルでない / symlink のいずれかなら**内側を起動しない**
- 検査はすべて bash 組み込み (`[` / パラメータ展開)
- 実起動テストに「空」「相対値」「`..` を含む値」「別ディレクトリに置いた、97 を返す同名スクリプト」の 4 ケースを追加する
- 保証限界は明記した: リポジトリルート自体のすり替えは証明できない。**Claude Code が渡す絶対パスを信頼境界とする**前提の上に立つ、と「保証しないもの」節へ書いた

## [Warning] 「JSON のエスケープは探すバイト列を消さない」は強すぎる → 一部対応 + 受容を明記

- `\/` は影響しない。探す語 `bug-hunt-shard.sh` に `/` が含まれないため
- ただし**許可シグナル側**の `.claude/worktrees/` は `/` を含むので、`\/` 形式で来ると許可を取りこぼし、正当な worktree 走行を誤って拒否する。照合パターンで各 `/` の前の `\` を任意にして受ける (実装契約に記載)
- `\uXXXX` 形式は取りこぼす。これは**受容**として「保証しないもの」節に記録した。本 hook は早期に気づける層であり権威層は `bug-hunt-shard.sh` 本体の `assert_worktree_context`。脅威モデルは「LLM がうっかり main から直叩きする」であって意図的な回避ではない (回避したい人は `BUGHUNT_ALLOW_MAIN=1` を付ければよく、迂回に手間をかける動機が無い)

## [Warning] 抽出失敗時に生入力の許可シグナルを効かせると別フィールドで解除できる → 一部対応

完全に評価しない案は筋が通るが、**逃げ道の無い詰みを作る** (抽出できない入力は再実行しても同じ形で来るため「正しく抽出できる形で再実行せよ」が実行不能になりうる)。2 つの許可シグナルは性質が違うので分けた。

- `.claude/worktrees/` = 偶然そこにあり得る**痕跡** → 抽出失敗時は**評価しない**
- `BUGHUNT_ALLOW_MAIN=` = 人が意図して置く**明示の解除** → 抽出失敗時も評価する

これで「別フィールドの文字列で誤って許可される」実害は消え、逃げ道は残る。失敗モード表を次に改めた。

| 状況 | 判定 |
|---|---|
| `"command"` を抽出できた | 抽出値だけで判定 (許可シグナル 2 種とも有効) |
| 抽出できない。生入力に `BUGHUNT_ALLOW_MAIN=` がある | 通す |
| 抽出できない。上記が無く `bug-hunt-shard.sh <空白> provision` を含む | 拒否 (97→2) |

## [Warning] 1 MiB 制限は実際の読み込み量の上限でなければならない → 対応した

標準入力の読み取りを 1 回だけにした。

```
LC_ALL=C
IFS= read -r -N 1048576 -t 5 input
```

- 最大 1 MiB で打ち切る
- **5 秒で打ち切る** (bash は時間切れ時も読めた分を変数へ残す) = 標準入力を閉じない相手に待ち続けない
- 読めた分だけで判定し、判定できなければ通す (早期層としての fail-safe 方向)
- 実起動テストに「1 MiB より後ろにだけ拒否対象を置いた入力」と「入力を閉じない producer」の 2 ケースを追加し、上限到達後に待ち続けないことを実測で固定する

## 追加した「保証しないもの」節

- リポジトリルート自体のすり替えは防げない (Claude Code が渡す絶対パスを信頼境界とする)
- ガードは敵対的入力に対する安全境界ではない (`\uXXXX` の取りこぼしを受容。権威層は `assert_worktree_context`)
- 索引更新 hook は索引の正しさを保証しない (保証するのは「止めない」と「黙らない」だけ)
- 配線が効いているかは worktree 内では確認できない (統合後の新セッションで確認)
- ガードのスクリプトが壊れているときは拒否が止まる (意図した取引。静的層が実在と構文を守る)
