### 3. 実現可能性

[Critical] `CLAUDE_PROJECT_DIR` が空・相対・不正なら 127 になる、という前提が成立しません。

現在の起動子では、変数が空なら次を実行します。

```text
/bin/bash -p "/scripts/bughunt-worktree-hook.sh"
```

相対値なら、その値を基準に組み立てたパスを実際に実行します。したがって、偶然または意図的にそのパスへスクリプトが存在し、それが 97 を返せば、無関係な Bash 呼び出しが終了コード2でブロックされます。

写像器は「正規のスクリプト以外が97を返す」経路を閉じていないため、「意図した拒否だけが2になる」という最重要不変条件をまだ満たしません。

修正提案: 外側の写像器で、内側スクリプトを起動する前に `CLAUDE_PROJECT_DIR` を検証してください。最低限、bash組み込みだけで以下を確認します。

- 空でない
- `/` から始まる絶対パス
- `.` または `..` のパス要素を含まない
- 期待するスクリプトが通常ファイルである
- スクリプトが symlink でない

検証不成立時は内側を起動せず0にします。さらに実起動テストへ、空だけでなく相対値、`..`、別ディレクトリに置いた「97を返す同名スクリプト」を追加してください。

なお、通常ファイル・symlink 検査だけではリポジトリルート自体のすり替えまでは証明できません。Claude Code が提供する絶対パスを信頼境界とするなら、その前提と保証限界を明記すれば十分です。

### 5. リスク

[Warning] 「JSONのエスケープは探すバイト列を消さない」は事実として強すぎます。

JSONでは、例えば `/` を `\/`、ASCII文字を `\uXXXX` で表現できます。そのため、意味上は `bug-hunt-shard.sh` を含むコマンドでも、生入力にその連続したバイト列が存在しないことがあります。段0で通過するため、これは限定的な fail-open です。

修正提案: 次のいずれかにしてください。

- 保証を「Claude Code が通常生成する非Unicodeエスケープ形式のJSON」に限定し、その入力形式をfixtureで固定する。
- 段0で最低限 `bug-hunt-shard.sh`、`bug-hunt\/shard`相当ではなく実際の対象表現、`\uXXXX`表現を正規化・検出する。
- 本hookは敵対的JSONに対する安全境界ではなく、権威層は `assert_worktree_context` であると明記し、このfail-openを受容リスクとして記録する。

本hookの位置付けが早期通知層であるため、受容を明記すればCriticalではありません。

[Warning] command抽出失敗時に、生入力中の許可シグナルまで有効にすると、別フィールドの文字列で拒否を解除できます。

例えば説明用フィールドに `BUGHUNT_ALLOW_MAIN=1` があり、実際のcommandには無い場合でも、段2の全体照合では許可扱いになる可能性があります。「許可シグナルを先頭に付ける」という既存条件も、生入力全体では正確に評価できません。

修正提案: commandを抽出できない場合は、許可シグナルを評価せず拒否してください。解除したい場合は、正しく抽出可能なcommand形式で再実行させる方が、deny-by-defaultとして一貫します。

### 7. 型安全性・機械統制

[Warning] 1 MiB制限が「実際に読み込む量の上限」になっていることを実起動テストで固定する必要があります。

入力全体を一度変数へ読み込んでから先頭1 MiBへ切り詰める実装では、正規表現時間は抑えられても、読み込み時のメモリ・待ち時間は制限できません。

修正提案: stdinから最大1 MiBだけを読み、その時点で判定を開始する実装契約にしてください。テストでは、1 MiBより後ろにだけ拒否対象を置いた入力と、入力を閉じずに継続するproducerを使い、上限到達後に待ち続けないことを確認してください。
