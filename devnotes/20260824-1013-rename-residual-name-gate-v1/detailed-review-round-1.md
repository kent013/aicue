## レビュー仮説

検証すべき中心仮説は「有効な各申告が必ず実出現位置を指すなら、未申告位置ゼロかつ申告位置の重複ゼロによって、実出現と申告の全単射を保証できる」である。

この仮説は成立している。ただし、その強化が必要になる決定的な負例が現在のテスト計画では十分に固定されていない。

## S1: 出現特定式の申告台帳

判定: **REQUEST_CHANGES**

アルゴリズム自体は正しい。

- `needle` が旧名をちょうど1回含む
- `needle` が本文にちょうど1回現れる
- したがって、算出した申告位置は必ず実出現位置の部分集合になる
- `actual - declared` が空なら申告外出現はない
- `declared` に重複がなければ、同じ出現への二重申告もない

このため、逆向きの `array_diff($declared, $actual)` がなくても抜け道にはならない。無効な申告は、それ以前の分岐で必ず違反になる。

また、基底実装より位置集合を強める価値もある。件数一致だけでは、異なる2本の `needle` が同じ旧名出現を指し、別の旧名出現が未申告でも通り得るためである。

[Warning] この「件数は一致するが、2申告が同じ位置を指して別の1件が未申告」という本質的な負例がN-4にない。

現在の `(j)` は実出現1件・申告2件なので、単純な件数比較だけでも赤になる。位置集合を導入する必要性の証明にはなっていない。

修正案: 実出現2件・申告2件を用意し、異なる2本の一意な `needle` が両方とも最初の出現を指すケースを追加する。期待違反は以下の2件になる。

- 2件目の実出現が未申告
- 1件目を二重に申告

このケースなら、件数比較では緑、位置集合では赤となり、強化の必要性を直接固定できる。

## S2: パス名の走査

判定: **APPROVE**

パス名に申告口を作らず0件固定にする判断は妥当である。

現在のgitツリーにおいて、過去記録を旧名のファイル名として維持する必要性は示されていない。例外機構を先回りして作らないため、YAGNIにも合致する。将来正当な事例が発生した時点で設計を再検討する方針も適切である。

除外判定がパス照合より先に働く点も、保証外として明記されており、隠れたfail-openにはなっていない。

セキュリティ上も、`Process` の引数は固定配列であり、パス由来のコマンド注入経路はない。

## S3: 空振り防止・負のコントロール・docblock

判定: **REQUEST_CHANGES**

正の対照、母集団下限、追跡下実在、置換先の内容・パス確認という構成は妥当である。照合名一覧もN-3の完全一致で非空が保証される。

[Warning] テストファースト手順2の赤・緑予測が事実と異なる。

「申告本数と実出現数の比較だけ」でも、現在のケースは以下のようになる。

- `(b)` すり替え: 1対1なので誤って緑
- `(j)` 二重申告: 2対1なので赤
- `(k)` needle内に旧名2件: 1対2なので赤

したがって「`(b) / (j) / (k)` が緑になる」という記録は実測できない。

修正案:

- 手順2で緑になるケースは、まず `(b)` のみと正確に記載する。
- 前述の「実出現2件・申告2件だが、2申告とも同じ位置を指す」負例を追加する。
- `(k)` は位置集合強化の根拠ではなく、「needleは旧名を1回だけ含む」という入力契約の負例として位置付ける。

[Warning] `$duplicateViolations[0]` と `$ambiguousViolations[0]` は、空リストだった場合の診断が不明瞭で、PHPStanのバージョン・設定によっては「offset 0 might not exist」の対象になり得る。

修正案: 既に `(b)` で採用している形へ統一する。

```php
expect($duplicateViolations)->toHaveCount(1);
expect(implode("\n", $duplicateViolations))->toContain('二重に指している');

expect(implode("\n", $ambiguousViolations))->toContain('ちょうど 1 回含まない');
```

`ambiguousViolations` についても期待件数を明示すると、余分な違反が増えた退化も検出できる。

## 個別観点

- `strpos()` の `!== false`: 正しい。バイト位置も一貫している。
- 重複出現を `+1` で探索: 正しい。重なりを見逃さない。
- array shape: PHPStan level 10向けとして適切。
- `array_diff` / `array_values` / `sort`: int位置の比較として問題なし。
- Pestの`toContain()`と`toHaveKey()`の引数認識: 設計書の理解は正しい。
- `mb_strlen()`: LaravelのComposerオートロード環境では通常mbstringまたはSymfony polyfillが提供するため、採用に問題はない。
- DTO / JsonResource / Inertia / DESIGN.md / Atomic Design: 本件では非該当。
- 認可・入力検証・テナント境界: アプリ実行経路を変更しないため新規リスクなし。
- `TrackedPhpSourceFiles`との非共有: 規約は「git追跡下のPHP全数」を対象にする場合の単一出典であり、本件は拡張子不問の全追跡ファイルなので抵触しない。
- `RemovedSurfaceScanTargets`との非共有: 母集団と関心事が異なるため妥当。ここで共通化する方が過剰設計になる。

## 全体判定

**CHANGES_REQUESTED**

実装述語そのものに致命的な論理欠陥はない。修正が必要なのは、位置集合へ強化する価値を証明する負のコントロールと、テストファースト手順の事実関係である。そこを直せば承認可能。
