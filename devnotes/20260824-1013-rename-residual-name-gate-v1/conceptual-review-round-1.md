全体判定: **APPROVED**

本件は業務機能ではなく、改名後の運用・規約文書・スキルに旧名が再流入することを防ぐ Architecture テストの追従です。North Star への寄与は間接的ですが合理的で、T214 と同種の開発失敗を早期に止める改善として適切です。

1. 使命との整合性

- [Suggestion] 期待効果の表現は「使命を直接改善する」ではなく、現状どおり「使命を実現する開発・運用手順の信頼性を守る間接的寄与」と明示し続けるとよいです。業務価値との因果が過大になりません。

2. 禁止事項違反

- [Suggestion] 違反は見当たりません。アプリコードや API 応答、LLM 実行経路、UI、DB に触れず、旧実装の件数 pin を同一変更で撤去するため、後方互換の並走も残しません。

3. 実現可能性

- [Suggestion] Laravel/Pest のテスト内で十分実現可能です。`bughuntNamingViolationsIn()` の `$declarations` は PHPStan level 10 向けに、少なくとも「ファイル・旧名・needle・理由」を表す厳密な array shape の PHPDoc を付けてください。任意の `array` に留めないことで、台帳形式の崩れを静的にも防げます。

4. 期待効果の妥当性

- [Suggestion] 妥当です。needle から導いたバイト位置集合と実出現位置集合を完全一致させる方式なら、同数のまま出現箇所だけを差し替える退化を検出できます。パス名も別途照合するため、旧クラス名を含むファイル名の復活も止められます。

5. リスク

- [Warning] needle が将来の文書編集で複数回出現すると、正しい旧名記録まで一時的にテスト失敗になります。これは fail-closed として望ましい一方、保守者が件数だけ直す誤修正をしやすい箇所です。  
  修正提案: 失敗メッセージに「対象ファイル・旧名・needle・検出回数・理由」を必ず含め、正しい復旧手順を「申告を追加・移動・削除する」と明示してください。

- [Suggestion] `devnotes/` とテスト自身を丸ごと除外する穴は、設計で明示されておりスコープとして許容できます。docblock では「そこに旧名を書いても検出しない」ことを断定的に残すのが重要です。

6. スコープの適切さ

- [Suggestion] 適切です。正典 v1 の差分に限定し、別 feature 管轄の shard-cap 改名や共有 SurfaceRemoval 基盤への統合を抱き込まない判断は、関心事と母集団の境界を保てています。

7. 型安全性

- [Suggestion] DTO/JsonResource はアプリ境界の話であり、本件のテスト専用純関数に導入する必要はありません。代わりに、厳密な配列 shape、`list<string>` 相当の戻り値、宣言値の runtime validation（空文字、理由長、needle 内の旧名回数、needle 一意性）を揃えれば、PHPStan level 10 と本リポジトリの静的検査規約に整合します。

特に良い点は、件数 pin を「申告本数から導かれる値」へ置き換えて二重管理を消していること、負のコントロールを実リポジトリの実測値から分離していること、そしてパス名走査を明示的に追加していることです。実装時は N-4 の負例を先に赤く確認し、その後に判定本体を置く流れであれば、提示された設計どおりに安全に追従できます。
