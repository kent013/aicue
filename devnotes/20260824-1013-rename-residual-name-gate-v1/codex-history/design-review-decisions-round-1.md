# 対応マトリクス: design-review Round 1

Codex 判定: **CHANGES_REQUESTED**（S1 REQUEST_CHANGES / S2 APPROVE / S3 REQUEST_CHANGES。
Critical 0 / Warning 3）。3 件すべて**対応する**。指摘はいずれも実測で裏が取れた。

## [Warning] S1: 「件数は一致するが 2 申告が同じ位置を指し、別の 1 件が未申告」の負例が無い
- 判断: **対応する**
- 根拠: 指摘のとおり。現行 `(j)`（実出現 1 件・申告 2 件）は件数比較でも赤になるため、
  位置集合まで強める価値の証明になっていない。素の PHP で実測して確認した —
  申告 2 件・実出現 2 件で 2 申告が同じ出現を指す入力は、件数比較なら緑・位置集合なら赤 2 件
  （`申告外の出現がある` + `二重に指している`）になる。
- 対応内容: N-4 に **(l)** を追加した。前提の「申告 2 件 = 実出現 2 件」を同じテスト内で
  `expect(count(...))->toBe(count(bughuntNamingOffsetsOf(...)))` として明示し、
  そのうえで違反 2 件と両方のメッセージを固定する。詳細設計に
  「### 判定の含意（正典の 3 方向が漏れないことの根拠）」を新設し、
  `$declared ⊆ $actual` の証明・逆向き差分を持たない理由・件数不一致が含意されることを書いた。

## [Warning] S3: テストファースト手順 2 の赤・緑予測が事実と違う
- 判断: **対応する**
- 根拠: 実測で指摘が正しいことを確認した。件数比較だけに落としたとき、
  `(j)`（1 対 2）と `(k)`（2 対 1）は**件数比較でも赤**になる。緑になるのは `(b)`（1 対 1）と
  新設 `(l)`（2 対 2）だけである。
- 対応内容: 手順 2 を「緑になるのは (b) と (l) の 2 ケースだけ」と書き直し、各ケースの
  実出現数・申告数を明記した。`(k)` は「位置集合の必要性の証明」ではなく
  **申告の入力契約の負例**として位置づけ直し、手順 2 の記録に混ぜないと明記した。

## [Warning] S3: `$violations[0]` の添字参照は空リスト時の診断が不明瞭で PHPStan の指摘も呼ぶ
- 判断: **対応する**
- 根拠: 妥当。`(b)` で既に `implode("\n", …)` に対する `toContain()` を使っており、
  形を統一するほうが読み手にも一貫する。
- 対応内容: `(j)` と `(k)` を `toHaveCount()` + `implode("\n", …)->toContain()` の形へ統一した。
  `(k)` は違反 2 件（周辺文字列の契約違反 + 申告外の出現）であることを実測して件数も固定した。
