全体判定: **CHANGES_REQUESTED**

Round 1 の Critical 4件は実質的に解消されています。ただし Phase 1 の実装境界と観測可能範囲に、新しい重大な問題があります。

## 1. 使命との整合性

[Suggestion] Phase 1 を単独でマージすること自体は妥当です。解析が失敗したままでも、「原因を識別できない状態」を解消する独立した価値があります。

ただし、完了条件は「ログ機構を追加した」ではなく、少なくとも実際の generate 失敗が1件記録され、Phase 2 の判断材料を取得できたことに置くべきです。Phase 1 マージ後に調査が止まらないよう、Phase 2 の開始条件と担当TODOも同時に確定してください。

## 2. 禁止事項違反

[Suggestion] factory 経由を維持し、Prism直呼びや guardrail の例外追加をしない方針は適切です。

テストファーストについて、以下を Phase 1 の必須テストとして明記すると設計が閉じます。

- 成功時は従来どおり completed のみ記録される
- 例外時は failed が一度だけ記録される
- retryごとに別試行として記録される
- ログ保存失敗が元のLLM例外を上書きしない
- fake経路のイベント契約が明確である

## 3. 実現可能性

[Critical] 「例外経路がvendor内にあるため、失敗観測はupstreamでしか実装できない」は成立していません。

`asText()` の例外がアプリへ伝播するなら、`AnalysisPipeline`、factoryが返す実行オブジェクト、またはアプリ側decoratorで開始時刻を保持し、catchして記録できます。例外が発生した場所と、観測責務を置ける場所は別です。

修正提案: 詳細設計前に次の比較を行い、最小の案を採用してください。

- `AnalysisPipeline::runGenerateStep` のcatchで記録する
- factory配下の共通executor/decoratorで全LLM呼び出しを記録する
- upstreamにfailed eventを追加する

generateだけが今回の対象なら、pipeline側記録が最小です。全prompt共通の観測が既にpackageの責務として確立している場合に限り、upstream変更が正当化されます。

[Warning] package側のイベントがアプリの`llm_call_logs`へ直接保存するように読めます。汎用packageがアプリ固有テーブルを知る設計なら責務が逆転します。

修正提案: upstreamは型付きイベントの発火まで、DB保存はアプリ側listenerの責務、と明記してください。

## 4. 期待効果の妥当性

[Critical] Phase 1だけでは「実出力トークン数が観測可能になる」という主張は実現できません。

`0 bytes received` のtimeout例外から取得できるのは、失敗までの経過時間・例外種別・試行情報などです。providerが生成したトークン数や最終的な所要時間はレスポンスがないため取得できません。これはPhase 2で完走して初めて測れます。

修正提案: Phase 1の観測可能項目を以下に限定してください。

- 失敗までの経過時間
- 例外種別と正規化した失敗理由
- prompt/model/max_tokens/timeoutなどの実行条件
- retry試行番号
- provider request ID（例外またはヘッダから取得できる場合のみ）

`output_tokens`は失敗時nullとし、実出力トークン数の取得はPhase 2の成果へ移してください。

[Warning] 「600秒ならstreaming + retries削減」という例は、streamingが生成時間を短縮するように読めます。streamingは通信上の壁時計timeoutを回避できますが、総生成時間や時間予算を減らしません。

修正提案: 「600秒でも製品上許容でき、時間予算内ならstreamingが通信方式として候補になる」と条件付きで記述してください。

## 5. リスク

[Warning] 失敗ログ保存自体が失敗し、元のLLM例外を覆い隠す可能性があります。

修正提案: 観測処理はbest-effortにするのか、同期保存を必須にするのかを決め、元例外を保持する不変条件をテストしてください。

[Warning] retry時のログ粒度が未定義です。1ジョブ1件では試行ごとの差が失われ、1試行1件では重複防止が必要です。

修正提案: `analysis_job_id + stage + attempt`などの試行識別子と、一意性・冪等性を詳細設計の必須事項にしてください。

## 6. スコープの適切さ

[Warning] Phase 1は過小ではありませんが、現在案は「観測だけ」に対してupstreamリリース、submodule、migrationまで含み、依然として重い可能性があります。

修正提案: まずアプリ側catchで必要なデータが取れるかを検証し、不足する情報を具体的に示せた場合だけupstream変更へ進んでください。

[Suggestion] timeout意味論スパイクをPhase 1に含めることは妥当です。ただし本番実装と独立した調査成果として扱い、失敗観測機能のマージをスパイク結果で不要にブロックしない方がよいです。

## 7. 型安全性

[Warning] `failure_reason`を生の例外メッセージだけで表現すると、不安定な文字列依存になります。

修正提案: `failure_type`をenumまたは閉じた値オブジェクトとして定義し、生メッセージとは分離してください。失敗DTOはnullable値の集合ではなく、取得可能な必須項目を持たせるべきです。

## Phase 3の進入条件

[Warning] 現在の条件は狭すぎます。

「timeoutがper-readであること」は特定実装案の成立条件であって、streaming一般の進入条件ではありません。壁時計timeoutでも、無効化・十分な上限・別のidle監視が可能なら設計余地があります。また「timeout延長では原理的に届かない」だけでなく、長い無応答待ちが運用上許容できない場合もstreamingの理由になり得ます。

修正提案: 次のように分離してください。

- 解決策再設計への進入条件: Phase 2で現行方式が製品時間予算・信頼性要件を満たさない
- streaming採用条件: 実測したhandler挙動でidle監視・総時間制限・中断・課金管理を実現できる
- upstream変更条件: アプリ内実装では責務分離と必要な観測情報を満たせない

Round 1への対応は形だけではありません。残る本質的な修正点は、**Phase 1で取得できる事実を正確に限定すること**と、**upstream変更が本当に最小手段かをアプリ側catchと比較して立証すること**です。
