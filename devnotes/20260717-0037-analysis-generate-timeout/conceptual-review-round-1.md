全体判定: `CHANGES_REQUESTED`

この概念設計は、問題設定そのものは妥当です。generate 段がアプリの North Star を直撃している点、現状の観測が成功時イベントに偏っていて失敗を捉えられていない点も、本質を突いています。  
一方で、**「まず計測器を正すべき」という主張に対して、提案されている一手がいきなり upstream パッケージ拡張＋ストリーミング化まで大きく飛んでいる**ため、思考原則の「仮説を立てろ」「データに真摯に向き合え」「オーバーエンジニアリング禁止」とまだ整合し切っていません。

**1. 使命との整合性**
- [Warning] generate 段の失敗解消を最優先に置く判断は、使命に強く整合しています。中核価値が成立していない以上、優先度は高いです。
  修正提案: ただし設計目標を「streaming を入れる」ではなく、**「generate を完走可能にし、その失敗要因を事実で分解できる状態を作る」**に置き直してください。これで手段先行を避けられます。
- [Suggestion] 「失敗を観測に載せる」は使命への間接貢献ですが、これは優先度が高い基盤改善です。方針自体は適切です。

**2. 禁止事項違反**
- [Warning] `Prism` 直呼びを避けて factory 経由を維持する、という判断は禁止事項 5 に沿っています。ここは筋が良いです。
  修正提案: ただし upstream 改修が必要な理由を、**「guardrail 回避のため」ではなく「既存の責務分離と観測経路を維持するため」**に言い換えた方が設計意図が明確です。
- [Suggestion] prompt 設定を YAML に置き続ける方針も禁止事項 6 と整合しています。

**3. 実現可能性**
- [Critical] 実現可能性の中核前提が未確定です。未検証前提 1 にある **`StreamHandler` / PHP stream context の timeout 意味論** が false なら、この設計の主張する効果は成立しません。これは詳細設計と並行ではなく、**概念設計の成立条件そのもの**です。
  修正提案: 設計を 2 段階に分けてください。  
  1. 先行スパイク: streaming 時の timeout / read timeout / abort 挙動だけを検証  
  2. 成立を確認できた場合のみ upstream 拡張の詳細設計へ進む
- [Warning] `CurlHandler -> StreamHandler` 切替に伴う `connect_timeout` 無効化や SSE 読み取り特性の差は、実装可能性というより**運用品質の変化**です。現案では副作用列挙に留まり、受容条件がありません。
  修正提案: 「何をもって許容とするか」を先に置いてください。例: 接続失敗時は N 秒以内に fail fast、プロバイダ停止時は idle timeout で回収、など。
- [Warning] upstream パッケージ改修自体は技術的には可能ですが、**アプリ側問題の解決に対して依存境界を跨ぎすぎ**です。
  修正提案: まずアプリ内で解ける範囲を切り分けてください。少なくとも「失敗観測」は streaming 導入と分離して評価すべきです。

**4. 期待効果の妥当性**
- [Critical] 「streaming 化すれば完走可能になる」という期待は、現時点では強すぎます。現状ある事実は「120 秒壁時計 timeout で 0 bytes」のみで、**TTFB が原因なのか、出力量過大なのか、モデル応答自体が不安定なのか**が分かっていません。
  修正提案: 期待効果を弱め、仮説として記述してください。  
  例: 「streaming により '120 秒間 1 byte も返らないこと' が主因だった場合の回避可能性がある」
- [Warning] 「timeout 延長は誤った計測器の目盛りを伸ばすだけ」という主張は、恒久策としては妥当です。ただし、**短期の切り分け手段としてまで退けるのは強すぎる**です。
  修正提案: timeout 延長 + retries 削減を「恒久策ではないが、生成が成立するかを切り分けるための一時診断策」として明示的に位置づけてください。
- [Suggestion] 「失敗ログを取れるようになる」効果は高確度です。これは streaming とは独立に価値があります。

**5. リスク**
- [Critical] 観測改善と送信方式変更を同時に入れると、**何が効いたのか分からなくなる**リスクがあります。思考原則の「結果から学ぶ」に反します。
  修正提案: フェーズを分離してください。  
  1. 失敗観測の追加  
  2. 実測取得  
  3. その結果に基づく streaming 要否判断
- [Warning] アプリ層デッドライン導入後、**途中中断時に provider 側リクエストがどう終わるか**が設計に書かれていません。ジョブは fail しても、外部 API 側では生成継続し課金だけ発生する可能性があります。
  修正提案: deadline 到達時のキャンセル方法、接続遮断時の課金/再試行方針、failed log との整合を明文化してください。
- [Warning] upstream への機能追加は、将来の package 更新コストと release 同期コストを増やします。
  修正提案: upstream 化の採否基準を追加してください。  
  例: 「アプリ内 workaround では guardrail/観測責務を満たせない場合のみ package 変更」

**6. スコープの適切さ**
- [Critical] 現案はスコープが広すぎます。1 つの問題に対して、**upstream API 追加、イベント追加、README/タグ切り、アプリ実装変更、テスト不変条件再設計**まで一気に含めています。概念設計としては、因果がまだ証明されていない段階で重すぎます。
  修正提案: スコープを 3 フェーズに分解してください。  
  1. 観測フェーズ: failed event / duration / timeout reason 収集  
  2. 検証フェーズ: timeout 延長の限定実験 or streaming スパイク  
  3. 解決フェーズ: 必要なら upstream 改修
- [Warning] 「段分割案」をスコープ外にしているのは理解できますが、**実測前に再検討対象からほぼ外している**のは早いです。
  修正提案: 「今回実装しない」ではよいですが、「実測で 1 回生成の出力/時間が製品予算に収まらないと判明した場合の有力代替」として残してください。
- [Suggestion] extract / decompose を今回は触らない判断は妥当です。問題が顕在化している generate に限定している点は良いです。

**7. 型安全性**
- [Warning] DTO / JsonResource の観点では大きな違反は見えませんが、`PromptExecutionFailed` 相当を追加した際に、**成功系と失敗系のログ payload 形状差**が曖昧だと PHPStan level 10 で詰まりやすいです。
  修正提案: 失敗イベント用に明示的 DTO を切り、成功系と union 的に扱わず、保存責務側で分岐を閉じてください。
- [Suggestion] `LlmCallLog` 周辺は、`duration_ms` / `output_tokens` / `failure_reason` / `provider_request_id` の nullable 条件を先に整理しておくと、後の型崩れを防げます。

**特に厳しく見るべき 3 点への回答**

1. **upstream の自作 package に streaming API を足す方針は妥当か**  
[Warning] 現時点では、**第一候補に据えるには早い**です。factory 経由維持という理由は強い一方、まだ「streaming でしか解けない」と立証できていません。  
修正提案: まず「失敗観測追加」と「限定的な切り分け実験」を先行させ、**その結果で only-if-needed で upstream 改修に進む**形へ落としてください。

2. **未検証の前提 3 点は先に潰すべきか**  
[Critical] 少なくとも 1 と 3 は先です。  
- 1: timeout 意味論  
- 3: handler 切替の実害  
これは詳細設計の前提条件です。  
[Warning] 2 の「generate の実出力トークン数・実所要時間」は、観測を入れた後に回収でよいですが、**streaming 実装前に最低限の切り分け実験は必要**です。

3. **実測 0 件で streaming 化を決めるのは正しいか**  
[Critical] 正しくありません。設計文自身が「値ではなく計測器を正すべき」と言っている以上、**先に決めるべきは streaming ではなく observability です**。  
修正提案: 概念設計を「streaming 導入案」から「generate timeout 調査・解消計画」にリフレームしてください。第一マイルストーンは「失敗した generate を測れるようにする」です。

修正後に目指すべき結論はシンプルです。  
**先に計測を入れる。次に、短期の切り分けで timeout 延長や retry 調整も含めて事実を取る。その結果、streaming が唯一筋の通る解なら upstream 改修に進む。**  
この順序なら、North Star に近づきつつ、思考原則とオーバーエンジニアリング禁止の両方を守れます。
