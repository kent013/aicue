## 施策 C: 抽出器の自己検査

判定: REQUEST_CHANGES

### [Warning] P31〜P33では引用符走査の正しさを観測できない

P31〜P33は、いずれも enum case の値にバックスラッシュを置いています。しかし受理正規表現自体がバックスラッシュを拒否するため、抽出器はその case で例外になります。

したがって「後続 case も正しく読めたこと」は戻り値から観測できません。最初の不正 case で即座に例外を投げる実装なら、後続 case へ到達したかどうかも判定できません。別理由の例外でもテストが通るなら、偶奇判定を壊しても緑になり得ます。

修正案:

- P13は「enum case の値にバックスラッシュがあれば限定文法として拒否する」テストとして残す
- P31〜P33では、バックスラッシュを含む文字列をメソッド本体などに置く
- その後に通常の enum case を置き、抽出結果で後続 case が含まれることを検査する
- 単に例外クラスだけでなく、期待値集合または正確な失敗理由を検査する

例えば概念上は次の形です。

```php
enum X: string
{
    public function example(): string
    {
        return '偶奇を試す文字列';
    }

    case A = 'a';
}
```

このメソッド内文字列を次の3系統に変え、いずれも `A` が抽出される、または意図した字句状態になることを固定します。

- 奇数本: 引用符はまだ文字列内
- 偶数本: 引用符は終端
- 3本・4本以上: 奇偶だけで判定される

PHPとして有効な文字列を組み立てにくいケースは、enum直下の case ではなく、字句走査専用の内部関数を公開範囲外で分離して単体検査する方法でも構いません。

### [Warning] TS fixture の実際の case 数は26ではなく27

現在の表を数えると次のとおりです。

- T1〜T9: 9件
- T10a・T10b: 2件
- T11〜T24: 14件
- T25a・T25b: 2件

合計は `9 + 2 + 14 + 2 = 27` 件です。本文の「TS 26件」と一致していません。

修正案:

- 現行行列のままなら TS pin を27件にする
- 実装時に確定するだけでなく、設計書の期待件数も27件へ直す
- matrix配列、件数定数、fixture実在集合の三者を同じテストで突き合わせる

`program-fixtures/` に正常なaugmentationを残す構成自体は妥当です。`registry-augmentation.ts` は外部モジュールとして成立するよう、`import "./registry-base"` または `export {}` を持たせてください。
