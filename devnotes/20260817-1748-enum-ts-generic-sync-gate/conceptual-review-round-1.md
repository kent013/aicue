全体判定: **CHANGES_REQUESTED**

主要な方向性は妥当です。特に、正規表現抽出を TypeScript Compiler API に置き換え、既存・未登録を含む完全一致の対応を目録化する判断は、無言の値域乖離を減らすために有効です。ただし、AG-099 後半の先送りを「後でやる」とするだけでは、追加される列挙の取りこぼしを防げません。

## 1. 使命との整合性

[Suggestion] 撮影・編集・課金・権限の状態値が画面で無反応や空白表示になる事故を防ぐため、North Star には間接的ながら明確に貢献します。特に `TakeStatus`、解析状態、役割、プラン符号を対象に含めるのは合理的です。

[Warning] 「状態値で分岐する面が多い」ことから、すべての値域同期が同程度に現場価値へ直結すると読める表現は避けるべきです。

修正提案: 期待効果を「サーバー由来の文字列値を TS union で受ける箇所に限る防御」と明記し、ラベル・表示順・フロント専用状態・部分集合は保証外と区別してください。

## 2. 禁止事項違反

[Suggestion] 禁止事項への直接の抵触は見当たりません。テストを削除すること自体も、同じ不変条件をより強い抽出器・広い母集団で同一変更内に再構築する移設であり、思考原則 3 と整合します。

[Warning] PHP テストを削除した後、`composer test` 単独ではこの不変条件を検証しません。コミット前に全検証を実行する運用だけに依存するなら、開発者が PHP レーンだけを回した際の検出時点は後ろ倒しになります。

修正提案: これは薄い PHP 委譲テストを復活させる理由にはしませんが、当該 gate の正本レーンを JS と明記し、CI の frontend/job と `pnpm test` が必須の保護境界であることを文書化してください。

## 3. 実現可能性

[Suggestion] Laravel 12 / Svelte 5 / Inertia の構成でも、Vitest から TypeScript Compiler API を使う設計は実現可能です。型チェッカーによる別名解決は `MemberRoleState` のようなケースを正しく扱えます。

[Warning] PHP 側を「最小の字句解析」で読む部分は、実装境界が曖昧なままだと別の静かな誤抽出器になり得ます。コメント、属性、文字列エスケープ、enum 内のメソッド・定数、入れ子の構文を安全に排除・通過できなければなりません。

修正提案: 抽出器の受理文法を明文化し、少なくとも以下を fixture として fail-closed テストに含めてください。

- コメント・文字列中の偽 `case`
- enum 本体外の `case`
- 属性、メソッド、定数を含む enum
- `'` / `"` とエスケープを含むリテラル
- 定数式・非文字列・構文不全
- TS の別名、多段別名、開いた union、非文字列 literal、`never`

また、目録の TS ファイルを root にしても import 先の型宣言が Program に含まれることを、別名参照 fixture で固定してください。

## 4. 期待効果の妥当性

[Suggestion] 正規表現の注釈誤認・開いた union 誤認・別名未解決という問題設定は妥当で、Compiler API はこの種の構文上の曖昧さを排除できます。14 組から 27 組への拡張も、少なくとも明示された対応については実効的です。

[Warning] 「実測で残り 1 件」という結論は、別名参照を読めない正規表現ベースの探索に依存しているため、網羅性の証拠にはなりません。48 件も下限だと明記されています。

修正提案: 「残り 1 件」は後半実装の見積り仮説として扱い、発見漏れがない事実としては扱わないでください。AG-099 後半の全数走査を入れた時点で初めて検証できる、と文書へ明記すべきです。

## 5. リスク

[Warning] 型情報を使う gate は、Program 構築・解決失敗・テストの並列実行で遅くなり、architecture レーンの安定性を損なう可能性があります。

修正提案: `beforeAll` の一回構築、明示タイムアウトに加え、対象ファイルの読込範囲、失敗時のエラー文（PHP enum path / TS path / 宣言名）、実行時間の上限を自己検査してください。型解決不能を空集合扱いせず、必ず失敗にしてください。

[Suggestion] `.svelte`、配列、switch、部分集合を対象外にすることは、v1 の抽出責務を過剰に広げない点で適切です。

## 6. スコープの適切さ

[Warning] AG-099 後半を今回外すことは、前半を安全に着地させるための分割としては妥当です。しかし、未登録の新規対応を今後検知できない状態が残ります。後半を TODO にするだけでは既定拒否の設計意図を満たしません。

修正提案: 後半を、所有者・完了条件・優先度を持つ `docs/TODO.md` の明示 TODO として同時に起票してください。完了条件は少なくとも「PHP 文字列 backed enum 全数を、登録・対象外理由・探索不能のいずれかに分類」「逆走査 2 規則を実装」としてください。

[Suggestion] 既に完全一致している未登録 13 組を今回追加するのはスコープ膨張ではありません。これは汎用 gate の初期母集団を正しい既知状態へ移す作業であり、分割すると「既知の穴を意図的に残す」ことになります。各行は新規仕様ではなく既存事実の宣言です。

## 7. 型安全性

[Suggestion] TS strict 下で実装可能です。目録は `as const satisfies readonly ...[]` とし、パス・宣言名・説明の構造を型で固定できます。Compiler API の戻り値は `TypeFlags.StringLiteral` と union の構成要素を明示的に狭めれば、`any` に逃げずに書けます。

[Warning] PHP enum 値の抽出結果、TS 値集合、目録行のエラー処理を曖昧な `string[]` や nullable 値で流すと、TS strict の利点を失います。

修正提案: 抽出成功を `ReadonlySet<string>`、失敗を path・宣言名・理由を持つ例外または discriminated union として表し、「空集合」と「抽出失敗」を型・実行時ともに区別してください。

## 固有論点の判断

(i) **PHP レーンから JS レーンへの移設と PHP テスト 4 本の削除は妥当です。**  
薄い PHP 委譲テストは独立した不変条件を増やさず、二重の宣言と保守対象を残します。型情報が必要な検査の正本は JS レーンに一本化し、旧抽出器と旧テストは同一変更で削除するべきです。

(ii) **AG-099 後半を今回の実装スコープから外す判断は条件付きで妥当です。**  
ただし、上記の明示 TODO が同時に作られ、探索結果が下限であることを認める必要があります。これがなければ、既定拒否の未達が無期限に残ります。

(iii) **未登録の完全一致 13 組を今回登録するのは妥当であり、膨張ではありません。**  
汎用 gate の既知母集団を一括で正規化する不可分の作業です。gate が実際に全 27 組を検証することで、調査結果そのものも検証されます。

(iv) **完全一致だけを登録する割り切りは妥当ですが、万能ではありません。**  
同一のドメイン値域を表す宣言には強い一方、部分集合の意図は表現できません。`SelectableTakeStatus` を登録しない判断は正しいです。ただし、未登録の完全一致候補を将来検出する仕組みは AG-099 後半で必須であり、それまではこの割り切りに発見保証はありません。
