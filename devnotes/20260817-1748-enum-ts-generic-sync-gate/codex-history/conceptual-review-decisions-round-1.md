# 対応マトリクス: conceptual-review Round 1

## [Warning] 1. 期待効果が「すべての値域同期が同程度に現場価値へ直結する」と読める
- 判断: 対応する
- 根拠: 誇張しない書き方は本リポジトリの規約 (AGENTS.md の各所が「保証範囲を誇張しない」を要求)。
- 対応内容: 概念設計の「期待効果」冒頭に守る範囲を限定して明記し、組ごとに重さが違うことを書いた。
  「保証しないもの (誇張しない)」節を新設し、ラベル・並び順・部分集合・`.svelte`・
  未登録の写しを保証しない側へ列挙した。

## [Warning] 2. PHP テスト削除後、`composer test` 単独ではこの不変条件を検証しない
- 判断: 対応する (委譲テストの復活はしない)
- 根拠: 指摘自体が「委譲テストを戻す理由にはしない」と述べており、同意する。
- 対応内容: 「保証しないもの」に**正本のレーンは vitest (`pnpm test`)、CI では `frontend` job が
  保護境界**であることを明記。施策 E (規約・文書) でも AGENTS.md へ同じ 1 文を書く。

## [Warning] 3. PHP 側の「最小の字句解析」が別の静かな誤抽出器になり得る
- 判断: 対応する
- 根拠: これが最大の実装リスク。受理文法を明文化しないと (a) 注釈内の `case`、
  (b) メソッド内 `switch` の `case`、(c) エスケープを含む値、で誤読しうる。
- 対応内容: 概念設計に受理文法 (波括弧の深さ 1 のみ / 注釈・文字列・属性を文脈で除外 /
  深さ 1 の `case` で形が合わないものは例外) を明記。詳細設計に fixture 一覧を置く
  (指摘された 11 項目をそのまま負例行列に入れる)。
  「別名参照 fixture で import 先が program に含まれることを固定する」も採用する。

## [Warning] 4. 「残り 1 件」は網羅の証拠にならない
- 判断: 対応する
- 根拠: そのとおり。実測は正規表現ベースで、別名参照を数えていない (#17 が実例)。
- 対応内容: 概念設計のスコープ外節と `survey.md` の両方に「これは見積りの仮説であり
  網羅の証拠ではない / 母数 48 件は下限」と明記した。

## [Warning] 5. 性能・失敗時のエラー文・型解決不能の扱い
- 判断: 対応する
- 根拠: aigenba も「program 構築が最初の 1 テスト内で走ると制限時間を超えうる」と実測している。
- 対応内容: 概念設計に「抽出の失敗と空集合を混同しない / 例外文に PHP パス・TS パス・宣言名・
  理由を必ず入れる」を追加。program は `beforeAll` で 1 度だけ、目録の TS ファイルだけを起点に、
  明示の制限時間つきで構築する (制約・前提に既記載)。実行時間の上限の自己検査は
  詳細設計で採否を判断する。

## [Warning] 6. AG-099 後半を TODO にするだけでは既定拒否の設計意図を満たさない
- 判断: 一部対応する (TODO.md への起票は本設計の権限外)
- 根拠: 本設計タスクは devnotes 配下の設計ファイルのみを書く任務で、`docs/TODO.md` の変更が
  明示的に禁止されている (起票は `app-todo-add` スキルの責務)。
- 対応内容: **本作業の完了条件に「後続 TODO の起票」を含める**とスコープ外節に明記し、
  起票内容 (全数走査の 3 分類 + 逆走査 2 規則) を完了条件の文面としてそのまま書いた。

## [Warning] 7. 抽出結果を `string[]` / nullable で流すと strict の利点を失う
- 判断: 対応する
- 根拠: 「空集合」と「抽出失敗」の区別は degenerate PASS 防止の核心。
- 対応内容: 概念設計に「値の集合を返すか例外を投げるかのどちらか」を明記。
  詳細設計で `ReadonlySet<string>` を戻り値、失敗を専用の例外型とする。
  目録は `as const satisfies readonly EnumTsMirror[]` で型固定する。
