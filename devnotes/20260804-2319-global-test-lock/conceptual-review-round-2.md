全体判定: **CHANGES_REQUESTED**

Round 1 の主要指摘は概ね適切に反映されています。特にマシン全体 × UID への変更、期待効果の限定、bug-hunt の残余リスク明示は妥当です。ただし、ロック保持期間に関する実装上の致命的な不整合が残っています。

## 1. 使命との整合性

[Suggestion] テストレーンの信頼性向上は、並行開発速度を通じた間接的貢献として妥当です。North Star への直接機能ではないため、現在の限定的な位置づけで問題ありません。

## 2. 禁止事項違反

[Critical] `devnotes/{dir}/verify-global-test-lock.sh` を一時検証スイートとするだけでは、禁止事項1の「不変条件を対応する Architecture/Feature テストへ登録」を満たしません。`devnotes` は恒久的な回帰防止境界ではなく、将来削除されても CI が検知できないためです。

修正提案: shell 検証本体は恒久的な `scripts/` またはテスト用ディレクトリへ置き、Architecture テストから実行するか、少なくとも恒久的な Architecture テストで次を固定してください。

- 4レーンの配線 inventory
- 旧ロックが残っていないこと
- 恒久 shell 検証スイートが存在し、成功すること

fail-first の観測用コピーや実行記録だけを `devnotes` に置く構成が適切です。

## 3. 実現可能性

[Critical] `exec "$@" 7>&-` は、ラッパ自身が唯一のロック保持者なら、テスト開始時に fd 7を閉じてロックを即解放します。特に次の2箇所は設計どおりでは排他が成立しません。

- `with-global-test-lock.sh` の `exec "$@" 7>&-`
- `run-vitest.sh` の `exec pnpm exec vitest run "$@" 7>&-`

「fdを子へ継承しない」と「コマンド実行中もロックを保持する」を両立するには、保持用の親プロセスが必要です。

修正提案: ラッパは `exec` せず、fd 7を保持した親 shell が子コマンドを `7>&-` で起動して終了を待ち、その終了コードを返す構造にしてください。

```bash
"$@" 7>&-
status=$?
exit "$status"
```

`set -e` 下でも終了コードを回収できる制御構造にする必要があります。ロック保持期間とプロセス構造を詳細設計の不変条件として明記してください。

[Warning] `EXIT / INT / TERM` をすべて同じ cleanup trap にすると、シグナル処理後の `EXIT` でcleanupが二重実行される可能性があります。

修正提案: cleanup を冪等化し、sidecar は「現在の内容のnonceが自分のnonceと一致する場合だけ」削除してください。INT/TERMではtrap解除後に対応する終了コードで終了する契約も固定してください。

## 4. 期待効果の妥当性

[Warning] 「H1が構造的に消える」は、このロック規約へ参加するテストレーン間に限って成立します。同一UIDの別ツールや未移植リポジトリは同じロックを取得せず、Playwrightプロセスへ干渉できます。

修正提案: 「本ロック規約を採用したテストレーン間ではH1を防止する」と表現を限定してください。

## 5. リスク

[Critical] bug-hunt とBrowser laneの非干渉を「プロセス名パターンの非マッチ」だけで証明することはできません。`playwright-cli kill-all` が何を列挙・停止するかは、Browser lane側の `pgrep` パターンとは独立した問題です。この検証では偽グリーンになり得ます。

修正提案: `playwright-cli kill-all` の対象決定方式を実装または公式契約から確認し、可能なら両サーバを同時起動する振る舞いテストで非干渉を固定してください。非干渉を証明できない場合は、bug-huntとの併走禁止を注意書きではなく機械的排他にする必要があります。

[Warning] UID接尾辞は、別ユーザーによる予測可能パスの先取りを防ぎません。別ユーザーも任意のUID文字列を含むファイルを先に作成できます。また、`${TMPDIR}` がプロセスごとに異なると同一UIDでも別ロックになります。

修正提案: マシン全体という保証を優先するなら、基点を一意に固定し、ファイルの所有者・種類・権限を検証してください。利用可能なら所有者専用のランタイムディレクトリを使い、フォールバック時の安全な作成規則も定義してください。

[Warning] sidecarは「診断専用」とされていますが、nonce再入判定にも使われているため、実際には認可判断の一部です。

修正提案: 「排他の正本ではないが、再入判定の正本」と役割を正確に記述し、原子的書き込み、所有者検証、nonce一致時のみ削除を不変条件に加えてください。

## 6. スコープの適切さ

[Suggestion] 4レーンの包含、CIを特別扱いしない判断、worktree-local flockの完全削除は、恒久inventoryとロック保持期間が正しく実装される条件で妥当です。

## 7. 型安全性

該当なし。

現時点で4要件のうち、ブロッキング取得・heartbeat・再入ガードは概念上定義されていますが、**fd非継承はロック保持期間と両立していません**。ここが承認を妨げる最大の問題です。
