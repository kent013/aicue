## 3. 実現可能性

[Critical] INT/TERM受信時の子プロセス処理が未定義です。親がtrapでsidecarを削除して自死しても、fd 7を持たないテスト子プロセスが生存し続ける可能性があります。その状態でロックだけが解放され、次のレーンと旧レーンが同時実行されます。

修正提案: 親は子PIDまたはプロセスグループを管理し、INT/TERM時に次を順序保証してください。

1. 子または専用プロセスグループへ同じシグナルを転送する。
2. 子の終了を待つ。
3. nonce一致を確認してsidecarを削除する。
4. fdを閉じてロックを解放する。
5. 親自身も同シグナルで終了する。

層1へ「TERM中も、子が終了するまで第三レーンが取得できない」「背景子が残らない」の検証を追加してください。

## 4. 期待効果の妥当性

[Suggestion] H1/H2/H3の効果と保証限界は適切に限定されています。

## 5. リスク

[Critical] bug-huntポートのlisten確認はTOCTOUがあるため、機械的排他にはなりません。

```text
Browser: ポート未使用を確認
bug-hunt: 起動してlisten開始
Browser: テスト開始
```

また、bug-huntの起動フェーズによっては活動中でも一時的にlistenしていない可能性があります。したがって「危険な併走経路を塞ぐ」「Browser laneは機械的に塞がれる」は成立しません。

修正提案: 排他を保証するなら両側が参加する共有プロトコルが必要です。例えばbug-huntが活動期間中に共有ロックを保持し、Browser laneが同じロックを非ブロッキング取得してfail-fastする方式です。bug-hunt側を変更しないなら、ポート検知はbest-effort guardへ格下げし、非干渉保証を撤回してください。

[Warning] ポートlisten検知に必要なコマンドと対応環境が前提へ記載されていません。`ss`、`lsof`、`netstat`では利用可能性や出力形式が異なります。

修正提案: 使用する検知手段、コマンド不在時の挙動、IPv4/IPv6双方の扱いを明記し、層1で固定してください。共有ロック方式なら、この依存自体を避けられます。

[Warning] UID接尾辞の説明に矛盾が残っています。前半では「UID接尾辞がパス先取りを塞ぐ」とし、後半では「UID接尾辞だけでは防げない」と正しく訂正されています。

修正提案: 前半の根拠を「ユーザー間の通常運用上の衝突を分離する」に変更し、悪意・事故による先取りは0700ディレクトリの検証によってfail-secureに検出すると整理してください。

## 6. スコープの適切さ

[Warning] bug-hunt側を完全にスコープ外としながら、bug-huntとの機械的排他を保証するスコープ設定は成立しません。

修正提案: bug-huntへの最小限の共有interlock追加を本件に含めるか、bug-hunt併走問題全体を残余リスクとして明示してください。保証とスコープのどちらかを合わせる必要があります。
