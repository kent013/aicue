# 概念設計: template-divergence-machine-layer

## 背景・課題

`docs/template-divergence.md` (テンプレートからの意図的逸脱の登録簿) は、家系の機能台帳 lctl の
feature `template-divergence-ledger` が管理する仕組みである。本アプリの現状は次のとおり。

- 実エントリは **18 件** (`## D1` 〜 `## D18`。冒頭の「エントリ形式」の記入例は囲みコード区画の中)。
  台帳の観測 (2026-08-14 / 13 件) より 5 件増えている。本日の作業で D14〜D18 が足されたためで、
  **台帳の観測値は現 HEAD と一致しない**。作業量の確定は現物の実読で行う。
- 各エントリは「3 列の比較表 + 3 つの節 (なぜ正当な差分か / 揃えている不変条件 / 関連)」の構成で、
  **家系の統一形式が要求する登録メタ表を 1 件も持たない**。状態・決めた日・決めた人・根拠・
  見直し期限・再判定の条件を書く場所そのものが無い。
- 見出しは全 18 件が `## D<n> ✅ <要約>` の形で、印 (✅) を含む。統一形式の正準形は
  **印を持たない `## D<n> <要約>` の行全体一致**である。
- `D9` は見出しに `✅→解消` を掲げ、本文が「記録は削除せず経緯として残す」と書いている。
  統一形式は**解消した逸脱を登録から消す**と決めている (残すと掃除漏れの検出を回避できるため)。
- 形式を見る検査が 1 本も無い。件数も期限も人の記憶だけで守られている。
- 過去の巡回が「記録されるべきなのに未登録」と指摘した逸脱が積み上がっている
  (2026-08-09 に 2 件 / 08-10 に 2 件 / 08-12 に 3 件)。現 HEAD でも登録されていない。

### 台帳の正典が 2026-08-15 に確定し、担当範囲が変わっている

本作業の起票時点の指示は「指紋台帳と突合検査 (機械層) を作る」だった。しかし
lctl の確定設計 (`ledger/features/template-divergence-ledger/design.md`、2026-08-15 確定) は、
不変条件 i13 で次のように決めている。

> 共有ファイルの中身の突き合わせは**台帳リポジトリの巡回が行い**、未記録の差分を各アプリの
> 受信箱へ届ける。各アプリの義務は届いた差分を自分の登録簿へ記録するか、テンプレートの内容へ
> 戻すことだけである。**各アプリに指紋の台帳と突合の検査を新設することは求めない**。

裁定 AG-159 (2026-08-13) が機械層の提供者を台帳リポジトリへ移したためで、本アプリ宛ての
実装タスク (lctl の申し送り 2026-08-15 09:35) も「形式の検査を提供元から移植する」までしか
求めておらず、指紋台帳・突合検査は項目に無い。

**したがって本作業は、指紋台帳と共有ファイルの突合検査を作らない**。作るのは
「登録簿の形式を機械で見る層」と「登録簿そのものの移行・掃除・追加」である。
テンプレートのソースはこのマシンに無いので、指紋を採る対象の母集合を本アプリだけで
正しく作ることは原理的にできない。作れば必ず手書きの母集合になり、
正典が禁じている「載せなければ検査されない抜け道」を自分で作ることになる。

### それでも「登録漏れ・掃除漏れ」の両方向は本作業の担当範囲に残る

内容の突合 (実ファイルがテンプレートと違うか) は台帳リポジトリが持つ。本作業が持つのは、
**登録簿という文書の中で起きる登録漏れ・掃除漏れ**であり、これは次の 3 つで両方向に見る。

| 方向 | 何が起きるか | どう見るか |
|---|---|---|
| 登録を触ったときの同期漏れ | 登録を足した / 消したのに、明示件数か検査側の固定件数が追随しない | 明示行の件数・解析した件数・検査側に固定した件数の **3 点一致** (増減どちらも不合格) |
| 掃除漏れ (登録対象の消滅) | 対象パスのファイルが無くなったのに登録が残る | 対象パスの**実在検査** |
| 掃除漏れ (解消を状態で表す形) | 解消したことにして登録を残す | 状態の値域に解消を表す語を持たせない (解消は登録の削除でしか表せない) + **登録エントリ領域** (最初の `## D<n>` 見出しから文書末尾まで) の中では `##` 見出しを正準形だけに限る (領域の中に履歴の節を作れない) |
| 二重計上 | 同じパスを 2 つの登録が挙げ、片方を消しても赤にならない | 全登録の対象パスの**和集合で重複禁止** |

**3 点一致は新しい登録を書かせる仕組みではない**。逸脱を作ったのに誰も登録簿に触らなかった場合、
3 つの件数はどれも動かないので緑のままである。実逸脱の未登録を見つけるのは台帳リポジトリの巡回だけである。

## 改善アイデア

1. **登録簿を家系の統一形式へ移す** — 見出しの正準形 (印なし)、9 行の登録メタ表、
   状態の値域 2 語、対象パスの複数記載、件数の明示行。
2. **解消済みの登録を消す** (D9)。経緯は設計ノートと TODO に残っているので情報は失われない。
3. **形式を見る検査を 1 系統新設する** — 判定は純粋ロジック層 1 か所に閉じ、検査層は薄くし、
   負例は単体テストで固定する。許可一覧を持たない (deny-by-default)。
4. **未登録の逸脱を洗い出して登録する** — 過去の巡回が挙げた 7 件を現 HEAD で 1 件ずつ検証し、
   「逸脱として登録する / 逸脱ではない (テンプレートに無い領域への追加) / 判定材料が足りない」の
   3 分類に決着させる。判定材料が足りないものは**でっち上げず、台帳リポジトリへ差し戻す**。

   **既定は「登録する」か「差し戻す」**であり、「逸脱ではない」は例外扱いとする (正典 i15 =
   誤検出は登録 1 行で消せるが検出漏れは永久に気付けない、という非対称に合わせる)。判定基準:

   - 「逸脱ではない」と結論してよいのは、次の 3 つのいずれかを根拠にできる場合**だけ**である。
     (a) 台帳リポジトリから届いた判定、(b) 既に確定している正典がテンプレートの管理範囲を定めている、
     (c) 候補を指摘した側 (巡回) が分類を認めている。**本アプリの中に新しく文書を書いて
     「アプリ固有だから逸脱ではない」と自分で証明する形は認めない** (テンプレートが手元に無い以上、
     自己証明は根拠にならない)
   - テンプレートの管理範囲かどうかが分からないものは「判定材料が足りない」へ倒す
     (テンプレートのソースはこのマシンに無いので、分からないことは頻繁に起きる)
   - **既存登録の説明文に同じパスが出るだけでは「登録済み」と数えない**。登録メタ表の対象パス欄だけを正とする
   - 候補ごとに結論・根拠・現 HEAD で確認した対象パスを判断ログ
     (`devnotes/{実装 dir}/unregistered-divergence-triage.md`) に残す。差し戻し分はこのログを根拠に
     監督セッションへ報告する (台帳への書き込みは行わない)

## 期待効果

- 使命への貢献は間接である。撮影 PWA の 3 枚セット (no-store / bfcache 秘匿 / 履歴暗号化) や
  テナント境界のような**セキュリティ不変条件は、テンプレートとの差の理由が記録されていないと
  「追従漏れ」と誤読されて戻される**。登録簿はその誤読を止める装置で、腐らせない仕組みが要る。
- 家系の他リポジトリと書式が揃うと、台帳リポジトリの巡回が本アプリの登録簿を
  「登録メタ表の対象パス欄」だけ読んで解釈できるようになる (現在は全文検索に頼っており、
  説明文でパスに触れただけでも記録ありと数える = 取りこぼす側に倒れている)。
- **登録簿を触ったときの同期漏れ** (件数の黙った増減 / 対象パスの消滅 / 期限切れ /
  対象パスの二重計上) が CI の赤として出る。**未登録の逸脱そのものの検出は台帳リポジトリの巡回の
  担当であり、本アプリの CI は肩代わりしない**。

## 保証しないもの (誇張しない)

本作業で作る検査が見るのは `docs/template-divergence.md` という**文書の中の整合だけ**である。
次のものは**一切保証しない**。

- **実ファイルがテンプレートから逸脱したのに登録が無いこと** (登録漏れそのもの)。
  実体との突合は台帳リポジトリの巡回が行い、差分は受信箱経由で届く (正典 i13 / 裁定 AG-159)。
- **共有ファイルの指紋の鮮度**。本アプリは指紋台帳を持たない。
- **登録の中身が正しいこと**。業務要件起因の説明・不変条件・再判定の条件は、空でないこと以外を
  機械で判定しない (文意は機械照合できない)。
- **対象パスが逸脱の全体を覆っていること**。挙げ漏らしたパスには沈黙する。
- **番号の連続性**。欠番は正常であり、検出も是正もしない。
- **内容としては解消済みの逸脱が残っていること**。ファイルを残したまま中身をテンプレート準拠へ戻した
  場合、対象パスは実在し続けるので検査は緑のままである。この向きの掃除漏れは台帳リポジトリの
  突合が見つける。
- **登録を書かせること**。3 点一致は「登録簿を触ったときに 3 つの数が揃っていること」しか見ない。
- **登録エントリ領域より前に置いた節**と、**エントリの中の `###` 見出しや地の文**。
  規約節を置く場所が要るので領域の前は自由にしてあり、エントリの中の小見出しも数えない。
  したがって「履歴を残す形は 1 つも作れない」とは書けない (作れるのは領域の中の `##` 見出しだけを塞いだ状態である)。

### 実行不能は不合格 (fail-closed)

登録簿が読めない / 見出しが 1 件も取れない / メタ表を解析できない / 明示行が読めない /
基準日が取れない — これらはすべて**明示的な検査失敗**にする。空集合へ落として緑にする経路と、
skip する経路は作らない (正典 i12)。

### 9 行の登録メタ表 (順序も規定)

| 行 | 値域 |
|---|---|
| 対象パス | リポジトリ相対のファイルパス 1 件以上。glob・絶対パス・上位への相対指定は不可。実在すること。全登録の和集合で重複しないこと |
| 業務要件起因の説明 | 自由記述 (空・プレースホルダ不可) |
| 揃え続ける不変条件と保証機構 | 自由記述 (空・プレースホルダ不可) |
| 再判定の条件 | 自由記述 (空・プレースホルダ不可)。**恒久の登録にも必須** |
| 決めた日 | `YYYY-MM-DD`。実在する日付で未来日は不可 |
| 決めた人 | `オーナー` / `開発者` の 2 語 |
| 根拠 | `T<n>` (`docs/TODO.md` と `docs/TODO-closed.md` の**両方**を照合先として実在) または `devnotes/<dir>/` (ディレクトリが実在)。プレースホルダ不可 |
| 状態 | `恒久` / `監視中` の 2 語 (どちらも「今ある逸脱」を表す。解消を表す語は持たない) |
| 見直し期限 | `監視中` は `YYYY-MM-DD` 必須 (検査実行日から 400 日以内・期限切れは不合格)。`恒久` は `—` 固定 |

### 件数の数え方と、固定件数の位置づけ

- 件数は**見出しに一致した行数**で数える。番号の最大値でも連続性でもない (欠番は正常)。
- 3 点一致の 3 点は「登録簿の明示行の N」「解析した見出しの件数」「検査側に固定した件数」。
  **固定件数は明示件数との同期検査であって、例外を許す一覧ではない**。個別の D 番号を
  名指しする許可一覧は持たない (持てば「登録しなくてよい逸脱」を作る口になる)。
- 見直し期限の判定は**基準日を引数で受け取る純関数**にする。検査層が今日の日付を渡し、
  単体テストは固定日を渡す (実行日でテストが揺れない)。

### 移行で新しく決める値の出どころ (推測しない)

既存 17 件は状態・決めた人・決めた日・根拠・再判定の条件を持っていない。これらは**推測で埋めない**。

埋め方は **「証拠から転記する」か「差し戻す」の 2 択**である。資料から推測して確定値を書かない。

| 行 | 転記できる条件 (これを満たすときだけ書く) | 満たさないとき |
|---|---|---|
| 決めた日 | **逸脱を最初に決めた日**で統一する (移行時の再確認日ではない)。逸脱を決めた設計文書を実読し、**その文書の中で当該逸脱が決まっていること**を確認できたら、その `devnotes/<dir>/` の日付を採る。設計文書が無いものは、対応する TODO の行に当該逸脱の実装が書かれていることを確認できたらその完了日を採る | 判断ログへ移行ブロッカーとして書き、監督セッションへ差し戻す。**「台帳へ登録した日」で代用しない** (代用の可否は正典の未決の論点 q2 であり、本アプリが勝手に決めてよい問題ではない) |
| 決めた人 | 家系の裁定 (AG-xxx) かオーナーの指示を根拠に持つものは `オーナー`、設計フローの中で決めたものは `開発者`。どちらも根拠文書で確認できること | 同上 |
| 根拠 | 対応する TODO 番号 (`docs/TODO.md` / `docs/TODO-closed.md` に実在)。無ければ逸脱を決めた設計の `devnotes/<dir>/` | 同上 |
| 再判定の条件 | 台帳本文の「揃えている不変条件」「収束条件」「保証しないこと」に材料があること | 同上 |
| 状態 | `監視中` にしてよいのは、根拠文書に**期限・予定時期・追跡中の事象**があり、そこから 400 日以内に見直す根拠を導ける場合**だけ**。解消の条件は書かれているが時期を導けないものは `恒久` にし、その条件を `再判定の条件` へ転記する | 見直す意思は明確なのに期限だけ導けないものは、期限を発明せず差し戻す |
| 見直し期限 | `監視中` のみ。**根拠文書から導ける日付**を書く (実装日から 400 日以内) | 同上 (差し戻す) |

**状態の既定を `恒久` にする理由** (推測ではないことの説明): `恒久` は「今のところ期限を切って
見直す予定が無い」という意味であって「永久に正しい」という主張ではない。正典 i9 が
**`恒久` にも再判定の条件を必須**にしているので、期限が無くても見直しの経路は必ず残る。
逆に見直しの時期を導ける材料が無い登録へ移行担当が期限を発明すると、
**根拠の無い日付で将来 CI が赤くなる** (仕組みが機能していない段階で値を弄る形)。
**解消の条件が書かれていることは `監視中` の根拠にならない** — i9 により `恒久` の登録も
「条件 X が成立したら見直す」を必ず持つので、条件の有無では区別にならないからである。
区別になるのは**期限付きで能動的に見直す証拠 (期限・予定時期・追跡中の事象) があるかどうか**で、
それがあるものだけ `監視中`、残りを `恒久` に置くのは証拠に基づく既定であって推測ではない。
**この割り当ては移行時の分類であり、逸脱そのものの是非の再判断ではない**ことを登録簿の規約節に明記し、
1 件ずつの根拠を判断ログに残す。

### 番号は振り直さない

`AGENTS.md` が D14 と D16 を名指しで参照しており、lctl 台帳も `aicue:D8` 等で参照している。
D9 を消しても後続を詰めない (欠番のまま)。新規登録は D19 から続ける。
統一形式が要求するのは**リポジトリ内で一意**であることだけで、連番であることではない。

### 検査の作り方は自リポジトリの先例に合わせる

本アプリには「文書に埋め込んだ一覧を機械と**双方向**で照合する」実装が既に 3 件ある
(`RouteBindingCustomBinderDocSyncTest` / 検証コマンドの同期テスト / 冪等性の契約テスト)。
うち `RouteBindingCustomBinderDocSyncTest` は、抽出を純関数に分け、
正のコントロール (両方向の違反を実際に検出できること) と負のコントロール
(対象範囲の外は拾わないこと) をテストで固定している。本作業はこの作法をそのまま踏襲する。

## 制約・前提

- **git 操作をしない**。設計ファイルの作成のみ (実装は別タスク)。
- 台帳への書き込み (`append_event`) はしない。判定材料が足りない候補の差し戻しは、
  監督セッションへの報告として返す。
- `docs/TODO.md` は編集しない。
- 検査は `composer test` の Architecture / Unit スイートで走る (CI で赤になる)。
- 期限切れが将来 CI を赤にするのは**仕様**である。直し方は登録簿の規約節が持つ 4 通りの遷移
  (逸脱を解消して登録を消す / 恒久へ変えて理由を足す / 期限を延ばして再判断の根拠を足す /
  対象を分けて個別に判断する) から選ぶ。**検査を緩めることは選択肢に入れない**。
- 移行は 1 ファイル (`docs/template-divergence.md`) に集中するため、他の設計者の作業と
  衝突しやすい。実装は本ティアの最後に行い、その時点の全エントリを一度に移す。

## スコープ外

- **共有ファイルの指紋台帳と突合検査** (正典 i13 / 裁定 AG-159 により台帳リポジトリの担当)。
- **既存登録 (削除する D9 を除く D1〜D18) の是非の再判断**。移行は書式の移し替えであり、既存の判断を覆さない
  (状態・決めた人・再判定の条件は新規に決めるが、逸脱そのものの是非は再議論しない)。
  施策 5 は「まだ登録されていない逸脱を登録するかどうか」の判断であり、これとは別の行為である。
- 番号の振り直し・エントリの統廃合。
- 本文 3 節 (比較表 / なぜ正当な差分か / 揃えている不変条件 / 関連) の書き直し。
  そのまま残す (捨てるものは無い)。
