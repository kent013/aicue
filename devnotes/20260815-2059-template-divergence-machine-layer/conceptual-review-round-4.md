全体判定: **CHANGES_REQUESTED**

Round 3 の全面対応2件は妥当です。状態割り当てへの反論も「根拠のない期限を発明しない」「`恒久` にも再判定経路がある」という部分は成立します。ただし、`監視中` の判定条件がまだ広すぎます。

### 1. 使命との整合性

[Suggestion] 使命への寄与と保証範囲は適切に限定されています。台帳リポジトリとの責務分離も一貫しています。

### 2. 禁止事項違反

[Suggestion] docs + tests の範囲に閉じ、Architecture/Unitテストまで計画されているため、禁止事項への抵触はありません。

### 3. 実現可能性

[Suggestion] `##` 制約を登録エントリ領域に限定した対応は妥当です。検出できない履歴表現も明示され、過大な保証は解消されています。

詳細設計では、囲みコード区画内の見本を領域開始や見出しとして数えない負例を固定すれば十分です。

### 4. 期待効果の妥当性

[Suggestion] 件数同期、実在性、期限、重複に限定されており、期待効果は検査能力と一致しています。

### 5. リスク

[Warning] 状態割り当てへの反論は一部成立しますが、「解消・卒業・収束の条件が書かれているだけで `監視中`」は成立しません。

i9により`恒久`にも再判定条件が必須なので、恒久登録にも「条件Xが成立したら解消を検討する」という記述があり得ます。条件の存在だけでは、400日以内に能動的に再確認する`監視中`との区別になりません。

また、「条件が判断できるようになる時期」から期限を決める規則は、その時期が根拠文書にない場合、Round 3で避けようとしている期限の発明に戻ります。

修正提案:

- `監視中`にできるのは、根拠文書に期限、予定時期、追跡中の事象など、400日以内に見直す根拠がある場合だけとする
- 見直し期限も、その根拠から導出できる場合だけ設定する
- 解消条件はあるが時期を導出できない場合は`恒久`とし、再判定の条件へ転記する
- 監視意思は明確だが期限だけ導出不能な場合は、期限を発明せず差し戻す

この条件なら、`恒久`を既定とする反論は成立します。これは逸脱の是非ではなく、期限付き監視を裏付ける証拠の有無による運用分類です。

[Suggestion] 「決めた日」を証拠から転記するか差し戻すかの二択にした判断は妥当です。正典の未決論点q2をアプリ側で先取りしない点も適切です。

### 6. スコープの適切さ

[Suggestion] D9を明示的に除外したことで、既存登録の再判断と削除済み登録の扱いに矛盾はありません。

### 7. 型安全性

[Suggestion] readonly class、型付き違反結果、日付注入、fail-closedの組み合わせでPHPStan level 10に適合可能です。

残る論点は1点です。`監視中`を「収束条件の存在」ではなく「期限付きで監視する証拠の存在」に結び付ければ、概念設計として承認可能です。
