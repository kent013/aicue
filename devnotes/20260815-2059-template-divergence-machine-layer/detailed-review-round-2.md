## 施策 4: REQUEST_CHANGES

[Critical] `CarbonImmutable::createFromFormat()` の失敗値に対する型締めがありません。

`createFromFormat()` は解析失敗時に `false` を返し得ます。そのまま `format()` を呼ぶ実装では、PHPStan level 10 のエラーまたは実行時エラーになります。「解析失敗を違反として返す」という設計にもなっていません。

修正案: 日付検査を次の条件として明記してください。

```php
$date = CarbonImmutable::createFromFormat('!Y-m-d', $value);

if (! $date instanceof CarbonImmutable || $date->format('Y-m-d') !== $value) {
    // 日付形式違反
}
```

TD6とTD8の双方について、`''`、`not-a-date`、`2026-02-30` が例外ではなく違反一覧へ入る負例を追加してください。

[Warning] 囲みコード区画の解析文法が Markdown の fence 文法より緩く、開始 fence と無関係な行でトグルします。

「行頭が ````` ならトグル」では、4文字以上の fence、開始・終了の長さ、`~~~` fenceを正しく扱えません。現行の記入例だけなら動きますが、「Markdown の囲みコード区画を落とす」という保証範囲とは一致しません。

修正案は次のどちらかです。

- 正式にバッククォート3個だけを台帳の許可書式と定め、それ以外の fence を違反にする。
- 開始時に fence の文字種と長さを記録し、同じ文字種かつ同じ長さ以上の終了 fenceだけで閉じる。`~~~` も扱う。

少なくとも4バッククォートと `~~~` の fixture を追加し、受理または明示的拒否のどちらになるか固定してください。

[Warning] メタ表のセル分割における `|` の扱いが未定義です。

自由記述3欄には Markdown のエスケープ済み `\|` やインラインコード内の `|` が入り得ます。単純な `|` 分割では列数が増え、意図せず解析不能になります。

修正案: 統一形式としてセル内の `|` を全面禁止するか、`\|` を許可してエスケープを考慮して解析するかを規約と Parser 仕様に明記し、対応する正例・負例を追加してください。簡潔さを優先するなら全面禁止で十分です。
