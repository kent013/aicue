全体判定: **CHANGES_REQUESTED**

Round 1 の主要指摘には概ね対応できています。特に i13 に基づいてアプリ側へ指紋台帳を作らない判断は妥当です。一方、検査能力の説明にまだ過大な部分があり、施策 5 と移行メタデータの証拠基準も確定が必要です。

### 1. 使命との整合性

[Warning] 登録簿内の件数一致を、依然として「登録漏れ」の検出と表現しています。

「逸脱を作ったのに登録が増えない」場合、明示件数・解析件数・固定件数はすべて変化せず、3点一致は緑のままです。検出できるのは、登録簿を変更した際の同期漏れです。

修正提案: 表と期待効果を次のように限定してください。

- 「登録漏れ」ではなく「登録エントリ変更時の件数同期漏れ」
- 実逸脱の未登録は台帳リポジトリ巡回だけが検出する
- 3点一致は新規エントリ作成を強制する仕組みではない

### 2. 禁止事項違反

[Suggestion] docs + tests に限定され、Architecture/Unit テストも計画されているため、明示された禁止事項への抵触はありません。

`response()->json()`、LLM 経路、DB 操作、UI、Artifact も対象外です。

### 3. 実現可能性

[Warning] i12 の「実行不能は不合格」が検査仕様として明示されていません。

ファイル未読、Markdown解析失敗、基準日の生成失敗などが「エントリ0件」やテストスキップとして扱われる余地があります。

修正提案: 入力ファイル不存在・読み込み失敗・構文解析不能・日付取得不能はすべて明示的な検査失敗とし、空集合へのフォールバックや skip を禁止してください。

[Suggestion] 基準日の注入、純粋ロジック層、readonly value object の方針は Laravel 12 / PHPStan level 10 で実現可能です。

### 4. 期待効果の妥当性

[Warning] 「掃除漏れ」の説明も一部過大です。

対象パスの実在検査が検出するのはファイル自体が消えた場合だけです。ファイルは残したままテンプレート準拠へ戻した場合、古い登録は検出できません。状態値から「解消」を排除しても、`恒久` のまま残る stale entry は検出できません。

修正提案: 「掃除漏れを検出」ではなく、次の保証に限定してください。

- 登録対象ファイルの消滅
- 解消状態を使った登録残置
- 同一対象パスの二重登録

内容上すでに解消した逸脱の残置は、本検査では保証しないものへ追加してください。

### 5. リスク

[Warning] 既存17件へ新設するメタデータの証拠規則が不足しています。

「状態・決めた人・再判定の条件は新規に決める」とありますが、移行担当者が過去の判断者・判断日を推測すると、形式は正しくても来歴が虚偽になります。

修正提案: 各値は既存TODO・devnotes等から導出し、導出不能なら推測せず移行ブロッカーとして判断ログへ出す、と定めてください。「決めた日」が原判断日か移行時の再承認日かも統一してください。

[Warning] 施策5の「根拠ファイル付き」の資格がまだ曖昧です。

ローカル文書を新設して「アプリ固有」と書けば自己証明できてしまいます。テンプレートが手元にない以上、根拠の権威性が必要です。

修正提案: 「逸脱ではない」の根拠を、台帳リポジトリから届いた判定、既存の正典による管理範囲定義、または候補指摘元が認めた分類に限定してください。それ以外は差し戻しに倒すべきです。

### 6. スコープの適切さ

[Suggestion] 1タスク内でコミットを分ける判断は妥当です。形式移行と候補判定のレビュー境界が明確になり、同一ファイルへの競合も増やしません。

ただし「逸脱の中身の再判断はスコープ外」と施策5は別行為なので、スコープ外の記述を「既存登録 D1〜D18 の是非は再判断しない」と限定すると矛盾がなくなります。

### 7. 型安全性

[Suggestion] `ParsedEntry` / `EntryMetadata` を readonly class にする方針は適切です。詳細設計では、解析エラーを欠損値や空配列で表さず、型付きの違反結果または例外として扱うと PHPStan level 10 と fail-closed を両立できます。

固定件数を個別D番号の許可一覧と分離した点も妥当です。

i13 の判断自体は承認できます。再修正の中心は、3点一致とパス実在検査が実際に検出できる範囲への表現修正、既存メタデータと「逸脱ではない」判定の証拠基準の固定です。
