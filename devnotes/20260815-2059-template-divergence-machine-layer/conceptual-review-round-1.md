全体判定: **CHANGES_REQUESTED**

**1. 使命との整合性**

[Suggestion] 使命への貢献は間接だが妥当です。実行コードを変えず、テンプレート逸脱の理由・対象・期限を機械検査することで、PWA 撮影やセキュリティ不変条件を「テンプレート追従漏れ」と誤って戻すリスクを下げる、という位置づけは合理的です。

[Warning] ただし、期待効果に「登録漏れが CI の赤として出る」とありますが、本設計の検査だけでは「実ファイルがテンプレートから逸脱したのに登録がない」ことは検出できません。検出できるのは登録簿内の件数不一致・対象パス重複・対象パス消滅などです。  
修正提案: 「未登録の逸脱そのものの検出は台帳リポジトリ巡回の担当。本アプリ側 CI は、登録簿に記載された内容の形式・整合性・掃除漏れを検出する」と明記してください。

**2. 禁止事項違反**

[Warning] 「未登録の逸脱 7 候補の判定と登録」は docs 変更のみなので原則問題ありませんが、判定材料が足りないものを台帳リポジトリへ差し戻す運用が曖昧です。台帳への書き込みはしない、とある一方で、どこにどう記録して次工程へ渡すかが不明です。  
修正提案: 実装タスクの成果物として「登録した候補」「逸脱ではないと判断した候補」「差し戻す候補」を `devnotes/.../review-result.md` のような非恒久メモに残す、など出口を定義してください。

[Suggestion] アプリ実行コードを変えず docs + tests のみというスコープは、`response()->json()`、Prism 直呼び、POST 応答などの禁止事項には基本的に触れません。

**3. 実現可能性**

[Warning] 「対象パスは実在すること」と「D9 を消しても欠番のまま」「件数の 3 点一致」は実現可能ですが、欠番を許す場合の件数定義を厳密に書く必要があります。最大番号ではなく、実エントリ数を数える設計にしないと D1〜D18 から D9 欠番の状態で誤判定しやすいです。  
修正提案: 検査仕様に「番号の連続性は要求しない。`## D<n> ` に一致した見出し数、明示件数、テスト固定値の 3 点一致を見る」と明記してください。

[Warning] 見直し期限の「検査実行日から 400 日以内」は CI 実行日依存のため、純粋ロジック層に現在日を直接読ませるとテストが不安定になります。  
修正提案: 判定関数は `today` を引数で受け取り、Architecture test から `CarbonImmutable` 等で固定日を渡す設計にしてください。実行不能は不合格という i12 とも整合します。

**4. 期待効果の妥当性**

[Warning] 施策 5 の「未登録の逸脱の判定」基準がまだ甘いです。現状の 3 分類は良いですが、「逸脱ではない」の判定条件が弱いと、台帳巡回が指摘した差分をアプリ側判断で握り潰せます。  
修正提案: 少なくとも次を判定基準に追加してください。

- 「逸脱ではない」は、対象がテンプレート管理外のファイル・節・アプリ固有領域であることを根拠ファイル付きで示せる場合に限る
- テンプレート管理範囲か不明な場合は「判定材料が足りない」に倒す
- 既存登録の説明文に同じパスが出るだけでは登録済み扱いにしない。9 行メタ表の対象パスだけを正とする
- 判断ログに候補ごとの結論・根拠・参照した現 HEAD の対象パスを残す

[Suggestion] i15 の「迷う場合は過剰検出寄り」に合わせるなら、7 候補の扱いも「未登録として追加」か「差し戻し」をデフォルトにし、「逸脱ではない」は例外扱いにするのが妥当です。

**5. リスク**

[Critical] 共有ファイルの指紋台帳と突合検査を作らない判断自体は妥当です。i13 と AG-159 が担当境界を明確にしており、各アプリ側で手書き母集合を持つと「載せなければ検査されない」抜け道を作る、という理由も正しいです。  
ただし、その代わりに本アプリ側で検出できない範囲を期待効果から削らないと、設計が過大な保証を主張します。  
修正提案: スコープ外だけでなく「保証しないもの」節を追加し、「テンプレート実体との差分検出」「共有ファイル指紋の鮮度確認」「台帳リポジトリとの突合」は本検査では一切保証しない、と明記してください。

[Warning] 「根拠: T<n> は TODO 台帳に実在」は、`docs/TODO.md` だけを見るのか `docs/TODO-closed.md` も見るのか不明です。解消済み逸脱を消す設計と矛盾しないよう、根拠が Closed に移った場合の扱いを決める必要があります。  
修正提案: `T<n>` の実在範囲を `docs/TODO.md` と `docs/TODO-closed.md` の両方にするか、Open のみとするかを明文化してください。監視中の根拠なら Open 必須、恒久の歴史根拠なら Closed 可、のように分けてもよいです。

**6. スコープの適切さ**

[Warning] docs + tests の移行としては概ね適切ですが、「未登録の逸脱 7 候補の判定と登録」まで同時に入れると、形式移行と内容判断が混ざります。スコープ外に「逸脱の中身の再判断」とあるため、候補の新規登録判断と少し衝突しています。  
修正提案: 本タスクでは「既存 17 件の形式移行」と「過去指摘 7 件の分類ログ作成」までにし、新規登録は分類ログで根拠が揃ったものだけ同一 PR に含める、と条件を明確にしてください。

**7. 型安全性**

[Suggestion] DTO/JsonResource はアプリ応答に関係しないため直接の論点ではありません。純粋ロジック層を PHPStan level 10 前提で作るなら、Markdown パース結果を配列のまま流すより、`TemplateDivergenceEntry`、`TemplateDivergenceMetadata`、`TemplateDivergenceViolation` のような小さな value object に閉じる方が堅いです。

[Warning] 「許可一覧を持たない」は正しい一方、テスト側に固定件数を持つ設計は実質的な台帳になります。これは i6 の要請なので問題ありませんが、許可一覧と誤解されない説明が必要です。  
修正提案: 固定件数は「例外許可」ではなく「明示件数との同期検査」であり、個別 D 番号の allowlist は持たない、と明記してください。
