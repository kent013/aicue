# 対応マトリクス: conceptual-review Round 3

## [Warning] `##` 見出しの禁止が文書全体に掛かると規約節を置けない (観点 3)
- 判断: 対応する
- 根拠: 指摘のとおり。規約節は登録エントリより前に置く必要がある
- 対応内容: 制約を**登録エントリ領域** (最初の `## D<n>` 見出しから文書末尾まで) の中だけに限定した。
  領域より前は自由。あわせて「領域より前の節」「エントリの中の `###` 見出しと地の文」を
  保証しないものへ追加し、「履歴を残す形は 1 つも作れない」とは書けないと明記した

## [Warning] 「決めた日」の導出規則がまだ推測を含む (観点 5)
- 判断: 対応する (ただし再承認日での代用は採らない)
- 根拠: ディレクトリの日付や TODO の完了日は、それ自体では「逸脱を決めた日」の証拠にならない。
  一方で「移行時に再承認してその日を決めた日にする」案は採れない — 特定できないときに
  「台帳へ登録した日」で代用してよいかは**正典の未決の論点 q2** であり、
  台帳リポジトリ側の実装タスクも「特定できないものが出た場合は差し戻すこと」と指示している。
  本アプリが勝手に決めると、家系の未決論点を一方的に確定させることになる
- 対応内容: 埋め方を「証拠から転記する」か「差し戻す」の**2 択**に固定した。転記できるのは
  **設計文書を実読してその中で当該逸脱が決まっていることを確認できたとき**だけとし、
  確認できないものは移行ブロッカーとして判断ログへ書き、監督セッションへ差し戻すと明記した

## [Warning] 状態を本文から機械的に決める規則は i9 と整合しない (観点 5)
- 判断: 一部対応する (「本文から機械的に決まる」は削除。オーナー再承認の必須化は採らない)
- 根拠: 「機械的に決まる」という書き方は誤りなので削除した。ただし全 17 件にオーナー再承認を課すと、
  書式の移行がオーナーの手番を待って止まる。正典 i9 が **`恒久` にも再判定の条件を必須**にしているため、
  `恒久` でも見直しの経路は必ず残る。逆に収束条件が書かれていない登録へ移行担当が期限を発明すると、
  根拠の無い日付で将来 CI が赤くなる (思考原則 = 仕組みが機能していない段階で値を弄らない)
- 対応内容: 「本文か設計文書が解消・卒業・収束の条件を書いているものだけ `監視中`、残りは `恒久`」とし、
  `恒久` が既定である理由 (i9 が再判定の条件を必須にしているので見直し経路は残る / 期限の発明は
  根拠の無い赤を作る) を明文化した。あわせて**この割り当ては移行時の分類であって逸脱の是非の
  再判断ではない**ことを登録簿の規約節に書き、1 件ずつの根拠を判断ログに残すことを必須にした。
  なお `決めた人` は逸脱を決めた主体を指す欄であり、状態の割り当て者を指す欄ではない (二重の意味を持たせない)
