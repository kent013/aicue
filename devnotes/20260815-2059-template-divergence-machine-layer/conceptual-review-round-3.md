全体判定: **CHANGES_REQUESTED**

Round 2 の指摘は適切に反映されています。i13 による責務分離、検査の保証限界、施策5の権威ある根拠、fail-closed、型安全性は承認できます。ただし、移行メタデータの導出規則に、推測禁止と矛盾する箇所が残っています。

### 1. 使命との整合性

[Suggestion] 使命への寄与を間接的な保守・セキュリティ保全として限定しており妥当です。3点一致の保証範囲も正確になりました。

### 2. 禁止事項違反

[Suggestion] docs + tests の変更であり、対応するArchitecture/Unitテストも計画されています。禁止事項への抵触はありません。

### 3. 実現可能性

[Warning] `## D<n>` 以外の `##` 見出しを文書全体で禁止する規則は、i4を超えた独自制約です。

規約節など、登録ではない正当な第2階層見出しまで置けなくなる可能性があります。また、履歴を `###` や通常文で残すことは防げないため、掃除漏れ対策としても十分ではありません。

修正提案: 登録エントリ領域を明示的に区切り、その領域内だけで見出しを制約するか、この規則を削除してください。解消済み内容の残置は、すでに「保証しないもの」で正確に扱えています。

### 4. 期待効果の妥当性

[Suggestion] 対象パス消滅、件数同期、期限切れ、重複に効果を限定したため、主張と検査能力が一致しています。

### 5. リスク

[Warning] 「決めた日」の導出規則は、なお推測を含みます。

devnotesのディレクトリ日付は作成日、TODOの完了日は完了日であり、「逸脱を最初に決めた日」の証拠とは限りません。現在の規則では、証明できない日を確定値として記録できます。

修正提案: 日付を採用できるのは、根拠本文がその日に逸脱を決定したと確認できる場合に限定してください。確認できなければ、移行時にオーナーまたは開発者が再承認し、その再承認日を「決めた日」とするか、移行ブロッカーとして差し戻してください。

[Warning] 状態を「本文に解消・卒業・収束条件があるか」で機械的に決める規則は、i9と整合しません。

再判定条件は恒久にも必須なので、収束条件の存在だけでは `監視中` と `恒久` を区別できません。期限付きで積極的に見直す意思があるかどうかは、既存本文から自動導出できない判断です。

修正提案: 状態は根拠文書に明示されている場合のみ転記し、それ以外はオーナーまたは開発者による再承認を必須にしてください。少なくとも「本文から機械的に決まる」は削除し、導出不能時をブロッカーに含める必要があります。

### 6. スコープの適切さ

[Suggestion] 既存登録の是非と未登録候補の分類を分離したことで、施策5との矛盾は解消されています。

ただし、スコープ外の「D1〜D18」には削除対象のD9も含まれます。「D9を除く既存登録の是非」とすると文面上も一貫します。

### 7. 型安全性

[Suggestion] readonly class、型付き違反結果、基準日の注入という方針で、PHPStan level 10に適合可能です。解析失敗を空配列へ落とさない方針もfail-closedと整合しています。

残る修正点は実装方式ではなく、移行データの真正性です。日付と状態を「資料から推測して埋める」のではなく、「明示的な証拠から転記するか、再承認するか、差し戻す」の三択に固定できれば承認可能です。
