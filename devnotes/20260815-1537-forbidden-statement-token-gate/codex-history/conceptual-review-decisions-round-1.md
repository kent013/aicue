# 対応マトリクス: conceptual-review Round 1

## [Warning] 観点 1 — `resources` を丸ごと除外すると `<?=` 禁止に穴が残る

- 判断: **対応する**
- 根拠: 指摘の前提を実測で確認した。Blade ファイルに対する `token_get_all()` の挙動は次のとおり。

  | Blade の書き方 | 割り当てられるトークン | 走査で見えるか |
  |---|---|---|
  | `<?= $raw ?>` | `T_OPEN_TAG_WITH_ECHO` | **見える** |
  | `<?php echo "x"; ?>` | `T_OPEN_TAG` + `T_ECHO` | **見える** |
  | `@php echo "x"; @endphp` | `T_INLINE_HTML` | 見えない |
  | `{{ $x }}` | `T_INLINE_HTML` | 見えない (Blade の逸出機構が担う) |

  「Blade はすべて地の文になる」という除外理由は**誤りだった**。
  PHP 開始タグで開いた区間は通常の PHP として字句化される。
  実測で `resources` 配下の追跡 PHP 24 ファイルに違反は 0 件なので、
  走査根へ加えるコストはゼロで、`<?=` を 0 件のまま固定できるようになる。
- 対応内容: `resources` を **走査する / 例外の登録を許さない** 側へ移す。
  除外は `devnotes` の 1 つだけになる。あわせて「保証しないもの」に
  「Blade の `@php` ブロックと `{{ }}` の中は字句走査では地の文になり見えない」を明記する。

## [Warning] 観点 3 — root の数え方が曖昧 (11 個と言いつつ分類は 12 区分に見える)

- 判断: **対応する**
- 根拠: 指摘のとおり。追跡 PHP を持つ実ディレクトリと、ディレクトリを持たない
  リポジトリ直下のファイル群を同じ「root」という語で数えていた。
  分類漏れ検査の期待値が曖昧になるという指摘は正しい。
- 対応内容: 「追跡 PHP を持つ実ディレクトリ 11 個 + リポジトリ直下 (疑似 root) 1 個 = 分類 12 件」と
  書き分ける。enum の case にも `RepositoryRoot` を独立に置く。

## [Warning] 観点 4 — `resources` 除外のままだと「`<?=` を 0 件のまま固定する」は成立しない

- 判断: **対応する** (観点 1 の対応で同時に解消する)
- 根拠: 同上。
- 対応内容: 期待効果は弱めない。走査根に `resources` を含めることで主張を成立させる。

## [Warning] 観点 5 — 負の対照の検体は構文として成立する完全な PHP 断片にすべき

- 判断: **対応する**
- 根拠: 妥当。`function echo(): void {}` を単体で置くと関数名としての `echo` は
  PHP の予約語規則上そもそも書けず (半予約語が使えるのはクラスメンバのみ)、
  検体そのものが実在しない書き方になる。実在しない書き方を検体にすると
  「その規則が現実の誤検出を防いでいる」ことの証明にならない。
- 対応内容: 検体はすべてクラス / 列挙 / 呼び出しの文脈を含む完全な断片にする
  (`class Foo { public function echo(): void {} }` / `enum E: string { case Echo = 'e'; }` /
  `Foo::goto();` / `f(global: 2);`)。詳細設計に全検体を列挙する。

## [Suggestion] 観点 7 — 走査結果は readonly の値オブジェクトで返す

- 判断: **対応する**
- 根拠: 既存の走査基盤がすでにその形 (`Tests\Support\ReferenceSite` /
  `Tests\Support\ReferenceScanResult`)。作法を揃えるほうが腐りにくい。
- 対応内容: `ForbiddenStatementSite`(readonly class) を返す設計にする。
