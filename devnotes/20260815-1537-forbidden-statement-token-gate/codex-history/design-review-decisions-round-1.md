# 対応マトリクス: design-review Round 1

## [Warning] S2 — `T_FUNCTION` 直後を無条件に読み飛ばすと取り逃がす

- 判断: **対応する** (指摘の例そのものは成立しないが、規則を狭める方向は正しい)
- 根拠: 指摘の検体 `$fn = function echo() {};` は PHP の文法として成立しない
  (`echo` は予約語であり、半予約語として使えるのはクラス / 列挙のメンバ名だけ)。
  そのため「取り逃がす」対象は**実行できないファイル**であり、実害は無い。
  ただし「字句走査は構文妥当性を保証しない」という指摘そのものは正しく、
  規則を狭めるコストは 1 行なので狭めるほうがよい。
- 対応内容: 読み飛ばし規則を「直前だけ」から「**直前と直後の組**」へ狭める。
  実測 (HEAD の PHP) に基づき次の形に限定する。

  | 直前の有意トークン | 直後の有意トークンの条件 | 根拠となる実在の書き方 |
  |---|---|---|
  | `T_FUNCTION` | `(` | `class A { public function echo(): void {} }` |
  | `T_CONST` | `=` | `class A { const echo = 1; }` |
  | `T_CASE` | `=` / `;` / `:` | `enum E: string { case Echo = 'e'; }` / `enum E { case Echo; }` / `switch ($x) { case ECHO: }` |
  | `T_DOUBLE_COLON` | (条件なし) | `Foo::goto();` / `Foo::echo` / `Foo::echo(...)` / トレイトの別名指定 |
  | `T_ATTRIBUTE` (`#[`) | (条件なし) | `#[Echo]` / `#[Echo(1)]` / `#[Echo, Other]` |

  `::` と `#[` に条件を付けないのは、直後に来られるトークンの種類が多く
  (`(` `;` `,` `)` `=` `]` `\` …)、列挙するほうがかえって穴を作るためである。
  この 2 つは「直後に名前しか置けない」ことが文法から言えるので、
  直前だけで十分に狭い。

## [Warning] S2 — `T_CONST` / `T_CASE` も名前位置と断定しすぎ

- 判断: **対応する** (上の対応に含まれる)
- 根拠 / 対応内容: 同上。加えて実測で**新しい取りこぼしの形を 1 つ発見した**ので記録する。
  `class A { const echo = 1, goto = 2; }` のように**複数宣言を読点で繋いだ 2 つ目以降**は、
  直前が `,` になるため名前位置と判定できず、**違反として報告される (誤検出)**。
  これは実在しない書き方であり、誤検出は赤として目に見える (取りこぼしと違って静かに壊れない)。
  **規則を増やして対応せず、走査器の説明文へ既知の誤検出として明記する**
  (今必要なものだけ作る)。

## [Critical] S3 — 読み飛ばしによる取りこぼしを壊すテストが無い

- 判断: **対応する**
- 根拠: 妥当な指摘。本設計の最大のリスクは誤検出ではなく取りこぼしであり、
  「読み飛ばし規則の近傍に本物の違反があっても検出できる」ことを固定していなかった。
- 対応内容: S3 に取りこぼし対照 (F1〜F6) を 6 本足す。指摘の検体のうち
  `#[Attr] echo "x";` は構文として成立しない (属性は宣言にしか付かない) ので
  `#[Attr] class Foo {} echo "x";` に置き換える。
  実測で 6 本とも「本物の違反として検出される」ことを確認済み
  (いずれも直前トークンが `{` / `}` / `:` / `;` になり読み飛ばし規則に一致しない)。

## [Warning] S3 — 「検体を `php -l` で確認」だけでは再現性が無い

- 判断: **対応する** (ただし検査の自動化はしない)
- 根拠: 再現性の指摘は妥当。一方でテスト内から `php -l` を 25 検体分起動するのは
  本題 (走査器の検出力) と関係ないコストであり、今必要なものではない。
- 対応内容: テストファイルの説明文へ「**全検体は構文として成立する PHP である**。
  半予約語をメンバ名に使えるのはクラス / 列挙の中だけなので、文脈を切り落とした断片を
  検体にしない」と明記し、実装手順に `php -l` の確認を残す。

## [Critical] S5 — G10 の記述が exact fit と矛盾している

- 判断: **対応する**
- 根拠: 表の検証欄は `count() === CAP` と書いていたが、名前と失敗の意味の欄が
  「上限を超えない」になっており読み手が `<=` と解釈しうる。指摘のとおり。
- 対応内容: G10 の名前・検証・失敗の意味をすべて「**登録件数が `CAP` と完全一致**
  (増えても減っても赤)」に統一する。

## [Warning] S5 — 例外ファイルを丸ごと除外する実装になると穴になる

- 判断: **対応する**
- 根拠: 指摘のとおり。設計の G8 は語彙ごとの完全一致を書いていたが、
  G1 の側に「例外ファイルも全語彙を走査する」と明記していなかった。
  実装者が「登録済みファイルは skip」と読む余地がある。
- 対応内容: G1 の仕様として次を明記する。
  (a) 例外に登録されたファイルも**全語彙を走査する** (skip しない)
  (b) 差し引けるのは目録に登録された `(パス, 語彙)` の組だけで、
      **登録の無い語彙は 1 件残らず違反になる**
  (c) 実測件数が登録件数と一致しない `(パス, 語彙)` は G8 が落とす。
      G1 は G8 が緑であることを前提に差し引く

## [Warning] S5 — 床値の失敗メッセージ

- 判断: **対応する**
- 根拠: 妥当。床値割れの原因が「分類漏れで除外が増えた」のか
  「単にファイルが減った」のか、メッセージから判別できるべき。
- 対応内容: G2 の失敗メッセージに「追跡 PHP の総数 / 除外された数 / 走査した数 /
  置き場所ごとの内訳」を出す。

## [Suggestion] S1 / S4 / S6 — 肯定的評価

- 判断: 対応不要。ただし S6 の「件数は完全一致」という記述は
  G10 の修正 (exact fit の統一) と整合する。
