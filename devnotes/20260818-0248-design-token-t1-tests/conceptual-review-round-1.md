全体判定: **CHANGES_REQUESTED**

## 1. 使命との整合性

[Warning] 状態色・文字サイズ・角丸が実際の CSS へ届くことを守る狙いは、PWA 撮影時の「迷わず読める」体験を支えるため、使命に整合しています。ただし現案の `tokens.test.ts` は `tokens.css` を密閉入力としてコンパイルするため、`app.css` からの実際の取り込みが壊れても、生成 CSS 検査自体は通り得ます。「最後の一区間を閉じる」という期待効果は現状では強すぎます。

修正提案: 実際の `app.css` を入力にしたコンパイル検査を少なくとも一つ持ち、`tokens.css` の import 削除・順序変更で生成 CSS 側の検査も失敗することを確認してください。密閉入力は utility 出力を安定して検査する補助用途に限定します。

[Suggestion] 「スマホでの可読性」をより直接的に使命へ接続するなら、現行のコントラスト検査と本検査が守る範囲（値の可読性／値が画面へ届くこと）を文書で明確に分けるとよいです。

## 2. 禁止事項違反

[Suggestion] 設計上、禁止事項への明白な抵触はありません。依存追加なし、トークン値の変更なし、JSON 直書きや LLM 経路にも無関係です。

[Warning] AGENTS.md のテストファースト原則に対し、「失敗をどう実証するか」が実装方針に明記されていません。

修正提案: 各新規ゲートについて、先に確認する red ケースを設計へ追加してください。例: `app.css` の import 削除、`@theme` の破損、ramp の `font-family` 不一致、必須文書アンカー削除。

## 3. 実現可能性

[Critical] 「静的 fixture を持たず、入力を組み立てる」案は、実アプリの `app.css` を検証対象から外すなら、t1 と同じ不変条件を満たしません。`source(none)` は出力を密閉する手段として合理的ですが、そこで `tokens.css` を直接 import すれば、アプリの import 経路は通りません。先頭二行の文字列検査だけでは「Tailwind を通って実際に出力される」ことを保証できません。

修正提案: 次の二層に分離してください。

- 実 `app.css` をコンパイルし、トークン変数と代表 utility が出力されることを確認する。
- `source(none)` を用いる密閉入力では、実 `tokens.css` を import し、全トークンから導出した utility の出力を安定して検査する。

これなら fixture を追加せずに、実 import 経路と密閉された全件検査を両立できます。

[Warning] PostCSS AST を使う選択は Tailwind v4 のネスト出力への耐性があり妥当です。ただし AST の `Rule`、`AtRule`、宣言探索には nullability と親子関係の絞り込みが必要で、雑な型アサーションは TypeScript strict を損ねます。

修正提案: PostCSS の公開型を使い、探索ヘルパーは `Rule | AtRule` の分岐を明示してください。コンパイル失敗は `beforeAll` で握り潰さず、テスト失敗としてそのまま伝播させます。

## 4. 期待効果の妥当性

[Warning] `canonical-source-parity.test.ts` と新設 `tokens.test.ts` の重複は実質ゼロではありません。両方とも DESIGN.md とトークン定義の値整合を扱います。ただし責務は異なります。

- parity: DESIGN.md と `tokens.css` の静的な写像が正しいこと。
- tokens: Tailwind/PostCSS がその定義を受け取り、変数・utility として出力すること。

この二段階は有効であり、既存側を縮める必要はありません。むしろ parity を削ると、生成物がたまたま存在しても正本との値対応が壊れた場合を見落とします。

修正提案: 設計文の「重複がない」は「同じ失敗原因を検出しない」に改め、各テストの代表的な red ケースを表で固定してください。

[Warning] 「全色トークン」の母集団を `inventory.ts` から導出するなら、inventory が `tokens.css` にのみ存在する派生トークンを取りこぼす可能性があります。`--color-primary-soft` を存在確認だけにする例外もあり、全件検査という説明とずれます。

修正提案: DESIGN.md 正本由来、CSS 固有の派生トークン、PENDING を明示的に分類し、未分類の CSS トークンを失敗させるか、理由付き例外として inventory に登録してください。

## 5. リスク

[Warning] `spacing` を PENDING として可視化すること自体は妥当ですが、PENDING が無期限の逃げ道になると既定拒否の意味が薄れます。

修正提案: PENDING に「未実装である理由」「解消条件」「追跡先」を必須にしてください。少なくとも、同じ節を実装済み扱いへ変更するには対応テストが必要、という契約を inventory の型で表現すべきです。

[Warning] 文書の必須フレーズ検査は、文言を残すだけで実態を失わせる形骸化リスクが高いです。特に「片方だけ更新する PR は merge しない」のような運用規範は、文字列の存在では守れません。

修正提案: 必須フレーズ検査は、次の条件を満たすものだけに絞ってください。

- 消失が実際に契約消失を意味する、安定した見出し・用語・構造である。
- 対応する機械ゲートまたは具体的な参照先が存在する。
- 文言の自由な改善を妨げないよう、完全一致文ではなく節見出し・構造化された参照・必須リンクを検査する。

表中の canonical source パス実在検査は、文書と実体の乖離を検出するため価値があります。一方、運用原則の単純な文言存在検査は、上記条件を満たせないなら導入しない方がよいです。

## 6. スコープの適切さ

[Warning] spacing の値是正や WCAG 拡張、実ビルド検査を外した判断は適切です。ただし `app.css` 経由のコンパイル検査は「pnpm build を通す」拡張ではなく、今回掲げる import 経路保証に必要な最小範囲です。これをスコープ外扱いにしてはいけません。

修正提案: 実 `app.css` の PostCSS コンパイルだけを本バッチへ含め、Vite/本番アセット全体の build 検査は引き続きスコープ外と明記してください。

[Suggestion] D27 は登録してよい差分です。ただし「あえて正典に従わない」ことを値の重複回避だけで正当化せず、上記二層テストにより t1 の検出能力を保持すること、正典実装が依存する fixture の目的を別手段で満たすことまで記載してください。そこまで満たせば「同一不変条件・別実装」は正当です。満たせないなら正典へ揃えるべきです。

## 7. 型安全性

[Suggestion] TypeScript strict で実装可能です。`design-md.ts` の戻り値、inventory の判別可能 union、PostCSS AST ノードの型を明示すれば、`any` や非 null アサーションは不要です。

[Warning] DESIGN.md から期待値を導出する共有パーサは、parity と tokens の共通障害点になります。パーサが誤っていれば両テストが同じ誤期待値で通る可能性があります。

修正提案: パーサ自体の既存テストがなければ、代表的な frontmatter を対象にした小さな unit test を追加してください。これは literal の値表を復活させることではなく、正本を読む境界の型・構文契約を独立に検証するものです。
