# 全体判定: CHANGES_REQUESTED

狙いと二層構成は妥当ですが、PostCSS AST の走査範囲が広すぎるため、意図しないスコープの宣言でも検査を通過します。また、R2 の失敗予測と文書同期検査の「双方向」という説明に事実誤認があります。現状では D27 の保証表現も実装より強すぎます。

## 施策 1: APPROVE

`designFrontmatterSections()` は、最上位キーだけを対象にする目的に合っています。重複キーがあれば、配列と `Record` の集合比較で件数差になり検出されます。

[Suggestion] 「書式変更時は集合一致が赤になる」という説明は概ね正しいですが、正規表現が別の最上位らしい文字列を拾う誤解析までは防ぎません。「抽出結果が変わる多くのケースを検出する」程度に表現を弱めると正確です。

## 施策 2: REQUEST_CHANGES

[Warning] `COMPILED_VALUE_EXEMPT_TOKENS` と `DERIVED_COLOR_TOKENS` の集合関係が固定されていません。将来派生色を追加した際、値検査にも免除一覧にも入らないまま、C の参照検査だけで通過します。

修正案: 次のいずれかを集合一致で固定してください。

- 全派生色を値免除する契約なら、`Object.keys(COMPILED_VALUE_EXEMPT_TOKENS)` と `DERIVED_COLOR_TOKENS` を集合一致させる。

[Warning] `rounded` と `typography` を `checked` と宣言していますが、子要素の母集団は DESIGN.md と集合一致していません。たとえば `typography.subtitle` や `rounded.xl` を DESIGN.md に追加しても、現在の固定配列に入らず見逃せます。色だけは既存テストが DESIGN.md キー集合を確認しています。

修正案:

- `designRounded().keys()` と `RADIUS_TOKENS` を集合一致させる。
- 必要なら tokens.css の `@utility text-*` 集合も確認する。

[Suggestion] `satisfies readonly string[]` は要素が文字列であることは確認しますが、トークン名の綴り自体をコンパイル時には検証しません。その説明は削除するのが正確です。

## 施策 3: REQUEST_CHANGES

[Critical] `cssVariables()` がセレクタ、レイヤー、メディア条件を問わず全宣言を集め、同名変数を後勝ちで上書きしています。このため、次のような本来の破綻を通します。

- `@theme` 外の任意の `.foo { --color-primary: ... }`
- `@media print` 内だけの宣言
- 正しいテーマ宣言と矛盾する後続の局所宣言
- 同名変数の複数宣言による競合

つまり A は「`@theme` 由来」を保証していません。

修正案: sealed 出力では、Tailwind のテーマ出力スコープ、例えば `@layer theme` 配下の `:root, :host` に相当する規則に限定し、直接の子である宣言だけを収集してください。対象変数が複数回あれば、同値重複を許すのか、競合として落とすのかも明示してください。小さな PostCSS fixture を使い、局所セレクタ、`@media`、競合する重複宣言が採用されないことをヘルパ自身のテストで固定するべきです。

[Critical] `declarationsOf()` も、同一セレクタの全規則と全子孫宣言を一つの `Map` に混ぜています。特に hover 検査は、外側の `.hover\:bg-*` の下に背景色があればよく、宣言が `&:focus` や `@media print` にあっても通ります。「hover 時の背景色」を保証していません。

修正案:

- 通常 utility は、該当規則の直接宣言だけを見る。
- hover は外側規則から `&:hover` の入れ子を明示的に辿り、その配下の宣言を見る。
- 同一セレクタが複数回現れた場合は、出現ごとの宣言と祖先コンテキストを保持し、競合を検出する。
- `@media (hover: hover)` 自体を契約にしないなら省略を許しても構いませんが、少なくとも `&:hover` は確認する。

[Critical] R2 の割り当てが誤っています。提示されたヘルパと実測結果から見込まれる反応は次のとおりです。

- A 色・radius・font: raw `:root` 宣言を `cssVariables()` が拾うため、基本的に緑
- B: `@utility` は残るため緑
- C: カスタム色 utility が生成されず赤
- D: hover 色 utility が生成されず赤
- E: Tailwind 既定テーマも `.rounded-* { border-radius: var(--radius-*) }` を生成するため緑
- F の変数アンカー: raw `:root` を拾うため緑
- F の `.bg-primary`: 生成されず赤
- G: 変更していないので緑

特に「E は `var(--radius-*)` でなくなる」は、前提として示された生成結果とも矛盾します。

修正案: R2 を上記に直してください。さらに A をテーマ出力スコープ限定に直すなら、その修正後は A も赤になる、と分けて記録してください。

[Warning] B の「4プロパティを持つ」は、実際には必要プロパティの存在だけを見ています。余分なプロパティや、DESIGN.md に `letterSpacing` がない ramp へ勝手に追加された `letter-spacing` は検出しません。

修正案: 必要なら宣言キーを集合一致させ、`letterSpacing` がない場合は `letter-spacing` がないことも確認してください。許容するならテスト名を「必要なプロパティが一致する」に変更してください。

[Warning] font-family は先頭 family しか比較していません。したがって「文字組が同じ値で現れる」「font-family が一致する」という保証は強すぎます。

修正案: DESIGN.md が先頭 family だけを正本にするなら、テスト名と D27 を「先頭 family」に限定してください。フォールバック列も正本なら、正規化した全リストを比較してください。

[Warning] G の行ベースコメント除去は複数行コメントを正しく解析しません。コメント本文が `*` で始まらない場合や、`/* ... */ @import ...` のような行で誤判定します。

修正案: PostCSS AST のトップレベル `@import` を順に検査するか、少なくともブロックコメント状態を扱う専用処理にしてください。

## 実装順序について

[Warning] 現在の手順では、施策3〜5を実装する前に「その assertion が赤になる」ことは確認できません。また、tokens.css の望ましい動作は既に存在するため、新規テストは通常の意味では最初から Green になる可能性があります。

修正案: これは通常の Red-Green ではなく、既存挙動への mutation testing／感度確認として明記してください。順序は次が正確です。

1. テストを追加する。
2. 現行状態での基準結果を確認する。
3. R1〜R6 の故障を一件ずつ注入し、狙った assertion が失敗することを確認する。
4. 必ず故障を戻し、Green を確認する。
5. 文書など新規契約が未実装の部分は、通常どおり Red を確認してから追加する。

R1〜R6 の記録には「想定した assertion」と「実際に失敗した assertion」を分けて残すべきです。特にR2は修正後の実測結果を正本にしてください。
