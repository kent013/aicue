## [Warning] 「検出力を落とさない」は強すぎる (禁止事項 1 との関係)
- 判断: 対応する
- 根拠: 指摘のとおり。CI 強制から人手手順への移行は、検出の頻度も強制力も確実に下げる。
  AGENTS.md が繰り返し戒める「保証範囲を誇張しない」に照らしても、下がることを書くのが正しい。
- 対応内容: AG-162 不採用の節から「検出力は落とさずに」を削り、
  「強制力は確かに下がる (正直に書く)」の段落を新設した。失うもの (毎 push の強制) と
  残るもの (文書更新時に実行できる双方向の差集合の手順) を並べて書いた。

## [Warning] 「台帳の aicue セルが implemented へ戻せる」は断定的
- 判断: 対応する
- 根拠: 台帳のセルを動かすのは実装完了・合流・push 後の報告と台帳側の判断であり、
  本作業の直接効果ではない。
- 対応内容: 期待効果を「未達として記録されている 2 条件を解消すること」までに弱めた。

## [Warning] CI から外した後の再発リスク — 完了報告に実測値を書かせよ
- 判断: 対応する
- 根拠: 指摘どおり、観測点が文書更新スキルの実行時に限られる以上、
  実行するたびに数が残る形にしておかないと「回したつもり」を防げない。
- 対応内容: 受け皿の説明に、完了報告へ書く実測値 4 つ
  (追跡下の件数 / 表のデータ行数 / 未記載件数 / 残骸件数) を明記した。
  詳細設計ではスキル本文の該当箇所として書き下す。

## [Warning] 負のコントロールで実ファイルを壊して戻すのは事故りやすい
- 判断: 対応する
- 根拠: 作業ツリーを崩す手順はコミット混入の事故を起こす。実害のある指摘である。
- 対応内容: 禁止事項との関係の節に、負のコントロールは作業用ディレクトリへ写した複製の上でのみ行い、
  リポジトリの作業ツリーには触れないと明記した。詳細設計のテストファースト計画にも同じ制約を書く。

## [Suggestion] 使命への貢献を「間接」と書いた点 / 実現可能性 / スコープ / 型安全性
- 判断: 対応不要 (現状維持)
- 根拠: いずれも現行の記述を肯定する内容で、変更の必要が無い。
