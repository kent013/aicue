## 使命 (North Star)

<!-- app-codex-review スキルはこのセクションをレビュー使命として参照する。 -->

**AI-CUE** は、現場に既にある**作業手順書(SOP)を起点に**、AI が撮るべきカットを設計した**動画シナリオ**を生成し、そのシナリオを**スマホ(PWA)でナビゲーション撮影**することで、専門知識ゼロの現場作業者でも**標準化されたマニュアル動画**を作れるようにする。

- 「思考ゼロ・編集ゼロ」— 台本作成・撮影判断・編集の 3 ハードルを AI とナビ撮影で肩代わりする。
- 競合(OJT を撮って形式化する tebiki)と異なり、**標準作業を起点に AI が教材設計し撮影を指示する**（撮影者・教える人のスキルに品質を依存させない）。
- 熟練者の暗黙知を動画マニュアルという形式知へ変換する装置（SECI）。

> 詳細な設計は本リポジトリの `doc/`（01〜10）に置く。ドメインをテンプレート構造へどうマップしたかは `doc/08`〜`doc/10`（特に `doc/10 §10.8` に設計レビュー反映済み）。
> **v1 スコープ**: 字幕のみ(TTS 後回し) / 撮影は PWA(同一オリジン・セッション認証) / 動画合成は自前 ffmpeg / 単一 Default Project。


## 禁止事項

1. テストなしの実装完了報告(不変条件は対応する Architecture/Feature テストへの登録まで含めて「実装済み」)
2. PHPStan エラーの widen(型を緩めて黙らせる)・baseline 化
3. dev DB への破壊操作(`migrate:fresh` 等)をエージェント判断で実行すること
4. `response()->json()` の直書き(DTO / JsonResource / Inertia を使う。仕様固定 endpoint のみ例外)
5. LLM 呼び出しの Prism 直呼び(`app/Prompts/` の factory → 窓口 (`PromptDefense`) →
   実行単位 (`GuardedPrompt`) の**1 本道のみ**。`PromptGuardrailTest` が
   app/ routes/ database/ config/ bootstrap/ の 5 走査根で検出する)。
   **実行経路を持つ prompt factory は `LlmCallContextData` を必須引数で受け、
   `PromptDefense::load()` へ渡して帰属 (organization / subject) を付ける** — 付け忘れは
   PHPStan level 10 が落とす。帰属の対象を持たない見本 (`ExampleSummaryPrompt`) だけが
   `PromptDefense::loadUnattributed()` を使え、窓口 gate が**この 1 件を名指しで pin** する。
   併せて `PromptUntrustedInputContractTest` の inventory へ**帰属キーを空配列で exempt 登録**する
   (deny-by-default なので exempt にする操作がレビューで必ず見える)。
   欠けると `llm_call_logs.metadata_missing` になり組織別・対象別の費用が出せない
6. prompt 文字列のコード直書き(`resources/prompts/*.yaml` に置く)
7. 操作系 POST の応答での `redirect()->intended()`(ログイン直後フロー専用。
   招待送信等は `back()->with(...)` で完結させる)
8. 必須条件未充足を理由にボタンを disabled にする UI(押下時にエラー表示する。DESIGN.md)
9. Artifact の使用(Artifact ツールでの成果物公開を行わない。成果物はリポジトリ内のファイルとして出力する)

データに真摯に向き合え。成果だけでなく、多様性の変化、構造の揺らぎ、想定外のパターン — 全てが判断材料になる。数値を見て即座に閾値を弄るな。何が起きているのかを理解し、なぜそうなったのかを考え、どの方向に進むべきかを判断してから手を動かせ。

先人の知恵を探せ。自分たちだけで登る必要はない。乗るべき巨人の肩があるなら乗れ。

機能の名前に立ち返れ。名前はその機能が果たすべき役割を示している。現在の設計がその役割を果たしているか、常に問え。

仕組みが機能していない段階で値を弄るな。閾値チューニングやフィールド追加は、設計の方向性が正しいと確認できてから行え。方向性が間違っているなら、値をいくら調整しても意味はない。設計そのものを見直せ。成果が出なければ早期に見切り、次の仮説へ進め。

## 背景・課題

`scripts/` へスクリプトを 1 本足したら `scripts/README.md` の表に 1 行足す、という運用規約がある
(AGENTS.md §設計・TODO・devnotes の運用)。本リポジトリはこの規約を **CI で落ちる Architecture テスト**
`tests/Architecture/ScriptsReadmeInventoryTest.php` で機械強制している。

家系の機能台帳 `scripts-readme-ledger` では、この規約の完成形は**機械検査を持たないこと**と決まっている。

- **AG-076 / AG-133**: 一覧と実態の整合確認は文書更新スキルの手順の中で人手で行う形をもって完成とする。
  破ると CI が落ちる機械検査は**意図的に 0 本**にする。
- **AG-076b**: 上記を選び直したうえで、本リポジトリの独自検査
  `tests/Architecture/ScriptsReadmeInventoryTest.php` の**撤去**を求めた。
- **AG-162 (2026-08-13)**: 「落とさない検査」(違反があっても正常終了し、一覧を報告するだけのもの) は
  **許す**。ただし義務ではない。台帳の実測では家系 6 リポジトリのいずれも未実装である。
- **AG-192 (2026-08-16、裁定)**: AG-076b を**維持し執行する**。裁定の見直しではなく配布の失敗の是正として扱い、
  本リポジトリの CI を落とす検査は撤去する。整合確認は家系統一の形 (文書更新スキル内の手順) へ一本化し、
  希望するなら AG-162 の落とさない検査への置き換えは可。撤去完了の報告をもって台帳のセルを implemented へ戻す。

裁定と実装が矛盾したまま放置された結果、撤去対象への投資が積み上がっている
(本リポジトリでは aicue:T176 が撤去対象の検査を拡張し、aicue:T208 がこの検査を前提にした
テストファーストの手順を実行している)。この矛盾を解消するのが本作業である。

### AG-162 の「落とさない検査」を採るか — 採らない

**採用しない。** 理由は 3 つある。

1. **思考原則 2 (今必要なものだけ作る)**。AG-162 は許しているだけで義務ではなく、
   家系 6 リポジトリのいずれも実装していない。ここで最初の 1 本を作ると、
   本リポジトリがまた家系で唯一の形になる (今回の是正はまさにその状態を解消するためのものである)。
2. **正本が 2 つになる**。突合の規則を「スキルの手順」と「報告だけする実行物」の 2 か所に持つことになり、
   必ず食い違う (AGENTS.md が繰り返し戒めている二重管理)。しかも報告だけの検査は
   `scripts/` 配下に置くことになるので、**その実行物自身が台帳の 1 行を要求する**。
3. **読まれない報告は偽の安心になる**。CI ログの中で終了コード 0 の出力は誰も読まない。
   一方でスキルの段に照合コマンドを直接書けば、文書更新を回すたびに人 (エージェント) が
   出力を読む場所で実行される。検出力は落とさずに、裁定の求める形に収まる。

**代わりに検出力を落とさないための担保**: スキルの段には照合の**実行可能なコマンド列**をそのまま書く
(手順の散文だけにしない)。これはテンプレートが採っている形でもある。

## 禁止事項との関係 (テストなしの実装完了報告)

AGENTS.md 禁止事項 1 は「不変条件は対応する Architecture/Feature テストへの登録まで含めて実装済みとする」
と定める。本作業はその**逆向き**に見えるので、矛盾しない理由を明記しておく。

- 本作業は「テストを書くのをさぼる」ものではなく、**この不変条件を機械強制しないという上位の決定
  (オーナー裁定 AG-076b、その執行を命じた AG-192) の執行**である。禁止事項 1 が守ろうとしているのは
  「不変条件の担い手を宙に浮かせない」ことであり、本作業は担い手を
  **文書更新スキルの手順**へ明示的に移す (受け皿を同じ変更で作る)。担い手が消える瞬間は無い。
- 撤去は**新しい不変条件を 1 つも作らない**。したがって新規に登録すべきテストも無い。
  代わりに、撤去が既存の検査群を壊していないことは `composer test` 全体の green で示し、
  受け皿が実際に効くことは手順を 1 回実走した実測 (未記載 0 件 / 残骸 0 件、および
  意図的に崩したときに検出されること) で示す。
- この判断は本リポジトリの一存ではなく家系の裁定であることを、
  撤去箇所の周辺 (スキルの段と `scripts/README.md`) に逐語で残す。
  残さないと、次に来た人が「検査が無いのは書き忘れ」と読んで作り直す。
