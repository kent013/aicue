**指摘**
- [Critical] **B / 使命との整合性・スコープ**: 導入/総括を `step` として永続化し、v1 では編集画面や撮影ナビ上も「手順1/手順N」と見せる許容は弱いです。導入/総括は手順そのものではなく、`doc/10 §10.1/§10.4` の `step/point` 限定を守るための内部表現としては理解できますが、ユーザー体験まで「手順」と誤認させるのは North Star の「思考ゼロ」に逆行します。SOP 上の手順番号と撮影ナビの番号がズレると、現場作業者に追加判断を要求します。  
  修正提案: DB スキーマは据え置きのままでも、少なくとも表示上は番号付け対象から導入/総括を外すか、汎用ラベルを `手順` ではなく `カット` に寄せる最小 UI 調整を入れるべきです。そこまでやらないなら、v1 の期待効果を「教材構造の補強」に限定し、「思考ゼロの撮影ナビ改善」までは主張しない方が正確です。

- [Critical] **D / 期待効果の妥当性**: 提案中の総括文面は、`doc/03 §3.5` の「要点・安全ポイント再掲」を満たしていません。「振り返りましょう」は締めの定型句であって、再掲ではありません。導入側も、`doc/06 §6.3` の「設備と立ち位置」までを満たすには不足です。現状案のままでは、設計文書が約束している教材価値を過大に見積もっています。  
  修正提案: v1 要件を明示的に下げて「導入=作業名提示と俯瞰」「総括=終端の締めカット」に修正文書化するか、非 LLM の範囲で既存 step/point から 1-2 個の要点を決定的に抜き出して字幕へ載せる最低限の再掲ロジックを追加してください。

- [Warning] **C / 共有ロック規約**: 「list を materialize 前に拡張するだけなので共有ロック規約に波及しない」という主張は、**導入/総括の内容生成も `lockForUpdate()` 後の同一トランザクション内で行う**場合に限って安全です。AnalysisPipeline 側で先にタイトル補間まで済ませると、書き込み経路自体は増えなくても、ロック前に読んだタイトルをもとに最終シナリオを確定することになります。  
  修正提案: 挿入の意思決定は AnalysisPipeline に置いてもよいですが、実際の文面組み立ては locked manual を受け取れる位置で行ってください。少なくとも設計書に「タイトル補間は `materializeIntoLockedManual()` 呼び出し直前の locked phase で行う」と明記すべきです。

- [Warning] **実現可能性・回帰リスク**: 再解析時の重複、手動編集後の再 materialize、削除後の round-trip の振る舞いが未定義です。ここが曖昧だと「毎回 2 カットだけ存在する」という利用者期待が崩れます。  
  修正提案: Feature/Architecture テストで、初回生成・再生成・手動 save 後再生成の 3 ケースを固定し、「先頭1件/末尾1件のみ」「順序固定」「重複なし」を検証してください。

- [Warning] **型安全性**: この改善は API 形状を変えないので DTO/JsonResource 方針とは整合しますが、挿入ロジックを生配列で足すと `GeneratedScenarioData` の外に第2の非型付けシナリオ生成経路が生まれます。PHPStan level 10 的に避けたい構造です。  
  修正提案: 追加カットは既存 enum と既存のシナリオ用 DTO/値オブジェクトを再利用する typed builder で生成し、`array<string,mixed>` の組み立てを避けてください。

- [Suggestion] **A / 選択の妥当性**: サーバ側決定的挿入の判断自体は妥当です。プロンプト/出力スキーマ/Canned response signature を維持しつつ、テストで「必ず前後に入る」を保証できるため、v1 としては最も筋が良いです。

- [Suggestion] **禁止事項整合**: 現案は、禁止事項 4/5/6/7 には概ね抵触していません。むしろ重要なのは禁止事項 1 で、仕様差分をドキュメントだけでなくテストの不変条件に上げることです。`ScenarioWritePathInventoryTest` への追加は不要でも、生成結果の構造保証は別テストで必須です。

- [Suggestion] **スコープ判断**: 独立 `CutType` を見送る判断は、v1 の「今必要なものだけ作る」と整合します。ただしこれは「永続モデルは最小、表示は少しだけ救う」が前提です。表示まで完全に `step` 扱いに寄せると、節約した複雑性を UX 負債として前倒しで払う形になります。

**観点別まとめ**
- 1. 使命との整合性: 一部不十分。内部実装は妥当だが、表示上 `step` と見せるのは使命に逆風です。
- 2. 禁止事項違反: 現時点では明確な違反なし。テスト未定義だけが懸念です。
- 3. 実現可能性: 高いです。スキーマ非破壊で実装可能です。
- 4. 期待効果: 過大評価があります。特に「総括」は現案だと再掲になっていません。
- 5. リスク: UX 上の手順誤認、再解析重複、ロック前タイトル参照の一貫性不足が主要リスクです。
- 6. スコープ: 独立 CutType を外す判断は妥当ですが、表示面の最小救済は必要です。
- 7. 型安全性: typed builder 前提なら問題ありません。生配列追加は避けるべきです。
