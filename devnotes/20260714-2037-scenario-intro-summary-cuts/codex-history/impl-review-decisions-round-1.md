## [Critical] UpdateScenarioRequest: 手動保存 API で bookend の存在/位置/一意性を検証していない
- 判断: **反論する**（コード変更なし）
- 根拠:
  1. これは詳細設計レビュー (同一 Codex, detailed-review Round 3) で **同一指摘が既に提起され、Round 4 で明示 APPROVED された論点**の蒸し返し。設計フェーズの結論は「v1 は独立 CutType / bookend 識別用の永続属性を持たない (doc/10 §10.1 の step/point 限定)。したがって保存経路は定型2件を判別できず、内訳 (通常100/定型2) を強制できない。手動保存が保証するのは top-level 総数 ≤ 102 のみ」。実装はこの承認済み設計に忠実。
  2. Codex 提案の「保存時にサーバ側で bookend を決定的に再構成」は**有害**。既存の先頭/末尾 cut は「前回の導入/総括」だが通常 step と区別不能なため、保存のたびに新しい導入/総括を再注入すると `導入, 旧導入, ...steps..., 旧総括, 総括` と bookend が毎回増殖する。「後方互換の並走を残さない」「不必要な複雑化」に反し、上限も破る。
  3. 手動保存経路はユーザーが著者となる編集。North Star の「思考ゼロ・編集ゼロ」は **AI 生成ドラフト**に対する型付与であり、ユーザー編集の禁止ではない。生成時 (AnalysisPipeline::finalize) に決定的に付与するのが本機能の責務で、実装はそこで正しく担保している。
  4. 「先頭/末尾が bookend か」を厳密検証するには bookend 識別用の永続属性が必要で、それは v1 スコープ外 (設計 Round 3/4 で明文化)。
- 対応内容: Round 2 で上記を提示し、設計フェーズ承認済みの scope 判断であることを説明して再評価を依頼する。コードは変更しない。
