# 概念設計: パスキー境界ハードニング 4 施策の未達分の完遂 (aicue:T216)

## 背景・課題

機能台帳 lctl の feature `auth-passkey-hardening` (パスキー境界ハードニング。発祥は
aigenba、成文化は spirux:T1108) は、パスキー本体ではなく**その境界**を固める 4 施策を
家系 6 リポジトリで共有している。台帳の aicue セルは 2026-08-16 の領域深掘り (auth 2 周目、
観測点 aicue@bac558f) で **status: pending** と再確認され、未達が 3 点残っていることが
実読で確定している。

| 台帳の施策 | aicue の現状 (2026-08-16 台帳観測 + 本設計での実読) | 判定 |
|---|---|---|
| 1. 認証ライブラリの版を機械で固定する検査 | `tests/Architecture/PasskeyPackageContractTest.php` が固定しているのは **`laravel/passkeys` の制約と解決値の 2 本だけ**。`laravel/fortify` の版を検査する式は tests 全体に 1 つも無い (説明文に名前が出るだけ) | **未達** |
| 2. 許可する接続元の正規化と即時失敗 | 宣言側 (config/fortify.php) は前後空白の除去と小文字化だけ。既定 port の除去・末尾スラッシュの受理・port 0 の拒否・非 ASCII ホストの拒否・path / query の拒否のうち、**裁定と逆を向く点が 2 つ**残る。例外文に許可元と身元の識別子の**生値**が入る | **前進したが最終形ではない** |
| 3a. 所有者の外部キーの文字列正規化 | `app/DataTransferObjects/Auth/LoginMethodRemoval.php` が実装済み | 達成 |
| 3b. パッケージ側の削除処理への対応 | `Laravel\Passkeys\Actions\DeletePasskey` を参照する箇所が app / tests ともに **0 件** | **未達** |
| 4. 2 要素認証の許可一覧へのパスキー確認 2 経路の追加 | `RequireTwoFactorForEnforcedOrganizations` に実装済み | 達成 |

未達を放置したときに起きること (使命との関係):

- **施策 1**: `laravel/passkeys` は `laravel/fortify` の推移依存であり、パスキーの公式統合が
  入ったのは fortify 1.37 である。1.37 未満へ退行すると **`Features::passkeys()` という
  有効化点そのものが消え**、パスキー経路が無言で失われる。現在の契約検査は
  `laravel/passkeys` の版しか見ないため、この退行を検出できない。
- **施策 2**: 既定 port つきの許可元 (`https://app.example.com:443`) は現在**素通りする**。
  ブラウザが申告する origin は既定 port を含まない (`https://app.example.com`) ため、
  照合は厳密文字列比較で必ず外れ、**登録も検証も全件が無言で失敗する**。
  末尾スラッシュは逆に**拒否**しており、裁定 2026-08-04 の
  「末尾スラッシュは正規化受理で統一」に従っていない (正当な設定で本番が起動しない)。
  例外文の生値は配備ログへ設定値を焼き付ける。
- **施策 3b**: パッケージ側の削除処理は「行を消してからイベントを発火する」形で、
  **その 2 つを 1 つのトランザクションで包まない**。本アプリはたまたま
  `EnsureLoginMethodRemains` が削除経路全体をトランザクションで包んでいるため
  結果的に原子的だが、**その事実はどこにも固定されていない**。
  中間層 (middleware) の設計が変わるか、パッケージ側の前提が変わったときに、
  監査記録の欠落や「消えたのに消えていない」状態を無言で作れる。

使命との関係: 本改善は教材設計そのものではなく、**現場作業者が撮影 PWA へログインし続けられること
(認証手段の可用性と継続性)** を守る基盤である。パスキーは現場でパスワード入力を不要にする
主要導線であり、設定事故が「昨日まで使えた生体認証が通らない」形で現れる。

## 改善アイデア

未達 3 点を、既に aicue に確立している形へ載せて閉じる。**新しい仕組みは作らない**。

1. **版の固定を `laravel/fortify` へも広げる** — `laravel/passkeys` に対して既にある
   「制約の書き方を 1 種類に絞る検査」と「解決値の系列を見る検査」の**同じ規約形**で
   2 本足す。下限側の固定 (1.37 系より前へ退行させない) であり、上限を締めるためではない。
2. **正規化の責務を宣言側へ置き、検証側は「正規形でなければ落とす」に徹する** —
   受理点 (env → config) で正規形へ寄せ、検証点 (本番起動時) で正規形からの逸脱を落とす。
   両者が同じ 1 つの正規化器を参照するので、判定基準が 2 か所に割れない。
   例外文からは許可元と身元の識別子の生値を落とし、**何番目の値か**だけを示す。
3. **パッケージ側の削除処理の非原子性を固定し、アプリ側の補償を実挙動で固定する** —
   契約検査でパッケージ側の性質 (トランザクションで包んでいないこと) を固定し、
   機能テストでアプリ側の帰結 (購読側が失敗したら削除ごと巻き戻ること) を固定する。
   **性質が変わったら赤くなる**ので、版を上げたときに読み直す契機になる。

## 期待効果

- 使命への貢献: 現場作業者が使うログイン導線 (パスキー) が、設定事故と依存の入れ替わりで
  無言に壊れる経路を 3 つ塞ぐ。効果は「壊れないこと」であって新機能ではない。
- 具体的な改善見込み:
  - 既定 port つきの許可元を書いた本番配備が、**手続き全件失敗**ではなく正しく動くようになる
    (正規化して受理する)。
  - 末尾スラッシュ付きの正当な設定で本番が起動しない現象が消える (裁定への整合)。
  - fortify が 1.37 未満へ退行する変更が CI で赤くなる。
  - パスキー削除の原子性についての前提が、**版を上げたときに必ず読み直される**形になる。
- 家系への還流: 台帳の aicue セルが未達としている 3 点が閉じ、report できる状態になる
  (台帳への書き込みは実装時の責務であり、本設計では行わない)。

## 実装方針（概要）

| # | 施策 | 触るもの |
|---|---|---|
| A | `laravel/fortify` の版の固定 (台帳施策 1) | 契約検査 (`tests/Architecture/PasskeyPackageContractTest.php`) と、これと食い違っている運用ドキュメントの記述 |
| B | 許可する接続元の正規化と例外文の是正 (台帳施策 2) | 宣言側 (`config/fortify.php`)、新設する正規化器、検証器 (`app/Support/PasskeyConfigValidator.php`)、対応するテスト |
| C | パッケージ側の削除処理への対応 (台帳施策 3b) | 契約検査への追加と、削除経路の原子性を実走で確かめる機能テストの新設。**削除 route が手段保持の関門を必ず通ることは既存の 2 本が固定済み** — `tests/Architecture/PasskeyRouteProtectionTest.php` が passkey route の middleware 構成を完全一致で固定し、`tests/Architecture/LoginMethodRemovalRouteTest.php` が手段保持の関門の付与を deny-by-default で強制する。本施策はそこへ「関門がトランザクション境界であること」と「パッケージ側は自前でトランザクションを持たないこと」を足す |
| D | 逸脱の登録 | `docs/template-divergence.md` への 1 件追加 (検証の置き場所が正典と違うことの記録) |

方針の要点:

- **正規化器は 1 つだけ置き、宣言側と検証側の両方がそれを参照する**。検証側は
  「与えられた値が正規形と一致するか」を見るので、正規形の定義が 2 か所に割れない。
- **正規化器が扱うのは「許可する接続元」だけである**。身元の識別子 (relying party id) は
  別概念 (scheme も port も持たない host 単独の識別子) なので、同じ器に入れない。
  身元の識別子の宣言側は現状のまま (前後空白の除去と小文字化)、検証側は既存の DNS 名検査を
  使い続ける。2 つの概念に共通する部品を作るとしても、それは接続元の**ホスト部分**に対する
  DNS 名検査までであり、「正規形へ寄せる」処理を身元の識別子へ適用しない
  (パスキーは身元の識別子に束縛されるため、この値を書き換える処理を増やすと
  **登録済みパスキーが全件使えなくなる**方向の事故を作りやすい)。
- **正規化器は純粋な静的関数に限る**。文字列を受けて文字列を返すだけで、
  サービスコンテナ解決・入出力・設定の読み出し・例外送出のいずれも行わない
  (config の評価時に呼ばれるため。この性質はテストで固定する)。
- **本番起動時 fail-fast の運用要件 (AGENTS.md) は壊さない**。検証点は今までどおり
  `ProductionEnvGuard` 経由の本番起動時ただ 1 か所であり、config の評価時に例外を投げる形
  (家系の正典側の作り) へは移さない。理由は下の「制約・前提」に書く。
- **既存の正当な設定が新たに落ちることは無い**ことを設計の前提として確かめる
  (下の「破壊的変更の有無」)。落ちるようになるなら AGENTS.md の運用要件の更新まで含める、
  という条件が本タスクにあるが、**該当しない**という判断を根拠付きで記録する。

## 制約・前提

- **検証点は本番起動時のまま動かさない**。家系の正典 (テンプレート / aigenba) は
  設定の評価時に落とす形だが、config は**すべての環境で評価される**ため、
  評価時に例外を投げると開発環境・テストレーンまで起動不能にできる。
  aicue は接続元の信頼設定 (TRUSTED_PROXIES) と受け入れホストで
  「本番起動時に落とす」形を先に確立しており、パスキーもそこへ相乗りしている
  (aicue:T166)。本設計はこの構図を維持し、**その逸脱を登録簿へ明記する** (施策 D)。
- **受理と検証の役割分担**: 裁定 2026-08-04 の「末尾スラッシュは正規化受理で統一」は
  **受理点 (env → config) で満たす**。検証点は正規形からの逸脱を落とす側に徹する
  (別経路が正規化せずに設定した値を黙って受けない)。運用者が env に書いた末尾スラッシュは
  本番でも通り、手続きも成立する = 裁定の要求は端から端まで満たす。
- **非 ASCII ホストは受理しない**。国際化ドメインの変換 (punycode 化) は行わず、
  運用者が punycode で書く前提とする (変換の実装を持つと、変換結果が正しいことを
  誰も検査できない層が増える)。
- **公開接尾辞の一覧は持たない**。`co.uk` のような値を身元の識別子に置いた設定は
  起動時には通る (既知の限界として既にテストで記録済み)。本設計でも変えない。
- 版の固定は**下限側**である。上限を締める意図は無く、fortify の minor 更新で
  検査が赤くなるのは「契約検査の前提を読み直す契機」として意図した挙動である
  (依存の脆弱性対応で版を上げるときは同じ変更で固定値も直す)。

### 破壊的変更の有無 (本タスクの条件に対する判断)

**主張の範囲を限定する**: ここで「新たに拒否されない」と言えるのは
**環境変数 → config という通常の宣言経路を通った設定**についてである。
config の値を直接差し替える経路 (テスト・将来の別の宣言経路) から正規形でない値を
入れた場合は、変更後は拒否される。これは意図した設計である —
検証点は「正規形でなければ落とす」に徹し、受理は宣言点の責務にするため。

通常の宣言経路について、新たに拒否されるようになる設定は**無い**。内訳:

| 設定の形 | 現在 | 変更後 |
|---|---|---|
| 末尾スラッシュ付き | 本番で起動しない | 正規化して受理し、正しく動く (緩和) |
| 既定 port 付き | 起動するが手続きが全件失敗する | 正規化して受理し、正しく動く (是正) |
| path / query / 利用者情報付き | 拒否 | 拒否 (変更なし) |
| 非 ASCII ホスト | 拒否 | 拒否 (変更なし。明示的なテストを足すだけ) |
| port 0 | 拒否 | 拒否 (変更なし) |

よって **AGENTS.md の運用要件 (パスキー) の意味は変わらない**。文面の更新は不要であり、
「初回デプロイ前に設定が要る破壊的変更」という既存の性質もそのまま維持する
(`PASSKEYS_USER_HANDLE_SECRET` の宣言必須は触らない)。

### 環境変数の改名 (`PASSKEYS_RELYING_PARTY_ID` → `PASSKEYS_RP_ID`) の採否

**見送る**。理由:

1. **無言で既定へ落ちる改名である**。改名しても旧名を宣言している環境では新名が未宣言に
   なるだけで、身元の識別子は `APP_URL` の host へ静かに戻る。身元の識別子が変わると
   **登録済みパスキーが全件使えなくなる**。安全にやるなら「旧名が存在したら起動時に落とす」
   検査まで要るが、それは利得の無い機構を 1 つ増やすことになる (思考原則 2)。
2. **利得が短さしかない**。現在の名前は config のキー名 (`relying_party_id`) と
   パッケージ側の用語 (relying party id) の両方に一致しており、読み手が対応を取れる。
3. **家系の他リポジトリと足並みが崩れる**。境界内の割れとしては、揃えるべき方向は
   むしろ現行名である。

再検討の条件: 家系の裁定として改名が決まったとき。そのときは旧名の残置を起動時に
落とす検査を同じ変更に含める。

## スコープ外

- パスキー本体 (登録・検証・ログインの経路) の変更。台帳でも `auth-passkey` 側の関心である。
- 本番で非暗号化接続の許可元を落とす強化 (家系の独自強化 1 件目)。**既に等価な検査が
  aicue にある** — 本番の許可元は `https://` で始まる形しか受理しない。二重に持たない。
- 2 要素認証との関係 (台帳施策 4) と所有者照合 (施策 3a)。いずれも実装済み。
- パッケージ側の登録処理の非原子性の**是正**。性質の固定 (施策 C) までは行うが、
  登録経路にトランザクションを被せる設計は本タスクに含めない
  (削除経路と違い手段保持の関門が無く、被せ方の設計が別途要るため)。
- 公開接尾辞の一覧を用いた身元識別子の検査。
- 台帳への書き込み (実装完了後の報告は実装タスクの責務)。
