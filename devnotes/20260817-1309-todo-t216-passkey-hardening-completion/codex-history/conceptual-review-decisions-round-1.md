# 対応マトリクス: conceptual-review Round 1

## [Critical] 観点 5: 接続元と身元の識別子を同じ正規化器へ寄せる危険

- 判断: 対応する (指摘のとおり概念設計の記述が曖昧だった)
- 根拠: 身元の識別子はパスキーが束縛される値であり、書き換える処理を増やすと
  登録済みパスキーの全件失効へ直結する。接続元 (scheme + host + port) とは別概念である。
- 対応内容: 「実装方針」に方針を明記した。正規化器が扱うのは**接続元だけ**、
  身元の識別子の宣言側は現状維持 (前後空白の除去と小文字化)、検証側は既存の DNS 名検査。
  共通化するとしても接続元のホスト部分に対する DNS 名検査までに留め、
  「正規形へ寄せる」処理を身元の識別子へ適用しない。

## [Warning] 観点 2: config から参照する正規化器が副作用を持つ危険

- 判断: 対応する
- 根拠: config はすべての環境で評価され、設定キャッシュの生成時にも走る。
- 対応内容: 「正規化器は純粋な静的関数に限る (コンテナ解決・入出力・設定読み出し・例外送出を
  行わない)」を方針へ明記し、その性質をテストで固定すると宣言した。

## [Warning] 観点 3: 削除経路の保護が機能テストだけでは弱い

- 判断: 一部反論・一部対応
- 根拠: 「削除 route が手段保持の関門を通ること」は**既に 2 本の検査が固定している** —
  `PasskeyRouteProtectionTest` が passkey route の middleware 構成を完全一致で固定し
  (増減どちらでも赤)、`LoginMethodRemovalRouteTest` が付与を deny-by-default で強制する。
  したがって「別経路の追加や付け替えの見逃し」は既に閉じている。
  一方「関門がトランザクション境界であること」は固定されていないので、そこは足す。
- 対応内容: 施策 C の説明に既存 2 本への参照を書き、本施策が足すのは
  「関門がトランザクション境界であること」と「パッケージ側は自前でトランザクションを
  持たないこと」の 2 点であると限定した。

## [Warning] 観点 4: 「新たに拒否される設定は無い」の主張が強すぎる

- 判断: 対応する
- 根拠: config を直接差し替える経路では、変更後は正規形でない値が拒否される。
- 対応内容: 主張の範囲を「環境変数 → config という通常の宣言経路」に限定し、
  それ以外の経路では正規形のみ受けることを意図した設計だと明記した。
  表による検査の分割 (宣言経路と検証器の直叩き) は詳細設計のテスト計画で行う。

## [Warning] 観点 7: 正規化結果を値オブジェクト / 結果型にする

- 判断: 見送る
- 根拠: 正規化器は**全域関数**であり失敗の場合分けを持たない (文字列を受けて文字列を返す)。
  失敗の判定と分類は検証器 1 か所に残るので、結果型を足しても分岐は増えも減りもしない。
  型を 1 つ足す代わりに「正規形か否か」を判定する場所が 2 か所に見えるようになるほうが
  害が大きい (思考原則 2 = 今必要なものだけ作る)。
- 対応内容: 反論として次ラウンドで伝える。失敗理由の列挙は例外文の位置表示で足りる。
