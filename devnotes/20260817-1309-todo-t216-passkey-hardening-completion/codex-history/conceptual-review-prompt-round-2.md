# Round 2: Round 1 指摘への対応

## 対応マトリクス

### [Critical] 観点 5: 接続元と身元の識別子の責務分離 — 対応した

概念設計の「実装方針」に次を明記した。

- 正規化器が扱うのは**許可する接続元だけ**である。身元の識別子 (relying party id) は
  scheme も port も持たない host 単独の識別子であり、別概念として扱う。
- 身元の識別子の宣言側は現状のまま (前後空白の除去と小文字化)、検証側は既存の DNS 名検査を使う。
- 共通化するとしても接続元の**ホスト部分**に対する DNS 名検査までに留め、
  「正規形へ寄せる」処理を身元の識別子へは適用しない
  (パスキーは身元の識別子に束縛されるため、この値を書き換える処理は
  登録済みパスキーの全件失効へ直結する)。

### [Warning] 観点 2: config から呼ぶ正規化器の副作用 — 対応した

「正規化器は純粋な静的関数に限る。文字列を受けて文字列を返すだけで、サービスコンテナ解決・
入出力・設定の読み出し・例外送出のいずれも行わない」を方針に明記し、この性質をテストで
固定すると宣言した。

### [Warning] 観点 3: 削除経路の保護の固定方法 — 一部反論・一部対応

反論の根拠 (現行コードの実読):

- `tests/Architecture/PasskeyRouteProtectionTest.php` は passkey route ごとの middleware 構成を
  **目録との完全一致**で固定している (`passkey.destroy` は
  `web / auth:web / throttle:passkeys / recent-auth / ensure-login-method` の 5 本ちょうど)。
  付け替えも削除も増設も赤になる。
- `tests/Architecture/LoginMethodRemovalRouteTest.php` は手段保持の関門の付与を
  deny-by-default で強制する (付与漏れだけでなく許可一覧の外への付与も赤)。

したがって「別の削除経路の追加」「route / middleware の付け替え」は既に閉じている。
固定されていないのは (a) 関門がトランザクション境界であること、
(b) パッケージ側が自前でトランザクションを持たないこと の 2 点なので、施策 C の範囲を
この 2 点に限定した (概念設計の施策表に既存 2 本への参照を追記済み)。

「削除 action をアプリ側で明示的にトランザクション境界へ閉じ込める」案は採らない。
すでに関門がトランザクションを開いており、その内側でパッケージ側の削除が走る。
二重にトランザクション境界を作ると、境界の正本が 2 か所になり、
ロック保持区間も伸びる (関門の docblock が「$next() を transaction 内で実行する」ことの
適用条件を明記している)。

### [Warning] 観点 4: 「新たに拒否される設定は無い」の範囲 — 対応した

主張を「環境変数 → config という通常の宣言経路を通った設定について」に限定し、
config を直接差し替える経路からは正規形でない値を拒否する (意図した設計である) と明記した。
表による検査の分割 (宣言経路 / 検証器の直叩き) は詳細設計のテスト計画で行う。

### [Warning] 観点 7: 正規化結果を値オブジェクト / 結果型にする — 見送る (反論)

正規化器は**全域関数**であり失敗の場合分けを持たない (文字列を受けて文字列を返す)。
失敗の判定と分類は検証器の 1 か所に残るため、結果型を導入しても呼び出し側の分岐は
増えも減りもしない。むしろ「正規形かどうかを決める場所」が 2 か所に見えるようになり、
判定基準の割れを招く。失敗理由の提示は例外文の**位置表示** (許可する接続元の何番目か) で足り、
生値を出さない方針とも両立する。よって型を足さない (思考原則 2)。
