# 対応マトリクス: impl-review Round 1

全体判定 **APPROVED**。Warning 2 / Suggestion 2 (いずれも非 blocking)。

## [Warning] `copy()` の不変条件コメントが強すぎる

- 判断: **対応する**
- 根拠: 実装と契約 13 は「利用者が選び直した選択は成功後も奪わない」を許容しているので、
  「選択が残っているのは手動コピーを促している間だけ」は言い過ぎ。正しくは「**所有** Selection が」。
- 対応内容: コメントを「**この component が張った選択**が残っているのは、手動コピーを
  促している間だけ (利用者が自分で選び直した選択は、成功後も破棄時も奪わない)」に修正。

## [Warning] 契約 13 は再試行経路の観測であり、破棄経路の同ケースを直接見ていない

- 判断: **対応を試みたが、実測により撤回した** (追加せず、理由を記録)
- 経緯: 助言どおり「契約 17: 同じ code 内の部分選択は unmount でも奪わない」を書いたところ
  **赤くなった**。原因を jsdom で直接測ったところ、`host.remove()` の後に
  **所有 range と利用者の部分 range が両方とも `(BODY, 0)` の同一点へ畳まれる**ことが判明した
  (実測値は `implementation-notes.md`)。つまり破棄時には両者を区別できない。
- 判断の根拠: 区別できないだけでなく、**区別する必要が無い**。subtree の内側にあった選択は
  削除そのものによって失われており、そこで `removeAllRanges()` を呼んでも
  「既に畳まれた選択」を消すだけである。破棄時の所有判定が意味を持つのは
  **選択が削除される subtree の外にあるとき** (= 契約 12) だけで、そちらは緑かつ
  mutation M11 で赤化を実測済み。
- 対応内容: 契約 17 は**追加しない**。代わりに契約 12 のコメントへ、
  破棄時の所有判定が効く範囲 (subtree の外だけ) と実測の参照を書いた。

## [Suggestion] `removeAllRanges` の呼び出し有無を契約にすると実装 API に寄る

- 判断: **記録のみ** (対応不要)
- 根拠: jsdom では結果状態だけで契約を観測できないため、この形が現状の唯一の観測手段である
  (M14 の実測がそれを示した)。将来 `Selection.empty()` 等へ実装を変えるなら
  テスト契約の更新が要る、という指摘は `implementation-notes.md` の「保証しないもの」へ記録した。
