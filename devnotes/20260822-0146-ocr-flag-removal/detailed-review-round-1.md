# 全体判定: CHANGES_REQUESTED

中核となるコード変更の方向性は妥当です。画像は直接 OCR、PDF は対象理由に限って OCR フォールバックする既存契約が維持され、認可・DTO・LLM 防御経路にも変更はありません。

ただし、運用文書の時制が矛盾している点と、完全撤去を確認する検索・検証計画に不足があります。Critical はありませんが、以下の Warning を解消してから承認すべきです。

なお、指示に従ってコマンド実行・ファイル操作は行わず、提示された設計書のみをレビューしています。

## 施策 1: config からフラグ削除

判定: APPROVE

[Suggestion] 「リスクなし」は少し強すぎます。施策2・3より先に単独適用すると挙動不整合になるため、「standalone PR内での同時適用を前提とすれば追加リスクなし」と記載する方が正確です。

設定キャッシュに旧キーが残っても参照元がなくなるため実害はありませんが、デプロイ時の通常のconfig cache再生成は必要です。

## 施策 2: 受理形式の単一情報源を固定値化

判定: APPROVE

`imagesEnabled()` の撤去、固定集合化、承認済みラベルの固定値維持はいずれも妥当です。戻り値の `list<string>` も維持されています。

[Suggestion] テストでは包含確認だけでなく、次の公開結果を完全一致で固定すると「唯一の情報源」という役割をより正確に検査できます。

- `extensions()`
- `mimes()`
- `acceptAttribute()`
- `formatsLabel()`

特に拡張子だけでなく、sniff MIME集合も画像受理のセキュリティ境界です。

## 施策 3: AnalysisPipeline の route 決定を無条件化

判定: APPROVE

ロジックは整合しています。

- 画像は媒体検証前から `ocr`
- PDFはOCR対象理由と判定した時点で `ocr`
- 媒体検証自体が失敗しても正しいrouteで終端ログを残す
- OCR対象外のPDF失敗は再送出
- `$input === null` の失敗ログ契約も維持

媒体検証、容量制限、OCR対象理由、LLM実行経路を変更していないため、今回のスコープにも適合します。

## 施策 4: docblock 更新

判定: APPROVE

実装と説明のずれを解消するだけで、責務の記述も正確です。追加テストが不要という判断も妥当です。

## 施策 5: Inertia / Svelte props の撤去

判定: APPROVE

常時有効化後に真偽値propを残さず、条件分岐そのものを削除する設計は適切です。Inertia propsで画面描画用の文字列を渡す用途であり、API用DTO・JsonResourceを新設する必要もありません。

Atomic Design上の階層や依存方向も変わらず、DESIGN.md上の禁止されたdisabled UIも発生しません。

## 施策 6: バックエンドテストの畳み込み

判定: REQUEST_CHANGES

[Warning] 「公開面の一貫性」テストについて、説明されているassertionは主に `create()` / `show()` のInertia propsです。一方、テスト名は「FormRequest / Service / Inertia Propsが同じ受理形式」と、より広い保証を主張しています。

修正案:

- FormRequest、Service、Inertiaの各境界を実際に何で検査するか明記する。
- 既存のアップロード成功・MIME偽装拒否テストをFormRequest/Service側の根拠にするなら、その対応関係をテスト計画に明記する。
- 当該テスト自身がInertiaしか検査しないなら、テスト名を「create/show の Inertia Props が同じ受理形式を表す」などへ狭める。

「検査名が主張する範囲」と「実際の検出力」を一致させる必要があります。

また、「PestテストファイルなのでPHPStan対象外」とは設計書だけでは断定できません。`phpstan.neon` の走査対象に依存するため、「既存PHPStan構成に従い、対象ならlevel 10を満たす」としてください。

無効状態のテストを削除する判断自体は妥当です。存在しない状態を互換性として残す必要はありません。

## 施策 7: フロントテストの畳み込み

判定: APPROVE

常時表示される法務案内、画像込みaccept、画像込みhelp文面に一本化されており、削除されるのは旧無効状態だけです。

旧コンポーネントにpropsなしで新期待値を与えるため、OCR固有文面が表示されず赤になるというテストファーストの成立条件も明確です。

## 施策 8: rollout文書の更新

判定: REQUEST_CHANGES

[Warning] 「本文を過去形へ変える」という方針と、「本文自体はそのまま残す」という具体策が矛盾しています。現在形の環境変数設定・`config:cache`・falseへ戻す手順を残すと、見出しの注意を読み飛ばした運用者が現行手順として実行できます。

修正案:

- 見出しを「旧rollout手順（廃止済み・実行禁止）」とする。
- 本文もすべて過去形へ直すか、明確に「当時の計画を引用保存した非実行資料」として囲う。
- 「実際に踏んだ（または踏むはずだった）」は区別し、実施済み事実と未実施計画を混ぜない。
- 現在の障害対応手段を独立した現行節に記載する。

[Warning] 「問題発覚時は無効化コードを作って通常デプロイする経路のみ」という断定も不正確です。デプロイ基盤によっては直前リリースへのrollbackが可能です。

修正案:

「環境変数切替による即時停止はできない。復旧はデプロイrunbookに従ったリリースrollback、または無効化patchのデプロイで行う」としてください。rollbackを保証できない環境なら、その制約を明示します。

また、リポジトリ外の本番環境・Secret管理に `MANUAL_OCR_ANALYSIS_ENABLED` が残っている可能性は別途扱うべきです。アプリから見れば無害ですが、完全撤去の運用作業として、管理主体と削除確認方法を記録してください。

## 施策 9: architecture更新

判定: APPROVE

現在の実装状態、撤去理由、履歴の参照先が区別されています。OCR仕様自体を変更したようにも読めず、適切です。

施策8の修正後は、ここから参照するrollout文書が明確に「履歴」と「現行対応」を区別していることも確認してください。

## 施策 10: 残存確認

判定: REQUEST_CHANGES

[Warning] `git grep` は原則としてGit追跡ファイルしか検査しません。通常は未追跡・ignore対象となる `.env` や `.env.local` を含めて「ゼロ件」と判断することはできません。

修正案:

- 追跡ファイルは提示された `git grep` で確認する。
- ローカルの `.env*` は、hidden/ignore対象を含める別の読み取り検索で確認する。
- 本番環境や外部Secret管理はリポジトリ検索の保証外として、施策8の運用確認へ分離する。

[Warning] 検索語が不足しています。現在の条件では、公開メソッド `imagesEnabled()` やローカル変数 `$ocrEnabled` が死んだコードとして残っても検出できません。PHPStanも未使用の公開メソッドを必ず検出するとは限りません。

修正案として、少なくとも次も残存確認へ加えてください。

- `imagesEnabled`
- `ocrEnabled`
- フラグの有効・無効を前提にしたテスト名やコメント

履歴文書で許可する一致と、実行コード・テストで禁止する一致は分けて結果を記録してください。

[Warning] PR完了条件に、AGENTS.mdが要求する全検証コマンドが揃っていません。

修正案として、完了条件へ以下を明記してください。

- `composer test`
- `composer phpstan`
- `vendor/bin/pint --test`
- `pnpm lint`
- `pnpm typecheck`
- `pnpm test`
- `pnpm build`
- `pnpm typecheck:packages`
- `pnpm build:packages`
- `pnpm test:packages`

恒久的な「旧フラグ文字列禁止」Architecture gateを新設しない判断は妥当です。これは継続的なドメイン不変条件というより、撤去PRの移行完了条件だからです。ただし、常時有効という実際の挙動はFeature/Unitテストで継続的に固定する必要があり、本設計は概ねそれを満たしています。

## セキュリティ・波及変更の総評

今回の変更で新規route、変更系endpoint、tenant境界、入力由来ID、外部URL取得は増えません。したがって認可・IDOR・SSRF inventoryの追加は不要です。

OCR媒体がLLMへ渡る経路についても、既存の `PromptDefense` → `GuardedPrompt`、媒体検証、容量上限、失敗契約を変更しない前提なら新たなコード上のセキュリティ後退は見当たりません。主な残余リスクは、フラグ撤去によって即時停止手段がなくなる運用リスクです。これは施策8で正確な現行対応手順に落とし込む必要があります。
