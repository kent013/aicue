- 全体判定: CHANGES_REQUESTED

1. 使命との整合性

- [Suggestion] 画像・スキャン SOP を常時受理可能にすることは、既存手順書を起点にするという使命と直接整合します。利用者が機能フラグの状態を意識せず取り込める点も「思考ゼロ」に寄与します。

2. 禁止事項違反

- [Warning] OCR の実行経路・プロンプト・防御機構を変更しない前提なら、LLM の Prism 直呼びや prompt 直書きには抵触しません。ただし `AnalysisPipeline` の分岐整理時に既存の `PromptDefense → GuardedPrompt` 経路を迂回しないことを明示すべきです。  
  修正提案: 実装受入条件に「OCR 経路の `LlmCallContextData`、`PromptDefense`、`GuardedPrompt`、応答検査の呼び出し構造は不変」を追加してください。

3. 実現可能性

- [Suggestion] Laravel の設定・サービス・Inertia props と Svelte 表示条件を一本化する変更であり、Laravel 12 + Svelte 5 + Inertia.js で問題なく実現可能です。常時 `true` の props を削る判断も適切です。

4. 期待効果の妥当性

- [Warning] 「コード単純化」は合理的ですが、`AnalysisPipeline` の分岐削減は OCR 経路の実行回数増加を伴います。外部送信量、LLM/OCR コスト、失敗率、処理時間は変わり得ます。これは機能フラグ撤去の妥当性を否定しませんが、「無条件有効化はリスクではない」と断定するのは不正確です。  
  修正提案: 期待効果とは別に、常時有効化後に確認する既存観測値（OCR 実行件数、失敗理由、処理時間、コスト）を明記し、値の調整ではなく挙動確認を初回デプロイ後の運用条件にしてください。

5. リスク

- [Critical] 画像内 prompt injection の手動評価は「未実施」であり、例外決定は残余リスクを消すものではありません。フラグを完全撤去すると、問題発見時に即時停止する運用手段も失われます。特に、画像・スキャン PDF の内容が外部 LLM に渡る経路である以上、誤誘導・情報流出・分析失敗増加時の対応を、単に「意図された帰結」として扱うのは不十分です。  
  修正提案: `docs/rollout-checklists.md` と `docs/architecture.md` に、以下を明記してください。
  - 手動評価未実施は「合格」ではなく、責任者による例外受容であること
  - 緊急停止フラグは存在しないこと
  - 問題発生時の復旧方法は、修正またはリバートを含む通常デプロイであること
  - 項目 3 の再評価トリガーと責任主体

- [Warning] OCR 固有の外部送信注意文言を常時表示にする方針は妥当ですが、画像だけでなく OCR フォールバック対象となるスキャン PDF についても、利用者への説明が実態と一致することを確認する必要があります。  
  修正提案: 注意文言の対象を「画像」だけに限定せず、「アップロードした SOP の内容が OCR/AI 分析のため外部処理される場合がある」等、PDF OCR フォールバックを含む実際の送信範囲に合わせてレビューしてください。

6. スコープの適切さ

- [Suggestion] フラグ機構だけを撤去し、OCR の受理形式・容量上限・プロンプト・失敗契約を変えない境界は適切です。他フラグへの一般化をスコープ外にした判断も良いです。

- [Warning] 「grep による全数列挙」は設計時の探索根拠として有用ですが、削除完了の保証には弱いです。env テンプレート、テスト設定、デプロイ設定、ドキュメント、フロント型定義などに残存する可能性があります。  
  修正提案: 受入条件として、`MANUAL_OCR_ANALYSIS_ENABLED`、`ocr_analysis_enabled`、`imageSourceDocumentsEnabled` の残存をそれぞれゼロ件にする静的な確認を追加してください。残すべき履歴記録に名称が必要なら、現役設定として誤認されない記述へ置き換えてください。

7. 型安全性

- [Suggestion] prop を削除し、Svelte 側の条件分岐を常時表示へ畳むため、DTO/JsonResource の型を不必要に緩める必要はありません。PHPStan level 10 と TypeScript の型検査に適した変更です。

- [Warning] Inertia props を削除する場合、共有 props・ページ props・Svelte の `$props()` 型・テスト用 props fixture の全てを同時に更新しないと、未使用プロパティや欠損プロパティが残ります。  
  修正提案: 実装受入条件に、バックエンドの props 定義、フロントの props 型、コンポーネントテスト fixture を一括で削除し、PHPStan・TypeScript typecheck・該当 Feature/UI テストを通すことを追加してください。

追加で、テストファーストの原則に沿って、まず「設定・env・Inertia prop が存在しない」「画像と OCR フォールバックが常時有効」「注意文言が常時表示」の失敗テストを置き、その後に実装する手順を設計へ明記すれば承認可能です。
