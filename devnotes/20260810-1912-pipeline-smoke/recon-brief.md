# 実査ブリーフ: パイプライン通し確認の自動化 (pipeline smoke)

## オーナーの指示 (設計の前提。逸脱不可)

> 「品質云々より、**プロセスが回るか**に重みを置いて、動作確認を自動化したい。
>  サンプルファイルとかも適当なデータでいい」

- **目的は品質評価ではない**。SOP 投入 → AI 解析 → シナリオ → 撮影テイク → ffmpeg 合成 → mp4
  の**全段が通ること**を機械で確認するのが目的。生成されたシナリオの中身の良し悪しは**問わない**。
- 入力は**ダミーで良い**。SOP は数手順の小さなテキスト、テイクは ffmpeg で生成した数秒のクリップで良い。
- **置き場所: bug-hunt レーン** (オーナー決定)。
- **LLM は 3 段すべて実呼び出し** (オーナー決定)。パイプラインが本当に回るかを見るのが目的なので、
  途中を fake にすると確認にならない。

## なぜ通常のテストレーンに置けないか (制約)

aicue:T130 で**テストレーンは HTTP 出口を既定拒否**にした (`StrayHttpRequestGuard`)。
実 LLM を呼ぶ通し確認を `composer test` に入れると、この既定と正面から衝突する。
したがって**別レーン**に置くのが正しい。

## 使える基盤 (実在を確認済み)

- **bug-hunt レーンは既定で実 LLM**。`scripts/bug-hunt-shard.sh` が `--real-llm` を既定とし、
  親 `.env` の `ANTHROPIC_API_KEY` を **serve/worker プロセスにだけ**注入する
  (未設定なら fail-fast)。`MODE_ENV` はフラグのみで秘密を載せない分離になっている。
- **fake storage が実バイトを置く**。`FakeTakeObjectStorage` は `TakeObjectStorage` を継承し、
  presigned PUT を署名付き route + `s3_fake` disk で emulate する。`FakeObjectStore::storeStreamed()`
  はストリームで sha256 を検証しながら実ファイルへ書く。**したがって ffmpeg がそのまま読める**
  = 実 S3 なしで合成まで通せる。
- `ffmpeg 7.1.5` / `ffprobe` が環境に実在する (`/usr/bin/`)。
- 隔離: DB `bug_hunt(_N)` / port `:8010` (直列) / 用途別 wrapper (`env -i` で親の DB_* を遮断)。

## 現状 (実在を確認済み)

- 中核 3 段のプロンプトは実在: `resources/prompts/{sop-extract,work-decomposition,scenario-generation}.yaml`
  と `app/Prompts/` の対応クラス。
- `app/Services/Manual/AnalysisPipeline.php` (533 行) が extract→decompose→generate→finalize。
  有界リトライ・preflight 所有権再検証・チケット 2 フェーズを持つ。
- `app/Services/Manual/RenderPipeline.php` (481 行) が scenario_version 固定 → DL → compose → upload → published。
- `app/Services/Render/FfmpegVideoComposer.php` (288 行) が ASS 字幕焼き込み・素材未撮影時の黒背景・
  音声欠落テイクへの anullsrc・concat demuxer。
- **smoke 的なコマンドは 1 本も無い** (`app/Console/Commands/` に該当なし)。
- seeder は `BughuntOAuthSeeder` / `BughuntBillingSeeder` / `ManualTestSeeder` が実在。

## 設計で決めるべきこと

1. **入口の形**。artisan コマンドか、bug-hunt スクリプトのサブコマンドか。
   オーナーは「bug-hunt レーンに乗せる」と決めたが、**実体をどちらに置くか**は設計判断。
   コマンドにして bug-hunt から呼ぶ形なら、将来 bug-hunt 以外からも使える。
2. **同期実行の方法**。`RunManualAnalysis` / `RunManualRender` は `ShouldQueue`。
   worker を待つのか、パイプラインを直接呼ぶのか。**待つなら timeout と失敗の見分け方**が要る。
   なお aicue:T137 で dispatch は業務 tx 内へ移設済みなので、その前提を壊さないこと。
3. **ダミー素材の作り方**。SOP テキストと、テイク動画 (ffmpeg で生成)。
   **リポジトリに動画バイナリを置かない** (生成する) 方針を推奨するが、設計者が判断してよい。
4. **合否の判定基準**。「回った」を何で判定するか。
   最低限: 各段が期待する状態へ遷移したか (`analyzing→ready`, `rendering→published`)、
   cuts が 1 本以上生成されたか、mp4 が生成され `ffprobe` で読めて尺が 0 でないか。
   **品質は見ない** (字幕の内容や語尾は判定しない)。
5. **失敗したときに原因が分かる出力**。段ごとの所要時間と、どの段で落ちたか。
   実 LLM は落ちうる (レート制限・スキーマ不一致・タイムアウト) ので、
   **LLM 起因の失敗と配線の失敗を見分けられる**こと。
6. **課金の扱い**。実 LLM を 3 段呼ぶので 1 回叩くたびに費用が出る。
   誤って連打しない仕掛け (確認 or 明示フラグ) が要るかを判断する。
   チケット台帳も消費する (解析 1 枚 / レンダ 3 枚) ので、残高の用意も要る。

## やらないこと

- **品質評価の自動化はしない**。生成物の良し悪しを判定する仕組みは作らない (オーナー指示)。
- **実 S3 配線はしない**。`--real-storage` は `scripts/bug-hunt-shard.sh` 自身が
  「実 S3 配線は未実装 = inert トグル」と書いている。fake storage で足りる。
- **ブラウザ操作は含めない**。撮影 UI の実機確認は別件 (aicue:T085 と同じ領域)。
  本件は CLI で通る範囲に閉じる。

## 追加のオーナー指示 (2026-08-10): コストレポート

> 「コストは知りたいんで、**spirux や aigenba と同じようにコストレポート作って**ね。」

### 前提 (実在を確認済み)

aicue は**呼び出し単位のコスト記録は既に持っている**。

- `llm_call_logs` テーブル (`database/migrations/2026_06_11_090000_create_llm_call_logs_table.php`) が
  `provider` / `model` / `finish_reason` / `step_count` / `input_tokens` / `output_tokens` /
  `cache_write_input_tokens` / `cache_read_input_tokens` / `thought_tokens` /
  `input_cost_usd` / `output_cost_usd` / `total_cost_usd` / `pricing_snapshot` / `fx_snapshot` /
  `total_cost_jpy` を持つ。
- `app/Services/LlmCallLogWriter.php` が記録し、`app/Filament/Resources/LlmCallLogResource.php` が
  管理画面に出している。

**足りないのは集計してレポートする側**である。

### 設計で決めるべきこと (コストレポート)

7. **家系の先例に揃える**。`ToolSearch` で `mcp__lctl__get_feature` を読み込み、**spirux / aigenba が
   どういうコストレポートを持っているか**を台帳で確認すること (feature id の候補: `llm-batch-billing`
   など。正確な id は台帳を引いて特定する)。**独自形式を発明せず先例に揃える**のが指示の主旨。
   先例が見つからない場合はその旨を設計に明記し、最小形を提案する。
8. **本 smoke との関係**。この通し確認は実 LLM を 3 段呼ぶので、**1 回の実行にかかった費用が
   その場で分かる**のが自然。レポートを「smoke 実行の出力の一部」として出すのか、
   独立したコマンド (期間集計) にするのか、両方かを決める。
9. **粒度**。呼び出し単位 / プロンプト種別 (sop-extract / work-decomposition / scenario-generation) 単位 /
   マニュアル単位 / 組織単位 / 期間単位。**smoke の用途に必要な粒度**と
   **運用で知りたい粒度**は違うので、両方を満たす形を考える。
10. **通貨**。`total_cost_usd` と `total_cost_jpy` の両方が記録されている
    (`fx_snapshot` つき = 記録時点のレートを保存している)。レポートでどちらを主に出すか、
    為替の扱いをどうするかを決める。

### やらないこと (コストレポート)

- **課金機能ではない**。利用者へ請求する仕組み (llm-batch-billing の本体) は本件の範囲外。
  本件は**開発者・運営者が費用を把握するための可視化**である。
- 価格表の自動追随はしない (`pricing_snapshot` が記録時点の価格を保存しているので、
  過去分の再計算は不要)。

## 追加のオーナー指示 (2026-08-10 その 2): 集計は小さく、仕組みは統一して還流する

> 「集計システムは**そんなにデカくなくていい**んですよ。DB に入るから、**ちゃんと設定して集計するだけ**
>  なんで。その辺わきまえて**あんまりオーバーエンジニアリングにならないように**気をつけて
>  **統一的なレポートの仕組み**を作って**還流**させてください。」

### この指示による設計の方向転換 (前回設計からの差し戻し)

前回の詳細設計は集計層が膨らみすぎていた。オーナーの指摘は正しい。**以下のとおり作り直す。**

#### (A) 「ちゃんと設定して」= 記録側を直すのが先

前回設計は `withMetadata()` 未呼び出しを**スコープ外**とし、
`metadata_missing` 件数を出して可視化するに留めた。**これは順序が逆である。**

記録側が組織・対象を落としている状態では、いくら集計層を作っても**出せる軸が段とモデルだけ**で、
運用で本当に知りたい「どの組織が / どのマニュアルが いくら使ったか」が永久に出ない。
**集計を小さくできるのは、記録が正しく入っているからこそ**であり、そこを直さずに
集計層で取り繕うのは本末転倒である。

→ **`withMetadata()` の配線を本件のスコープに入れる**。`AnalysisPipeline` の 3 プロンプトが
   組織 / 対象 (マニュアル) / 段 を記録するようにする。これが「ちゃんと設定して」の実体。

#### (B) 集計層は薄くする

前回設計は 集計サービス + DTO 2 本 + enum + コマンド の 5 点構成だった。**GROUP BY 1 本に対して重い。**
**load-bearing でないものを削る。** 判断基準は「消しても保証が減らないなら消す」。

- 集計結果の DTO を 2 段にする必要があるか (行と全体) を再検討する
- group-by の enum が要るか、コマンドの入力検証で足りるかを再検討する
- サービスクラスが要るか、Model の scope / query 1 本で足りるかを再検討する

**ただし削りすぎない**。このリポジトリは DTO を規約にしている (AGENTS.md 禁止事項 4) ので、
**規約に反してまで削らない**。削ってよいのは「規約が要求していないのに足したもの」である。

#### (C) 「統一的なレポートの仕組み」= 1 実装・複数入口

smoke 用と運用用で**2 つ作らない**。1 つの集計を、
- smoke の末尾 (この実行分)
- 期間集計のコマンド

の 2 入口から使う。この方針は前回設計にもあったので**維持する**。

#### (D) 還流を前提に設計する

**台帳を引いた結果、LLM コスト集計レポートは家系のどのリポジトリにも無い** (前回調査で確認済み)。
共有されているのは記録層 `llm_call_logs` の語彙までである。

→ **この実装は家系初になる。他リポジトリがそのまま持っていける形で作ること。**
   具体的には:
   - **aicue 固有の概念に依存しない**。マニュアル / カット / 撮影といった aicue のドメイン語彙を
     集計層に持ち込まない。集計層が知ってよいのは `llm_call_logs` の列だけ。
   - 対象 (subject) は**多態で持つ**。aicue はマニュアルだが、他リポジトリは別のものを指す。
   - **記録層の列を増やさない**。既存の `llm_call_logs` で足りる設計にする
     (増やすと他リポジトリが migration ごと持っていく必要が出る)。
   - 還流のとき何を渡せばよいかが分かるよう、**移植に必要なファイルの一覧**を設計に書く。

### 還流の手順 (実装後)

1. コスト集計レポートに相当する feature は台帳に無いので、**`/lctl-curate --add` で起票を依頼する**
   (新規 feature の起票はキュレーター専権であり MCP からはできない)。
2. 起票されたら `status_reported` を出す。その際、**他リポジトリが移植するのに必要な情報**
   (移植対象ファイル / 前提となる記録層の列 / aicue 固有部分の切り離し方) を本文に含める。

### 変わらないこと

- pipeline smoke 本体 (実 LLM 3 段・bug-hunt レーン・品質は判定しない) の方針は**前回設計のまま**。
- 費用の見積り ($0.078〜0.114 / 回) と、誤って連打しない仕掛けも**そのまま**。
