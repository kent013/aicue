# 概念設計: bfcache-session-generation-cookie

対象: lctl feature `authenticated-no-store-bfcache` の未反映 2 点 (家系裁定 AG-029b / 補正済み標準形 t1)。

## 背景・課題

### 何が未反映なのか

台帳 (観測点 `aicue@8f0dddd` 実読、feature_revision 24) は、AG-029b が求める 4 点のうち
2 点は別の形で満たされていると判定し、残る未反映を 2 点に絞っている。

1. **理由記述の差し替え** — `NoStoreCacheHeadersForAuthenticatedPages` の説明文が
   「他のブラウザは保存禁止ヘッダで塞げるが特定ブラウザだけが例外」という枠組みで書かれている。
   家系の裁定はこの理由記述を誤りとして補正済みで、実測に合わせた記述へ差し替える必要がある。
2. **通信を待たない同期判定の前置** — ガードには世代 cookie を読む経路が無く、
   復元時は必ずプローブへ問い合わせてから判定する。

あわせて持たない 4 点として、セッション世代 cookie とその供給元 / 契約ずれの検査 /
文書の期限検査 / 実機受入の手引き が挙げられている。

### 未反映 2 点の裏に実在する穴 (本設計の主目的)

台帳の項目名だけを追うと「速くする話」に見えるが、現行コードを実読すると
**復元後に他人の画面を開示しうる経路が残っている**。

現在の秘匿ガード (`resources/js/lib/bfcache-guard.ts`) が開示を決める根拠は、
プローブ `/session/status` が返す `authenticated` の 1 ビットだけである
(`app/Http/Controllers/Auth/SessionStatusController.php` は
`$request->user() !== null` をそのまま返す)。この 1 ビットは
**「いま誰かがログインしているか」しか答えない**。したがって:

> 利用者 A の認証済み画面が bfcache に入る → A がログアウトし、同じ端末で B がログインする
> → 「戻る」で A の画面が復元される → プローブは `authenticated: true` を返す
> → ガードは秘匿を解除し、**A の個人情報が B に見える**。

共有端末は撮影 PWA の想定利用環境そのもの (現場で端末を持ち回る) であり、
この経路は使命に直結する。**世代の印は速さのためではなく、この穴を塞ぐために要る。**

### なぜ「同期判定の前置」が要るのか

**本設計の主目的は漏えい防止であり、速さではない。** 上の穴は「開示の根拠に世代の一致を足す」
だけでも塞げる。同期判定の役割はそこに乗る **fail-closed の早期分岐**であり、次の 2 つを足す:

- 世代が変わっていることは往復を待たずに確定できる (= 開示しないと決めるのが早い)。
  復元のたびに必ず 1 往復する現状より秘匿オーバーレイの滞在が短くなるのは**副次効果**である。
- 判定材料が「cookie (同期)」と「プローブ応答 (通信)」の 2 系統になり、
  **どちらか片方が古くても開示側には倒れない**構造になる
  (同期側は開示を決められないので、材料が増えても開示は増えない)。

## 改善アイデア

### 全体像 — 4 層のうち足りない 2 層を足す

| 層 | 現状 | 本設計 |
|---|---|---|
| 1. 認証状態で判定する保存禁止ヘッダ | 実在 (変更しない) | 説明文だけ差し替える |
| 2. セッション世代の印の供給 | **無い** | cookie (同期読み取り用) と Inertia 共有 prop (描画世代) を同一の出所から出す |
| 3. セッション生死のプローブ | 実在 (`authenticated` のみ) | 要求が運んだ印を受け取り、**現セッションの世代と一致するか**も答える |
| 4. 復元時の秘匿ガード | 実在 (プローブ必須) | 同期判定を前置し、開示の根拠は「認証済み **かつ** 世代一致」だけにする |

### 印の 2 つの運び方と責務分離 (混同すると設計が壊れる)

同じ値を 2 経路で運ぶが、**役割は交わらない**。

| 運び方 | 何のためか | 誰が読むか | 開示の根拠になるか |
|---|---|---|---|
| **Inertia 共有 prop (描画世代)** | いま画面に出ている内容が、どのセッション世代の応答で来たかを内容と同じ 1 通で運ぶ | 画面側 (ガード) が同期に読み、プローブ要求のヘッダへ載せる | **なる** (サーバがこれと現世代を照合する) |
| **cookie (現世代の写し)** | 通信を待たずに「世代が変わった」と分かるようにする | 画面側 (ガード) だけ | **ならない** (不一致を検出する側にしか使わない) |

**プローブへ送る比較対象は cookie ではなく、復元された文書が保持する描画世代**である。

### 核心の不変条件 (これを守る設計にする)

- **同期判定は「開示しない」側にしか到達しない。** 開示の根拠はプローブ応答ただ 1 つで、
  cookie は開示側の分岐に現れない。cookie が古くても新しくても開示は増えない
  (前置は保守的なふるい分けであり、判定の置き換えではない)。
- **サーバの一致判定は、要求ヘッダで運ばれた描画世代とサーバが導出した現世代だけを見る。**
  要求の Cookie ヘッダに載ってくる世代 cookie の値は**一致判定に使わない**
  (画面側から書き換えられる値であり、開示の根拠に混ぜない)。
- **cookie の改ざん・欠落から到達できるのは「秘匿維持」と「読み直し」だけ**である
  (偽の一致を作っても、その先はプローブの照合が待っている)。
- **描画世代は内容と同じ応答で運ぶ。** 印を「cookie を読んだ時刻の値」として持つと、
  別タブが cookie を書き換えた瞬間に「内容は A・印は B」になりうる。
  Inertia の応答は内容と印を同じ 1 通で運ぶので、この取り違えが構造的に起きない。
- **失敗はすべて秘匿維持へ倒す。** 印が無い / 読めない / 判定不能はすべて
  「開示しない」であり、既存の fail-closed (プローブ失敗 → 秘匿維持 + 再試行) を弱めない。
- **秘匿の終端は「同じ URL の読み直し」に統一する。** 読み直した先は復元ではないので
  必ず秘匿が解け、**1 つの文書につき読み直しは高々 1 回**でループにならない。

### 具体的な変更

1. **世代の印の供給元を 1 つ作る** (`App\Support\Auth\SessionEpoch`)。
   セッション ID から鍵付きハッシュで導出する (セッション ID そのものは画面側へ出さない)。
   値は **32 文字の 16 進文字列**に固定し、「無い」(null) と「空文字」を同一視しない。
2. **cookie で配る** (`IssueSessionEpochCookie` middleware)。画面側から読める必要があるため
   暗号化対象から外す。web グループの append 列 (= `StartSession` より内側) に置き、
   短絡しない middleware として目録へ登録し、優先順位一覧の鎖へ 1 リンク足す。
   値は **`$next` の後に、応答時点のセッション ID から導出**して載せる
   (ログイン・ログアウトでのセッション ID 再生成を拾うため)。
   **未認証でも発行し、削除しない。必ず応答時点のセッション ID 由来の値で上書きする**
   (「無い」状態を作らない。ログアウト応答では未認証セッションの世代へ入れ替わる)。
3. **描画世代を Inertia 共有 prop で配る** (毎応答に載せる)。同一文書内でログインが完了する
   経路 (Inertia のクライアント遷移) でも印が置き去りにならない。
4. **プローブを拡張する**。要求ヘッダが運んだ描画世代と現セッションの世代を照合し、
   `authenticated` と `sessionEpochMatches` の 2 つを返す
   (既存の DTO + JsonResource を拡張し、top-level・data ラップなしの shape を維持する)。
5. **ガードに同期判定を前置する**。印と cookie が食い違う / どちらかが無いときは
   **通信を待たずに**秘匿したまま読み直す。一致したときだけ従来どおりプローブへ進み、
   `認証済み かつ 一致` のときだけ秘匿を解く。
6. **説明文を実測に合わせる**。ブラウザ名で例外を作る書き方をやめ、
   「保存禁止ヘッダは bfcache への格納を禁じる指示ではない」という事実に置き換える。
7. **検査を足す** — 言語をまたぐ名前・語彙の契約ずれ検査と、対応ブラウザ方針の文書の期限検査。
   契約ずれ検査は PHP 側 (供給元クラスの定数 / 共有 prop のキー / 応答フィールド名) と
   画面側 (ガードの定数・応答パーサ・検証ページの状態語彙) を**同じ契約名から**突き合わせる。
   期限検査の目的は「**実機再確認と一次情報の再確認が未実施のまま忘れられるのを防ぐ**」ことで、
   保証しないもの (確認日は自己申告であり、日付を更新しても内容の正しさは担保しない) も併記する。

## 期待効果

- **使命への貢献**: 共有端末で端末を持ち回る現場運用において、
  「戻る」で前の作業者の個人情報が次の作業者に見える経路を塞ぐ。
  撮影 PWA の主戦場 (iOS Safari) は復元が実際に起きる環境であり、
  ここは自動回帰では再現できていないため設計で閉じるしかない。
- **UX**: 世代が変わっている復元は往復を待たずに読み直しへ倒れるため、
  秘匿オーバーレイの滞在時間が短くなる。正常な復元 (同一セッション) の挙動は変わらない。
- **家系への追従**: 未反映 2 点が閉じ、持たない 4 点のうち 3 点 (世代 cookie と供給元 /
  契約ずれの検査 / 文書の期限検査) が埋まる。

## 制約・前提

- **既存の fail-closed を弱めない**。プローブ失敗は今までどおり秘匿維持 + 再試行で、
  自動再試行はしない。**cookie を偽の値に書き換えても開示に至らないこと**を
  画面側 (vitest) とサーバ側 (Feature) の両方で固定する。
- **`popstate` は扱わない**。経路 C は Inertia 公式機構の担当で、
  `bfcache-guard.ts` の説明文がフックを足さない理由まで書いている (設計フェーズで却下済み)。
- **管理パネル (`/admin`) は対象外**。web グループを経由せず Inertia でも描画されないため、
  ガードも共有 prop も届かない。この非対称は `docs/supported-browsers.md` に既に書かれている。
- **優先順位一覧は動かさない**。web グループへ middleware を 1 本足すため、
  `TenantBoundaryOrderingTest` の完全一致列と短絡分類の目録に登録が要る
  (どちらも「増えたら赤」の deny-by-default なので、登録が漏れると検出される)。
- **T161 の検証ページと連動する**。ガードの状態語彙が増えるため、
  検証ページの `GuardState` と軸 2 の終端も同時に更新しないと、
  T085 の実機確認で記録が拒否される。

## スコープ外

- **実機受入の手引き (runbook) は本設計では作らない。** 手順の正本は既に
  `docs/supported-browsers.md` の「実機受入確認の再確認条件」と「検証ページ」節にあり、
  実施そのものは **T085 (Open)** が持っている。別ファイルの手引きを新設すると
  同じ手順が 2 か所になり、同書が明記している「記録の二重管理を作らない」方針に反する。
  本設計は挙動変更を含むため同書の再確認条件のトリガに当たる = **T085 は本件のマージ後に実施する**。
  この順序と、検証ページの終端語彙が変わることを T085 側へ申し送る。
- **実機受入確認の実施そのもの** (T085 の責務)。
- **`/admin` (Filament) への秘匿ガードの導入**。
- **プローブへの流量制限レーンの新設** (現状 throttle 無しの契約を変えない)。

## 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| CSRF トークンの cookie を世代の印として流用する | 用途が違う値を「変わるタイミングが似ている」だけで統合することになる (思考原則 4)。トークンの再生成契機は CSRF 防御の都合で決まっており、世代の意味を担わせると片方の変更が無言でもう片方を壊す |
| 印を `<meta>` としてサーバ描画に埋める | 同一文書内でログインが完了する経路 (Inertia のクライアント遷移) で印が古いままになり、正常な復元まで読み直しになる。内容と同じ応答で運ぶ Inertia 共有 prop なら取り違えが起きない |
| 同期判定の一致だけで通信を待たずに開示する (家系の 3 リポジトリの形) | cookie は別タブから書き換わりうる client 側の状態であり、開示の根拠にすると「内容は A・印は B」の取り違えが残る。テンプレートの実装報告が同じ穴を 3 件挙げており、開示の根拠をプローブ 1 つに絞る形を採る |
| 世代不一致を `/login` への遷移で扱う | いま別の利用者がログインしている場合に嘘の着地になり、元の URL も失う。読み直しなら現在の利用者に対して正しい画面か `/login` かをサーバが決める |
| プローブの照合を持たず cookie の照合だけで済ませる | cookie は web グループ経由の応答でしか更新されないため、別の面 (管理パネル) でセッションが差し替わると古いまま一致してしまう。開示の根拠は cookie に依存しない側へ置く |
