全体判定: APPROVED

Round 1 の Critical / Warning はすべて概念設計レベルで解消されている。特に、描画世代と cookie の責務分離、サーバ照合から Cookie ヘッダを排除した点により、開示条件が明確になった。

## 1. 使命との整合性

[Suggestion] 共有端末で利用者 A の復元画面を利用者 B に開示しないことが主目的として明確になっている。撮影 PWA の実運用と直接結びついており、North Star への寄与は妥当。

## 2. 禁止事項違反

[Suggestion] 禁止事項への抵触は認められない。DTO + JsonResource の既存経路を維持し、Architecture / Feature / vitest まで検査対象としている。

実装完了条件には、記載済みの検査に加えて PHPStan level 10 と既定の全検証コマンドが green であることを含めればよい。

## 3. 実現可能性

[Suggestion] Laravel 12、Svelte 5、Inertia.js の範囲で実現可能。`$next` 後のセッション ID を cookie に載せる方針も、ログイン・ログアウト時の再生成を拾う目的に合っている。

詳細設計では、次を確定すると実装時の解釈差を防げる。

- epoch cookie の `path`、`domain`、`secure`、`sameSite`、有効期限
- セッション cookie と epoch cookie の適用範囲を一致させるか
- プローブ要求ヘッダの欠落、不正長、非16進文字列を照合前に拒否する方法
- `SessionEpoch` が使用する鍵と domain separation

## 4. 期待効果の妥当性

[Suggestion] 漏えい防止効果は合理的に期待できる。開示には、復元文書が保持する描画世代と、サーバが現在のセッション ID から導出した世代の一致が必要になるため、A から B へのセッション切り替えを検出できる。

UX 改善は副次効果として適切に格下げされており、効果の誇張も解消されている。

## 5. リスク

[Suggestion] 「読み直した先は必ず秘匿が解ける」は、ネットワーク障害や読み直し失敗まで含めると少し強い表現。詳細設計では、次のように保証範囲を限定するのが正確。

> 読み直しが完了して新しい文書が生成された場合、その文書は bfcache 復元マーカーを継承しない。

また、cookie の欠落や競合応答による古い値への巻き戻りは情報開示ではなく、保守的な再読み込みに倒れることをテストで固定するとよい。

## 6. スコープの適切さ

[Suggestion] セキュリティ修正、契約検査、実機再確認の失念防止までが一つの変更理由で結ばれており、過大ではない。T085 に実機確認を残し、手順書を二重化しない判断も妥当。

## 7. 型安全性

[Suggestion] `authenticated: bool`、`sessionEpochMatches: bool`、epoch を32文字の16進文字列として固定したことで、PHP / TypeScript 双方の契約は十分明確。

詳細設計では、PHP 側で生の `string` を広く流すのではなく、検証済み描画世代を表す Value Object または厳格な DTO 境界を置くと、PHPStan level 10 と入力検証の責務を揃えやすい。TypeScript 側も `unknown` から専用パーサを通してのみ応答型へ昇格させる形が適切。
