# 対応マトリクス: conceptual-review Round 1

## [Critical] readable cookie を照合に使うと client 状態が開示根拠に混入する
- 判断: 対応する
- 根拠: 指摘のとおり。cookie は改ざん可能な client 側状態であり、サーバの一致判定に混ぜると
  「開示の根拠は 1 つだけ」という不変条件が壊れる。設計の意図はそのとおりだったが、
  明文の不変条件になっていなかった。
- 対応内容: 概念設計に不変条件を 2 本追加した。
  (a) サーバの一致判定は **要求ヘッダで運ばれた描画世代とサーバが導出した現世代だけ**を見る。
      要求の Cookie ヘッダの値は一致判定に使わない。
  (b) cookie が改ざん・欠落しても到達できるのは「秘匿維持 / 読み直し」だけで、開示側へは倒れない。
  検査方針 (cookie を偽装しても開示に至らないことの vitest / Feature) も明記した。

## [Warning] 「速さ」と「漏えい防止」が混ざっている
- 判断: 対応する
- 根拠: 主目的は漏えい防止であり、同期判定は fail-closed の早期分岐にすぎない。
- 対応内容: 「同期判定の役割」を明示し、速さは副次効果である旨を書き分けた。

## [Warning] DTO / JsonResource 経路を維持し top-level shape を固定する
- 判断: 対応する
- 対応内容: 応答フィールド名を `authenticated` / `sessionEpochMatches` と確定し、
  既存の `SessionStatusDto` + `SessionStatusResource` (top-level, data ラップなし) を
  拡張する形であることを明記した。

## [Warning] middleware の配置が未確定
- 判断: 対応する
- 対応内容: 「`StartSession` より内側 (web グループの append 列)」「短絡しない middleware として
  目録へ登録」「優先順位一覧の鎖へ 1 リンク追加」「cookie は `$next` の**後**に、
  応答時点のセッション ID から導出して載せる (ログイン・ログアウトでの ID 再生成を拾うため)」を
  概念設計へ書いた。確定した列と鎖の位置は詳細設計で示す。

## [Warning] プローブへ送る比較対象が cookie 由来か prop 由来か曖昧
- 判断: 対応する
- 根拠: 指摘のとおり両者は役割が違う。
- 対応内容: 「プローブへ送るのは復元された文書が保持する**描画世代** (Inertia 共有 prop 由来)」
  「cookie は同期判定専用」と責務分離を表にした。

## [Warning] ログアウト直後の cookie 発行順序が曖昧
- 判断: 対応する
- 対応内容: 「削除しない。必ず**応答時点の**セッション ID 由来の値で上書きする」と契約を明記した。
  ログアウト応答では invalidate 後の新しいセッション ID が使われるため、
  未認証セッションの世代へ入れ替わる。

## [Warning] 文書の期限検査はスコープ膨張気味
- 判断: 対応する (目的を明確化して残す)
- 根拠: 家系の裁定 AG-029b が要求する 4 点の 1 つであり、本設計が触る文書
  (対応ブラウザ方針) には日付つきの一次情報と「原因未特定」の宿題が載っている。
  ここが陳腐化すると、実機再確認が未実施のまま忘れられる。
- 対応内容: 目的を「実機再確認と一次情報の再確認が忘れられることを防ぐ」と書き、
  期限検査が保証しないこと (自己申告であり内容の正しさは担保しない) も併記した。

## [Warning] TS 側 shape ガードと語彙の同期
- 判断: 対応する
- 対応内容: 「PHP の DTO / Resource / TS の応答パーサ / 検証ページの状態語彙を
  同じ契約名から検査する」ことを検査方針に追加した。epoch 値の型は
  「32 文字の 16 進文字列」に固定し、null と空文字を同一視しないことを明記した。
